管理员正常部署先读[管理员快速部署](管理员快速部署.md)，日常操作先读

逐条审计时，才按本文进入完整章节。安全审批和参数边界见

[开发者部署实现](开发者部署实现.md)。

公开手册中的账号、集群、VPC、子网、节点和 endpoint 均为变量或占位符。真实环境
取值与逐轮执行结果只保存在私有证据库。

## 一、先选阅读路线

### 路线 A：区域生产部署

正常路径先执行《管理员快速部署》中的
`deploy（内含 preflight）→ status --full → 训练验收`。
只有前置基础设施尚未准备时，才按
`0 → 1 → 2 → 3 → 4 → 5.1 → 5.3 → 5.4 → REG-8`
补齐详细步骤。这是当前唯一生产交付形态。

### 路线 B：历史单集群迁移

只在维护旧环境或迁移时阅读附录 A 和 §5.2。
单集群路径未经过区域形态同等级的完整验收，不用于新生产部署。

### 路线 C：区域数据面节点交付

REG-6 默认使用 Installer/Reconciler；无法运行特权 Job 时，阅读
§5.5。两者安装的是同一套 Collector/Node Agent。

### 路线 D：区域日常运维与故障处置

先从《管理员日常运维》的任务/症状索引进入对应 runbook；需要底层证据时再阅读
`REG-8～14、6、7、8、9、10、EFA/RDMA、Host 资源监控、异构 inventory、
配置管理与客户端身份约束`。不要为了排障临时扩大 allowlist 或关闭 fail-closed 门禁。

## 二、全局概念

- **绿地部署**：新环境首次建立 Aurora、NLB、Secret、schema、CPU/GPU 工作负载。
- **应用层 bootstrap**：共享 EKS、Aurora、ACM、subnet、SG 已存在，只部署本方案对象。
- **required pin**：稳态必须使用的 Agent artifact/config/protocol。
- **compatible pin**：只在滚动升级窗口临时接受的候选或旧版本。
- **fail closed**：证据、身份、版本或执行 owner 不完整时停止动作，而不是猜测。
- **三层控制面**：ingress 接收请求；control-worker 处理故障和 workflow；
  spool-worker 可选处理 routine telemetry。
- **区域 Executor**：运行在 GPU EKS，领取控制面 remote command 并操作本地
  Kubernetes、Node Agent 或 HyperPod API。

## 三、逐章解读

## 0. 使用顺序与目录

这是整份手册的入口，解决“应该走哪条部署路径”和“章节为什么交叉”的问题。

### 0.1 区域绿地部署总顺序

- **目的**：明确区域部署同时包含 AWS 基础设施层和应用层。
- **顺序**：测试 → CPU-1～3 → REG-1/2 → CPU-4 → CPU-5～9 →
  REG-3～8 → 两种训练提交 → 最终验收。
- **关键结论**：Aurora Serverless v2 和公网 TLS NLB 都是区域方案必需组件。
- **易错点**：低层 `rollout-regional-release.sh bootstrap` 只负责应用层；
  ARN-only `gpu-fault-admin deploy` 才会先自动创建当前站点独占的 Aurora、LBC/IAM、
  NLB/PKI 和监控资源；同站点标签对象只作为未清理遗留接管。

### 0.2 区域变量持久化与会话恢复

- **目的**：防止大量 shell 变量因断线丢失或被空值带入 `sed/aws/kubectl`。
- **做法**：将非敏感变量写入仓库外的 `0600 regional-env.sh`，每次登录重新 source。
- **Region**：由操作者显式填写，不从 shell 或 kubectl context 推断；CPU/GPU EKS ARN
  必须与该 Region 一致。
- **敏感值**：token、CA 私钥、fleet master、数据库口令只进入 Secret、
  Secrets Manager 或 `${SECURE_DIR}`。
- **通过标准**：变量、Region 和 EKS ARN 门禁全部成功，CPU/GPU `/readyz` 可访问。

### 0.3 保留 EKS 集群并重新安装

- **目的**：清空本方案状态后重新安装，同时只保留 CPU EKS 和所有 GPU EKS。
- **入口**：正常使用 `gpu-fault-admin uninstall --cpu-cluster keep`；底层
  `prepare-clean-redeploy.sh --mode reset --node-mode uninstall` 只用于 break-glass。
- **删除内容**：两侧方案 namespace/组件、节点安装、整个专用 Aurora Serverless v2、
  NLB/SG、ACM/PKI 和 LBC/IAM。
- **安全边界**：脚本不调用 CPU/GPU EKS 删除 API；发现仍被 quarantine 的 GPU
  节点会拒绝重置。Aurora 删除需要显式选择是否保留最终快照。
- **重部署入口**：回到 §0.1，CPU-2 重建 Aurora，CPU-3/5 重建 LBC/NLB，
  REG-3～8 在原 GPU EKS 重新安装。

### 0.4 永久退役方案

- **目的**：以后不再使用本方案。
- **删除内容**：CPU EKS/HyperPod、Aurora、NLB、IAM、监控和全部持久状态。
- **GPU 边界**：所有 GPU EKS/HyperPod cluster 必须保留，只卸载本方案组件。
- **入口**：`gpu-fault-admin uninstall --cpu-cluster delete`，Aurora 注册表先导出，
  非 Aurora 资源和 CPU 集群验证后才进入 Aurora 最终阶段。
- **入口**：REG-13；不要先执行 §0.3 reset，否则最终 Aurora 快照会失去审计数据。

## 1. 适用范围

- **目的**：定义唯一生产形态和非交付边界。
- **生产形态**：区域 CPU 控制面与一个或多个 HyperPod EKS GPU 集群分离。
- **非生产/未交付**：单集群只作历史过渡；通用 Kubernetes 未实现；
  systemd 是区域数据面安装方式。
- **关键结论**：区域控制面不能直接 apply `deploy/control-plane/base/` 的 renderer 输入，也不能在
  CPU 控制面集群运行单集群 `deploy.sh`。
- **示例资源**：示例 Region 名称、VPC、EKS 仅是已验证样例，不能复制到新环境。

## 2. 上线前决策

- **目的**：在创建资源前确定全局稳定身份和恢复责任。
- **必须决定**：`cluster_id`、Runtime Profile、Store、控制面 URL、DCGM endpoint、
  lifecycle owner、初始 operation allowlist。
- **关键原则**：HyperPod managed recovery 与本系统 mutation 不能成为双 writer。

### 2.1 上线前强制 Checklist

- **代码门禁**：`make check` 与真实 PostgreSQL 测试通过。
- **发布门禁**：release metadata 完整，compatible 字段稳态为空。
- **Secret 门禁**：execution token、processor replay secret、node action secret
  三者齐全且不同。
- **运行门禁**：退出预算、PDB、邮件/ADOT、Agent key version、collector readiness
  全部满足。
- **意义**：这一节是上线否决清单，不是建议清单；任一失败都不得发布。

### 2.2 区域生产方案硬约束

- HyperPod `NodeRecovery` 必须为 `None`。
- 本方案代码和执行角色永不调用 `BatchReplaceClusterNodes`，
  `GPU_FAULT_ALLOW_HYPERPOD_REPLACE` 恒为 `false`。
- 任务自动恢复必须禁用，训练恢复只由本方案负责。
- 当前只支持 HyperPod EKS，不支持 HyperPod Slurm。

## 3. 软件与网络前置条件

### 3.1 通用

列出 Python、PostgreSQL、NVIDIA driver、`nvidia-smi`、`/dev/kmsg`、Node Agent
9099、DCGM 9400 等最低依赖。这里失败时不应继续创建 Kubernetes 对象。

### 3.2 稳定私有 DNS、公网 NLB 与私有 CA

- **目的**：在 GPU VPC 与 CPU VPC 分离或 CIDR 冲突时，通过公网 NLB + NAT
  建立受限 TLS 通道。
- **要求**：证书 SAN 必须覆盖稳定私有 hostname；CNAME 只在 NLB active、原始
  DNS 可解析且 target healthy 后发布。GPU Pod 必须使用私有 CA 完成
  DNS/TLS/`/healthz` 验证；禁止 `curl -k`。
- **边界**：CA 私钥不进入 Kubernetes ConfigMap；GPU 数据面只拿 CA 公钥。

### 3.3 HyperPod EKS

核对 AWS CLI、kubectl、Helm、IAM、EKS 子网、Load Balancer Controller 权限和
HyperPod HMA/DCGM。CPU/GPU context 必须显式指定。

### 3.4 方案组件镜像与客户训练镜像的边界

- **方案镜像**：Python runtime、节点安装 Job、DCGM Exporter、ADOT。
- **训练镜像**：完全由客户 workload 决定，不由控制面替换。
- **企业镜像**：通过四个 `GPU_FAULT_*_IMAGE` 变量统一镜像或固定 digest。
- **关键结论**：业务版本由内容寻址 wheel 决定，不由 Python base image tag 决定。

## 4. 构建与测试

- **目的**：由CI得到一份签名的deployable schema v3 release，其中包含独立wheel/
  bundle、渲染摘要、依赖lock、Node template和不可变OCI image digest。
- **门禁内容**：Ruff、全量 mypy/Mixin 契约棘轮、compileall、
  architecture ratchet、deploy 布局、
  bash/ShellCheck、环境变量参考、用例索引、generated config、artifact consistency、
  全量 pytest。
- **PostgreSQL**：使用 CAP-005 runner 创建隔离 PostgreSQL 16 database，执行
  8×40 锁竞争、completion concurrency 2/4、counter/fencing/deadlock 测试并要求
  JUnit 零 skip；`make check` 本身不会连接外部数据库。
- **制品纪律**：`make check`验证source-only制品；`release-build`push OCI后生成并签名
  deployable Manifest，部署机只验签和应用。构建固定时间戳和
  归档顺序，同一源码重复构建必须得到相同组件 SHA 和 release ID。

## 5. 区域分离生产部署（唯一生产形态）

该章把 CPU 控制面、GPU 数据面、训练任务和节点交付放在一个连续编号下，是新生产
环境唯一需要执行的部署主章。

### 5.1 区域 CPU 控制面绿地部署

这是区域模式的 AWS 基础设施和 CPU 应用层 runbook。

| 章节 | 解读 |

### 5.2 从集群内控制面迁移到区域控制面

- **目的**：把原 GPU EKS 内的一体化控制面迁到独立 CPU EKS。
- **顺序**：先建区域控制面和数据面凭据，再停旧 writer/Service/Secret。
- **核心风险**：双控制面同时写 Aurora、旧 execution token 残留、旧 Service 继续接流量。
- **通过标准**：GPU 集群只保留数据面组件，区域控制面成为唯一事实源。

| `REG-14.7 HyperPod reboot 报 "unknown outcome" 或 "already reserved"` | 查 reboot provider 观察窗口、幂等键和真实 CloudTrail 结果；provider replace 恒禁用。 |

### 5.4 区域数据面训练任务提交与验收

训练 workload、Completion Watcher 和 Cluster Executor 都位于 GPU EKS，CPU 控制面
只接收 observation、terminal event 和故障事件。

#### TRAIN-1. 使用统一训练提交命令

- **直接提交**：`gpu-training-submit` 注入元数据后调用 `kubectl apply`。

##### TRAIN-1a. 先注入 YAML，再单独提交

`gpu-fault-workload-annotate` 只生成 YAML，
  适合审批、扫描、GitOps 和 server-side dry-run。

##### TRAIN-1b. 客户自定义训练镜像

系统不修改 image/command/args；客户负责 CUDA/NCCL/EFA、
  pull Secret、资源和 checkpoint。

##### TRAIN-1c. 三节点 24 GPU/48 EFA 示例

真实执行 24-rank NCCL、DDP forward/backward、
  SGD 参数更新和 loss 下降；managed `expected-critical-ranks=3` 表示三个关键 Pod，
  PyTorch `world_size=24` 表示 24 个进程；提交前必须预拉大镜像。

### 5.5 区域数据面节点 systemd 安装详解

| 子章节 | 解读 |
|---|---|
| `8.2.1 适用范围和系统行为` | 自动替换要求一一对应 spare；不足时原 workflow 保持失败，人工创建新 attempt。 |

| `8.2.4 第三步：复核并人工预留健康 spare` | 验证 HyperPod/K8s/Agent 健康，写 reservation 后才 uncordon。 |

## 9. 数据迁移

- **目的**：SQLite→PostgreSQL 或 PostgreSQL→PostgreSQL。
- **区域停写顺序**：记录副本 → 停 ingress → 等 processor/spool 排空 →
  停 consumer。
- **恢复顺序**：先以 1 worker + 1 ingress 验证，再 consumer → ingress 恢复原副本。
- **关键要求**：目标数据库为空；状态文件保留到原副本全部 Ready。

## 10. 分阶段启用破坏性能力

### 阶段 A：观察

只取证、采集、simulation，不修改 workload 或节点。

### 阶段 B：隔离与训练控制

开放隔离、停止和重启 workload，先证明新旧 attempt 不重叠。

### 阶段 C：GPU reset

按 Node Agent readiness → drain → quiesce → no-client → reset → restore →
validation → scheduling/workload 恢复的顺序启用。

#### 阶段 C.0：XID 74 NVLink workflow

要求完整寄存器、Link ID、诊断命令和 SHA。未知/全零/secondary-only fail closed；
满足 Catalog 条件后才 reset 或升级支持。

#### 阶段 C.1：H200 SXID 恢复

普通 Fatal Trunk/full-reset 使用全 GPU/NVSwitch reset barrier；Always-Fatal 进入
节点 reboot。Kernel Collector 是生产主路径，FM Collector 是补充源。

#### 阶段 C.2：显式启用驱动/固件修复

只有站点已经验证目标版本、命令和 SHA 时才能启用。任何版本、上传、验证或 client
门禁失败都保持隔离并升级 support。

### 阶段 D：节点生命周期（provider replace 恒禁用）

当前生产 Profile 同时 OWN `nodeReboot` 和 `nodeReplace`，所以两个能力必须分别验收；
它们不是两个独立环境开关。

#### 阶段 D.1：HyperPod reboot

仅 `NodeRecovery=None` 且 profile OWN 时开放 provider reboot。每次调用必须有
cluster 二次确认、incident/workflow fencing 和幂等键；旧 mutation 总开关不得设置。

#### 阶段 D.2：warm-spare nodeReplace

`nodeReplace` 固定使用 `HEALTHY_WARM_SPARE_ONLY`，只激活同规格健康 spare，并要求
全量原子分配、动作后 GPU/fabric 验证和 workload 重启。provider replace 恒关；
健康 spare 不足时保持隔离并告警，不得部分替换或回退到
`BatchReplaceClusterNodes`。

## 配置 EFA/RDMA 流量与 hung 诊断

- 配置 EFA 流量 baseline、SPIKE/DROP/ZERO/HUNG 阈值和抑制预算。
- hung 诊断采集 GPU process、Python stack、`/proc`、strace、RDMA counters、
  ethtool 和日志快照。
- 真正的 hung 与 checkpoint/图编译必须结合训练进度和 per-rank liveness 区分。

### 升级前的 per-rank liveness 判定（不依赖应用埋点）

Host Collector 根据每个 GPU 进程的写入速率、CPU 活跃度和 GPU idle 判断 rank 是否推进。
信号缺失不静默；抑制有最长预算，避免永久掩盖 hang。

## 配置 Host 资源持续隐患监控

- 监控低 CPU/GPU 利用率、低内存、高 page cache、磁盘占用和 EFA/RDMA 状态。
- 低利用率只在控制面通过 attempt observation 解析出节点上唯一一个运行中的受管训练 attempt 时计时，节点 collector 自报的 ACTIVE 状态只是预过滤；内存/磁盘异常不要求存在训练。
- 动作固定为诊断，不自动重启；邮件按节点/job/signal 冷却去重。

### Windows 下载与解压诊断包

说明从 S3 下载、校验大小/SHA、外层 tar.gz 与内层
`nvidia-bug-report.log.gz` 的两次解压，以及如何区分普通诊断包和 hung 包。

## 配置异构节点 GPU/EFA ACTIVE inventory 检查

### 1. 理解配置作用域

expected GPU/EFA 是节点级值，按实例类型写入 collector.env，不是控制面全局值。

### 2. 部署前核对节点标签

核对 instance type、cluster label、`nvidia-smi`、EFA PCI/driver、端口
ACTIVE/LinkUp。

### 3. 配置参数

定义 instance type、expected GPU、expected ACTIVE EFA、连续异常次数和采样周期。

### 4. 为异构 HyperPod 节点部署

逐节点读取实例类型并生成安装 Job。未知机型必须显式提供 GPU/EFA 数，不能静默跳过。
本节同时解释三层控制面资源、连接预算、schema smoke 和容量探针。

### 5. 验证每个节点的最终配置

检查 collector.env、Host Collector 日志、expected/active/missing/excess 和 mismatch。

### 6. 异常后的控制面行为

根据 GPU 缺失、EFA PCI 缺失、driver 未绑定、端口 inactive、allocatable 缺失选择
plugin restart、driver remediation、reboot 或 replace；动作后重新验证 inventory。

## 四、推荐的日常使用方式

1. **首次区域部署**：严格执行 §0.1，不要只跑 bootstrap。
2. **日常发布**：先 `plan/status`，确认 remote open=0，再 `upgrade`。
3. **新增 GPU 集群**：使用`gpu-fault-admin join-cluster --state-dir ...
   --gpu-cluster-arn ...`，不要重建CPU控制面。
4. **节点新增/替换**：由 Reconciler 根据 Node UID 和 artifact/config pin 自动安装。
5. **故障排查**：先检查 wheel/module digest，再查认证、队列、Executor、Agent。
6. **破坏性动作**：按阶段 A→D 开放，每一阶段都需要维护窗口和回滚证据。
7. **训练任务**：客户镜像自定义；示例 PyTorch Training DLC 只用于 NCCL/DDP smoke。
8. **验收记录**：生产声明必须同时保存版本、规模、时间窗、命令输出和清理结果。

## 附录 A. 旧版 HyperPod 单集群（非生产）

本附录仅用于历史环境维护、迁移起点和有限 Canary，不是生产部署入口。

### A.1 设置参数

- **目的**：配置单集群自动部署的容量、Aurora、processor、告警、恢复与采集参数。
- **重点**：processor worker、Store I/O、PostgreSQL pool、退出预算必须一起核算。
- **已有部署的数据库升级流程**：schema ensure → backfill → dual →

### A.2 选择 DCGM Exporter 模式

- `auto`：探测既有 endpoint，不存在时部署 managed exporter。
- `existing`：只复用客户 exporter，字段缺失即失败。
- `managed`：本方案部署 exporter，发现端口冲突即失败。
- `disabled`：只有显式启用 nvidia-smi fallback 时允许。
- **通过标准**：所有节点采用一致模式，必需 DCGM 字段齐全。

### A.3 执行部署

`deploy/hyperpod/deploy.sh deploy` 负责 kubeconfig、Aurora、wheel/bundle、
三层控制面、Runtime Profile、Watcher、Exporter、节点安装和非破坏性 E2E。

### A.4 观察部署

查看 Pod、Deployment、DaemonSet、PDB、日志和 `/healthz`。单集群路径保留
`gpu-fault-api-canary` 兼容 Service，区域路径使用 `gpu-fault-api`。

### A.5 Runtime Profile 选择

- **作用**：声明每项能力由本系统 OWN、委托 DELEGATE、观察 OBSERVE 或禁用。
- **关键要求**：事件、Collector、Agent、Watcher 和训练任务必须引用已注册的同一
  profile version。
- **常见故障**：引用示例文件中的未注册 profile 会让 Watcher 永久 404。

### A.6 过渡单集群验收清单（非生产）

本节只用于旧单集群环境和迁移前 Canary；生产区域模式使用 REG-8。检查 API、fleet、collector、DCGM、
PDB、RBAC、幂等、lease fencing 和非破坏性 E2E。

### A.7 过渡单集群故障排查（非生产）

#### API 无法启动

检查 Store URL、execution token、allowlist、Secret 和 Pod 日志。

#### Agent readiness 失败

比较 Agent version、wheel SHA、policy、profile、config digest、Node UID、boot ID、
generation 和 heartbeat age。

#### DCGM 无数据

检查 9400 endpoint、required counters 和 collector 日志；nvidia-smi fallback
不能替代完整 DCGM。

#### Workflow 一直 WAITING

检查等待 step、旧 Pod、HyperPod identity、Agent compatibility 和 remote command。

#### Workflow BLOCKED

这是安全终态或安全等待。按 `blocked_reasons` 补证据/owner/新鲜度，不得扩大 allowlist。

#### 禁止管理员调用 HyperPod provider replace

- `BatchReplaceClusterNodes`、`BatchDeleteClusterNodes` 或等价 provider replace
  对自动化和管理员都禁止。
- `REPLACE_NODE` 只表示 `HEALTHY_WARM_SPARE_ONLY`。有合格 spare 时继续受检
  warm-spare workflow；不足时执行 §8.2 的人工降级新 attempt 或 support escalation。
- 故障节点保持隔离。节点因独立维修或永久退役消失后，才按 drain→revoke 清理 stale
  fleet 记录；重新纳入 spare 前必须完成硬件验收、Agent 收敛、spare label、
  `AVAILABLE` 状态和 cordon。
- 通用 `MARK_UNSCHEDULABLE` 完成通知仍是缺口，但任何后续通知都必须明确写
  “仅 warm-spare、禁止 provider replace”。

主手册保留的子章节用于执行替代路径和清理，不是 provider replace SOP：

| 子章节 | 当前含义 |
|---|---|
| `何时可以启动替代处置：前置条件` | 先证明隔离和停训已完成 |
| `不需要避让 warm spare 分配窗口` | 故障节点与 spare reservation 是不同对象 |
| `允许的处置步骤` | 只允许 warm-spare 或 §8.2 人工降级 |
| `节点因外部维修或永久退役消失后清理 fleet 记录` | drain→revoke stale Agent |
