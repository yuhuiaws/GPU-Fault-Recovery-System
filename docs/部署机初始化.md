# 部署机初始化

本文定义运行`gpu-fault-admin deploy`之前唯一支持的部署机准备入口。初始化只修改指定
venv和本地工具目录，不创建AWS或Kubernetes资源，也不读取站点凭据。

## 1. 职责边界

初始化入口负责：

- 创建Python 3.12 venv；
- 按`requirements/deploy-host.lock`和hash安装Python依赖；
- 安装与bundle同源的项目wheel；
- 校验AWS CLI、Cosign、Docker daemon/Buildx、kubectl、Helm及基础命令；
- 保存不含凭据的版本、路径和bundle摘要报告。

Docker Engine及宿主机级基础包由固定部署机镜像或AMI提供。venv不能安装Docker daemon，
`gpu-fault-admin deploy`也不会在线下载、提权安装或升级系统软件。

## 2. 平台兼容范围

deploy-host bundle不是跨OS通用包。Manifest和文件名绑定以下字段：

- OS family；
- CPU architecture；
- Python implementation、3.12版本和ABI cache tag；
- Python `sysconfig` platform；
- libc实现名称，并记录构建机libc版本供审计。

例如当前Linux x86-64 CPython 3.12 bundle使用平台ID：

```text
linux-x86-64-cpython-312
```

setup在创建venv前逐项比较bundle与目标主机；OS、架构、Python ABI、sysconfig platform
或libc实现不同都会fail closed。不同发行版只有在这些字段兼容且wheel满足目标glibc时
才能共用。Alpine/musl、ARM64、macOS、Windows或其他Python版本必须在对应受信环境重新
构建并签名bundle，不能强制复用。

生产setup还要求bundle记录的源码树为clean，且`git_commit`与当前checkout的HEAD完全
一致，防止已签名Python环境与另一版本的Makefile、Dockerfile或部署脚本混用。

宿主机镜像必须提前提供：

| 软件 | 用途 |
|---|---|
| Python 3.12 | 运行初始化器和创建venv |
| Docker Engine | 构建runtime image |
| Docker Buildx | OCI push和registry cache |
| AWS CLI | 发现和创建AWS资源、ECR登录 |
| Cosign | 验证deploy-host bundle和签名release |
| kubectl、Helm | CPU/GPU EKS部署与验证 |
| curl、jq、OpenSSL、sha256sum、make | TLS、结构化检查、摘要和发布编排 |

这些软件由部署机AMI、镜像或`DEPLOY_HOST_TOOLS_DIR`中的审核后二进制提供。初始化器不
调用系统包管理器，也不修改Docker daemon。

## 3. 生产离线初始化

Release CI生成：

```text
dist/gpu-fault-deploy-host-linux-x86-64-cpython-312.tar.gz
dist/gpu-fault-deploy-host-linux-x86-64-cpython-312.tar.gz.sha256
dist/gpu-fault-deploy-host-linux-x86-64-cpython-312.sigstore.json
```

bundle包含锁文件、Python wheelhouse、项目wheel、工具清单，以及可选的审核后二进制目录。
文件清单记录每个payload的SHA-256、大小和可执行位；archive由Cosign签名。

部署机使用固定public key验签：

```bash
make deploy-host-setup \
  DEPLOY_HOST_ARCHIVE=/secure/release/gpu-fault-deploy-host-linux-x86-64-cpython-312.tar.gz \
  DEPLOY_HOST_SIGNATURE_BUNDLE=/secure/release/gpu-fault-deploy-host-linux-x86-64-cpython-312.sigstore.json \
  DEPLOY_HOST_COSIGN_KEY=/secure/release/cosign.pub \
  DEPLOY_HOST_VENV=/secure/gpu-fault/deployer-venv
```

keyless bundle使用审批过的certificate identity和issuer：

```bash
make deploy-host-setup \
  DEPLOY_HOST_ARCHIVE=/secure/release/gpu-fault-deploy-host-linux-x86-64-cpython-312.tar.gz \
  DEPLOY_HOST_SIGNATURE_BUNDLE=/secure/release/gpu-fault-deploy-host-linux-x86-64-cpython-312.sigstore.json \
  CERTIFICATE_IDENTITY=<release-identity> \
  CERTIFICATE_OIDC_ISSUER=<release-issuer> \
  DEPLOY_HOST_VENV=/secure/gpu-fault/deployer-venv
```

安装在同目录临时venv完成，依赖和系统工具检查全部通过后才原子替换目标venv。相同bundle
重复执行时验证现有环境并返回`reused=true`。

## 4. 开发机联网初始化

联网模式只用于开发checkout，必须显式批准：

```bash
make deploy-host-setup-online DEPLOY_HOST_VENV=.venv
. .venv/bin/activate
make check
```

该模式仍按hash lock安装依赖，然后以editable方式安装当前checkout。生产部署机不得使用
联网模式。

## 5. 独立检查

```bash
make deploy-host-check DEPLOY_HOST_VENV=/secure/gpu-fault/deployer-venv
```

报告只包含：

- Python期望/实际版本；
- bundle与宿主机的OS、架构、Python ABI、platform和libc兼容结果；
- 系统工具解析路径、状态和版本输出；
- bundle SHA-256、项目版本和源commit；
- `healthy`与`reused`状态。

报告、bundle和venv中不得包含AWS凭据、token、私钥、数据库密码或kubeconfig内容。

## 6. 构建bundle

在干净源码树和受信Release环境执行：

```bash
make deploy-host-bundle PYTHON=.venv/bin/python
```

可通过`DEPLOY_HOST_WHEELHOUSE`提供预审离线wheel目录，通过
`DEPLOY_HOST_TOOLS_DIR`加入已审核的用户态二进制。未提供wheelhouse时，只有bundle构建
阶段允许联网解析lock；最终部署机安装始终使用`--no-index`。

每个支持平台都要在对应受信构建环境单独运行该目标并发布独立签名。不得在一个平台构建
后手工改名为另一平台。

初始化失败时保留原venv，不写入半成品状态。修复bundle、签名、宿主机工具或Docker权限后
重跑同一命令。
