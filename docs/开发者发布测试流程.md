# 开发者发布与测试流程

本文给出开发者修改代码后，从本地验证、生成签名 release、部署到 staging、完成测试，
再把同一制品晋级生产的最短受支持流程。

本文适用于已有 `site.yaml` 的站点升级。首次创建站点或集群使用
[管理员快速部署](管理员快速部署.md)；CI内部构建细节见[CI 发布流程](CI发布流程.md)；
Manifest、Profile、组件DAG和回滚细节见[开发者部署实现](开发者部署实现.md)。

## 1. 一屏流程

```text
修改代码
  -> 运行最小相关pytest
  -> make test-impact BASE=origin/main
  -> make regional-impact-plan BASE=origin/main
  -> make check
  -> 形成经过审阅的干净commit
  -> Release CI构建签名制品（推荐）
     或受信环境运行make release-build
  -> 把同一签名release部署到staging
  -> verify + status + 变更相关非破坏性测试
  -> 审核报告和回滚状态
  -> 复用同一签名release晋级生产
  -> verify + status + 保存上线证据
```

必须先构建 release，再部署。以下命令只会部署 `site.yaml` 已声明的 release，不会把当前
工作区代码自动上线：

```bash
gpu-fault-admin deploy -f /secure/gpu-fault/site.yaml
```

因此不能在修改源码后直接运行该命令，并期待它读取当前 checkout。

## 2. 开发与环境前提

开发机可以联网创建开发 venv：

```bash
make deploy-host-setup-online DEPLOY_HOST_VENV=.venv
. .venv/bin/activate
```

生产或正式 staging 部署机必须使用
[签名离线bundle](部署机初始化.md)，不能使用联网初始化模式。

开始发布前还应具备：

- 一个隔离的 staging 站点和对应 `site.yaml`；
- Python 3.12、Docker Buildx、Cosign、AWS CLI、kubectl 和 Helm；
- 已登录且有权限推送的 ECR repository；
- 独立 PostgreSQL 16 测试库，连接信息通过受控环境提供；
- Release 签名身份或受控 Cosign 私钥；
- staging 变更批准、Region、context、cluster ID、维护窗口、停止条件和回滚方案。

受管 GPU HyperPod 必须保持 `NodeRecovery=None`。默认测试流程不执行 GPU reset、节点
reboot、warm-spare 切换、workload restart 或其他破坏性动作。

## 3. 修改代码后的本地验证

### 3.1 先运行最小相关测试

根据修改模块先执行最小 pytest，例如：

```bash
python -m pytest -q tests/<related-test>.py
```

新增 operation、channel、Store、路由、Manifest、环境变量或资源时，先按
[扩展指南](扩展指南.md)和[开发者部署实现](开发者部署实现.md)补齐 registry、生成物、
文档和测试，不要等到发布阶段再补。

### 3.2 执行影响选择

```bash
make test-impact BASE=origin/main
make regional-impact-plan BASE=origin/main
```

`test-impact` 会读取已提交、staged、未提交和未跟踪变化，执行匹配的静态检查与 pytest。
`regional-impact-plan` 只输出受影响的区域 case，不会连接集群或执行 live/destructive
动作。

如果选择器 fail closed 升级到完整门禁，按输出执行，不要缩小范围或跳过失败测试。

### 3.3 执行完整门禁

```bash
make check
```

涉及 PostgreSQL schema、事务、lease、counter、fencing 或 Processor 并发时，还要在
隔离 PostgreSQL 16 上运行：

```bash
test -n "${GPU_FAULT_TEST_POSTGRES_URL}"
make test-postgres-stress
```

不得使用生产 Aurora 运行开发测试，也不得通过降低 coverage、跳过测试或放宽断言掩盖
失败。

## 4. 形成可发布提交

发布候选必须来自经过审阅的干净 Git commit：

```bash
git status --short
git rev-parse HEAD
```

运行 `release-build` 前，`git status --short` 必须没有输出。构建器会拒绝 dirty
checkout。`DEPLOY_HOST_ALLOW_DIRTY` 只影响部署机bundle的开发构建，不能让
`release-build`接受dirty checkout，也不能用于正式发布。

同时确认：

- diff 中没有 token、私钥、数据库密码、kubeconfig 或客户标识；
- 没有手工修改 generated Manifest、`dist/` 制品摘要或历史 migration；
- 文档、测试和生成物与最终 commit 一致。

## 5. 构建签名 release

### 5.1 推荐：使用 Release CI

1. 推送经过审阅的 commit 或 `v*` tag；
2. 触发并等待 GitHub `Release` workflow 全部成功；
3. 下载该 run 的完整 `gpu-fault-release` artifact；
4. 将内容恢复为匹配 checkout 下的 `dist/...` 布局；
5. 不混用其他 run 的 Manifest、wheel、签名或 deploy-host bundle。

CI会完成 `make check`、PostgreSQL stress、Runtime Image push、三个组件wheel、Node
bundle、attestation、部署机离线bundle和Cosign签名。完整顺序见
[CI 发布流程](CI发布流程.md)。

### 5.2 受信环境本地构建

只有在受控 Release 环境中才使用本地签名构建。先安全设置
`GPU_FAULT_TEST_POSTGRES_URL`并完成ECR登录，然后执行：

```bash
COSIGN_SIGNING_KEY=/secure/release/cosign.key \
make PYTHON=.venv/bin/python release-build \
  RUNTIME_IMAGE_REPOSITORY=<ecr-repository>
```

成功标准：

- `dist/current-release.json` 为 `deployable=true`；
- `dist/current-attestation.json` 和签名 bundle 已生成；
- Runtime Image 已按不可变 digest 推送；
- 三个 wheel、Node bundle 与镜像内组件一致。

构建成功后不得修改 `dist/`，也不得在 staging 部署前再次 build。

## 6. 部署到 staging

部署前先确认目标确实是 staging，并记录 Region、CPU/GPU context、cluster ID、维护窗口、
停止条件和回滚方案。未经批准，不在生产站点试跑新 commit。

先执行只读检查：

```bash
gpu-fault-admin preflight -f /secure/gpu-fault/staging/site.yaml
gpu-fault-admin status -f /secure/gpu-fault/staging/site.yaml
```

### 6.1 消费 CI keyless 制品

```bash
make PYTHON=.venv/bin/python release-deploy \
  SITE=/secure/gpu-fault/staging/site.yaml \
  CERTIFICATE_IDENTITY=<approved-release-identity> \
  CERTIFICATE_OIDC_ISSUER=<approved-release-issuer>
```

### 6.2 消费本地固定密钥签名制品

```bash
make PYTHON=.venv/bin/python release-deploy \
  SITE=/secure/gpu-fault/staging/site.yaml \
  COSIGN_KEY=/secure/release/cosign.pub
```

两种验签模式二选一，必须与构建时的签名方式一致。

如果修改了 Runtime Profile，首次运行会生成 `profile-plan.json`并停止。审核差异并取得
审批后，在对应验签命令前增加 `PROFILE_APPROVAL`。以下以推荐的CI keyless制品为例：

```bash
PROFILE_APPROVAL=<change-reference> \
make PYTHON=.venv/bin/python release-deploy \
  SITE=/secure/gpu-fault/staging/site.yaml \
  CERTIFICATE_IDENTITY=<approved-release-identity> \
  CERTIFICATE_OIDC_ISSUER=<approved-release-issuer>
```

`release-deploy` 会自动执行：

```text
验签 -> preflight -> deploy/upgrade -> verify -> stability -> release-summary
```

不要在该命令运行期间使用 `kubectl edit`、`kubectl set env` 或直接 apply `deploy/`。

## 7. staging 测试

### 7.1 必做只读验收

部署成功后再次执行：

```bash
gpu-fault-admin verify -f /secure/gpu-fault/staging/site.yaml
gpu-fault-admin status -f /secure/gpu-fault/staging/site.yaml
```

并检查站点 release state 目录中的：

```text
verification-report.json
release-summary.json
```

实际发生变更时还必须有 `stability-report.json`。明确分类为 `NOOP` 时稳定窗口会跳过，
不要求该报告。

成功标准至少包括：

- CPU Control Plane、GPU Executor/Watcher/Collector/Reconciler 全部健康；
- Node Agent 为 `ACTIVE`，artifact/config/Profile/protocol pin 一致；
- NLB/TLS、Aurora、AMP/SNS 和 remote command backlog 检查通过；
- 没有持续重启、critical alert 或非终态发布记录。

### 7.2 默认非破坏性回归

执行 catalog 中默认的非破坏性 pytest 场景：

```bash
make fault-test-cases
```

该命令不连接生产 Kubernetes，也不会执行 GPU reset、reboot、warm-spare 或 workload
restart。它不能替代 staging 的 `verify/status`。

### 7.3 变更相关 staging case

根据 `make regional-impact-plan` 的输出选择额外 case。默认只执行非破坏性 case。
任何 `--include-live`、command、manual、destructive、provider reboot、warm spare 或
真实训练 workload 测试，都必须另行取得明确批准，并按
[故障模拟测试手册](故障模拟测试手册.md)记录目标节点、停止条件、清理和证据。

## 8. 失败处理

任一 build、deploy、verify 或 stability 步骤失败时：

1. 立即停止后续测试和生产晋级；
2. 保留 release state、已有报告和checkpoint；
3. 确认线上是候选 release、previous release，还是已自动回滚；
4. `autoRollback=true` 且回滚成功时，对 previous release 再执行 `verify/status`；
5. 修复源码后生成新的干净 commit 和签名 release；
6. 对可续跑的部署，修复外部原因后重跑同一条 `release-deploy`。

不要手工改签名 Manifest、artifact pin、Profile version，或只执行
`kubectl rollout undo`。schema 不向后兼容等禁止自动回滚的情况按
[开发者部署实现](开发者部署实现.md)执行 fail-forward 或显式恢复。

## 9. 晋级生产

只有 staging 的构建、部署、只读验收和变更相关测试全部通过后才能晋级。

生产晋级原则：

- 复用 staging 已验证的同一签名 Manifest、wheel、Node bundle 和 OCI digest；
- 不为生产重新 build，也不手工改写 release JSON；
- 确认生产能够访问该不可变 ECR digest；
- 明确生产 Region、context、cluster ID、维护窗口、停止条件和回滚方案；
- 使用生产 `site.yaml` 重复第 6 节的 `release-deploy`；
- 完成生产 `verify/status`并保存上线证据；
- 默认不在生产执行 fault injection 或破坏性测试。

如果生产位于不同 Region、账号或 registry，不能只复制并改写 Manifest。应按
[开发者部署实现](开发者部署实现.md)的受检交付流程准备对应签名 release。

## 10. 完成清单

一次代码上线只有同时满足以下条件才算完成：

- 最小相关测试、`test-impact`和`make check`通过；
- 必需的 PostgreSQL stress 零失败；
- 发布候选来自干净、经过审阅的 commit；
- Runtime Image、三个 wheel、Node bundle、Manifest 和签名来自同一 release；
- staging `release-deploy`、`verify`、`status`和相关非破坏性测试通过；
- 失败恢复或自动回滚状态已明确；
- 生产复用同一已验证制品并完成只读验收；
- release、验证报告、维护窗口和审批引用已保存，且不包含敏感值。
