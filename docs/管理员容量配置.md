# 管理员容量配置

本文定义管理员调整区域控制面和Aurora容量的正式入口。容量变更不修改源码，不重新
构建镜像或wheel；CLI复用当前已验签release，对Aurora执行受审计的RDS变更，并只为
需要进程重载的配置滚动受影响CPU角色。

## 1. 支持范围

当前管理员可配置：

- control-worker副本数；
- 站点拓扑：最大单个GPU集群节点数（`largestClusterNodeCount`）和受管节点总数
  （`managedNodeCount`）；
- telemetry spool enabled/disabled和spool-worker副本数；
- remediation budget的Region、cluster和resource class上限；
- Aurora Serverless v2 Min/Max ACU；
- Processor总队列、单集群队列、客户端退避、持久重试和完成记录保留；
- Workflow扫描周期和dispatcher线程数；
- 通知批量大小和最大尝试次数；
- 原始证据保留小时数和每节点记录上限。

正式模板共包含22个管理员可配置叶子字段。node和failure-domain remediation budget
属于安全常量，运行时保持1，不出现在模板中。

凭据、Region、cluster identity、Runtime Profile、operation allowlist、release pin、
破坏性能力开关和安全不变量不属于通用管理员配置。只有正式模板声明的字段可以修改，
不得把任意`GPU_FAULT_*`变量透传给Pod。

## 2. Release模板

源码Release包含：

```text
config/admin-config.example.yaml
```

签名deploy-host bundle安装后，同一模板位于：

```text
<deploy-host-venv>/share/gpu-fault/admin-config.example.yaml
```

模板是只读发布资产，权限为`0644`。管理员实际输入必须位于受控目录且权限为`0600`。

## 3. 首次部署

管理员首次部署前已经确定容量值时，基于Release模板准备自己的配置文件，然后使用一个
deploy命令直接应用：

```bash
gpu-fault-admin deploy \
  --cpu-cluster-arn <cpu-arn> \
  --gpu-cluster-arn <gpu-arn> \
  --state-dir /secure/gpu-fault \
  --admin-email <operations-email> \
  --config /secure/gpu-fault-input/admin-config.yaml
```

CLI在源码构建或AWS/Kubernetes访问前校验配置，把规范化值写入
`<state-dir>/admin-config/desired.json`，并把可编辑副本写入：

```text
<state-dir>/admin-config.yaml
```

首次部署不需要先执行`config`。未提供`--config`时使用release默认值，并生成默认的
`<state-dir>/admin-config.yaml`。

## 4. 已有站点修改

同一动词下还有一个子动作 `gpu-fault-admin config spare --state-dir STATE_DIR --node NODE [--declare|--release ...]`，用于声明或释放热备 GPU 节点；它不涉及本文的容量配置，见[管理员日常运维](管理员日常运维.md)任务表。

管理员编辑`<state-dir>/admin-config.yaml`后直接执行：

```bash
gpu-fault-admin config \
  --state-dir /secure/gpu-fault \
  --reference CHG-12345
```

也可以临时指定另一个`0600`文件：

```bash
gpu-fault-admin config \
  --state-dir /secure/gpu-fault \
  --file /secure/gpu-fault-input/admin-config.yaml \
  --reference CHG-12345
```

CLI内部自动计算差异、生成计划SHA、绑定站点和当前签名release、持久化审计、执行
Aurora变更和config-only rollout并完成verify/stability。提高Min ACU时，命令还会等待
writer和reader的`ServerlessDatabaseCapacity`均达到目标Min。管理员不需要读取或回传
`plan_sha256`。只预览不应用时增加`--dry-run`；该模式不写活动计划或审批。

当前签名release来自`state-dir`内由源码部署保留的隔离checkout。CLI会核对
content-addressed Manifest、Cosign attestation与CPU集群中已commit的live release
state；开发目录后来生成新的`dist/`不会影响该命令，任一身份或签名漂移则在写计划前
fail closed。

如果同一命令在Aurora收敛、rollout、verify或stability中途被中断，活动plan和approval
会保留。重跑原命令时，CLI只接受Aurora仍为计划中的当前值或目标值；其他live值按漂移
fail closed。release续跑仍要求目标配置摘要和已审批计划一致，不能把该例外用于创建
新计划或切换目标。

容量预设使用同一个命令：

```bash
gpu-fault-admin config \
  --state-dir /secure/gpu-fault \
  --preset 32-disabled \
  --reference CHG-12345
```

使用preset时不需要另设capacity环境变量，也不需要准备`admin-config.yaml`；CLI从当前
持久化AdminConfig继承其他非capacity字段，应用preset中的capacity值（含节点数拓扑）。
preset命名的是一个拓扑，而拓扑决定Aurora Min ACU下限（见§6）：当前Min ACU低于该
preset下限时，计划会把Min ACU提到下限、Max ACU提到`max(当前Max, 128)`，并像其他
Aurora变更一样进入审批和RDS审计路径；已经高于下限的Aurora不会被降低。正式压测使用的
`124/128`高于`32-*`的下限`82`，仍必须显式设置，不能从`32-enabled`推断；`50-*`的
下限恰好是`128/128`。

支持的预设（多集群拓扑按每集群256节点计，见性能压测验收方案§2）：

| preset | Region budget | 每集群 | 每resource class | spool | 最大集群/受管节点 | Aurora下限 |
|---|---:|---:|---:|---|---:|---:|
| `default` | 20 | 5 | 2 | disabled，0副本 | 512 / 512 | 8/32（模板值） |
| `32-disabled` | 128 | 4 | 4 | disabled，0副本 | 256 / 8192 | 82/128 |
| `32-enabled` | 128 | 4 | 4 | enabled，3副本 | 256 / 8192 | 82/128 |
| `50-disabled` | 200 | 4 | 4 | disabled，0副本 | 256 / 12800 | 128/128 |
| `50-enabled` | 200 | 4 | 4 | enabled，3副本 | 256 / 12800 | 128/128 |

内部审计计划记录当前值、目标值、站点身份、签名release ID、Manifest SHA、配置摘要、
角色摘要、受影响角色、Aurora字段差异和`plan_sha256`。Aurora变更结果及回滚结果写入
应用审计。失败时活动记录保留，相同config命令幂等续跑；成功完成verify、stability和
commit后，审计保存在：

```text
<state-dir>/admin-config/history/<plan-sha256>/
```

从只包含`capacity`、旧版18字段或缺少节点数字段的20字段desired state升级时，CLI先按
旧版配置摘要和三角色摘要双重验真，再在管理员文件锁内原子补齐缺失字段。旧站点缺少
Aurora字段时按历史`0.5/8`保留，不会因软件升级静默改库；新站点默认使用`8/32`。旧记录
缺少节点数时，按它自己声明的单集群队列深度反推拓扑（`min(512, depth / 4)`，历史
`1024`即256节点，受管节点数取同值），不会按新默认512读入一个该深度容不下的集群。旧
记录结构未知、内容被修改或任一摘要不匹配时仍然fail closed。

读取已持久化或线上捕获的状态只做结构校验，不套用§6的实证下限：低于下限的旧站点是
事实，拒绝读取只会让管理员无法加载状态去计划修复。任何生成新desired的入口（文件、
preset、显式参数、计划）都完整校验，低于下限的组合会被拒绝并同时点名两个字段。

## 5. 显式参数

不使用文件或预设时可组合以下参数：

```bash
gpu-fault-admin config \
  --state-dir /secure/gpu-fault \
  --control-worker-replicas 6 \
  --largest-cluster-node-count 512 \
  --managed-node-count 2048 \
  --spool disabled \
  --spool-replicas 0 \
  --max-active-region 128 \
  --max-active-per-cluster 4 \
  --max-active-per-resource-class 4 \
  --reference CHG-12345
```

未填写字段继承当前持久化值。`--preset default`用于显式恢复release默认值。CLI拒绝
未知字段、错误类型、spool开关与副本不一致、node/failure-domain上限大于1、
cluster/resource-class大于Region、`managedNodeCount`小于`largestClusterNodeCount`、
超过已验收PostgreSQL fleet连接预算的组合，以及违反§6拓扑派生规则的组合（例如上例
2048个受管节点要求Aurora Min ACU至少20.5，只提高节点数而不改`--file`中的
`aurora.minAcu`会被拒绝）。`--file`不能与preset或显式容量参数组合。

## 6. 配置文件格式

当前模板内容为：

```yaml
apiVersion: gpu-fault.aws/v1alpha1
kind: AdminConfig
spec:
  capacity:
    controlWorkerReplicas: 6
    largestClusterNodeCount: 512
    managedNodeCount: 512
    telemetrySpool:
      enabled: false
      replicas: 0
    remediation:
      maxActiveRegion: 20
      maxActivePerCluster: 5
      maxActivePerResourceClass: 2
  aurora:
    minAcu: 8
    maxAcu: 32
  processor:
    maxQueueDepth: 65536
    maxClusterQueueDepth: 4096
    retryAfterSeconds: 2
    retryBackoffSeconds: 1
    retryBackoffMaxSeconds: 30
    completedRetentionSeconds: 600
  workflow:
    pollIntervalSeconds: 5
    dispatcherWorkers: 8
  notificationDelivery:
    batchSize: 25
    maxAttempts: 8
  evidence:
    retentionHours: 24
    maxRecordsPerNode: 10000
```

文件中未出现的字段继承当前持久化值。普通代码升级保持当前配置，不会意外恢复默认。
fault reserved depth、global admission guard、retryable response age、cleanup批次、
workflow batch、notification poll/lease/backlog grace等内部参数由代码根据公开字段或
固定生产契约派生，不进入管理员模板。

`largestClusterNodeCount`和`managedNodeCount`是拓扑输入，不是调优项；三条派生规则
都来自本仓库的压测证据（性能压测验收方案§13.3–§13.4），由同一份代码为CLI校验、
两个manifest renderer和运行时启动自检共用：

| 规则 | 依据 |
|---|---|
| `processor.maxClusterQueueDepth >= 4 x largestClusterNodeCount` | §13.4：单集群1000节点在深度1024下产生243个HTTP 429，提高到4096后为0 |
| `aurora.minAcu >= ceil(managedNodeCount / 100, 0.5 ACU)` | §13.3：约12800节点在`0.5/96 low-start`下产生3076个HTTP 503，预置Min≈124–128后为0 |
| `GPU_FAULT_PROCESSOR_FAULT_RESERVED_CLUSTER_DEPTH = max(maxClusterQueueDepth / 8, largestClusterNodeCount)` | 产品要求：整集群相关故障是每节点一条fault优先请求，落在同样多的node lane上，预留必须容下一整波 |

默认值`512 / 512 / 4096 / 8`满足全部三条（512节点的Aurora下限为5.5 ACU）。4个512节点
集群的站点必须同时把`managedNodeCount`写成2048并把`minAcu`提到至少20.5。节点数与
`GPU_FAULT_PROCESSOR_FAULT_RESERVED_*`一起渲染进三个CPU角色的ConfigMap
（`GPU_FAULT_CAPACITY_LARGEST_CLUSTER_NODE_COUNT`、
`GPU_FAULT_CAPACITY_MANAGED_NODE_COUNT`），运行时在启动时拒绝预留小于最大集群节点数的
环境，`/metrics`以`gpu_fault_capacity_largest_cluster_node_count`和
`gpu_fault_capacity_managed_node_count`两个gauge导出。回滚捕获线上AdminConfig时，只
读取ConfigMap中实际存在的节点数；线上没有声明时按上文旧记录规则从捕获到的深度反推，
不用release默认值补位。

## 7. 优先级与省略字段

运行时配置优先级从高到低为：

1. 安全不变量和专用审批；
2. Secret、release身份和兼容性pin；
3. 规范化AdminConfig；
4. role-split renderer生产默认；
5. 应用代码中的`os.getenv`兜底默认。

AdminConfig在部署环境合并时覆盖同名shell变量，并被固化到角色ConfigMap。显式`env`
与`envFrom`重复、未知字段或越界组合都会在应用前失败。

首次部署没有历史`desired.json`，配置文件省略字段时使用AdminConfig默认值。已有站点
省略字段时继承当前`desired.json`值，适合用部分`--file`只修改少数字段。正常的
`<state-dir>/admin-config.yaml`始终写出完整22项；要恢复默认值应显式填写模板默认值，
容量整体也可使用`--preset default`。

## 8. 生效与回滚

配置摘要独立于代码release ID、镜像摘要和wheel摘要。config-only release：

- 不上传或重建任何代码制品；
- Aurora字段变化先调用RDS API，等待cluster、writer和reader可用；提高Min时还等待
  两实例实际ACU到位；
- 不执行schema、GPU数据面、Node Runtime或Runtime Profile阶段；
- 不发布cluster registry revision；
- remediation budget或worker副本变化只滚control-worker；节点数变化改变三个角色共用
  的fault reserved depth，因此滚全部三个CPU角色；
- spool启用先滚spool-worker，再滚ingress；
- spool禁用先关闭ingress admission，等待spool depth和leased都为0，再缩容
  spool-worker；
- release state和Deployment metadata记录全局配置摘要，Pod template记录角色摘要，
  ConfigMap变化不会被误判为`NOOP`。

发布器在变更前保存角色ConfigMap和旧AdminConfig。Aurora或release任一步骤失败时，
CLI把Aurora恢复到计划前Min/Max；verify或stability失败时同时沿用现有CPU自动回滚，
恢复旧配置、旧副本拓扑和旧角色进程。Aurora回滚本身失败会单独记录并使命令fail
closed。只执行`kubectl rollout undo`不构成完整配置回滚。

## 9. 热更新边界

CPU配置通过环境变量在进程启动时加载，因此使用Kubernetes滚动生效，不支持通用无重启
热更新。Aurora Min/Max是独立AWS资源变更，可在部署后通过同一管理员命令在线调整，但
仍必须经过计划、审批、收敛验证和回滚。副本数、Uvicorn进程、线程池、PostgreSQL pool
和spool拓扑不适合进程内热改。

若未来确实要求部分阈值不重启即时生效，必须另行实现配置revision、全进程ACK、
mixed-revision门禁、失败回滚和状态指标。该机制不得复用cluster registry记录，也不得
绕过本文件的字段白名单和审计。
