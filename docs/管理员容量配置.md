# 管理员容量配置

本文定义管理员调整区域控制面和Aurora容量的正式入口。容量变更不修改源码，不重新
构建镜像或wheel；CLI复用当前已验签release，对Aurora执行受审计的RDS变更，并只为
需要进程重载的配置滚动受影响CPU角色。

管理员只需要做两件事：编辑`<state-dir>/admin-config.yaml`，运行
`gpu-fault-admin config --state-dir <state-dir>`。

## 1. 支持范围

当前管理员可配置：

- control-worker副本数；
- 站点拓扑：最大单个GPU集群节点数（`largestClusterNodeCount`）和受管节点总数
  （`managedNodeCount`）；
- telemetry spool enabled/disabled、spool-worker副本数和单集群spool深度
  `maxClusterDepth`（64..65536，默认1024；单集群普通遥测超过该深度后收到reserved 429。
  性能压测验收方案§13.4的1000节点单集群完整模型：1024下3000条普通遥测中1150条429，
  4096下6500条请求全部202、P0与证据无变化。单集群节点数≥512时建议设为4096；
  默认1024对应预设的256节点集群模型）；
- remediation budget的Region、cluster和resource class上限（Region为1..400：dispatcher每个tick选取最老的
  max(100, Region上限 + 50)个未结束workflow、最多400个，Region上限超过该批次时拒绝启动）。需要超过400的
  站点做的是一次有意的产品变更而不是配置：为控制面角色显式设置不小于该上限的`GPU_FAULT_WORKFLOW_BATCH_SIZE`
  （它不是管理员字段，须经评审的发布模板变更），并在同一发布中放开这里的上界；事先核对一个tick仍在15 s
  派发租约之内（约1 s + 每个workflow 0.15 s摊到dispatcher线程；增加`dispatcherWorkers`，或设置低于租约的
  `GPU_FAULT_WORKFLOW_DISPATCH_CYCLE_SECONDS`，可让它留在租约内）；
- Aurora Serverless v2 Min/Max ACU；
- Processor总队列、单集群队列、客户端退避、持久重试、完成记录保留和ingress普通准入批量延迟
  （`admissionBatchDelaySeconds`，0..0.5秒，默认0.002；缺省值不写入记录与YAML，live摘要不变，见§4.6）；
- ingress准入flush的站点级并发区间：上限`admissionFlushConcurrency`/`faultAdmissionFlushConcurrency`/
  `evidenceAdmissionFlushConcurrency`（各1..1024，默认96/48/24）与下限`admissionFlushConcurrencyFloor`/
  `faultAdmissionFlushConcurrencyFloor`/`evidenceAdmissionFlushConcurrencyFloor`（各1..1024，默认96/48/12，必须不大于
  对应上限），由3个api-ha副本×4个进程分摊，每进程取ceil(值/12)，在自己的下限与上限之间按flush时延自适应调节in-flight
  flush数（普通与故障层默认下限等于上限，即实测通过的固定上限，控制器为常量）；以及批量延迟的自适应上限
  （`admissionBatchDelayMaxSeconds`，0..0.5秒，默认0.05）；七个字段的缺省值同样不写入记录与YAML，见§4.6；
- Workflow扫描周期和dispatcher线程数；
- 离场节点自动清理开关`workflow.departedNodeCleanup`（默认`true`；缺省值同样不写入记录与YAML，live摘要不变，
  因此不在22个模板字段之内）：`false`时控制面不再自动退役离场节点的Agent、关闭其从未改动节点的workflow与
  ESCALATED incident，这些记录留给`workflow-reconcile`（管理员日常运维§10.1.1）；
- 通知批量大小和最大尝试次数；
- 原始证据保留小时数和每节点记录上限。

正式模板共包含22个管理员可配置叶子字段。node和failure-domain remediation budget
属于安全常量，运行时固定为1，不出现在模板中；旧文件里若仍写着
`maxActivePerNode: 1`或`maxActivePerFailureDomain: 1`会被接受并忽略，写成其他值
会被拒绝。

凭据、Region、cluster identity、Runtime Profile、operation allowlist、release pin、
破坏性能力开关和安全不变量不属于通用管理员配置。只有正式模板声明的字段可以修改，
不得把任意`GPU_FAULT_*`变量透传给Pod。

## 2. Release模板

源码Release包含：

```text
config/admin-config.example.yaml
```

签名deploy-host bundle安装后，同一模板位于：

```text
<deploy-host-venv>/share/gpu-fault/admin-config.example.yaml
```

模板是只读发布资产，权限为`0644`。管理员实际输入必须位于受控目录且权限为`0600`。

## 3. 首次部署

管理员首次部署前已经确定容量值时，基于Release模板准备自己的配置文件，然后使用一个
deploy命令直接应用：

```bash
gpu-fault-admin deploy \
  --cpu-cluster-arn <cpu-arn> \
  --gpu-cluster-arn <gpu-arn> \
  --state-dir /secure/gpu-fault \
  --admin-email <operations-email> \
  --config /secure/gpu-fault-input/admin-config.yaml
```

CLI在源码构建或AWS/Kubernetes访问前校验配置，把规范化值写入
`<state-dir>/admin-config/desired.json`，并把可编辑副本写入：

```text
<state-dir>/admin-config.yaml
```

首次部署不需要先执行`config`。未提供`--config`时使用release默认值，并生成默认的
`<state-dir>/admin-config.yaml`。

## 4. 已有站点修改

### 4.1 命令

```text
gpu-fault-admin config --state-dir STATE_DIR [--file ADMIN_CONFIG] [--dry-run] [--reference REFERENCE]
```

同一动词下还有一个子动作 `gpu-fault-admin config spare --state-dir STATE_DIR --node NODE [--declare|--release ...]`，用于声明或释放热备 GPU 节点；它不涉及本文的容量配置，见[管理员日常运维](管理员日常运维.md)任务表。

管理员编辑`<state-dir>/admin-config.yaml`后直接执行：

```bash
gpu-fault-admin config --state-dir /secure/gpu-fault
```

- `--file`：临时改用另一个`0600`文件作为输入；成功后CLI把规范化结果写回
  `<state-dir>/admin-config.yaml`，使它始终等于线上期望值。
- `--dry-run`：只读本地`desired.json`和YAML，打印变更计划（受影响角色、逐字段前后
  值、Aurora是否变化）后退出。不做Cosign验签，不读集群，不解析执行者身份，不写任何
  状态文件，也不迁移旧版`desired.json`。输入文件缺失时直接拒绝，不创建模板或修改
  目录权限；普通非dry-run命令仍可初始化缺失的默认模板。
- `--reference`：可选的变更单或维护窗口号，格式为3到128个字母、数字或`. _ : / -`。
  缺省时记录为`<执行者身份>:<开始时间>`。执行者身份始终自动取自
  `aws sts get-caller-identity`的caller ARN（取不到时退化为`user@host`），与
  reference一起进入审计记录；管理员不需要也不能手填身份。

文件中未出现的字段继承当前持久化值。CLI拒绝未知字段、错误类型、spool开关与副本不
一致、cluster/resource-class大于Region、`managedNodeCount`小于
`largestClusterNodeCount`、超过已验收PostgreSQL fleet连接预算的组合，以及违反§5
拓扑派生规则的组合（例如把受管节点数提到2048却不把`aurora.minAcu`提到至少20.5）。
错误信息给出下一步要运行的确切命令。

### 4.2 应用流程

不带`--dry-run`时，整条命令持有站点操作锁（与`deploy`、`join-cluster`
同一把锁），按顺序：

1. 读取`desired.json`（旧版记录先按§4.5验真并原子补齐）和YAML，计算目标配置并完整
   校验；没有变化时打印`NOOP`退出，不写任何文件。
2. 核对content-addressed Manifest与Cosign attestation，读取CPU集群中的live release
   state：必须是当前签名release且已commit，否则fail closed（§4.3的续跑例外除外）。
3. 写审计：`history/<开始时间>-<目标配置摘要>/before.json`（变更前的
   `desired.json`）、`pending.json`（变更前后配置、站点身份、签名release身份、
   执行者、reference、开始时间），然后把`desired.json`改为目标配置。
4. Aurora Min/Max有变化时先调用RDS `modify-db-cluster`，等cluster、writer和reader
   在新窗口上回到`available`（连续三次观察）；没有变化时只读核对live窗口等于变更前值
   （`verify_aurora_capacity`），不让一次apply在别人改过的窗口上记成`APPLIED`。
   实例爬到新Min之前RDS一直报`modifying`，而发布preflight要求cluster与两个实例都是
   `available`，所以提高Min的爬坡就落在这一步：Min从8提到124 ACU实测在这里等了
   742–822秒（五次，`ServerlessDatabaseCapacity`约每分钟涨10 ACU），124/128→128/128与
   128/128→8/32约两分钟，不改Aurora的apply整段只有十几秒。等待期间状态一变、否则每30秒
   打印一行`aurora-capacity-wait`（cluster与两实例状态、窗口、连续稳定次数，见
   [管理员日常运维](管理员日常运维.md) §4.1）。
5. 只滚受影响的CPU角色，完成verify/stability/commit。滚动前先做可调度性预检：按live节点的
   allocatable CPU/内存减去全部已调度Pod的requests，逐角色模拟滚动（ingress的surge Pod需要
   一个4核/4Gi的空槽，consumer新增副本长期占用余量）；放不下即在改动集群之前fail closed，
   报错指名缺少的核数与各节点余量，证据写入`<state-dir>/control-plane-apply/`（部署和运维
   手册§2.1）。ingress的surge-first滚动还逐个旧Pod模拟删除顺序：恰好一个空槽时（禁用spool
   的变更先滚api-ha，spool-worker仍占着CPU），apply在新模板之前把顺序写成旧Pod的
   `controller.kubernetes.io/pod-deletion-cost`注解（与surge节点同节点的旧Pod最后删，否则
   controller总是先删它而下一个新Pod无处可落），rollout等待期间按新Pod实际落点重算；连引导
   顺序也推不动才拒绝并指名缺核的节点与数量（"free one 4-core / 4Gi slot on a second node
   or add a CPU node"）。角色一次只滚一个并各自等待就绪：ingress → control-worker → spool-worker。
6. 提高Min ACU时，角色滚动之后再证明writer和reader的`ServerlessDatabaseCapacity`都达到
   新Min（样本不超过3分钟）。第4步已用连续三次观察确认这次变更开始并结束，这里一次新鲜
   观察即是证明，不再重复三次轮询（三次实测约38秒，一次约6秒）；样本过旧照样继续等。
   爬坡本身已在第4步走完，这一步通常一次读取就结束。
7. 写`history/<...>/after.json`和`result.json`（`APPLIED`），删除`pending.json`，
   把规范化后的完整22项写回`<state-dir>/admin-config.yaml`。

日志按步骤打印`admin-phase-begin <时间> command=config phase=<步骤>`与
`admin-phase-end ... status=ok|failed elapsed=<秒>s`：第1–3步为`release-identity`、
`attestation`、`live-release`、`apply-record`，第4步为`aurora-request`或`aurora-verify`，
第5步为`release-deploy`（其中发布驱动在release-diff之前另以`command=release-deploy`打印
`attestation`、`live-state`、`profile-plan`、`prepare`），第6步为`aurora-await`（仅提高Min时），
第7步为`apply-complete`。哪一步慢直接看它的`elapsed`。

第4到6步失败时，CLI重新读取live release state，不能仅凭发布子进程的退出码恢复
Aurora。只有证明角色仍处于原已提交配置、匹配的配置发布尚未开始角色变更，或匹配的
回滚已经验证并清理完成，才恢复变更前Min/Max和`desired.json`。
`result.json`记为`FAILED`并附`details.release_recovery`和实际Aurora补偿结果；
`pending.json`保留，管理员的YAML不被改写。

**Aurora漂移**（live窗口既不是变更前值也不是目标值，例如被没有评审记录的工具改过）在任何修改之前以
`AuroraCapacityDriftError`拒绝：本次什么都没改，所以不做Aurora补偿，`desired.json`恢复为变更前配置，
`result.json`记`FAILED`并给出三组窗口。修复二选一：`gpu-fault-admin deploy --state-dir <dir>`按`desired.json`
收敛Aurora（deploy没有评审记录，把live收敛到desired），或把live窗口显式写进admin-config.yaml使其进入评审
（desired等于live即被接受）。性能压测runner因此只核验、不修改Aurora（性能压测验收方案§8.4）。

已提交候选的收尾失败、禁用自动回滚、回滚失败、状态不完整或读取失败，均保留pending
目标，不自动降低数据库容量。发布子进程若已局部对齐本地管理配置，CLI会重新写回
pending中的规范目标与原审批信息，避免把未知结果误记成旧配置。先按错误提示调和发布，
再重跑`config`；旧版或不完整的恢复证据不能用来推定成功。
第6步仅等待实际ACU爬坡超时且角色发布已成功时，Aurora窗口和目标配置不回退，
重跑同一`config`完成等待即可。Aurora补偿本身失败也保留目标并fail closed。

### 4.3 中断续跑

同一命令在任何一步被中断后，以相同的`--state-dir`（和相同的YAML）重跑即续跑：
`pending.json`按站点身份、签名release身份和目标配置摘要匹配。上次已记录失败的重跑
是一次新的尝试，得到自己的`history/<新开始时间>-<摘要>/`目录、执行者和reference；
中途崩溃、尚无`result.json`的尝试则在原目录继续。目标配置不同的重跑会把旧的
`pending.json`记为`SUPERSEDED`后替换。

续跑对live状态的要求不变：CPU集群中未commit的live release只有在它是
`CONTROL_PLANE_ONLY`且其`admin_config_sha256`等于`pending.json`目标配置摘要、且处于
release引擎可续跑的阶段时才被接受；其他未commit状态一律fail closed，并提示先用
`gpu-fault-admin deploy --state-dir <state-dir>`完成那次发布。Aurora方面CLI只接受
live窗口仍是变更前值或目标值，其他live值按漂移fail closed。`desired.json`在中断
期间被改动也会被拒绝并指出要核对的文件。

### 4.4 状态文件

```text
<state-dir>/admin-config/
  desired.json                      权威期望配置：配置、配置摘要、三角色摘要、
                                    来源、reference、执行者身份、更新时间
  pending.json                      进行中或被中断的那一次应用；成功后删除
  history/<开始时间>-<配置摘要>/
    before.json                     这次应用开始前的 desired.json
    after.json                      这次应用结束后的 desired.json
    result.json                     APPLIED / FAILED / SUPERSEDED、release ID、
                                    受影响角色、执行者、reference、错误与Aurora详情
```

`desired.json`和`pending.json`都带摘要自校验，内容被改动即fail closed。可调度性预检的证据
（每节点余量、每角色surge/新增Pod、实际滚动顺序，以及ingress步的`steering`：`nodes_with_a_free_slot`、
预测的`surge_nodes`、带`cost`的`deletion_order`、`progress_guaranteed`、不引导时的`without_steering.stalling_order`）
在`<state-dir>/control-plane-apply/schedulability-<release>-<时间>-<pid>-<n>.json`，每次预检一份（`<n>`为同一次
apply内的序号）：每次CPU角色apply一份，回滚中未能在`/healthz`证明pin、回落到重启的层再预检一次，多一份。

### 4.5 旧版记录升级

从只包含`capacity`、旧版18字段或缺少节点数字段的20字段desired state升级时，CLI先按
旧版配置摘要和三角色摘要双重验真，再在站点操作锁内原子补齐缺失字段。旧站点缺少
Aurora字段时按历史`0.5/8`保留，不会因软件升级静默改库；新站点默认使用`8/32`。旧记录
缺少节点数时，按它自己声明的单集群队列深度反推拓扑（`min(512, depth / 4)`，历史
`1024`即256节点，受管节点数取同值），不会按新默认512读入一个该深度容不下的集群。旧
记录结构未知、内容被修改或任一摘要不匹配时仍然fail closed。`--dry-run`只读取，不
补齐。

读取已持久化或线上捕获的状态只做结构校验，不套用§5的实证下限：低于下限的旧站点是
事实，拒绝读取只会让管理员无法加载状态去计划修复。任何生成新desired的入口（文件、
preset、计划）都完整校验，低于下限的组合会被拒绝并同时点名两个字段。

### 4.6 容量预设

预设通过同一个YAML声明，没有单独的命令行参数：

```yaml
apiVersion: gpu-fault.aws/v1alpha1
kind: AdminConfig
spec:
  capacity:
    preset: 32-disabled
```

`preset`先应用，同一文件里其他显式字段再覆盖其上；非capacity字段从当前持久化
AdminConfig继承。preset命名的是一个拓扑，而拓扑决定Aurora Min ACU下限（见§5）：当前
Min ACU低于该preset下限时，计划会把Min ACU提到下限、Max ACU提到`max(当前Max, 128)`，
并像其他Aurora变更一样进入审计和RDS路径；已经高于下限的Aurora不会被降低。正式压测
使用的`124/128`高于`32-*`的下限`82`，仍必须显式设置，不能从`32-enabled`推断；
`50-*`的下限恰好是`128/128`。`preset: default`用于显式恢复release默认容量。

支持的预设（多集群拓扑按每集群256节点计，见性能压测验收方案§2）：

| preset | worker副本 | Region budget | 每集群 | 每resource class | spool | 最大集群/受管节点 | Aurora下限 |
|---|---:|---:|---:|---:|---|---:|---:|
| `default` | 6 | 20 | 5 | 2 | disabled，0副本 | 512 / 512 | 8/32（模板值） |
| `32-disabled` | 6 | 128 | 4 | 4 | disabled，0副本 | 256 / 8192 | 82/128 |
| `32-enabled` | 5 | 128 | 4 | 4 | enabled，3副本 | 256 / 8192 | 82/128 |
| `50-disabled` | 6 | 200 | 4 | 4 | disabled，0副本 | 256 / 12800 | 128/128 |
| `50-enabled` | 5 | 200 | 4 | 4 | enabled，3副本 | 256 / 12800 | 128/128 |

节点规格：`32-enabled`/`50-enabled`稳态为3 api-ha × 4核 + 5 control-worker × 3核 + 3 spool-worker × 1核
= 30核（另加系统、HyperPod operator与kueue约3核），3 × `ml.c5.4xlarge`（每节点约15.9核allocatable）可承载；
滚动最紧的一步是ingress的surge Pod，要求某节点`free ≥ 4核且≥ 4Gi`（free = allocatable − 该节点全部Pod
requests）。`config`在apply前按同一公式做可调度性预检（§4.2第5步）：恰好一个空槽可以滚（旧Pod的删除顺序
被引导），一个空槽也没有、或引导后仍有新Pod无处可落时报错指名节点与缺核数，先加CPU节点再apply。

准入批量延迟：预设不改变`processor.admissionBatchDelaySeconds`（保持release默认0.002，即2 ms）。性能压测验收方案
§13.3的调优组以0.05改善completion p99约14%、吞吐不变，但PostgreSQL `xact_rollback`由4增至59，§15第6条要求重复验证后
才作为默认，因此默认值不悄悄改动。按ingress普通准入批量上限64估算，20–50 ms的延迟在约1,000 req/s下把每批平均9.7条
（25k条用了2,553个事务）提高到约29–48条，准入事务数下降3–5×，代价是不超过该延迟值的额外接收时延；该字段改动会滚动
三个角色（processor段进入每个角色摘要），走与其他字段相同的审计与回滚路径。

准入flush并发区间：`processor.admissionFlushConcurrency`（普通遥测，默认96）、`faultAdmissionFlushConcurrency`
（P0故障层，默认48）与`evidenceAdmissionFlushConcurrency`（证据层，默认24）是**站点级上限**——同一时刻全部api-ha进程
对`gpu_fault_processor_queue`并发执行的准入INSERT事务数的最大值；`admissionFlushConcurrencyFloor`/
`faultAdmissionFlushConcurrencyFloor`/`evidenceAdmissionFlushConcurrencyFloor`（默认96/48/12，校验不得大于对应上限）
是每个进程启动时、以及中等负载下运行的**下限**。渲染器把上下限与分摊进程数一起下发
（`GPU_FAULT_PROCESSOR_{,FAULT_,EVIDENCE_}ADMISSION_FLUSH_CONCURRENCY{,_FLOOR}`与ingress的
`GPU_FAULT_INGRESS_WRITER_PROCESSES` = 3副本×4进程 = 12），每个进程各取`ceil(值 / 12)`（默认下限8/4/1、上限8/4/2；
不能整除时按向上取整后的站点总量生效），不再渲染每进程的`*_ADMISSION_BATCH_GROUPS`字面值（显式GROUPS仍按进程把上下限钉在同一值）。
下限等于上限时控制器是常量：默认配置下普通层与故障层就是实测通过的固定上限（每进程8与4），只有证据层（每进程1..2）与管理员
主动放开的区间才会自适应。进程内的控制器（`app/admission_concurrency.py`）在每次派发时决定：槽位全忙且仍有积压（饱和）、
flush时长EWMA低于打开阈值（`GPU_FAULT_PROCESSOR_{,FAULT_,EVIDENCE_}ADMISSION_FLUSH_CONCURRENCY_OPEN_SECONDS`，默认0.15 s）
时多开一个槽；EWMA超过关闭阈值（`..._CLOSE_SECONDS`，默认0.30 s）时把高于下限的余量减半（加性增、乘性减）；两阈值之间保持
不变；上限不再成为约束（槽位有空闲）时回收一个槽，突发过后回到下限，空闲站点不会持有多于下限的并发。每一次变动——开槽、
收槽或回收——都要求当前层级已完成一代flush（`max(3, 当前上限)`次），因此EWMA反映的是被评判的层级，一个慢样本不会把宽上限
一路压到下限，上限也不可能在相邻两轮里一开一收。到达时的期限投影按控制器**即将打开**的槽数（EWMA低于打开阈值时取上限，
否则取当前值）计算排队等槽的轮数，不会把正要打开的容量算作缺失而误拒。`/metrics`导出
`gpu_fault_processor_{,fault_,evidence_}admission_batch_in_flight_limit`（当前值）与
`..._in_flight_limit_raised_total`/`..._lowered_total`。

数值来源（本站integrated-32压测，同一schema v22、同一32集群突发、同样12个ingress进程，无日期）：此前上限是每进程字面值
（16 + 8 + 4），12个进程最多336个并发INSERT事务落在同一张表，负载开始的前30–65 s出现134–182个并发队列INSERT、85%活跃语句
等待`LWLock:BufferContent`的convoy，P0请求自己的INSERT在其中等到30 s期限（503）——放大器是v21唤醒探测的缓存计划，已由
schema v22修正。此后的三个校准点：**固定24**（每进程2）把问题换成了拒绝遥测——每个进程整个负载期都顶在上限、每进程积压
762–801条、4,601个请求在队列里等到期限（普通遥测reserved 503占比18.7%，预算2%），517 req/s，每次16条的flush平均0.59 s
（排队，不是存储瓶颈）；**固定96/48**（每进程8/4）通过——1,051 req/s、reserved 503与P0 503均为0、每次flush 81 ms、
每进程积压峰值60–69、数据库活跃语句峰值113持续约5 s、`BufferContent`等待1%；**自适应48..192**（每进程4..16，故障层
24..96，打开/关闭阈值1.0/2.0 s）失败——控制器让全站并发flush达到约250，队列表的页锁convoy重现（69 s风暴、活跃语句峰值
142、`BufferContent` 36%、`XactSync` 23%），每次flush平均1.08 s却低于2.0 s的关闭阈值，于是槽位一直开着而遥测按期限投影被拒
（543 req/s，reserved 503占比35.8%，P0也出现503，故障p99 28.4 s），上限还在震荡（14分钟内开81次、收51次）；从每进程4
起步也让突发的第一秒就出现拒绝。结论：这套schema上数据库能承受约100个并发准入flush、再高就convoy，
`gpu_fault_processor_queue`的页锁争用是上限的物理来源；本站历史上在192槽达到的1,400+ req/s早于v20按writer分行的账本
（当时单一计数行把writer串行化，恰好抑制了页争用），仅靠并发数在这套schema上不可复现。因此默认上限就是实测通过的固定上限
96/48/24，普通与故障层的下限等于上限（突发的第一秒必须由下限承接而不拒绝），证据层保留12..24；阈值取未争用flush 81 ms的
约2倍与4倍（0.15/0.30 s）：1.08 s的平均flush应当触发硬收槽而不是保持。故障层有独立区间，进程内也有独立的batcher与Store
I/O线程，遥测突发不会占用故障槽；深度预留（`GPU_FAULT_PROCESSOR_FAULT_RESERVED_*`）语义不变。推荐站点值即默认值；默认配置
的验收目标是本站校准点的1,000+ req/s、reserved 503与P0 503均为零，`..._in_flight_limit`在普通/故障层恒为8/4且
`..._raised_total`/`..._lowered_total`为0。
批量延迟的自适应上限`admissionBatchDelayMaxSeconds`（默认0.05，0..0.5）：flush时长EWMA超过100 ms时batcher把合并窗口从
`admissionBatchDelaySeconds`线性抬高到该上限（EWMA达200 ms时取满），恢复后回落；上限不大于基础延迟即关闭自适应
（运行时取两者较大值，只提高基础延迟仍是合法配置）。合并窗口不是"每次flush条数"的杠杆：一次flush是一个集群范围的
一个事务，它携带的是派发时该集群在本进程内排队的请求数，而不是窗口期内到达的请求数。单进程闭环模拟（32集群、8槽、81 ms
存储往返）里，无论窗口如何，16/96/400个在途请求都对应每次flush 1.0/3.0/12.5条；而把基础窗口提到20 ms使吞吐下降17%、
在饱和期把窗口撑到50 ms下降35%——派发前的等待让刚空出的槽位闲置。线上每进程约65条积压分摊到32个集群，就是每次flush
2.5条的来源；要让一次flush带8–16条，需要的是更多突发请求同时进入进程（在途请求数），不是更长的窗口。因此基础窗口保持
2 ms，自适应拉宽只在flush EWMA超过100 ms（存储成为瓶颈、语句数本身是代价）时发生，先于控制器的保持区（0.15 s）与收槽
阈值（0.30 s）。convoy的放大器——v21唤醒触发器的`NOT EXISTS`反连接在队列为空时缓存了
对整个积压做哈希的计划（一条10行INSERT读49k页、250–320 ms，直到autoanalyze才换计划）——由schema v22修正
（详细设计§3.1.3）。七个字段的缺省值不写入记录与YAML（live摘要不变）；改动同样滚动三个角色。

进程内线程数不是突发下存活探针的杠杆。同一50集群cold-connect突发的本地复现（`scripts/perf/ingress_event_loop_burst.py`）里，
解码线程32与8、flush槽位16与8的探针时延和event loop时延完全一致（最长停顿0.25–0.6 s，均为一次gen-2 GC），探针被杀的机制是
service监听套接字的accept队列（见部署和运维手册的liveness一节），因此本方案没有引入"每进程CPU线程预算"类字段，也不让并发
控制器因event loop时延收槽——收槽只会把排队从进程内挪到内核accept队列（2槽时探针中位数94 ms但1,074个503），换来503而不减少
停顿。与之相关的三个运行时变量由渲染器直接下发、不是AdminConfig字段：`GPU_FAULT_LIVENESS_PORT`（每角色service端口+10，
专用存活监听端口）、`GPU_FAULT_GC_FREEZE_AFTER_STARTUP=true`（lifespan启动末尾`gc.freeze()`：同一突发下每进程GC总耗时
9.0 s→6.6 s、吞吐+7%、最长停顿不变）、`GPU_FAULT_GC_GEN2_THRESHOLD`（默认沿用CPython的10；实测抬到100把gen-2回收从45次
降到4–5次、总耗时再降30%，但单次停顿拉长到0.45–0.59 s，对event loop是更差的交换，只建议A/B时临时设置）。

service端口的accept队列也按worker拆开：三个角色由`python -m gpu_fault.app.serve`启动，每个worker自己以`SO_REUSEPORT`绑定服务端口，
Pod能排队的已完成连接数从`somaxconn`（4096）变为`--workers × 4096`。这不是吞吐杠杆（同一复现里4,250并发cold连接下吞吐与中位数延迟在
噪声之内、尾延迟+3–11%），而是容量杠杆：连接数超过4096时共享套接字开始丢SYN（5,500并发：961 req/s、73个503、客户端p99 27.9 s），
per-worker套接字不丢（1,117 req/s、0非2xx、p99 5.35 s）。50集群preset每Pod约4,266个cold连接正好跨过这条线。随之变化的还有
`--timeout-keep-alive 5 → 100`（渲染器常量`KEEP_ALIVE_TIMEOUT_SECONDS`，高于节点侧连接池90 s的空闲上限）：节点Agent心跳（30 s）与
GPU inventory（60 s）各自保持每进程一条长连接，300 s的健康摘要仍每次重连。容量算术要记住uvicorn `--limit-concurrency 4096`把空闲
keep-alive连接也计入：设计规模12,800节点×2条通道=25,600条长连接/12个ingress进程≈2,133条/进程，剩余约1,960条供突发用；把300 s通道
也改成长连接会再加4条/节点（≈4,267条/进程）而超出该限额，因此客户端空闲上限默认保持90 s。节点侧抖动
（`GPU_FAULT_COLLECTOR_CADENCE_JITTER_RATIO` 0.1、`GPU_FAULT_COLLECTOR_STARTUP_JITTER_SECONDS` 20）把整队重启后的首次上报从15 s
窗口散到35 s，并要求静默阈值≥cadence×1.1+35+47 s（默认值全部满足，由`tests/collectors/test_cadence_jitter.py`守住）。

### 4.7 PostgreSQL连接预算

运行时、管理员校验和容量runner共用
`postgres_capacity.PostgresPoolCapacity`，按每个角色的副本数、每Pod进程数、
pool上限以及独立LISTEN连接计算总上限。worker每进程还需1条processor queue与
2条dispatcher连接；spool-worker需1条spool连接。每个regional进程另预留1条按需
启动的remote-command claim连接，不能因为当前尚未收到long poll就省略。

默认disabled组合的上限为1164，低于原1200预算；3个spool副本加5个worker的enabled
预设为1190，低于原1240预算。enabled沿用6个worker则为1302，不能通过新目标校验。
只有显式选择preset时才计算其默认worker数；管理员显式覆盖不会被悄悄缩小，普通升级
也不自动改写现有拓扑。旧配置允许只读加载以便计划修正，结构、摘要和新目标校验不变。

这是本方案进程的连接上限，不是实测并发量，也未替Aurora管理连接、发布surge、
查询工具或其他应用预留容量。历史压测中的6-worker enabled结果仍是历史配置，
不代表当前preset或授权提高1200/1240的预算。

### 4.8 热表物理布局与后台压实

容量预设假定 Store 的热表索引与小表处于紧凑布局。一次批量删除（一轮 32 集群正式压测的拆卸、
一个集群退出 fleet）会把 `gpu_fault_processor_queue` 的 9 个索引、`gpu_fault_gpu_metric_latest` 的
2 个索引和 lanes/queue counts/priority shards 三张小表留在高水位：同一 release、同一准入默认值下，
ingress 吞吐从全新 store 的 1,572 req/s 跌到 538 req/s（49% 活跃语句等 `LWLock:BufferContent`），
只重建索引、`VACUUM FULL` 三张小表就回到 1,141 req/s。控制面 worker 的周期任务 `store-compaction`
（`GPU_FAULT_STORE_COMPACTION_INTERVAL_SECONDS`，默认 300 s，`0` 关闭）按目录事实自动做这件事，
并导出 `gpu_fault_store_hot_table_heap_pages_per_live_row{table}`、
`gpu_fault_store_hot_table_index_pages_per_live_row{table}`、
`gpu_fault_store_hot_table_index_min_entries_per_page{table}`、`gpu_fault_store_hot_table_index_max_pages{table}` 与
`gpu_fault_store_hot_table_due_actions{table}`；控制面 ADOT 的 keep 列表把这些族连同
`gpu_fault_store_compaction_*` 计数与时钟、`gpu_fault_store_bloat_scan_timestamp_seconds` 一起送进 AMP，
控制面 Pod 换掉之后仍能在 AMP 查到任务最近一次运行和重建的时刻；这些数值不依赖 planner 统计目标或代价模型，
压测 runner 把它们写进每轮 `summary.json` 的 `store_bloat`。判定看的是每个 ≥64 页索引自己的密度，不是每活行索引页数——
队列只剩两行活行时 149 页索引读作 74.5 每活行索引页而无一索引够到下限，`due_actions` 为 0 才是结论（管理员日常运维 §10.3）。阈值（索引 ≥64 页且每页活条目 <8；小表 ≥16 页且
每页活行 <4）不是容量参数，不随 preset 变化；大表的堆与 TOAST 只由 `gpu-fault-admin store-maintenance` 在维护窗口
回收（管理员日常运维 §10.3），它们约占吞吐的四分之一。调整该变量走 ConfigMap 环境变量，不属于 `admin-config.yaml`
的容量预设字段。

## 5. 配置文件格式

当前模板内容为：

```yaml
apiVersion: gpu-fault.aws/v1alpha1
kind: AdminConfig
spec:
  capacity:
    controlWorkerReplicas: 6
    largestClusterNodeCount: 512
    managedNodeCount: 512
    telemetrySpool:
      enabled: false
      replicas: 0
      maxClusterDepth: 1024
    remediation:
      maxActiveRegion: 20
      maxActivePerCluster: 5
      maxActivePerResourceClass: 2
  aurora:
    minAcu: 8
    maxAcu: 32
  processor:
    maxQueueDepth: 65536
    maxClusterQueueDepth: 4096
    retryAfterSeconds: 2
    retryBackoffSeconds: 1
    retryBackoffMaxSeconds: 30
    completedRetentionSeconds: 600
    admissionBatchDelaySeconds: 0.002
    admissionBatchDelayMaxSeconds: 0.05
    admissionFlushConcurrency: 96
    admissionFlushConcurrencyFloor: 96
    faultAdmissionFlushConcurrency: 48
    faultAdmissionFlushConcurrencyFloor: 48
    evidenceAdmissionFlushConcurrency: 24
    evidenceAdmissionFlushConcurrencyFloor: 12
  workflow:
    pollIntervalSeconds: 5
    dispatcherWorkers: 8
  notificationDelivery:
    batchSize: 25
    maxAttempts: 8
  evidence:
    retentionHours: 24
    maxRecordsPerNode: 10000
```

YAML里的字段名是`desired.json`中snake_case字段名的camelCase拼写，两者由同一份
schema派生，只声明一次。文件中未出现的字段继承当前持久化值。普通代码升级保持当前
配置，不会意外恢复默认。fault reserved depth、global admission guard、retryable
response age、cleanup批次、workflow batch、notification poll/lease/backlog grace等
内部参数由代码根据公开字段或固定生产契约派生，不进入管理员模板。

`largestClusterNodeCount`和`managedNodeCount`是拓扑输入，不是调优项；四条派生规则
都来自本仓库的压测证据（性能压测验收方案§8.4、§13.3–§13.4），由同一份代码为CLI校验、
两个manifest renderer和运行时启动自检共用：

| 规则 | 依据 |
|---|---|
| `processor.maxClusterQueueDepth >= 4 x largestClusterNodeCount` | §13.4：单集群1000节点在深度1024下产生243个HTTP 429，提高到4096后为0 |
| `aurora.minAcu >= ceil(managedNodeCount / 100, 0.5 ACU)` | §13.3：约12800节点在`0.5/96 low-start`下产生3076个HTTP 503，预置Min≈124–128后为0 |
| `GPU_FAULT_INGRESS_NORMAL_CONCURRENCY = clamp(ceil(managedNodeCount / 5), 1000, 3584)`（仅 ingress 角色） | §8.4：50 集群 preset（12800 节点）在固定 1000/进程、等 2 秒下，六次实跑普通遥测 reserved 503 占比 0.58–3.85%，32 集群 preset（8192 节点）为 0；上限 3584 使其与 256 个 fault 槽位合计仍低于 uvicorn `--limit-concurrency 4096` |
| `GPU_FAULT_PROCESSOR_FAULT_RESERVED_CLUSTER_DEPTH = max(maxClusterQueueDepth / 8, largestClusterNodeCount)` | 产品要求：整集群相关故障是每节点一条fault优先请求，落在同样多的node lane上，预留必须容下一整波 |

默认值`512 / 512 / 4096 / 8`满足全部四条（512节点的Aurora下限为5.5 ACU，普通遥测并发取下限 1000）。4个512节点
集群的站点必须同时把`managedNodeCount`写成2048并把`minAcu`提到至少20.5。节点数与
`GPU_FAULT_PROCESSOR_FAULT_RESERVED_*`一起渲染进三个CPU角色的ConfigMap
（`GPU_FAULT_CAPACITY_LARGEST_CLUSTER_NODE_COUNT`、
`GPU_FAULT_CAPACITY_MANAGED_NODE_COUNT`），运行时在启动时拒绝预留小于最大集群节点数的
环境，`/metrics`以`gpu_fault_capacity_largest_cluster_node_count`和
`gpu_fault_capacity_managed_node_count`两个gauge导出。回滚捕获线上AdminConfig时，只
读取ConfigMap中实际存在的节点数；线上没有声明时按上文旧记录规则从捕获到的深度反推，
不用release默认值补位。

## 6. 优先级与省略字段

运行时配置优先级从高到低为：

1. 安全不变量和专用审批；
2. Secret、release身份和兼容性pin；
3. 规范化AdminConfig；
4. role-split renderer生产默认；
5. 应用代码中的`os.getenv`兜底默认。

AdminConfig在部署环境合并时覆盖同名shell变量，并被固化到角色ConfigMap。显式`env`
与`envFrom`重复、未知字段或越界组合都会在应用前失败。

首次部署没有历史`desired.json`，配置文件省略字段时使用AdminConfig默认值。已有站点
省略字段时继承当前`desired.json`值，适合用部分`--file`只修改少数字段。成功应用后
`<state-dir>/admin-config.yaml`始终写出完整22项；要恢复默认值应显式填写模板默认值，
容量整体也可写`preset: default`。

## 7. 生效与回滚

配置摘要独立于代码release ID、镜像摘要和wheel摘要。config-only release：

- 不上传或重建任何代码制品；
- Aurora字段变化先调用RDS API并等待cluster、writer和reader在新窗口上可用，再滚
  角色（RDS爬到新Min前一直报`modifying`，所以提高Min的爬坡在滚角色之前，8→124 ACU约
  13分钟）；提高Min时在角色滚动之后再用一次新鲜观察证明两实例实际ACU到位；
- 不执行schema、GPU数据面、Node Runtime或Runtime Profile阶段；
- 不发布cluster registry revision；
- remediation budget或worker副本变化只滚control-worker；节点数变化改变三个角色共用
  的fault reserved depth，因此滚全部三个CPU角色；`workflow`段（含`departedNodeCleanup`）进入每个角色的
  摘要，改动同样滚动全部三个CPU角色；
- 角色一次只滚一个、各自等待就绪，顺序为ingress → control-worker → spool-worker（ingress的surge Pod
  需要节点上一个空槽，consumer新增副本会占掉它；ingress旧Pod的删除顺序由预检决定并写成`pod-deletion-cost`，
  rollout超时前先打印卡住诊断）；spool启用也按此顺序：spool是持久表，spool-worker
  就绪前ingress spool的请求在表里等待，超过深度上限的请求以503 Retry-After退回由Agent重试；只有当该
  顺序放不下而某个角色的副本缩减能腾出余量时，预检才把缩减的角色排到前面，并把实际顺序记入证据；
  重跑（§4.3）时渲染结果与live模板一致的角色不再滚动，预检也不为它要求空槽；
- spool禁用先关闭ingress admission，等待spool depth和leased都为0，再缩容
  spool-worker；
- release state和Deployment metadata记录全局配置摘要，Pod template记录角色摘要，
  ConfigMap变化不会被误判为`NOOP`。

发布器在变更前保存角色ConfigMap和旧AdminConfig。verify或stability失败时沿用现有
CPU自动回滚，恢复旧配置、旧副本拓扑和旧角色进程；外层CLI必须按§4.2验证恢复证据，
才能补偿Aurora Min/Max。目标已commit、回滚未完成或结果未知时不得自动补偿。
Aurora补偿失败单独记录并fail closed。只执行`kubectl rollout undo`不构成完整配置回滚。
发布器的自动回滚与`deploy --rollback`只恢复角色配置、副本拓扑和角色进程，不改
Aurora容量窗口：`desired.json`的`aurora`保持回滚前的期望值，前一发布快照里的
`aurora`来自当时的release state（不再由解析默认值补齐），回滚也不会把它写回。

## 8. 热更新边界

CPU配置通过环境变量在进程启动时加载，因此使用Kubernetes滚动生效，不支持通用无重启
热更新。Aurora Min/Max是独立AWS资源变更，可在部署后通过同一管理员命令在线调整，但
仍必须经过校验、审计、收敛验证和回滚。副本数、Uvicorn进程、线程池、PostgreSQL pool
和spool拓扑不适合进程内热改。

若未来确实要求部分阈值不重启即时生效，必须另行实现配置revision、全进程ACK、
mixed-revision门禁、失败回滚和状态指标。该机制不得复用cluster registry记录，也不得
绕过本文件的字段白名单和审计。

## 10. 控制记录保留

控制记录（incident/workflow 及其关联 marker、通知、completion 记录）的 archive-first 保留**缺省开启**
（控制面组件审查 2026-09-08 的决定），管理员不需要改任何文件；`site.yaml` 缺省等价于：

```yaml
spec:
  retention:
    controlRecordRetentionDays: 30          # 缺省 30；显式写 0 才关闭
    # archiveS3Uri: s3://<bucket>/<prefix>  # 可选；缺省按账户/Region/站点推导
    # archiveIntervalSeconds: 600           # 可选；归档扫描周期，缺省 600
```

不写 `archiveS3Uri` 时，站点加载与 bootstrap 都把目标解析为
`s3://gpu-fault-control-records-<account>-<region>/<site>/control-record-archive`
（account 取 `spec.cpu.eksArn`；首次 bootstrap 尚无 site.yaml 时取 CPU 集群身份）。首次 bootstrap 与每次 `gpu-fault-admin deploy --state-dir` 都会：

1. bootstrap 任务 `control_record_archive_bucket` 创建该桶（不存在时；站点 Region，us-east-1 不带
   LocationConstraint）并在每次运行时强制开启版本控制、SSE-S3 默认加密和 Block Public Access，
   已有桶也会被收敛到这三项；`head-bucket` 只把 404/NoSuchBucket 当作"不存在"，AccessDenied 直接报错。
2. 控制面 pod identity 角色被授予该 prefix 的 `s3:PutObject`（归档器只写不读不删对象）。
3. `GPU_FAULT_CONTROL_RECORD_RETENTION_DAYS / ARCHIVE_S3_URI / ARCHIVE_INTERVAL_SECONDS` 只渲染进
   control-worker（只有它运行归档器）；`GPU_FAULT_CONTROL_RECORD_ARCHIVE_BATCH_SIZE` 缺省 200。
4. deploy 预检 `control_record_archive_bucket` 用只读 `s3api get-bucket-location` 核对桶存在且在站点
   Region，不满足即拒绝发布（bootstrap 任务在预检之前运行，正常情况下它已经建好）。

桶缺失时归档 put 失败只计入 `gpu_fault_control_record_archive_errors_total` 并在下一轮重试，
**不会**删除任何 live 记录（先归档、校验 SHA、再删）。

**关闭**：在 `site.yaml` 显式声明 `spec.retention.controlRecordRetentionDays: 0` 再 deploy，归档器与
incident/workflow 删除全部停止；桶与对象保留。`GPU_FAULT_MARKER/NOTIFICATION/COMPLETION_RECORD/REGISTRY_MEMBER_RETENTION_SECONDS`
是独立的无归档清扫（缺省 30 天 / 30 天 / 30 天 / 1 天），各自 `≤0` 关闭，遵守"incident 仍存在
即保留"的规则。
