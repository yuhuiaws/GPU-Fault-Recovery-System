# GPU 故障处理系统安全与参数参考

本文汇总管理员需要审批的硬约束和配置边界。日常查询先看按类别整理的
[管理员环境变量参考](管理员环境变量参考.md)；完整机器清单由代码生成的
[环境变量参考](环境变量参考.md)提供。

## 1. 不可放宽的生产约束

1. 受管 GPU HyperPod 必须为 EKS 编排且 `NodeRecovery=None`。
2. 本方案永不调用 `BatchReplaceClusterNodes`；
   `GPU_FAULT_ALLOW_HYPERPOD_REPLACE` 恒为 `false`。
3. HyperPod Job Auto Restart、EKS auto-resume 和 Slurm auto-resume 必须禁用。
4. 未知策略、缺少证据、版本不一致或 workload 状态未知时必须 fail closed。
5. CPU 控制面不持有 GPU kubeconfig；每集群 Executor 只操作本地 GPU EKS。
6. 每个 GPU 集群使用独立 token、IRSA、namespace allowlist 和 Node Action key。
7. 禁止 `curl -k`、`verify=false`、未签名 Node Action 和在线扩大 allowlist。
8. 生产 Agent endpoint 必须使用 HTTPS，控制面只信任签名 heartbeat 携带的节点
   证书；每个 `RegionalClusterRegistration.agent_endpoint_allowed_cidrs` 必须收口到
   该 GPU 集群节点子网。
9. 节点mutation的workload ownership只接受120秒内刷新过的active Observation；
   stale记录必须从ownership排除并单独告警。当前fresh overlap为critical，
   Alertmanager使用5秒group wait；stale Observation为warning。

## 2. 破坏性能力阶段

| 阶段 | 能力 | 上线前证明 |
|---|---|---|
| A | 观察、取证、simulation | 事件、allocation、Collector、Agent 和证据链完整 |
| B | 隔离、停止和重启 workload | 新旧 attempt 不重叠，provider taint 不被删除 |
| C | quiesce、无 GPU client 校验、GPU/fabric reset | fail-safe timer、签名、fencing 和动作后验证 |
| D.1 | HyperPod reboot | `NodeRecovery=None`、二次 cluster 确认、fencing、provider 幂等和重启后验证 |
| D.2 | warm-spare `nodeReplace` | `HEALTHY_WARM_SPARE_ONLY`、同规格健康 spare、原子全量分配和替换后验证 |

不能因为节点侧开关已打开就跳过控制面 allowlist、Runtime Profile owner 或维护窗口。
当前 `regional-hyperpod-safe` Profile 的 `nodeReboot` 和 `nodeReplace` 同时由
`gpu-fault-hyperpod-adapter` OWN，因此 D.1/D.2 是分开验收的子阶段，不是两个独立
环境开关。只批准 D.1 时必须发布新的 Profile version，将 `nodeReplace` 保持为
`OBSERVE`；不得依赖关闭 spare coordinator 来阻止替换。

D.2 只允许从已纳管的健康 warm-spare 池执行本地切换，故障节点保持隔离且不被销毁。
`GPU_FAULT_ENABLE_HYPERPOD_SPARE_FAILOVER=true` 是拒绝回退到 provider replace API
的安全锁，不是单独的动作授权；必须同时保持
`GPU_FAULT_ALLOW_HYPERPOD_REPLACE=false`。健康 spare 不足时整个事务失败，不得部分
激活，也不得调用 `BatchReplaceClusterNodes`。

`BatchReplaceClusterNodes` 不仅由环境变量和 IAM 禁止：运行时 provider client
协议已移除该方法，任何 `HyperPodAction.REPLACE` 进入 provider submit 都直接失败。

## 3. 配置事实源

| 配置类型 | 正常事实源 |
|---|---|
| 区域拓扑、身份和健康目标 | `state-dir`中由CLI生成的内部site |
| AWS站点基础设施 | ARN bootstrap state和Aurora installation resource registry |
| 低层发布输入 | CLI 临时生成的 `regional-release.json` |
| Runtime Profile | 开发者维护template；`release-deploy`生成不可变source快照和内容寻址version |
| Runtime Profile审批 | `state-dir/release-deploy/profile-plan.json`、活动审批和按计划摘要归档的消费记录 |
| release artifact | `dist/current-release.json` |
| GitHub main CI候选只读凭据 | 权限`0600`的`GPU_FAULT_GITHUB_TOKEN_FILE`；仅clean `HEAD == origin/main`候选恢复使用 |
| 管理员容量期望值 | `state-dir/admin-config/desired.json`；由CLI生成、摘要校验，不含Secret |
| 管理员容量计划和审批 | `state-dir/admin-config/pending.json`（在飞或被中断的那一次 apply）、`desired.json` 和按计划SHA归档的审计 |
| CPU 非敏感配置 | 按 core/postgres/processor/telemetry/notification/recovery 拆分的 ConfigMap |
| Processor 重试与完成并行度 | 由角色化 processor ConfigMap 生成；生产 backoff `1..30s`、completion cluster concurrency `1`，提高到 2/4 前必须通过 CAP-005 |
| 修复并发预算 | `GPU_FAULT_REMEDIATION_MAX_ACTIVE_*`；生产默认值由代码固定，显式覆盖才进入配置；Region、cluster、node、failure domain 和 resource class claim 随 workflow lease 持久化。failure domain 来自 SXID 的 fabric partition 与 deploy/join/remove 自动渲染的节点映射 ConfigMap `gpu-fault-failure-domain-map`（标签键取自 site.yaml `spec.failureDomainLabels`；`GPU_FAULT_REMEDIATION_FAILURE_DOMAIN_MAP`，可选挂载，存在即必须合法，渲染侧在 apply 前用同一加载器校验） |
| Secret | Kubernetes Secret、Secrets Manager 或受控文件引用 |
| 区域 registry runtime | Aurora 不可变 revision/head；Secret 仅 bootstrap/灾备 |
| 节点配置 | Installer 生成的 `/etc/gpu-fault/*.env` |
| 管理员常用参数 | [管理员环境变量参考](管理员环境变量参考.md) |
| 完整机器清单 | [环境变量参考](环境变量参考.md) |

管理员不得手工修改内部site、低层release JSON、`regional-env.sh`或在线
`kubectl set env`来改变身份或策略。`regional-env.sh`和直接release JSON只用于详细
手工流程和break-glass。

完整环境变量清单不是通用写接口。管理员配置仅开放正式模板中的20项控制面容量、
Aurora Min/Max、队列/重试、Workflow调度、通知投递和证据保留字段；凭据、身份、
Runtime Profile、operation
allowlist、release pin、破坏性开关和安全不变量必须继续使用各自专用事实源。首次部署可用
`deploy --config`导入权限`0600`的严格YAML；已有站点编辑
`<state-dir>/admin-config.yaml`后执行带审批引用的`gpu-fault-admin config`。计划SHA
由CLI内部生成和归档，不是管理员参数。

CPU容量配置通过滚动生效，不支持通用无重启热更新；Aurora Min/Max通过受审计RDS事务
在线调整，并要求双实例收敛与失败回滚。只有未来明确实现独立配置revision、全CPU进程
ACK、mixed-revision门禁和回滚后，才允许把其他白名单字段标记为hot-reloadable；
不得复用cluster registry记录来绕过这些门禁。

## 4. Release 与 Runtime Profile

- Control Plane、Executor、Node Runtime wheel 和 Node bundle 必须来自同一份
  签名的schema v3 release manifest；Manifest还必须覆盖渲染后资源摘要、renderer、
  `uv.lock`、Node template及runtime/installer/DCGM/ADOT image digest。
- schema v3 runtime image必须由CI预装锁定依赖。生产Pod和Schema Job不得在启动时执行
  `pip install`；部署机只验证attestation签名和摘要。共享OCI image中的
  `/opt/gpu-fault/control-plane`与`/opt/gpu-fault/executor`必须分别安装Manifest声明的
  component wheel，系统Python不得回退到完整项目包。
- dirty源码只能由统一`gpu-fault-admin deploy`内部准备器生成`staging_only=true`的隔离
  测试release。普通
  `release-deploy`和生产验签默认拒绝该等级；只有最终clean commit和Release CI可以
  生成生产release。
- Runtime image复用只能依据完整image input digest：Dockerfile、固定base digest、
  runtime lock、platform、build args、control-plane/executor wheel SHA和module
  digest。Registry中tag、platform或任一config label不一致时必须fail closed。
- BuildKit cache必须与immutable runtime repository分离。Cache repository允许mutable
  tag但只用于layer加速；ARN bootstrap只清理超过7天的untagged cache artifact，保留
  当前cache tag。已有生命周期策略不一致时必须fail closed，release Manifest永远只能
  引用校验后的immutable OCI digest。
- 容量压测默认使用隔离control plane/registry。synthetic集群必须携带run ID和TTL；
  live registry mutation需要双确认，且所有执行路径必须在`finally`中完成可重试、
  可验证的teardown。不得通过让status忽略`perf-cap-*`掩盖残留。
- 生产部署机必须从Cosign签名的离线deploy-host bundle安装Python环境。bundle只包含
  hash锁定wheel、项目wheel、工具清单和可选审核后二进制，不得包含凭据。在线初始化只
  用于开发checkout，`gpu-fault-admin deploy`不得安装或升级宿主机软件。
- 管理员CLI必须来自独立`gpu-fault-deploy-host` distribution；生产Control Plane
  Runtime wheel/image不得包含`gpu-fault-admin`入口、`admin_cli.py`或
  `deploy-host-tools.json`。部署机代码变化不得伪装成应用Runtime变化。
- GitHub候选token不得写入site、源码、普通artifact、日志或命令参数；候选恢复缺少凭据
  或API暂时不可用时可回退本地完整门禁，但已下载候选的签名、repository、commit/tree、
  gate或文件清单不匹配时必须fail closed。
- 物理 wheel SHA-256 证明实际文件，组件 `module_digest` 证明行为内容；Agent 和
  Executor 的 required/compatible 窗口同时校验两者。
- Runtime Profile 按 `profile_version` 在区域控制面共享。
- Profile策略变化必须先由deploy生成计划，再通过同一条
  `gpu-fault-admin deploy --state-dir ... --approve-profile-plan <plan_sha256> --reference ...`
  写入一次性state审批并继续部署；命令必须把管理员审核并记录到变更单的`plan_sha256`与
  当前计划持锁比较，一致后才允许写入。没有单独的审批动词；
  环境变量和手工JSON不得替代这个显式参数。计划必须直接展示
  `site_identity.site_name/aws_region/cpu_eks_arn`并以`site_identity_sha256`校验；
  审批同时绑定原/目标版本、策略/模板/快照摘要和live baseline，任一漂移都必须失效重审。
- Profile审批只在verify、stability和commit成功后消费。发布失败且计划未漂移时保留用于
  幂等续跑；成功消费或被新计划取代后不得重放。审批与发布必须由同一state-dir文件锁
  串行化。管理员完整命令和异常处理见
  [Runtime Profile变更审批](管理员Profile变更审批.md)。
- PostgreSQL schema 当前为 v7；生产业务 Pod 的
  `GPU_FAULT_POSTGRES_AUTO_SCHEMA_INIT=false`，DDL 只能由 ensure Job 执行。
- 同一版本内容不可覆盖；策略变化必须使用新版本。
- CPU required profile、Collector、Watcher workload annotation 和 Node Agent config
  必须引用同一版本。
- Profile变化finalize前，旧Profile的非终态workflow和PENDING/RUNNING workload必须
  全部归零；当前实现不允许隐式双版本过渡。
- reset、fabric reset或动作后验证失败升级为reboot/replace时，如果新workflow包含
  `RESTART_WORKLOAD`，必须从失败workflow继承同一组`cluster_id`、`job_id`、
  `source_attempt_id`、`source_gpu_count`和`restart_budget`。字段缺失或多个来源不一致时
  升级workflow必须保持`BLOCKED`，不得使用默认值重新授权一次训练重启。
- Node Runtime升级按`FleetDeployment.max_unavailable/waves`推进，并同时校验
  artifact、bundle、template和签名ACTIVE heartbeat。
- 共享release默认一次只升级一个GPU集群；跨集群并行度由站点配置的
  `upgradeMaxParallelClusters`（默认1、最大8）显式开启，不是状态语义，也不改变
  自动回滚：回滚始终按实际mutation时间逆序串行。任一集群失败会阻止尚未开始的集群，
  已在推进的集群跑完当前波次序列后统一进入`PAUSED`或`FAILED`。站点配置中的
  `upgradeMaxUnavailable`默认0（auto，取规模上限）、最大32，upgrade第一波固定1；UNKNOWN故障域强制1，
  已知故障域按节点数把单集群上限自适应为4、8、16或32并均衡分布，显式1..32则取配置值与上限的较小者。
  `rollbackMaxUnavailable`默认2且最大4，rollback第一波固定1；少于6节点、UNKNOWN
  故障域或证据不完整时强制1，6至31节点最多2，至少32节点才允许4；多故障域每域每波
  最多1。
- 涉及GPU或Node Runtime的候选在schema Job和CPU rollout前必须完成
  `candidate-preflight-ready`：对候选GPU/DCGM/Reconciler/Installer Manifest执行
  server-side dry-run，校验Action key/Secret引用，并通过只读host预检证明bundle/wheel
  摘要、磁盘、Python/systemd/驱动工具、quiesce状态和旧runtime回滚槽。该门禁失败时
  不得滚动CPU/GPU进程、apply Reconciler或创建Fleet wave。
- GPU/DCGM Manifest在实际apply前必须再次server-side dry-run，防止早期门禁后发生的
  admission或RBAC漂移导致部分资源mutation。
- CPU候选发布后必须等待Agent重新向候选控制面刷新心跳；每个节点波次在claim前执行
  有界重试安全门，并要求wave外Agent保留足够lease余量，claim后立即用更小余量复检。
  一次性瞬时检查不得作为开始节点mutation的依据。
- 每个rollback wave开始前必须证明Executor全部Ready、wave外Agent ACTIVE且心跳有效、
  remote command为0、无活动破坏性workflow；任一节点失败不得开启下一波。
- upgrade、join和rollback在第一台节点mutation前还必须执行动态只读barrier：重新校验
  目标Node UID/Ready/cordon/隔离taint和failure domain，并验证Executor、remote command、
  破坏性workflow及Agent lease。upgrade的确定性候选与host事实必须已在CPU rollout前
  证明；join和rollback若没有可复用的当前候选证明，仍在本地流程中先执行同一只读host
  预检。只读host预检Job可以创建和清理自己的Pod/Job，但host root必须只读，禁止写节点
  文件、annotation或systemd。
- Node Runtime候选必须先安装到`/opt/gpu-fault/releases/<artifact-sha>/venv`并校验，
  再原子切换`/opt/gpu-fault/current`。旧槽位和首次legacy `/opt/gpu-fault/venv`
  在rollback window内不得删除或原地覆盖。
- terminal event是attempt Observation的单调终态屏障。保存terminal event必须在同一
  Store事务中把对应Observation转为终态；后到的`PENDING/RUNNING`不得恢复active ownership。
- cluster registry只有`ACTIVE`成员可派发操作；`PENDING/FAILED/ROLLED_BACK`只保留
  接入、验证和审计能力。并发join必须使用单集群CAS transition，禁止从过期候选site
  全量覆盖registry revision。同一站点的join CLI全事务串行；单个batch最多4路，并受
  全局64节点Installer预算约束。Secret灾备副本也必须使用`resourceVersion` CAS。
- join候选verify必须绑定source/candidate site、live release identity、registry
  generation/content和完整cluster state，并在15分钟内提交。site、release state与
  Aurora资源注册先完成；`ACTIVATION_STARTED`之后只允许fail-forward，不得把ACTIVE
  集群转换为FAILED/ROLLED_BACK后清理。
- 首次多ARN deploy只为首个基线GPU集群创建token、IAM、NAT白名单和Private Hosted Zone
  VPC关联。关联按VPC去重；remove与join共用站点事务锁，Route53 ChangeInfo达到`INSYNC`
  且实际关联消失后才允许提交移除。
- deploy/bootstrap、Profile审批、AdminConfig、join/remove和uninstall必须竞争同一个
  state-dir mutation锁；拿锁后重新加载site并校验CPU稳定锚点，禁止并发覆盖site、
  bootstrap state或release state。
- commit/rollback先持久化已提交/已回滚终态，再清理临时Secret备份。清理失败只能幂等
  续清理，不得把已经越过不可回退点的release重新标成可回滚。
- 禁止直接删除incident/workflow/plan数据库行或手工改写workflow JSON。已由恢复
  successor收敛的历史`BLOCKED`记录只能通过
  `gpu-fault-admin workflow-reconcile`（`--dry-run` 只看计划，去掉即执行）处理；必须重新校验fencing、
  lease、remote command、provider动作、source plan和GPU节点隔离状态，成功后仅转为
  `SUPERSEDED`并保留完整审计，最终删除仍走S3 archive-first。
- Agent artifact/compatibility digest、config digest、protocol 或 Runtime Profile
  任一漂移时，节点动作必须被 compatibility 门禁拒绝；Executor 领取命令前同样校验
  artifact、compatibility digest 和 protocol。

## 5. 凭据边界

| 凭据 | 允许位置 | 禁止位置 |
|---|---|---|
| execution token | CPU Secret、CPU Pod | GPU EKS、文档、日志 |
| cluster token | CPU registry、对应 GPU Secret、目标节点 env | 其他 GPU 集群 |
| fleet master | CPU Secret、可信部署机短期文件 | GPU Secret、节点 |
| per-node action key | CPU/GPU key map、对应节点 | 其他节点 |
| CA 私钥 | Secrets Manager 等 PKI 存储 | ConfigMap、节点 |
| CA 公钥 | GPU Secret、节点 trust bundle | 无 |
| Aurora 密码 | Secrets Manager、Kubernetes DSN Secret | shell 参数、普通 artifact |

### 5.1 邮件通知边界

- `adminEmail`是站点运维联系人；`emailSender`是已验证SES identity；
  `emailRecipients`是独立、可多值的接收列表，三者不得在实现中强制相等。
- `emailSubjectPrefix`只用于站点环境标识。SES发送层会统一加入site、Region、
  AWS account和cluster上下文，避免同名集群邮件被误判。
- SNS原生email subscription的发件人为AWS管理的`no-reply@sns.amazonaws.com`；
  `emailSender`仅控制本方案直接发送的SES故障/动作通知。
- SNS确认请求绑定Topic generation、endpoint、真实Subscription ARN和48小时窗口；
  pending期间不得重复`Subscribe`。同Topic/邮箱出现多条confirmed或
  confirmed+pending时必须fail closed，不自动猜测应删除哪一条。普通deploy/rollback
  不得删除站点告警Topic；只有正式uninstall按installation registry处理。
- 节点、workload、Incident和Workflow标识必须来自当前事件或持久状态；生产模板禁止
  写入示例节点名、固定HyperPod实例ID或测试fixture标识。
- 邮件中的kubectl审批命令必须显式携带context，context未知时使用
  `GPU_FAULT_KUBE_CONTEXT`必填保护，禁止回退当前kubectl context。
- `vendor-ticket-*`是本方案内部支持升级记录，不代表AWS Support Case已创建。
  模板只能列出实际FAILED的Workflow operation，不得笼统宣称reset、reboot和replace
  均已执行失败。
- 固定标题、处置说明或字段变化时必须提升`template_version`，保证dedup和审计能够
  区分新旧模板。

## 6. 上线否决项

以下任一项失败都不得进入 active：

- production attestation既没有绑定已验签的main CI gate，也没有来自受信本地与
  `make check`加PostgreSQL stress等价的完整门禁；
- `make release-preflight`或CAP-005 PostgreSQL 16压力套件
  （8×40、JUnit零skip）未通过；
- Runtime Profile 有 warnings；
- required/compatible pin 不符合发布阶段；
- SES 或 AMP/SNS 没有可用接收端；
- Executor claim、Agent heartbeat 或 Collector freshness 不满足；
- NLB/TLS、Aurora credential refresh 或证书有效期未验证；
- 破坏性步骤缺少 adapter owner、签名、fencing 或 action 后验证；
- Agent endpoint CIDR 为空、使用 HTTP 或签名 heartbeat 未携带 TLS 证书；
- 容量测试出现持续 429/503、队列增长或数据库连接耗尽。
- 发布后120至300秒稳定窗口出现新Pod重启、持续队列增长、非终态远程命令或critical
  firing alert。正式稳定窗口前只允许对`GpuFaultStoreIoRejected`执行最多420秒的
  有界收敛等待，且必须先证明所有运行中CPU Pod的新序列带`process_id`并为0；其他
  critical、重启、非终态命令或超时仍立即否决，不能把等待写成告警豁免。
  Executor internal error告警必须依据最近错误时间戳，不得对会随retention清理下降的
  保留记录数使用counter `increase()`。

详细门禁见[部署和运维手册](部署和运维手册.md) §2、§6、§7 和 §10。
