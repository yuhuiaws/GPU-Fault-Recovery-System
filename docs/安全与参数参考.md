# GPU 故障处理系统安全与参数参考

本文汇总管理员需要审批的硬约束和配置边界。完整参数由代码生成的
[环境变量参考](环境变量参考.md)提供；本文不复制 500 余个环境变量。

## 1. 不可放宽的生产约束

1. 受管 GPU HyperPod 必须为 EKS 编排且 `NodeRecovery=None`。
2. 本方案永不调用 `BatchReplaceClusterNodes`；
   `GPU_FAULT_ALLOW_HYPERPOD_REPLACE` 恒为 `false`。
3. HyperPod Job Auto Restart、EKS auto-resume 和 Slurm auto-resume 必须禁用。
4. 未知策略、缺少证据、版本不一致或 workload 状态未知时必须 fail closed。
5. CPU 控制面不持有 GPU kubeconfig；每集群 Executor 只操作本地 GPU EKS。
6. 每个 GPU 集群使用独立 token、IRSA、namespace allowlist 和 Node Action key。
7. 禁止 `curl -k`、`verify=false`、未签名 Node Action 和在线扩大 allowlist。

## 2. 破坏性能力阶段

| 阶段 | 能力 | 上线前证明 |
|---|---|---|
| A | 观察、取证、simulation | 事件、allocation、Collector、Agent 和证据链完整 |
| B | 隔离、停止和重启 workload | 新旧 attempt 不重叠，provider taint 不被删除 |
| C | quiesce、无 GPU client 校验、GPU/fabric reset | fail-safe timer、签名、fencing 和动作后验证 |
| D.1 | HyperPod reboot | `NodeRecovery=None`、二次 cluster 确认、fencing、provider 幂等和重启后验证 |
| D.2 | warm-spare `nodeReplace` | `HEALTHY_WARM_SPARE_ONLY`、同规格健康 spare、原子全量分配和替换后验证 |

不能因为节点侧开关已打开就跳过控制面 allowlist、Runtime Profile owner 或维护窗口。
当前 `regional-hyperpod-safe` Profile 的 `nodeReboot` 和 `nodeReplace` 同时由
`gpu-fault-hyperpod-adapter` OWN，因此 D.1/D.2 是分开验收的子阶段，不是两个独立
环境开关。只批准 D.1 时必须发布新的 Profile version，将 `nodeReplace` 保持为
`OBSERVE`；不得依赖关闭 spare coordinator 来阻止替换。

D.2 只允许从已纳管的健康 warm-spare 池执行本地切换，故障节点保持隔离且不被销毁。
`GPU_FAULT_ENABLE_HYPERPOD_SPARE_FAILOVER=true` 是拒绝回退到 provider replace API
的安全锁，不是单独的动作授权；必须同时保持
`GPU_FAULT_ALLOW_HYPERPOD_REPLACE=false`。健康 spare 不足时整个事务失败，不得部分
激活，也不得调用 `BatchReplaceClusterNodes`。

## 3. 配置事实源

| 配置类型 | 正常事实源 |
|---|---|
| 区域拓扑、身份和健康目标 | `site.yaml` |
| 低层发布输入 | CLI 临时生成的 `regional-release.json` |
| Runtime Profile | 开发者维护template；`release-deploy`生成不可变source快照和内容寻址version |
| release artifact | `dist/current-release.json` |
| CPU 非敏感配置 | 按 core/postgres/processor/telemetry/notification/recovery 拆分的 ConfigMap |
| Secret | Kubernetes Secret、Secrets Manager 或受控文件引用 |
| 节点配置 | Installer 生成的 `/etc/gpu-fault/*.env` |
| 详细参数 | [环境变量参考](环境变量参考.md) |

管理员不得同时用 `site.yaml`、低层 release JSON、`regional-env.sh` 和在线
`kubectl set env` 修改同一个身份或策略值。`regional-env.sh` 和直接 release JSON
只用于详细手工流程和 break-glass。

## 4. Release 与 Runtime Profile

- Control Plane、Executor、Node Runtime wheel 和 Node bundle 必须来自同一份
  schema v2 release manifest；三个运行面不得互相安装对方的 wheel。
- 物理 wheel SHA-256 证明实际文件，组件 `module_digest` 证明行为内容；Agent 和
  Executor 的 required/compatible 窗口同时校验两者。
- Runtime Profile 按 `profile_version` 在区域控制面共享。
- 同一版本内容不可覆盖；策略变化必须使用新版本。
- CPU required profile、Collector、Watcher workload annotation 和 Node Agent config
  必须引用同一版本。
- Agent artifact/compatibility digest、config digest、protocol 或 Runtime Profile
  任一漂移时，节点动作必须被 compatibility 门禁拒绝；Executor 领取命令前同样校验
  artifact、compatibility digest 和 protocol。

## 5. 凭据边界

| 凭据 | 允许位置 | 禁止位置 |
|---|---|---|
| execution token | CPU Secret、CPU Pod | GPU EKS、文档、日志 |
| cluster token | CPU registry、对应 GPU Secret、目标节点 env | 其他 GPU 集群 |
| fleet master | CPU Secret、可信部署机短期文件 | GPU Secret、节点 |
| per-node action key | CPU/GPU key map、对应节点 | 其他节点 |
| CA 私钥 | Secrets Manager 等 PKI 存储 | ConfigMap、节点 |
| CA 公钥 | GPU Secret、节点 trust bundle | 无 |
| Aurora 密码 | Secrets Manager、Kubernetes DSN Secret | shell 参数、普通 artifact |

## 6. 上线否决项

以下任一项失败都不得进入 active：

- `make check`、真实 PostgreSQL 测试和 release preflight 未通过；
- Runtime Profile 有 warnings；
- required/compatible pin 不符合发布阶段；
- SES 或 AMP/SNS 没有可用接收端；
- Executor claim、Agent heartbeat 或 Collector freshness 不满足；
- NLB/TLS、Aurora credential refresh 或证书有效期未验证；
- 破坏性步骤缺少 adapter owner、签名、fencing 或 action 后验证；
- 容量测试出现持续 429/503、队列增长或数据库连接耗尽。

详细门禁见[部署和运维手册](部署和运维手册.md) §2、§6、§7 和 §10。
