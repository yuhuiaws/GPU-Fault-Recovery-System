# GPU 故障处理系统安全与参数参考

本文汇总管理员需要审批的硬约束和配置边界。日常查询先看按类别整理的
[管理员环境变量参考](管理员环境变量参考.md)；完整机器清单由代码生成的
[环境变量参考](环境变量参考.md)提供。

## 1. 不可放宽的生产约束

1. 受管 GPU HyperPod 必须为 EKS 编排且 `NodeRecovery=None`。
2. 本方案永不调用 `BatchReplaceClusterNodes`；
   `GPU_FAULT_ALLOW_HYPERPOD_REPLACE` 恒为 `false`。
3. HyperPod Job Auto Restart、EKS auto-resume 和 Slurm auto-resume 必须禁用。
4. 未知策略、缺少证据、版本不一致或 workload 状态未知时必须 fail closed。
5. CPU 控制面不持有 GPU kubeconfig；每集群 Executor 只操作本地 GPU EKS。
6. 每个 GPU 集群使用独立 token、IRSA、namespace allowlist 和 Node Action key。
7. 禁止 `curl -k`、`verify=false`、未签名 Node Action 和在线扩大 allowlist。
8. 生产 Agent endpoint 必须使用 HTTPS，控制面只信任签名 heartbeat 携带的节点
   证书；每个 `RegionalClusterRegistration.agent_endpoint_allowed_cidrs` 必须收口到
   该 GPU 集群节点子网。
9. 节点mutation的workload ownership只接受120秒内刷新过的active Observation；
   stale记录必须从ownership排除并单独告警。当前fresh overlap为critical，
   Alertmanager使用5秒group wait；stale Observation为warning。

## 2. 破坏性能力阶段

| 阶段 | 能力 | 上线前证明 |
|---|---|---|
| A | 观察、取证、simulation | 事件、allocation、Collector、Agent 和证据链完整 |
| B | 隔离、停止和重启 workload | 新旧 attempt 不重叠，provider taint 不被删除 |
| C | quiesce、无 GPU client 校验、GPU/fabric reset | fail-safe timer、签名、fencing 和动作后验证 |
| D.1 | HyperPod reboot | `NodeRecovery=None`、二次 cluster 确认、fencing、provider 幂等和重启后验证 |
| D.2 | warm-spare `nodeReplace` | `HEALTHY_WARM_SPARE_ONLY`、同规格健康 spare、原子全量分配和替换后验证 |

不能因为节点侧开关已打开就跳过控制面 allowlist、Runtime Profile owner 或维护窗口。
当前 `regional-hyperpod-safe` Profile 的 `nodeReboot` 和 `nodeReplace` 同时由
`gpu-fault-hyperpod-adapter` OWN，因此 D.1/D.2 是分开验收的子阶段，不是两个独立
环境开关。只批准 D.1 时必须发布新的 Profile version，将 `nodeReplace` 保持为
`OBSERVE`；不得依赖关闭 spare coordinator 来阻止替换。

D.2 只允许从已纳管的健康 warm-spare 池执行本地切换，故障节点保持隔离且不被销毁。
`GPU_FAULT_ENABLE_HYPERPOD_SPARE_FAILOVER=true` 是拒绝回退到 provider replace API
的安全锁，不是单独的动作授权；必须同时保持
`GPU_FAULT_ALLOW_HYPERPOD_REPLACE=false`。健康 spare 不足时整个事务失败，不得部分
激活，也不得调用 `BatchReplaceClusterNodes`。

`BatchReplaceClusterNodes` 不仅由环境变量和 IAM 禁止：运行时 provider client
协议已移除该方法，任何 `HyperPodAction.REPLACE` 进入 provider submit 都直接失败。

### 2.1 区域验收夹具边界

Live runner 的 plan 必须绑定目标、kubeconfig 内容、当前源码和成功前检；
只读分析或本地代理 PASS 不授权真实动作。监管丢失、目标 UID 漂移、读取失败或未清理
残留均禁止继续，不得以手改 verdict 恢复正式序列。

WORKLOAD-001/002 必须执行 README 的真实训练提交入口，不能用内部函数或
create 替身证明 apply 路径。仅对本次测试创建临时命名空间级 get/create 身份，
先证明它没有 patch/update/delete 权限，再通过私有 impersonation kubeconfig
执行提交；原部署身份只用于前检及按 UID/resourceVersion 清理本次拥有的资源。
同名对象出现、权限扩大、读取失败或清理身份不明时停止，不修改既有 workload、
组件 ServiceAccount 或 namespace allowlist。

受管测试 workload 清理先保留已验证的删除专用记录，再以 UID/resourceVersion
条件和 `Orphan` 策略移除控制器，最后显式零宽限删除 Pod，避免 Job controller
重新创建 Pod。父链消失后的清理仍校验已保存的 UID、内容摘要与 owner 引用；
只允许正常 orphan 去除 owner 引用和运行时 finalizer 变化，不接受新归属或内容漂移。
版本冲突只在同一已验证对象内有限重读，未知创建结果、读取失败和身份变化仍停止。
提交前仅省略 Kubernetes 会规范化掉的空 annotations 映射；非空声明仍必须保留。
创建已确认但声明校验未通过的控制器，只能在当前内容仍匹配原始 ACK 时前台级联
回滚，不以其父链把子资源登记为已批准。

CMD 合成身份的热注册凭据只通过受保护 stdin 进入 CPU probe，不写入 argv、环境、
源码或日志；必须匹配当前 registry revision、独立当前 token 和本次 run/有效期。
探针只可使用回环 Agent 范围且无 Agent 注册的合成身份，不能借此断言物理 consumer
不存在。CPU 本地 watchdog 的强制终止不等于清理证明，累计清理预算不能续期；
数据和注册删除仍依赖原始登记回执及已停止 producer 的证据。

NOTIFY-008 和 HA-011 的探针只使用本次独占、优先级 0、非默认且不可抢占的 PriorityClass；
不得借用系统组件类别或去掉不可抢占约束来绕过 admission。类别的 namespace owner、
创建 UID 和删除前版本必须受检，namespace 消失也不能省略类别残留核验。

CAP-002 使用独占 ADOT 抓取器及探针自己的 token 文件，禁止把生产 execution token
复制到容量夹具或改为匿名 metrics。抓取器只读取本次探针，不修改生产 ADOT、IAM 或
Secret；plan 必须绑定部署中的 collector 身份。先证明本次指标新鲜、释放后归零及
告警消退，再按 UID 清理抓取器和依赖资源。无法证明进程停止时不得删除依赖后报告
成功。工作区的全局容量告警仍可能沿既有 SNS 路由发出通知。

COLLECT-017 的临时 plugin affinity 试验只支持事先批准配置为 `OnDelete` 的
DaemonSet；runner 不允许在线转换 `RollingUpdate`。先确认 GPU 本地恢复 watchdog
ARMED，再做 UID/resourceVersion 条件更新；原 affinity 必须完整恢复并核验后才能
取消 watchdog。仅批准本次资源/节点的最小权限，失败时保留恢复日志，不吞掉清理错误。

COLLECT-022 仅使用本次私有 FM 日志、checkpoint 和不转发的 sink。不得以测试为由
删除真实 collector 游标、修改其服务，或把私有软件日志描述为真实硬件故障。
BOOT-030/031 的专表验收只读连接 writer，不自动推进迁移或清理旧数据。

COLLECT-004 的 live 发布仍会触发真实 reboot，不是只读用例。新路径仅在独立 Collector
实例中使用 `baseline+1`，私有 sink 不联网；采样完成后才允许将已保存、绑定原 Node、
boot、生产配置摘要和采集进程的两个批次投递到真实入口。生产 `collector.env` 和 Host
Collector 服务不得为此修改，不能启动持续转发的第二个 producer。
发布必须显式确认并匹配采样摘要，保留原批次 ID；响应丢失只能查询持久证据，不能盲目
重发、伪造已接收或清理未知工作流。最终仍要求恰一条恢复工作流 SUCCEEDED、新 boot、
配置摘要不变及完整探针清理。CloudTrail 证明严格绑定批准的集群、单个实例、完整调用
角色及成功提交窗口，不能仅计数或比角色短名。
旧版 override journal 的恢复兼容路径仍要求原归属、私有备份、固定期限、节点锁和
完整 CLEANED 证明；不得因新用例不再依赖该路径而放宽旧守卫或补造过去的身份。
隔离采样、模拟生命周期和本机平台检查均不构成 COLLECT-004 live PASS。

DESTR-008 的所有合成热备不足请求必须保留只限制行为的 `activation_forbidden=true`。
旧 Executor 协议不得领取这类命令；任何真实 activation、cached activation 拒绝都不能
冒充场景本身的健康检查通过。三个限时场景还须有独立 CPU 取消 watchdog 与 Node UID
绑定的 GPU admission 防护；admission dry-run 不等于全 API Server 缓存已收敛，因此
不能取代产品内部的不可变 inhibition。原 producer 未撤销、POST 来源不明或命令未
静默时不恢复夹具；原运行只允许清理续跑。参见
[DESTR008 Cancellation](components/destr008-cancellation.md)。

DESTR-014 只有持久化独立恢复 service/timer 对原 Node、boot、release 和 runtime
明确回报 ARMED 后，才可移除原 Agent 启用链接。固定恢复期限不可续期；失联后仅恢复
同一个 Agent，不授权 reset、reboot、切换热备或重启 workload。到期、身份漂移、
未知 supervision 或 systemd job 未停止都不能签发清理成功。普通瞬态 timer 和
旧的无绑定 restore 命令不能替代该协议，参见
[Reboot-Surviving Recovery](components/destr014-recovery-safeguard.md)。

DESTR-015/PREEMPT-033 的物理归属 companion 必须等待普通 DESTR-015 通过并完成清理，
再为三个独立变体分别审批；PREEMPT-033 引用同一组证据，不重复执行同一物理试验。
生产 Agent protocol 4 在出队后的物理检查点等待节点 key 签名的单次许可；
challenge 最多 90 秒且不超过原命令期限，许可最多 3 秒。签发前重新检查租约和全部
参与节点的 workload/Pod/Node 归属，执行前还需检查本地 generation、fencing、
quiesce、client 和许可有效期。拒绝结果不能触发 reboot/replace 升级。

许可可能送达后的畸形响应、结果查询失败和相互矛盾的响应必须保留原 command ID、
意图摘要及结果未知状态，只查询原命令，不重新提交替代命令。原 phase、fencing、
参数或 GPU 范围改变时不能把旧结果当作新动作成功。否定许可不覆盖 Agent 已返回的
执行事实；后续检查拒绝时保留此前获准检查点，不能宣称整条命令从未开始。
步骤或 workflow 超时不证明物理动作已停止。仍有未确认节点动作时，控制面不得自动恢复
GPU 服务或把节点占用释放为普通终态，而应保留 `BLOCKED / NEEDS_OPERATOR` 等待调和。
已确认普通失败、明确的执行前拒绝仍可补偿；节点既有 quiesce failsafe 不变，
但不能被当作物理动作完成证明。
区域单步及复合命令的WAITING记录必须携带这些物理状态。LEASED变更即使上次前检
尚未开始，也可能在之后已提交；取消后和终态/自动恢复之前必须重新核对远端证据。
瞬态读取失败只允许重试和保留占用，不授权恢复服务。DAG派发还须使用当下计划的
依赖、目标范围和退役状态，不能提交缓存ready列表里已经撤销的动作。

单 GPU 和整机 fabric reset 的 `nvidia-smi` 超时均保存
`outcome_unknown/manual_confirmation_required` 及实际逐 GPU 进度，并贯穿 Agent、
adapter 和工作流。新旧版本混跑时，旧结果中非空的 `reset_outcome_unknown` 也按未知处理；
无结构化进度的旧整机结果只识别明确的 `ResetOutcomeUnknown` 异常类别，不从任意
超时文案推断执行结果。未知状态保持节点占用并等待人工调和，不自动恢复 GPU 服务或升级动作。
保留的非区域多节点 barrier 兼容路径使用同一规范化规则，并以 `node_failure_details`
保留失败节点的逐 GPU 进度；它不能把旧版未知结果降成可自动补偿的普通失败。

同一工作流已确认的 reboot 可以解释 boot 变化，但原 STOP 回执不能被覆盖或重新签发。
提交时记录的 `stop_reboot_authorization_v1` 必须绑定原回执摘要、Node UID、旧 boot、
工作流/phase/fencing 及 execution epoch/owner，再与确认后的 Agent/provider 观察对应。
轮询沿用原绑定；旧代码缺少该证明、外部 reboot、Node 重建或 workload/Pod 漂移仍拒绝。
provider 已接收 reboot、但原续跑证明丢失时，即便幂等重放返回缓存结果，也不能根据后来
的 Kubernetes 读取补签证明；返回 `STOP_REBOOT_AUTHORIZATION_MISSING` 并保留结果未知，
等待人工调和，不再提交 reboot 或升级为替换。
这不构成外部归属写入与 provider 调用之间的原子互斥。

分布式 reset 在编译时先计算逐节点 DAG 的展开大小，与执行器共用 256 步上限。
超过上限不截断节点集合，也不保存为可执行 reset；只在原 Profile 允许时执行取证、
禁止调度和隔离，完成后保持 `BLOCKED / SAFETY_SETTLED`。无法执行隔离时直接
`BLOCKED / NEEDS_OPERATOR`，均保留人工恢复原因。

终局隔离不是只读事件，也不能由 reboot 前的临时隔离覆盖。合并及后继中的
`terminal_quarantine_node_ids` 绑定故障节点；未提交的恢复步骤可以收窄或撤销，
已经提交、执行或退役的步骤不得改写身份。热备恢复必须跟随真实节点替换绑定，
后来加入的隔离与取证仍针对原故障节点。仅有 REPLACE 计划或成功标记、但没有真正
移到非隔离目标，不能放行原节点的恢复调度；拒绝发生在任何 patch 或 no-op 之前。
终态与ownership报告也使用节点范围：A的恢复不能抵消B的终局隔离，未执行或退役的
恢复步骤不算完成证明。历史误标为RECOVERED的incident不能单独授权takeover，
后继仍必须保留实际受管节点的隔离约束。
恢复完成证明必须绑定phase、step index和operation的成功执行回执；部分完成索引、
未分phase的旧摘要或单独的成功状态不能释放隔离。已经验证的SPARE_FAILOVER可以使
incident恢复并允许依赖任务在热备继续，但原故障节点仍保留ownership隔离；明确的
持续隔离或其他未恢复分支不会被热备成功抵消。

成功reset结果区分`reset_successes`与`reset_busy_refusals`。busy重试仍执行原来的
身份和client检查，不增加成功物理动作预算；多次调用缺少一致的结构化计数、
存在未知/失败/未执行GPU或超过固定重试上限时，验收不能判为一次成功reset。
runner不直接恢复quiesce来完成清理，保留产品自身补偿、failsafe和人工调和边界。
CPU恢复入口与runner使用同一`recovery_safety`判据，包含旧版
`reset_outcome_unknown`及嵌套节点结果。SQL超时取消或终态不等于物理完成，
DESTR-014已记录的人工保护不会由后续终态读取自行解除。
已有incident的清理必须取得实际排空证明；读取失败不能因未启用holder而授权删除
workload或恢复隔离。只有尚无incident且未启用holder的准备失败路径可直接清理。

该试验在排队后、签发许可前引入受控变化，并用独立连续执行跟踪判定是否越过动作边界。
顺序的 Kubernetes 读取、许可签发和实际系统调用之间不是原子事务；不能据此宣称能
阻止任意一次读取之后发生的所有变化。缺少跟踪或清理证明不得签发 PASS，companion
也不得覆盖普通用例结果。精确边界和人工调和条件见
[Physical Late-Ownership Acceptance](components/late-ownership-acceptance.md)。
本方案不为此新增要求外部 Operator、调度器或业务客户端接入统一归属写入协议、
更换写入口或修改权限；不能假设它们会配合暂停写入。现有 `NodeRecovery=None`、
禁用自动重启等安全前提不变，已检测到的归属漂移、读取失败和结果未知仍按现有规则拒绝
或保持人工调和。该边界不表示能够发现任意一次读取之后的所有变化。
完整原子互斥仍未实现，已评估但未采用的协调器方案及其平台前提见
[Atomic Ownership Fence Design](components/atomic-ownership-fence-design.md)；
它不是当前部署前置条件、已部署能力或全 API Server 生效证明。原场景缺口和验收门禁
保持不变，不因不采用该架构而计为通过。

## 3. 配置事实源

| 配置类型 | 正常事实源 |
|---|---|
| 区域拓扑、身份和健康目标 | `state-dir`中由CLI生成的内部site |
| AWS站点基础设施 | ARN bootstrap state和Aurora installation resource registry |
| 低层发布输入 | CLI 临时生成的 `regional-release.json` |
| Runtime Profile | 开发者维护template；`release-deploy`生成不可变source快照和内容寻址version |
| Runtime Profile审批 | `state-dir/release-deploy/profile-plan.json`、活动审批和按计划摘要归档的消费记录 |
| release artifact | `dist/current-release.json` |
| GitHub main CI候选只读凭据 | 权限`0600`的`GPU_FAULT_GITHUB_TOKEN_FILE`；仅clean `HEAD == origin/main`候选恢复使用 |
| 管理员容量期望值 | `state-dir/admin-config/desired.json`；由CLI生成、摘要校验，不含Secret |
| 管理员容量计划和审批 | `state-dir/admin-config/pending.json`（在飞或被中断的那一次 apply）、`desired.json` 和按计划SHA归档的审计 |
| CPU 非敏感配置 | 按 core/postgres/processor/telemetry/notification/recovery 拆分的 ConfigMap |
| Processor 重试与完成并行度 | 由角色化 processor ConfigMap 生成；生产 backoff `1..30s`、completion cluster concurrency `1`，提高到 2/4 前必须通过 CAP-005 |
| 修复并发预算 | `GPU_FAULT_REMEDIATION_MAX_ACTIVE_*`；生产默认值由代码固定，显式覆盖才进入配置；Region、cluster、node、failure domain 和 resource class claim 随 workflow lease 持久化。failure domain 来自 SXID 的 fabric partition 与 deploy/join/remove 自动渲染的节点映射 ConfigMap `gpu-fault-failure-domain-map`（标签键取自 site.yaml `spec.failureDomainLabels`；`GPU_FAULT_REMEDIATION_FAILURE_DOMAIN_MAP`，可选挂载，存在即必须合法，渲染侧在 apply 前用同一加载器校验） |
| Secret | Kubernetes Secret、Secrets Manager 或受控文件引用 |
| 区域 registry runtime | Aurora 不可变 revision/head；Secret 仅 bootstrap/灾备 |
| 节点配置 | Installer 生成的 `/etc/gpu-fault/*.env` |
| 管理员常用参数 | [管理员环境变量参考](管理员环境变量参考.md) |
| 完整机器清单 | [环境变量参考](环境变量参考.md) |

管理员不得手工修改内部site、低层release JSON、`regional-env.sh`或在线
`kubectl set env`来改变身份或策略。`regional-env.sh`和直接release JSON只用于详细
手工流程和break-glass。

统一启动校验要求数值型环境变量为有限数；`NaN`、`Inf` 和 `-Inf` 不能作为超时、容量或
阈值绕过范围检查。错误只报告变量名与约束，不回显值；`warn`/`ignore` 仅影响未知变量名，
不能放行不可用的数值。

完整环境变量清单不是通用写接口。管理员配置仅开放正式模板中的22项控制面容量、
Aurora Min/Max、队列/重试、Workflow调度、通知投递和证据保留字段；凭据、身份、
Runtime Profile、operation
allowlist、release pin、破坏性开关和安全不变量必须继续使用各自专用事实源。首次部署可用
`deploy --config`导入权限`0600`的严格YAML；已有站点编辑
`<state-dir>/admin-config.yaml`后执行带审批引用的`gpu-fault-admin config`。计划SHA
由CLI内部生成和归档，不是管理员参数。

CPU容量配置通过滚动生效，不支持通用无重启热更新；Aurora Min/Max通过受审计RDS事务
在线调整，并要求双实例收敛及有证据的失败补偿。发布子进程失败不证明原角色已恢复；
候选已提交、回滚未完成或live结果未知时，保留pending目标，不自动降低Aurora容量。
只有匹配的未变更或完成回滚证据才能授权恢复旧窗口。只有未来明确实现独立配置revision、全CPU进程
ACK、mixed-revision门禁和回滚后，才允许把其他白名单字段标记为hot-reloadable；
不得复用cluster registry记录来绕过这些门禁。

## 4. Release 与 Runtime Profile

- Control Plane、Executor、Node Runtime wheel 和 Node bundle 必须来自同一份
  签名的schema v4 release manifest；Manifest还必须覆盖渲染后资源摘要、renderer、
  `uv.lock`、Node template、各角色image digest及节点离线依赖inventory。旧schema v3
  共享镜像release继续读取和回滚，但不得为其猜测新的独立镜像身份。
- runtime image必须由CI预装锁定依赖。生产Pod和Schema Job不得在启动时执行
  `pip install`；部署机验证attestation签名和摘要。schema v4的CPU和Executor分别使用独立
  OCI image及`/opt/gpu-fault/control-plane`、`/opt/gpu-fault/executor`，只包含自己的
  component wheel，系统Python不得回退到完整项目包。独立镜像不改变required/compatible
  pin与协议窗口；previous快照缺少v4的独立Executor身份时必须拒绝回滚。
- 节点wheelhouse通过固定digest的OCI分发，只读挂载；安装前验证签名Manifest绑定的
  inventory、每个文件、平台及候选bundle中的lock，强制`--no-index --require-hashes`，
  py-spy仍检查二进制摘要。旧bundle必须使用旧依赖身份，不能混入候选wheelhouse。
  即使bundle内容相同，rollback也通过显式previous目标选择旧依赖镜像；缺失或不匹配的
  cluster/bundle/依赖绑定必须失败。部署机镜像缓存仅接受私有HMAC receipt和新鲜固定OCI
  身份校验，其认证密钥不得进入源码、普通artifact或发布资产，缓存不替代release验签。
- previous同时保存旧Reconciler已经信任的完整模板内容SHA，与模板来源SHA区分。
  捕获和恢复时都验证ConfigMap的实际Job字节及依赖镜像、inventory和只读挂载，不得对
  线上当前内容重新计算SHA后将其当成旧版本授权。显式模板覆盖必须携带可信内容pin，
  preflight检查实际选中的模板；受管入口清除继承的模板覆盖变量，缺少证明时fail closed。
  rollback在恢复CPU、刷新器或Profile前，先验证所有尚待AGENT/RECONCILER补偿的集群
  模板；逐目标执行前仍复验，CPU-only范围不读取无关GPU模板。
- 产品返回的“已安装/可复用”提示不是安全证明。Shell入口仍须执行完整Node key字节
  摘要/归属校验，并核对实际选中模板的受信内容pin；不能用hint跳过任一门禁。
- dirty源码只能由统一`gpu-fault-admin deploy`内部准备器生成`staging_only=true`的隔离
  测试release。普通
  `release-deploy`和生产验签默认拒绝该等级；只有最终clean commit和Release CI可以
  生成生产release。
- Runtime image复用只能依据完整image input digest：Dockerfile、固定base digest、
  runtime lock、platform、build args、control-plane/executor wheel SHA和module
  digest。Registry中tag、platform或任一config label不一致时必须fail closed。
- BuildKit cache必须与immutable runtime repository分离。Cache repository允许mutable
  tag但只用于layer加速；ARN bootstrap只清理超过7天的untagged cache artifact，保留
  当前cache tag。已有生命周期策略不一致时必须fail closed，release Manifest永远只能
  引用校验后的immutable OCI digest。
- 容量压测默认使用隔离control plane/registry。synthetic集群必须携带run ID和TTL；
  live registry mutation需要双确认，且所有执行路径必须在`finally`中完成可重试、
  可验证的teardown。不得通过让status忽略`perf-cap-*`掩盖残留。
- 生产部署机必须从Cosign签名的离线deploy-host bundle安装Python环境。bundle只包含
  hash锁定wheel、项目wheel、工具清单和可选审核后二进制，不得包含凭据。在线初始化只
  用于开发checkout，`gpu-fault-admin deploy`不得安装或升级宿主机软件。
- 管理员CLI必须来自独立`gpu-fault-deploy-host` distribution；生产Control Plane
  Runtime wheel/image不得包含`gpu-fault-admin`入口、`admin_cli.py`或
  `deploy-host-tools.json`。部署机代码变化不得伪装成应用Runtime变化。
- 本地构建的临时PostgreSQL只监听loopback，密码不得进入Docker参数、URL或普通artifact；
  使用仓库外的私有授权目录。精确CID、镜像和归属确认后的清理仍须证明资源不存在；
  创建未知、监督丢失或清理失败不允许宣告构建成功，不能按名称接管或删目录绕过拒绝。
  PG测试子进程使用自己的凭据HOME，不改变ECR、Docker构建和签名的HOME。
- GitHub候选token不得写入site、源码、普通artifact、日志或命令参数；候选恢复缺少凭据
  或API暂时不可用时可回退本地完整门禁，但已下载候选的签名、repository、commit/tree、
  gate或文件清单不匹配时必须fail closed。
- 物理 wheel SHA-256 证明实际文件，组件 `module_digest` 证明行为内容；Agent 和
  Executor 的 required/compatible 窗口同时校验两者。
- Runtime Profile 按 `profile_version` 在区域控制面共享。
- Profile策略变化必须先由deploy生成计划，再通过同一条
  `gpu-fault-admin deploy --state-dir ... --approve-profile-plan <plan_sha256> --reference ...`
  写入一次性state审批并继续部署；命令必须把管理员审核并记录到变更单的`plan_sha256`与
  当前计划持锁比较，一致后才允许写入。没有单独的审批动词；
  环境变量和手工JSON不得替代这个显式参数。计划必须直接展示
  `site_identity.site_name/aws_region/cpu_eks_arn`并以`site_identity_sha256`校验；
  审批同时绑定原/目标版本、策略/模板/快照摘要和live baseline，任一漂移都必须失效重审。
- Profile审批只在verify、stability和commit成功后消费。发布失败且计划未漂移时保留用于
  幂等续跑；成功消费或被新计划取代后不得重放。审批与发布必须由同一state-dir文件锁
  串行化。管理员完整命令和异常处理见
  [Runtime Profile变更审批](管理员Profile变更审批.md)。
- PostgreSQL schema 当前为 v18（以 `schema_migrations.LATEST_POSTGRES_SCHEMA_VERSION` 为准）；生产业务 Pod 的
  `GPU_FAULT_POSTGRES_AUTO_SCHEMA_INIT=false`，DDL 只能由 ensure Job 执行。
- workflow/remote_command 专表默认保持 legacy。数据迁移由受检 Store CLI 显式执行，
  不随 deploy 自动切换；dedicated 前必须完成规范 JSON/缺失/差异校验并排空活动命令和
  workflow lease。切换后旧表 writer 被数据库屏障拒绝，不能通过回滚模式恢复旧写入；
  旧行和索引只能在稳定期后显式退役。
- 专表维护入口持有 schema 共享屏障，并验证 release 版本、完整迁移历史和状态表定义。
  旧工具、缺失或停用的触发器、函数漂移均不得进入模式变更、回填和退役流程。
  模式切换遇到活动 writer 时立即拒绝并要求重试，不排队形成旧 writer 的锁循环；
  进入 dual 通过受限 DELETE 清空非权威副本，不再使用 TRUNCATE。有锁定副本行
  未能清除时整个事务回滚，不允许部分激活。
- 区域鉴权与 Processor 摄取共用有界请求体读取器；`Content-Length` 只用于提前拒绝，
  分块请求和缺少长度声明的请求仍按实际接收字节限制内存。读取使用请求剩余预算与
  30 秒读取上限的较小值，超时返回可重试的 503，不接收半个事件。gzip 在线路字节
  与解压后分别限量，超限返回 413；成功读取仍保持下游解码与集群身份绑定。
- 同一版本内容不可覆盖；策略变化必须使用新版本。
- CPU required profile、Collector、Watcher workload annotation 和 Node Agent config
  必须引用同一版本。
- Profile变化finalize前，旧Profile的非终态workflow和PENDING/RUNNING workload必须
  全部归零；当前实现不允许隐式双版本过渡。
- reset、fabric reset或动作后验证失败升级为reboot/replace时，如果新workflow包含
  `RESTART_WORKLOAD`，必须从失败workflow继承同一组`cluster_id`、`job_id`、
  `source_attempt_id`、`source_gpu_count`和`restart_budget`。字段缺失或多个来源不一致时
  升级workflow必须保持`BLOCKED`，不得使用默认值重新授权一次训练重启。
- Node Runtime升级按`FleetDeployment.max_unavailable/waves`推进，并同时校验
  artifact、bundle、template和签名ACTIVE heartbeat。
- 共享release默认一次只升级一个GPU集群；跨集群并行度由站点配置的
  `upgradeMaxParallelClusters`（默认1、最大8）显式开启，不是状态语义，也不改变
  自动回滚：回滚始终按实际mutation时间逆序串行。任一集群失败会阻止尚未开始的集群，
  已在推进的集群跑完当前波次序列后统一进入`PAUSED`或`FAILED`。站点配置中的
  `upgradeMaxUnavailable`默认0（auto，取规模上限）、最大32，upgrade第一波固定1；UNKNOWN故障域强制1，
  已知故障域按节点数把单集群上限自适应为4、8、16或32并均衡分布，显式1..32则取配置值与上限的较小者。
  `rollbackMaxUnavailable`默认2且最大4，rollback第一波固定1；少于6节点、UNKNOWN
  故障域或证据不完整时强制1，6至31节点最多2，至少32节点才允许4；多故障域每域每波
  最多1。
- 涉及GPU或Node Runtime的候选在schema Job和CPU rollout前必须完成
  `candidate-preflight-ready`：对候选GPU/DCGM/Reconciler/Installer Manifest执行
  server-side dry-run，校验Action key/Secret引用，并通过只读host预检证明bundle/wheel
  摘要、磁盘、Python/systemd/驱动工具、quiesce状态和旧runtime回滚槽。该门禁失败时
  不得滚动CPU/GPU进程、apply Reconciler或创建Fleet wave。
- GPU/DCGM Manifest在实际apply前必须再次server-side dry-run，防止早期门禁后发生的
  admission或RBAC漂移导致部分资源mutation。
- 只读候选预检最多4个集群并行、每集群同时执行Host预检Job最多8个节点；私有拓扑快照不含凭据，
  只能用于渲染和只读预检，不能替代真实安装前的新鲜Node、workflow和lease检查。
  分批server-side dry-run每批最多4节点、8个Job和1MiB；必须所有对象通过后才创建host
  预检Job，不能以批次成功掩盖部分对象失败。admission独立最多8批并行，仍共用全部署
  kubectl配额；该只读请求窗口不能替代Host执行窗口或真实节点不可用预算。
- 部署机嵌套CLI借还API配额须验证PID/starttime、祖先关系及暂停状态，不得信任PARENT
  环境变量直接放行。只能暂停本次派生且身份匹配的CLI进程，不能操作GPU Pod或宿主服务；
  无配额时不得恢复暂停的调用者。匿名认证输出只可暂存在0600临时文件中，stdout/stderr
  合计不得超过8MiB，超限清理并丢弃部分输出，不进入ledger、普通artifact或日志。
- API配额的SQLite文件仅用于部署机单次命令的临时跨进程协调，不是生产Store，也不部署到
  CPU/GPU集群；生产业务数据仍使用Aurora。协议v4在STOP前持久化仍占配额的`stopping`，
  全线程停止后才记`parked`；归还先提交计入容量的`resuming`再SIGCONT，不允许崩溃恢复
  或兄弟分支绕过该顺序。账本不保存凭据，正常退出删除，异常遗留不能证明后续deploy成功。
- 进程监督的内外两层subreaper分别提供独立完成证明；一层丢失时，必须由存活所有者证明
  完整后代树已停止并回收，才可进入普通失败补偿。全部有效证明丢失时抛出
  `ProcessSupervisionLost`，禁止当前进程继续发命令和自动回滚，不得将“监督进程已退出”
  或“输出管道已关闭”视为清理成功，也不能仅靠重启CLI推定原命令停止。
- 整个操作由`interruption_scope`保护，SIGINT请求取消受监督的非清理命令，并在安全
  边界失败；重复SIGINT不能提前释放站点锁或打断后代回收。命令环境准备、配额等待和启动
  共用绝对`expires_at`，补偿/清理只能使用自己的有界窗口，不能绕过监督丢失。
  此契约不承诺硬抢占父进程中的任意线程或不可终止的内核等待。
- Grafana/AMP的网络与HTTP framing在`native_http`的`-I -S -B`私有stdio worker中受监督执行；
  认证header、body、代理认证及响应不得进入argv、ledger、普通artifact或日志。AMP的
  `aws configure export-credentials`同样受监督、准入和输出上限约束，导出后只用冻结
  凭据签名，不写入新环境变量或重新触发SDK凭据刷新。凭据解析与AMP请求共用最多30秒
  查询窗口，私有消息及响应有8MiB上限；超时、超限或TLS验证失败不得放行。
- 已有release的ADOT/AMP候选更新必须在捕获previous之后进行，不得由bootstrap提前覆盖。
  只读漂移必须进入发布修复计划并在完成后复检。确认缺失的对象记录为明确absence；
  ADOT缺失须先证明CPU namespace锚点，权限/网络错误不得作为absence。
- 监控IAM、Pod Identity和SNS发布权限归bootstrap所有，使用既有site级role；release的
  运行安装模式只能验证这些前提，不能另建role或改写基础权限。SNS共享statement固定
  `AllowAmpAlertmanagerPublish`，来自同一`amp-sns-publish-policy.json`，绑定本账号、
  本workspace和topic，保留其他statement；topic身份、generation或策略读取不明确时
  停止，不把读取错误当成首次创建。内部`--runtime-only`在apply前验证这些前提，不调用
  IAM、Pod Identity association或SNS policy的写接口。
- Aurora刷新器同样归发布事务所有：快照保存旧CronJob、ServiceAccount与RBAC，
  不保存数据库密码。回滚先恢复旧刷新程序，再同步`AWSCURRENT`，最后才允许CPU重启；
  不以只改镜像代替完整恢复。CronJob查询失败或身份不明必须停止，不能静默跳过刷新。
- 公开`preflight`只读。内部`preflight --for-deploy`允许已授权deploy对实际计划选中的
  刷新器执行前置修复，不是管理员可用来放宽预检的开关。Store依赖门禁之前必须先持久化
  `aurora_prerequisite_repair`，绑定候选pin、数据库身份、原state及完整旧快照，再运行
  禁止消费者重启的`AWSCURRENT`验证Job。Store门禁不能省略，DDL、业务restart、Profile
  和GPU rollout不得提前；失败保留可续跑journal，正式previous继承修复前对象。
  候选在`READY`后放弃留下的孤儿journal，只能由下一候选在站点已提交、baseline精确匹配、
  数据库身份一致时先恢复原刷新器再接管，或由`deploy --rollback`独立恢复；不改写旧binding。
- 首次bootstrap必须用CPU只读数据库Job证明实际空库，不能由缺少Pod、release state或
  `CREATED`标记推断。证明绑定Aurora/namespace UID、候选schema、run/Job UID和新鲜时间，
  DSN只来自CPU Secret，TLS必须`verify-full`，不能自动建表。已绑定origin只允许续跑，
  每次仍检查schema/migration和活动记录；未初始化库的view或未知表，以及未知状态、
  schema或身份漂移均fail closed。
  proof Job以受管Aurora刷新CronJob的实际UID为唯一owner，固定非controller引用，
  不由CronJob定时调度或作为active Job管理；创建前journal登记run/spec身份及
  `owner_uid`，preview和live Job均须匹配。清理使用UID precondition和foreground确认；
  创建ACK丢失、失败或中断均须清理自己的Job，不删除替换或被重新指定owner的对象，
  父资源垃圾回收和TTL不能替代显式清理证明。
  失去全部本地监督完成证明时不得继续发清理命令，也不得声称远端Job已清理。
- installed-resource发现包含方案Job，只有唯一owner精确匹配同namespace的已注册
  CronJob UID才视为已覆盖子资源。孤儿、同名父对象重建、未登记父对象、跨namespace或
  多owner均作为未登记资源阻断清理预检，不能按名称盲删；客户namespace Job仍不被接管。
  Job admission校验不为后续Pod admission改写背书，CPU namespace的Pod admission
  策略仍属于受信边界。
- installed-resource的清理授权只来自受信源inventory，包括显式retired条目，不来自
  可变ConfigMap自行计算的SHA。来源不明的旧行即使对象已不存在，也必须在任何注册表
  改写前停止并保留原记录，先审阅并将显式retired条目纳入签名release的受信源清单；
  完整`scope + kind + namespace + name`身份不同的对象不共享授权。
  多GPU快照的`gpu.by_context[context]`必须保留各集群完整同步文档及其实际`.resources`，
  顶层并集不授权跨集群清理。context非空且唯一，写CPU注册表前先校验；所选context缺失
  时不能用同名对象或并集猜测归属。
  仅标准`aws eks get-token`由部署工具按显式有效期手工缓存，没有有效期不跨请求复用；
  通用exec插件及其他exec选项交由原生kubectl处理，保留`KUBERNETES_EXEC_INFO`和
  `provideClusterInfo`协议。刷新失败不复用旧token，也不输出凭据。
  API不存在和暂时不可用只接受受控脚本的精确stdout/退出状态协议，不解析任意错误文本
  来绕过API；成功还须验证完整资源确认，直接SQL须确认精确行数。兼容Aurora回填仍受
  不可变资源身份及整批事务约束，使用当前挂载DSN，不执行DDL。
- 可选 HMA 转发入口已退役。候选 preflight 发现旧 HMA producer Deployment 或无法确认
  其状态时拒绝升级；先用旧 release 排空或归档事件，再在批准的维护窗口退役资源。
  不自动删除 AWS HMA、CloudFormation 栈、SQS/DLQ 或历史证据，也不放宽热备健康标签、
  quiesce、`NodeRecovery=None` 与 provider replace 恒禁用约束。
- CPU候选发布后必须等待Agent重新向候选控制面刷新心跳；每个节点波次在claim前执行
  有界重试安全门，并要求wave外Agent保留足够lease余量，claim后立即用更小余量复检。
  一次性瞬时检查不得作为开始节点mutation的依据。
- 每个rollback wave开始前必须证明Executor全部Ready、wave外Agent ACTIVE且心跳有效、
  remote command为0、无活动破坏性workflow；任一节点失败不得开启下一波。
- upgrade、join和rollback在第一台节点mutation前还必须执行动态只读barrier：重新校验
  目标Node UID/Ready/cordon/隔离taint和failure domain，并验证Executor、remote command、
  破坏性workflow及Agent lease。upgrade的确定性候选与host事实必须已在CPU rollout前
  证明；join和rollback若没有可复用的当前候选证明，仍在本地流程中先执行同一只读host
  预检。只读host预检Job可以创建和清理自己的Pod/Job，但host root必须只读，禁止写节点
  文件、annotation或systemd。
- Node Runtime候选必须先安装到
  `/opt/gpu-fault/releases/<artifact-sha>-<dependency-sha>/venv`并校验，
  再原子切换`/opt/gpu-fault/current`。旧槽位和首次legacy `/opt/gpu-fault/venv`
  在rollback window内不得删除或原地覆盖。
  dependency身份绑定lock字节、Python/ABI、平台、libc及解释器二进制；缺失或不匹配时
  不得复用槽位。共享依赖层按该身份不可变保存，复用前校验真实文件、版本闭包及层引用，
  不先执行候选`.pth`或应用代码；损坏的已发布层不得原地重建。
  旧回滚槽也必须在候选预检和停止服务前通过实际文件、旧依赖闭包与入口模块校验；
  可执行文件存在本身不证明可回滚。合法Python别名只接受同一二进制的软链接链，
  不放宽解释器版本或系统site-packages隔离要求。
- terminal event是attempt Observation的单调终态屏障。保存terminal event必须在同一
  Store事务中把对应Observation转为终态；后到的`PENDING/RUNNING`不得恢复active ownership。
- cluster registry只有`ACTIVE`成员可派发操作；`PENDING/FAILED/ROLLED_BACK`只保留
  接入、验证和审计能力。并发join必须使用单集群CAS transition，禁止从过期候选site
  全量覆盖registry revision。同一站点的join CLI全事务串行；单个batch的发现与前置工作最多4路，
  滚动并行度取站点`upgradeMaxParallelClusters`，batch与升级共用该旋钮（默认1、上限8）。
  全站Installer预算固定为64节点，每集群wave再受`floor(64 / 集群并行度)`约束，不能分别
  放大集群和节点并行度。Secret灾备副本也必须使用`resourceVersion` CAS。
- registry收敛不能仅检查发布时抓取的成员集合。所有当前活跃CPU进程，包括后加入者，
  都须以有效持久心跳确认同一generation和摘要；未来心跳和缺失required记录仍阻塞。
  只有仍有活跃且全部ACK的机群时，已知过期成员才可退出等待；全体失联不是成功。
  运行时服务资格同时绑定成功刷新及心跳写入，不能用读库成功延续已经过期的心跳租约。
  此规则依赖同release与一致stale窗口，不声称已观察到旧Pod真正终止。
- join候选verify必须绑定source/candidate site、live release identity、registry
  generation/content和完整cluster state，并在15分钟内提交。site、release state与
  Aurora资源注册先完成；`ACTIVATION_STARTED`之后只允许fail-forward，不得把ACTIVE
  集群转换为FAILED/ROLLED_BACK后清理。
- join补偿必须等待已启动的并行任务收尾，只处理本attempt证明拥有的namespace、
  IAM和网络变更；身份漂移或无法证明命令停止时不自动清理。未完成补偿先续补偿，不能
  同时开启新attempt；仍被回滚registry引用的cluster token不得丢弃后换成新凭据。
- Node key探针私有读取完整Secret JSON，按实际base64解码字节计算摘要，不先strip，
  不只比键名。GPU key集合必须精确匹配当前目标节点，CPU按CAS合并并保留全站其他key
  和metadata；未知同名key冲突必须拒绝，已有合法随机轮换值不得被重新派生值覆盖。
  pending rotation标记即使两侧摘要相同也必须进入ensure，在再次验证Node UID、CPU镜像
  和GPU身份后才CAS清除；不得把标记当作成员归属证明。helper与wrapper共同交付并绑定
  TaskInputSpec/release身份，只在受信deploy-host环境执行，不扩大Node Runtime权限。
  join先排除跨集群NodeName冲突，`BoundNodeKeyRunner`携带新鲜NodeName到UID映射；
  补偿只允许已可能开始key写入且有完整Node/key证明的目标，使用最初绑定的实际GPU
  key摘要校验CPU当前值，再以resourceVersion CAS删除。摘要漂移或无证明时不得按名称删key。
- 首次多ARN deploy只为首个基线GPU集群创建token、IAM、NAT白名单和Private Hosted Zone
  VPC关联。关联按VPC去重；remove与join共用站点事务锁，Route53 ChangeInfo达到`INSYNC`
  且实际关联消失后才允许提交移除。
  DNS关联只有精确`CREATED/DETACH`注册记录才可解除；CPU原生、共享或外部关联保留。
  列表位置、成员数量、名称和观察到对象存在都不是创建来源证明；旧记录身份或来源
  不明时先调和，不能改写不可变key/ownership来取得删除权限。
  初始目标承诺只有在全部目标已纳管，或缺失目标具备完整身份、当前site/release匹配的
  已完成移除journal后才能解除。畸形目标、仅同名移除行、未完成或旧版journal，以及
  `COMPLETE`但site缺失均不得放行后续部署。
- deploy/bootstrap、Profile审批、AdminConfig、join/remove和uninstall必须竞争同一个
  state-dir mutation锁；拿锁后重新加载site并校验CPU稳定锚点，禁止并发覆盖site、
  bootstrap state或release state。
- 继承锁FD必须确实持有该文件的排他flock，inode一致本身不是持锁证明；跨线程也须
  保持互斥，锁路径拒绝symlink和FIFO。`config`不得用锁外读取的旧站点目标发起Aurora
  修改或计划写入。轮换、热备写入、手工处置、workflow收敛、远程outbox和显式rollback
  同样受站点锁约束；本地文件锁不提供跨部署机或复制state目录的分布式互斥。
- membership后的失败域映射刷新不得把worker读取错误当作不存在，也不得静默丢弃
  身份缺失或冲突的Node记录。受管调用要求worker存在，使用UID/resourceVersion
  守卫更新模板，并等待rollout；只有显式bootstrap内部路径可接受尚未创建的worker。
- remove先将目标置为`DRAINING`，排空并卸载节点/Executor，确认namespace实际消失后
  才允许并行撤销registry/key和独占AWS资源。CPU或其他GPU仍使用的VPC/NAT及共享资源
  依赖必须保留；节点key删除绑定原Secret UID、原始key摘要和新鲜全站NodeName归属，
  使用UID/resourceVersion CAS并回读确认。
  续跑绑定完整EKS/HyperPod ARN、集群/namespace/Node身份及原site/release摘要；
  已移出site的目标只能由精确的提交journal恢复，不能按同名对象猜测。缺少这些绑定的旧
  在飞journal须显式调和，不删除状态或手工补哈希放行。
- namespace删除须把已证明UID作为`DeleteOptions.preconditions.uid`发给API，等待期间
  拒绝同名重建；仅在删除前读过UID不够。节点Installer annotation清理先校验完整目标
  UID集合，再以UID/resourceVersion JSON Patch修改；最多8路metadata worker不是
  节点不可用预算，也不授权扩大Fleet wave。
- uninstall的`keep/delete/reset`模式、有效策略和源快照绑定同一事务。历史
  `REUSED/PRESERVE`的兼容处理只形成执行计划，不改写注册表不可变ownership或delete
  policy。历史LBC attachment边仅在预验证/删除共用的临时执行图中规范化，原依赖仍不可变；
  先解除role自身attachment并删role，再删policy，保留消费者、缺失依赖和环均阻塞，
  不能放宽policy删除时的attachment否决。live归属、调用账号和共享依赖仍须验证。
  Kubernetes/非Aurora/CPU验证通过并
  保存pre-Aurora证明后才可删数据库，最终快照须绑定原数据库incarnation并确认available。
  已完成卸载的重跑只复验，不能沿用旧清理证据删除同名重建站点。
- 全站清理先以同一registry revision将目标置为DRAINING，再停producer；ingress与CPU
  消费者保持运行直到严格排空，之后依次停消费者、ingress与GPU Executor，最后进入
  `NODE_RUNTIMES_STOPPED`，其后才清理auxiliary和对象。节点阶段只使用原journal保存的
  fleet/UID证明，CPU消费者停止后不得再读取数据库，不以批量孤儿SQL结算替代drain。
  schema-v2 journal用phase_order固定新顺序；旧版本或旧顺序须显式调和，禁止改版本、
  顺序数组、补造phase或猜测最新
  failed checkpoint。停放spare只按明确拥有的`previous-unschedulable`基线恢复，
  使用Node UID/resourceVersion并回读；缺少基线即阻断，不能默认uncordon。
- 动态workload RBAC仅在完整renderer策略、namespace/SA UID及外来绑定检查通过后纳入
  原per-context清理快照；标签或快照自哈希不是删除授权，也不豁免orphan。remove和
  uninstall共用后续删除路径，等待真实drain及GPU Executor停止，且在归属锚点删除前
  使用原UID/当前resourceVersion并确认消失。`DRAINING` ACK不能替代这些前置证明。
  停机复验拒绝仍存在的Pod，不因副本数为零放行。CPU已删除后的跳过检查仅用于原journal
  清理完成、所有RBAC删除已逐项确认的只读复验；剩余删除仍须验证CPU及全部停机前提。
- remove/uninstall的本地监督丢失须在原journal持久化为拒绝续跑；重启CLI后不能因为
  内存中的监督标记消失而继续发出mutation。先确认原操作结束并调和，不自动清除此标记。
- token轮换在Secret更新、数据面滚动、节点wave和本地文件替换前记录意图；本地
  `TOKEN_FILE_WRITTEN`意图落盘即禁止rollback，即使尚未记录文件替换完成也只能
  fail-forward。回滚覆盖已开始但ACK丢失的变更，终态先落盘再删临时token。
  journal固定`keep_window/window_minutes/quiet_seconds/acceptance_timeout_seconds`的值和
  类型，在飞或终态清理续跑不得修改；缺字段的旧journal须显式调和，不猜默认值。
  静默观察在等待前固定ingress Deployment UID/generation/期望副本数，要求完整健康
  且归属匹配的Pod集合；缺副本、缩容、重建或读取失败不能只靠尚存Pod的日志判定静默。
  同时校验稳定Ready的Pod及api容器身份，固定每轮窗口边界，受总deadline约束。
  无since过滤的当前日志前缀最多4096字节，须有不晚于窗口起点的完整记录；窗口读取后
  按原receipt长度重读并验证完整性和摘要。正常append允许，留存无法证明、来源漂移、
  不完整/未来/迟到日志均fail closed。该校验不证明Kubelet/CRI未静默漏报或恶意保留同一
  前缀改写日志，也不证明离线调用方已迁移；真实kubectl loopback测试不是live Kubelet验收。
- 热备声明/释放须绑定cluster、Node UID和原label/cordon基线，修改带resourceVersion并
  回读确认；未知池状态、并发预留、隔离或节点重建一律拒绝。机械检查确认annotation也须
  绑定节点身份和resourceVersion，不能把名称相同当成同一节点。
- commit/rollback先持久化已提交/已回滚终态，再清理临时Secret备份。清理失败只能幂等
  续清理，不得把已经越过不可回退点的release重新标成可回滚。
- 禁止直接删除incident/workflow/plan数据库行或手工改写workflow JSON。已由恢复
  successor收敛的历史`BLOCKED`记录只能通过
  `gpu-fault-admin workflow-reconcile`（`--dry-run` 只看计划，去掉即执行）处理；必须重新校验fencing、
  lease、remote command、provider动作、source plan和GPU节点隔离状态，成功后仅转为
  `SUPERSEDED`并保留完整审计，最终删除仍走S3 archive-first。
- Agent artifact/compatibility digest、config digest、protocol 或 Runtime Profile
  任一漂移时，节点动作必须被 compatibility 门禁拒绝；Executor 领取命令前同样校验
  artifact、compatibility digest 和 protocol。

## 5. 凭据边界

| 凭据 | 允许位置 | 禁止位置 |
|---|---|---|
| execution token | CPU Secret、CPU Pod | GPU EKS、文档、日志 |
| cluster token | CPU registry、对应 GPU Secret、目标节点 env | 其他 GPU 集群 |
| fleet master | CPU Secret、可信部署机短期文件 | GPU Secret、节点 |
| per-node action key | CPU/GPU key map、对应节点 | 其他节点 |
| CA 私钥 | Secrets Manager 等 PKI 存储 | ConfigMap、节点 |
| CA 公钥 | GPU Secret、节点 trust bundle | 无 |
| Aurora 密码 | Secrets Manager、Kubernetes DSN Secret | shell 参数、普通 artifact |

安装期 Node key custody 由显式 `gpu-fault-admin node-key-custody configure` 登记，
依赖外部受信的非对称签名授权、实际写入 start/completion 和独立运行时 activation。
登记不旋转 key，也不调用 KMS 签名；未授权请求只准备实际身份并停止。旧 checkpoint、
当前 Secret 形状或点时扫描不能补造历史保管证明。AUTH-015 消费完整签名链并对真实
Agent 验证新 key、旧 key 和 sibling key；自身不下发 master、不重启或重装节点。
该证据只覆盖受信 provisioning 路径，不为未观察的历史活动背书，详见
[Node Key Custody Evidence](components/node-key-custody-evidence.md)。

### 5.1 邮件通知边界

- `adminEmail`是站点运维联系人；`emailSender`是已验证SES identity；
  `emailRecipients`是独立、可多值的接收列表，三者不得在实现中强制相等。
- `emailSubjectPrefix`只用于站点环境标识。SES发送层会统一加入site、Region、
  AWS account和cluster上下文，避免同名集群邮件被误判。
- 可选`sesConfigurationSet`只在`channel: ses`下生效，名称限制为1至64个ASCII
  字母、数字、连字符或下划线。其值由site.yaml声明，渲染为三个CPU role ConfigMap的
  `GPU_FAULT_SES_CONFIGURATION_SET`并进入回滚环境；未声明时显式清空该变量，不能继承
  部署机shell中的值。声明后preflight必须确认该SES配置集存在、名称一致且允许发送；
  不自动创建或扩大IAM权限。回滚恢复实际捕获的旧ConfigMap和逐角色env，不能用候选配置
  覆盖旧通知环境。
- SNS原生email subscription的发件人为AWS管理的`no-reply@sns.amazonaws.com`；
  `emailSender`仅控制本方案直接发送的SES故障/动作通知。
- SNS确认请求绑定Topic generation、endpoint、真实Subscription ARN和48小时窗口；
  pending期间不得重复`Subscribe`。同Topic/邮箱出现多条confirmed或
  confirmed+pending时必须fail closed，不自动猜测应删除哪一条。普通deploy/rollback
  不得删除站点告警Topic；只有正式uninstall按installation registry处理。
- 节点、workload、Incident和Workflow标识必须来自当前事件或持久状态；生产模板禁止
  写入示例节点名、固定HyperPod实例ID或测试fixture标识。
- 邮件中的kubectl审批命令必须显式携带context，context未知时使用
  `GPU_FAULT_KUBE_CONTEXT`必填保护，禁止回退当前kubectl context。
- `vendor-ticket-*`是本方案内部支持升级记录，不代表AWS Support Case已创建。
  模板只能列出实际FAILED的Workflow operation，不得笼统宣称reset、reboot和replace
  均已执行失败。
- 固定标题、处置说明或字段变化时必须提升`template_version`，保证dedup和审计能够
  区分新旧模板。

## 6. 上线否决项

以下任一项失败都不得进入 active：

- production attestation既没有绑定已验签的main CI gate，也没有来自受信本地与
  `make check`加PostgreSQL stress等价的完整门禁；
- `make release-preflight`或CAP-005 PostgreSQL 16压力套件
  （8×40、JUnit零skip）未通过；
- Runtime Profile 有 warnings；
- required/compatible pin 不符合发布阶段；
- SES 或 AMP/SNS 没有可用接收端；
- Executor claim、Agent heartbeat 或 Collector freshness 不满足；
- NLB/TLS、Aurora credential refresh 或证书有效期未验证；
- 破坏性步骤缺少 adapter owner、签名、fencing 或 action 后验证；
- Agent endpoint CIDR 为空、使用 HTTP 或签名 heartbeat 未携带 TLS 证书；
- 容量测试出现持续 429/503、队列增长或数据库连接耗尽。
- 发布后120至300秒稳定窗口出现新Pod重启、持续队列增长、非终态远程命令或critical
  firing alert。正式稳定窗口前只允许对`GpuFaultStoreIoRejected`执行最多420秒的
  有界收敛等待，且须先证明所有运行中CPU Pod的完整新鲜零视图：聚合器degraded=0、
  有界slot数量匹配process-count，每slot完整发布三个reason的有限非负零值。
  缺失、旧合并格式、重复、畸形或非零数据不能授权等待，process_id不能替代slot；其他
  critical、重启、非终态命令或超时仍立即否决，不能把等待写成告警豁免。
  Executor internal error告警必须依据最近错误时间戳，不得对会随retention清理下降的
  保留记录数使用counter `increase()`。

详细门禁见[部署和运维手册](部署和运维手册.md) §2、§6、§7 和 §10。
