阅读约定：

- 「NVIDIA 官方建议」列原样引用 Xid Catalog / Fabric Manager User Guide 的文本；「本方案判定」是策略引擎输出的 disposition 和 `RecoveryAction`；「实际执行」是编译出的 `WorkflowOperation` 步骤链。
- `[...]` 表示条件步骤：`STOP_WORKLOADS` 仅在 workload_state 为 ACTIVE 时插入；`CHECKPOINT_WORKLOADS` 仅在有 checkpoint_manifest_ref 时插入（只记录引用，不做真实 checkpoint）；`RESTART_WORKLOAD` 仅在有 affected_workload_ids 时追加。
- 属于 `NODE_MUTATING_OPERATIONS` 的硬件、驱动及 workload 变更在 workload_state 为 UNKNOWN 时编译即拒绝（fail closed）；纯调度隔离不因此被禁止。BLOCKED 类判定的安全隔离仍须由 Profile 授权，获准后执行 FREEZE_EVIDENCE → MARK_UNSCHEDULABLE → QUARANTINE 并等待人工。
- NVIDIA `RESTART_APP`（含 NVLink5 `XID_154_EVAL` 无伴随 154 时的回退；XID 154 的五个驱动标签里没有 restart app）在 workload_state 为 IDLE 时由策略引擎改判 MONITOR_ONLY / `NO_ACTION`（本方案对 catalog 的偏离：没有受管应用可重启）：只写 INFO marker 与调查通知，不建 workflow、不 cordon。下表 RESTART_APP 各行的「实际执行」列描述的是 ACTIVE 且能归因到 workload 的情形；ACTIVE 但归因不到 workload 仍走 SAFETY_PENDING 隔离，UNKNOWN 仍按上一条 fail closed。
- 链 A = GPU reset 链，链 B = 节点 reboot 链，定义见第一部分末尾的 RecoveryAction 落地表。

## 一、通用故障类别（非 XID/SXID）

本节 32 类的逐项整改状态、已有测试边界和新增端到端验收规格见
[通用故障逐项验收](components/general-fault-e2e-audit.md)。案例已登记不代表
整改完成或真机通过；待实现和未执行项保留为显式缺口。

| 故障类别 | 数据来源 / 检测方式 | 判定规则 | 本方案 RecoveryAction | 实际执行 |
|---|---|---|---|---|
| CPU 过载 | Host collector `/proc/stat`、`/proc/loadavg`，15s 周期 | `cpu_usage_percent` ≥98 或 `load1_per_cpu` ≥2.0，持续 120s（控制面接收时钟） | WARNING → `RUN_DIAGNOSTICS` | FREEZE_EVIDENCE → VALIDATE_HOST（只读校验控制面遥测） |
| 内存/交换耗尽 | `/proc/meminfo` | `memory_used_percent` ≥95 持续 120s；`swap_used_percent` ≥80（无该持续窗口） | WARNING → `RUN_DIAGNOSTICS` | 同上 |
| 低利用率/资源持续异常 (`SITE_HOST_RESOURCE_HEALTH`) | 同上 + nvidia-smi 利用率与计算进程（`--query-compute-apps=pid,gpu_uuid` + `/proc/<pid>/stat`） | `LOW_GPU_UTILIZATION`：attempt 持有的每张 GPU `host_gpu_utilization_percent` ≤5% 持续 300s；`LOW_CPU_UTILIZATION`：同一张 GPU 上持有计算上下文的进程所用 CPU（`training_rank_cpu_percent`，按单核百分比，与主机 vCPU 数无关）≤5% 持续 300s（两条都仅当控制面解析出节点上唯一一个受管 attempt（PENDING 或 RUNNING，观测落在批次前 120 s 至后 30 s 内，且在本节点有存活容器）时计时，collector 自报 ACTIVE 不足以启动；只评估该 attempt 在本节点存活容器持有的 GPU——按 completion watcher 读到的 GPU UUID，声明的 `nvidia.com/gpu` 覆盖整节点时视为全部持有——其余 GPU 只是重置窗口的空闲样本，分配无法确定的 GPU 不评估，attempt 已 RUNNING 300 s 且该 GPU 越界时在控制面日志里告警一次（不发通知）；窗口属于该 attempt，节点换 attempt 或 job 即从零重新计时）；`LOW_MEMORY_AVAILABLE` ≤5% 持续 60s；`HIGH_PAGE_CACHE` ≥90% 持续 300s；`HIGH_LOCAL_FILESYSTEM_USAGE` ≥90% 持续 60s | WARNING → `RUN_DIAGNOSTICS` | FREEZE_EVIDENCE → VALIDATE_HOST（`LOW_GPU_UTILIZATION` 为 FREEZE_EVIDENCE → VALIDATE_GPU：只读诊断契约，不跑 DCGM 诊断、不升级硬件）；验证经 `host_diagnostic_probe` 重读触发指标，仍越界即以 RECOVERED「diagnostic inconclusive」结束；另发聚合通告邮件 |
| 本地磁盘满 | `statvfs` 于 `GPU_FAULT_FILESYSTEMS` 列出的挂载（缺省 `/`,`/var`,`/tmp`；块与 inode）；只读由宿主挂载表判定，被 collector 沙箱遮住的路径不上报 | `filesystem_used_percent` ≥98；inode 耗尽 `filesystem_inodes_used_percent` ≥98 同规则独立判定（`f_files=0` 不产生样本）；挂载不可用 `filesystem_unavailable` ≥1（`failure_mode` 为 `READ_ONLY`、`MOUNT_MISSING`（statvfs ENOENT）或 `PROBE_FAILED`（其他 statvfs 错误）；statvfs 挂起改报 `shared_filesystem_unavailable` / `PROBE_TIMEOUT`） | 容量与 inode：CRITICAL → `QUARANTINE`；不可用：CRITICAL → `RUN_DIAGNOSTICS` | 容量与 inode：FREEZE_EVIDENCE → MARK_UNSCHEDULABLE → QUARANTINE（cordon + taint `gpu-fault.io/quarantined`，不停任务）；不可用：FREEZE_EVIDENCE → VALIDATE_HOST（只读；信号仍为 1 时诊断失败，incident 以 RECOVERED「diagnostic inconclusive」结束，不隔离、不 reset/reboot） |
| 共享存储不可用/满 | 宿主挂载表 `/proc/1/mountinfo` 中 lustre/nfs 挂载的 statvfs 加一次有界目录项读取（数据路径探针，只读）；曾见过的节点级共享挂载从表中消失按跨重启记忆报 MOUNT_MISSING | `shared_filesystem_unavailable` ≥1（CRITICAL；`failure_mode` 为 PROBE_TIMEOUT / PROBE_FAILED / IO_ERROR / IO_TIMEOUT / MOUNT_MISSING，每个共享样本带 `source`（export，跨节点故障域身份）与 `fstype`，报错时带 `errno`）；`shared_filesystem_used_percent` ≥98（WARNING） | `RUN_DIAGNOSTICS` | FREEZE_EVIDENCE → VALIDATE_HOST（只读；信号仍为 1 时诊断失败，节点 incident 以 RECOVERED「diagnostic inconclusive」结束，不隔离；信号保持 active 不重复告警，重新挂载或恢复 export 后清零）；≥2 个节点在 600 s 内报同一 export（样本标签 `source`，即 mountinfo 的挂载源，或 `server`+`export`）不可用时，控制面另记一条集群级 `SHARED_STORAGE_FAILURE_DOMAIN` incident（`node_ids` 为成员节点，`policy_reference=shared-filesystem:<export>`，reasons 列出 export、节点与各节点 incident），各节点 incident 回指该记录，故障域记录只发一封通知（后加入的成员不重发；各节点自身诊断链失败时仍各发「diagnostic inconclusive」通告）；该记录无 workflow、无动作，节点链不变、不隔离不停任务；所有成员都报 0 后自动 RECOVERED，成员静默（最后一次为不可用且超过窗口）则转 ESCALATED 交运维关闭；无 export 标识（挂载点不是标识）不关联 |
| 磁盘 IO 饱和 | `/proc/diskstats` | `disk_io_util_percent` ≥98 或 `disk_io_await_ms` ≥100，持续 120s；await 为 iostat `await` 口径：区间内 Δ(字段 4 读耗时 ms + 字段 8 写耗时 ms) / Δ(字段 1 读完成数 + 字段 5 写完成数)，不计 discard/flush；任一单调计数器回退的区间不产生读数（见表后"磁盘 await 口径"）；设备离开 `/proc/diskstats` 或计数器重启时，collector 对每个 `disk_io_*` 指标报一次 `device_state=GONE`（只清除该设备的信号，不是读数，不进最新指标）；节点仍在上报而某设备连续 `GPU_FAULT_HEALTH_SIGNAL_DEVICE_AGE_OUT_SUMMARIES`（缺省 3，0 关闭）个主机健康摘要周期（`GPU_FAULT_HOST_HEALTH_SUMMARY_SECONDS`，缺省 300 s）没有样本时，控制面按接收时钟与节点时钟都满足才老化清除该信号 | WARNING → `RUN_DIAGNOSTICS` | 同上 |
| SMART 失败 | `smartctl --scan-open`、`smartctl -H -j` | `smart_health_failed` ≥1（仅布尔 `passed=false`）；扫描失败、盘无法打开、查询失败/超时/格式错误另报 `smart_query_failed`（`SCAN_FAILED`/`OPEN_FAILED`/`QUERY_FAILED`）和 collection error；无 smartctl、无盘或无 SMART 结论报 `smart_status_unsupported`（NOT_SUPPORTED，不记采集错误；出现/变化/消失为 `not-supported:*` 边沿，最新值留在 `telemetry_metric_latest`） | 自检失败 CRITICAL → `QUARANTINE`；查询失败不推断硬件故障 | 自检失败 cordon + QUARANTINE；查询失败重试并保留观测异常 |
| 网卡链路 down | `/sys/class/net/*/operstate`，仅必需接口；完整枚举后也检查接口缺失 | `network_link_down` ≥1；读取失败单独记录，不丢弃已读到的链路状态 | CRITICAL → `QUARANTINE` | cordon + QUARANTINE；受控恢复的 VALIDATE_HOST/VALIDATE_FABRIC 只判节点最新一次无采集错误的主机批次仍上报的接口，移出必需列表或已删除接口的最后读数不再阻止恢复 |
| 网卡错误/丢包 | rx/tx errors、drops 增量 | `network_errors_delta` ≥1；`network_drops_delta` ≥1 持续 60s；TCP 重传有意不设规则；计数器回退为 collection error（UNKNOWN），本轮不发该指标、不报 0 | WARNING → `RUN_DIAGNOSTICS` | FREEZE_EVIDENCE → VALIDATE_FABRIC |
| EFA/RDMA 计数错误 | `/sys/class/infiniband/*/ports/*/{counters,hw_counters}`、`ethtool -S` | `rdma_errors_delta`、`rdma_link_down`、`efa_rnr_errors_delta`、`efa_retry_errors_delta`、`efa_cq_errors_delta` ≥1；`ethtool` 差值只来自真实读数：失败/超时/重置为 collection error（UNKNOWN），缺失计数器报 `efa_ethtool_counters_unsupported`（运行中出现、变化或消失为 `not-supported:*` 边沿，投递一次；最新值留在 `telemetry_metric_latest`），都不报 0；sysfs 端口计数器回退同样为 collection error，本轮不发 `rdma_errors_delta` | WARNING → `RUN_DIAGNOSTICS` | FREEZE_EVIDENCE → VALIDATE_FABRIC |
| EFA 流量状态机 (`SITE_EFA_TRAFFIC`) | EFA hw_counters 字节速率，基线 EMA；仅节点有唯一活跃 attempt 时评估 | `SPIKE` ≥4× 基线；`DROP` ≤0.25×；`ZERO_WARNING` 零流量（≤1 B/s）≥60s；`HUNG_SUSPECTED` 零流量 ≥600s（只在该 attempt 曾有 ≥1 MiB/s 流量且过 120 s 启动宽限后计时；基线取第一个 ≥1 MiB/s 样本，之后按 α=0.2 的 EMA 只在正常样本上更新；采样间隔过长或观测无效即重新计时；rank 进度、训练步数/阶段与写盘只作上下文，不抑制也不重置计时；同一停滞 episode 只报一次，流量持续恢复后才重新武装） | 前三者 WARNING → `RUN_DIAGNOSTICS`；HUNG_SUSPECTED CRITICAL → `RUN_DIAGNOSTICS`(capture_process_state)；四者都另发 EFA/RDMA 事件邮件（`efa-rdma-event-zh-v1`） | SPIKE/DROP/ZERO_WARNING：FREEZE_EVIDENCE → VALIDATE_FABRIC（节点范围）。HUNG（DAG，`orchestration/hung_dag.py`）：FREEZE_EVIDENCE → COLLECT_HUNG_SUMMARY（BASELINE：attempt 全部节点的被动采样）→ COLLECT_HUNG_SUMMARY（RECHECK）→ COLLECT_HUNG_TRIAGE（首轮：按两次被动采样的分析在至多 4 个节点上只读采样，优先候选节点、RAS 线索节点与报告节点）→ COLLECT_HUNG_TRIAGE（扩采：剩余预算内的其他候选节点；两轮合计不超过 `GPU_FAULT_HUNG_TRIAGE_MAX_NODES`，缺省 8；采样 py-spy 栈、NCCL flight recorder、/proc 与 EFA 计数）→ COLLECT_DIAGNOSTIC_BUNDLE（首轮节点）；VALIDATE_FABRIC 在 RECHECK 之后并行，二者完成后 ESCALATE_SUPPORT；不隔离、不停任务，incident 以 `ESCALATED` 交人工。VALIDATE_FABRIC 只验任务自己的 EFA 端口（由 rank 进程线程持有的 QP 绑定），无法确定时显式 `fabric_status=UNKNOWN` 立即结束而不等待；任一取证步骤失败只退役依赖它的步骤，`ESCALATE_SUPPORT` 仍执行，发只读交接通知 `hung-support-handoff-zh-v1`（不是硬件升级邮件） |

磁盘 await 口径：`disk_io_await_ms` 是 sysstat iostat(1) 的 `await`（"Device Utilization Report" 一节，
`https://man7.org/linux/man-pages/man1/iostat.1.html`，sysstat 12.6.1 手册页同句）："The average time (in
milliseconds) for I/O requests issued to the device to be served. This includes the time spent by the
requests in queue and the time spent servicing them."。按 Linux 内核 `Documentation/admin-guide/iostats.rst`
"I/O statistics fields" 一节（`https://docs.kernel.org/admin-guide/iostats.html`）的字段定义，取采样区间内
字段 4 "# of milliseconds spent reading" 与字段 8 "# of milliseconds spent writing" 增量之和，除以字段 1
"# of reads completed" 与字段 5 "# of writes completed" 增量之和。不用字段 11 "weighted # of
milliseconds spent doing I/Os"：它是按在途 I/O 数加权累计的时间，其速率是 iostat 的 `aqu-sz`，不是单请求耗时，
且 5.0+ 内核把 discard 与 flush 的耗时也计入该字段——稠密 fsync 负载下与标准 await 的偏差会超过
GF-GENERAL-LIVE-006 `reference_iostat` 的容差。discard/flush（字段 12-17）不计入 await（它们对应
`d_await`/`f_await`）；`disk_io_util_percent` 仍取字段 10 "# of milliseconds spent doing I/Os"。内核文档要求
"Applications reading these counters should detect and handle resets when comparing stat snapshots"：设备重建、
重新挂接、重启或计数器溢出使任一单调计数器回退时，跨越回退的区间不产生 util/await 样本，下一周期从新基线重新
计算。稳态负载下两种口径按 Little 定律一致，100 ms 阈值的含义与默认值不变。

相同 Host 指标持续异常但 action、severity 或 failure_mode 改变时会重新产生 finding，
包括 EFA `LINK_INACTIVE -> PCI_DEVICE_MISSING`，无需先恢复为零。已提交 incident 的确认
绑定原接收时刻与处置指纹，旧投递不能确认新一轮语义。

观测完整性修正：EFA PCI/driver/port 读取失败不推进掉卡计数；未知 failure_mode
（包括无 PCI 证据的 `INVENTORY_UNAVAILABLE`）只诊断，不默认 reboot，也不因验证失败
升级 reboot。EFA 速率须有完整可比较的计数器对，`efa_traffic_observation_valid=0`
不代表零流量并会中断零流量连续窗口；UNKNOWN collector 也发送流量变化沿，受管
attempt 仍由控制面确认。新 Host 诊断步骤通过 `host_diagnostic_probe` 绑定触发
指标、设备、阈值及时间，缺失数据等待，单独的性能/Host 触发条件未恢复不授权硬件升级。
详见 [Host hardening](components/host-observation-hardening.md)；其余部分完成项见逐项清单。

原 12 类待改项的第二批分级、恢复意图和软件测试见
[Health policy hardening](components/health-policy-hardening.md)。
温度/功耗后续修改依据见[环境策略复核](components/gpu-environment-policy-review.md)。
指标策略版本为 `site-dcgm-metric-policy/v5`，复合规则为
`site-dcgm-correlation/v3`；旧工作流不在升级中自动重写。

关联 marker 不代表旧动作足够：后到 XID/SXID 仍须校验完整动作、GPU 范围及 attempt。
GPU 和显存温度均属于热故障类别；kernel XID 32/79 只有与同一可信设备、有效窗口内的
PCIe 越界同时存在时才参加联合规则，kernel XID 单独到达仍走独立策略。DCGM last-XID gauge 按它变化成
32/79 的时刻计窗口，停在旧值的 gauge（过期）与异卡的 XID 都不联合，PCIe 越界仍只读诊断。
持续隔离也不同于 reboot 流程中的临时隔离，合并后不得重新接纳受约束的故障节点；
健康热备的恢复必须针对实际替换后的节点。

### RecoveryAction 的落地机制

以下通用 `DRAIN` / GPU `RUN_DIAGNOSTICS` 描述适用于未携带新健康恢复契约的路径。
首表中的温度/热降频类、只读诊断契约名单内的性能/计数器诊断、训练进度和观测恢复，以
`health_recovery_contract` 为准：WARNING 只读验证（`DIAGNOSTIC_ONLY`，不跑 DCGM 诊断、禁止硬件升级）；
确认的温度/热降频 CRITICAL 走 `ENVIRONMENT_REVIEW`（终态隔离交人工，不自动冷却接纳；旧版已持久化的
冷却计划仍按原规则收尾）；不会因为动作枚举相同就进入下面的 legacy DCGM 失败升级链。名单外的 GPU 诊断
（1423/1424、PCIe 降速与 1501、1211/1213、fabric health 降级）按下面的通用 RUN_DIAGNOSTICS 行执行。

## 四、实现说明

- `CONTACT_SUPPORT`、`CHECK_MECHANICALS`、`UPDATE_SWFW` 在策略层是 EXECUTABLE 而不是 BLOCKED：
  `CONTACT_SUPPORT` 编译为 `ESCALATE_SUPPORT`（固定模板邮件，不 cordon），`CHECK_MECHANICALS`
  编译为通知并等待人工确认，`UPDATE_SWFW` 编译为含 `UPDATE_SOFTWARE_FIRMWARE` 的完整停机链。
  只有缺证据、产品不适用、未知 XID 和没有 resolver 的 workflow 才走 BLOCKED + `QUARANTINE`。
- Always-Fatal SXID（Table 23 内的码）直接执行 `REBOOT_NODE`，不需要 fabric_partition 或 GPU inventory；
  fatal trunk 与 10003/19084 直接执行 `RESET_ALL_GPUS_AND_NVSWITCHES`，要求 fabric_partition 和完整节点 GPU
  inventory，缺一即 BLOCKED。不在钉死表内却声明 Fatal/Always-Fatal 的码不授权任何破坏性恢复（BLOCKED）。
- XID 152/153 官方为 IGNORE，但 catalog 未列出适用产品，产品门禁会判为 NOT_APPLICABLE 并隔离节点，
  比官方建议严格（本方案的偏离；catalog 标注 Unused 的 61 个 XID 同理）。
- 示例 profile 把 `nvlinkDiagnostics`、`memoryDiagnostics`、`driverRemediation`、
  `softwareFirmwareUpdate` 声明为 OBSERVE，因此 XID 74 的现场诊断分支、XID 78、
  `row_remap_failure` 追加的 `RUN_FIELD_DIAGNOSTIC`，以及 SXID 的驱动/固件修复步骤在该 profile
  下会以 "no executable owner" fail closed，转交人工——但不再是「整条计划编译期 BLOCKED、节点照常可调度」：
  故障族一直以安全计划（FREEZE_EVIDENCE → MARK_UNSCHEDULABLE → QUARANTINE）先含容，节点健康族与节点生命周期族
  同样先执行首个无 owner 步骤之前的含容/取证前缀，记录停为 `BLOCKED/SAFETY_SETTLED`、incident
  `QUARANTINED`，并以 `contained-operator-handoff-zh-v1` 通知运维哪个能力待人工（首步即无 owner 的计划仍在编译期 BLOCKED）。
- 节点处于产品自身发起的重启窗口（`RESTART_NODE`/`REPLACE_NODE` 步已下发且其后的
  `RESTORE_SCHEDULING` 尚未完成）期间，该节点上的 kmsg XID/SXID 与 node-health 标记不再开新 incident，
  而是作为证据链接到拥有该重启的 incident；带旧 boot_id 的 kmsg 事件（agent 已按新 boot 心跳）视为
  重启前残留，落为 RECOVERED、不产生 workflow（`NOT_APPLICABLE` 的通知照常发出，写明未编排任何操作）。
  规则见 `orchestration/reboot_window.py`。
- 事件时间早于节点上正在运行的 attempt、且该 attempt 没有恢复 workflow 时：只有恢复类判定
  （`EXECUTABLE`，等级不高于 `RESTART_WORKLOAD`）因 attempt 重启已回应而记为被忽略的 RECOVERED；表中
  NOT_APPLICABLE、SITE_SAFETY 与 BLOCKED 各行的隔离或取证照常执行，与事件落在当前 attempt 内时相同。
- 同一 XID 的内核 NVRM 行与 DCGM 字段 230（`DCGM_FI_DEV_XID_ERRORS`）的变化是一次发生
  （`policy/xid_cross_source.py`）：第二份报告——同一 GPU 上与其内核行相隔 120 s 内的变化，或遇到已先行以相同方式决定的
  变化的内核行——作为证据链接到第一份的 incident，不执行任何操作，因此表中每一行的实际执行按一次发生计一次，而非按报告计；FAULT_DETECTED 通知同样每次发生一封。
  XID 154、74 或 144-150 的变化，其解码需读内核行，会最多等待 120 s 以待内核行，只有内核行始终未到才保持 BLOCKED + `QUARANTINE`。
