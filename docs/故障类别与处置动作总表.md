# 故障类别与处置动作总表

本文是[概要设计 v2](概要设计-v2.md) §2「故障分类与策略矩阵」的逐项展开：把每一类故障
的检测规则、NVIDIA 官方建议、本方案的策略判定和实际编译出的执行步骤放在一张表里。
事实源是代码，本文只做整理：

- 策略判定：`src/gpu_fault/policy/engine.py`、`src/gpu_fault/policy/nvlink74.py`；
- 官方目录：`src/gpu_fault/data/nvidia-xid-catalog-610.generated.yaml`、
  `src/gpu_fault/data/nvidia-fabric-manager-sxid-2025-11-14.yaml`；
- 步骤编译：`src/gpu_fault/orchestration/workflow_builder.py`、
  `src/gpu_fault/orchestration/coordinator.py`、`src/gpu_fault/orchestration/families/health.py`；
- 非 XID 规则：`src/gpu_fault/host_health.py`、`src/gpu_fault/gpu_metrics.py`；
- 能力开关：`config/runtime-profile.regional-hyperpod-safe.example.yaml`。

规则阈值、动作名和步骤顺序若与代码不一致，以代码为准并修订本文；
NVIDIA 目录供应链与门禁语义见[NVIDIA 策略供应链与实现](components/nvidia-policy.md)。

阅读约定：

- 「NVIDIA 官方建议」列原样引用 Xid Catalog / Fabric Manager User Guide 的文本；「本方案判定」是策略引擎输出的 disposition 和 `RecoveryAction`；「实际执行」是编译出的 `WorkflowOperation` 步骤链。
- `[...]` 表示条件步骤：`STOP_WORKLOADS` 仅在 workload_state 为 ACTIVE 时插入；`CHECKPOINT_WORKLOADS` 仅在有 checkpoint_manifest_ref 时插入（只记录引用，不做真实 checkpoint）；`RESTART_WORKLOAD` 仅在有 affected_workload_ids 时追加。
- 所有会改动节点的计划在 workload_state 为 UNKNOWN 时编译即拒绝（fail closed）；BLOCKED 类判定统一附加 safety_action `QUARANTINE`，执行 FREEZE_EVIDENCE → MARK_UNSCHEDULABLE → QUARANTINE 后等待人工。
- NVIDIA `RESTART_APP`（含 XID 154 的 `restart app` 标签、NVLink5 `XID_154_EVAL` 无伴随 154 时的回退）在 workload_state 为 IDLE 时由策略引擎改判 MONITOR_ONLY / `NO_ACTION`：没有受管应用可重启，只写 INFO marker 与调查通知，不建 workflow、不 cordon。下表 RESTART_APP 各行的「实际执行」列描述的是 ACTIVE 且能归因到 workload 的情形；ACTIVE 但归因不到 workload 仍走 SAFETY_PENDING 隔离，UNKNOWN 仍按上一条 fail closed。
- 链 A = GPU reset 链，链 B = 节点 reboot 链，定义见第一部分末尾的 RecoveryAction 落地表。

### RecoveryAction 的落地机制

| RecoveryAction | 实际机制 |
|---|---|
| `MARK_UNSCHEDULABLE` / `QUARANTINE` | 同一 K8s patch：`spec.unschedulable=true`、taint `gpu-fault.io/quarantined=sha256(incident)[:24]:NoSchedule`、写 incident/fencing annotation；被他 incident 隔离且未终态则拒绝 |
| `STOP_WORKLOAD` | patch Job/PyTorchJob/JobSet `suspend=true`，抓 pod 日志为证据，grace 0 删 pod，等待非 active；`enable-job-auto-resume=true` 直接 FAILED |
| `RESTART_WORKLOAD` | 预留 restart budget；终态 Job 新建 `<name>-r-<sha8>`，否则取消 suspend；应用热备重绑定与 NotIn 反亲和；GPU 数变化需审批注解 |
| `RESET_GPU`（链 A） | FREEZE_EVIDENCE → MARK_UNSCHEDULABLE → [CHECKPOINT] → [STOP_WORKLOADS] → QUIESCE_GPU_SERVICES（systemctl stop fabricmanager/dcgm/persistenced/collector/kubelet，ctr kill HMA 与 device-plugin 容器，清扫 `/dev/nvidia*` 持有者，420s 失败自恢复定时器）→ VERIFY_NO_GPU_CLIENTS → RESET_GPU（`nvidia-smi --gpu-reset -i <uuid>`）→ RESTORE_GPU_SERVICES → VALIDATE_GPU → RESTORE_SCHEDULING → [RESTART_WORKLOAD]；失败升级 REBOOT_NODE |
| `REBOOT_NODE`（链 B） | FREEZE_EVIDENCE → MARK_UNSCHEDULABLE → [QUARANTINE，健康路径] → [CHECKPOINT] → [STOP_WORKLOADS] → RESTART_NODE（`sagemaker.batch_reboot_cluster_nodes`，要求 NodeRecovery≠Automatic，等待 boot_id 变化 + 60s 稳定）→ VALIDATE_GPU → VALIDATE_HOST → VALIDATE_FABRIC → RESTORE_SCHEDULING → [RESTART_WORKLOAD]；失败升级 REPLACE_NODE |
| `REPLACE_NODE` | 不调用任何 provider 替换 API；从 `gpu-fault.io/spare=true` 且同实例组/类型的健康热备中选一台，隔离热备并返回 node_rebindings，后续 VALIDATE_* 与 RESTART_WORKLOAD 改到热备；无热备则 FAILED + 邮件；失败升级 ESCALATE_OPERATOR |
| `DRAIN` | cordon → [stop] → QUARANTINE → COLLECT_DIAGNOSTIC_BUNDLE（nvidia-smi -q/nvlink/topo、dcgmi diag -r 1、journal、nvidia-bug-report）→ [RUN_FIELD_DIAGNOSTIC，仅 `RUN_FIELD_DIAGNOSTIC_FOR_RMA`] → VALIDATE_GPU → ESCALATE_SUPPORT（SES 固定模板邮件 + vendor-ticket 记录）；无 RESTORE_SCHEDULING，节点保持 cordon+taint，incident 终态 `ESCALATED`，人工 RMA 后经 `POST /v1/incidents/{id}/close` 关闭 |
| `RUN_DIAGNOSTICS` / `VALIDATE_NODE` | 只读：VALIDATE_GPU/HOST/FABRIC 校验控制面中的新鲜遥测；GPU 类加 `dcgmi diag -r 1 -j`，FAIL 则升级 DRAIN |
| `REMEDIATE_EFA_DRIVER` / `RESTART_*_DEVICE_PLUGIN` | 见上表 EFA 行；节点需 `GPU_FAULT_NODE_ALLOW_EFA_DRIVER_REMEDIATION`，profile 需 `efaDriverRemediation: OWN` |
| `ESCALATE_OPERATOR` | FREEZE_EVIDENCE → cordon → [stop] → QUARANTINE → ESCALATE_SUPPORT（SES 固定模板邮件，无外部工单 API） |
| `RESTORE_SCHEDULING` | 校验 annotation 归属后去 taint、恢复原 unschedulable 值 |
| `COLLECT_EVIDENCE` / `NO_ACTION` | 仅 FREEZE_EVIDENCE（记录引用）/ 不建 workflow |

## 二、XID 表（NVIDIA Xid Catalog 610，172 条）

引擎顺序：catalog 查表 → 产品门禁（A*→A100，H*/GH*→H100，B*→B100，GB*→GB200）→ 版本门禁（xid154Linkage 含驱动/CUDA 要求时事件必须带 driver_branch、cuda_version，缺失 BLOCKED_MISSING_EVIDENCE，低于要求 NOT_APPLICABLE）→ 30s 内伴随 XID 154 的驱动报告动作覆盖本 XID 的 Immediate Action → 直接映射（IGNORE→NO_ACTION，RESTART_APP→RESTART_WORKLOAD，RESET_GPU→RESET_GPU，RESTART_BM→REBOOT_NODE）或专用 workflow。

## 四、实现说明

- `CONTACT_SUPPORT`、`CHECK_MECHANICALS`、`UPDATE_SWFW` 在策略层是 EXECUTABLE 而不是 BLOCKED：
  `CONTACT_SUPPORT` 编译为 `ESCALATE_SUPPORT`（固定模板邮件，不 cordon），`CHECK_MECHANICALS`
  编译为通知并等待人工确认，`UPDATE_SWFW` 编译为含 `UPDATE_SOFTWARE_FIRMWARE` 的完整停机链。
  只有缺证据、产品不适用、未知 XID 和没有 resolver 的 workflow 才走 BLOCKED + `QUARANTINE`。
- Always-Fatal SXID 直接执行 `REBOOT_NODE`；fatal trunk 与 10003/19084 直接执行
  `RESET_ALL_GPUS_AND_NVSWITCHES`。两者都要求 fabric_partition 和完整节点 GPU inventory，
  缺一即 BLOCKED。
- XID 152/153 官方为 IGNORE，但 catalog 未列出适用产品，产品门禁会判为 NOT_APPLICABLE 并隔离节点，
  比官方建议严格。
- 示例 profile 把 `nvlinkDiagnostics`、`memoryDiagnostics`、`driverRemediation`、
  `softwareFirmwareUpdate` 声明为 OBSERVE，因此 XID 74 的现场诊断分支、XID 78、
  `row_remap_failure` 追加的 `RUN_FIELD_DIAGNOSTIC`，以及 SXID 的驱动/固件修复步骤在该 profile
  下会以 "no executable owner" fail closed，转交人工。
