# GPU 故障处理系统开发者部署实现

本文是生产交付契约，只面向修改方案源码、生产 Manifest、renderer、配置模型或资源
生命周期的开发者。新增 operation、channel、Store、路由、插件或指标先阅读
[扩展指南](扩展指南.md)；扩展需要进入生产时再执行本文。

GitHub Actions从源码提交构建Runtime Image、三个组件wheel、Node bundle、
attestation和部署机离线bundle的端到端顺序见[CI 发布流程](CI发布流程.md)。本文继续
定义这些制品进入站点后的渲染、部署、升级和回滚契约。
只需要按主路径完成“修改代码、staging测试、生产晋级”的开发者先阅读
[EC2源码统一部署流程](EC2源码Staging复现流程.md)，遇到Profile、资源或回滚分支时再回到本文。
单EC2源码staging的首次和后续部署由
[EC2源码Staging统一部署流程](EC2源码Staging复现流程.md)封装为同一个四参数
`gpu-fault-admin deploy`入口。
clean与dirty工作区都会先复制到canonical `state-dir`下的内容寻址隔离checkout。
dirty工作区再转换为不修改开发分支的临时commit并生成`staging_only`候选。clean正式
commit只有在`HEAD == refs/remotes/origin/main`时才尝试自动下载并验签同commit main CI
候选，命中后使用`release-build-promoted`；个人clean commit或候选不可用时使用本地
`release-build`。GitHub Release也使用promoted入口，三种attestation不能互换。
生成的内部site固定引用该隔离checkout，不能回指之后仍会变化的开发工作区。

| 源码状态 | 构建入口 | 强制门禁 | 发布等级 |
|---|---|---|---|
| dirty开发工作区 | `release-build-staging` | public scan、影响测试、区域影响计划；不确定时升级全量 | `staging_only=true` |
| clean个人commit或无CI候选 | `release-build` | static后并行普通pytest/PostgreSQL stress/source-only artifact，最后完整制品一致性 | `staging_only=false` |
| GitHub main CI已签名候选 | `release-build-promoted` | CI gate验签与源码/清单匹配、最终制品一致性 | `staging_only=false` |

staging attestation还绑定影响测试`BASE`；源码commit相同但`BASE`变化时也必须重新执行
影响选择。普通生产部署和验签默认拒绝staging-only等级。

main CI把unit证据分成`runtime`、`deployment`、`fault_runner`和`postgres`四个逻辑
域；runtime再按稳定pytest nodeid哈希拆成三个签名执行shard，共生成六份物理shard。
每个shard分别绑定自己消费的源码、测试、依赖、Python/Runner环境；PostgreSQL shard还
绑定实际PostgreSQL image。shard未命中时只重跑该域，六份数据最后统一
`coverage combine`并执行生产78%组合floor、`coverage.module_floors`声明的per-module
floor，以及 production/runner 各自95%的语句和分支门禁（deployment-only模块只在合并报告里可见）。deploy-host-only管理员源码变化只使
deployment shard失效，不要求重新测试未变化的应用Runtime；runtime共享源码变化会
保守地使依赖它的多个shard失效。只修改文档或`.github`时由当前static负责验证并可复用
全部shard。当前commit始终重新执行static、文档/CI契约和artifact检查。

管理员部署现有 release 时使用[管理员快速部署](管理员快速部署.md)和
[管理员日常运维](管理员日常运维.md)，不阅读本文逐个 apply 方案资源。
管理员和客户不编写方案 Manifest；客户自己的训练 workload YAML 是明确例外。

## 1. 支持边界与正常入口

唯一生产拓扑是区域 CPU EKS/HyperPod 控制面、Aurora PostgreSQL、TLS NLB 与一个或
多个 `NodeRecovery=None` 的 HyperPod EKS GPU 集群。通用 Kubernetes、Slurm 和
CPU/GPU 单集群一体化不是新生产功能的交付目标。

正常管理员入口是：

```bash
gpu-fault-admin deploy \
  --cpu-cluster-arn <cpu-eks-or-hyperpod-arn> \
  --gpu-cluster-arn <gpu-eks-or-hyperpod-arn> \
  --state-dir /secure/gpu-fault \
  --admin-email <operations-email>
gpu-fault-admin status --state-dir /secure/gpu-fault
gpu-fault-admin status --full --state-dir /secure/gpu-fault
gpu-fault-admin workflow-reconcile --state-dir /secure/gpu-fault --dry-run
gpu-fault-admin join-cluster --state-dir /secure/gpu-fault \
  --gpu-cluster-arn <existing-gpu-eks-or-hyperpod-arn>
gpu-fault-admin remove-cluster --state-dir /secure/gpu-fault \
  --gpu-cluster-arn <gpu-eks-or-hyperpod-arn> --confirm REMOVE_GPU_CLUSTER
gpu-fault-admin uninstall --state-dir /secure/gpu-fault \
  --cpu-cluster keep --confirm UNINSTALL_GPU_FAULT
```

首次、后续升级和失败续跑都使用第一条四参数命令。`release-ref`、artifact、site、
`release-build/release-deploy`、bundle和venv路径是内部实现，不属于公共CLI契约。
隐藏site模式只保留给内部编排和兼容审计。

`resume`和`rollback`仍是低层区域编排器命令。开发者可以在staging和break-glass验收
中使用它们，但不得把低层 release JSON 写成管理员日常事实源。高层
`join-cluster`必须从`state-dir`中的内部site与GPU ARN进入持久状态机。

源码统一部署生成的deploy-host安装与一个canonical `state-dir`绑定。绑定记录独立于
签名bundle内容、权限为`0600`；安装后的管理员CLI对不同state目录fail closed，且拒绝
发生在日志创建、源码准备、AWS和Kubernetes动作之前。绑定读取拒绝不私有、不可读、
软链接、重复字段、未知schema或不一致路径；已有站点的安装不完整时不能当作未绑定。
未绑定的开发`.venv`只能对已有绑定站点执行普通源码deploy或真正只读的子命令，
rollback、显式site及prepared-source形式不属于普通源码deploy。原有release/pin、
目标、源码和审批门禁不因此放宽，也不提供继承环境变量作为绕过。

源码准备器分别计算deploy-host payload、deploy-host编排、Control Plane、Executor、
Node Runtime和release/Manifest输入身份。已有站点只有deploy-host身份变化时，只更新
内容寻址bundle/overlay venv，运行影响门禁和只读preflight；应用身份完全相同时不生成
Runtime Image或应用release，不进入GPU rollout。仅测试/文档变化只执行影响门禁。
上次成功身份来自本地Cosign签名授权记录，缺失或不匹配时保守回到应用release流程。

## 2. 角色与事实源

| 角色 | 维护内容 |
|---|---|
| 管理员 | 已有集群ARN、state-dir、管理员邮箱、审批和验收证据 |
| 开发者 | 源代码、源Manifest、renderer、site schema、生命周期契约、测试和文档 |
| 自动化 | 内部`site.yaml`、私有release JSON、generated Manifest、构建期cleanup inventory和运行时注册表 |
| 客户 | 自己的训练workload YAML；不修改本方案Manifest |

管理员不维护内部`site.yaml`。管理员不维护 `regional-release.json`。CLI从state中的内部site在
`0700/0600`临时目录生成低层配置；直接release JSON和`regional-env.sh`只用于详细
手工流程或break-glass。

生产资源有三层事实源：

| 层级 | 事实源 | 作用 |
|---|---|---|
| Kubernetes | 每个CPU/GPU EKS的`gpu-fault-installed-resources` | 卸载实际安装的workload、RBAC和namespace资源 |
| 节点 | `/opt/gpu-fault/installed-units.txt`及AgentRecord摘要 | 卸载实际安装的systemd unit |
| AWS | Aurora中的`installation_resource`对象 | 记录ARN/ID、ownership、delete policy、依赖和状态 |

不得新增第二份手工Kubernetes、unit或AWS资源清单。

区域 cluster registry 的运行时事实源是 Aurora 中不可变、单调 generation 的
revision/head。`gpu-fault-regional-clusters` Secret 只作为首次 bootstrap、部署输入和
灾备副本；已有 durable head 时，进程启动不得再用 Secret 内容删除或覆盖 runtime
revision。首次上线 watcher/ACK 协议仍需一次 CPU rollout；完成后
`join-cluster/remove-cluster` 通过 execution-token API 发布
`PENDING/ACTIVE/FAILED/ROLLED_BACK/DRAINING/REVOKED` revision，并等待所有当前活跃的
CPU进程ACK，包括发布后加入的进程，无需重启CPU Deployment。ACK必须匹配当前
generation与内容摘要，且ready和持久心跳均有效。发布时的`required_member_ids`快照
保持不可变；其中已知记录超过stale窗口后，可以不再阻塞仍活跃且全部ACK的机群。
记录缺失、未来心跳或全机群心跳过期不能算收敛，只有required集合和成员记录都为空
才是首次bootstrap的空机群成功。运行时readiness同时受最近成功刷新和成功写入心跳的
新鲜度约束，不能只靠持续读库延长服务资格。该契约要求同release及一致的stale配置，
不把心跳过期描述成Kubernetes Pod退出证明。只有 `ACTIVE` 集群允许领取远程命令；join失败只转换
目标集群 lifecycle，不用候选site覆盖其他并发加入的集群。Secret灾备副本的单集群更新
必须使用Kubernetes `resourceVersion` CAS重试，不能并发执行无条件读改写。

## 4. 配置、Profile与Release契约

新增配置必须先确定唯一事实源：

- 区域拓扑、身份、制品引用和健康目标进入`RegionalSite`/`site.yaml`；
- Runtime Profile策略进入版本化Profile YAML，同一`profile_version`内容不可覆盖；
- CPU非敏感配置进入按领域拆分的ConfigMap；
- 管理员可变配置进入`state-dir/admin-config/desired.json`，由严格`AdminConfig`
  schema规范化并生成全局及角色摘要；公开模板当前包含22项控制面容量、Aurora
  Min/Max、Processor、Workflow、通知投递和证据保留字段；
- token、密码和私钥进入Kubernetes Secret、Secrets Manager或仓库外受控文件；
- 节点配置由Installer生成`/etc/gpu-fault/*.env`。

Processor 参数必须按角色经 renderer 生成，不能把 worker 的长 lease/deadline
复制到 ingress/spool-worker，也不能在线 `kubectl set env`。当前区域 worker 使用
request lease/renew/deadline `150/10/120s`，ingress/spool 使用 `30/5/20s`；
retry backoff 为 `1..30s`，completion cluster concurrency 生产固定为 1。
三个CPU角色均禁止 Uvicorn `--limit-max-requests`：ingress 在burst中重叠回收会减少
服务进程并放大准入等待，worker回收会中断claim/lease。进程替换必须通过受检
Deployment rollout、Pod replacement或liveness完成。
容量验收改变 telemetry spool、control-worker副本、remediation budget或Aurora
Min/Max时，管理员编辑`<state-dir>/admin-config.yaml`并执行`gpu-fault-admin config`。
CLI在同一命令内生成并归档计划SHA，同时校验字段上下界、ACU步长和Min/Max关系、
spool开关/副本一致性及PostgreSQL fleet连接预算，再把规范化配置写入低层release JSON。
发布器复用当前签名镜像和wheel，在临时目录调用同一role-split renderer，不修改检入的
默认生成物。全局摘要进入release state和Deployment metadata，角色摘要进入Pod
template；CPU纯配置变化分类为`CONTROL_PLANE_ONLY`，不执行schema、GPU、Node Runtime、
Profile或cluster registry revision，只按摘要滚动受影响CPU角色。release delivery还
分别维护ingress、worker和spool Manifest摘要；角色Manifest单独变化时只render/apply并
等待该角色，共享CPU输入、Control Plane wheel或pin变化仍保守滚动全部CPU角色。
Aurora-only变化先
通过RDS API收敛，随后release走`NOOP`验证并刷新全局配置摘要；混合变化在后续release
失败时，只有证明原角色未变或匹配回滚完成，才恢复原Aurora Min/Max。
`admin.config_recovery`绑定本次准入baseline、目标完整配置及角色摘要、previous快照、
明确的未开始组件进度或已完成回滚证据。若管理对齐已清除回滚journal，还必须核对本次
调用时间范围内同站点、同release的driver回执，确认回滚PASSED且管理状态已同步。
候选已commit、部分变更、回滚策略拒绝或读不到live状态时，保留pending目标并失败；
失败审计记录恢复决策、原因和所读live状态摘要，不新建另一套journal。
不得在线`kubectl set env`或绕过管理员事务直接改RDS。

Aurora ACU 窗口只有一个写入口：`gpu_fault.admin.aurora_capacity`。
`create_db_cluster_arguments(AuroraClusterSpec)`生成bootstrap的`create-db-cluster`
参数（引擎版本常量`AURORA_ENGINE_VERSION`、`gpu-fault:site-id`与`Application`两个标签），
`_modify_window`是唯一的`modify-db-cluster`容量调用，三个公开入口共用它：
`reconcile_aurora_capacity`一次做完修改与settle（bootstrap、压测夹具、管理员命令的
Aurora回滚），`request_aurora_capacity`/`await_aurora_capacity`把同一变更拆成"发起并等
RDS就位"与"等实例真正跑在新ACU上"两半，供`config`在中间滚动受影响的控制面角色；`expected`可省略
（bootstrap与压测夹具没有变更计划记录）、`aws_json`可注入（bootstrap传
`CommandRunner.aws_json`；`config --dry-run`只打印计划，不调用RDS）。旧版`deploy.sh`和运维手册
通过`python -m gpu_fault.admin.aurora_capacity create|reconcile`调用同一模块；
`tests/admin/test_admin_aurora_capacity.py`扫描全仓库，保证该RDS参数只出现在这个模块里。
bootstrap对已有集群的容量对账放在writer/reader就位之后，因为共享reconciler要在两个
实例上证明窗口已生效。

`config`创建计划或NOOP审计前必须同时验证隔离checkout中的
`dist/current-release.json`与`dist/<release-id>/release.json`逐字节一致，使用state
内Cosign公钥验证attestation确实绑定该Manifest，并读取CPU集群
`gpu-fault-regional-release-state`，要求事务已commit、phase complete且live release
ID相同。开发checkout的`dist/`漂移、snapshot被修改、签名不匹配或live release不一致时
均fail closed，不得把审计绑定到错误release。

`regional_release_config.load_release_artifacts`先规范化Manifest的真实路径，再用
`gpu_fault_release.containing_repository_root`定位其所属源码快照。定位同时要求仓库目录
锚点和实际区域rollout入口文件，不以同名目录代替完整源码树。三个组件wheel和Node
bundle的相对路径都从该根解析，并使用同一组规范化路径完成存在性、摘要校验及返回，
避免校验后再次解析软链接而选中不同文件。已经定位的快照缺少制品时直接失败，不回退
到运行引擎的checkout；仓库外旧Manifest保留原引擎根回退，未使用Manifest的配置仍以
配置文件目录为基准。此定位不替代验签，也不改变schema-v4的独立OCI及离线依赖身份。

新AdminConfig计划只能从已commit的live release创建。发布中断后的幂等续跑是唯一例外：
活动plan与approval必须仍然存在并绑定同一release/target config，live state必须是
`CONTROL_PLANE_ONLY`、目标配置摘要完全相同且不处于rollback。满足全部条件时允许
`transaction_committed`暂未恢复并继续原发布；缺少审批、目标漂移或rollback状态仍立即
fail closed。

spool enable按spool-worker→ingress顺序；disable先关闭ingress admission，等待
`gpu_fault_telemetry_spool_depth`和`gpu_fault_telemetry_spool_leased`归零，再缩容
spool-worker。配置热更新不属于当前契约；进程仍在启动时读取环境变量。

### 4.1 Runtime Profile的作用

Runtime Profile不是普通参数文件，而是区域控制面对“谁可以执行哪类能力”的授权和
路由契约。策略引擎先产生恢复意图，workflow再通过Profile决定该能力是仅观察、由本方案
执行还是委托给其他实现。

Profile分成两类文件：

| 文件 | 维护者 | 作用 |
|---|---|---|
| `runtimeProfile.templateSource` | 开发者 | 唯一可编辑策略模板 |
| `runtimeProfile.source` | `release-deploy` | 按策略内容生成的不可变快照 |

开发者不得直接修改`source`快照、`site.yaml`中的Profile版本或Agent config digest。
`release-deploy`根据模板内容自动生成版本、快照和相关site字段。

Profile在区域控制面按`profile_version`只注册一次，并由所有引用该版本的GPU集群共享。
修改Profile影响的是整个站点中使用新版本的训练任务和节点，不是某一个注册锚点集群。

### 4.2 Profile字段与模式

| 字段 | 含义 | 修改规则 |
|---|---|---|
| `cluster_id` | 首次注册时使用的稳定锚点 | 模板保留占位符；发布器从site注入，不随GPU集群增删改变 |
| `environment` | Profile适用的编排环境 | 当前生产固定为`hyperpod-eks` |
| `profile_version` | 不可变策略版本 | 模板值不作为发布版本；由内容摘要自动生成 |
| `claims[]` | 对每个capability声明期望模式、owner和adapter | 策略变更的主要编辑位置 |
| `observed[]` | 声明owner实现是否可用及实现版本 | `OWN/DELEGATE`必须有匹配且`available=true`的事实 |

Capability mode：

| mode | 含义 | 约束 |
|---|---|---|
| `DISABLED` | 能力完全关闭，不进入effective Profile | 用于明确删除能力 |
| `OBSERVE` | 只识别、记录和通知，不允许执行动作 | 新能力和高风险能力的默认阶段 |
| `AUGMENT` | 多个检测来源共同补充证据 | 只允许非破坏性能力 |
| `OWN` | 本方案指定owner是唯一执行者 | 破坏性能力的正常生产形态 |
| `DELEGATE` | 将能力委托给外部owner | 当前生产硬约束通常禁止托管恢复委托 |

破坏性capability不能使用`AUGMENT`，也不能有两个active writer。`OWN/DELEGATE`缺少
匹配observed事实时会降级为`OBSERVE`并产生warning；统一发布入口会拒绝带warning的
Profile。

3. 确认Node Agent allowlist、安装参数和heartbeat实际广告该能力；
4. 完成[安全与参数参考](安全与参数参考.md)对应破坏性阶段的维护窗口验收。

### 4.4 什么时候不修改Profile

以下变化通常不改变能力授权，不修改模板：

- 普通bug修复或内部重构；
- Control Plane、Executor或Node Runtime重新build；
- wheel、bundle、Schema或protocol版本变化；
- 增删GPU节点或接入/移除GPU集群；
- 修改超时、队列、Collector周期或资源requests/limits；
- 能力owner、mode、adapter和实现version都不变的发布。

这些变化由release manifest、环境配置或Agent config digest表达。

### 4.5 Profile修改与自动发布流程

开发者只编辑`templateSource`指向的YAML，不修改site和历史快照。推荐流程：

1. 修改目标claim的`mode/owner/adapter`及对应observed事实。
2. 运行相关单元测试和Profile编译测试：

   ```bash
   .venv/bin/python -m pytest -q tests/regional/test_capabilities.py
   ```

3. CI构建、测试并推送不可变runtime image：

   ```bash
   make PYTHON=.venv/bin/python release-build \
     RUNTIME_IMAGE_REPOSITORY=<registry/repository>
   ```

4. 执行目标站点原有部署命令。Profile内容变化时，首次运行会在
   `<state-dir>/release-deploy/profile-plan.json`输出差异并停止。审核其中的
   `change_kind`、capability变化、原/目标版本、live baseline、策略摘要和目标快照摘要。
5. 获得变更单或维护窗口批准后，在同一条deploy上带审批参数重跑一次，写入绑定该计划
   摘要的一次性state审批并继续同一部署：

   ```bash
   gpu-fault-admin deploy \
     --state-dir /secure/gpu-fault \
     --approve-profile-plan "$(jq -er '.plan_sha256' \
       /secure/gpu-fault/release-deploy/profile-plan.json)" \
     --reference CHG-12345
   ```

6. 没有单独的审批动词；审批失败或计划漂移时按错误里给出的当前摘要重新审核。
   之后的普通升级仍是 `gpu-fault-admin deploy --state-dir ...`，不带审批参数。
7. 脚本自动：
   - 规范化claims/observed，忽略YAML顺序和`cluster_id/profile_version`；
   - 计算策略digest并生成`regional-hyperpod-<digest12>`版本；
   - 写入`<site目录>/profiles/<version>.yaml`不可变快照；
   - 更新site的`source/version`和Agent config digest；
   - 验证CI attestation签名、Manifest SHA和delivery identity，不在部署机重新build；
   - 由组件DAG选择CPU、Executor、Watcher、Collector、DCGM、Reconciler和Agent；
   - 首次部署只把第一个GPU集群写入基线site并完成CPU加单GPU基线；其余GPU ARN在
     基线verify后进入独立batch join，不把多个GPU集群绑成一个原子bootstrap事务；
   - Node Runtime按Fleet waves收敛节点systemd Collector/Agent；
   - Profile finalize前拒绝仍引用旧Profile的非终态workflow或活动workload；
   - 执行quick gate并生成绑定release ID、delivery、站点/集群身份、时间和live release
     state SHA的结构化证据；紧随其后的完整verify只复用证据明确覆盖的
     CPU role-split、逐GPU Executor verifier和`runtime_component_identity`，其他检查
     继续执行，证据过期或不匹配时补跑完整检查；首次bootstrap使用同一证据协议；
     若只剩
     `GpuFaultStoreIoRejected`，且所有运行中CPU Pod证明了完整、新鲜的零值进程视图，
     最多等待420秒让旧5分钟rate窗口和Alertmanager状态清零；
   - upgrade前同时冻结Executor internal error的保留数和最近错误时间戳；保留数是会随
     terminal command清理而下降的gauge，完整verify以最近错误时间戳是否前移判断本次
     发布是否新增缺陷。`GpuFaultRemoteCommandExecutorInternalError`同样按最近900秒内
     是否出现新错误触发，不再对保留数使用Prometheus `increase()`；
   - critical清零后才开始120至300秒stability window。每轮CPU、各GPU集群、Store和AMP
     只读采样最多8路并行，再生成轻量summary。其他
     critical、新Pod重启、非终态remote command或等待超时仍按`autoRollback`恢复
     在线release。

计划通过`site_identity.site_name`、`site_identity.aws_region`和
`site_identity.cpu_eks_arn`直接展示稳定站点身份，并用`site_identity_sha256`校验该
可读对象。审批记录还绑定注册锚点、原/目标Profile版本、
规范化策略摘要、模板/快照摘要和审批时的live Profile SHA。管理员必须把审核过的
`plan_sha256`通过`deploy --approve-profile-plan`显式传回；命令在同一文件锁内比较当前计划，一致后才写
审批并继续发布。失败续跑且live baseline未变化时保留审批；站点身份、模板、目标内容或live
baseline变化时旧审批自动归档为`SUPERSEDED`并要求重新审核。只有发布完成
verify、stability和commit后才写入`CONSUMED`审计并删除活动计划和审批，不能重放。
审批与发布共用`state-dir`文件锁；不得手工编辑或复制这些JSON记录。
管理员操作契约见[Runtime Profile变更审批](管理员Profile变更审批.md)。

区域 release diff 比较规范化策略摘要，而不是 Profile 文件路径或原始 YAML SHA。
`source` 从模板切换到不可变快照、字段顺序变化或注册锚点替换时，只要规范化策略与
版本不变就分类为 `NOOP`。source/template 原始 SHA 仍写入 release state，仅用于审计
和旧状态迁移。
若site的`source`路径漂移但
`<state-dir>/profiles/<current-version>.yaml`字节SHA与live release state完全一致，
发布规划器可用该本地不可变快照恢复可信baseline并原子修正site；缺少快照或SHA不一致时
仍分类为`UNKNOWN_BASELINE`并要求停止，不得通过审批绕过。

训练提交不再手工填写Profile版本：

```bash
gpu-training-submit --site /path/to/site.yaml training.yaml
gpu-fault-workload-annotate --site /path/to/site.yaml training.yaml
```

显式`--runtime-profile-version`与`--site`同时使用时必须完全一致，否则命令拒绝提交。

新增配置还必须：

1. 更新`site.example.yaml`、schema解析、脱敏审计摘要和负向测试；
2. 重新生成`src/gpu_fault/data/env-inventory.json`和两份环境变量参考；
3. 拒绝未知拼写、跨Region ARN、残留占位符和不安全Secret位置；
4. 进入`preflight`、`verify`或`status`中的至少一个可观测检查。

清单里的`value_kinds`是生成器从读取处的转换推断出来的类型（`int(...)`、`float(...)`、
与`0/1/true/false/yes/no/on/off`比较），五个运行时进程启动时按它校验取值并 fail
closed。因此新增一个数值或开关变量时，读法要保持单一且不要用`except ValueError`
兜住解析——多处读法冲突或被兜住的变量会退回“无类型、不校验”，重新生成清单时静静
少一条，而不是报错。开关的启用词也来自代码：只判等`"true"`的开关不会接受`yes`，
若要接受就同时改读取处，不要只改文档或配置。

`site.yaml`允许`spec.clusters: []`，因为已完成站点可以注销最后一个GPU集群并保持
空载控制面。该语义不能用于首次bootstrap：区域部署状态机在没有release state或仍处于
`bootstrap-*`恢复阶段时要求至少一个GPU集群，并在首个Kubernetes apply前fail closed。

Aurora凭据刷新属于跨角色配置：`preflight/verify`必须同时解析CronJob的
`GPU_FAULT_AURORA_RESTART_DEPLOYMENTS`和live Role的Deployment
`resourceNames`，两者集合不完全一致时fail closed。只允许ingress而漏掉worker
会形成“Secret已更新、部分消费者仍使用旧密码”的隐蔽漂移。控制面审查2026-09-08（CP-3 /
H1）后刷新器默认不再滚动Deployment——三角色把`gpu-fault-aurora` Secret整体挂到
`/etc/gpu-fault/aurora`，连接池经`GPU_FAULT_STORE_URL_FILE`重读DSN；
`GPU_FAULT_AURORA_RESTART_DEPLOYMENTS`只在`--restart-deployments`（或
`GPU_FAULT_AURORA_REFRESH_RESTART_DEPLOYMENTS=true`）兼容开关下驱动滚动，但RBAC一致性
仍照旧要求，因为开关随时可能被打开。`verify-control-plane-role-split.sh`新增
`verify_aurora_credential_mount`核对三角色的volume/secretName/无items/mountPath/只读/无
subPath与`GPU_FAULT_STORE_URL_FILE`来源。

凭据刷新器的版本化资源由`regional_release_aurora_refresh`统一渲染，首次安装和验证Job
也由区域release负责。ARN bootstrap在首次和已有站点均只收敛外围IAM/Pod Identity，
不提前apply候选ServiceAccount、Role、RoleBinding或CronJob。
`aurora-refresh`是独立发布组件：Manifest、
Control Plane wheel、runtime image或只读漂移决定是否执行；纯刷新器变化不滚动CPU/GPU，
也不执行DDL。只读取`gpu-fault-aurora`的master Secret ARN引用用于渲染，不把数据库密码
读入普通发布快照。

公开`preflight`保持只读，不修复刷新器、创建proof Job或绕过未知状态。内部
`preflight --for-deploy`仅由已授权的deploy driver调用，不是公共只读预检的别名：
`regional_admin_commands.build_deploy_preflight_report`从真实发布计划选择允许修复的
刷新器/监控项，先校验非Store前提；只有计划包含`AURORA_REFRESH`才暂缓workflow读取，
在刷新完成后补回该硬门禁。监控项的WARN也只表示已验证且计划会修复，不代表忽略读取
失败或提前更新ADOT/AMP。

`src/gpu_fault_release/regional_release_prerequisite_repair.py`在任何依赖Store的门禁
之前建立独立`aurora_prerequisite_repair` journal，解决密码已轮换而旧刷新器无法修复
自身的顺序问题。先绑定候选Manifest pin、CPU EKS/namespace、Aurora资源身份、原release
state摘要和旧刷新器完整快照，再持久化`PREPARED`；不能先apply候选再捕获previous。
需要更新时先以`suspend=true`安装候选CronJob，用一次性Job证明它支持禁止消费者重启的
接口、同步`AWSCURRENT`并验证新鲜刷新状态，成功后才恢复候选调度并记录`READY`。
一次性Job直接导入候选wheel的`aurora_credential_refresh.refresh_once`，确认其
`restart_deployments`参数存在后才运行入口；回归测试执行实际生成的Python程序，不能只
模拟Job完成状态，否则运行时API改名可能通过测试却在容器启动时失败。
该前置事务只准备CA、候选wheel和刷新器，不执行DDL、业务Pod重启、Profile或GPU rollout。
Store门禁通过后，应用事务接管最初的旧刷新器快照与组件进度，不能把已修复的候选误当旧版。
失败或清理未完成时保留journal；续跑验证同一候选、数据库和baseline并重新刷新，
不复用旧的密码有效性证明。尚未被应用事务接管的修复可独立恢复原对象，不把候选标为已提交。

bootstrap的前置修复会单独保存phase、集群完成列表、清理进度、清理失败信息和续跑phase
的原始表示；这些经过类型与范围校验的进度写入不改变原始完整baseline摘要，其他字段
仍须完全匹配。旧首次安装journal只在还原已知初始进度后完整SHA精确匹配时才兼容，
不能忽略未知字段、应用完成证据或真正的身份漂移。
直接bootstrap也在资源和候选checkpoint写入之前检查尚未接管的前置修复。

仅对已清理、未接管且没有应用部署完成证据的bootstrap，允许换到另一候选：
重新验证原baseline、原候选绑定、CPU/namespace UID、数据库、集群成员和快照，
先按原Job身份完成清理并恢复完整刷新器，再原子记录新候选baseline和新repair journal，
保留前驱审计关联。恢复或持久化失败保留可续跑记录，不直接修改旧binding来冒充新候选。
新候选必须重新验证Manifest pin、凭据及Store；同一release的Manifest漂移仍拒绝，
此路径不扩大supersede或commit-live的权限。

升级候选同样可能在修复`READY`之后、应用事务开始之前中止（2026-09-18线上：候选在
workflow门禁被拒），而release id是源码树的摘要，原候选不会再出现；若journal只认原候选，
已提交的站点会被这条孤儿journal永久锁住，`deploy --rollback`也进不去。因此
`validate_upgrade_repair_handoff`允许**下一候选**接管非bootstrap的孤儿journal，条件全部
必须成立：当前state减去journal后与原baseline完整SHA精确匹配（应用事务从未开始）；state与
baseline都是`phase=complete`、`transaction_committed=true`、`release_lifecycle=COMMITTED`、
`commit_cleanup_completed=true`，且线上release id不是孤儿候选；绑定为`bootstrap=false`、
`commit_live=false`、执行计划仅含刷新器；CPU EKS/namespace/数据库身份一致；快照摘要与内容
通过刷新器快照校验；Job账本字段完整。接管先按原Job身份复查清理、恢复原刷新器完整快照并
复验数据库身份，再原子写入绑定新候选的journal：它继续携带最初的旧刷新器快照（不重新捕获
孤儿候选的对象），`supersedes`保存前驱审计和接管前的state摘要——deploy driver在
release-diff时pin的就是那份含孤儿journal的state，apply阶段的expected-state门禁据此桥接。
恢复或持久化失败保留原journal，下次重复恢复。resume、supersede、commit-live仍拒绝
（`candidate binding differs`）；`rolled-back`站点上的孤儿不在此路径内。
`deploy --rollback`对同类孤儿执行同一验证后独立恢复原刷新器并删除journal，随后按原提示
停止，不回滚应用。

首次bootstrap没有业务Pod可供执行Store探针，因此
`src/gpu_fault_release/regional_release_store_proof.py`以固定候选CPU image创建只读
数据库proof Job，执行同一受信部署源码中的`regional_release_store_probe.py`。
Job保留模板中指向组件venv的`PATH`，使`python -I`加载同一CPU组件wheel；
这也兼容基础Python仅含共享依赖的旧镜像。新镜像的默认`PATH`已经指向单一应用环境，
仍保留显式组件路径，不能用基础解释器代替该环境完成Store检查。
proof绑定namespace UID、Aurora ARN/resource ID、endpoint、数据库、用户名、master
Secret引用、schema目标、run ID、Job UID和完成时间，读取前后重验数据库身份。
Job只在CPU namespace引用DSN Secret和RDS CA，不挂载ServiceAccount token；连接强制
`verify-full`、只读repeatable-read事务及连接/语句/锁等待上限，不实例化会自动建表的
业务Store。
首次必须实际证明数据库未初始化且为空：允许已声明但仍无行的部分建表，不接受未知
table/view、RLS或未验证的执行策略。Pod、release state缺失或历史`CREATED`标记都不能
证明空库。普通bootstrap只有已绑定的`bootstrap_database_origin`空库证明允许续跑检查已初始化库，
且每次仍新读schema版本、连续migration身份及两处workflow/remote-command/Observation
状态；非终态、未知状态或schema漂移均阻塞。密码及数据库安全证明完成前不得运行schema
ensure或启动业务Pod，历史origin不是当前“无活动记录”的缓存。

受管proof Job失败时，`regional_release_probe_job`在UID限定清理前用最多20秒、
且不超过既有deadline的预算采集诊断。只读取最多两个归属于该Job的Pod、每Pod最多两个
容器，读取后重验Pod和Job UID；只输出允许的退出状态、信号和Python错误类别。
原始日志、Pod规格和Secret内容不输出、不写入release state。普通诊断读取失败不替换
原失败；监管丢失或deadline异常仍失败关闭，清理失败也不能记为已完成。
Job身份比较允许API Server省略空的`args: []`，两种表示均不覆盖镜像默认参数；
非空参数的增加、删除或替换仍属于执行规格变化，必须在创建Job之前拒绝。
Job的`Complete`状态不代表数据库安全证明通过：探针可能捕获错误并返回`safe=false`。
`regional_release_store_probe`仅输出固定执行阶段和允许的错误类别，包装器仍验证原有
身份、时间、schema和阻塞记录条件；拒绝时只报告字段是否存在与已经评估的布尔条件，
不输出原始结果、身份值或异常文本，也不把未评估的条件当成已失败。

受管 `uninstall --cpu-cluster keep` 完成后的重装另走
`regional_release_retained_database`：已完成卸载记录、原 Aurora incarnation、站点身份
和新 installation ID 组成独立 handoff，首次使用还固定一个新的 namespace UID。
该路径保存 `retained_database_origin`，不能复制旧 namespace 的空库 origin，也不把保留库
宣称为空。每次继续都重新读取当前安全状态。仅经审阅的 v17 到 v18 前检可以校验完整
历史前缀和物理 heap/列而不执行旧存储函数，再由正常 schema Job ensure 到候选版本，
之后才允许业务 Pod；更旧、未来、缺失或漂移的 schema 不作通用兼容。

回滚先按组件进度恢复旧刷新器的完整对象，再由旧程序同步Secrets Manager的`AWSCURRENT`，
随后才能重启控制面。绝不恢复旧数据库密码，也不在verify中通过`set image`偷偷修复。
对象原本不存在时，只有CPU namespace锚点已验证才能记录absence并在回滚时删除候选对象。
缺少完整快照的旧事务不能声称已恢复被修改的刷新器；自动回滚在mutation前拒绝，
需使用经过验证的旧快照恢复。CronJob查询只有成功且空结果才代表未安装；
Forbidden、超时、错误JSON或身份不匹配均停止发布，不能解释成“跳过刷新”。

### 4.6 邮件通知模板契约

邮件路由由site声明：`adminEmail`、`emailSender`、`emailRecipients[]`和
`emailSubjectPrefix`分别表达运维联系人、SES identity、接收列表和环境前缀。ARN-only
入口允许独立传入sender和多个recipient；旧site未声明recipient列表时才兼容回退到
`adminEmail`。

SES适配器统一在外发Subject和正文中加入site、Region、AWS account和cluster，不要求
每个故障模板重复维护这些字段。各Builder只接受当前事件、Incident、Workflow和节点
参数；生产模板不得包含具体节点名或测试fixture。生成kubectl审批命令时必须使用显式
context保护。`support_case_draft`和`vendor-ticket-*`仅是内部升级记录，只有外部工单
适配器返回真实case ID后才能宣称AWS Support Case已创建。

模板正文或Subject协议变化必须提升对应`template_version`，并同步更新Builder测试、
preview测试和去重键。固定产品文案可以保留在版本化模板中；站点身份、节点、执行结果
和失败operation必须动态渲染。

新发布使用release manifest schema v4，同时覆盖运行制品和交付身份；
source-only构建及旧共享镜像release继续支持schema v3：

| 组件 | 允许的运行面 |
|---|---|
| `control_plane` wheel | CPU ingress/worker/spool、schema和凭据刷新 |
| `executor` wheel | GPU Executor、Watcher、Resource Collector、Reconciler |
| `node_runtime` wheel | GPU节点systemd Agent和Collector |
| `node_bundle` | 节点安装脚本、unit模板和精确的Node Runtime wheel |

此外必须记录渲染后CPU/GPU/Schema/NLB/Observability摘要、renderer输入、
`uv.lock`及哈希化requirements、Node template SHA，以及CPU runtime、Executor、
Node Installer、节点离线依赖、DCGM和ADOT的不可变image digest。只有CI生成的image-set descriptor才能把
Manifest标记为`deployable=true`；source-only artifact不能进入部署。
当前runtime基础层固定为UBI 9 Python 3.12 minimal的不可变digest；镜像构建阶段使用
root安装锁定依赖，最终运行阶段固定为UID 1001并清空基础镜像的S2I默认入口。
每个CPU/Executor镜像均只在`/opt/gpu-fault/runtime`隔离venv安装全部hash锁定依赖及
自己的component wheel；默认`PATH`/`VIRTUAL_ENV`指向此处，不启用system-site-packages，
不通过`.pth`借用基础Python的包。基础解释器、标准库和自带打包工具继续保留，但不安装
本方案的runtime依赖或项目wheel。CPU的`/opt/gpu-fault/control-plane`和Executor的
`/opt/gpu-fault/executor`只是各自runtime目录的软链接，兼容既有Manifest、探针及CLI，
不构成多套包环境。第三方依赖层位于组件参数和wheel之前，因此保持跨镜像缓存复用。
内容验证真实启动默认Python和兼容路径的`-I`解释器、加载console入口并执行`pip check`；
除模块digest外，还要求依赖、包搜索路径和入口解释器都属于同一venv。已知旧Dockerfile
摘要继续使用旧布局验证，不要求旧签名镜像凭空出现新目录，也不降低新镜像门禁。
两个镜像分别绑定自己的component wheel，
独立内容寻址、验证和复用；CPU镜像变化不再自动选择GPU rollout。Executor wheel变化仍须
执行必要的CPU compatibility pin stage/finalize，不能因为拆镜像就跳过协议窗口。
schema v3保留原共享镜像解释；schema v4缺少独立Executor身份必须失败，不能猜测为CPU镜像。
previous快照、resume、rollback和回滚后的管理site均保存或恢复各自镜像身份。
节点依赖目标通过`NodeDependencyTarget`显式区分候选和previous，并贯穿host预检、
每个wave和稳态Reconciler恢复；即使两个release的bundle SHA相同，也不能据此选择
候选依赖镜像。previous的cluster、bundle及v4依赖身份必须完整匹配，否则拒绝回滚。

三个 wheel 必须来自同一次构建，但不得互换安装。每个组件记录物理
`wheel_sha256`和行为`module_digest`：前者识别实际文件、驱动制品差异分类和严格
artifact pin，后者判断实现协议是否行为兼容并作为compatibility pin。即使代码
`module_digest`不变，只要许可证、打包元数据或其他wheel内容使`wheel_sha256`变化，
也不得分类为`NOOP`。Collector、Watcher、Installer和训练annotation仍必须使用同一
Runtime Profile版本。

`verify/status`必须检查每个运行Pod实际加载的component digest，不能抽样或只看
Deployment image/annotation。CPU和GPU context保持隔离，所有Deployment的Pod列表读取和
`kubectl exec`共享一个最多8路的线程池；单副本Deployment也能跨角色、跨集群并行。
所有Pod都完成后按Pod名排序输出。任一副本错误都会汇总后
fail closed，并发只优化等待时间，不减少覆盖面。

同一次`verify/status`或previous快照捕获中的Kubernetes JSON读取共享一个有界
read snapshot。健康检查会在每个CPU/GPU context各执行一次`get deployment -o json`，
把列表项填入线程安全缓存；后续按名称读取Deployment直接使用独立深拷贝，不再重复远程
调用。不同报告、不同发布阶段或任何mutation之后不得跨snapshot复用该缓存。

发布构建必须与调用者的shell `umask`无关。组件构建固定使用
`setuptools==84.0.0`、`SOURCE_DATE_EPOCH`和`umask 022`，复制到临时项目的Python、
packaged data与LICENSE统一为`0644`；Node bundle目录统一为`0755`，普通文件为
`0644`，脚本为`0755`。`artifact-check`必须分别在`umask 077`与`umask 002`
下得到相同release ID，不能因为ZIP external attributes变化制造一次虚假升级。

Agent和Regional Executor分别使用 artifact SHA、compatibility digest、protocol；
Agent另有config digest。它们共同使用required/compatible两阶段pin：

1. 稳态旧版本保持required，候选版本临时加入compatible；
2. GPU apply前检查候选Executor的artifact、compatibility和protocol已被
   required/compatible窗口接受；不接受时立即失败，不等待Deployment超时；
3. 滚动CPU和所有GPU集群，等待全部Agent精确收敛；
4. 候选提升为required并清空compatible；
5. 失败时恢复previous pin、对应组件wheel、bundle、Profile和节点artifact。

不得先切严格required pin再安装节点，也不得在Fleet未收敛时清空compatible窗口。
回滚到 **release manifest schema v1** 的单 wheel release 时（不是 PostgreSQL
schema v1），旧 Agent compatibility digest 等价于旧 artifact SHA；旧进程的环境
变量白名单不认识 component pin，因此
`filter_legacy_release_env.py`必须在apply前结构化移除这些env，不能依靠空字符串。

`RegionalRelease.noop` 默认仍校验并补齐 Watcher 的前置状态资源。
BOOT-023 发布历史验收显式传入 `allow_prerequisite_repair=False`，只做验证与历史追加；
缺失前置资源时必须失败，不能在声称仅改 history 的验收窗口补建 GPU ConfigMap/RBAC。
此参数不会跳过 release 验证，也不允许非 NOOP diff。

`NOOP/CONTROL_PLANE_ONLY/DATA_PLANE_COMPATIBLE/FULL`仍作为管理员摘要分类，实际执行
由组件DAG决定。纯Watcher或Collector Manifest变化只滚对应Deployment；Node bundle、
template或Agent pin变化进入Reconciler/Agent节点；schema、CPU、endpoint、observability
和DCGM分别独立。新增字段必须登记依赖节点，不能把`FULL`等同于全部重做。
CPU角色和GPU Executor/Watcher/Collector的单次rollout上限为5分钟；Node Installer
Job有active deadline和宿主`flock`，Reconciler只处理Fleet当前wave。pin、
协议或compatibility确定性不匹配必须在apply前失败，不能消耗完整rollout窗口。
Node Installer ConfigMap名称使用渲染后Job YAML摘要；节点annotation和Agent
heartbeat使用release提供的模板源摘要。两者不得复用同一个自引用变量。
previous另存旧Reconciler已信任的`GPU_FAULT_INSTALLER_TEMPLATE_CONTENT_SHA256`，
用它验证ConfigMap中实际`job.yaml`的完整字节以及旧依赖image/inventory/只读挂载；
不能对可变的线上Job重新计算摘要后将其授权为旧版。显式template覆盖必须同时提供该
可信内容pin，host预检验证实际选中的模板；受管入口清除调用者继承的覆盖变量。

每个Fleet wave不重新部署Reconciler Deployment：release先等待Reconciler
rollout健康，再校验容器env中的bundle/template identity仍等于本次暂停时记录的
identity，然后merge patch `GPU_FAULT_INSTALLER_WAVE_CONFIG_MAP`指向的
`gpu-fault-node-installer-wave`（`allowed-nodes`、`max-unavailable`、`generation`），
并回读确认patch已生效。Reconciler每轮reconcile重新读取该ConfigMap，因此allowed-node
集合是热更新的、不属于installer identity。identity校验发生在patch之前，Installer Job的
cancel/retry与原路径一致。Reconciler使用`strategy: Recreate`，逐波次重建会让该集群在
波次之间没有installer控制器；只有当运行中的Reconciler没有wave ConfigMap env（早于该
契约部署）时才回退到逐波次重新部署。

## 5. Kubernetes生命周期契约

运行型Deployment、DaemonSet和CronJob必须在顶层声明：

| annotation | 合法值与作用 |
|---|---|
| `gpu-fault.io/cleanup-phase` | CPU：`ingress/consumer/auxiliary`；GPU：`producer/executor` |
| `gpu-fault.io/cleanup-order` | 同一phase内的非负稳定停机顺序 |
| `gpu-fault.io/cleanup-action` | `delete/namespace/reset`，缺省为`delete` |
| `gpu-fault.io/deploy-mode` | GPU Deployment可用`regional_rollout/regional_reconciler` |

ServiceAccount、RBAC、PDB和普通Service通常推导为`support/delete`；CPU NLB Service使用
`nlb/reset`；ConfigMap、Secret和Namespace由namespace生命周期覆盖。不要为了让生成器
通过而给资源选择错误phase。

资源kind、name和scope由生成器从源YAML推导。更新入口只有：

```bash
make PYTHON=.venv/bin/python deployment-contracts-update
```

它渲染CPU三角色、生成构建期候选`cleanup-inventory.json`、验证allowlist并运行契约
测试。发布入口再按`kubectl get`的实际结果刷新CPU/GPU
`gpu-fault-installed-resources`。资源退役必须在受信源inventory中保留显式retired条目，
直到live对象真正删除；不能仅删除Manifest后，让可变ConfigMap中的历史行继续授权删除。
条目的`provenance_sha256`只用于内容完整性诊断，不是签名或所有权证明。未知旧行即使
自摘要正确、或对象已不存在，也会在任何注册表改写前停止，保留原记录，要求先审阅并在
受信源清单中登记退役。资源身份包含scope、kind、namespace和name；历史namespace中的
同名对象不能被当前namespace条目覆盖。

提交前运行：

```bash
make PYTHON=.venv/bin/python deployment-contracts-check
```

cleanup preflight还会扫描历史namespace和cluster-scoped RBAC中的未登记
`gpu-fault-*`对象；发现out-of-band资源必须fail closed并先分类。
发现和同步通过同一受监督命令入口执行，资源读取只接受明确absence，不把工具、权限或
网络错误当作不存在。按`scope + kind + namespace`分组读取，逐项验证kind、namespace和
name，不把同名对象跨scope或namespace合并。
`collect_installed_resource_registry.py`还在`gpu.by_context[context]`保存每个原始GPU
context的完整同步文档，其中`.resources`只列该集群实际安装的受信资源。context必须
非空且唯一，校验发生在CPU注册表写入之前。顶层`gpu.resources`是汇总视图，不证明
其中每项都属于每个GPU集群；清理及残留验证按对应context的文档执行。多集群live清单
缺少所选context时拒绝清理，不能回退到并集猜测归属。
部署工具只为标准`aws eks get-token`建立进程私有`0600`临时kubeconfig缓存：返回值必须
带明确、带时区的`expirationTimestamp`才跨请求复用，提前60秒刷新；没有有效期则每次请求
重新取token，刷新失败不得继续使用旧token。其他exec插件，以及需要`provideClusterInfo`
或不满足该标准路径的exec选项，继续交由原生kubectl执行，保留
`KUBERNETES_EXEC_INFO`、交互模式和证书凭据协议，不由部署工具手工缓存。
认证诊断不回显插件输出，私有配置在完成或失败后清理。此优化不改变受信kubeconfig和
release验签边界，也不提供跨命令认证缓存。

前置刷新和数据库proof的一次性CPU Job由
`src/gpu_fault_release/regional_release_probe_job.py`管理。创建前读取受管Aurora刷新
CronJob的实际UID，并设置唯一`ownerReferences`，固定`controller=false`和
`blockOwnerDeletion=false`：该引用把Job接入已注册父资源的垃圾回收链，不将proof交给
CronJob作为定时调度或active Job管理。父对象缺失或正在删除时拒绝创建。
动态身份及`owner_uid`先写入release journal的`jobs`，状态从`PLANNED`到`RUNNING`再到
`REMOVED`。server-side dry-run和创建后回读都核对完整Job spec，仅接受明确列出的API
默认值，并校验name、namespace、run/spec标记和owner引用。run/spec摘要、Job UID及
journal绑定的父UID共同约束完成证明和删除。创建ACK丢失时也按同一身份回读，不能按名字
盲删、信任被替换的Job，或删除owner已被改写的对象。
本地命令监督仍可信时，成功、失败和中断均尝试有界foreground、UID-precondition清理
并确认消失；失去全部完成证明时禁止再发清理命令。失败保留清理记录，下一次先完成清理
才创建新Job。父资源垃圾回收、active deadline和300秒TTL是兜底，不代替显式清理及
`REMOVED`证明。数据库probe只输出状态、计数和身份摘要，驱动异常只输出类型，不记录DSN。
常驻刷新CronJob、ServiceAccount和RBAC仍由既有installation resource registry管理；
临时Job通过该已注册父对象覆盖资源生命周期，不引入第二份手工资源清单。
`deploy/control-plane/tools/collect_installed_resource_registry.py`的发现范围包含Job：
仅当唯一owner引用的apiVersion、CronJob名称、UID及Job namespace与当前已注册父对象
完全匹配时，才视为已覆盖子资源。孤儿、父对象同名重建后的旧UID、未登记父对象、
跨namespace或多owner的方案Job均报告为`unregistered_resources`，由cleanup preflight
fail closed并要求先分类，不自动认领或盲删。既有名称/namespace范围不扩大，客户
namespace中的Job不被接管。
Job模板校验不等同于对后续Pod admission改写的独立证明，CPU namespace的Pod admission
策略仍须受信。

当前区域 GPU rollout inventory 必须保持：

```text
completion-watcher.yaml
kubernetes-node-resource-collector.yaml
cluster-action-executor.yaml
```

`node-installer-reconciler.yaml` 单独标记为 `regional_reconciler`。若要重新启用任何
DaemonSet collector，必须先移除同功能 systemd producer、定义迁移/回滚和双写检测，
不能仅把历史 YAML 加回 inventory。

`completion-watcher.yaml` 还声明
两个 ConfigMap：`gpu-fault-completion-watcher-outbox` 只放 write-ahead 日志，
`gpu-fault-completion-watcher-outbox-active` 放常态 attempt 状态。failure/terminal 事件
必须先写入前者，再发送控制面并在确认后删除；普通`workload-observations`健康时直接发送，
失败时才按`cluster_id + attempt_id` latest-wins写入同一 WAL 并在下一轮重放，避免短暂控制面
写入失败把CPU端Observation永久留在`RUNNING`。`-active` 对象里的`active-attempts.json`
只在attempt结构首次出现或变化时保存活跃Observation，且每个 Pod 只存 spec 之外的归因身份
（uid/rank/node 加 `gpu_uuids`、`container_id`、`cgroup_path`、`host_pid`，约 833 B/Pod，
900 KB 上限约容纳 1080 个受管 Pod，超出的 attempt 只丢重启记忆、不影响投递）；Watcher
重启后从活 Pod 重建其余字段，Pod已消失时按cleanup timeout发布`STOPPED`。拆分的理由是
ConfigMap 的 1 MiB 上限：常态状态与 WAL 同住一个对象时，上千个 Pod 的观测会把终态事件
的写入挤成 `CompletionOutboxFull`。升级到本版本时 Watcher 首次读取会把旧对象里的
`attempt:*` 键一次性迁到 `-active`（先写新对象再删旧键，删失败由后续写入补偿重试，
按 `observed_at` 较新者合并），迁移后的第一轮会按 attempt 各重写一次 `-active`。迁移单向：回滚到上一版 watcher 后旧对象已无 attempt 状态，重启记忆只能从活 Pod 重建。Role 的
`resourceNames` 必须同时列出两个对象且不授 `create`（RBAC 不能按名字限定 create），
对象由发布器创建；`-active` 读到 403/404 时 Watcher 降级运行（无重启记忆），60 s 重试一次、
ERROR 每小时最多一条，并把 `gpu_fault_completion_active_state_unavailable` 置 1。发布器
发现任一 ConfigMap 已存在时必须从rollout Manifest中省略该文档，禁止用默认空数据覆盖
outbox/attempt state。不得改回 Pod 内存或
`emptyDir`。每个 GPU cluster
的 `site.yaml` 必须提供 `agentEndpointAllowedCidrs`。该字段进入对应
`RegionalClusterRegistration`，heartbeat 按认证 `cluster_id` 选择网段，不合并为区域
allowlist。节点安装器默认自动生成本地 TLS cert/key，广告 HTTPS，并在签名 heartbeat
中携带证书供 Executor pin。

Watcher产生terminal event时，发布的Observation必须同时映射为终态：
`TIMED_OUT/FAILED -> FAILED`、`SUCCEEDED -> SUCCEEDED`、`STOPPED -> STOPPED`，
且未知仍运行rank不得保留。Store保存terminal event时在同一attempt事务中终态化
Observation；之后到达的`PENDING/RUNNING`单条或批量Observation均拒绝覆盖。周期cleanup
只选择仍缺失或仍active的矛盾记录，因此不会被更早、已经一致的terminal event按limit
长期饿死。

## 6. 节点systemd生命周期

新增unit时：

1. 模板放入`deploy/systemd/gpu-fault-*.service|timer`；
2. `install-gpu-fault-collector.sh`显式复制或渲染模板；
3. 安装完成后由脚本扫描实际unit并写入`/opt/gpu-fault/installed-units.txt`；
4. Agent在启动或清单变化时上报完整列表和SHA-256，稳定心跳只上报digest；
5. 卸载后确认unit、`/opt/gpu-fault`、`/etc/gpu-fault`和`/var/lib/gpu-fault`无残留。

Node Runtime 使用内容寻址 A/B 槽位：

- 候选先安装并校验到 `/opt/gpu-fault/releases/<artifact-sha>-<dependency-sha>/venv`；
- systemd 只执行 `/opt/gpu-fault/current/venv/bin/*`，`current` 通过原子软链接切换；
- 首次从旧版迁移时保留真实的 `/opt/gpu-fault/venv`，供旧 installer rollback 使用；
- 切换后服务启动或验证失败时恢复原 `current`、配置、unit enable/active 状态；
- 旧签名槽位保留到 rollback window 结束，不在发布路径中提前删除。

`runtime-slot.sh`中的依赖身份绑定`node-runtime.lock`字节、Python实现/版本、ABI、
平台、libc和解释器二进制摘要。独立依赖venv保存在
`/opt/gpu-fault/dependencies/<dependency-sha>/venv`，不同应用wheel的槽位通过受检`.pth`
引用同一不可变依赖层；只更新wheel不再重复安装整个lock。lock或解释器变化仍创建新层。
`runtime_integrity.py`由宿主Python以`-I -S`执行，先逐文件验证RECORD、版本闭包、额外文件、
字节码与源文件一致性、解释器及层引用，再允许启动候选Python；不会先执行未验证的`.pth`。
RECORD文本摘要仅作为附加封印，不代替实际文件摘要。已发布依赖层损坏时拒绝复用，
不得原地重建仍可能被活动/回滚槽引用的层；只有带`.building`且未发布的中断构建可重建。
缺少新身份的旧槽位不当作候选复用，但仍保留供旧release回滚。活动槽位校验失败时停止，
禁止原地删除或覆盖。
候选只读host预检还通过候选bundle中的受信helper逐文件检查当前回滚槽，包括旧依赖层、
RECORD封印、依赖闭包和入口模块；真正安装前再校验一次，均发生在停止旧服务之前。
旧槽按自己的lock和解释器身份校验，不用候选lock判断旧依赖；legacy独立venv和旧的
artifact-only槽仍支持实际文件与闭包校验。合法Python软链接路径按同一解释器链识别，
仍要求实际二进制、版本与隔离配置一致。

候选节点环境在 RECORD、依赖闭包和 `pip check` 通过后、激活前完整验证 Collector
插件；候选 Executor 镜像在无网络、只读容器中运行安装环境的
`python -I -B -m gpu_fault.collectors_cli validate-plugins`。普通 CLI 的按需加载
不能替代这一步。旧节点槽位没有 Collector registry 接口时，仅在未安装任何
`gpu_fault.collectors` 插件的情况下兼容，不因新 CLI 子命令缺失而破坏旧版本回滚。
镜像检查先创建具备独立归属标签的容器，核对返回的完整 CID 与私有 CID 文件，再启动
检查命令；结束、超时和主线程中断均按完整身份清理容器及匿名卷，并确认容器已不存在。
创建结果或清理结果未知时门禁失败，保留私有归属记录供调和；名称或标签相同不能替代
原容器身份，也不能把这份记录当作清理成功证明。

节点候选预检先渲染一份共同 Job 模板，再由 `regional_node_batch` 单次读取私有节点快照
和模板；`node_installer_rendering` 与运行中的 Reconciler 共用节点绑定逻辑，逐对象校验
name、UID、InternalIP、机型及节点级 Secret key。全部 Job 完成 server-side dry-run 后，
才以最多 8 路启动只读 host 预检；失败停止提交新节点并清理已创建的预检 Job。
dry-run通过stdin发送有界JSON List，每批最多4个节点、8个Job和1MiB，命令预算60秒；
admission独立最多8批并行并共享全部署kubectl配额；Host执行窗口仍单独限制为最多8节点。
分批减少CLI启动和重复发现，不减少逐对象admission检查，
任何一批失败均不得开始host Job，已提交批次仍须收尾。
创建请求丢失ACK时同样读取run-bound Job并确认节点/制品身份，以UID precondition删除，
不删除被替换的对象；重复Node UID在渲染前拒绝。失败日志限量读取并脱敏。
不再为每个节点启动 shell 渲染进程或重新解析全量节点快照。绑定器、机型表与 DCGM
采样周期同时进入 Node template 身份，不能改变绑定逻辑却沿用旧模板 pin。

schema v4的节点依赖从独立OCI镜像分发，不进入ConfigMap。`node_wheelhouse`在Linux
Python 3.12构建机上按`node-runtime.lock`和`node-tools.lock`下载hash固定的Linux amd64
wheel，后者包含py-spy；inventory绑定平台、lock和每个文件的摘要/大小，其摘要进入签名
delivery。非root initContainer只把wheelhouse复制到有大小上限的emptyDir，不挂载host或
Secret；Installer通过只读挂载在chroot内使用它。只读host预检和真正安装前均核对
inventory、每个文件、宿主平台及候选bundle中的lock，再以`--no-index --require-hashes`
安装。py-spy保留独立二进制摘要检查。首次部署仍需拉取OCI并安装本地wheel，但不再逐节点
访问PyPI；后续按原不可变依赖层复用。回滚使用previous的依赖身份，不能把候选wheelhouse
配给旧bundle。原schema v3回滚路径保持兼容，不伪造一个旧版本从未声明的离线依赖镜像。

EFA驱动修复保持默认启用。Installer Job的
`GPU_FAULT_ENABLE_NODE_EFA_DRIVER_REMEDIATION`只接受`true`或`false`；显式`false`
传递`--disable-efa-driver-remediation`并移除`REMEDIATE_EFA_DRIVER`能力，不因省略
enable参数而回落到安装器默认值。collector-only安装仍不得启动Node Agent。
节点动作ledger默认保留`2592000`秒（30天），帮助文本与实际默认值一致。


### 6.1 Node Action key准备与同步

`deploy/node/provision-node-action-keys.sh`调用同目录的
`provision_node_action_keys.py`，在受信deploy-host Python环境执行，不给Node Runtime
增加管理员依赖。Node bundle必须同时携带wrapper和helper；`TaskInputSpec`将两者及
`src/gpu_fault/admin/node_key_proof.py`、目标集群绑定到`node_keys:*`任务摘要，helper也
进入release的`node_template_inputs`身份，不能只更新脚本而沿用旧checkpoint或template pin。

Secret读取使用受监督的私有JSON通道，区分存在、确认不存在和读取失败；只有成功且空的
`--ignore-not-found`结果允许创建。实际值只在私有内存/stdio中处理，身份校验包含
Secret类型、namespace/name、UID及resourceVersion。对base64解码后的原始字节计算
SHA-256，不先strip；原始JSON、key和fleet master不得进入日志或普通artifact。
GPU key集合必须精确等于当前已验证的目标节点，CPU key map则是全站并集。CPU以
UID/resourceVersion保护的CAS合并目标条目，保留无关key和metadata；GPU已有合法随机
轮换值原样复用，只为缺失节点派生v2 key。读取失败、同名Secret重建或未知CPU key冲突
都不能授权覆盖；相同key字节本身也不证明NodeName属于该集群。

GPU Secret上的`gpu-fault.io/node-action-key-rotation`是部分轮换的续跑标记，不是成员
归属证明，也不是新资源。标记绑定cluster、Node UID、CPU Secret作用域/UID及轮换前后
字节摘要；任意标记存在都必须进入ensure，即使CPU/GPU摘要已相同。完成前再次验证当前
Node UID集合、CPU镜像值及GPU身份，再CAS移除标记，不能在CPU写入失败后重新生成随机key。
每个CAS阶段最多3次，单命令20秒、Kubernetes请求15秒、helper总窗口300秒，仍受父级
deadline限制。join传入的新鲜NodeName到UID绑定及CPU补偿摘要守卫见§8.1。

### 6.2 Node Key Custody

custody是对上述受信交付路径的前瞻性取证，不是第二套key同步器。管理员流程见
[日常运维§6.2](管理员日常运维.md#62-node-key-custody)，完整签名schema和证明边界见
[Node Key Custody证据契约](components/node-key-custody-evidence.md)。

公开入口为`gpu-fault-admin node-key-custody configure`，显式要求`--state-dir`、`--file`
和`--trust-sha256`。`src/gpu_fault/admin/cli.py`解析参数，
`src/gpu_fault/admin/node_key_custody_admin_config.py::configure_admin_custody`
持站点mutation锁验证并写入私有`node-key-custody/registration.json`。选择文件必须为
受控`0600`文件；`AdminCustodySelection`要求非空的完整GPU EKS ARN映射，值是`null`
或request路径，`trust`及request路径相对选择文件解析，`allow_staging`默认`false`。
没有环境变量opt-in；未登记时保持原同步行为，登记目录已存在但注册损坏/缺失时必须
fail closed，不能回退到legacy。

登记固定选择、request、authorization、trust及其公钥、Manifest、前驱链的内容身份。
加载和消费时重新计算并比对；同一路径替换内容也须显式重新登记。外部批准的trust
SHA-256独立于证据提供，approval、provisioner、witness的P-256公钥身份彼此不同，
也不得复用release签名key。provisioner不能取得approval签名权限；所有取证签名权限
均留在各自受控部署/见证角色，不能下发GPU节点或运行组件。
`configure`本身不生成授权、不调用KMS Sign、不创建namespace、不轮换Secret。

| 阶段 | 实际入口与证据 | 必须保持的边界 |
|---|---|---|
| 显式准备 | `node_key_custody_admin.provision_admin_custody`在目标request为`null`时，经当前绑定生成`CustodyPreparation` | 仅正常deploy/join的执行路径可写preparation；`authorization=false`，不能冒充独立批准 |
| 独立授权后续跑 | 再次`configure`登记签名request，重跑同一条deploy/join | 当前release、source、cluster/namespace/Node UID、master来源及request快照全部匹配后才准入真实helper |
| 受信交付 | `Started`先于key写入；实际CAS和回读成功后签署`Completed` | genesis要求目标key此前不存在；rotation要求已激活前驱且只推进一个节点，不能从当前相同key补历史 |
| 独立运行见证 | 已部署的HTTPS Agent接收fresh challenge，独立witness签署`Activated` | 初始activation只是前提，不是完整AUTH-015轮换PASS；Secret完成态不代替endpoint验证 |

`src/gpu_fault/admin/node_key_custody_admin.py::write_preparation`输出
`<state-dir>/node-key-custody/preparations/<statement-sha256>.json`，绑定已验签schema v4
候选release、site/Region及CPU/GPU EKS身份、两侧cluster/namespace UID、完整NodeName到
UID集合、CPU master Secret UID/key/字节摘要，以及producer/witness源码身份。
资源准备和构建仍按正常授权执行；准备暂停只保证尚未写目标key，不声称整个deploy只读。
独立authorization绑定这些事实、用途、前驱及最长24小时窗口，真实写入仍逐阶段核验窗口。

`src/gpu_fault/admin/bootstrap_services.py::provision_node_action_keys`仅在收到
`custody_context`时进入custody分支，并先核对context与实际调用参数；未选中的目标保留
原同步实现。受检`AdminNodeKeyContext`由bootstrap和join构造，不从CLI环境猜测。
helper仍是`deploy/node/provision-node-action-keys.sh`及其Python实现，管理员调用增加
`--custody-request`、`--custody-trust-sha256`和`--custody-input-sha256`。
最后一项固定子进程交接前后的全部输入内容，是完整性守卫而不是签名授权。
敏感参数只传受控文件/配置引用，原始master和key不得进入argv、普通artifact或日志，
GPU仍只接收节点级key。
完成receipt还固定CPU无关key集合的摘要；内部串行不等于跨部署机锁，必须协调其他
writer的静默窗口。CAS保留无关值并不能让并发摘要变化自动成为本次取证的一部分。

`src/gpu_fault/admin/node_key_custody_admin_probe.py::verify_completed_custody`
是签名receipt probe；它验证完整链和当前release/UID绑定，私有读取CPU/GPU Secret，
比对实际字节摘要、Secret UID和无pending rotation，不以键名齐全放行。
`provision_admin_custody(..., probe_only=True)`与公开preflight都不能调用KMS Sign、
创建preparation或执行helper；缺证据要求准备/调和。有效完成链可在外层bootstrap
checkpoint丢失后重新满足probe，旧shape-only checkpoint不能跳过custody。
`Completed.runtime_activation_proved=false`，管理员任务结果也明确返回
`runtime_activation=NOT_PROVED`，不能把配置或交付成功升级为运行时证明。

同release的后继rotation仍须经过
`node_key_custody_activation.CustodyActivation`。它在key写入之前记录绑定快照、
执行安全门并drain指定Agent，接管唯一节点的Installer wave；之后才交付key、
刷新Executor签名、安装指定节点、刷新CPU验证进程、观察新鲜Agent并恢复wave。
意图先于每次mutation落盘，固定期限不超过独立授权expiry与1800秒预算；
实际key writer携带已落盘activation state的路径与摘要，在每次Secret提交前复验
同一截止时间、单调时钟和受管wave UID/完整data。FENCED之后的续跑、CPU/GPU滚动
与节点annotation提交也重新校验wave，提前恢复为原开放wave不能充当归属证明。
只有已开始的最后UNFENCED阶段可以确认自身丢失的ACK，不重开前面的mutation。
中断只沿原journal前进或保持人工调和，不由NOOP跳过，不重新生成key或自动写回旧key。
rotation的只读probe还检查该激活状态，Secret completion本身不足。
完成操作状态为`DEPLOYED_NOT_WITNESSED`，不改变上述签名completion的证据含义；
独立witness仍须验证真实Agent的新key、旧key和sibling拒绝。新增的节点activation
annotation由既有Installer annotation清理清单登记，不新增另一份资源事实源。

存在`Started`而缺少有效完成链、未知Secret创建ACK、读取失败、source替换或UID漂移时，
保留意图并抛出`CustodyReconciliationRequired`；相同当前字节和legacy rotation标记均
不能授权重开writer或制造完成receipt。`cluster_join`分别记录
`CUSTODY_AWAITING_AUTHORIZATION`/`CUSTODY_BLOCKED`并保留namespace和输入，不执行普通
失败的自动补偿。未开始request可显式重新登记；已开始request只能由新独立授权的
rotation接续，其已签完成和activated前驱必须匹配原登记交易。登记不能移除集群、
撤换trust pin或隐式降级；v1不提供未知writer取消、回溯取证或跨release/身份自动迁移。

独立witness使用release绑定的Agent、fresh heartbeat、TLS证书和实际协议结果，证明
新key认证、旧key/兄弟key在命令和结果查询两条路径均被拒绝，且兄弟runtime身份不变。
challenge采用不可准入的时间窗和禁止的`FREEZE_EVIDENCE`，验证命令始终不存在，
不派发物理动作、不轮换Secret、不建host probe、不重启或restore。
它仍请求独立KMS签名并写公开receipt，不能绕过原live runner的计划、目标、源码、
连接身份及维护窗口批准。
初次witness即使签出`Activated`，完整`GF-REGIONAL-AUTH-015`仍为FAIL，必须部署并
见证已授权的单节点轮换；详见[AUTH-015 witness](components/node-key-custody-evidence.md#auth-015-witness)。
独立退役key文件只供负向挑战，留在可信部署机的受控`0600`路径，不进入receipt目录、
release或GPU。签名不证明未观察的主机行为；hermetic测试不构成LIVE安装/KMS IAM证据。

custody模块属于deploy-host import closure，并进入交付的Node template/source身份，
不加入Control Plane、Executor或Node Runtime wheel。相关源变更必须重新验证显式
登记、unsigned准备、独立授权续跑、签名probe、旧checkpoint拒绝、初始activation与
完整rotation的不同verdict，以及未登记站点保持原行为。

## 7. AWS资源生命周期

正常首次部署由ARN入口创建Aurora、AMP、SNS、runtime/cache ECR、PKI、IAM和方案
安全组，并把每项资源写入bootstrap state和installation registry。ARN入口是本方案
唯一的站点AWS基础设施writer。

ARN bootstrap为mutable BuildKit cache ECR设置固定生命周期策略：只删除超过7天的
untagged cache artifact，保留当前带tag的cache manifest。缺失策略会幂等补齐；已有
策略与事实源不一致时fail closed，不在线覆盖。策略摘要和保留天数写入bootstrap state，
runtime ECR不应用该清理策略。

SNS email subscription使用独立持久状态机。Topic带随机generation tag，因此同名Topic
删除重建后即使ARN不变也会失效旧pending checkpoint。调用`Subscribe`前先写
`REQUESTING`，成功后保存`--return-subscription-arn`返回的真实ARN和48小时确认窗口；
同generation在确认或窗口过期前不得重复调用。`list-subscriptions-by-topic`发现一条
confirmed时直接复用；同邮箱多条confirmed，或confirmed与pending并存时fail closed，
由管理员明确保留一条后再重跑。email subscription作为`DETACH`资源进入installation
registry；普通deploy和rollback不得删除Topic或subscription。

Kubernetes cleanup registry不覆盖Aurora、NLB、ACM、Route53、SNS、AMP、IAM、SG、
subnet或其他AWS资源。新增资源必须创建`InstallationResource`记录，至少包含：

- 稳定`resource_key`和ARN/ID；
- Region和账号；
- `CREATED/EXTERNAL` ownership；
- `DELETE/DETACH/PRESERVE` delete policy；
- 依赖的其他`resource_key`；
- 非敏感attributes和状态。

`site_id + resource_key` 是稳定键；provider/type/ID/ARN/Region/account/ownership/
delete policy/dependencies 属于不可变身份。attributes 禁止 secret/token/password/
credential 类 key，注册表不是凭据存储。

注册表API兼容访问由`src/gpu_fault/admin/resource_registry_scripts.py`提供自包含脚本，
仅在明确的机器返回码及stdout标记匹配时识别旧API或可重试503；任意stderr中的404/503
字样不允许触发回退。快照通过私有stdin发送，不进入命令参数。旧版控制面的直接Aurora
回填同样按不可变身份做原子冲突判断，任一冲突回滚整批，不允许无条件upsert改写资源ID或
删除策略。连接优先使用当前挂载的`GPU_FAULT_STORE_URL_FILE`，配置了文件但无法读取时
拒绝回退启动时旧密码；未使用该挂载的旧版本才沿用原环境引用。连接、语句、锁和外层命令
均有时间上限，数据库错误只输出类别。该兼容路径只写注册记录，不执行DDL。
成功退出本身不是同步证明：API返回的完整资源集合必须与本次快照逐项一致，直接SQL
回填必须返回精确行数；缺失、额外或不匹配的确认均失败。卸载根据审批模式计算的有效
删除策略只存在于执行计划和审计，不回写原资源的不可变ownership、delete policy或依赖；
注册表更新只推进对应状态，不能借历史`REUSED/PRESERVE`兼容处理放宽身份约束。
本地快照的文件摘要和`source_sha256`只能检测内容损坏，删除前仍须绑定本站点身份并验证
真实资源归属；新的bootstrap记录还核对`initial_deploy_target`中的CPU身份。

部署或接管同站点遗留资源后，通过`admin_resource_registry.py`同步到Aurora
`gpu_fault_objects(kind=installation_resource)`。管理员不在`site.yaml`中手写这些
字段，也不得新增第二份AWS inventory文件。

新增AWS基础资源必须接入ARN bootstrap并输出同一site契约。所有应用拥有的AWS资源必须
同时接入：

1. ARN发现、确定性名称、site ownership tag和`site.yaml`生成；
2. ownership标签验证和外部同名冲突fail-closed；
3. `preflight/status/verify`；
4. `remove-cluster`（若为集群专属）；
5. `uninstall`依赖排序、真实删除查询和最终残留验证；
6. registry snapshot、SHA-256和Aurora最后删除阶段。

统一卸载先导出Aurora注册表，再把条目标记为`DELETE_PENDING`。Kubernetes、非Aurora
资源和CPU保留或删除全部验证完成后，先保存pre-Aurora清理证明并进入
`READY_TO_DELETE_AURORA`，删除模式才允许按实际reader、writer、cluster和依赖的顺序
删除Aurora；不能把数据库删除与前序验证并行。最终
`installation-resources-final.json`必须只含`DELETED/DETACHED/PRESERVED`，且
`delete_policy_residuals=0`。

至少覆盖：

```text
tests/admin/test_admin_resource_registry.py
tests/admin/test_admin_cluster_removal.py
tests/admin/test_admin_uninstall.py
```

`cleanup_state.py`仍可用于break-glass阶段状态，但不能替代Aurora
`installation_resource`注册表。

## 8. 管理员接口完成标准

新增功能不能只提供手工`kubectl`、`aws`或`curl`片段。完成标准包括：

- 正常发布从`site.yaml`进入区域orchestrator；
- `preflight`在修改环境前检查输入、身份和依赖；
- `deploy`幂等并具有持久状态、恢复或回滚边界；
- `verify`独立只读验证真实功能，不只检查Pod Ready；
- `status`输出结构化健康、release/Profile/pin和失败原因；
- 集群专属资源进入`remove-cluster`，全站资源进入`uninstall`；
- 危险操作具有dry-run、审批、成功标准、回滚和证据；
- 新凭据具有创建、轮换、吊销、最小权限和日志脱敏定义；
- 管理员文档只描述决策和正式入口，内部细节保留在开发者文档。

新增GPU集群的正式入口是：

```bash
gpu-fault-admin join-cluster \
  --state-dir /secure/gpu-fault \
  --gpu-cluster-arn <gpu-arn>
```

首次四参数deploy收到多个GPU ARN时，先用第一个集群建立并验证基线，其余集群进入有界
batch join：共享候选preflight和verify。接入与共享release升级使用同一
`upgradeMaxParallelClusters`（默认1，上限8）；只读接入准备最多4路。站点级Installer
预算固定为64节点，每集群wave上限进一步取`floor(64 / 集群并行度)`，并与规模、
显式`upgradeMaxUnavailable`和故障域限制取最小值；首波仍为1。
每个集群仍有独立state、`PENDING -> ACTIVE`事务和补偿；正式site、
release state、bootstrap state及Aurora资源注册表在membership锁内逐集群增量提交。
同一站点的多个`join-cluster` CLI由全事务文件锁串行化，不会把不同进程各自的并行度相加
后突破全局预算。
以上batch并行适用于未登记custody的默认路径；已登记站点由`cluster_batch_join`逐个
调用受锁single join，遇到custody准备或阻塞即停止，不继续后续目标，见§6.2。
首次目标GPU身份和顺序持久化到bootstrap checkpoint；失败重跑时，当前成员允许是原目标
的单调子集，bootstrap只reconcile已纳管成员，缺失成员继续走独立join。只有原目标全部
已纳管，或缺失目标有精确EKS/HyperPod/CPU身份且与当前site/release匹配的`COMPLETED`
移除journal，才算原承诺完成；部分site或仅同名`removed_clusters`行不能释放承诺。
完成后允许原成员集合及其扩展，新待接入目标形成下一次checkpoint；省略仍受管的
成员仍须先执行`remove-cluster`。畸形checkpoint、身份漂移或`COMPLETE`却缺失site
均拒绝，不通过删除旧记录重新开始。
checkpoint还绑定目标、release Manifest、AdminConfig和bootstrap实现摘要。状态schema v3为每个任务保存
独立输入摘要，只使输入或实现来源变化的任务失效；Pod Identity Agent、Load Balancer
Controller、Control Plane/Executor IAM role、通知和监控资源即使checkpoint命中也再次
执行只读live probe。probe确认addon、IAM trust/policy/tag、Pod Identity association、
Helm values、SES Secret、AMP/SNS及订阅均一致时直接复用checkpoint；只有发现漂移
才进入ensure并允许mutation，避免健康站点每次deploy重复apply/update/Subscribe。
AWS基础资源、集群接入和平台前置任务在同一张依赖图中调度（`bootstrap_tasks.TaskSpec`、
`bootstrap_access.ClusterAccessPlan`、`run_parallel`，单个8线程池）。任务的ensure、
probe、重验策略、依赖和失败策略保存在同一个TaskSpec；重复名称、未知登记和循环依赖
在执行前拒绝。只向线程池提交当前有空位且依赖就绪的任务，不排入无界待执行队列。
输入身份由`bootstrap_task_inputs.TaskInputSpec`统一定义，TaskSpec必须声明fingerprint
或明确的每次重验原因；checkpoint从同一目录计算摘要，不再维护第二份任务名映射。
输入尚未绑定的图不得复用checkpoint。渲染、预检、registry、制品和凭据刷新接口使用明确
的RegionalRelease类型；外部JSON仍在边界验证，不能用动态方法缺失跳过漂移检查。
旧Aurora配置先迁移到规范化AdminConfig，再绑定早期输入和启动构建；依赖图消费同一次
解析的容量值，避免迁移改变`desired.json`后前后两次输入身份冲突。同进程刚完成的任务
也必须重新核对摘要，不能以“本次已经执行”豁免失效。
CPU kubeconfig/namespace/base Secret完成后立即允许`aurora`创建cluster及实例，不再
等待GPU kubeconfig/namespace或Pod Identity；GPU共享kubeconfig的写入仍然串行。
`nlb_network`、`pki`、monitoring资源及独立IAM role可与这些接入链重叠。CPU role及LBC
等待CPU接入和Pod Identity；ADOT writer role仍等待对应Executor OIDC和AMP workspace。
`monitoring_install`保留原checkpoint名称，但只准备site级amp-writer role和Pod Identity，
等待CPU接入、Pod Identity与`monitoring_resources`，不再等`release`。监控资源任务还通过
共享`amp-sns-publish-policy.json`收敛SNS的AMP发布权限；保持其他statement不变，验证
账号、workspace、topic、site tag与generation，已一致时不写入，观察到并发变化则停止。
`grafana_install`只等
`monitoring_resources`，不等待镜像构建或ADOT安装；`aurora` 任务通过
`ensure_serverless_instances(wait=False)` 创建实例，仍受实际 primary 和 cluster 就绪屏障约束：
先创建 writer，确认实际 primary 与 cluster 可用后才创建 reader。`wait=False` 只把最后的
双实例就绪核验交给 `aurora_ready`，不会跳过创建 replica 的前置条件。
新增副本前读取实际primary，续跑和故障切换后不按实例名称猜角色。
首次实例仍为`creating`时，允许等待其成员记录从未指定writer转为唯一primary；
实例可用后的成员信息同步最多再读6次、间隔5秒，且受父deadline约束。
已经可用却没有primary、未知成员、多个primary或等待后身份变化仍拒绝创建reader。
这是[AWS添加Aurora Replica的前置条件](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/aurora-replicas-adding.html)，
不能用并行waiter绕过。RDS实例和cluster waiter显式使用2100秒预算，覆盖默认30秒间隔、
60次检查及API开销，不再落入通用900秒上限。`bootstrap_aurora`读取本地botocore waiter
模型的acceptor、间隔与次数上限，每次describe经受检CommandRunner单独准入，轮询间隔
不占用AWS CLI配额；不在runner背后创建SDK客户端。实际等待仍取操作预算与父任务剩余
时间的较小值，线程池中的实例waiter继承同一父deadline。每次请求及返回后的成功判断
重新检查剩余时间，终态失败、错误响应和身份不一致立即停止。
`aurora_ready`等待`aurora`及CPU接入，验证双实例最终可用、有界重试（18次×10秒）
读取master Secret后写入`gpu-fault-aurora` Secret；
受管bootstrap显式使用`admin.rds_ca_bundle.RDS_CA_BUNDLE_PATH`生成
`sslmode=verify-full`的DSN，与CPU、schema Job和刷新器的非可选只读CA挂载一致，
不依赖部署机预先导出CA路径，也不接受继承环境覆盖该路径。CA安装仍校验官方bundle
的固定摘要；缺失挂载或不可信证书仍拒绝连接，旧手工调用缺少CA输入时仍拒绝生成DSN。
`aurora_refresh`同样只准备刷新程序的IAM访问，等待`aurora_ready`和Pod Identity，不等待
候选wheel或镜像；首次安装的CronJob/ServiceAccount/RBAC也由release部署。
默认`node_keys:*`等待CPU/GPU接入及fleet master。显式登记custody时，所有共享CPU
key map的节点键任务（含未选中的legacy目标）还须在`release`完成后串行执行；
无关IAM和资源准备仍独立并行。依赖失败的任务记为skipped而非各自失败；接入或release构建失败还会
停止尚未开始的独立任务，已开始的任务必须收尾。`aws-infrastructure-ready`在基础子集
完成时记录，`platform-prerequisites-ready`在全图完成时记录；随后的release rollout
中，首次NLB Service在schema/CPU部署前创建，让AWS异步准备与CPU工作重叠；
健康target、TLS和DNS验证及CNAME发布仍必须等待CPU就绪。
CPU、Profile和endpoint门禁通过后，首次安装的控制面监控配置与GPU bootstrap并行；
`regional_release_bootstrap.bootstrap_observability`在验证、失败持久化及清理前等待两边
结束。并行阶段使用installer的leave-as-is模式，不读取、发布或删除expected-collector
规则；仅在GPU和控制面监控均成功后单独发布该规则，并跳过已经ACTIVE且内容相同的定义。
GPU checkpoint仍由原调用线程写入，配置完成不代表Collector已经健康。
签名release的构建（ECR仓库、发布门禁、wheel、runtime镜像）在scope发现后立即于独立线程
启动（`release_repositories.SignedReleaseBuild`），与这张图并行：它只读源快照，AWS基础
资源不读它；`release`依赖节点等待构建完成并绑定候选输入。`monitoring_install`、
`aurora_refresh`、`aurora_ready`以及未登记custody时的`node_keys:*`按各自资源依赖立即
启动，不消费构建产物。custody节点键任务必须取已验签release，不能复用该默认例外。
基础设施任务的输入摘要在启动构建/调度前绑定，依赖任务完成后重新读取checkpoint是否
有效，不能复用调度开始时复制的旧completed集合。release同意校验在第一次取用
构建结果时执行一次，因此不同意的release在任何平台任务用到它之前就被拒绝。首次建站
由此把Aurora等待与冷构建两段最长的时间重叠起来。
`SignedReleaseBuild`在成功、前置错误、图失败和中断路径均通过`finally`收尾；可取消尚未
启动的工作，已运行的构建必须收尾后才能释放站点锁。SIGINT会请求取消受监督的子命令，
但不会硬抢占父进程的Python线程。最终失败phase在收尾后写入，防止晚到的
`release-ready`覆盖失败；不能把取消请求等同于所有工作已立即停止。
调度器输出task start/cache-hit/end，`bootstrap-state.json`的`task_reports`保留本次
执行/探测模式、起止时间、耗时和CommandRunner命令计数。计数按AWS/kubectl/总数分类，
不含参数或凭据；`runner_commands`只统计直接调用。新增`subprocess_api`独立记录本阶段
及继承部署作用域的子进程API命令、等待容量的耗时和观测到的SDK重试。
每个失败任务还立即保存异常类型与有界脱敏原因，不等独立长任务结束，也不只保留首个失败；
进度流只输出异常类型，详细原因从私有state读取，最终仍等待在途任务收尾后抛出原异常。
`admin.api_budget`用私有跨进程ledger约束整个部署的AWS、kubectl和HTTP并发，分别为
8、8、4；Shell子命令使用同一预算，原子维护的PID/starttime租约不会因PID复用误占容量。
租约回收（`_reap_leases`）以`/proc/<pid>/stat`判定CLI是否退出时，**僵尸态（Z）本身不是
退出证据**：snap 打包的 aws/kubectl 由 Go 启动器（`snap run`、`snap-exec`）从非主线程 exec，
内核在 exec 线程接管 pid 之前会把已死的主线程按同一 pid、同一 starttime 报告为 Z，窗口
为一次调度延迟。2026-09-19 部署 #18 就是这样：一个垫片把兄弟垫片刚启动的 `aws` 判为已退出，
复查时又发现它在运行，于是以 `cannot release a running API command` 失败了自己无辜的命令。
现在 `_identity_gone` 看到 Z 后先检查 `/proc/<pid>/task/` 是否还有活线程，再按
`EXIT_CONFIRMATION_DELAYS`（2/5/10/20/30 ms）复读，只有始终为 Z 或条目消失才算退出；
回收方（非租约所有者）复查发现命令仍在运行时只保留其容量、不再抛错，`_finish_slot`
中所有者释放仍在运行的命令仍然拒绝。
垫片进程退出时的失败行在通用文本之后附上底层异常的类名与文本
（`…capacity/deadline: <Error>: <detail>`）：一次只因垫片失败的发布否则没有任何可诊断的信息
（2026-09-18 收尾身份校验的 20 条并发 kubectl 里 2 条只留下裸的通用行）。收尾的运行时组件身份校验
（`validate_runtime_component_identity`）对只读的 Pod 列表和模块摘要探针在首次失败后原地重试一次，
仍失败才计入错误：一次垫片抖动不应把已经完整滚出的候选判成失败并触发回滚。
这里的ledger是部署机上单次命令临时目录内的`budget.sqlite3`，使用Python标准库SQLite
协调本地子进程；不是生产Store，不下发CPU/GPU集群，不保存业务对象或凭据，正常退出后
删除。生产控制面的业务存储仍为Aurora PostgreSQL。异常退出遗留的临时账本不能作为下一次
deploy的成功证明或复用状态。
S3高层传输强制classic client及4路并发，并占用4个AWS容量单位；用户AWS配置不被修改。
ledger协议v4会检查继承作用域的schema和所有者上限，不兼容时在命令启动前拒绝，不能
另建独立预算绕过全局限制。嵌套CLI的PARENT只是身份提示，必须验证PID/starttime及祖先链。
同backend借出配额前以pidfd暂停本次命令派生的父CLI，并确认全部线程已停止；同一父CLI
只允许一个借用分支，最多8层，分支保留祖先最高权重以便归还。STOP前先持久化仍占用配额的
`stopping`及借用者身份，全部线程停止后才提交`parked`；归还先提交计入容量的`resuming`，
之后才能SIGCONT，最后清除借用标记。中途崩溃由其他准入者或存活shim恢复，不能让已恢复
进程仍以`parked`漏计，也不能让兄弟分支在恢复提交前开始新的STOP。
取消且无法归还配额时终止已暂停的调用者，不能无配额恢复。这里暂停的是部署机的
AWS/kubectl子进程，不是GPU Pod、HMA容器或节点服务。
嵌套CLI输出暂存于匿名0600文件，stdout/stderr合计最多8MiB，写入前检查；
超限终止子命令并丢弃部分输出，不限制正常下载目标文件的大小。恢复调用者后才回传输出，
避免已暂停的调用者无法排空管道。临时输出不进入ledger或普通artifact。
需要暂停中的父进程继续提供stdin/IPC的自定义
helper不属于该非交互认证helper契约。
该预算限制命令/传输并发并平滑命令起始速率，不是每个HTTP请求的精确RPS限流。
暂停只约束可运行的CLI工作，不会撤销或冻结已经发出的HTTP请求。
AWS CLI内部调用与重试通过loopback CSM采集，只有数字计数进入ledger；原始CSM可能含
凭据，禁止持久化或输出。UDP可能丢包，报告明确标记`observed-csm-lower-bound`，
不能把未收到遥测解释成零重试，不能据此自动扩大并发或推算AWS计费。
Python并发预算集中在`admin.deploy_limits.DEPLOY_CONCURRENCY`，Shell预检入口另外强制
每集群1至8节点的上限并拒绝无效预算；只读查询、候选预检和实际Installer/不可用节点
预算不能相互替代。
`regional_node_batch`的server-side dry-run独立最多8批并行，每批仍最多4节点、8个Job
及1MiB，跨集群继续共用全部署kubectl配额和启动间隔；全部admission成功之后才创建
Host预检Job。Host执行窗口仍按每集群1至8节点单独限制，不能把批次并发当成扩大Host
或真实Installer不可用预算。批量调度收益由确定性的启动/逐对象RTT模型验证，不等同于
真实AWS端到端耗时测量。
`admin.deadlines`为原生HTTP、配额等待和`admin.execution`子命令提供同一时钟；
execution保留原有公开入口。整个deploy、TaskSpec和子命令分别设置deadline，子级不能延长父级；
默认总窗口6小时、release构建2小时、Aurora任务1小时，其他任务按登记策略执行。
普通命令受正常deadline约束；生命周期driver等待的是预留补偿时间后的硬截止，
避免父进程在子进程开始rollback时先行退出。硬截止逐层继承，嵌套driver不得再追加两小时；
rollback最多两小时且不得超过该硬截止，嵌套补偿不得延长当前补偿deadline。
只读管理员命令不预留补偿窗口。清理仍使用独立有界短窗口。
`run_command`在环境/协议准备之前计算绝对monotonic截止，并以`expires_at`传入
`run_owned_command`；准备、准入和启动开销不能重新获得完整窗口，启动及返回成功前重验
剩余时间。`execution.deployment_deadline`包住整个操作的`interruption_scope(wait_all=True)`：
SIGINT只登记取消请求并通过pidfd通知已注册的非清理命令，安全边界再抛出
`KeyboardInterrupt`；退出前等待所有监督者收尾。重复SIGINT不能异步打断清理，
`allow_interrupted`仅用于受限补偿/清理，不绕过监督丢失或延长deadline。
已知的命令stdin通过匿名、`0600`文件描述符传给子进程，不写入有名称的文件或日志。
这样大于管道容量的Manifest、dashboard和私有HTTP消息不依赖`communicate()`轮询续写，
也不会因子进程启动稍慢而只收到前半段输入。准备输入仍计入原deadline，启动前再次检查
时限和中断状态；子进程及其后代的终止、回收和完成证明不变。
Grafana和AMP原生HTTP通过`src/gpu_fault/admin/native_http.py`的`-I -S -B`隔离Python
worker执行DNS、TLS、HTTP framing及响应读取，整个worker树受同一进程监督与绝对deadline约束；
不能只依靠线程内`read1`轮询处理阻塞调用或持续chunked trailer。worker取得同一HTTP/AWS
配额后重算超时，单次窗口最多30秒，分块响应与私有JSON消息分别限制为最多8MiB，迟到
响应不得成功。URL、认证header、body和响应仅经私有stdin/captured stdout传递，
不放入argv、ledger、普通日志或artifact。
AMP在同一30秒查询窗口内通过受监督worker调用
`aws configure export-credentials --format process`，沿用原AWS shim的准入和凭据链；
stdout/stderr合计最多8MiB。导出的临时凭据只在内存和私有stdio中使用，以冻结凭据做
SigV4签名，不交给可能再次阻塞的SDK刷新链，也不写入新环境变量。TLS验证保持启用。
这些隔离只覆盖交给worker的I/O，不承诺硬抢占父线程中的任意Python或系统调用。
每条命令由`admin.process_supervisor`的内外两层独立Linux subreaper监督，使用PID身份和
pidfd终止并回收完整后代树；新session、双重fork和被终止的中间Python进程不能使后代逃逸。
内层被终止时外层接管孤儿进程，外层被终止时内层通过父进程退出信号收尾。两层有独立的
完成报告管道，实际命令不继承报告写端；只有存活所有者证明完整回收后才允许报告普通失败
或进入补偿，不能把监督进程退出本身视为命令完成。
部署机必须支持Linux subreaper和pidfd，无法建立监督时在启动目标命令前失败。
所有完成证明都丢失时抛出`ProcessSupervisionLost`，拒绝当前进程继续发命令或进入自动
回滚；即使孤儿仍持有输出管道，也不能无限阻塞于输出读取后再误判为普通失败。这种状态
不代表已清理成功，也不能仅凭重启CLI推定原命令已停止。不可终止的内核等待同样不会被
伪报为清理成功。
JSON driver的stdout保持机器可读，stderr实时输出受限的结构化阶段进度及30秒等待心跳；
其他诊断保留整份JSON和多行凭据上下文后统一脱敏，超出大小上限只保留安全错误类别。
实时管道/终端输出使用独立的非阻塞描述符，不修改其他写入者的阻塞状态；关闭或写满的
console不能使监督进程退出或阻塞回收。常规文件诊断延后到命令结束输出，诊断reader收尾
也有单独上限；机器可读stdout不丢弃、不混入进度信息。
凭据轮换、操作锁、审批、稳定窗口和节点安全barrier不因此省略。
正向证明缓存只在同一进程、限定有效期内复用：工具60秒，制品解压校验60秒，CPU凭据
结构校验30秒。键绑定作用域、内容和验证器身份；资源证明额外绑定新读到的UID及
resourceVersion。失败不缓存，同一键single-flight，不同键可并行。凭据结构证明不代表
数据库密码仍为AWSCURRENT，Aurora同步刷新不跳过。资源查询统一区分存在、确认不存在、
读取失败，只有成功的空`--ignore-not-found`结果允许走不存在分支。
监控基础资源、Aurora实例就绪、刷新器IAM和Node Action key这些任务同样probe-before-ensure。
`TaskInputSpec`绑定各自真正的输入，普通基础设施任务不绑定整个release identity：监控资源绑定告警邮箱、
SNS policy helper及共享asset，监控安装/刷新器基础任务绑定CPU身份和bootstrap实现，
默认节点键绑定wrapper、helper、私有证明实现与目标集群；登记custody时还绑定完整登记、
候选release和custody/bootstrap相关实现摘要。`bootstrap_custody_profile`拒绝未解决的
Profile/template策略变化，不得按旧Profile预授权；首次默认沿用正常`hyperpod-v1`及
config digest计算。源码部署分类也须让已登记custody进入application/bootstrap路径，
不能以unchanged或deploy-host-only跳过证据核验。ARN bootstrap的probe检查IAM、
Pod Identity、SNS等前提；
release另以`observability_drift`和`aurora_refresh_drift`检查ADOT/AMP定义、可用副本及
刷新CronJob的镜像/wheel/master Secret引用，把运行资源漂移纳入发布计划。不能以基础
任务checkpoint命中代替运行资源验证。节点键probe通过`read_node_key_proof`私有读取完整
Secret JSON，要求GPU key集合精确匹配当前HyperPod节点，并逐节点比较CPU并集中对应的
实际字节摘要；不是names-only检查。缺失、不一致、pending rotation标记或显式单节点
轮换请求均进入ensure；无效JSON、读取失败或身份冲突直接拒绝，不能当作确认缺失。
产品复用hint不能替代这份完整key证明；Shell入口同样保留完整字节校验及实际选中模板的
受信内容pin检查，不将产品“已验证”提示转换为跳过key或模板校验的授权。
release的监控安装脚本本身也按对象比较后再写：AMP rule groups
namespace和Alertmanager definition先`describe`并解码线上blob，与即将写入的文件逐字节
相同且状态为`ACTIVE`时跳过put，从而也跳过AMP异步校验的`UPDATING -> ACTIVE`等待；
runtime-only路径的ADOT collector只在ConfigMap/Deployment的apply结果不是`unchanged`
或本应运行的Deployment当前不可用时才`rollout restart`，否则只做`rollout status`确认；
`GPU_FAULT_FORCE_ADOT_RESTART=true`可强制重启。IAM inline policy和SNS topic属性由基础
任务按漂移收敛，不由runtime-only写入。脚本在stdout按步骤输出`amp-step-elapsed <秒> <步骤>`，
release日志里可以直接归因这一阶段的耗时。
已有release接管监控后，bootstrap仍不提前覆盖ADOT/AMP。所有权依据CPU集群的release
state判断，本地site缺失不能证明这是首次安装。发布分类通过
`regional_observability_drift.observability_drift`只读检查ADOT声明差异、可用副本和AMP
定义；漂移选择OBSERVABILITY节点，即使应用源码未变也不得走deploy-host-only/NOOP捷径。
status以退出码1返回的合法不健康JSON仍可用于发布差异诊断，包括监控和刷新器漂移；
它不构成健康证据，不能复用为verify通过。无效输出和其他退出码不按正常诊断接受。
实际修复仍在previous快照之后；完成后再次证明无漂移。ADOT缺失时必须先验证CPU namespace
锚点，才能在快照中记录明确absence；AMP只有ResourceNotFound才记为absence，权限/读取
失败不等于不存在。回滚还原原对象或原absence，不从候选Manifest猜测旧状态。

首次和已有应用release均由bootstrap收敛监控外围IAM、Pod Identity及SNS发布权限，不提前
覆盖候选ADOT/AMP配置。release通过安装器的内部`--runtime-only`模式验证既有IAM、
关联关系与SNS条件，只更新版本化运行资源；不创建或切换第二个region级role。
这些版本化资源在捕获previous后更新，保证回滚快照确实属于旧版本。实际ADOT渲染与
漂移检查使用同一namespace，包含collector内嵌的Kubernetes发现范围。
Grafana使用独立的`grafana_install` checkpoint，兼容读取旧的`monitoring_install.grafana`；
仅修改dashboard或Grafana选项不再触发监控重装。
自动发现/创建/导入的展示链路暂时不可用时记录`DEGRADED`和task warning，下次deploy
重试；AMP、SNS、告警订阅仍是硬门禁。归属不一致、多个workspace冒认同一site、显式
workspace/viewer输入错误必须失败，不能通过展示降级绕过身份和授权检查。
Grafana单次HTTP请求的30秒窗口耗尽仅在外层任务/部署deadline仍有效、进程监督安全时
按展示故障处理；外层到期、中断、监督丢失或来源不明的超时仍抛出，不可降级为成功。

schema与凭据刷新共用`wait-for-kubernetes-job.sh`：保持原超时预算，同时监视Job
`Failed/FailureTarget`和确定性容器配置错误，并拒绝等待期间被替换的Job UID。
GET遇到明确的限流、暂时服务故障或网络超时时只在同一总deadline内重试；权限、TLS信任、
NotFound及未知错误立即拒绝。成功watch直接返回并验证Complete对象及UID，不在超时边缘
因补一次GET而把成功误报为超时。
普通schema/刷新路径的失败Job保留供诊断；前置事务的proof Job按第5节的journal与UID
清理契约处理，不因失败而绕过清理。release history每次只读取一次ConfigMap；不可读时
告警而不覆盖旧审计。

deploy/bootstrap、Profile审批、AdminConfig、Node key custody登记、join、remove和uninstall竞争同一个
state-dir mutation锁。耗时源码准备可在锁外执行；拿锁后重新读取site并校验站点名、
Region和CPU EKS锚点，不能继续使用CLI启动时的陈旧成员快照。
`config`也在锁内重新读取实际Aurora及其他目标引用，身份漂移发生在计划或配置文件写入
之前即拒绝。继承锁不仅检查文件inode，还通过Linux fdinfo确认该open file description
确实持有排他flock；独立打开同一个文件、已解锁的旧FD或另一线程的继承FD均不能绕过
互斥。同一调用线程持有的有效锁仍可供受控嵌套命令复用。
锁路径必须是普通文件，拒绝symlink和FIFO。token轮换、热备声明/释放、手工处置写入、
workflow收敛和显式rollback也使用同一锁并在锁内重读site；collector-outbox的远程
`stats/list`同样创建持久workflow，因此也属于受锁管理员事务。
这是单部署机canonical `state-dir`的文件锁，不是跨部署机或复制state目录之间的分布式锁；
运行时registry CAS、Store原子操作、节点UID/resourceVersion和fencing仍各自必需。

新站点的AWS/Kubernetes mutation同样只覆盖首个基线GPU集群：GPU kubeconfig context、
namespace、token、Executor IAM、Node Action key、NLB NAT EIP和Private Hosted Zone
VPC association均不得为待join集群提前创建。其余ARN只保留为batch join输入。Route53
association按`Region + VPC ID`去重；多个GPU集群共用VPC时只登记一次，remove仅在没有
剩余集群引用该VPC时解除。
`resource_registry_dns`集中生成关联记录：CPU原生关联显式标记，不能从列表位置推断；
新GPU关联使用稳定物理key，已有数值或cluster形式key按完整zone/Region/VPC身份保留，
不会因成员排序变化改写不可变ownership、删除策略或依赖。关联来源必须明确：
成功创建且已验证的响应才记录`CREATED`，仅观察到已有对象不授予删除权；失去创建响应
后只读发现不能补造来源。PKI准备将已确认关联及时写入同一checkpoint，任务完成仍由
调度器登记；DNS helper摘要属于PKI任务输入。
注册表同步区分确认空清单与读取失败。旧关联缺少CPU/来源证明、身份冲突或同一物理
关联有重复不可变行时必须调和，不根据剩余一个集群猜归属。remove在drain前核验精确
`CREATED/DETACH`授权及反向依赖；底层网络解除默认不删除DNS，只有受检调用显式开启。
CPU原生关联、共享VPC、`EXTERNAL/REUSED/PRESERVE`关联均不因移除单一集群而撤销。

候选verify证据绑定source/candidate site摘要、live release identity、完整registry
cluster state、generation/content摘要和验证时间，有效期15分钟；verify期间或提交前漂移
立即失败。提交顺序固定为site、release state、Aurora资源注册等可补偿步骤，随后持久化
`ACTIVATION_STARTED`并执行幂等`PENDING -> ACTIVE`。该标记是不可回退点；之后失败只能
fail-forward续跑，不得清理已ACTIVE数据面。

修改该流程时必须同时维护ARN发现、候选site、提交前补偿回滚、提交后fail-forward、
Aurora资源注册和低层release JSON契约。

### 8.1 接入阶段、性能与补偿边界

以下顺序来自`src/gpu_fault/admin/cluster_join.py`与
`src/gpu_fault/admin/cluster_batch_join.py`，不是可自由重排的任务清单。

| 阶段 | 必要性 | 性能与并行边界 |
|---|---|---|
| 持锁、发现和恢复旧attempt | 绑定CPU锚点、GPU EKS/HyperPod、账号/Region及`NodeRecovery=None`；先完成未结束补偿 | 批次共用一次Aurora注册表导出和网络基线，发现最多4路；不得跨站点混批 |
| 本地输入与前置资源 | 准备独立token、受管namespace、节点key和专属网络/IAM | 默认共享GPU kubeconfig写入串行；Executor role、网络、节点key可并行，ADOT role等待Executor/OIDC；custody附加边界见§6.2 |
| 候选preflight与数据面安装 | 只给`PENDING`成员安装当前签名release，执行节点动态barrier和Fleet waves | 批次共用候选preflight；集群并行度与64节点总预算沿用release，不新增另一套并行参数 |
| 完整候选verify | 同时验证原成员和新成员，绑定site、live release、registry全量生命周期与generation/content | 共用一次完整verify，不再重复基线verify；证据15分钟有效，过期最多为待提交目标补验一轮形成新证明，不能只改旧时间戳 |
| 批次故障域屏障 | 对已完整验证的待加入成员生成合并映射，先保存发布意图，再发布并核对worker UID、模板摘要、副本收敛及registry稳定性 | 一次批次共用一次节点清单构建和worker收敛；屏障通过后才逐集群激活，不通过不得继续 |
| 提交与激活 | 先site/bootstrap、release state、Aurora资源注册，再`ACTIVATION_STARTED`和`ACTIVE`，最后复验 | 批次逐集群串行提交；已提交兄弟的预期revision变化可以推进剩余证明，但不得隐藏其他成员或release漂移 |
| 失败补偿或fail-forward | 未激活且`autoRollback=true`时补偿本attempt；激活意图之后只前进 | 先等待已启动的并行任务收尾，才做补偿；不撤销已成功兄弟，也不并行启动下一attempt与旧补偿 |

custody等待授权或证据阻塞不走表中的普通失败补偿，必须保留已准备的namespace/UID和
原输入；不能靠删除资源、自动重建或重复密钥写入来使下一次probe通过。

未完成事务续跑重新发现并比较持久化GPU身份；CPU被当作GPU、HyperPod重绑或namespace UID变化时
停止，不能用旧证据清理新对象。网络mutation先记意图与已完成的独占变更，不能确认请求
是否落地时不得标记清理成功。`ROLLBACK_STARTED/ROLLBACK_FAILED`必须先继续原补偿；
远端补偿完成、本地凭据清理未完成时只继续本地收尾。仍被回滚registry引用的cluster token
保存在与cluster/EKS/HyperPod身份绑定的受控路径，不能删除后自动生成新token来复用旧登记；
临时fleet master不作
普通证据保留。`SUPERVISION_LOST`禁止自动重试或补偿，需先明确调和未证明停止的命令。
`ACTIVATION_STARTED`后的续跑允许旧verify超过15分钟，但仍核对原绑定并完成ACTIVE终态
复验，不能重新要求目标回到`PENDING`或再次走撤销路径。
已完成且仍在本地site中的成员可幂等返回，不代表重新执行了实时verify；当前健康仍由
`status --full`独立检查。

每次批内提交仍复验故障域屏障的 worker/映射身份和当前成员状态；证明过期或失败恢复
可能需要为剩余的已验证成员生成新屏障。不能为减少 rollout 跳过屏障，或把候选成员
提前标为 ACTIVE。单集群 join/remove 继续执行其原有映射刷新和收敛检查。

节点key准备前通过当前成员Node集合、Agent归属、CPU key占用及同批目标排除全站
NodeName冲突，保存`NODE_NAMES_VERIFIED`的完整NodeName到UID绑定。
`BoundNodeKeyRunner`把该映射经内部`GPU_FAULT_NODE_KEY_EXPECTED_NODES_JSON`传给helper，
不能只传名称列表而漏掉发现到写入之间的同名重建。初次证明中的`expected_key_sha256`
采用GPU现有合法key的实际原始字节摘要，缺失项才使用v2派生值；因此已有随机轮换key
仍能被保留并正确补偿。续跑不得改用新观察值覆盖原证明。只有已可能开始key写入且
Node/key归属证明完整时，补偿才撤销CPU条目；先重验Node UID，再逐项比较CPU当前实际
摘要并使用resourceVersion CAS。摘要变化或归属未知时停止，不能按NodeName删除外来key。
已提交过site的join补偿即使发现本地site已恢复，也必须完成release state修复；已清理
资源须按原不可变身份发送明确的`DELETED/DETACHED`等终态更新，不能从upsert列表省略后
就假定Aurora记录已撤销。

### 8.2 移除阶段、性能与续跑边界

公共入口按完整GPU ARN选择目标；`src/gpu_fault/admin/cluster_removal.py`、
`src/gpu_fault/admin/cluster_removal_state.py`及其network/resources/Kubernetes helper
共同维护事务。

| 阶段 | 必要性 | 性能与并行边界 |
|---|---|---|
| 发现与绑定 | 核对CPU/GPU EKS endpoint、创建身份、HyperPod ARN、namespace UID、Node UID集合、token摘要及registry | CPU、目标和剩余集群网络查询去重、最多4路；续跑必须新读，不用长期缓存作为删除授权 |
| `CONTROL_REGISTRY_DRAINING` | 阻止目标领取新命令，保留排空与清理所需访问 | 与后续停止、drain串行，不能先吊销凭据 |
| `KUBERNETES_QUIESCED` | 停producer、排空队列、卸载节点unit、停止Executor并验证受绑定清理证据 | 复用已验证的清理checkpoint；退出码0不能代替完整清理状态 |
| `KUBERNETES_REMOVED` | 按已记录namespace UID删除并确认实际消失，防止终止中的Pod与吊销/IAM删除竞争 | 请求删除后必须等待absence，不能把这段等待与凭据或AWS撤销重叠 |
| registry/key撤销与`AWS_DETACHED` | 撤销目标membership、只移除目标节点key，清理独占IAM/NAT/VPC关联 | 两条分支可并行；AWS按逆依赖wave、每wave最多4路，失败不进入下一wave；Secret写入用resourceVersion CAS |
| Aurora、site和release提交 | 将本次状态增量合并到新读的registry，移除成员、token和bootstrap引用，刷新失败域映射 | 所有前置分支成功后串行提交；`SITE_COMMIT_STARTED`先于site写入，不能用旧快照覆盖其他条目 |
| `VERIFIED/COMPLETED` | 证明namespace和registry目标缺失、CPU/剩余成员健康、GPU EKS/HyperPod仍存在 | 独立只读检查可并行；未确认或无效JSON不等于absence |

`src/gpu_fault/admin/cluster_removal_kubernetes.py`在namespace删除请求中使用
`DeleteOptions.preconditions.uid`和foreground propagation，读取时已核对UID也不能
替代这个API前置条件。删除ACK丢失仅在重新成功读取并确认absence后才可继续；
等待期间出现同名新UID即停止，不能把新namespace当作旧删除仍在进行。
节点Installer annotation清理一次读取目标HyperPod的完整Node集合，核对已保存的
Node UID和resourceVersion之后，才以最多8个`metadata_cleanup` worker提交JSON Patch，
每个patch再次test UID/resourceVersion；初读集合或身份不匹配时不提交任何patch。
后续冲突停止未开始任务并等待已开始任务收尾。这8路是metadata API并发，与Host预检、
Fleet wave及节点不可用预算无关，不授权同时停止或重装8个节点。

Route53关联按`Region + VPC ID`处理，不按最早登记它的cluster key决定归属。
CPU或其他GPU集群仍使用的VPC及共享NAT EIP不得撤销；独占EIP逐条撤销并检查残留，
其中一条已不存在不能使其余条目被跳过。独占VPC关联必须等ChangeInfo为`INSYNC`并重新
确认实际关联消失。保留资源仍依赖目标IAM等资源时，在停止数据面之前拒绝移除。

site已移除目标但后续同步中断时，原完整EKS或HyperPod ARN可以通过同一attempt的精确
tombstone继续；不得用名称或ARN后缀猜目标。旧`COMPLETED`记录不授权跳过重新接入的
成员，必须归档旧attempt并重新发现。当前remove state要求schema v2及完整绑定；
缺少绑定的旧journal需显式调和，不能手工补摘要、删除状态目录或当作首次执行。
节点key清理还绑定已保存的CPU Secret UID和原始key字节摘要，重验全站NodeName归属
及Node UID后，才用UID/resourceVersion CAS删除并回读确认；不保存原始key。
移除或卸载遇到本地`ProcessSupervisionLost`必须在原journal持久化拒绝标记，后续
进程即使内存监督状态已重置也不能自动续跑，必须先确认原操作停止并完成调和。

接入/移除后的失败域刷新由`src/gpu_fault/admin/failure_domain_map.py`执行，所有外部
命令纳入统一监督和deadline。Node列表中的缺失身份、重复名称或HyperPod归属冲突必须
拒绝，不能静默丢行后把不完整映射发布为成功。写ConfigMap前先证明control-worker可读
且身份完整；权限错误不等于缺失，受管membership操作也不接受缺失worker。只有显式的
内部bootstrap调用可以把尚未创建的worker留给后续部署。模板摘要已一致时不重复patch；
变化时使用Deployment UID/resourceVersion守卫更新，等待rollout完成后再次核对同一
Deployment UID和目标摘要才返回；按名字等待就绪本身不能证明原对象已完成更新。

### 8.3 卸载与AWS删除阶段

`src/gpu_fault/admin/uninstall.py`采用单调phase，调用
`deploy/control-plane/regional/prepare-clean-redeploy.sh`完成Kubernetes/节点部分；
`src/gpu_fault/admin/aws_cleanup.py`只按注册类型执行AWS删除，不是公共独立命令。

管理员卸载 journal 的 schema-v2 绑定 installation ID、站点身份和原始清单。
下一次 deploy 只在卸载明确 COMPLETED 后，以有持久化意图和断点的方式归档整个
`uninstall/` 及旧 release/join/remove 事务目录和站点记录，不只改名主 state 文件；
新安装不能继续使用旧 namespace UID 和旧删除计划。管理员配置、凭据、签名密钥及
审计归档保留。未完成或丢失绑定的旧 journal 仍须调和，不能自动初始化成新的清理。

资源注册表按安装代次隔离存储作用域：旧站点首次登记继续使用原 site_name，完整退役
后才分配 `<site_name>:installation:<installation_id>`。所有当前 build/fetch/sync、
join/remove/uninstall 统一读取 `RenderedSite.registry_site_id`；AWS 名称、标签及 scope
校验仍使用原逻辑 site_name。旧数据库中的历史资源 ID 保持不变，新代次可以登记重新
创建的 AWS ID；同代次身份冲突仍拒绝，不能靠临时切换作用域绕过不可变约束。

| 阶段 | 必要性 | 性能与并行边界 |
|---|---|---|
| `REGISTRY_EXPORTED` | 校验site摘要、完整CPU/GPU/Aurora身份、账号/Region、依赖及有效策略，先保存原始清单和待删状态 | 重试复用受绑定快照；不在破坏性清理中重写installed-resource registry以消除未知条目 |
| Kubernetes preflight与drain | 保存清理inventory、namespace对象、集群/Node UID及完整fleet/unit清单；拒绝活动或未知记录 | 全站先在同一revision将目标置为DRAINING，再停GPU producer；ingress与消费者保持运行直到严格排空，不用批量孤儿SQL放行 |
| 消费者与Executor停止 | 依次完成`CONTROL_CONSUMERS_STOPPED`、`INGRESS_STOPPED`和`GPU_EXECUTORS_STOPPED` | 已无活动记录才停CPU角色；必须先于节点卸载，不能因拆除节点再制造无人执行的命令 |
| `NODE_RUNTIMES_STOPPED` | 按原journal保存的fleet/UID清单卸载Node Runtime与Agent | CPU消费者停止后不再读取数据库；已有临时节点DaemonSet仍绑定run/spec/UID，不新增资源种类 |
| auxiliary、对象与namespace清理 | 停辅助组件、删除注册对象和受管namespace并逐项验证 | 停放spare只恢复明确拥有的原始调度基线，写入带Node UID/resourceVersion并回读；未知基线阻断，不删客户对象 |
| `NON_AURORA_VERIFIED` | 先完成边缘、监控、IAM及网络等非数据库资源，保留后续验证所需依赖 | 逆依赖且同priority的独立资源每批最多4路；CPU Helm/LBC等必须在CPU API可用时证明已删除 |
| `CPU_VERIFIED` | 按`keep/delete`保留或删除CPU集群，并再次核对GPU集群保留 | CPU HyperPod先于CPU EKS；nodegroup可先全部请求再逐项等完成，Fargate profile必须逐个请求并等完成，addon也逐个处理 |
| `READY_TO_DELETE_AURORA` | 固定前序残留为0和pre-Aurora快照，保留最后的数据库审计边界 | `keep`不带reset只验证整套Aurora；删除模式先持久化数据库incarnation与最终快照策略 |
| Aurora删除与`COMPLETED` | 删除模式按当前实际reader、writer、cluster、依赖收尾，核对保留快照available和最终残留 | 同一reader wave先发请求，再等全部消失才动writer；writer身份变化立即停止，不按名称猜角色；不能与前序阶段并行 |

AWS每次删除前重新核对scope、当前调用账号、live tag或精确关联；只缓存当前cleaner内
已核对的调用账号，不缓存资源归属。未知类型、缺失身份、权限/TLS/解析错误或共享依赖
均停止。NotFound仅接受对应服务的精确错误码及受检退出状态，不能匹配任意错误子串。
IAM instance profile使用者、仍附着的policy、其他role信任的OIDC provider、外部
route table使用的IGW，以及仍服务客户Service/Ingress的LBC均阻塞相关删除。
Route53 CNAME须精确指向本站点拥有的NLB；SQS只移除精确topic statement，混合或通配
共享授权必须先人工调和，不批量清空其他权限。

历史LBC注册行的policy依赖role边只在`uninstall._execution_dependencies`的临时执行图
中规范化为role使用policy，供同一份预验证和删除调度使用：先由role删除流程解除自身
attachment并删除role，再删除policy。不能改写导出快照、删除计划或API/SQL中
`InstallationResource.immutable_identity()`包含的依赖、ownership和delete policy。
保留role却删除其policy必须在清理前拒绝，删除role而保留policy可以执行；缺失依赖、
环和其他保留消费者仍须拒绝。policy删除器继续拒绝任何剩余attachment，不强制detach。

AWS waiter每次请求和成功返回均受同一剩余deadline约束；长资源等待不等于单条AWS CLI
可以无限运行。重试已处于`deleting`的对象只继续等待与验证，不重复发删除；保留最终快照
时，cluster已消失也必须证明快照属于原数据库且为available。快照名称冲突或数据库
incarnation漂移在删除实例之前拒绝。`COMPLETED`重跑只复验，不授权清理同名重建资源；
缺失原site/清单/目标绑定的旧在飞状态须明确调和，不能因哈希自洽推定安全。

Kubernetes清理journal当前为schema-v2，固定包含独立的`NODE_RUNTIMES_STOPPED`阶段。
全站顺序新增`CLUSTERS_DRAINING`，以批量CAS保留未选中集群的完整durable状态；
不得用候选site把其他集群重新置为ACTIVE。journal的`phase_order`必须精确匹配当前顺序，
旧v2顺序与schema-v1同样需要显式调和，不能只补写phase或更新自算摘要。
续跑只接受原journal及其run/site/namespace/Node UID和fleet绑定；不查找或猜测“最新失败”
checkpoint，不重新初始化原始身份或补造drain完成记录。schema-v1属于旧顺序，必须显式调和，不能只改版本号、
补造新phase或重新初始化同一路径来继续。停放spare的`previous-unschedulable`必须来自
本次清理拥有的明确基线；缺失或归属未知时不得默认uncordon。

消费者尚未停止的续跑，会重新证明DRAINING及已完成的队列排空，不能把旧完成标记当作
持续准入屏障。消费者停止后的续跑只使用原fleet/UID证明，不再读取数据库。纯registry
drain使用不消费镜像的上下文；正常`RegionalRelease`构造及直接调用仍校验schema-v3/v4
镜像锁，不能通过CLI分支或环境变量绕过镜像使用路径。

动态workload RBAC通过
`src/gpu_fault/admin/cluster_removal_rbac.py::inspect_workload_namespace_rbac`
进行只读检查。collector的`attach_workload_rbac`在静态同步之后，把证明通过的
Role/RoleBinding追加到同一GPU context快照，行标记为`guarded_delete=workload-rbac`；
原UID和namespace/SA/Deployment锚点保存在该快照的proof，不写回安装ConfigMap，
不按标签或自行计算的摘要豁免orphan。
remove-cluster和全站uninstall均进入同一`prepare-clean-redeploy.sh`流程。
`cleanup_kubernetes.delete_workload_rbac`核验原journal的drain/停止阶段及实际静默状态后，
在`APPLICATION_OBJECTS_DELETED`内、归属锚点删除前调用
`src/gpu_fault/admin/cluster_removal_rbac.py::delete_recorded_workload_namespace_rbac`。
它复验renderer、scope、原UID和外来绑定，以UID/当前resourceVersion删除并确认消失；
caller逐项把删除进度写入原journal。行与proof不一致、未知读取、checkpoint失败或同名
重建均停止。不得恢复提前prune、独立RBAC journal或仅凭`DRAINING`的删除路径。
停机复验还必须确认对应Deployment的Pod对象全部消失，包括仍在终止的Pod；副本数为零
不能单独证明停止。CPU集群已按卸载计划删除后，内部`verify-targets --skip-cpu`只允许
原journal已完成`CLEANUP_COMPLETED`且全部RBAC删除均有checkpoint的只读复验；
继续验证GPU集群及原资源缺失，不允许借此发起剩余删除或省略在途清理的CPU检查。

### 8.4 其他管理员命令的阶段边界

| 命令 | 必要阶段与成功条件 | 性能、并行与失败边界 |
|---|---|---|
| `node-key-custody configure` | 显式私有选择文件和外部trust pin，持锁核验并固定内容身份；仅记录登记 | 不签名、不修改Secret；准备和授权后的执行仍由原deploy/join完成，注册损坏不能隐式退出custody（§6.2） |
| `rotate-token` | 持锁重读site和release门禁，发布重叠revision，更新GPU Secret，滚数据面/节点，观察静默窗口，提交本地token和最终revision | 节点沿用release waves；Secret/rollout先记开始意图，补偿包含已开始但未确认完成的wave。`TOKEN_FILE_WRITTEN`写入意图即不可回退，ACK丢失后校验新旧摘要并fail-forward；终态先于临时token删除 |
| `config spare` | 只读体检；声明先保存cluster/Node UID和原label/cordon基线，再带UID/resourceVersion修改并回读；释放只恢复该基线 | 单节点受锁mutation，不扩大热备分配并行；未知池状态、预留/隔离、跨cluster记录或Node UID变化拒绝释放 |
| `workflow-reconcile` | 构建计划，按目标GPU kubeconfig读取节点证据，apply前重新建计划并校验Store原子条件，归档结果；运行中发布只因缺source plan拒绝而又有verified restore后继的非plan记录，命令行侧提升为`verified-restore-non-plan`，经Pod内只用既有store原语的`apply-verified-restore`写入 | 同cluster节点证据单次读取可复用；计划不是动作授权缓存，apply仍串行受锁，部分失败须保留结果；显式空白selector不得扩大为全站；提升项与运行时apply分开发送，运行时子集单独重建计划以匹配其摘要 |
| 事件关闭 | 选择明确incident或受限发现范围，在CPU逐条判断；QUARANTINED额外取得GPU隔离证据后二次判断 | 同一受锁入口，逐条记录closed/refused及证据，任一refused非零退出；整批不是一个原子事务 |
| `submit-remediation` | `--plan`只读；apply持锁重读site与事件/节点，按选择创建受检workflow、写入机械检查确认，或（`confirm-node-action --node`）为BLOCKED记录上结果未知的节点动作写入人工确认 | 机械检查annotation带resourceVersion，节点身份不全或冲突即失败；多节点不是一个Kubernetes原子事务，已写入节点须审计后续跑；人工确认在命令行侧算判定，Pod内脚本只用既有store原语比对被确认步骤原文、复核Agent记录与boot id后以`save_workflow(expected=)`写入 |
| `collector-outbox` | 提交单步maintenance workflow，有界轮询对应request ID/已知status，校验目标action的节点结果，归档元数据 | `stats/list`虽不修改outbox，也写控制记录；轮询每次读取共享剩余deadline，超时不取消远端workflow。只有`SUCCEEDED`且有效节点结果、无error才成功 |
| `deploy --rollback` | 持锁重读live state，只取已提交previous，受监督运行rollback，再对齐管理site/配置并sync-state | 不独立build、不并行启动第二个生命周期事务；引擎失败或管理面对齐失败均不能报告成功，旧事务应先按原方向续跑 |

token journal固定`keep_window`、`window_minutes`、`quiet_seconds`和
`acceptance_timeout_seconds`的值及类型。在飞续跑、提交后仅剩临时文件清理的续跑均须
一致；缺字段的旧journal需显式调和，不能补猜默认值。`--rollback`方向不属于这四项
策略绑定，因此写入意图之前仍可按相同策略回滚；越过不可回退点或终态后遵循原方向。

`submit-remediation restore`按节点判定隔离归属：带本事件quarantine taint或本事件隔离
annotation的节点进入restore，已干净或由其他事件隔离的节点跳过并在`node_decisions`里给出理由；
没有节点仍由本事件隔离时拒绝并提示关闭事件。只恢复部分节点时步骤不带事件GPU范围，做逐节点
全量验证。`submit-remediation restore`读取事件节点的GPU库存，只把它作为逐节点验证的路由依据。
库存完整且每个事件GPU的归属唯一时，GPU/Fabric验证可拆成逐节点步骤；全部验证通过后
才执行唯一的`RESTORE_SCHEDULING`。库存缺失、不完整或有歧义时保留原验证范围，
不得因某个UUID暂时枚举不到而删除验证要求，也不得把空交集降成无GPU范围的成功检查。
单节点升级事件优先使用原步骤上已有的节点/GPU对应关系，不能继承无关兄弟节点的GPU；
无法证明的历史范围错误需受检调和，不在restore时猜测修正。

静默观察要求`0 < quiet-seconds < acceptance-timeout-seconds`，首次等待在最后一次
数据面mutation之后，读取和轮询共用剩余deadline，每轮探针固定`quiet_start`。
首次等待前固定受管ingress Deployment的UID、generation及期望副本数，并要求完整、
健康且归属链匹配的Pod集合；探测结束时继续匹配同一Deployment及Pod集合。不能只对
尚存的Pod取日志，而漏掉静默窗口内消失的副本。前后同时检查全部ingress Pod UID及
`api`容器的Ready、container ID、启动时间和重启次数，缺副本、缩容或重建均拒绝。
每个来源先无since过滤，以`--container=api --prefix --timestamps --tail=-1`及
`--limit-bytes=4096`读取当前日志前缀，首条完整记录必须不晚于`quiet_start`；只对完整前缀
记录字节长度及SHA-256，receipt仅在本轮内存中使用。仅恰好触及byte cap的末尾片段可以
截去；低于cap却不完整、无旧完整记录或空响应都拒绝。
随后按向下取整到秒的`--since-time`读取窗口，并以原固定纳秒边界筛选退役token记录。
所有窗口读完后，按各receipt的精确长度重读前缀，必须长度、完整性及摘要一致，再复验
来源身份。正常append不使receipt失效；前缀丢失/轮转、未来时间戳、不完整或迟到响应
均不能解释成静默。该证明依赖受信的正常append/rotate语义，不证明Kubelet/CRI未静默
漏报、恶意同前缀改写或窗口内未发请求的离线调用方已更换token。
辅助命令共用受监督、有界的CPU exec/节点查询与脱敏诊断，不把原始认证helper错误或
凭据放进argv、普通证据或日志。实现依据为`src/gpu_fault/admin/`中各同名命令模块及
`rotate_token_policy.py`、`rotate_token_acceptance.py`；验证边界见
[Validation limitations](validation-limitations.md)。

## 9. 修改与验收流程

生产部署机只消费签名离线bundle；`deploy-host-setup-online`仅用于开发checkout。
该在线入口先只读校验路径和版本配置，再由有界的两个Make任务并行准备锁定Python/admin CLI与
独立供应链工具环境，无需调用者添加`make -j`。两路均使用系统Python 3.12；
可用`DEPLOY_HOST_BOOTSTRAP_PYTHON`指定系统解释器路径，不依赖正在创建的主venv。
工具分支同时下载并校验Prometheus archive、准备Python工具，等两者完成后才安装和验证promtool，
同一venv内的pip写入仍串行。tool-only版本检查只依赖Python标准库。
固定版本、依赖闭包及archive摘要校验通过后复用工具，缺失或不符时修复。
任一步失败均等待已启动任务结束后返回失败；不回滚另一路已完成的环境。CI保留独立工具目标，
签名离线安装不联网、不增加promtool要求。在线Python初始化仍按原流程重建，可再次联网。

deploy-host wheel（`gpu-fault-deploy-host`）由 `scripts/component_wheels.py` 按导入闭包
打包，闭包同时跟随 `gpu_fault` 与 `gpu_fault_release`：管理员 CLI 在模块层导入发布引擎
（状态头、部署 consent、schema 变更接受、rollback），两者必须同版本随 wheel 一起安装。
deploy-host同时交付现有`gpu-training-submit`和`gpu-fault-workload-annotate`入口及其闭包；
Control Plane中的兼容入口保留，不因此新增管理员权限或改变提交的安全检查。
发布引擎的非 Python 输入仍在 `deploy/` 下，由 `gpu_fault_release.repository_root()` 定位：
从 checkout 运行时就是该 checkout；装在 venv 里时依次取 `GPU_FAULT_REPOSITORY_ROOT`
（安装冒烟 `gpu-fault-admin --help` 时由 `setup_deploy_host` 设置）和 venv 绑定的
`gpu-fault-managed-state-dir.json` → `site.yaml` 的 `spec.repositoryRoot`。
绑定site用受限YAML解析器读取，接受合法折行、引号和行尾注释；相对repositoryRoot以
site文件目录为基准，非字符串、空值及缺失的仓库锚点仍拒绝。
bundle必须绑定OS、CPU架构、Python 3.12 ABI/sysconfig platform、libc和全部payload摘要；
schema v2以当前clean checkout的payload身份匹配，commit授权由独立签名CI gate或本地
成功记录承担，旧schema v1仍精确匹配内嵌commit。setup先验签，再使用`--no-index`
安装到临时venv，依赖与系统工具检查
全部通过后才原子切换。新bundle还记录由`build.lock`、`deploy-host.lock`和平台计算的
`dependency_identity_sha256`：每个身份只安装一次共享依赖venv，不同项目wheel使用
轻量overlay venv和`.pth`复用该依赖层。共享层缺失、损坏或身份不一致时fail closed；
旧bundle没有该字段时继续使用完整安装。相同bundle只验证并复用，失败时保留原venv。
初始化器不得调用系统包管理器，报告不得包含凭据。新增构建期Python依赖时必须更新
`requirements/deploy-host.lock`，新增系统工具时必须更新
`src/gpu_fault/data/deploy-host-tools.json`、bundle构建、初始化检查和测试。
离线venv安装必须移除继承的`PYTHONPATH/PYTHONHOME`并强制安装bundle中的项目wheel，
不能因语义版本相同而误用工作区egg-info；相同bundle摘要但缺少CLI或状态文件的
不完整venv必须自动重建，只有完整且依赖检查健康的venv才允许复用。
源码准备器切到受检deploy-host CLI时，同时把选中venv的`bin`加入子进程PATH首部；
后续site命令也绑定当前CLI的解释器目录。选择目录不解析Python软链接的最终目标，
否则会错误回到系统环境；移除继承的`PYTHONHOME`，避免覆盖受检venv的包路径。
受检执行器再置顶API配额shim，操作锁和deadline继续传递；
无需激活内部内容寻址venv，也不改变GPU节点上的解释器选择。
启动受检CLI的内部交接还移除旧`PYTHONPATH`并显式绑定本次repositoryRoot，
避免旧checkout覆盖已安装代码；后续site脚本只使用所绑定仓库的源码路径。
接收完整环境的移除/轮换入口不得再叠加原环境，把已移除的`PYTHONHOME`重新带回；
进程内轮换作用域退出时仍恢复调用者的完整原环境。
bundle还记录`project_distribution=gpu-fault-deploy-host`、项目wheel SHA和
`project_module_digest`；setup在激活前读取已安装distribution并重新计算
`gpu_fault.module_digest()`，禁止把Control Plane项目wheel误装为管理员CLI。
`COSIGN_PASSWORD`只允许进入最终`cosign sign-blob`进程；质量门禁、PostgreSQL测试、
镜像/制品构建、attestation生成和deploy-host bundle构建必须显式移除该变量。

### 9.1 普通代码修改后的build与部署升级

本流程适用于没有修改Profile模板、站点拓扑和AWS资源的普通代码变更。

已有站点的代码候选可独立执行build：

```bash
COSIGN_SIGNING_KEY=/secure/release/cosign.key \
make PYTHON=.venv/bin/python release-build \
  RUNTIME_IMAGE_REPOSITORY=<registry/repository>
```

该目标要求干净源码树，先执行static，再按CPU容量以1至3路执行普通pytest、
PostgreSQL stress和source-only artifact。全部通过后使用`uv.lock`导出的哈希requirements
准备runtime image。首次ARN deploy会先创建ECR、完成登录，再以同一
目标构建control-plane/executor wheel；独立build则显式提供repository。镜像身份以
Dockerfile、固定base image digest、runtime lock、platform、build args、wheel SHA和
module digest计算规范化image input digest，并使用完整digest生成不可变tag。
static内部把Ruff、mypy、compile、架构、契约、安全、部署配置、文档、YAML和Shell拆成
最多10路；普通`make check`在static通过后并行运行artifact与排除重复artifact测试的
全量pytest。
quality gate子进程隔离外层deploy的deadline、补偿标记、API预算和shim PATH，避免测试
的模拟时钟或fake CLI使用实际部署上下文；外层构建进程的监督和超时仍有效，后续实际镜像
构建及发布继续使用原部署预算。

本地release-build需要PostgreSQL且未显式提供测试连接时，由
`admin.release_postgres.isolated_postgres_allocation`创建隔离数据库。它固定本机Docker
socket，先解析并绑定PostgreSQL 16镜像ID，再持久化创建意图，核对完整CID、CID文件、
归属标签及loopback端口后启动；就绪检查和清理均使用受监督的有界命令。
密码只进入私有文件，不在Docker参数或URL中。真实构建的授权与凭据放在仓库外、
权限0700的`<state-dir>/release-postgres`，文件0600。

本机受管PostgreSQL门禁由`scripts/run_postgres_shards.py`拆成独立实例分片；
`POSTGRES_TEST_WORKERS`默认按核数四分之一取4至16（与`PYTEST_XDIST_WORKERS`同一推导），允许1至16。公开生产构建与staging影响门禁只有在
有效本机allocation授权存在时，才给原`test-postgres-stress`目标传入
`POSTGRES_TEST_PARALLEL=1`；原质量门禁名称、8个竞争worker和40轮stress参数不变。
每个分片使用独立进程创建自己的PostgreSQL 16和私有授权，pytest仍为`-n 0`。
完整收集清单、实际选择的无重复并集、成功的测试阶段和零skip必须全部验证；
某个分片成功或总数看似相同不能代替完整证明。该本地报告不是CI shard回执。
外层已有allocation仍由原部署作用域保管，分片不得接管或清理它；
分片自身的身份、停止和清理继续沿用受管PostgreSQL生命周期，不做全局Docker清理。
手工外部连接、CI覆盖率路径和显式自定义impact测试命令不因此改变执行方式。
staging影响计划要求完整门禁和PostgreSQL时，有效本机授权且使用默认stress命令的路径
直接复用`run_release_gates`：先static，再并行普通pytest、PostgreSQL分片和source-only
artifact，不再先跑完`make check`才开始PostgreSQL。其他影响计划仍按原选择执行。

构建只继承无密码URL和授权引用；`postgres_test_environment`仅为release-gates的
PostgreSQL分支和影响测试的PostgreSQL子进程选择私有HOME/PGPASSFILE，普通测试、
artifact、ECR/Docker和签名工具的HOME不变。native测试仍独立验证CID、归属、端口和
服务版本，不因父进程创建过数据库就省略校验。
退出时按确切CID删除容器及卷，确认CID/名称均不存在后才删除私有目录。
创建结果未知、清理未确认或监督丢失时，整个构建失败并保留归属证据；后续构建或制品
复用也拒绝未解决的`release-postgres`目录。先按原操作恢复流程确认进程及资源归属，
再受控调和，不能仅按同名容器删除或擦掉目录绕过拒绝。显式外部测试连接仍由调用方
负责隔离和授权，本helper不会接管或删除该服务。

Shell脚本与Python共用同一条体积棘轮：`scripts/check-python-architecture.py`把
`deploy/`、`scripts/`、`tools/`、`tests/`下`*.sh`的文件行数和`name() {`函数行数一并
记入`architecture-baseline.json`，阈值与Python相同（文件1500行、函数200行），超限条目
只能经评审后`--write-baseline`登记，之后只准缩不准长。`make shell-check`与CI static作业
中的shellcheck以`--severity=info`运行，全部脚本在该级别为零告警；确实需要字面`$`或
反斜杠的远端payload和JMESPath查询只允许逐行`# shellcheck disable=`并写明原因，不接受
文件级排除。

若registry中该tag已存在，只有目标platform和全部`gpu-fault.*` config labels与本次输入
完全一致才复用其OCI digest；tag存在但任一label不一致时fail closed。未命中时执行
build/push并再次从registry回读manifest digest和labels。可选BuildKit远端cache使用独立
mutable cache repository，只加速layer构建，不能进入Manifest或替代上述校验。
只有匹配目标引用的registry缺失响应允许进入冷构建；Docker credential helper缺失、
认证、TLS、网络、进程退出或输出解析错误必须停止，不能按通用`not found`文本推断。
错误信息保留安全的工具类别和排障方向，不回显可能包含凭据的helper输出。
`release_image_set`以CSV结构解析BuildKit选项，把registry cache tag分别追加
`-control-plane`、`-executor`、`-node-dependencies`，local cache使用对应子目录，
避免并行导出覆盖同一个cache index。普通cache import同时尝试组件目标和原共享目标；
固定digest、带selector或其他backend的import保持原语义，不猜测新地址。split export
仅支持明确的registry ref和local dest，重复、冲突、歧义或不支持的目标在构建前拒绝。

`make check`中的`artifact-check`先构建本次唯一一套canonical三个组件wheel和
Node bundle。Runtime Image和最终artifact阶段验证source identity、物理SHA、
`module_digest`及bundle内嵌wheel后复用该套制品，生成deployable Manifest v4和
attestation，并在同一`release-build`内用cosign生成
`dist/current-attestation.bundle.json`。PostgreSQL并发、lease、counter或fencing变化
仍须通过CAP-005。

image-set descriptor schema v3必须分别记录control-plane/executor wheel SHA和module digest，
以及节点离线依赖inventory SHA；每个镜像记录完整image input及其SHA。
三个构建最多并行3路，沿用同一个不可变ECR repository，不新增AWS资源。镜像复用仍会验证
registry labels；构建器在输出descriptor前通过`verify_release_images`启动禁网、只读容器，
检查组件入口、实际module digest、另一组件目录确实不存在，以及离线依赖的全部文件摘要。
节点依赖镜像额外保存部署机本地构建receipt，位置为
`~/.cache/gpu-fault/node-dependency-images-v1/`。目录权限0700、文件0600，
独立本地密钥以HMAC认证receipt，禁止将密钥或receipt加入源码、发布制品或ConfigMap。
receipt绑定repository、两个lock、平台、base、Dockerfile及构建/发布器摘要；复用时仍
向registry重新验证固定OCI digest、platform和全部预期labels。只有认证和身份校验均
通过才跳过wheel下载及构建；缓存缺失或镜像明确不存在时走冷路径，损坏、权限或身份错误
必须失败，不能信任普通inventory文件。receipt不代替最终release签名和镜像内容检查。
inventory中的wheel名称、版本、平台tag和文件hash还要逐项绑定当前lock；pip的requirements
解析和兼容tag计算放在有30秒上限的隔离子进程中，避免其全局日志配置污染部署机或应用。
已验签的split release在同一ECR repository中批量检查CPU、Executor和依赖镜像digest，
验证返回的registry/repository/digest完整集合；读取失败不作为镜像不存在。
schema v3共享镜像的单镜像入口复用同一验证器，显式绑定Region和registry ID；空集合、
错误账号、错误digest、重复条目或未读完的分页都不能当作可复用镜像。
`make runtime-image-check`执行同样的本地构建/内容检查，不推送。
最终artifact build会重新计算并逐项比对canonical
artifact，而不是串行重建第二、第三套wheel；不一致时不得生成deployable Manifest。

应用release identity与deploy-host bundle identity独立：部署机lock、setup脚本或工具
清单变化只重建deploy-host bundle，不强制生成新的Runtime Image或应用release。
应用Python行为继续由三个component wheel SHA和`module_digest`绑定，不能因为从
`runtime_image_inputs`移除宽泛的`src/**/*.py`就绕过源码校验。

`gpu_fault.admin.cli`及其依赖闭包属于独立`gpu-fault-deploy-host` distribution。
`gpu-fault-control-plane` wheel和Runtime Image中禁止出现`gpu-fault-admin`入口、
`admin_cli.py`或`deploy-host-tools.json`。因此管理员CLI、bootstrap、source deploy
代码变化更新部署机bundle和deployment域测试，但不改变应用component digest；
若Manifest、renderer输出、Node bundle和Runtime组件均未变化，集群应用发布分类为
`NOOP`并只执行最终verify。

dirty staging的source-only组件制品还会写入
`<state-dir>/component-artifacts/<component-build-identity>/`。identity覆盖Python、
平台、`pyproject.toml`、固定build frontend、三个组件源码闭包和Node bundle全部输入。
后续delivery-only或deploy-host-only快照可以复用物理wheel和Node bundle，但必须重新
生成当前delivery Manifest；任何组件、节点脚本、systemd unit、cleanup inventory或
build lock变化都会使用新identity。缓存损坏时忽略该entry并重新构建，不从旧Manifest
继承delivery identity。

部署阶段：

```bash
make PYTHON=.venv/bin/python release-deploy \
  SITE=/path/to/site.yaml \
  COSIGN_KEY=/secure/release/cosign.pub
```

`release-deploy`默认读取同一checkout的`dist/current-attestation.json`和
`dist/current-attestation.bundle.json`，不运行`make check`、Docker build或依赖下载。
已有站点职责分离时，Release CI执行build、管理员执行deploy；固定制品文件名不变。
部署阶段为：

1. cosign验证签名、CI identity和OIDC issuer，再校验attestation绑定的
   `dist/current-release.json`、release ID和delivery SHA。
2. 比较Profile template和线上Profile；策略变化缺少匹配的state审批时只生成
   `profile-plan.json`并停止。管理员在同一条deploy上加
   `--approve-profile-plan <plan_sha256> --reference <ref>`重跑，审批并继续部署。
3. 原子准备Profile快照、Agent config digest、site release和各角色image digest。
4. 通过只读取release state的`release-diff`判定NOOP；该判定不要求新旧release ID相同。
   `release_delivery/rendered_manifests`等非运行时变化可以在release ID变化时仍分类为
   NOOP。非NOOP执行preflight和组件DAG：

   | 代码变化 | 典型分类 | 实际动作 |
   |---|---|---|
   | 制品文件、配置和Profile均未变化 | `NOOP` | 快速路径不滚动，只运行一次最终verify |
   | 仅Control Plane闭包变化 | `CONTROL_PLANE_ONLY` | 只滚CPU ingress/worker/spool |
   | wheel许可证或打包元数据变化，代码digest不变 | `DATA_PLANE_COMPATIBLE` | 按物理SHA上传变化制品，建立compatible窗口后最小滚动 |
   | Executor或Node Runtime兼容变化 | `DATA_PLANE_COMPATIBLE` | 只滚受影响GPU数据面或节点Agent |
   | Schema、协议、Agent配置、Profile或集群集合变化 | `FULL` | 摘要分类；DAG只执行依赖节点并保留两阶段pin |

5. 每个phase和cluster写checkpoint；共享release默认按site中的GPU集群顺序串行推进，
   每个集群记录`PENDING -> RUNNING -> CONVERGED`，异常为`FAILED/PAUSED`。
   `upgradeMaxParallelClusters`（release config中的`upgrade_max_parallel_clusters`，
   默认1、上限8）把跨集群推进改为有界并行：所有集群共用一把可重入state锁，
   `component_progress`、`cluster_attempts`和checkpoint都在同一次read-modify-write内
   完成，因此并行集群不会互相覆盖各自的子树。首个失败立即关闭闸门，尚未开始的集群写入
   `not_started_cluster_ids`，已经在推进的集群先跑完当前波次序列再汇总；
   `failure_scope`仍按是否全部为cluster-local决定`PAUSED`或`FAILED`。
   自动回滚不使用该开关，`component_progress.clusters[*].updated_at_epoch`保证按实际
   mutation时间逆序串行恢复。节点使用
   确定性FleetDeployment ID和`waves/next-wave`，中断后复用原波次。
   `upgradeMaxUnavailable`默认0（auto，取规模上限）、上限32，第一波固定1；拓扑含UNKNOWN时强制1，已知
   failure domain下按节点数把单集群上限自适应为4、8、16或32并均衡分布，显式值取与上限的较小者。
   `rollbackMaxUnavailable`默认2、上限4，rollback第一波固定1；少于6节点或UNKNOWN
   强制1，6至31节点最多2，至少32节点才允许4，多failure domain时每域每波最多1。
   affected artifacts上传后、schema Job和CPU rollout之前先完成
   `candidate-preflight-ready`：候选GPU/DCGM/Reconciler/Installer Manifest执行
   server-side dry-run，节点级Action key和regional Secret引用只读校验，并用只读
   host-root预检Job证明bundle/wheel摘要、磁盘、Python 3.12、systemd、NVIDIA/EFA工具、
   quiesce残留和旧runtime回滚槽。集群预检最多4路，admission独立最多8批，每批最多
   4节点/8个Job/1MiB；只读host Job采用每集群最多8节点的滑动窗口，任一节点完成即可
   启动下一节点，不等最慢的整批节点。
   全部dry-run通过才开始host Job；失败后停止新节点并等待已启动节点收尾。
   被强制终止的子进程通过有界存活检查识别，不只依赖退出通知，避免等待无法到达的通知。
   私有输入快照仅保存拓扑和
   已验证的Secret引用，不保存凭据；`--node-inputs`仅供渲染或只读预检使用，不能授权
   真实安装。节点清单缓存按线程上下文隔离。结果按节点顺序汇总，任一节点失败整个阶段失败。
   该阶段失败时CPU/GPU进程、
   Reconciler和Fleet wave均未mutation。第一台节点mutation前再执行动态barrier，重新读取目标Node集合/UID/failure
   domain、Ready、cordon/隔离taint，并验证Executor、remote command、破坏性workflow和
   Agent lease；这些依赖候选进程或最新运行态的事实不能只复用早期checkpoint。
   该barrier唯一豁免的是**停在热备池里的节点**：未预留且
   `gpu-fault.io/spare-pool-state=AVAILABLE` 的节点，其 cordon 与派生的
   `node.kubernetes.io/unschedulable` taint不计为阻塞。热备必须保持 cordon
   （`HyperPodSpareCoordinator` 会以"unreserved spare is schedulable"拒绝可调度的
   候选），所以把 cordon 一律读成"有人在排空或修这台机器"会让任何声明了热备池的站点
   无法升级——barrier 失败、release 回滚，客户只能在"保留热备"和"接受修复"之间选一个。
   停放中的热备不承载 workload，且只有 node agent 保持 fleet-ready 才可被分配，
   因此必须随波次升级；installer 本身已 tolerate cordon taint，rollout 也不会
   uncordon 任何节点，池的不变量不受影响。被预留、处于非 AVAILABLE 池状态、
   带 quarantine taint、未 Ready、正在删除或 installer 仍在运行的节点照旧阻塞。
   中断续跑只要尚未达到`data-converged`，就重新执行只读候选/host预检；持久化
   checkpoint用于恢复顺序，不能无限期证明磁盘、rollback slot或资源引用仍未漂移。
   GPU/DCGM Manifest在实际apply前还会再次server-side dry-run，以阻止早期证明后发生的
   admission或RBAC漂移造成部分资源mutation；只读host probe不在同一正常事务内重复。
   其余阶段对"没有变化"的输入也不付无谓的等待：`endpoint-ready`先读取线上CNAME，
   Name/Type/TTL/Value与期望完全一致时不提交UPSERT，也就不等Route53的INSYNC传播
   （rollback写入的是不同值，仍然照常提交并等待）；`cpu-staged`/`cpu-finalized`
   调用的role-split脚本只读一次`gpu-fault-release-metadata`再本地取全部pin字段，
   并把选中角色的全部ConfigMap合成一个多文档流一次apply。正常路径把wheel、image、
   通知/容量配置、failure-domain及pin摘要一次写入最终Pod模板，不再先apply再patch/restart。
   pin变化由`gpu-fault.io/pin-config-sha256`触发滚动，显式force使用新restart时间戳；
   非force保留原时间戳。历史手工环境变量存在时，`apply_control_plane_deployment.py`
   先取得server-side dry-run的最终对象，只移除已退役且候选未声明的字段，再按UID和
   resourceVersion执行一次replace；冲突时有界重试完整预览，不额外`set env`滚动。
   其他现场字段保留，显式rollback快照中的旧环境变量不被过滤。Fleet wave等待
   Agent收敛时以固定5秒轮询`get nodes`，不再退避到15秒（退避只会在installer已经完成后
   多空等最多10秒）。这些都不改变任何门禁的判定条件，只去掉门禁之间的空转。
6. Profile变化在CPU finalize前查询Aurora Store；旧Profile活动未归零即失败。
7. 组件`STARTED`和`FAILED`立即写release state；同一GPU action/wave中的多个组件共享
   一个时间戳并合并成一次checkpoint写入。`COMPLETED`先在内存更新，由紧随其后的phase
   或cluster checkpoint合并落盘。进程在两者之间退出只会幂等重放该组件，不会漏掉
   已开始mutation的回滚证据。随后运行change-specific quick gate，再只运行一次最多8路
   并行的完整verify并保存`verification-report.json`。该次verify及previous快照捕获按context预读Deployment
   列表并在报告作用域内复用JSON结果，不跨mutation复用。quick gate的独立verifier并行执行，
   全部成功后才写证据；runtime identity检查所有Pod，共享全局8路预算。
8. 实际变更发布在正式stability前执行critical收敛门禁。只有当前critical集合精确属于
   `GpuFaultStoreIoRejected`，且全部运行中CPU Pod的
   `gpu_fault_store_io_rejections_total`按process和reason完整覆盖且为0时，才允许最多等待420秒
   让旧序列退出5分钟rate窗口；其他critical立即失败。清零后再运行120至300秒
   stability window，检查Pod重启、Ready、Processor队列趋势、远程命令和critical
   alerts，保存`stability-report.json`。verify与stability互不依赖，并行执行，任一失败
   只触发一次回滚。队列趋势判据为相对增幅：最近三个样本非降、末样本与首样本之差不小于
   `max(GPU_FAULT_RELEASE_QUEUE_GROWTH_MIN_DEPTH（默认8）, 首样本的一半)`且最老请求年龄
   超过两个采样间隔时才判定持续增长；数据面刚收敛后600秒内，
   `GPU_FAULT_RELEASE_STABILITY_GRACE_ALERTS`（默认
   `GpuFaultCollectorSilent,GpuFaultCollectorMetricsSnapshotStale`）列出的critical告警不计入，
   其他critical仍立即失败。`release_diff.kind`为`CONTROL_PLANE_ONLY`时窗口最早可在60秒
   （基线后两个干净采样）结束，条件是每个采样都干净（无任何critical告警，含被宽限的）且
   全部控制面Deployment已收敛（`replicas == updatedReplicas == readyReplicas ==
   spec.replicas`、`observedGeneration == generation`）；报告以`early_exit`和
   `early_exit_reason`说明适用的窗口。deploy在`complete`且未commit时写出的快速验证证据可被随后的
   verify复用（`pending_commit`且release ID一致），只跳过只读verifier脚本。verify或
   stability失败而站点没有回滚（fail-forward release）时，事务停在`complete`且
   `transaction_committed=false`：同一候选再跑deploy会resume进commit；**不同候选**的deploy
   先把这笔线上事务按其自身身份commit（`commit_live_release`→`save_recorded_state`，不用
   `save_state`，否则候选的摘要会盖到描述线上的state上），再以它为`previous`开自己的事务，
   stderr打印`commit-live-release release_id=… reason=…`。2026-09-09 deploy #25的verify因
   检查本身有缺陷而失败，旧候选永远过不了verify、新候选被引擎以
   `resume release_id does not match the candidate`拒绝，这条路径就是为此补的。
9. 最后才生成一次`release-summary.json`；NOOP只登记新release state并运行一次完整
   verify，跳过mutating deploy、重复quick verifier和稳定窗口。

失败行为：

- CI门禁、OCI push、attestation或签名失败：不产生可部署release；
- 验签失败：部署机不修改site或集群；
- preflight失败：不开始滚动；
- 升级失败且`autoRollback=true`：恢复上一稳定制品、pin、Profile、regional cluster
  registry、CPU role ConfigMap、DCGM和节点身份。previous只按execution plan捕获会发生
  mutation的面；CPU-only不读取GPU Deployment、Installer或Agent rollback身份，AMP未
  变化时也不读取规则blob。previous规范JSON经gzip后写入不可变、内容寻址、分块
  ConfigMap，主`gpu-fault-regional-release-state`只保存摘要和chunk引用，避免超过
  ConfigMap 1 MiB限制；任一chunk缺失、非canonical或摘要漂移均fail closed。旧内嵌状态
  保持兼容，后续成功commit只保留当前state引用的snapshot加最近2份旧snapshot
  （`PREVIOUS_SNAPSHOTS_RETAINED=3`），更旧的才删除；
- 每次`save_state`还向append-only的`gpu-fault-release-history` ConfigMap
  （`history.ndjson`，保留最近200条）追加一条审计记录：release ID、phase、state与
  execution plan的sha256、UTC时间戳、操作者身份（`aws sts get-caller-identity`的
  ARN，不可用时为`user@host`）和脱敏后的命令行；`gpu-fault-admin`通过
  `GPU_FAULT_RELEASE_HISTORY_DIR`把同一条记录镜像到state目录`history/history.ndjson`。
  记录里只有摘要，从不含token或state正文；写入失败只告警不阻断发布；
- `autoRollback=false`时，高层verify或stability失败只持久化失败和
  `rollback.status=SKIPPED_POLICY`，保留原事务供修复后续跑，不得擅自回滚；
- 低层已完成自动回滚但以非零退出时，高层只对齐正式site、容量desired和release state，
  不启动第二次rollback。commit与rollback先持久化不可回退终态，再幂等删除临时
  Secret备份；清理失败只续清理，不得反向回滚已提交事务；
- rollback根据持久化`execution_plan`、component progress和cluster checkpoint只补偿
  实际开始mutation的组件；CPU-only不得触碰GPU，Executor-only不得重装Agent。低层先
  验证compensation plan涉及的范围，高层完成管理面对齐后再执行完整站点verify。GPU集群
  按实际mutation时间逆序串行恢复；候选Installer Job和
  Agent FleetDeployment只在对应cluster/component范围内取消，旧/新A/B槽位和不可变
  制品保留到rollback window结束。`rollback_timing`记录failure detected、controller、
  每集群/每wave、restore、verify以及`T_safe/T_full`；
- 首次从启动时安装wheel的legacy release迁移到不可变runtime image前，`sync-state`
  必须同时记录线上真实旧镜像和已扫描、预装旧release CLI的rollback兼容镜像。升级
  开始时真实旧镜像发生漂移或兼容镜像不是不可变digest时必须在mutation前失败；
- rollback先恢复GPU数据面和节点，再恢复CPU；legacy节点仍满足旧artifact、config、
  node UID和Succeeded状态且没有Installer Job时跳过新Fleet协议，不强制旧Agent补报
  新增的bundle/template字段。
- legacy节点已被候选部分更新时，由候选CPU和候选Reconciler按Fleet wave安装previous
  制品；每个wave精确核对旧版本支持的protocol、agent version、artifact、
  compatibility、policy、Profile、config、Node Action key和node UID。
  bundle/template继续由previous模板和安装包恢复，但在旧Agent heartbeat中保持`None`。
- rollback必须复用previous记录的不可变Installer template ConfigMap；不能重新渲染
  一个内容不同、名称不同的模板。`regional_release_rollback_target.validate_rollback_node_template`
  在rollback入口先验证所有尚未完成且需补偿AGENT/RECONCILER的集群，发生在CPU、
  刷新器或Profile恢复之前；每个目标真正补偿前仍复验。CPU-only回滚不读取无关GPU模板，
  缺少旧可信内容pin或依赖绑定时不能先恢复其他组件再失败。
  `rollback-data-restored`尚未通过verify时允许幂等重放。
- 每个非resume upgrade和`sync-state`都必须建立新的transaction state，清空上一release
  的`rollback_completed_phases`、cluster checkpoints、failure和result字段；只有同一
  未提交release处于`failed`或已持久化upgrade checkpoint时，显式resume才可以复用当前
  transaction checkpoint。resume必须从持久状态重建并校验retry diff，不得回退默认
  `FULL`。resume校验必须checkpoint-aware：release ID、执行计划、previous快照摘要、
  CPU required/compatible窗口、集群身份和节点集合不得漂移；已完成集群必须匹配候选，
  未开始集群必须匹配previous，失败或暂停集群只允许状态机定义的混合状态。
- installed-resource registry按`scope + kind + namespace`批量查询资源，仅对标准
  `aws eks get-token`按显式有效期使用私有`0600`临时kubeconfig，减少重复认证；没有
  有效期不跨请求复用。通用exec插件和其他exec选项保留原生kubectl协议，不手工缓存。
- `database_schema_version`变化未声明向后兼容时禁止自动rollback；仅ensure Job清单或
  镜像变化会以同一目标版本幂等执行，不视为DDL版本跃迁；AMP rules与Alertmanager在
  mutation前保存原始blob并可自动补偿；ADOT collector同样可补偿：快照按Manifest声明的
  对象顺序读取线上ServiceAccount、ConfigMap、Deployment、PDB、Role和RoleBinding，剥离
  API server自有字段，把候选新增对象记为`absent`，回滚时apply旧对象、逆序删除`absent`
  并`rollout restart`加`rollout status`收敛collector，因此ADOT Manifest和ADOT image变化
  不再拒绝自动rollback；线上缺少collector Deployment时必须验证CPU namespace锚点并记录
  明确absence，否则快照fail closed。续跑一个previous
  快照不含ADOT对象的旧事务时在滚动任何组件之前就拒绝自动rollback，而不是等到observability
  restore才失败。endpoint和cluster registry仍没有补偿面，仍拒绝自动rollback，要求
  fail-forward或显式恢复；
- 原始升级异常和rollback异常分别保存，任何一方都不会覆盖另一方；
- verify或stability失败：先原子写入`FAILED`、`failed_at`、原始异常和
  `rollback.status=IN_PROGRESS`，再调用低层rollback；回滚完成后更新为
  `PASSED/FAILED`。进程中断时必须保留`IN_PROGRESS`证据，不得回退为无错误的
  `VERIFIED`假状态，也不得宣称上线成功；
- Profile发布失败：绑定同一计划和live baseline的活动审批保留用于幂等续跑；计划或
  baseline变化时旧审批归档并失效；
- release summary失败：保留`COMPLETED`和已签入的verify证据，同时写入
  `release_summary.status=UNAVAILABLE`与`completion_warnings`；
- 修复后重跑同一条`make release-deploy`。`failed`或中断在upgrade checkpoint的事务
  只允许同一release按持久checkpoint续跑；`rolled-back`是已验证终态，后续候选复用
  保守差异集合但从当前线上baseline开启新事务，不把旧release ID当作resume目标。
- 已验证rollback完成后，发布器必须把正式site、管理员容量desired配置和release state
  同步到previous线上版本。历史`rolled-back`状态尚未完成该管理面同步时，`status`使用
  previous不可变Manifest和Profile生成临时只读基线；不得继续拿失败候选判断线上健康。
- 历史`BLOCKED` predecessor只有在同incident已`RECOVERED`、当前successor为
  `SUCCEEDED`且完成`RESTORE_SCHEDULING`时才可不阻塞Profile/release门禁。公开
  `workflow-reconcile`（`--dry-run`/执行同一命令）还必须绑定fencing、过期lease、无open command、
  无WAITING provider动作、FAILED source plan和GPU节点无残留隔离；apply通过Store原子
  操作更新predecessor、incident和plan，永不直接删除记录，删除仍只由archive-first执行。
- `partial-convergence`和upgrade checkpoint走upgrade resume；`rollback-*`、
  `rollback-failed`及已回滚但清理未完成的状态只走rollback resume。已提交但备份清理
  未完成的`complete`状态只重试commit cleanup。

首次legacy迁移的能力矩阵是代码契约：

| 面 | legacy实际支持 | legacy不支持 | rollback使用者 |
|---|---|---|---|
| FleetRequest | protocol、agent version、artifact、compatibility、policy、Profile、config、node list、max unavailable | deterministic deployment ID、bundle、template | 候选CPU Fleet |
| Agent heartbeat / record | protocol、version、artifact、compatibility、policy、Profile、config、Node Action key | bundle、template | previous Agent |
| 节点annotation | version、artifact、config、node UID、Succeeded | bundle、template | previous节点 |
| Node Installer Reconciler | version、artifact、config、node UID、Succeeded | allowed-node wave、bundle/template identity、controller max-unavailable | 候选Reconciler执行wave；完成后切previous Reconciler |

`previous.agent_identities`必须在mutation前从ACTIVE且lease有效的真实Agent记录捕获；
同集群记录必须完全一致，节点集合必须等于目标HyperPod节点。release metadata没有
agent version和policy version，禁止从候选代码或版本号猜测。

发布期间不得再次build，也不得手工编辑Deployment、pin、generated Manifest或
`agentConfigDigest`。

### 9.2 包含配置、Profile或资源变化的开发流程

1. 明确变化属于代码扩展、生产交付或两者，并按文末选择表进入对应文档。
2. 明确组件位于CPU还是GPU、运行phase、权限、Profile owner、pin、回滚和卸载边界。
3. 修改源码、源Manifest、renderer、site schema和资源注册逻辑。
4. 补齐resources、探针、termination grace、安全上下文和负向测试。
5. 运行所需生成器，审阅generated Manifest、cleanup inventory和环境变量参考。
   PostgreSQL DDL 变化还要追加连续 schema migration；当前基线为 v18，下一版本必须
   是 v19，并通过 `make test-postgres-stress` 或 CAP-005 runner。
6. 执行第一步build并签名：

   ```bash
   COSIGN_SIGNING_KEY=/secure/release/cosign.key \
   make PYTHON=.venv/bin/python release-build \
     RUNTIME_IMAGE_REPOSITORY=<registry/repository>
   ```

   随后直接执行`release-deploy`；它默认使用第一步生成的`dist/current-*`签名制品。
   开发者只修改
   `runtimeProfile.templateSource`指向的策略模板；脚本按规范化内容自动生成不可变
   Profile版本和快照。真实策略变化时，首次部署生成计划并停止；审核后在同一条deploy上
   带审批参数重跑，审批并继续部署：

   ```bash
   gpu-fault-admin deploy \
     --state-dir /secure/gpu-fault \
     --approve-profile-plan "$(jq -er '.plan_sha256' \
       /secure/gpu-fault/release-deploy/profile-plan.json)" \
     --reference CHG-12345
   ```

   内容未变化时不需要审批记录。隐藏参数和环境变量不得替代该state审批。
7. `release-build`先执行static，再按预算并行普通pytest、PostgreSQL stress和source-only
   artifact，全部通过后执行OCI复用/构建和签名；
   `release-deploy`验签、计算生产Agent config digest、生成
   `<site目录>/profiles/<content-digest>.yaml`、原子准备`site.yaml`，然后执行
   `deploy -> verify -> stability -> release-summary`。报告分别保存为
   `verification-report.json`、`stability-report.json`和`release-summary.json`；
   不会在同一次发布中重复执行
   全量`status`。组件diff明确为`NOOP`时，即使release ID因delivery identity变化，
   `deploy`阶段仍记录
   `SKIPPED_NOOP`并直接进入并行verify；任何不确定性都回退完整deploy。实际滚动范围
   仍由区域release diff自动分类为
   `NOOP/CONTROL_PLANE_ONLY/DATA_PLANE_COMPATIBLE/FULL`。
8. 在staging按变更范围补充验证`join-cluster/remove-cluster/uninstall`，并使用低层
   `plan/upgrade/resume/rollback`演练失败续跑和回滚，不以
   `kubectl rollout undo`代替区域回滚。
9. 在同一PR提交源码、源Manifest、生成物、测试、管理员文档和证据说明。

发布状态和site备份位于：

```text
<site目录>/release-deploy/<release-id>/
```

该目录至少包含`plan.json`、`state.json`、`verification-report.json`、
实际变更时的`stability-report.json`和`release-summary.json`。管理员之后单独执行
`gpu-fault-admin status`时仍会重新获取
完整实时健康状态，不复用历史verify报告。

构建失败时不会修改site；部署失败时保留目标site和`FAILED`状态，在线release由既有
`autoRollback`策略处理，修复后重跑同一命令即可。

### 9.3 供应链检查

CI static作业在yamllint之后执行`make ci-supply-chain-tools`（把Makefile顶部固定版本的
pip-audit、cyclonedx-bom装进独立venv，不触碰哈希锁定环境；同时按版本号和
发布 tarball 的 SHA-256 下载 Prometheus 的 `promtool`），随后
`make promtool-check`（`scripts/check-alert-rules.py`）把`deploy/observability/amp-rules.yaml`
与`deploy/control-plane/regional/processor-alerts.yaml`（先剥掉PrometheusRule外壳）交给
`promtool check rules`——`verify-regional-alerting.py`只校验runbook/注解/聚合形状，
PromQL本身是否能解析只有promtool说了算。该目标还以固定版本的真实工具运行
Makefile声明的完整`PROMQL_TESTS`集合，
要求完整成功的 pytest 回执。这两组测试归始终重新执行的 static 门禁所有，不复用
coverage shard 缓存；本地缺少 promtool 同样失败，不记为 skip。
`test`、`test-shuffled`、`test-parallel`和`test-parallel-release`在pytest之前执行
`promtool-preflight`；`run_release_gates`的check/release模式在昂贵门禁之前先做同一前检。
Make统一导出`PROMTOOL`，默认来自独立工具环境，显式配置仍须通过可执行性与精确版本
检查。`check-alert-rules.py --tool-only --version ...`只检查工具，不读取规则、不启动
pytest，也不把缺失工具当作可跳过。缺失或版本不符时提示受检安装入口，不自动联网安装。
该前提适用于实际运行本地测试的源码构建；只消费已签名CI制品、不跑本地测试的部署路径
不会因此要求额外工具。测试子进程仍清除签名密码和未经授权的数据库连接环境。
定向影响测试从Make的`PROMQL_TESTS`清单判断所选文件、目录或node ID是否需要该工具，
需要时在其他检查前执行同一前检，并将返回的已验证绝对路径传给实际pytest子进程；
不依赖之前某个Make子进程修改Python父进程的环境。不含PromQL的选择不新增工具依赖，
原测试选择、风险分类及独立PostgreSQL授权保持不变。
`make pip-audit-check`以`--require-hashes`审计三份出厂lock（`requirements/build.lock`、
`requirements/runtime.lock`、`requirements/deploy-host.lock`），接受的漏洞id只能写在
`requirements/pip-audit-ignore.txt`并注明修复版本。`make lazy-export-check`
（`scripts/check-lazy-exports.py`）解析每张`_EXPORTS`惰性导出表及声明的入口并逐项
导入；`make doc-facts-check`（`scripts/check-doc-facts.py`）随`make docs-check`校验声明的
文档断言与代码一致。三个`release-build*`目标在生成attestation前先执行`make sbom`，把每份
lock的CycloneDX SBOM写到`dist/sbom/`，`--sbom-dir`把各文件的SHA-256绑进cosign签名的
attestation；本地缺少工具时这些目标只打印跳过，`CI=true`下缺工具即失败。

可选 HMA CloudWatch 链路退役后，最后一份 CloudFormation 模板及其专用 cfn-lint
安装/检查目标一并删除；YAML、惰性导出、pip-audit、SBOM 和 promtool 门禁仍保留。
`generate-cleanup-inventory.py` 的 retired 资源表只生成历史清理条目，不能带 deploy
模式或重新出现在可部署 Manifest 中。候选 `preflight_retired_collectors` 在各 GPU 集群
确认旧 producer Deployment 已退役后才继续应用变更；旧队列与证据的处理顺序见运维
手册 §7.4。此处不变更 Runtime Profile 的 AWS provider 职责或任何恢复授权。

修复pip-audit报出的传递依赖时不要手改lock：`uv.lock`是唯一来源，三份lock由各自文件
头记录的命令导出。2026-09-07关闭urllib3 2.3.0的6个PYSEC条目就是这条路：urllib3是
botocore/requests/kubernetes的传递依赖，被`kubernetes==34.1.0`的`urllib3<2.4.0`卡住，
于是把`pyproject.toml`的`kubernetes>=31,<35`放宽到`<36`，用uv 0.8.12（与现有lock的导出器
一致，能逐字节复现两份export）执行`uv lock --upgrade-package kubernetes --upgrade-package
urllib3`，得到kubernetes 35.0.0与urllib3 2.7.0，并去掉kubernetes 35不再依赖的google-auth、
cryptography、cffi、pycparser、pyasn1、pyasn1-modules；然后逐份用文件头命令原样重导出：
`uv export --frozen --no-dev --no-emit-project --extra collectors --extra postgres --extra performance --format requirements-txt --output-file requirements/runtime.lock`、
`uv export --frozen --no-dev --no-emit-project --extra dev --extra collectors --extra postgres --extra performance --format requirements-txt --output-file requirements/deploy-host.lock`、
`uv pip compile --generate-hashes requirements/build.in --output-file requirements/build.lock`
（后者无urllib3，零变化）；节点侧的第四份lock用
`uv export --frozen --no-dev --no-emit-project --extra collectors --format requirements-txt --output-file requirements/node-runtime.lock`
导出，不加任何`--no-emit-package`（见部署和运维手册的节点安装一节）；`git diff`只应出现目标包及被迫一起动的依赖的版本/哈希行；每份lock
跑`pip-audit --require-hashes`归零后删掉`pip-audit-ignore.txt`里的id。`deploy-host.lock`或
`build.lock`变化会改变`dependency_identity_sha256`，因此签名的deploy-host bundle必须重建
并重新签名后才能进行下一次线上部署；`runtime.lock`变化走正常Runtime Image发布。

### 9.4 区域发布编排器是一个包；部署侧源码的覆盖率floor

区域发布编排器（rollout / rollback / join / status 等模块）是
`src/gpu_fault_release/` 包，入口模块 `src/gpu_fault_release/rollout.py`，模块间一律
`from gpu_fault_release.<module> import …` 绝对导入。它以前是
`deploy/control-plane/regional/*.py` 一堆按裸名互相导入的脚本，只有把那个目录塞进
`sys.path` 才能加载；`tests/test_release_architecture.py` 现在守住这条边界——仓库里任何
文件都不得按裸 stem 导入编排器模块，也不得把包目录塞进 `sys.path`。管理员 CLI
（`src/gpu_fault/admin/cli.py`、`site.py`、`cluster_join.py`、`cluster_removal.py`）和
`scripts/release_deploy.py` 仍按路径 exec
`deploy/control-plane/regional/rollout-regional-release.sh`；它现在是薄壳：把
`<repo>/src` 放进 `PYTHONPATH` 后 `exec python3 -m gpu_fault_release.rollout "$@"`，
argv 与环境原样透传，所以不装 wheel 的干净 checkout 照样能跑。非 Python 输入没有搬：
`deploy/control-plane/regional/generated/`、patch/prerequisites YAML、
`cleanup-inventory.json` 和 `probes/`（编排器以源码文本发给 Pod 执行，不 import）
仍在deploy树下。`scripts/component_wheels.py`的导入闭包同时追踪`gpu_fault`和
`gpu_fault_release`，release包随独立deploy-host wheel交付；非Python输入通过
`gpu_fault_release.repository_root()`从当前源码checkout或受检venv绑定的site解析，
不是复制到业务Runtime image。数据面observability的安装脚本和manifest同样通过该
locator读取，不能从wheel的`site-packages`目录按固定父级猜deploy树位置。部署机身份
`scripts/deploy_source_identity.py`的`DEPLOY_HOST_ORCHESTRATION_INPUTS`覆盖
`src/gpu_fault_release/*.py`、启动脚本和有界Job waiter，包含前置修复、数据库proof和
动态Job管理helper；`native_http`、进程监督和SNS policy helper也在deploy-host闭包中，
不进入三个业务组件wheel。共享`amp-sns-publish-policy.json`由
`config/release-identity.yaml`同时纳入Manifest输入和observability组件身份，
`bootstrap_task_inputs`还绑定该asset与`monitoring_policy.py`以使所属checkpoint失效。
数据库proof复用的`deploy/migrations/postgres-schema-preflight-job.yaml`由同一Manifest
输入规则覆盖；发往CPU Job的probe源码必须来自本次受信部署源码，不能另取未绑定脚本。

SES配置集由`spec.notifications.sesConfigurationSet`映射到低层
`notifications.ses_configuration_set`，按SES名称规则验证；
`render_notification_config_maps`是plan和CPU apply共享的结构化YAML修改入口。
所有选中CPU角色均消费同一值，未声明时显式清空，不能继承shell中的通知或旧快照控制。
通知摘要在未声明该字段时保持旧格式；回滚优先使用真实捕获的旧ConfigMap和各角色env。
preflight只查询声明的既有SES配置集并验证名称与发送状态，不创建资源或扩展权限。

`probes/workflow_safety.py` 是发布预检的 `workflow_safety` 门：
`PENDING`/`SAFETY_PENDING`/`RUNNING`/`BLOCKED` 的破坏性 workflow 默认计为
`blockers`。只有 `resolved_blocked`、`abandoned_generation`、`compile_blocked`
和 `settled_incident_blocked` 各自的完整安全谓词成立时才可排除；后两种还由
dispatcher 清扫关闭。`settled_incident_blocked` 要求 incident 已 `RECOVERED`，
不能将 `ESCALATED` 当成恢复；现存 owner、未到期 lease、source plan、未结 remote
command、仍占用节点或未确认节点/provider动作均不能只凭 incident 终态释放占用。
探针与运行时谓词必须保持一致，
由 `tests/regional/test_release_workflow_safety.py` 验证。源码快照和 deploy-host
交付不改变这些运行时安全条件。

`config/ci-unit-gate.json`（schema 4）的`coverage.sources`列出五个被测源码根：
生产范围为 `src/gpu_fault`、`src/gpu_fault_release`、`deploy/control-plane/tools`，
runner 范围为 `scripts/e2e/regional`、`tools`。两个范围独立统计和强制95%语句/分支；
生产范围的78%组合floor及原 per-module floor 保留。两个部署专用根同时
出现在`coverage.deployment_only_sources`里，只由`deployment` shard测量（runtime、
fault_runner、postgres shard的`source`里根本没有这两个根，因此它们的身份和floor不受
部署侧源码变化影响；非deployment shard的数据里若出现这两个根的文件，`verify_coverage_data`
直接拒绝）。测试像导入任何包一样 `from gpu_fault_release import …`，coverage按路径记录。
`deploy/control-plane/regional/probes/*.py`不在这五个源码根的floor内，但不能据此认为
只需AST校验。`test_store_io_zero_view_probe`实际执行发往Pod的标准库脚本，以替换的
urllib传输覆盖合法、不完整、畸形及读取失败场景；其他探针也须按风险补行为测试。

Store-I/O清警等待只接受完整零视图：聚合器必须唯一、无标签地报告degraded=0和
整数process-count=1..16；有界process slot数量须匹配，每个slot恰有capacity、
deadline、backend_unavailable三个有限非负零counter。slot可以不连续，既有process_id
可以并存，但不能替代slot或把重复slot/reason当不同序列。未知、缺项、重复、非零、
畸形或超过8MiB的响应均拒绝，HTTP响应在各路径关闭且不回显原始数据。
旧版合并counter格式不足以证明完整性，不据此授权快速清警等待；这只约束已有的
transient critical收敛分支，不改变一般回滚、无critical路径及既定等待/稳定窗口。

`regional_release_interfaces` 为快照、CPU rollout 和 GPU rollout 提供窄 Protocol，
升级/回滚选项及节点集合使用显式类型，关键边界由 `RegionalRelease` 的类型化方法委托
原实现。JSON 在原持久化入口继续运行时验证；TypedDict 不替代验签、状态校验或回滚屏障。

部署侧源码的每个模块必须属于一个`coverage.module_floors`族
（`tests/test_ci_unit_gate.py::test_module_floors_cover_every_deployment_only_source_file`
守卫）：`regional-release-orchestrator`（`src/gpu_fault_release/regional_release_*.py`、
`rollout.py` 与 `__init__.py`）、`regional-deployment-support`（其余按名字列出的
`src/gpu_fault_release/regional_*.py`）、`control-plane-tools`
（`deploy/control-plane/tools/*.py`）。floor取自首次测量：族floor是测得值向下取整再减2，
文件floor是族内最低文件向下取整，目的是让数字不再下滑，而不是宣称达标。提高floor的做法：跑
`make coverage-shard COVERAGE_SHARD=deployment COVERAGE_SHARD_ROOT=/tmp/x`，用
`coverage json`（`source`写三个根）生成报告，`python scripts/ci_coverage_gate.py module-floors
--coverage-json <报告>`确认通过后把新的整数写进对应族；只能上调。新增
`gpu_fault_release` 模块时把它加进`regional-deployment-support`的`globs`（或新建族），
否则该守卫测试会失败。

### 9.5 mypy 收敛方向

`mypy-baseline.json`按（文件, 错误码）逐项 ratchet，只能阻止增长，不表达"先修哪里"。
`mypy-convergence.json`补上方向：按目录给出严格错误数的上限（`ceiling`）、优先级和理由，
当前四个目录按优先级依次是 `src/gpu_fault/store`、`src/gpu_fault/orchestration`、
`src/gpu_fault/app`、`deploy`——它们承载了基线里绝大多数 `no-untyped-def` / `type-arg` /
`no-any-return`，也正是"dict 形状写错"作为主要故障模式的三层加回滚路径。规则：某目录的
总数超过上限即失败（提示是修该目录的错误，不是抬上限）；低于上限不算 slack，
`python scripts/check-mypy-baseline.py --write-baseline` 会把上限收紧到当前值且永不回升；
`--report` 打印各目录 `当前/上限（理由）`。加目录只需在该 JSON 里加一行，上限用当前基线
总数起步。
