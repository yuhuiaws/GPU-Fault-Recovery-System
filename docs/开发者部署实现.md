# GPU 故障处理系统开发者部署实现

本文是生产交付契约，只面向修改方案源码、生产 Manifest、renderer、配置模型或资源
生命周期的开发者。新增 operation、channel、Store、路由、插件或指标先阅读
[扩展指南](扩展指南.md)；扩展需要进入生产时再执行本文。

管理员部署现有 release 时使用[管理员快速部署](管理员快速部署.md)和
[管理员日常运维](管理员日常运维.md)，不阅读本文逐个 apply 方案资源。
管理员和客户不编写方案 Manifest；客户自己的训练 workload YAML 是明确例外。

## 1. 支持边界与正常入口

唯一生产拓扑是区域 CPU EKS/HyperPod 控制面、Aurora PostgreSQL、TLS NLB 与一个或
多个 `NodeRecovery=None` 的 HyperPod EKS GPU 集群。通用 Kubernetes、Slurm 和
CPU/GPU 单集群一体化不是新生产功能的交付目标。

正常管理员入口是：

```bash
gpu-fault-admin preflight -f /secure/gpu-fault/site.yaml
gpu-fault-admin deploy -f /secure/gpu-fault/site.yaml
gpu-fault-admin verify -f /secure/gpu-fault/site.yaml
gpu-fault-admin status -f /secure/gpu-fault/site.yaml
gpu-fault-admin join-cluster -f /secure/gpu-fault/site.yaml \
  --gpu-cluster-arn <existing-gpu-eks-or-hyperpod-arn>
gpu-fault-admin remove-cluster -f /secure/gpu-fault/site.yaml \
  --cluster-id <cluster-id> --confirm REMOVE_GPU_CLUSTER
gpu-fault-admin uninstall -f /secure/gpu-fault/site.yaml \
  --cpu-cluster keep --confirm UNINSTALL_GPU_FAULT
```

`resume`和`rollback`仍是低层区域编排器命令。开发者可以在staging和break-glass验收
中使用它们，但不得把低层 release JSON 写成管理员日常事实源。高层
`join-cluster`必须从`site.yaml + GPU ARN`进入持久状态机。

## 2. 角色与事实源

| 角色 | 维护内容 |
|---|---|
| 管理员 | `site.yaml`、仓库外Secret引用、已有集群/AWS输入、审批和验收证据 |
| 开发者 | 源代码、源Manifest、renderer、site schema、生命周期契约、测试和文档 |
| 自动化 | 私有临时release JSON、generated Manifest、构建期cleanup inventory和运行时注册表 |
| 客户 | 自己的训练workload YAML；不修改本方案Manifest |

管理员不维护 `regional-release.json`。CLI从`site.yaml`在`0700/0600`临时目录生成
低层配置；直接release JSON和`regional-env.sh`只用于详细手工流程或break-glass。

生产资源有三层事实源：

| 层级 | 事实源 | 作用 |
|---|---|---|
| Kubernetes | 每个CPU/GPU EKS的`gpu-fault-installed-resources` | 卸载实际安装的workload、RBAC和namespace资源 |
| 节点 | `/opt/gpu-fault/installed-units.txt`及AgentRecord摘要 | 卸载实际安装的systemd unit |
| AWS | Aurora中的`installation_resource`对象 | 记录ARN/ID、ownership、delete policy、依赖和状态 |

不得新增第二份手工Kubernetes、unit或AWS资源清单。

## 4. 配置、Profile与Release契约

新增配置必须先确定唯一事实源：

- 区域拓扑、身份、制品引用和健康目标进入`RegionalSite`/`site.yaml`；
- Runtime Profile策略进入版本化Profile YAML，同一`profile_version`内容不可覆盖；
- CPU非敏感配置进入按领域拆分的ConfigMap；
- token、密码和私钥进入Kubernetes Secret、Secrets Manager或仓库外受控文件；
- 节点配置由Installer生成`/etc/gpu-fault/*.env`。

### 4.1 Runtime Profile的作用

Runtime Profile不是普通参数文件，而是区域控制面对“谁可以执行哪类能力”的授权和
路由契约。策略引擎先产生恢复意图，workflow再通过Profile决定该能力是仅观察、由本方案
执行还是委托给其他实现。

Profile分成两类文件：

| 文件 | 维护者 | 作用 |
|---|---|---|
| `runtimeProfile.templateSource` | 开发者 | 唯一可编辑策略模板 |
| `runtimeProfile.source` | `release-deploy` | 按策略内容生成的不可变快照 |

开发者不得直接修改`source`快照、`site.yaml`中的Profile版本或Agent config digest。
`release-deploy`根据模板内容自动生成版本、快照和相关site字段。

Profile在区域控制面按`profile_version`只注册一次，并由所有引用该版本的GPU集群共享。
修改Profile影响的是整个站点中使用新版本的训练任务和节点，不是某一个注册锚点集群。

### 4.2 Profile字段与模式

| 字段 | 含义 | 修改规则 |
|---|---|---|
| `cluster_id` | 首次注册时使用的稳定锚点 | 模板保留占位符；发布器从site注入，不随GPU集群增删改变 |
| `environment` | Profile适用的编排环境 | 当前生产固定为`hyperpod-eks` |
| `profile_version` | 不可变策略版本 | 模板值不作为发布版本；由内容摘要自动生成 |
| `claims[]` | 对每个capability声明期望模式、owner和adapter | 策略变更的主要编辑位置 |
| `observed[]` | 声明owner实现是否可用及实现版本 | `OWN/DELEGATE`必须有匹配且`available=true`的事实 |

Capability mode：

| mode | 含义 | 约束 |
|---|---|---|
| `DISABLED` | 能力完全关闭，不进入effective Profile | 用于明确删除能力 |
| `OBSERVE` | 只识别、记录和通知，不允许执行动作 | 新能力和高风险能力的默认阶段 |
| `AUGMENT` | 多个检测来源共同补充证据 | 只允许非破坏性能力 |
| `OWN` | 本方案指定owner是唯一执行者 | 破坏性能力的正常生产形态 |
| `DELEGATE` | 将能力委托给外部owner | 当前生产硬约束通常禁止托管恢复委托 |

破坏性capability不能使用`AUGMENT`，也不能有两个active writer。`OWN/DELEGATE`缺少
匹配observed事实时会降级为`OBSERVE`并产生warning；统一发布入口会拒绝带warning的
Profile。

### 4.3 当前Profile中的每个capability

| capability | 当前模式/owner | 功能含义 | 何时修改及可能影响 |
|---|---|---|---|
| `gpuDetection` | `AUGMENT/hyperpod-hma` | 将HyperPod HMA的GPU故障信号补充到本方案Collector证据 | 增删检测源或HMA协议变化时修改；会改变事件来源和去重范围，不直接授权恢复动作 |
| `providerHealthIsolation` | `OBSERVE/hyperpod-hma` | 观察provider健康隔离事实 | 当前保持OBSERVE；改为执行模式可能引入第二个生命周期writer |
| `evidenceCapture` | `OWN/gpu-fault-control-plane` | 冻结事件、指标、allocation和诊断引用 | 证据存储实现或owner迁移时修改；错误配置会让workflow缺少审计证据 |
| `schedulerDrain` | `OWN/gpu-fault-kubernetes-adapter` | cordon、quarantine和恢复节点调度 | Kubernetes隔离实现变化时修改；影响节点是否可调度，属于破坏性能力 |
| `checkpointRestore` | `OWN/gpu-fault-kubernetes-adapter` | 在停训和重启前管理checkpoint相关步骤 | 接入新的训练框架checkpoint协议时修改；错误实现可能造成训练状态丢失 |
| `workloadStop` | `OWN/gpu-fault-kubernetes-adapter` | 停止当前受管训练attempt | 当前必须由本方案OWN；禁用后硬件动作前无法可靠停训 |
| `workloadRestart` | `OWN/gpu-fault-kubernetes-adapter` | 按restart budget创建新attempt | 当前必须由本方案OWN；变化会影响任务恢复和GPU数量门禁 |
| `mechanicalInspection` | `OWN/gpu-fault-kubernetes-adapter` | 让workflow进入等待人工机械检查和明确确认的步骤 | CHECK_MECHANICALS状态机变化时修改；不会自动完成实体维修 |
| `deepDiagnostics` | `OWN/gpu-fault-validation-adapter` | 执行GPU、Host和Fabric动作后验证 | 验证器或健康判据版本变化时修改；失败会阻止恢复调度 |
| `supportEscalation` | `OWN/gpu-fault-support-escalation` | 生成固定模板的支持升级记录和通知 | 接入真实工单系统或模板协议变化时修改；当前不代表外部工单已创建 |
| `diagnosticBundleCapture` | `OWN/gpu-fault-node-agent` | 收集节点日志、进程、DCGM和诊断包 | 区域生产默认启用，用于reset/fabric恢复前后的审计证据 |
| `gpuReset` | `OWN/gpu-fault-node-agent` | quiesce、无客户端检查、GPU reset和服务恢复 | 区域生产默认启用；仍受策略证据、workload、签名、fencing和动作后验证门禁约束 |
| `fabricManagerRestart` | `OWN/gpu-fault-node-agent` | 受控重启Fabric Manager并验证新PID/active状态 | 区域生产默认启用；只由固定策略和Node Agent执行 |
| `fabricReset` | `OWN/gpu-fault-node-agent` | 对节点全部GPU/NVSwitch执行完整reset barrier | 区域生产默认启用，但必须满足完整inventory、全局停训和barrier门禁 |
| `nvlinkDiagnostics` | `OBSERVE/gpu-fault-node-agent` | 执行带Link ID和固定SHA的NVLink Field Diagnostic | 工具、参数和SHA经过站点验证后改OWN；可能长时间占用GPU |
| `memoryDiagnostics` | `OBSERVE/gpu-fault-node-agent` | 执行整卡显存/ECC/row-remap诊断 | 内存诊断工具完成验证后改OWN；诊断失败通常保持节点隔离 |
| `driverRemediation` | `OBSERVE/gpu-fault-node-agent` | 执行固定命令和目标分支的GPU驱动修复 | 只有厂商结论、目标版本和命令SHA齐备时改OWN；失败可能形成部分更新状态 |
| `softwareFirmwareUpdate` | `OBSERVE/gpu-fault-node-agent` | 更新并验证GPU或相关固件 | 仅在隔离维护环境完整验收后改OWN；属于不可逆高风险动作 |
| `nodeReboot` | `OWN/gpu-fault-hyperpod-adapter` | 调用HyperPod原节点reboot并等待新incarnation | adapter协议变化或阶段D.1撤销时修改；会重启物理节点 |
| `nodeReplace` | `OWN/gpu-fault-hyperpod-adapter` | 仅执行`HEALTHY_WARM_SPARE_ONLY`本地切换 | warm-spare协议变化或阶段D.2撤销时修改；不得调用`BatchReplaceClusterNodes` |

如果把任一Node Agent能力从`OBSERVE`改为`OWN`，还必须：

1. 给claim配置正确`adapter`；
2. 在`observed[]`加入同capability/owner的`available: true`和实现version；
3. 确认Node Agent allowlist、安装参数和heartbeat实际广告该能力；
4. 完成[安全与参数参考](安全与参数参考.md)对应破坏性阶段的维护窗口验收。

### 4.4 什么时候不修改Profile

以下变化通常不改变能力授权，不修改模板：

- 普通bug修复或内部重构；
- Control Plane、Executor或Node Runtime重新build；
- wheel、bundle、Schema或protocol版本变化；
- 增删GPU节点或接入/移除GPU集群；
- 修改超时、队列、Collector周期或资源requests/limits；
- 能力owner、mode、adapter和实现version都不变的发布。

这些变化由release manifest、环境配置或Agent config digest表达。

### 4.5 Profile修改与自动发布流程

开发者只编辑`templateSource`指向的YAML，不修改site和历史快照。推荐流程：

1. 修改目标claim的`mode/owner/adapter`及对应observed事实。
2. 运行相关单元测试和Profile编译测试：

   ```bash
   .venv/bin/python -m pytest -q tests/regional/test_capabilities.py
   ```

3. 执行统一发布入口。内容未变化时不需要审批：

   ```bash
   make PYTHON=.venv/bin/python release-deploy \
     SITE=/path/to/site.yaml \
     ADMIN_EMAIL=<optional-operations-email>
   ```

4. Profile内容变化时，首次运行会在
   `<site目录>/release-deploy/profile-plan.json`输出差异并停止。审核其中的
   `change_kind`、capability变化和目标内容摘要。
5. 获得变更单或维护窗口批准后，以同一入口重跑：

   ```bash
   PROFILE_APPROVAL=CHG-12345 \
   make PYTHON=.venv/bin/python release-deploy \
     SITE=/path/to/site.yaml
   ```

6. 脚本自动：
   - 规范化claims/observed，忽略YAML顺序和`cluster_id/profile_version`；
   - 计算策略digest并生成`regional-hyperpod-<digest12>`版本；
   - 写入`<site目录>/profiles/<version>.yaml`不可变快照；
   - 更新site的`source/version`和Agent config digest；
   - 执行`make check`和组件构建；
   - 由release diff选择`FULL`发布，注册新Profile；
   - 滚动CPU、Collector、Watcher、Reconciler和Agent；
   - 执行一次verify并保存验收报告，再生成不重复健康检查的轻量release summary；
     部署或verify失败时按`autoRollback`恢复在线release。

区域 release diff 比较规范化策略摘要，而不是 Profile 文件路径或原始 YAML SHA。
`source` 从模板切换到不可变快照、字段顺序变化或注册锚点替换时，只要规范化策略与
版本不变就分类为 `NOOP`。source/template 原始 SHA 仍写入 release state，仅用于审计
和旧状态迁移。

训练提交不再手工填写Profile版本：

```bash
gpu-training-submit --site /path/to/site.yaml training.yaml
gpu-fault-workload-annotate --site /path/to/site.yaml training.yaml
```

显式`--runtime-profile-version`与`--site`同时使用时必须完全一致，否则命令拒绝提交。

新增配置还必须：

1. 更新`site.example.yaml`、schema解析、脱敏审计摘要和负向测试；
2. 更新`src/gpu_fault/data/env-inventory.json`和生成的环境变量参考；
3. 拒绝未知拼写、跨Region ARN、残留占位符和不安全Secret位置；
4. 进入`preflight`、`verify`或`status`中的至少一个可观测检查。

release manifest schema v2 包含四个独立组件：

| 组件 | 允许的运行面 |
|---|---|
| `control_plane` wheel | CPU ingress/worker/spool、schema和凭据刷新 |
| `executor` wheel | GPU Executor、Watcher、Resource/HMA Collector、Reconciler |
| `node_runtime` wheel | GPU节点systemd Agent和Collector |
| `node_bundle` | 节点安装脚本、unit模板和精确的Node Runtime wheel |

三个 wheel 必须来自同一次构建，但不得互换安装。每个组件记录物理
`wheel_sha256`和行为`module_digest`：前者识别实际文件，后者用于差异分类和
compatibility pin。Collector、Watcher、Installer和训练annotation仍必须使用同一
Runtime Profile版本。

Agent和Regional Executor分别使用 artifact SHA、compatibility digest、protocol；
Agent另有config digest。它们共同使用required/compatible两阶段pin：

1. 稳态旧版本保持required，候选版本临时加入compatible；
2. 滚动CPU和所有GPU集群，等待全部Agent精确收敛；
3. 候选提升为required并清空compatible；
4. 失败时恢复previous pin、对应组件wheel、bundle、Profile和节点artifact。

不得先切严格required pin再安装节点，也不得在Fleet未收敛时清空compatible窗口。
回滚到schema v1单wheel release时，旧Agent compatibility digest等价于旧artifact
SHA；旧进程的环境变量白名单不认识component pin，因此
`filter_legacy_release_env.py`必须在apply前结构化移除这些env，不能依靠空字符串。

区域编排器按差异分类执行：`NOOP`不滚动，`CONTROL_PLANE_ONLY`只滚CPU，
`DATA_PLANE_COMPATIBLE`只处理变化的数据面组件，`FULL`处理schema/协议/Profile等
跨面契约。新增配置字段时必须明确它应触发哪一类，不能默认把所有变化升级为全站滚动。

## 5. Kubernetes生命周期契约

运行型Deployment、DaemonSet和CronJob必须在顶层声明：

| annotation | 合法值与作用 |
|---|---|
| `gpu-fault.io/cleanup-phase` | CPU：`ingress/consumer/auxiliary`；GPU：`producer/executor` |
| `gpu-fault.io/cleanup-order` | 同一phase内的非负稳定停机顺序 |
| `gpu-fault.io/cleanup-action` | `delete/namespace/reset`，缺省为`delete` |
| `gpu-fault.io/deploy-mode` | GPU Deployment可用`regional_rollout/regional_reconciler` |

ServiceAccount、RBAC、PDB和普通Service通常推导为`support/delete`；CPU NLB Service使用
`nlb/reset`；ConfigMap、Secret和Namespace由namespace生命周期覆盖。不要为了让生成器
通过而给资源选择错误phase。

资源kind、name和scope由生成器从源YAML推导。更新入口只有：

```bash
make PYTHON=.venv/bin/python deployment-contracts-update
```

它渲染CPU三角色、生成构建期候选`cleanup-inventory.json`、验证allowlist并运行契约
测试。发布入口再按`kubectl get`的实际结果刷新CPU/GPU
`gpu-fault-installed-resources`；Manifest已删除但live对象仍存在时，旧条目保留到对象
真正删除。

提交前运行：

```bash
make PYTHON=.venv/bin/python deployment-contracts-check
```

cleanup preflight还会扫描历史namespace和cluster-scoped RBAC中的未登记
`gpu-fault-*`对象；发现out-of-band资源必须fail closed并先分类。

## 6. 节点systemd生命周期

新增unit时：

1. 模板放入`deploy/systemd/gpu-fault-*.service|timer`；
2. `install-gpu-fault-collector.sh`显式复制或渲染模板；
3. 安装完成后由脚本扫描实际unit并写入`/opt/gpu-fault/installed-units.txt`；
4. Agent在启动或清单变化时上报完整列表和SHA-256，稳定心跳只上报digest；
5. 卸载后确认unit、`/opt/gpu-fault`、`/etc/gpu-fault`和`/var/lib/gpu-fault`无残留。

至少运行：

```bash
.venv/bin/python -m pytest -q \
  tests/node_agent/test_node_deployment.py \
  tests/node_agent/test_service.py \
  tests/fleet/test_installation_inventory.py
```

## 7. AWS资源生命周期

Kubernetes cleanup registry不覆盖Aurora、NLB、ACM、Route53、SNS/SQS、AMP、IAM、SG、
subnet或其他AWS资源。新增资源必须创建`InstallationResource`记录，至少包含：

- 稳定`resource_key`和ARN/ID；
- Region和账号；
- `CREATED/EXTERNAL` ownership；
- `DELETE/DETACH/PRESERVE` delete policy；
- 依赖的其他`resource_key`；
- 非敏感attributes和状态。

部署或接管同站点遗留资源后，通过`admin_resource_registry.py`同步到Aurora
`gpu_fault_objects(kind=installation_resource)`。管理员不在`site.yaml`中手写这些
字段，也不得新增第二份AWS inventory文件。

新增AWS资源必须同时接入：

1. ARN-only bootstrap和已有`site.yaml`部署；
2. ownership标签验证和外部同名冲突fail-closed；
3. `preflight/status/verify`；
4. `remove-cluster`（若为集群专属）；
5. `uninstall`依赖排序、真实删除查询和最终残留验证；
6. registry snapshot、SHA-256和Aurora最后删除阶段。

统一卸载先导出Aurora注册表，再把条目标记为`DELETE_PENDING`。所有非Aurora资源和可选
CPU集群验证完成后才能进入`READY_TO_DELETE_AURORA`；最终
`installation-resources-final.json`必须只含`DELETED/DETACHED/PRESERVED`，且
`delete_policy_residuals=0`。

至少覆盖：

```text
tests/admin/test_admin_resource_registry.py
tests/admin/test_admin_cluster_removal.py
tests/admin/test_admin_uninstall.py
```

`cleanup_state.py`仍可用于break-glass阶段状态，但不能替代Aurora
`installation_resource`注册表。

## 8. 管理员接口完成标准

新增功能不能只提供手工`kubectl`、`aws`或`curl`片段。完成标准包括：

- 正常发布从`site.yaml`进入区域orchestrator；
- `preflight`在修改环境前检查输入、身份和依赖；
- `deploy`幂等并具有持久状态、恢复或回滚边界；
- `verify`独立只读验证真实功能，不只检查Pod Ready；
- `status`输出结构化健康、release/Profile/pin和失败原因；
- 集群专属资源进入`remove-cluster`，全站资源进入`uninstall`；
- 危险操作具有dry-run、审批、成功标准、回滚和证据；
- 新凭据具有创建、轮换、吊销、最小权限和日志脱敏定义；
- 管理员文档只描述决策和正式入口，内部细节保留在开发者文档。

新增GPU集群的正式入口是：

```bash
gpu-fault-admin join-cluster -f site.yaml --gpu-cluster-arn <gpu-arn>
```

修改该流程时必须同时维护ARN发现、候选site、提交前补偿回滚、提交后fail-forward、
Aurora资源注册和低层release JSON契约。

## 9. 修改与验收流程

### 9.1 普通代码修改后的build与部署升级

本流程适用于没有修改Profile模板、站点拓扑和AWS资源的普通代码变更。开发者只执行：

```bash
make PYTHON=.venv/bin/python release-deploy \
  SITE=/path/to/site.yaml \
  ADMIN_EMAIL=<optional-operations-email>
```

也可以预先设置一次：

```bash
export GPU_FAULT_SITE_FILE=/path/to/site.yaml
make PYTHON=.venv/bin/python release-deploy
```

脚本内部顺序固定：

1. 读取site并确认`repositoryRoot`就是当前checkout，拒绝猜测其他仓库或站点。
2. 比较Profile template、当前不可变快照和线上Profile SHA；普通代码修改应判定为
   `UNCHANGED`，不需要`PROFILE_APPROVAL`。
3. 运行完整`make check`，包括格式、mypy、架构、文档、Manifest、Shell/YAML、
   artifact和全量pytest门禁。
4. 构建同一release ID下的Control Plane、Executor、Node Runtime三个wheel及Node
   bundle，写入`dist/current-release.json`。
5. 使用生产Node Agent配置重新计算config digest，并原子更新site中的release声明。
6. 目标与线上release ID相同时，先执行轻量`release-summary`。只有报告无错误且
   `next_deploy=NOOP`才记录`deployment.status=SKIPPED_NOOP`并跳过deploy内的
   preflight和NOOP verifier；显式邮件更新、状态缺失、分类异常或非NOOP都回退完整路径。
7. 完整路径执行`gpu-fault-admin deploy`，由它自动preflight并按差异执行最小滚动：

   | 代码变化 | 典型分类 | 实际动作 |
   |---|---|---|
   | 没有行为内容变化 | `NOOP` | 快速路径不滚动，只运行一次最终verify |
   | 仅Control Plane闭包变化 | `CONTROL_PLANE_ONLY` | 只滚CPU ingress/worker/spool |
   | Executor或Node Runtime兼容变化 | `DATA_PLANE_COMPATIBLE` | 只滚受影响GPU数据面或节点Agent |
   | Schema、协议、Agent配置、Profile或集群集合变化 | `FULL` | 建立兼容窗口并执行跨面两阶段升级 |

8. 数据面变更时最多并行处理4个独立GPU集群；单集群内部仍按Endpoint/DCGM、
   Executor、Reconciler、Agent顺序收敛。
9. 所有Agent收敛后将候选pin提升为required并清空compatible。
10. 自动执行一次独立`verify`；各健康领域最多8路并行、报告顺序保持稳定，并原子保存
    `verification-report.json`。
11. 执行低层`release-summary`，只读取release state、wheel/Profile引用和
    `next_deploy`分类，不再次查询AWS、Aurora、NLB、AMP或完整集群健康。
12. 将轻量摘要保存为`release-summary.json`后标记`COMPLETED`。摘要生成异常记录为
    `completion_warnings`，不得把已经通过verify的在线部署误标为失败。

失败行为：

- `make check`失败：不修改site或集群；
- preflight失败：不开始滚动；
- 升级失败且`autoRollback=true`：恢复上一稳定制品、pin和Profile；
- 首次bootstrap失败并进入`bootstrap-cleaned`：CPU/GPU Deployment已缩容到0且旧集群
  进度失效；重跑同一deploy必须重新部署CPU控制面，不得把0副本判定为CPU已就绪；
- verify失败：状态写入`FAILED`，不得宣称上线成功；
- release summary失败：保留`COMPLETED`和已签入的verify证据，同时写入
  `release_summary.status=UNAVAILABLE`与`completion_warnings`；
- 修复后重跑同一条`make release-deploy`，脚本按持久状态幂等续跑。

发布期间不得再次build，也不得手工编辑Deployment、pin、generated Manifest或
`agentConfigDigest`。

### 9.2 包含配置、Profile或资源变化的开发流程

1. 明确变化属于代码扩展、生产交付或两者，并按文末选择表进入对应文档。
2. 明确组件位于CPU还是GPU、运行phase、权限、Profile owner、pin、回滚和卸载边界。
3. 修改源码、源Manifest、renderer、site schema和资源注册逻辑。
4. 补齐resources、探针、termination grace、安全上下文和负向测试。
5. 运行所需生成器，审阅generated Manifest、cleanup inventory和环境变量参考。
6. 使用统一发布入口：

   ```bash
   make PYTHON=.venv/bin/python release-deploy \
     SITE=/path/to/site.yaml \
     ADMIN_EMAIL=<optional-operations-email>
   ```

   也可以预先设置`GPU_FAULT_SITE_FILE`后直接运行`make release-deploy`。开发者只修改
   `runtimeProfile.templateSource`指向的策略模板；脚本按规范化内容自动生成不可变
   Profile版本和快照。真实策略变化必须在同一命令提供审批引用：

   ```bash
   PROFILE_APPROVAL=CHG-12345 \
   make PYTHON=.venv/bin/python release-deploy \
     SITE=/path/to/site.yaml
   ```

   内容未变化时不需要`PROFILE_APPROVAL`。
7. 该入口自动执行完整`make check`、重建三个组件和Node bundle、计算生产Agent config
   digest、生成`<site目录>/profiles/<content-digest>.yaml`、原子准备`site.yaml`，然后
   执行`deploy -> verify -> release-summary`。其中verify报告和轻量摘要分别保存为
   `verification-report.json`和`release-summary.json`；不会在同一次发布中重复执行
   全量`status`。同release ID且分类明确为`NOOP`时，`deploy`阶段记录
   `SKIPPED_NOOP`并直接进入并行verify；任何不确定性都回退完整deploy。实际滚动范围
   仍由区域release diff自动分类为
   `NOOP/CONTROL_PLANE_ONLY/DATA_PLANE_COMPATIBLE/FULL`。
8. 在staging按变更范围补充验证`join-cluster/remove-cluster/uninstall`，并使用低层
   `plan/upgrade/resume/rollback`演练失败续跑和回滚，不以
   `kubectl rollout undo`代替区域回滚。
9. 在同一PR提交源码、源Manifest、生成物、测试、管理员文档和证据说明。

发布状态和site备份位于：

```text
<site目录>/release-deploy/<release-id>/
```

该目录至少包含`plan.json`、`state.json`、`verification-report.json`和
`release-summary.json`。管理员之后单独执行`gpu-fault-admin status`时仍会重新获取
完整实时健康状态，不复用历史verify报告。

构建失败时不会修改site；部署失败时保留目标site和`FAILED`状态，在线release由既有
`autoRollback`策略处理，修复后重跑同一命令即可。
