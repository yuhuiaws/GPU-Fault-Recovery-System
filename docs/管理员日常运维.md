# GPU 故障处理系统管理员日常运维

本文从站点首次上线验收完成后开始，按“任务或症状”组织，不要求管理员理解内部模块
调用链。首次建站或应用层重建见[管理员快速部署](管理员快速部署.md)；底层命令、安全
理由和特殊恢复步骤保留在[部署和运维手册](部署和运维手册.md)。

## 1. 常用任务入口

| 任务 | 正常入口 | 详细参考 |
|---|---|---|
| 首次部署或应用层重建 | [管理员快速部署](管理员快速部署.md) | 一条 `deploy`、训练smoke和上线证据 |
| 查看区域健康 | `gpu-fault-admin status --state-dir ...`；完整只读验收（TLS、Agent/Collector、NLB、Aurora、告警）加 `--full` | REG-8、REG-14 |
| 升级全部已纳管集群 | `gpu-fault-admin deploy --state-dir ...`（一个参数；ARN、邮箱、Grafana 都从 state-dir 恢复） | REG-8.1.3/8.1.4、§4 |
| 中断后续跑 | 原样重跑同一条 `deploy --state-dir ...`；没有单独的 `resume` | REG-8.1.4、§4 |
| 回滚到上一已提交 release | `gpu-fault-admin deploy --state-dir ... --rollback` | REG-8.1.4、REG-8.2、§4 |
| 调整管理员配置 | `gpu-fault-admin config --state-dir ... [--file F] [--dry-run] --reference ...` | [管理员容量配置](管理员容量配置.md) |
| 审批待发布Profile计划 | 同一条 `deploy --state-dir ... --approve-profile-plan <plan_sha256> --reference ...`；没有单独的审批动词 | [Runtime Profile变更审批](管理员Profile变更审批.md) |
| 跨 schema 版本的发布 | `deploy --state-dir ... --accept-schema-change`（先拍 Aurora 快照；`--accept-schema-change-without-snapshot` 跳过快照） | §4.7 |
| 接入 GPU 集群 | `deploy --state-dir ... --gpu-cluster-arn <新ARN>`（比站点多出的 ARN 即为接入），或等价别名 `gpu-fault-admin join-cluster --state-dir ... --gpu-cluster-arn ...`（一个 release 内完成） | REG-8.1.5、§5 |
| 移除 GPU 集群 | `gpu-fault-admin remove-cluster --state-dir ... --gpu-cluster-arn <ARN> --confirm REMOVE_GPU_CLUSTER` | REG-8.1.6、REG-12、§5 |
| 重装但保留 CPU/GPU EKS | `gpu-fault-admin uninstall --state-dir ... --cpu-cluster keep --confirm UNINSTALL_GPU_FAULT` 后重新 `deploy`；keep 默认保留 Aurora（历史 incident/workflow 不丢），只有显式 `--reset-database` 才清库 | §3 |
| 永久退役且删除 CPU 集群 | `gpu-fault-admin uninstall --state-dir ... --cpu-cluster delete --confirm DELETE_CPU_CONTROL_PLANE`（`--aurora-final-snapshot retain|skip` 决定最终快照） | REG-13、§3 |
| 排查命令 PENDING/LEASED、Pod 不 Ready、证书/Agent 版本漂移 | `gpu-fault-admin status --full`（原 `doctor` 设想已并入 status），再按症状表 | §7、REG-14.2/14.3 |
| 轮换 cluster token | `gpu-fault-admin rotate-token --state-dir ... --gpu-cluster-arn <ARN>`（一条命令完成 registry 重叠窗口、GPU Secret、数据面滚动和节点 Agent 切换） | §6.1、REG-9 |
| CHECK_MECHANICALS 后提交明确处置 | `gpu-fault-admin submit-remediation --state-dir ... --incident-id ... --disposition {inspected,reset-gpu,reboot-node,quarantine} [--plan]` | §9、REG 8.3 |
| 数据迁移 | `gpu-fault-store-migrate` 加停写状态机 | §10 |
| 归档并删除过期 incident/workflow | 默认**关闭**；在 `site.yaml` 声明 `spec.retention` 后重跑 `deploy --state-dir ...` | §10 |
| 收敛已恢复但仍为BLOCKED的历史workflow | `gpu-fault-admin workflow-reconcile --state-dir ... --dry-run` 看计划，去掉 `--dry-run` 加 `--reference` 一次执行 | §10.2 |
| 节点失败域（机架/instance group）映射供修复预算限流 | 自动：`deploy`/`join-cluster`/`remove-cluster` 渲染并 apply；只读查看用 `gpu-fault-admin failure-domain-map --state-dir ... [--output ...]` | §5.1 |
| 处置一条 AMP 告警 | 按告警名进入分诊卡 | §8 |

所有管理员命令均通过`state-dir`恢复内部site，不要求site、artifact或release JSON路径。
续跑就是原样重跑 `deploy --state-dir`，回滚就是同一条命令加 `--rollback`；任何路径都不得
依赖当前默认kubectl context。

## 2. Runbook 固定格式

任何新增管理员 runbook 都必须包含以下七项：

1. **适用条件**：什么状态下允许执行。
2. **影响范围**：CPU、哪些 GPU 集群、训练任务和外部资源会受影响。
3. **只读检查**：执行前必须满足的门禁和预期输出。
4. **执行命令**：唯一正式入口，默认 dry-run 时必须说明。
5. **成功标准**：不能只以进程退出码或 Pod Ready 判断。
6. **回滚**：恢复顺序、状态文件和不可逆边界。
7. **证据**：变更单、release/profile、命令输出和最终状态。

不得把“扩大权限、关闭 TLS、删除 fencing、修改终态记录”写成排障步骤。

### 2.1 容量配置

普通容量变化不重新build代码，也不发布Aurora动态revision。编辑
`<state-dir>/admin-config.yaml`后执行一条命令：

```bash
# 先看会改什么：只读本地文件，不验签、不连集群、不写任何状态
gpu-fault-admin config --state-dir /secure/gpu-fault --dry-run

# 应用；--reference 可选，缺省记录为“执行者身份:开始时间”
gpu-fault-admin config --state-dir /secure/gpu-fault --reference CHG-12345
```

命令自动记录执行者身份（STS caller ARN）、变更前后配置和结果到
`<state-dir>/admin-config/history/<开始时间>-<配置摘要>/`。该路径复用当前签名镜像和
wheel，先下发Aurora容量变更，再只滚受影响的ingress、control-worker或spool-worker，
最后等待Aurora扩容到位。中断后以相同命令重跑即续跑。完整字段、模板、首次部署和回滚
语义见[管理员容量配置](管理员容量配置.md)。

## 3. 完整卸载或永久退役

**适用条件**

- 已停止新的训练提交，活动 workflow、remote command 和节点隔离状态满足清理门禁；
- `state-dir`中的内部site包含当前全部受管GPU集群；
- 执行身份仍能访问 CPU/GPU Kubernetes API 和注册表中的 AWS 资源。

**影响范围**

- 两种模式都卸载 CPU/GPU 侧本方案组件、节点 systemd、NLB、方案 IAM/监控/PKI 和
  方案专属网络对象；
- 所有 GPU EKS/HyperPod 和客户训练 workload 始终保留；
- `--cpu-cluster keep` 是**重装**：保留 CPU EKS/HyperPod，也保留方案专属 Aurora
  （站点的 incident/workflow/注册表记录；GPU 节点上的隔离 taint 以其中的 incident id
  为键）。下一次 `deploy` 接管这套已有 Aurora（CPU-2），记录不丢失。只有显式加上
  `--reset-database` 才连 Aurora 一起删除，让下一次 `deploy` 从空库开始；
- `--cpu-cluster delete` 是**退役**：删除 CPU EKS/HyperPod（不删除其外部 VPC）和
  Aurora，默认保留一份最终快照作为审计证据；`--aurora-final-snapshot skip` 只对
  `delete` 有效，与 `keep` 同用会被拒绝。

卸载依赖三层资源事实源：

| 清单 | 位置 | 用途 |
|---|---|---|
| Kubernetes安装清单 | 每个CPU/GPU EKS的`gpu-fault-system/gpu-fault-installed-resources` | 删除实际安装的workload、RBAC、Secret、ConfigMap和namespace |
| 节点安装清单 | `/opt/gpu-fault/installed-units.txt`，摘要和完整列表同步到Aurora AgentRecord | 卸载实际安装的systemd unit |
| AWS方案资源注册表 | Aurora `gpu_fault_objects`中的`installation_resource` | 记录ARN/ID、`CREATED/EXTERNAL`、`DELETE/DETACH/PRESERVE`和依赖 |

**执行命令**

```bash
# 重装：保留 CPU 集群和 Aurora 记录，之后直接重新 deploy
gpu-fault-admin uninstall \
  --state-dir /secure/gpu-fault \
  --cpu-cluster keep \
  --confirm UNINSTALL_GPU_FAULT

# 重装但从空库开始：显式删除 Aurora（默认仍保留一份最终快照）
gpu-fault-admin uninstall \
  --state-dir /secure/gpu-fault \
  --cpu-cluster keep \
  --reset-database \
  --confirm UNINSTALL_GPU_FAULT

# 永久退役 CPU 控制面
gpu-fault-admin uninstall \
  --state-dir /secure/gpu-fault \
  --cpu-cluster delete \
  --aurora-final-snapshot retain \
  --confirm DELETE_CPU_CONTROL_PLANE
```

**成功标准**

- CPU 和每个 GPU EKS 的 `gpu-fault-installed-resources` 以及方案 namespace 不存在；
- 所有注册表 `DELETE`/`DETACH` 条目经真实 AWS 查询确认不存在；
- `PRESERVE` 条目仍存在，尤其是所有 GPU EKS/HyperPod，以及不带
  `--reset-database` 的 `keep` 模式下的整套 Aurora（cluster、writer/reader、托管
  主密码、subnet group/SG/参数组）；
- `uninstall/state.json` 为 `COMPLETED`；
- `uninstall/installation-resources-final.json` 的 `delete_policy_residuals` 为 `0`；
- 输出里的 `aurora_cluster` 与所选模式一致：`keep` 为 `preserved`，
  `keep --reset-database` 和 `delete` 为 `deleted`。

Aurora 中的 AWS 注册表必须在卸载开始时先导出。非 Aurora 资源和可选 CPU 集群验证
完成后才进入 `READY_TO_DELETE_AURORA`。`keep` 模式在这一阶段只核对整套 Aurora 仍然
存在并标记 `PRESERVED`；`--reset-database` 和 `delete` 模式才把 Aurora cluster 及其
因依赖只能后删的 subnet group/SG/集群参数组 `<集群名>-pg`
（`aws/aurora/parameter-group`）作为最后一个销毁阶段。Aurora 删除后，带 SHA-256
的外部最终快照是本次退役证据，不再依赖已经销毁的数据库。

固定顺序为：

1. 导出Aurora注册表，将待删条目标记为`DELETE_PENDING`。
2. 停止新请求并排空队列，卸载节点unit和CPU/GPU Kubernetes对象。
3. 确认两侧installed-resource ConfigMap、注册对象和方案namespace已不存在。
4. 按依赖删除NLB/listener/target group、DNS、PKI、监控、IAM和方案专属网络资源。
5. 按`--cpu-cluster`保留或删除CPU EKS/HyperPod，并再次确认所有GPU集群存在。
6. 写出`installation-resources-pre-aurora-delete.json`；`keep`模式到此核对Aurora
   仍在，`--reset-database`/`delete`模式才删除Aurora stack。
7. 写出带SHA-256的`installation-resources-final.json`并确认残留为0。

**失败续跑**

直接以完全相同的参数重跑命令。`uninstall/state.json`、Aurora 导出清单和
`kubernetes-cleanup.json` 会被复用；删除 API 都按幂等方式执行。不要删除
`uninstall/` 状态目录后手工续跑。

旧线上版本没有 `/v1/installation-resources` 时不需要改走手工流程。CLI 会从同站点
bootstrap state、live NLB 和 AWS 标签重建清单，并利用运行中控制面 Pod 的现有
Aurora 连接直接回填注册表。只有所有权证据缺失或冲突时才中止。

旧版注册表中标成`REUSED/PRESERVE`的方案专属IAM、SG、PKI、监控或LBC不会继续保留；
卸载器按同站点遗留资源处理。Aurora 的去留只由模式决定（`keep` 保留，
`--reset-database`/`delete` 删除），与注册表里的旧策略无关。只有EKS/HyperPod、
外部公共subnet、VPC IGW、OIDC Provider和预装Pod Identity Agent等集群基础能力可继续
`PRESERVE`。

`uninstall` 只从 `--state-dir` 下的 `site.yaml` 读取站点；没有内部 site 的目录不是
受管站点，命令会直接拒绝。

## 4. 区域升级

**适用条件**

- 配置包含全部已纳管 GPU 集群；
- remote command 的 `PENDING/LEASED/WAITING` 为 0；
- `gpu-fault-aurora-credential-refresh` CronJob 能跑通：deploy 与 rollback 都会先
  同步跑它一次（`create job --from=cronjob`，等 Complete，默认 300 秒），Job 不
  Complete 就 fail closed，不滚任何组件；
- Runtime Profile内容未变化，或已按本节生成并独立审批新的计划。
- 若变更涉及 `ddl*.py`、Processor claim/retry/completion 或 PostgreSQL pool，
  CAP-005 runner 已在隔离 PostgreSQL 16 database 上零 skip 通过。

**只读检查**

**执行命令**

```bash
gpu-fault-admin deploy --state-dir /secure/gpu-fault
```

已有站点只需这一个参数：CPU/GPU ARN 和管理员邮箱从 `site.yaml` 读取（再传 ARN 时必须与
纳管集合一致或是其超集，见 §5）。`deploy` 根据 live release state 自动选择 bootstrap 或 upgrade。
命令第一分钟内先检查 SNS 订阅是否已确认（`spec.notifications.channel: ses` 的站点还检查 SES 发件身份）；线上事务停在
`failed/partial-convergence` 而候选是另一个 release、或候选跨 schema 版本时，发布构建一结束
就用引擎原话拒绝并指明要加的参数（`--supersede-failed-transaction` / `--accept-schema-change`），
命令行参数优先于残留的环境变量。
当前 PostgreSQL schema 基线为 v12（`store-review-hot-query-indexes`：6 个热查询/指标覆盖索引，删除被取代的 `gpu_fault_remote_command_workflow`）；schema 变化必须分类为 `FULL`，并且只能fail-forward 发布：在 deploy 命令上加 `--accept-schema-change`（§4.7），不要改 `site.yaml`。`deploy` 的 schema 阶段
（`deploy/control-plane/tools/ensure-postgres-schema.sh`，附录 A 的单集群 `deploy.sh` 同序）在滚动
业务进程之前按顺序运行三个一次性 Job，任一失败即停止，不会滚动：

1. `gpu-fault-postgres-index-build`（`gpu-fault-store-migrate --build-indexes-concurrently`）：
   对代码声明但库里缺失或无效的索引逐条执行 `CREATE INDEX CONCURRENTLY`，见 §4.2。
2. `gpu-fault-postgres-schema-ensure`（`--ensure-schema`）：幂等 DDL 与迁移登记，把
   `gpu_fault_schema_migrations` 推进到 wheel 要求的版本。索引已由上一步建好，这里只是跳过。
   自 v12 起这一步在"没有变化"时不再拿任何表锁：每条 `CREATE INDEX` / `ADD COLUMN` /
   触发器 / `ENABLE TRIGGER` 都先查系统目录再决定是否执行（裸的 `IF NOT EXISTS` 形式在索引已存在时
   仍会对表拿 ShareLock 直到事务提交，`ALTER TABLE` 则是 ACCESS EXCLUSIVE），`partition_id`
   清扫只在库版本 < 5 时运行。忙时段部署不再因为一次例行 ensure 阻塞全部写入或撞上 `lock_timeout`。
3. `gpu-fault-postgres-schema-preflight`（`--schema-preflight`，只读）：见 §4.3 的门禁清单，
   JSON 报告打印在部署日志里。

不能让 Pod 启动时自行 DDL：`GPU_FAULT_POSTGRES_AUTO_SCHEMA_INIT` 必须保持 `false`。

`deploy` 把快验证据写到 `<state-dir>/quick-validation.json`（`<state-dir>` 就是放
`site.yaml` 的受管状态目录，不在 `release-deploy/<release_id>/` 下；发布驱动在
部署完成后原地写入线上 release state 摘要，模式 0600，判定为不可复用的证据会被删除
而不是留下）。随后的 `gpu-fault-admin status --full`——无论用 `--state-dir` 还是 `-f`
指定站点——都从同一路径读取它，复用刚刚跑过的只读校验（control plane role split
和每个 GPU 集群的 data plane executor 探针），并在报告里列出
`reused_validation_checks`。复用有硬条件：release id、交付摘要、site 身份和线上
release state 摘要必须全部一致，且证据不超过 10 分钟；任何一项不满足就重新执行探针，
并在 `validation_evidence_fallback` 里给出原因。不带 `--full` 的 `status` 只跑
`cpu_workloads` 与 `control_api` 两项轻量检查（`health_scope: quick`），根本不涉及
这些探针；发布驱动内部的 verify 门禁不复用证据——要门禁就跑探针。

`status` 先在 stderr 打五行给人看的摘要（healthy 是否、线上 release id 与 phase、
下一次部署分类、失败检查名、JSON 去向），再把完整 JSON 原样输出到 stdout；脚本照旧解析
stdout。
安装资源登记（installation resource registry）的同步也不再挡在 `deploy` 的返回码上：
它在发布 commit 之后由发布驱动执行，失败只记为 `state.json` 里的
`installation_registry.status=UNAVAILABLE` 和一条 `completion_warnings`，发布本身仍是
`COMPLETED`。

若命令因Runtime Profile策略变化停止，停止信息已打印
`<state-dir>/release-deploy/profile-plan.json`的审核字段、真实`plan_sha256`和续跑
命令。审核并取得变更单批准后，原样执行该续跑命令（只替换变更单号）：

```bash
gpu-fault-admin deploy \
  --state-dir /secure/gpu-fault \
  --approve-profile-plan <plan_sha256> \
  --reference CHG-12345
```

该命令先审批再继续同一部署，没有单独的审批动词。`--approve-profile-plan`只接受
当前待审批计划的摘要，没有计划或摘要不一致时拒绝并给出当前待审批摘要。审批绑定
具体计划和live baseline；计划漂移会废止旧审批并重新停止打印新摘要，失败续跑不需要
重复审批，成功后活动记录被消费且不能重放。

| 分类 | 实际动作 |
|---|---|
| `NOOP` | 不上传、不迁移、不滚动，只运行 CPU/GPU verifier |
| `CONTROL_PLANE_ONLY` | 只上传 Control Plane wheel并滚动CPU三层角色 |
| `DATA_PLANE_COMPATIBLE` | 只上传变化的Executor/Node制品，按GPU集群顺序推进 |
| `FULL` | schema、协议、Agent配置、Profile或集群集合变化时执行完整两阶段发布 |

物理 SHA-256 用于确认 Pod/节点安装的实际文件，组件 `module_digest` 用于判断行为内容。
Agent 和 Executor 都携带 artifact SHA、compatibility digest 和 protocol；只有这些
值实际变化时才打开 required/compatible 窗口。共享release默认一次只推进一个GPU集群；
单集群内Executor先收敛，Watcher/Collector同波并行，随后进入Reconciler和Node Runtime。
upgrade第一波固定1，之后按节点规模和故障域自适应到4、8、16或显式32；rollback第一波
固定1，后续保守自适应为1、2或4。

涉及GPU或Node Runtime的upgrade会在schema Job和CPU rollout前写入
`candidate-preflight-ready`：候选Manifest完成server-side dry-run，逐节点只读host
probe证明制品摘要、磁盘、Python/systemd/驱动和rollback slot。进入第一台节点mutation
前仍会重新检查Node状态、Executor、remote command、破坏性workflow和Agent lease。
早期门禁失败不会触发CPU/GPU rollout；晚期动态门禁失败则按已有事务证据裁剪回滚。
未达到`data-converged`的resume会重新执行只读候选/host预检，不会永久信任旧checkpoint。

某个GPU集群出现本地容量、Agent安全门或收敛超时、Installer失败时，站点release进入`PAUSED`：已经
`CONVERGED`的集群保持候选版本，当前失败集群保留checkpoint，后续集群保持`PENDING`。
修复原因后重跑同一条四参数deploy，系统会重新校验release、执行计划、previous摘要、
CPU兼容窗口、集群身份和节点集合，然后从失败集群续跑。未知范围或全局故障仍fail closed。

**成功标准**

- CPU 三层角色、GPU Executor/Watcher/Resource Collector/Reconciler，以及节点
  systemd Collector/Agent 全部收敛；
- Control Plane、Executor、Node Runtime 各自指向目标 component；
- Agent/Executor required artifact、compatibility digest 为新版本，compatible 为空；
- Runtime Profile、Agent config digest 和 protocol 一致；
- verifier 通过且 remote command 没有新增积压。

**回滚**

```bash
gpu-fault-admin deploy --state-dir /secure/gpu-fault-bootstrap --rollback
```

`--rollback` 只退一步：目标固定是 release state 里的 `previous`，即当前 release 提交
前线上运行的那个 release，没有 release id 参数，也不需要确认字面量。命令先读线上
state，以下情形拒绝执行并说明原因：没有 `previous`（首次 bootstrap 后或 NOOP release）；
事务还在进行中（任何 upgrade/rollback 中间 phase、`complete` 未 commit、commit 清理未
完成——先原样重跑 `deploy --state-dir X` 让它 resume/收尾）；上一 release 与当前 release
之间跨了 PostgreSQL schema（引擎拒绝，命令转述引擎原话和快照 id）。

回滚完成后 state 为 `rolled-back`，`previous` 就是此刻线上版本，更早的已提交 release
不再有记录，因此**连续第二次 `--rollback` 会被拒绝**；要退到更早版本，把
`dist/current-release.json` 指到那个旧 release 后按普通流程 `deploy`。回滚需要的
Secret 备份在 commit 时保留到下一个事务 commit 才清理，所以已提交 release 的回滚能
找到自己的备份。引擎跑完后命令会像自动回滚一样对齐管理侧（改回 `site.yaml`
并 `sync-state`），随后 `gpu-fault-admin status` 按回滚后的线上版本判断健康。

只执行 `kubectl rollout undo` 不会恢复 release metadata、installer bundle 或节点
artifact，不构成区域回滚。

回滚目标若是尚无独立 component pin 的旧单 wheel release，编排器会自动把 Agent
compatibility digest 回退到旧 artifact SHA，并在应用旧 Deployment 前移除新版本才
认识的 6 个 component-pin 环境变量；不得手工把这些变量留给旧进程。

升级失败或自动回滚后，直接重跑同一条四参数`gpu-fault-admin deploy`。尚未完成回滚的
`failed`事务只允许同一release按原始`release_diff`执行resume；已经验证回滚并进入
`rolled-back`终态后，下一候选复用保守差异集合，但从当前线上基线开启新事务，不把旧
release checkpoint当作resume状态。新事务会清空上一release的rollback phase和cluster
checkpoint，避免把历史回滚误判为当前回滚已完成。不要删除release state ConfigMap。
回滚只补偿有mutation证据的组件和集群，并按实际升级顺序逆序恢复；Executor-only失败
不会重装Agent，GPU-only且未改CPU pin的事务不会无意义滚动CPU。rollback verify通过后
管理site、容量desired配置和release state会对齐previous版本，因此
`gpu-fault-admin status`应以当前回滚后线上版本报告健康，而不是继续比较失败候选。
`partial-convergence`继续原upgrade checkpoint；任何`rollback-*`或
`rollback-failed`只继续rollback。若线上已经commit/rolled-back而仅临时Secret备份
清理失败，重跑只补清理，不会重新滚动组件。站点设置`autoRollback=false`时，verify或
stability失败保留候选中间态并标记`SKIPPED_POLICY`。

**deploy 说 "a failed fail-forward transaction only resumes the release that failed"。**
这是 fail-forward 事务停在 `failed`/`partial-convergence` 之后，你修了缺陷再 deploy 时会看到的
拒绝：修复产生了一个新的 release id，而失败事务只允许同一 release resume。报错里写明失败的
release id、当前候选 id 和出路——在同一条四参数 deploy 上加 `--supersede-failed-transaction`：

```bash
gpu-fault-admin deploy \
  --cpu-cluster-arn <cpu-arn> \
  --gpu-cluster-arn <gpu-arn> \
  --state-dir /secure/gpu-fault \
  --admin-email <operations-email> \
  --supersede-failed-transaction
```

它为新候选开一个**新事务**：回滚基线继承失败事务的 `previous`（上一已提交 release 及其 Secret
备份，不是现在的混合态，所以自动回滚会落回已知良好的版本）；要滚的组件是"新候选相对失败候选的变化
∪ 失败事务已经动过的组件"，失败候选滚过的东西即使新候选和基线一样也会重滚；`status` 的
`live_release.superseded_transaction` 记录被替代的事务（id、phase、原始失败、时间）。失败事务已接受
且版本相同的 schema 变化自动沿用，不必再传 `--accept-schema-change`。参数在其他任何状态
（`complete`、中途 checkpoint、`rollback-*`、`rolled-back`、候选就是失败 release 本身）下都会被拒绝并
说明原因；同一 release id 重跑不需要也不能带这个参数，那是普通 resume。不要为了绕过拒绝去改
release state ConfigMap 或手写脚本调用编排器。细节见 `部署和运维手册.md` REG-8.1.4。

**Aurora 密码轮转与 `password authentication failed`。** RDS 每 7 天轮转 Aurora
主密码，`gpu-fault-aurora` Secret 只靠 `gpu-fault-aurora-credential-refresh`
CronJob（现为每小时 `17 * * * *`）同步。运行中的 Pod 通过 `/etc/gpu-fault/aurora/postgres-url`
挂载重读 DSN：Secret 刷新后 kubelet 同步（约 1–2 分钟）即恢复，刷新前被 `max_idle` 回收后
重建的连接会认证失败并由池退避重试，不再丢槽位（控制面审查 2026-09-08，CP-3）；刷新器默认
不再滚动 Deployment，发布输出里的 create/wait/delete 三行不变。轮转到刷新之间，每个**新建**
的控制面 Pod 仍会以 `FATAL: password authentication failed` 退出——
一次发布恰好就是一批新 Pod。2026-09-07 12:13Z 生产上一次事务撞进这个窗口：re-apply
失败，自动回滚重启 control-worker，新 Pod 同样无法认证，事务停在 `rollback-failed`，
从发布输出看与真正坏掉的 release 无法区分。因此 deploy（含 resume）和 rollback 现在
都在滚动任何组件之前同步跑一次这个 CronJob 并 fail closed：

- 正常情况下发布输出里多出 `+ kubectl ... create job --from=cronjob/...`、`wait`、
  `delete job` 三行，用时几秒；
- Job 没在时限内 Complete，事务以
  `Aurora credential refresh Job gpu-fault-system/gpu-fault-aurora-credential-refresh-<后缀> did not complete within 300s`
  失败，不写 release state、不滚组件，Job 保留在原地。按错误信息里的 Job 名读
  `kubectl -n gpu-fault-system logs job/<名>` 与 `describe job/<名>`，修好（多为
  Pod Identity/KMS 权限或 RDS CA bundle）后 `delete job`，重跑同一条命令；
- 时限用部署主机上的 `GPU_FAULT_RELEASE_AURORA_REFRESH_WAIT_SECONDS`（正整数秒）
  覆盖；CronJob 不存在的旧站点打印 `aurora-credential-refresh skipped` 后跳过。

若一次事务仍停在 `rollback-failed` 且新 Pod 日志是 `password authentication failed`
（`PoolTimeout` 只是表象），不要动 release：手动
`kubectl -n gpu-fault-system create job --from=cronjob/gpu-fault-aurora-credential-refresh <名>`
（约 5 秒，Pod 约 2 分钟 Ready），再重跑同一条部署命令续跑。诊断与恢复细节见
《部署和运维手册》CPU-2R。

endpoint和regional cluster registry的变化不是事务性的，
`autoRollback=true`时部署在滚动任何组件之前就会以
`automatic rollback is not yet transactional for: <字段>`失败。这类发布必须由管理员
显式改为fail-forward：在`site.yaml`把`spec.autoRollback`设为`false`再重跑同一条部署
命令。重新部署会重新渲染site，但会保留管理员声明的`autoRollback`，不会悄悄改回
`true`；缺失或非布尔值仍按`true`处理。fail-forward期间失败不会自动回滚，恢复手段是
修复后重跑同一条部署命令续跑，或用本节上面的`deploy --state-dir X --rollback`显式回滚到上一已提交
release——但**跨 schema 版本的发布不能这样回滚**，显式回滚同样会以
`rollback across this PostgreSQL schema change is not declared backward-compatible`拒绝，
见 §4.7。发布提交后应把
`spec.autoRollback`改回`true`，让后续事务性发布重新获得自动回滚。

ADOT Manifest和ADOT image不属于这一类，只改ADOT不需要fail-forward：升级在改动
collector之前会把线上ADOT对象读入observability快照，回滚按快照恢复这些对象、删除候选
新增的对象，并重启collector等待其重新Ready，恢复的是上一release自己applied的配置和
镜像。快照缺少collector Deployment、或旧state里没有ADOT对象时回滚fail closed，不会声称
补偿了没有恢复的面。续跑一个在该能力上线之前开始的失败事务时，它的previous快照没有ADOT
对象，部署会在滚动任何组件之前以
`previous observability snapshot predates ADOT rollback capture`失败；这一个事务仍按上面
的fail-forward流程续跑，提交后再把`spec.autoRollback`改回`true`。

### 4.0 节点被 HyperPod 重镜像后 Agent 消失（UpdateClusterSoftware）

`UpdateClusterSoftware` 会原地重装 GPU 节点的系统盘：Node 对象与 UID 不变、注解全部保留，
但 `/opt/gpu-fault`、`/var/lib/gpu-fault`、`/etc/gpu-fault` 与全部 `gpu-fault-*` systemd
unit 都会消失，Agent 租约随之过期。node-installer-reconciler 过去只比对注解与 Node UID，
因此把这样的节点判为 `current`、不再重装；发布会在"previous Agent identity capture"处以
`<cluster> has no active Agent identity to capture` 失败。

reconciler 现在把安装记录绑定到 `status.nodeInfo.bootID`（注解
`gpu-fault.io/installer-boot-id`）：boot id 变化后先探测 Agent 端口
（`GPU_FAULT_NODE_AGENT_PORT`，默认 9099）——有应答只是普通重启，重新盖上 boot id；
无应答且节点 Ready 已超过 `GPU_FAULT_INSTALLER_REBOOT_GRACE_SECONDS`（默认 600）则标记
`Retrying` 并按常规波次重装（`rebooted`/`recovering` 两个计数会出现在 reconcile 日志里）。
旧版本安装的节点没有该注解，第一次 reconcile 只补注解、不重装。

携带本修复的 release 部署之前若已经发生重镜像，用 reconciler 自己的重试通道触发重装：

```bash
kubectl --context "${GPU_CONTEXT}" annotate node <node> \
  gpu-fault.io/installer-state=Retrying --overwrite
```

reconciler 会为该节点创建 installer Job（受 `max-unavailable` 约束，逐节点进行），完成后
Agent 租约恢复。这只改动安装簿记注解；不得以同样方式改动隔离/incident 注解或污点。


### 4.1 读部署日志的耗时

一次升级输出三千多行，过去只有 `release-phase` 带秒级时间戳，任何"这次为什么慢"的问题
都要人工去减两个时间戳，而单条命令的耗时根本无处可查。现在按三层读：

| 行 | 含义 |
|---|---|
| `release-begin <stamp> mode=<mode> dry_run=<bool>` | 本次脚本调用开始。一条 `gpu-fault-admin deploy` 会驱动这个脚本十余次（plan/preflight/deploy/verify/commit），所以日志里有多段 begin/end |
| `release-end <stamp> mode=<mode> exit_code=<n> total=<秒>s` | 本次调用结束，含失败路径。看不到 end 就说明进程还卡在最后一条命令里，或已被杀掉 |
| `release-phase <stamp> <phase> ... elapsed=<秒>s total=<秒>s` | `elapsed` 是从上一个 checkpoint 走到这个 checkpoint 的代价，`total` 是本次调用累计 |
| `command-elapsed <秒>s <命令>` | 单条命令耗时。只有超过 15 秒才打印，否则几千条亚秒级 kubectl 会把命令轨迹淹掉；`probe` 类只读检查本来不回显命令，也走这条线 |

phase 是 checkpoint 之间的间隔，而升级最长的一段恰好落在**一个** phase 里面：
`data-plane-progress` 每个集群只 checkpoint 一次，一个四波次的集群会打出两条相隔七分半
的 phase 行，中间全是 `get nodes`/`get jobs` 的轮询。这一段现在有自己的行，都带 `total`
但不带 `elapsed`——它们在 phase 内部打印，占用 phase 的 split 会把七分钟的 phase 记成
最后三十秒：

| 行 | 含义 |
|---|---|
| `fleet-wave <stamp> cluster=<id> phase=<phase> wave=<i>/<n> ready=<就绪>/<总数> nodes=<节点>` | 一个波次开始。`wave` 是它在本集群波次序列里的位置，`ready` 是滚动前已经在新身份上的节点数 |
| `fleet-wave-done <stamp> cluster=<id> wave=<i>/<n> ready=<就绪>/<总数> safety=<秒>s handoff=<秒>s install=<秒>s elapsed=<秒>s` | 波次结束，并把耗时拆成三段：`safety` 是 Agent lease 与未完成命令的等待，`handoff` 是 Reconciler rollout 加上一波遗留 Job 的清理，`install` 是节点自己装 |
| `installer-wait <stamp> cluster=<id> nodes=<n> aligned=<n> waiting=installers\|heartbeats pending=<节点>:<状态>,... elapsed=<秒>s` | 波次内部的等待。`waiting=installers` 是还有节点没装完，`pending` 逐个给出节点名和它的 `gpu-fault.io/installer-state`（`<none>` 表示 Reconciler 还没建 Job，下一个 reconcile pass 才会建）；`waiting=heartbeats` 表示节点已经装上新身份，在等 Agent 心跳上报。状态一变就打印，否则每 30 秒重复一次，节点多于 5 个时只列前 5 个并以 `+N` 收尾 |

看 `fleet-wave-done` 的三段拆分才知道一个慢波次值不值得优化：`install` 大就是集群在做
升级本来的工作，`safety`/`handoff` 大才是控制面自己的开销。`installer-wait` 的轮询间隔
从 5 秒退避到 15 秒，但只要 `pending` 集合缩小就立刻回到 5 秒——一波一个节点滚动时，
退避会把下一个节点的安装尾巴整段睡过去。

`make check` 的十个静态门并行跑，墙上时间等于最慢的那个门，所以每个门收尾会打印
`static-gates: <门> passed in <秒>s`；一个门里包含多条命令时，超过 5 秒的那条单独打印
`static-gates: <门> step took <秒>s: <命令>`，失败行也带上命令名和耗时。

耗时都用 monotonic 时钟测量，中途时钟跳变不会产生负数 phase。计时随每次进程调用重置，
因此 `total` 是本次调用的耗时，不是整条 deploy 的；要整条 deploy 的耗时就把各段
`release-end` 的 `total` 相加，或直接看首尾时间戳。

**边界**

- 这些行只是观测，不构成门禁。不得因为某个 phase 慢就上调超时、跳过探针或删除门；
  §8 的同一条约束在这里同样适用。
- `<sensitive command>` 的耗时行同样不展开参数。不要为了看清慢命令去打印敏感命令的
  参数，含密码/令牌的命令必须保持不可见。
- 不要为了让日志"干净"去调大慢命令阈值：那等于把要找的慢命令重新藏起来。
- `installer-wait` 长时间停在同一个 `pending` 节点上，处理的是那个节点（看它的 installer
  Job 与 `installer-state`），不是去缩短 `wait_agents` 的超时或放宽收敛判定：`pending`
  的成员判定和门禁用的是同一个 `agents_converged`，改一个就等于改门。

### 4.2 索引三步法（为什么不能让 DDL 建索引）

- 幂等 DDL 在**一个事务**里执行，而 PostgreSQL 禁止在事务内 `CREATE INDEX CONCURRENTLY`；
  如果让 ensure Job 或 Pod 启动去建一条新索引，它只能用普通 `CREATE INDEX`，建索引期间
  `gpu_fault_objects`（全部 workflow / incident）或 `gpu_fault_processor_queue`（处理器队列）
  的写入被锁住，准入、认领、完成、派发全部停摆，时长取决于表大小。
- 所以规则是：① `gpu-fault-postgres-index-build` Job 用 `CONCURRENTLY` 在线建；② DDL 先查
  `to_regclass` 再决定要不要发 `CREATE INDEX IF NOT EXISTS`——裸的 `IF NOT EXISTS` 在索引已存在时
  仍会对表拿 ShareLock 直到提交，所以"已存在就跳过"必须发生在语句之外；③ 每个副本启动时校验代码声明的索引
  全部存在，缺失即拒绝启动（`PostgreSQL indexes are missing`），宁可起不来也不让热点查询
  退化成全表扫描而无人察觉。
- `CONCURRENTLY` 建索引失败（连接中断、超时）会留下一个 `indisvalid = false` 的无效索引；
  index-build Job 会先 `DROP INDEX CONCURRENTLY` 再重建。手工核对：

```sql
SELECT c.relname, i.indisvalid
FROM pg_class c JOIN pg_index i ON i.indexrelid = c.oid
WHERE c.relname LIKE 'gpu_fault_%' ORDER BY 1;
```

- 需要手工执行时（例如 Job 无法运行），在 writer 上逐条执行
  `gpu-fault-store-migrate --build-indexes-concurrently --postgres-url <url>`，或按
  `src/gpu_fault/store/postgres/ddl*.py` 里的定义手写 `CREATE INDEX CONCURRENTLY IF NOT EXISTS`。

### 4.3 FULL 发布前的 schema preflight 清单

`gpu-fault-postgres-schema-preflight` Job 只读检查以下三项，任一不满足就以非零退出并停止部署；
也可在任何时候手工运行 `gpu-fault-store-migrate --schema-preflight --postgres-url <url>`：

| 检查 | 通过条件 | 不通过时怎么办 |
| --- | --- | --- |
| schema 版本 | `gpu_fault_schema_migrations` 的最大版本等于 wheel 要求的版本，且历史校验和一致 | 落后：跑 ensure Job；超前：wheel 比库旧，换正确的 release；校验和不一致：停止，人工比对迁移登记 |
| 索引 | 代码声明的索引全部存在且 `indisvalid` | 跑 index-build Job（§4.2） |
| 在飞的安全流程 | 没有 `RUNNING`/`SAFETY_PENDING`、`blocked_reasons` 非空且缺 `safety_only` 字段的工作流 | 等这些工作流结束（通常几分钟）再滚动；它们是 `safety_only` 字段出现之前写下的老记录，新代码无法判断它们该跑哪套步骤 |

报告里另有一段**不阻断**的 `diagnostics` / `warnings`：`log_lock_waits`、`deadlock_timeout`、
`log_min_duration_statement`、`shared_preload_libraries` 的当前值，以及 `pg_stat_statements` 是否已安装。
`log_lock_waits` 关着时 store 自动重试掉的 `40P01` 死锁在数据库日志里不可见；没有 `pg_stat_statements`
就没有按语句的 ACU 视图。两者都是参数组的事（§4.6）；参数就位后用
`gpu-fault-store-migrate --ensure-diagnostics --postgres-url <url>` 在库内建扩展并打印同一段诊断。

对应的只读查询（在 writer 或只读副本上执行）：

```sql
SET default_transaction_read_only = on;
SELECT key, payload->>'status'
FROM gpu_fault_objects
WHERE kind='workflow'
  AND payload->>'status' IN ('RUNNING','SAFETY_PENDING')
  AND jsonb_array_length(coalesce(payload->'blocked_reasons','[]'::jsonb)) > 0
  AND coalesce(payload->>'safety_only','false') <> 'true';
```

### 4.4 本轮新增配置项（默认值可直接上线）

以下变量都有代码默认值，部署配置不需要新增任何键；列出是为了知道它们存在和何时调整。
完整清单见 `管理员环境变量参考.md`。

| 变量 | 默认 | 含义 | 何时调整 |
| --- | --- | --- | --- |
| `GPU_FAULT_WORKFLOW_INTERNAL_ERROR_BACKOFF_SECONDS` | 60 | 派发遇到未识别的内部错误时，工作流退避多久再试（以前直接 BLOCKED） | 内部错误多为瞬时故障且希望更快重试时调低 |
| `GPU_FAULT_PROCESSOR_DEADLINE_EXCEEDED_PROCESS_THRESHOLD` | 3 | 多少个不同请求执行超时后，处理器进程才认为是自身问题并自毁 | 更保守取 2；单条毒请求不再能重启整个机队 |
| `GPU_FAULT_PROCESSOR_UNHEALTHY_TTL_SECONDS` | 300 | 进程 unhealthy 闩锁多久后自动清除 | 关掉自毁开关时尤其重要，否则后台服务永久停摆 |
| `GPU_FAULT_JOB_WORKFLOW_MAX_LIFETIME_SECONDS` | 3600 | 作业工作流（含作业重启）从首次领取起的硬上限；到点失败并升级到人工，之后同作业事件只记录 | 作业规模大、换备机链路长时调高 |
| `GPU_FAULT_NODE_WORKFLOW_MAX_LIFETIME_SECONDS` | 3600 | 单节点无作业工作流的硬上限，整条 reset→reboot→换机链共用 | 同上 |
| `GPU_FAULT_BRANCH_ESCALATION_MAX_RUNGS` | 2 | 作业工作流里单个节点分支就地升级的最大级数（reset→reboot→换机） | 不希望自动换备机时设为 1 |
| `GPU_FAULT_JOB_WORKFLOW_NODE_BUSY_WAIT_SECONDS` | 240 | 规则 A 的唯一窗口：训练作业的节点正被别的修复占用时，作业只等这一段时间。修复在窗口内完成则作业继续（排队的作业工作流被派发；`after_incident` 重启把作业重启）；超过窗口作业不再重启——还在跑的作业以带控制面发起者标记的 STOP_WORKLOADS 停掉、已经死掉的作业其重启计划失败，工作流 FAILED、incident ESCALATED，系统自己停掉的作业不会再被任何人重启。派发器（未开始的作业工作流）与执行器（已在跑的重启前提）读的是同一个变量 | 单节点修复常超过 4 分钟时调高；两处读值不等即拒绝启动 |
| `GPU_FAULT_PROCESSOR_LEASE_RECLAIM_SECONDS` | 30 | 周期任务多久扫一次处理器队列，把 lease 已过期仍为 LEASED 的请求退回 PENDING；每次回收计入 `gpu_fault_processor_expired_leases_reclaimed_total` | 一般不调；lease 本身（`GPU_FAULT_PROCESSOR_LEASE_SECONDS`）调长时可同步放宽 |
| `GPU_FAULT_PROCESSOR_COUNTER_DRIFT_SCAN_SECONDS` | 60 | 周期任务多久对比一次处理器队列分片计数器与真实 PENDING/LEASED 行数，刷新 `gpu_fault_processor_counter_drift_abs` 与 `gpu_fault_processor_counter_mismatched_clusters`（不在 scrape 里算） | 队列表很大、这次 COUNT 明显拖慢 Aurora 时调长；告警窗口是 5 分钟，不要调到接近它 |
| `GPU_FAULT_PENDING_TRIAGE_DEADLINE_SECONDS` | 900 | 完成事件的决策允许停留在 `PENDING_TRIAGE` 多久，超过后由周期任务收口；`GpuFaultCompletionPendingTriageBacklog` 的 `for` 是它的两倍 | 观察器投递本来就慢的环境可调高，同时把告警 `for` 同比调整 |
| `GPU_FAULT_PENDING_TRIAGE_SCAN_SECONDS` | 60 | 周期任务多久扫一次超期的 `PENDING_TRIAGE` 决策；每次收口计入 `gpu_fault_completion_pending_triage_reconciled_total` | 一般不调 |
| `GPU_FAULT_WORKFLOW_INVARIANT_CHECKS` | log | 执行器每次带 lease 写入后核对 workflow 记录的状态机不变量（索引有序无重、DAG join 标记、终态无 owner/lease、`events` 有界有序等）；`off` 不查，`log` 记 error 日志继续，`raise` 让该次写入失败 | 生产保持 `log`；staging 与验收演练用 `raise` 把畸形记录当场暴露 |

**时序参数之间的顺序关系。** 上表与 §4 其它地方的等待类参数不是各自独立的，代码里有一条隐含的排序，
启动时由 `gpu_fault.execution.config.validate_timing_relationships` 逐条核对（违反即拒绝启动，
只能核对不了的项以 `warning:` 日志给出）：每个步骤等待上限（默认 `GPU_FAULT_WORKFLOW_STEP_TIMEOUT_SECONDS`
与各覆盖值，含 `GPU_FAULT_HYPERPOD_MANAGED_RECOVERY_TIMEOUT_SECONDS` 的托管恢复窗口）≤ 单节点生命周期
`GPU_FAULT_NODE_WORKFLOW_MAX_LIFETIME_SECONDS`（否则生命周期先于步骤上限把步骤判失败，adapter 自己的超时处理——
托管恢复的升级通知——不会跑；`CHECK_MECHANICALS` 的人工确认上限除外，claim 时生命周期会以它为下限）；
托管恢复窗口 + 一次 reboot 配额 ≤ 作业生命周期 `GPU_FAULT_JOB_WORKFLOW_MAX_LIFETIME_SECONDS`，且作业生命周期 ≥
`GPU_FAULT_BRANCH_ESCALATION_MAX_RUNGS` × 托管恢复窗口（升级后的分支最多做这么多次委托恢复）；执行超时
`GPU_FAULT_WORKFLOW_EXECUTION_TIMEOUT_SECONDS` ≤ 两个生命周期（claim 取两者较小值，配大了等于没配）；lease
`GPU_FAULT_WORKFLOW_LEASE_DURATION_SECONDS` < 执行超时；`GPU_FAULT_JOB_WORKFLOW_NODE_BUSY_WAIT_SECONDS`
在执行器配置与派发器配置里必须相等（规则 A 只有一个窗口，两者读同一个变量，不等说明有人绕过环境变量各配了一份），且 <
`GPU_FAULT_GPU_CLIENT_VERIFY_MAX_ATTEMPTS` × `GPU_FAULT_WORKFLOW_POLL_INTERVAL_SECONDS`（作业工作流放弃等待、
STOP 作业的时刻必须早于节点修复 VERIFY 放弃的时刻，否则 STOP 永远来不及帮到 VERIFY）；
`GPU_FAULT_WORKFLOW_DISPATCH_LEASE_SECONDS` ≥ 3 × 轮询间隔（默认即 `max(15, 3×poll)`，显式覆盖时校验）；
`GPU_FAULT_WORKFLOW_DISPATCH_CYCLE_SECONDS` 若 > 0 则 ≥ 轮询间隔。调任何一个都先对着这张关系表看它的邻居。

### 4.5 处理器计数器模式必须先看 `/metrics`，再决定要不要 finalize

处理器 admission 的按集群深度读的是哪张计数表，由 `gpu_fault_processor_counter_mode`
单行决定，只有两个值：`dual`（绿地初始化和滚动升级期间的默认值）和 `partitioned`。
`dual` 不是"半开"：每次入队仍然锁 `gpu_fault_processor_queue_counts` 里该集群的那一行直到提交，
16 个优先级分片只是多写了一份，对行锁争用没有任何缓解；只有 `partitioned` 才让分片成为事实源。
2026-09-07 检查生产库时它一直停在 `dual`，之前没有任何指标暴露这件事。

现在 `/metrics` 导出 `gpu_fault_processor_counter_mode{mode="dual"}` 与
`{mode="partitioned"}` 两条序列，激活的那条为 1（SQLite/内存 store 不导出）。升级后的例行检查：

```bash
curl -s http://<control-worker>:8080/metrics | grep gpu_fault_processor_counter_mode
```

看到 `mode="dual"} 1` 且全部副本已滚动到同一 module digest，就按 `部署和运维手册.md` CPU-4U
的顺序 finalize：先确认 processor queue 的 `PENDING/LEASED` 为 0（`gpu-fault-store-migrate
--processor-counter-shard-status` 的 `expected_total` 与 `counter_total` 都是 0），再运行
`postgres-counter-shards-finalize-job.yaml`（`--finalize-processor-counter-shards`）。
finalize 在 advisory lock 与 queue table lock 下重新 seed 分片，队列不空会直接拒绝，不要靠
反复重试。切换后各进程最多 0.25 秒内读到新模式，指标随之翻转；若某副本迟迟不翻，先查它的
`gpu_fault_periodic_job_errors_total`，不要重启它来"刷新"。

回滚方向是 `--restore-legacy-processor-counters`，同样要求队列为 0，且必须先于回滚到不认识
priority shards 的旧 wheel。

### 4.6 Aurora 参数组与日志导出：deploy 自动对齐，人工只剩重启窗口

store 遇到 `40P01`（deadlock detected）会自动重试并成功，所以死锁在业务上不可见；Aurora
默认参数组里 `log_lock_waits` 是关的，它在数据库日志里也不可见。`pg_stat_statements` 是唯一能按
语句看 ACU 花在哪的视图，默认也没有装。

**这些不再需要手工做。** 区域 bootstrap 自己建 Aurora（`src/gpu_fault/admin/bootstrap.py`
`_ensure_aurora`），现在建库时就带上专用集群参数组 `<集群名>-pg` 和 `postgresql` 日志导出；对已经在线的
集群，每次 `gpu-fault-admin deploy` 都会像校正 ACU 容量一样对账：参数组缺失就建、四个参数偏离就改、
集群没挂这个组或没开导出就一条 `modify-db-cluster --apply-immediately` 补上。全部在线生效、不重启
任何实例、不断连接；已经对齐的库一条修改命令都不会发。四个参数：

| 参数 | 值 | 生效方式 |
| --- | --- | --- |
| `log_lock_waits` | 1 | 挂组即生效 |
| `log_min_duration_statement` | 1000 | 挂组即生效 |
| `pg_stat_statements.track` | all | 挂组即生效 |
| `shared_preload_libraries` | pg_stat_statements | **要 writer 重启**；此前集群显示 `pending-reboot`，这是预期状态 |

只读核对（Aurora 在集群所在 region，注意 `--region`；部署主机默认 region 可能不是它）：

```bash
aws rds describe-db-clusters --db-cluster-identifier <aurora-cluster-id> --region <region> \
  --query 'DBClusters[0].[DBClusterParameterGroup,EnabledCloudwatchLogsExports]'
aws rds describe-db-instances --region <region> \
  --query "DBInstances[?DBClusterIdentifier=='<aurora-cluster-id>'].[DBInstanceIdentifier,DBParameterGroups[0].ParameterApplyStatus]"
```

**唯一的人工步骤：让 `pg_stat_statements` 库加载。** 两台实例都是 promotion tier 0，互为故障转移目标，
选一个没有 live 验收用例、没有 `LEASED` 工作流的窗口：

1. `aws rds reboot-db-instance --db-instance-identifier <reader>`，等它 `available`；
2. `aws rds failover-db-cluster --db-cluster-identifier <aurora-cluster-id>`，reader 升为 writer，
   业务连接在这一刻断一次，几秒到几十秒，store 的连接池自愈；
3. `aws rds reboot-db-instance --db-instance-identifier <原 writer>`。
4. 之后 `gpu-fault-store-migrate --ensure-diagnostics --postgres-url <url>` 在库内执行
   `CREATE EXTENSION IF NOT EXISTS pg_stat_statements`；部署的 `--schema-preflight` 报告里
   `diagnostics.pg_stat_statements_installed` 应为 true。

实例名截到 63 字符后 `-writer` / `-reader` 后缀可能被摘要顶掉，角色要看
`DBClusterMembers[].IsClusterWriter`。

日志导出打开后 RDS 把 `postgresql.log` 推到日志组 `/aws/rds/cluster/<aurora-cluster-id>/postgresql`，
每个实例一条日志流；给这个日志组设保留期（建议 30 天），否则默认永久保留。这个库正常时每秒几十条
语句，四个参数只在锁等待和慢语句时产生日志，日志量以 KB/天计。死锁在该日志组里以
`process ... detected deadlock while waiting` 出现，可以用 Logs Insights
`filter @message like /deadlock detected/` 查，也可以配指标过滤器告警；超过 1 秒的语句带完整 SQL
进日志——注意日志里会出现 workflow/command id，按《故障证据隐私约束》不要把这些行粘贴进对外的工单。

### 4.7 schema 版本变化的发布：一条命令，一个参数

**怎么知道这次发布改了 schema。** release 的 `database_schema_version` 与线上不同时，`deploy`
在滚动任何组件之前就停下来，报
`automatic rollback across this PostgreSQL schema change is not declared backward-compatible`，
并告诉你该加哪个参数。这是设计如此：新 wheel 启动时要求 `gpu_fault_schema_version.version`
与代码完全相等，回滚到旧 wheel 的 Pod 在新版本的库上会拒绝启动。因此
`gpu-fault-admin deploy --state-dir X --rollback` 也会以
`rollback across this PostgreSQL schema change is not declared backward-compatible` 拒绝。
**没有任何开关能把这次 schema 变化声明成"可回滚"**：release manifest 里的 `database.rollback_compatible: true` 会被 `deploy` 直接拒绝（运行时要求 schema 版本与 migration 历史完全相等，旧 wheel 回到新 schema 上必然 CrashLoop），唯一的出路就是下面这个参数。

**只需要在同一条 deploy 命令上加一个参数：**

```bash
gpu-fault-admin deploy \
  --cpu-cluster-arn <cpu-arn> \
  --gpu-cluster-arn <gpu-arn> \
  --state-dir /secure/gpu-fault \
  --admin-email <operations-email> \
  --accept-schema-change
```

这个参数只表达一件事：我知道这次跨 schema 版本、不能回滚。其余由发布引擎在**这一个事务**里完成：

1. 放行那道门，并把接受记录（模式、时间、schema 版本）写进 release state。
2. 在 index-build → ensure → preflight 三个 schema Job 之前，对 Aurora 集群创建一份手工快照
   （名字固定为 `gpu-fault-pre-v<版本>-<release id 前 12 位>`），等它 `available` 再继续。
   同名快照已存在就直接复用，所以续跑不会再打一份。快照 id 写进 release state，
   `gpu-fault-admin status` 的 `live_release.schema_change_acceptance` 里能看到。
3. 之后 verify 或 stability 失败时按 fail-forward 处理：候选保留中间态、`SKIPPED_POLICY`
   的 reason 写明是 schema 接受，不去尝试一定会被拒绝的回滚。
4. `site.yaml` 一个字不改。事务提交后，下一次 deploy 照常读 `spec.autoRollback`（仍是 `true`），
   自动回滚自然还在——没有"改回去"这一步。
5. 失败后续跑同一条命令（带不带参数都可以）：引擎从 release state 里读到已接受，不会重复打快照。

**快照打不了怎么办。** 集群 id 取 `health.aurora_cluster_id`，没配置时从 `gpu-fault-aurora`
Secret 的 writer 地址推导。部署主机角色需要 `rds:DescribeDBClusterSnapshots`、
`rds:CreateDBClusterSnapshot`、`rds:AddTagsToResource`；权限不够时命令停在 schema Job 之前，
库和 Pod 都没动，报错里写明缺什么。等待上限 `GPU_FAULT_RELEASE_SCHEMA_SNAPSHOT_WAIT_SECONDS`
（默认 900 秒）。对没人会去恢复的库（staging）可以用
`--accept-schema-change-without-snapshot` 放弃快照，生产不要用。

**失败后的两条路。** 修好原因后重跑同一条 `deploy` 续跑；或者用快照把库恢复到旧版本
（`aws rds restore-db-cluster-from-snapshot`，再把应用切到恢复出的集群），此时库与旧 wheel 一致，
再按 §4 的 `deploy --state-dir X --rollback` 回滚整套。引擎不会替你恢复库：那是有损操作，要人决定。

**收尾核对：**

```sql
SELECT version FROM gpu_fault_schema_version;
SELECT max(version) FROM gpu_fault_schema_migrations;
```

两者都等于新版本；`gpu-fault-admin status` 健康；再跑一次
`gpu-fault-store-migrate --schema-preflight --postgres-url <url>`，`ok` 为 true。

**v12 特别说明。** v12 新增 6 个 `gpu_fault_objects` 上的索引，index-build Job 会在滚动前建好；
ensure 阶段删除被 `gpu_fault_remote_command_workflow_all` 取代的 `gpu_fault_remote_command_workflow`。
库很小（十几万行）时整个 schema 阶段在一两分钟内完成。v12 之后的 `--ensure-schema` 在无变化时
不再拿表锁（§4 开头），所以例行发布的 ensure 阶段对业务写入不再有影响。

**v13 特别说明（控制面组件审查）。** v13 新增 9 个 `gpu_fault_objects` 上的文本表达式索引
（归档候选、fleet_deployment 终态、marker/notification/event 保留、workflow/incident 指针等）并给
`gpu_fault_objects` 设置更激进的 autovacuum 表参数。发布时仍然只是那一个 `--accept-schema-change`
参数：index-build Job 会在滚动前 `CREATE INDEX CONCURRENTLY` 建好全部 9 个索引，不需要人工先跑
`gpu-fault-store-migrate --build-indexes-concurrently`；但 v13 之后启动校验也检查索引**有效**
（`indisvalid`）且定义与代码一致，一个被中断的 CONCURRENTLY 留下的 INVALID 索引会让副本拒绝启动，
preflight 报 `indexes.drifted`——那时才需要手工重跑 index-build Job（§4.2）。

### 4.8 发布前后的两项自动核对：归档桶与 ADOT 自监控指标名

这两项以前只写在发布记录里靠人记，现在都是 `gpu-fault-admin deploy` 报告里的检查项，任一失败即停止：

| 检查 | 阶段 | 通过条件 | 不通过时怎么办 |
| --- | --- | --- | --- |
| `control_record_archive_bucket` | 预检 | `GPU_FAULT_CONTROL_RECORD_ARCHIVE_S3_URI` 是 `s3://bucket/prefix`，且桶存在于站点 Region（只读 `s3api get-bucket-location`） | 先建桶并在 site.yaml `spec.retention.archiveS3Uri` 指向它（见 `管理员容量配置.md` §10）；控制面 pod identity 对该前缀的 `s3:PutObject` 由 bootstrap 按 `spec.retention` 授权。桶缺失时归档器只会计 `gpu_fault_control_record_archive_errors_total`、不删任何 live 行，但保留就静默停止了 |
| `adot_self_metrics` | 部署后 verify | 通过 API server 代理读 ADOT Pod `:8889/metrics`，告警规则与 keep 列表引用的每个 `otelcol_*` 序列都真的导出 | 说明采集器镜像换了指标命名（多半是加了 `_bytes` 一类后缀）：同步改 `deploy/observability/adot-control-plane.yaml` 的 keep 正则与 `amp-rules.yaml` 里的 `GpuFaultAdotMemoryHigh` / remote_write 告警，再重跑 verify。在此之前 ADOT 自身的告警是哑的 |

两项都可以用 `gpu-fault-admin preflight` / `gpu-fault-admin verify` 单独重跑。

## 5. 接入和移除 GPU 集群

在 `deploy` 上多给一个 ARN 即接入：传入全部已纳管 GPU ARN 加上新集群，`deploy` 校验
集合是纳管集合的超集，发布（或 release 未变化时直接跳过滚动）后把多出的集群交给同一套
batch join；少给集群会拒绝并提示 `remove-cluster`。`join-cluster` 保留为别名，只接受新集群
的 ARN：

```bash
gpu-fault-admin deploy \
  --state-dir /secure/gpu-fault \
  --gpu-cluster-arn arn:aws:eks:us-west-2:123456789012:cluster/gpu-prod-a \
  --gpu-cluster-arn arn:aws:eks:us-west-2:123456789012:cluster/gpu-prod-b

# 别名（保留一个 release）
gpu-fault-admin join-cluster \
  --state-dir /secure/gpu-fault \
  --gpu-cluster-arn \
    arn:aws:eks:us-west-2:123456789012:cluster/gpu-prod-b \
  --gpu-cluster-arn \
    arn:aws:eks:us-west-2:123456789012:cluster/gpu-prod-c
```

命令自动发现 EKS/HyperPod 身份并校验同账号同 Region、`NodeRecovery=None`，然后更新
独立 kubeconfig、创建 cluster token、Executor IAM/OIDC、NLB NAT EIP 白名单、
Route53 VPC association和节点Action key。它使用候选site执行低层join与完整verify；
全部通过后才原子更新正式`site.yaml`并把EKS、HyperPod、Executor IAM和DNS association
写入Aurora注册表。

首次deploy一次提供多个GPU ARN时，第一个集群先形成稳定基线，其余集群自动使用batch
join：只读发现和各集群的前置资源（IAM、网络白名单、节点key）并行准备，全批次共用
一次候选preflight和一次最终verify；不再单独对现有站点做基线verify，候选verify已覆盖
全部集群。同时滚动几个集群由发布引擎的`spec.release.upgradeMaxParallelClusters`
决定（默认1，最大8），batch join直接读取该值，不再自带并发数或节点预算。
每个目标仍独立经历`PENDING -> ACTIVE`；一个集群失败进入`FAILED/ROLLED_BACK`，不会
撤销同批次已成功集群。每集群的记录就是`join-cluster/<arn-hash>/state.json`，批次
摘要（joined/already_managed/failed 与各集群记录路径）直接打印在命令结果里，部分失败时
也随错误信息一并输出。并发启动多个join CLI时，同一站点只有一个操作能拿到站点锁，
其余立即失败并报出持锁进程的pid和命令，不会静默等待。
首次多ARN目标会写入bootstrap state。中途失败后重跑原命令时，已成功成员允许是原目标
的子集，只为缺失成员继续join；原目标身份、顺序或CPU锚点变化会fail closed。

首次基础设施阶段只创建CPU和首个基线GPU集群所需的namespace、token、IAM、NAT白名单
及Private Hosted Zone VPC关联；其他GPU ARN不会提前获得网络权限。每个后续join只增加
自己的独占资源。多个集群共用同一VPC时只关联一次，移除其中一个集群不会解除仍被其他
集群使用的VPC。

状态位于`site.yaml`同目录的`join-cluster/<arn-hash>/state.json`。提交`site.yaml`
前失败会自动清理数据面、发布FAILED/ROLLED_BACK并回收本次IAM/网络变更；提交阶段在
membership锁内增量合并site、release state和Aurora registry，不会覆盖并发join。
候选verify证据有效期15分钟，提交前重新检查site、release和registry未漂移。完成这些
可补偿提交后才进入`ACTIVATION_STARTED -> ACTIVE`；该点之后失败保留已部署资源并要求
重跑同一命令fail-forward，不再执行rollback。成功标准是 registry、connection
Secret、Executor、Collector、Reconciler、全部当前Agent和Aurora资源键同时就绪。

移除前必须确认目标集群没有活动 workflow 或 remote command。正常入口是：

```bash
gpu-fault-admin remove-cluster \
  --state-dir /secure/gpu-fault \
  --gpu-cluster-arn \
    arn:aws:eks:us-west-2:123456789012:cluster/gpu-prod-b \
  --confirm REMOVE_GPU_CLUSTER
```

`--gpu-cluster-arn` 与 `deploy`、`join-cluster` 使用同一个 ARN（GPU EKS 或 HyperPod
ARN 均可）；命令自行把它对应到 site 里的内部 cluster id，管理员不需要知道该 id。ARN
不属于任何已纳管集群时命令拒绝执行并列出当前纳管的集群 ARN。

该命令按状态机完成目标GPU集群的数据源停止、队列drain和节点systemd卸载。
join/remove使用同一站点事务锁。独占Route53 VPC关联的解除会保存ChangeInfo，等待
`INSYNC`并确认hosted zone中关联实际消失；若其他剩余GPU集群仍使用同一VPC则保留关联。
Agent/Executor停止后先异步请求namespace删除，再并行执行CPU registry/key清理及
IAM/网络依赖波次清理，最后统一等待namespace消失，并行验证目标缺失、registry、
EKS/HyperPod保留和剩余站点健康。CPU控制面、其他GPU集群及目标GPU EKS/HyperPod均保留。

可以移除最后一个 GPU 集群；CPU 控制面会以显式空 registry `[]` 继续运行，方便以后
重新接入。Runtime Profile 注册锚点是稳定标识，不因当前 GPU 集合为空而重写。

状态和证据位于 `site.yaml` 同目录的
`remove-cluster/<cluster-id>/`（cluster-id 为 site 记录中该 ARN 对应的内部 id）。失败后以完全相同参数重跑，不要删除该目录。

### 5.1 节点失败域映射（自动）

修复并发预算的 `GPU_FAULT_REMEDIATION_MAX_ACTIVE_PER_FAILURE_DOMAIN`（生产固定为 1）
只对 Executor 知道的失败域生效。一个 GPU 集群就是一个 AZ，所以 zone 标签区分不了同一
集群里的任何两个节点；有意义的失败域是 HyperPod instance group、机架/PDU 或网络 leaf。
控制面自身没有节点拓扑，映射 ConfigMap `gpu-fault-failure-domain-map` 由产品从各 GPU
集群的节点标签渲染、校验、apply 并滚动，**管理员不需要运行任何命令**：

- `deploy`（upgrade 与 bootstrap）在控制面 apply 步骤内读取每个已纳管集群的节点
  （与滚动升级共用同一次 `get nodes`），渲染映射，先用 worker 启动时的同一加载器校验
  （非法映射在 apply 之前就被拒绝，不会到达 worker），再 apply ConfigMap，并把内容摘要
  写入 control-worker Pod 模板注解 `gpu-fault.io/failure-domain-map-sha256`：映射变了
  worker 才滚动，没变就不动，不额外 `rollout restart`。
- `join-cluster` / `remove-cluster` 在成员集合确定后同样重新渲染并 apply；节点增删后
  下一次 `deploy` 会自动刷新。**节点变更后没有任何需要手动执行的步骤。**
- 默认标签优先级为 `sagemaker.amazonaws.com/instance-group-name` →
  `topology.kubernetes.io/zone` → `failure-domain.beta.kubernetes.io/zone`。机群带 EC2
  拓扑标签时在 `site.yaml` 的 `spec.failureDomainLabels` 里按"最细的域在前"声明（哪一层
  是机架取决于实例族，所以不默认），例如：

  ```yaml
  spec:
    failureDomainLabels:
      - topology.k8s.aws/network-node-layer-3
      - sagemaker.amazonaws.com/instance-group-name
  ```

  该字段随 site 持久化，每次渲染都读取它；滚动升级的每失败域上限（`upgradeMaxUnavailable`
  相关）读取同一字段、同一函数，两处对"失败域"的定义不会分叉。
- 没有任何所选标签的节点不进入映射：它们不占用 `domain:` 配额，只受 node/cluster/region
  配额约束，不会阻塞修复。滚动升级侧把同一批节点记为 `UNKNOWN` 拓扑并把每波收紧到 1 个节点。
- control-worker 的 `GPU_FAULT_REMEDIATION_FAILURE_DOMAIN_MAP` 从 ConfigMap 的 `map-path`
  键取值且挂载为 `optional`：没有标签的站点得到一份空映射，效果与没有 ConfigMap 相同
  （没有按失败域的限流）；内容非法的映射不会被 apply。deploy 末尾的 role-split verifier
  按 kubelet 的 `optional` 语义解析这一项。
- 需要查看产品会渲染什么时，用只读调试命令
  `gpu-fault-admin failure-domain-map --state-dir "$STATE_DIR" [--output PATH]`：
  它打印每个集群的映射摘要、`unmapped`（没有任何所选标签的节点）和内容摘要，不 apply 任何东西。

## 6. 凭据和证书生命周期

| 对象 | 当前行为 | 管理员要求 |
|---|---|---|
| Aurora 主密码 | Secrets Manager 轮转，CronJob 同步到 Kubernetes，运行中 Pod 经挂载文件重读（不滚动） | 看 `last-refresh-status.json` 年龄与 `GpuFaultAuroraCredentialRefreshStale/Failing`；轮转后核对三角色挂载文件摘要已更新、无认证失败日志 |
| cluster token | 每集群一个当前 token，轮换期可额外接受一个有界期限的退役 token | 用 `gpu-fault-admin rotate-token` 一次完成 registry 重叠窗口、GPU Secret、数据面和节点 Agent 的切换（§6.1、REG-9） |
| Node Action key | 每节点派生 key version 2 | 单节点轮换后重装目标节点 Agent，并验证 generation |
| Node Agent TLS | 每节点安装时生成证书并由签名 heartbeat pin | 证书变化会提升 Agent generation；通过正式节点 rollout 轮换，不回退 HTTP |
| NLB 服务端证书 | bootstrap 自签发并**导入** ACM 的证书（私有 CA，有效期 3650 天，节点持有 CA 公钥）。ACM 不会自动续期导入的证书；`status` 按 `certificateMinValidityDays`（默认 30）提前告警 | 到期前重新签发并导入证书、更新数据面信任链后按正式节点 rollout 切换；没有也不计划有 `renew-certificate` 动词；禁止 `curl -k` |
| execution token | 只存在 CPU 控制面 | 不得下发到 GPU 数据面 |
| 通知邮件通道 | 默认 `channel: sns`：管理员地址是站点 SNS topic 上唯一一条已确认订阅，与 AMP 告警共用，控制面 role 仅持 `sns:Publish`；`channel: ses` 的站点另有已验证的 SES 发件身份 | 订阅失效时 `status` 的 monitoring 检查给 WARN，重跑 `deploy` 会重发确认邮件；从 SES 切到 SNS 只需把 `site.yaml` `spec.notifications.channel` 改为 `sns` 后重跑 `deploy`，旧 SES 身份由 `uninstall` 按注册表删除 |
- `GPU_FAULT_OPERATOR_ACKNOWLEDGEMENT_TIMEOUT_SECONDS`（默认 86400）：等待人工确认的步骤
  （目前只有 `CHECK_MECHANICALS`）的等待上限，同时是含该步骤的工作流执行截止与生命周期的下限。
  按"一个工作日"取值：机械检查天然要等几小时，600 秒的通用步骤上限会让 COLLECT-009 永远过不去；
  不设为无限是为了工作流终会闭合。收紧它即可缩短等待；不得低于通用步骤上限。

### 6.1 cluster token 重叠窗口轮换

registry 里每个 GPU 集群可以同时声明当前 token 和一个**退役中**的 token：
`token_sha256` 是新凭据，立刻生效；`retiring_token_sha256` 是旧凭据，只在
`token_rotation_expires_at` 之前继续被接受。两者必须同时出现或同时缺失，摘要必须不同，
期限必须带时区且相对 `updated_at` 不超过
`gpu_fault.regional.MAX_TOKEN_ROTATION_WINDOW`（7 天）。窗口过期后仍然只接受
`token_sha256`，因此忘记收尾不会让已经切换的 Executor 掉线，只会让还没切换的调用方
fail closed。运行时权威 registry 是 Aurora revision；bootstrap/灾备用的
`GPU_FAULT_REGIONAL_CLUSTERS_JSON` 只在尚无 durable revision 时生效。

轮换的唯一正式入口（管理员不再手工计算摘要、发布 revision 或滚动数据面）：

```bash
gpu-fault-admin rotate-token \
  --state-dir /secure/gpu-fault \
  --gpu-cluster-arn arn:aws:eks:us-west-2:123456789012:cluster/gpu-prod-a \
  --reference CHG-12345
```

1. **适用条件**：目标集群无 `PENDING`/`LEASED`/`WAITING` remote command，无未完成
   release 事务；不需要停止故障处置。
2. **影响范围**：仅目标 GPU 集群的 registry 条目、connection Secret、Executor /
   Completion Watcher / Resource Collector 三个 Deployment，以及全部节点 Agent（按
   release 同款 fleet wave 逐波重装）。
3. **只读检查**：`gpu-fault-admin status` 健康；
   `<state-dir>/rotate-token/<cluster-id>/state.json` 不是 `IN_PROGRESS`。
4. **执行命令**：如上。命令按顺序执行：发布携带 `retiring_token_sha256` 的重叠
   revision → 更新 GPU connection Secret → 滚数据面 → 按 wave 重装节点 → 等待控制面
   日志连续 `--quiet-seconds`（默认 180）内没有
   `regional cluster <id> authenticated with the retiring token` → 原子写
   `secure/<cluster-id>.token`（旧文件保留为 `.retired-<时间>`）→ 发布删除退役摘要的
   revision。`--window-minutes`（默认 120，按分钟或小时设置，不按天）、`--keep-window`、
   `--rollback` 及状态机、续跑规则见 REG-9。
5. **成功标准**：输出 `status=COMPLETED`；`GET /v1/regional/clusters` 中该集群
   `retiring_token_sha256_present=false`（两个摘要本身始终脱敏）；token 文件摘要等于输出的
   `new_token_sha256`；`warnings` 为空。
6. **回滚**：`TOKEN_FILE_WRITTEN` 之前用同一命令加 `--rollback`（Secret → 数据面 →
   已重装节点 → 只含旧摘要的 registry，全程无中断）；之后旧 token 已退役，改做一次新
   轮换。
7. **证据**：`<state-dir>/rotate-token/<cluster-id>/state.json` 与命令输出 JSON，只含摘要。

轮换过程中不修改 execution token，也不把任一 cluster token 下发到其他 GPU 集群。真机验收见
`GF-REGIONAL-AUTH-016`。

## 7. 按症状排障

| 症状 | 首查项 | 详细参考 |
|---|---|---|
| CPU Pod CrashLoopBackOff | registry、Aurora DSN、启动守卫、配置重复 | REG-14.1 |
| remote command 一直 PENDING | Executor claim、token、CA、cluster ID、owner、protocol | REG-14.2 |
| command 长期 LEASED | Executor Pod、lease renewal、结果回传 | REG-14.3 |
| step FAILED 原因不清 | `status_source` 和 executor traceback | REG-14.4 |
| 全部 Agent 非 ACTIVE | 节点 token、systemd、artifact/config/profile pin | REG-14.5 |
| operator API 返回 403 | execution token 与 cluster token 是否混用 | REG-14.6 |
| HyperPod outcome unknown | CloudTrail、节点实际状态、幂等提交记录 | REG-14.7 |
| Profile同版本内容漂移 | 发布新的profile version，不得覆盖原版本 | REG-8.1.3 |
| 升级后Agent未收敛 | 保持compatible窗口，检查Reconciler/Installer，不得强制finalize | REG-8.1.4 |
| Executor verifier失败 | IRSA、token、CA、owner、artifact和protocol | REG-14 |
| SNS确认邮件重复到达 | 同Topic是否有重复confirmed/pending、bootstrap pending checkpoint | REG-7 |
| StaleAttemptObservation | 训练Pod、Completion Watcher、Observation投递/outbox | REG-14 |
| workflow FAILED 但 incident 是 `RECOVERED`，reason 含 `diagnostic inconclusive` | 设计如此：该 workflow 只含取证/诊断/验证步骤，失败即「诊断无结论」，incident 关闭、该 incident 的 marker 退役、发 `DIAGNOSTIC_INCONCLUSIVE` 邮件；节点没有被隔离也不需要放行，作业可照常重启 | `详细设计-v2.md` §6.3 |
| XID 计划全部 `BLOCKED NEEDS_OPERATOR`，原因 `workload state is UNKNOWN` | 集群 600 s 内既无 attempt 观测也无 Completion Watcher 覆盖心跳（`get_workload_coverage` 的 `scanned_at` 年龄）；watcher 停机即 UNKNOWN 属预期，修 watcher 而不是放行 | `部署和运维手册.md` `GPU_FAULT_WORKLOAD_CONTEXT_FRESHNESS_SECONDS` |

排障顺序固定为：

```text
release/module digest
  -> 身份与 TLS
  -> queue/lease
  -> Executor owner 与 protocol
  -> Node Agent/Collector
  -> provider 实际状态
```

本节按管理员观察到的症状进入。若入口是一条 AMP 告警，直接按告警名进入 §8 的分诊卡，
不要先在本表反查症状。

## 8. 告警处置索引

本节是 `deploy/observability/amp-rules.yaml` 每条告警的收件人入口。每条告警的
`annotations.runbook_url` 指向本节同名小节，`scripts/verify-regional-alerting.py`
校验双向一致：告警缺 `runbook_url`、`runbook_url` 与告警名不符、指向的小节不存在、
或本节有小节却没有告警指向它，都会让验收失败。

小节标题直接用告警名而不是 `8.1` 编号，因为 `runbook_url` 的锚点必须能从告警名机械
推导（小写、去掉非字母数字），编号会在插入告警时漂移。

本节是三行分诊卡，不是 §2 的七项 runbook：每条只给「含义 / 首查 / 边界」，需要执行
动作时跳到卡片里引用的正式 runbook。任何告警都不得通过上调阈值、删除 Store 记录或
静音规则来消除。

### 8.0 仪表盘

`deploy/observability/dashboards/*.json` 是 8 张 Grafana 仪表盘：1 张总览加上
`amp-rules.yaml` 的 7 个告警分组各 1 张。它们由 `scripts/build-grafana-dashboards.py`
从 `scripts/grafana_dashboard_catalog.py` 的面板表生成，`make grafana-dashboards-check`
保证签入的 JSON 与生成结果逐字节一致。生成器会读 `amp-rules.yaml`：凡告警表达式以
`> N` / `>= N` / `< N` 结尾，绘制该指标的面板就画一条同值阈值线（critical 红、warning
橙）；每个面板的描述里列出它覆盖的告警名、`for` 时长和本节卡片的锚点，所以从面板到
分诊卡只有一步。46 条告警每条至少落在一个面板上（`tests/test_grafana_dashboards.py`
断言这一点，阈值也一并断言），阈值改了规则而没重新生成，门禁会红。

导入路径：`gpu-fault-admin deploy` 的 Grafana 供给步骤在部署时自动导入到
「GPU Fault Recovery」文件夹并绑定 uid 为 `gpu-fault-amp` 的 Prometheus（AMP）数据源；
手工回退是 Grafana → Dashboards → New → Import → 上传对应 JSON → 选择 AMP 数据源。
每张仪表盘顶部有 `control_plane_cluster` / `region` 变量，画了按集群指标的还有
`cluster_id` 多选变量（默认 All）。

**登录与授权。** 部署侧的导入用的是工作区服务账号的短期 token，不依赖任何人的登录权限；
但人要打开仪表盘仍走工作区自己的认证方式（Amazon Managed Grafana 只支持 IAM Identity Center
或 SAML，没有本地用户名密码）。工作区 id 与地址在 bootstrap state 的
`resources.monitoring_install.grafana.dashboards_url`（形如
`https://<workspace-id>.grafana-workspace.<cpu-region>.amazonaws.com/dashboards/f/gpu-fault-recovery`）。
第一次打开前，给自己的 Identity Center 用户授权，这是部署留下的唯一手工步骤，有两种做法：

1. 部署时直接传 `gpu-fault-admin deploy … --grafana-viewer <sso-user-id>`，导入完成后 deploy 代为
   授予 VIEWER（用户 id 写错会让部署失败，改对再跑一次即可）。
2. 不传时，deploy 结束会在 stderr 打印仪表盘地址和针对本站点 workspace 的那一行命令，把
   `<sso-user-id>` 换成自己的 Identity Center 用户 id 后原样执行（在 CPU 集群所在 Region）：

```bash
aws grafana update-permissions --region <cpu-region> --workspace-id <workspace-id> \
  --update-instruction-batch '[{"action":"ADD","role":"VIEWER","users":[{"id":"<sso-user-id>","type":"SSO_USER"}]}]'
```

用户 id 在 IAM Identity Center 控制台的用户详情页；命令行查法是 `aws identitystore list-users
--identity-store-id <store-id> --filters AttributePath=UserName,AttributeValue=<用户名>`，
`<store-id>` 来自组织启用 Identity Center 的主 Region 的 `aws sso-admin list-instances`。

角色选择：值班看盘用 `VIEWER`；要改面板或数据源才给 `EDITOR` / `ADMIN`，且改动会在下次
`gpu-fault-admin deploy` 重导入时被签入的 JSON 覆盖——长期修改必须改
`scripts/grafana_dashboard_catalog.py` 再重新生成。撤销把 `"action":"ADD"` 换成 `"REVOKE"`。
授权后用 Identity Center 门户或直接打开上面的地址登录；`Alerting → Alert rules` 选 AMP 数据源
即可看到 46 条规则的实时状态，与下文卡片一一对应。

看盘的读法与卡片一致：阈值线之上（或 `< N` 型面板的阈值线之下）持续超过 `for` 时长
才是告警；总览的「Alerts firing」面板直接读 AMP 的 `ALERTS{alertstate="firing"}`，
名字就是下面的卡片名。

### GpuFaultCollectorSilent

- **含义**：某 GPU 节点的某个 collector channel 超过静默阈值没有成功投递批次；该节点
  的故障信号此刻不可信，策略对它是盲的。
- **首查**：节点 systemd 服务状态、Node Agent TLS 与私有 CA 信任链、cluster token、
  collector outbox 积压（节点上 `gpu-fault-collector outbox --collector kernel
  stats|list|requeue-dead --yes`；`list`/`stats` 只显示元数据，不打印载荷）、最后一次成功
  批次时间戳。「有没有投递、多久一次」看
  `GET /v1/collector-status/{cluster_id}`：`collector_status` 在每个被接受的批次上更新，
  而 raw evidence 只在批次带 finding、采集错误或非 `health-summary` 原因时才写——健康
  节点的 `GPU_METRICS` 证据为 0 条是设计如此，不是采集器死了；「采集器看到了什么」才看
  evidence。
- **边界**：不得用 `curl -k` 验证连通性，不得上调静默阈值消警。修复入口 REG-6、
  REG-14.5。

### GpuFaultCollectorCollectionErrors

- **含义**：某 collector channel 上有节点「在按时投递、但投递的内容是失败」——
  `last_error_at` 不早于 `last_success_at`。它和 `GpuFaultCollectorSilent` 是两种
  状态：这类节点连通性正常、批次不迟到，所以在最后一次成功老化到静默阈值之前
  （node-logs 是一刻钟）静默告警看不见它，而节点其实已经在丢数据。
- **首查**：`GET /v1/collector-status/{cluster_id}` 读该 channel 的 `errors` 字段，
  它是节点自己写的原因（例如 journalctl 退出码、训练日志轮转、放弃的时间窗）；再看
  节点上 collector 的 journal。
- **边界**：这条告警自愈的唯一方式是节点真的成功投递一次——不要改阈值、不要删
  `collector_status` 记录。修复入口 REG-6、REG-14.5。

### GpuFaultCollectorMetricsSnapshotStale

- **含义**：`/metrics` 里的 collector 静默快照超过 120 秒没有刷新，说明
  `GpuFaultCollectorSilent` 本身已经失去数据来源。
- **首查**：抓取目标是否指向 ingress 副本而不是 worker；ingress 到共享 Store 的
  连通性和 Aurora 凭据刷新 CronJob。
- **边界**：在快照恢复前不要把 `GpuFaultCollectorSilent` 的静默判为「已恢复」。
  详见 REG-14.1。

### GpuFaultTelemetryRemoteWriteFailing

- **含义**：ADOT 到 AMP 的 remote_write 在丢点。超过 120s 重试窗口还没成功的批次会被
  直接丢弃且不再重发，所以 AMP 里的数据是有洞的：本节其余全部告警都在这些洞上求值，
  此时「图很干净」不等于「机群没事」。
- **首查**：`kubectl -n gpu-fault-system logs deploy/gpu-fault-adot` 里的
  `Exporting failed. Dropping data.` 及其 `error`；sigv4 role 与 AMP workspace 的
  写入限流。指标自带 `error_type` / `error_permanent` 两个标签，按它们拆开看能区分
  被拒（权限/限流）和暂时性失败。
- **边界**：计数器停止上涨不代表已恢复——collector 重启同样会让它归零。要用
  `otelcol_exporter_sent_metric_points` 恢复上涨来确认。不得靠放宽
  `max_elapsed_time` 消警：那只会把丢点换成 OOMKill（容器上限 256Mi）。
- **注意**：这些 `otelcol_*` 指标名没有 `_total` 后缀，是从固定版本镜像
  （aws-otel-collector v0.49.0）的 `:8889` 实测得到的，与上游文档里带后缀的写法不同。
  改镜像版本时必须重新实测，否则告警会静默失效。

### GpuFaultTelemetryRemoteWriteQueueSaturated

- **含义**：ADOT 的重试队列已用掉 80% 以上，写 AMP 的速度跟不上抓取速度，下一波积压
  会被丢弃而不是延迟送达。这是 `GpuFaultTelemetryRemoteWriteFailing` 之前唯一的预警。
- **首查**：`otelcol_exporter_queue_size` / `otelcol_exporter_queue_capacity` 的走势；
  AMP workspace 的 ingestion 限流；控制面副本数是否刚扩容导致时间线数量上涨。
- **边界**：不得靠加大 `sending_queue` 消警——容器上限 256Mi、`GOMEMLIMIT` 220MiB，
  队列换来的是 OOMKill。

### GpuFaultAdotSelfMetricsMissing

- **含义**：ADOT 自身的 telemetry（`up{job="gpu-fault-adot-self"}`）在 AMP 里缺失。
  要么 collector 没在跑，要么 remote_write 完全失败——后一种情况下
  `GpuFaultTelemetryRemoteWriteFailing` 无法触发，因为它的计数器走的是同一条通路。
- **首查**：先和 `GpuFaultControlPlaneMetricsMissing` 对比。两条同时在响：collector
  或写入通路整体挂了，查 Pod 状态与 export 错误日志。只有这一条在响：自身 telemetry
  reader（`service.telemetry` 绑在 127.0.0.1:8889）或 `gpu-fault-adot-self` 的 keep
  过滤被改坏了。
- **边界**：这条告警存在时不得判定「无故障」，理由同
  `GpuFaultControlPlaneMetricsMissing`。

### GpuFaultControlPlaneMetricsMissing

- **含义**：`up{job="gpu-fault-control-plane"}` 缺失，整个 CPU 控制面在监控上不可见，
  本文件其余全部告警同时失效。
- **首查**：ingress Pod 状态与启动守卫日志、Service/target 发现、抓取配置里的
  namespace 和端口。
- **边界**：这条告警存在时不得判定「无故障」。详见 REG-14.1。

### GpuFaultProcessorQueueDepthHigh

- **含义**：处理器全局队列超过容量 70%，还没有拒收，但排队时延已经在增长。
- **首查**：control-worker 副本数与 lane 占用、Aurora 延迟、是否有单集群 fault 风暴
  （对比 `GpuFaultProcessorClusterBacklogHigh`）。
- **边界**：扩容走 [管理员容量配置](管理员容量配置.md) 的 `gpu-fault-admin config`，
  不下调告警阈值，也不打开 queue bypass。

### GpuFaultProcessorQueueDepthCritical

- **含义**：队列超过容量 90%，距离 admission 拒收只剩一步。
- **首查**：同 `GpuFaultProcessorQueueDepthHigh`，并确认 worker 是否在 lane 上互相
  阻塞（`gpu_fault_processor_lane_wait_seconds_max`）。
- **边界**：这是维护窗口外允许扩 worker 副本的少数情况之一，但仍需变更单和回滚方案。

### GpuFaultProcessorOldestRequestDelayed

- **含义**：最老的排队请求已经等待超过 30 秒。队列深度可能正常——这条抓的是长尾饥饿，
  通常是某个 lane 被单个慢请求占住。
- **首查**：`gpu_fault_processor_phase_oldest_seconds` 定位阶段、
  `gpu_fault_processor_claimed_not_started` 是否非零、Aurora 连接池等待。
- **边界**：不要靠重启 worker 清队列；先取到卡住的阶段和请求 ID。

### GpuFaultProcessorClusterBacklogHigh

- **含义**：单个 GPU 集群的队列超过其配额 70%，说明积压集中在一个集群而不是全局过载。
- **首查**：该集群的 collector 是否在重放、Executor 是否在 claim、是否有节点级
  fault 风暴。再看 `gpu_fault_processor_cluster_queue_oldest_age_seconds{cluster_id}`：
  claim 窗口是全区域 FIFO，一个集群的风暴会拖慢其他集群，这条按集群给出各自最老请求的等待时长。
- **边界**：单集群配额是隔离手段，不得为消警而扩大该集群配额挤占其他集群。

### GpuFaultWorkflowMetricScanTruncated

- **含义**：workflow 表已超出 `/metrics` 的扫描预算，
  `gpu_fault_workflow_step_total`、`gpu_fault_workflow_duration_seconds`、
  `gpu_fault_closed_loop_milestone_seconds` 三族只覆盖最新的一段，不再是全量普查。
  `gpu_fault_workflow_total` 仍是数据库侧聚合，不受影响。
- **首查**：`gpu_fault_workflow_scan_size` 与 `gpu_fault_workflow_scan_limit` 的差距、
  workflow 保留策略是否停止清理、是否有 workflow 风暴在制造新记录。
- **边界**：先确认是保留策略失效还是真实增长。仅调大
  `GPU_FAULT_METRICS_WORKFLOW_SCAN_LIMIT` 会把成本转给 Aurora 和每次抓取，
  不解决表不再收敛的问题。

### GpuFaultAttemptObservationMetricScanTruncated

- **含义**：attempt observation 表已超出 `/metrics` 的扫描预算，
  `gpu_fault_ambiguous_attempt_ownership_current` 与
  `gpu_fault_stale_attempt_observations` 只覆盖最新的一段。此时独占所有权不变量是
  在切片上求值的，较老观测之间的所有权冲突不会被报出来，
  `GpuFaultExclusiveNodeOwnershipInvariantViolation` 可能因此静默。
- **首查**：`gpu_fault_attempt_observation_scan_size` 与
  `gpu_fault_attempt_observation_scan_limit` 的差距、observation 保留清理
  （`GPU_FAULT_ATTEMPT_OBSERVATION_MAX_AGE_SECONDS`，默认 7 天）是否还在执行、
  是否有 attempt 风暴或 Completion Watcher 停止终态化导致行数不收敛。
- **边界**：切片保留的是最新的行，而所有权与过期两族的信号都在最近端，所以这是
  warning 而不是不变量失效。仅调大 `GPU_FAULT_METRICS_OBSERVATION_SCAN_LIMIT`
  会把成本转给 Aurora 和每次抓取；先确认表为什么不再收敛。

### GpuFaultProcessorAdmissionRejected

- **含义**：已经在拒收请求。被拒的 fault 事件依赖客户端重投，存在真实的检测丢失窗口。
- **首查**：拒收按路径和集群的分布
  （`gpu_fault_processor_admission_rejections_by_path_total`、`_by_cluster_total`）、
  telemetry spool 是否同时在拒收。
- **边界**：critical。先恢复容量再回溯这段窗口内是否有未处理的 XID/SXID。

### GpuFaultStoreIoSaturated

- **含义**：Store I/O lane 在用容量超过 90%，处理器随时可能开始拒 Store 操作。
- **首查**：Aurora CPU 与连接池等待、是否有全表扫描型请求、
  `gpu_fault_store_io_admission_wait_seconds_max`。
- **边界**：扩 lane 宽度前先确认不是单一慢查询；把 lane 调宽只会把压力转给 Aurora。

### GpuFaultStoreIoRejected

- **含义**：已经在拒 Store I/O。此时写入路径不完整，编排状态可能落后于真实集群状态。
- **首查**：同 `GpuFaultStoreIoSaturated`；并检查是否有 workflow 因此转入重试或
  fail-closed。
- **边界**：critical。恢复后必须核对该窗口内的 workflow 与节点实际状态是否一致。

### GpuFaultProcessorP95Slow

- **含义**：请求处理 p95 超过 5 秒并持续 10 分钟，是容量类告警里最早的领先指标。
- **首查**：event loop lag、Aurora 连接池等待、是否刚做过发布（对比 release digest）。
- **边界**：单独出现时属于 warning；与队列或 Store 告警同时出现时按后者的优先级处置。

### GpuFaultProcessorExpiredLeasesReclaimed

- **含义**：有排队请求被 worker 领取（LEASED）后超过 lease 仍没完成，被周期回收任务退回
  PENDING。请求没有丢，但至少多等了一个 lease；每一次非零增长都对应一个中途死掉或卡住的
  处理器 worker。队列深度类告警看不到它——回收前后深度不变。
- **读的是哪个指标**：`gpu_fault_processor_expired_leases_reclaimed_total`（每进程计数，
  规则按 `control_plane_cluster, region` 求和后取 10 分钟增量）。
- **首查**：同一窗口内 control-worker Pod 是否有重启（`kubectl -n <ns> get pod` 的
  RESTARTS 列与发布时间对照）；`gpu_fault_processor_phase_oldest_seconds` 是否有某个阶段
  长期偏高；`gpu_fault_periodic_job_errors_total{job=…}` 回收任务本身有没有报错。
  滚动发布期间出现一两次是预期的；发布窗口之外持续增长才是 worker 在挂。
- **边界**：不得为消警调长 `GPU_FAULT_PROCESSOR_LEASE_SECONDS`（那只是让卡住的请求多等
  一会儿）；也不要手工把 LEASED 行改回 PENDING，回收任务就是做这件事的。

### GpuFaultProcessorCounterDrift

- **含义**：处理器队列的按集群深度读的是分片计数器而不是 `COUNT(*)`，两者连续 5 分钟不一致。
  此时 `gpu_fault_processor_cluster_queue_depth`、按集群配额的 admission 判定都在用一个错
  的数。周期任务每 `GPU_FAULT_PROCESSOR_COUNTER_DRIFT_SCAN_SECONDS` 对比一次，单次采样可能
  正好跨在一次批量提交上，所以规则取 5 分钟窗口内的最小值。
- **读的是哪个指标**：`gpu_fault_processor_counter_drift_abs`（|期望总数 − 计数器总数|）
  与 `gpu_fault_processor_counter_mismatched_clusters`（有多少个集群的分片计数器不等于真实
  行数）；两者任一持续非零都算。
- **首查**：漂移量是稳定常数还是在增长——常数通常是一次事务只写了表没写计数器，增长说明
  写路径还在持续漂；对照 `GpuFaultProcessorClusterBacklogHigh` 是否同时在误报或漏报；
  `gpu_fault_periodic_job_errors_total` 看对比任务有没有失败。先看 `gpu_fault_processor_counter_mode`
  当前哪一边为 1：`dual` 下对比的是 legacy 行，`partitioned` 下对比的是分片；模式刚切换后的第一个
  扫描周期出现一次性漂移是预期的，持续 5 分钟才算。
- **边界**：计数器由 backfill 路径从队列表重建，不得手工改计数器行；也不要靠重启 worker
  消警，重启不会重建计数器。

### GpuFaultTelemetrySpoolListenerDown

- **含义**：telemetry spool 消费者的 `LISTEN/NOTIFY` 断开，退化为轮询。功能仍然正确，
  时延变大。
- **首查**：Aurora 连接是否被中间层掐断、spool worker Pod 重启历史、
  `gpu_fault_telemetry_spool_fallback_polls_total` 的增速。
- **边界**：不要靠禁用通知来消警；轮询是降级路径，不是目标状态。

### GpuFaultTelemetrySpoolDataLoss

- **含义**：spool 丢弃了常规样本。丢弃只作用于常规遥测，不作用于 fault 事件，但
  主机与网络趋势会出现空洞。
- **首查**：`gpu_fault_telemetry_spool_depth` 与 `_bytes` 是否触到上限、丢弃前是否
  先出现 `GpuFaultTelemetrySpoolDrainDelayed`。
- **边界**：critical。丢弃窗口内的主机健康结论不可用于事后判定。

### GpuFaultTelemetrySpoolAdmissionRejected

- **含义**：spool 在入口拒收常规样本，比 `DataLoss` 更早一环。
- **首查**：入口批量参数、in-flight 字节上限、是否有单集群刷量。
- **边界**：同上，先恢复容量再评估遥测空洞范围。

### GpuFaultTelemetrySpoolReplayError

- **含义**：spool 回放失败。已落盘的样本没能进入处理路径。
- **首查**：spool worker 日志里的异常类型、`_abandoned_total` 与 `_superseded_total`
  的比例、Store schema 版本是否与 wheel 匹配。
- **边界**：critical。回放失败可能是版本漂移，先做 REG-10A 制品一致性校验。

### GpuFaultTelemetrySpoolDrainDelayed

- **含义**：spool 中最老的样本超过 60 秒未排空，是丢弃与拒收的领先指标。
- **首查**：spool worker 副本数与 lane 占用、Aurora 写入延迟。
- **边界**：warning，但持续存在时按容量问题处置，不要等到 `DataLoss` 才动作。

### GpuFaultRemoteCommandUnclaimed

- **含义**：某个 PENDING remote command 超过 600 秒没有任何 Executor claim。周期清扫会在
  `GPU_FAULT_REMOTE_COMMAND_CLAIM_DEADLINE_SECONDS`（默认 900 秒）后把它置为 FAILED 并触发
  `GpuFaultRemoteCommandUnclaimedExpired`；本告警是命令还能被领取时更早一步的信号。
- **首查**：该步骤的 runtime profile owner 是否被目标集群 Executor 实际构造出的
  adapter 广告、Executor 到控制面的 TLS、cluster ID 与 owner 是否匹配、protocol
  version 是否在 compatible 窗口内。
- **边界**：critical。不得手工把命令改成终态；按 REG-14.2 逐项排查。

### GpuFaultRemoteCommandExecutorInternalError

- **含义**：Executor 因自身缺陷失败一条命令，而不是拒绝一个不安全动作。
- **首查**：Executor Pod 日志里的 traceback；重试前先读栈。告警用的是保留期内最新的
  错误时间戳，所以终态记录清理不会被误读成计数器归零。
- **边界**：critical。这是代码缺陷通道，修复走发布流程，不通过重试掩盖。详见
  REG-14.4。

### GpuFaultUnknownProductFamily

- **含义**：出现了没有映射到 NVIDIA Catalog family 的 GPU 产品；该产品上的 XID
  自动恢复是 fail-closed 的。
- **首查**：告警的 `product` 标签、当前 pinned catalog 版本、节点 instance type。
- **边界**：把产品前缀加入 pinned catalog 的 `spec.catalog.productFamilies` 并走正式
  发布，不得在线放宽策略或按未知产品猜测 family。

### GpuFaultExclusiveNodeOwnershipInvariantViolation

- **含义**：同一个 GPU 节点被多个「新鲜」active attempt 同时声明所有权，节点变更已经
  fail-closed。过期观测不计入所有权，另有独立告警。
- **首查**：告警标签里的 `cluster_id` 与 `gpu_node`、这些 attempt 对应的训练 Pod 是否
  都真实存在、Completion Watcher 的投递是否重复。
- **边界**：critical。不得手工拼造或删除 attempt/allocation 来解除歧义；处置必须引用
  真实 workload observation。见 §9。

### GpuFaultStaleAttemptObservation

- **含义**：该节点上有超过 120 秒未刷新的 `PENDING/RUNNING` attempt 观测。值是 attempt
  数量，不是邮件合并的告警实例数。
- **首查**：训练 Pod 是否仍存在、Completion Watcher 的 Ready 与日志、
  `gpu-fault-completion-watcher-outbox` 的内容。
- **边界**：等待正式的 `STOPPED/FAILED/SUCCEEDED` observation 覆盖；不得直接删 Store
  记录来消警。

### GpuFaultFleetRolloutFenceStuck

- **含义**：该集群存在一条非终态的 fleet deployment，已经超过 2 小时。fleet 围栏会把该
  集群上**所有**破坏性 remediation（GPU reset、reboot、隔离恢复）挡在它后面，所以这条
  告警的实际含义是「这个集群的自动恢复当前是停摆的」，而不是「一次升级慢了」。
- **为什么用时长而不是条数**：一次正常的区域 roll 本来就会让 deployment 处于非终态，这正
  是围栏存在的理由。四节点 p5en 观测到的最长 roll 约 7 分钟，2 小时远在其外。
- **读的是哪个指标**：`gpu_fault_fleet_rollout_fence_age_seconds{cluster_id}` 是最老那条
  非终态 deployment 的年龄。同集群的
  `gpu_fault_fleet_rollout_never_started{cluster_id}` 是分诊位：
  - **非零** —— 这条记录一个 wave 都没起过（`DeploymentStatus.PLANNED` 是派生态，只有全部
    节点仍为 `PENDING` 时才成立）。说明创建它的那次发布在写完记录后就死了，没有任何东西
    在飞。2026-09-03 就是这一类，围栏锁了 36 小时。
  - **为零** —— rollout 真的卡在某个 wave 中间。先查该 wave 节点的 Agent lease、
    `gpu-fault-node-installer-reconciler` 日志，再决定 retry 还是 rollback。
- **首查**：`gpu-fault-admin status` **不报** fleet deployment，要看 `/metrics` 的上述两个
  指标，或在控制面 Pod 内读 `list_active_fleet_deployments(<cluster_id>)`。
- **边界**：不得删 Store 行，不得关闭围栏，也不得调大 2 小时阈值来消警。
  终态化只能走发布引擎：对被放弃的记录，下一次 `rollout-regional-release`
  的 `rollback-rollout-cleaned` 阶段会扫掉同 release 的残留，而新建 deployment 时
  `supersede_never_started_deployments` 会把同集群从未启动的旧记录置为终态。

### GpuFaultWorkflowLifetimeExceeded

- **含义**：一条恢复工作流从首次被领取起超过了生命周期上限（作业工作流
  `GPU_FAULT_JOB_WORKFLOW_MAX_LIFETIME_SECONDS`、单节点工作流
  `GPU_FAULT_NODE_WORKFLOW_MAX_LIFETIME_SECONDS`，默认都是 1 小时），控制面已把它写成 FAILED、
  取消在飞远程命令，incident 进入 ESCALATED；此后同节点/同作业的事件只记录到该 incident，
  不再自动修复，直到运维处置完、incident 关闭。
- **读的是哪个指标**：`gpu_fault_workflow_lifetime_exceeded_total`（执行器计数，按进程累计）。
- **首查**：`gpu-fault-admin status` **不列** incident。incident_id 取自这次升级发出的
  hardware-escalation 通知邮件（正文 `Incident: <id>`），计数看 Grafana `gpu-fault-overview`
  Closed loop 面板或 `/metrics` 的 `gpu_fault_incidents_by_state{state="ESCALATED"}`；然后
  `GET /v1/incidents/{incident_id}`、`GET /v1/workflows/{workflow_id}` 读该 workflow 最后一条
  FAILED 步骤记录里的 `workflow_lifetime_exceeded` 与被取消的远程命令；看它经历了哪几级升级
  （`branch_escalation_counts`）。
- **处置**：人工判断节点是否需要换机或送修；处理完把 incident 关闭，之后该节点的新事件才会
  重新触发自动修复。不要通过延长生命周期来"修好"这个告警。
- **相邻计数**：`gpu_fault_hardware_escalation_chain_terminated_total` 统计"升级出来的
  support 工作流自己也失败了，但没有再开第三条"的次数——升级链在第二级封顶，incident 保持
  ESCALATED 等运维；`gpu_fault_hardware_escalation_containment_refused_total` 统计含容步骤全部
  因安全拒绝（例如目标节点在 Kubernetes 里不存在）而失败、support 工作流只编 FREEZE_EVIDENCE
  与 ESCALATE_SUPPORT 的次数。两者按进程累计，任一增长都意味着有 incident 需要人工判断节点身份。

### GpuFaultJobWorkflowNodeBusyTimeout

- **含义**：规则 A 触发。一个训练作业的节点正被别的修复工作流占用，作业只等
  `GPU_FAULT_JOB_WORKFLOW_NODE_BUSY_WAIT_SECONDS`（默认 4 分钟）这一个窗口；修复在窗口内完成
  作业就继续（排队的作业工作流被派发，`after_incident` 重启把作业重启）。窗口过了作业不再重启：
  还在跑的作业以 STOP_WORKLOADS（带控制面发起者标记 `termination_initiator_incident_id`）停掉，
  已经死掉的作业其重启计划失败；工作流 FAILED、incident ESCALATED。系统自己停掉的作业不会被
  重启——完成服务看到发起者标记只记 NO_ACTION。占用节点的那条修复工作流不受影响。
  派发器（作业工作流未开始）与执行器（`RESTART_WORKLOAD` 的 `requires_incident_state` 前提已在等）
  读同一个变量，后者的步骤记录以 `reason=NODE_REMEDIATION_TIMEOUT` 收尾。窗口从派发器为该行
  记的**首个** `HOLD(node under remediation)` 事件起算（`details.held_since`），不是 `created_at`
  ——被聚合窗 `not_before` 或未终态前驱挡住的时间不算等待（D-11）；执行器侧的顺序循环每步都
  重查作业是否已被撤回。同一步骤的连续等待折叠成一条 STEP_ATTEMPT，`attempt` 是「有变化的
  尝试数」，等得过久时 `details.step_waiting_slow=true`（RF-2）。
- **读的是哪个指标**：`gpu_fault_workflow_dispatch_node_busy_timeouts_total`（派发器放弃）；执行器侧
  的放弃是 STEP_ATTEMPT 事件的 `NODE_REMEDIATION_TIMEOUT` 码。
- **首查**：读失败工作流的 `terminal_failure_reason`，里面列出哪些节点被哪条工作流占着；
  确认那条节点工作流是否仍在正常推进（没有的话它自己会触发生命周期告警）。
- **处置**：节点修复完成后作业方重新提交即可——控制面不会替它重启；若作业反复落到正在修复的
  节点上，检查调度器为什么把作业放到了被 cordon 的节点。

### GpuFaultProcessorRetryHorizonFailures

- **含义**：处理器队列里某条请求的执行或完成持续失败，被释放重试的累计时间超过了
  `GPU_FAULT_PROCESSOR_RETRYABLE_RESPONSE_MAX_AGE_SECONDS`（默认 300 秒），控制面把它以
  503 完成、结束流转，车道因此解封。请求的业务副作用没有被确认。
- **读的是哪个指标**：`gpu_fault_processor_retry_horizon_failures_total`；配套看
  `gpu_fault_processor_completion_failure_releases_total`（每次带退避的失败释放）。
- **首查**：处理器日志里 `completed as failed past its retry horizon` 一行给出
  request_id、path、failure 与 retry_count；按 request_id 读完成体里的 JSON。
- **处置**：确定性失败通常是 handler 缺少参数、存储写入被拒或数据面返回 5xx；修复根因后
  由数据面重投同类事件，不要手工改队列行。

### GpuFaultRecoveryBlockedBacklog

- **含义**：`BLOCKED` 是 fail-closed 终态——证据、身份或 workload 状态不足以继续变更
  节点。单条属于正常安全行为；持续积压说明没有人在处置，每条都对应一个长期不回训练池
  的 GPU 节点。
- **读的是哪个指标**：`gpu_fault_workflow_blocked_unreconciled`，即「`BLOCKED` 且没有
  已验证 restore successor」的条数，与发布前置检查判定 workflow 是否阻塞发布用的是同一
  判据。它**不是** `gpu_fault_workflow_total{status="BLOCKED"}`：后者统计的是历史全表，
  `BLOCKED` 又是终态，所以那个数字只会因 `workflow-reconcile` 或归档而下降——同 incident
  的 successor 已经把节点放回训练池之后它仍然不降，据此告警会按 `repeat_interval` 一直
  重发。所以本告警静默的正确含义是「没有节点还被 BLOCKED 记录扣着」，不是「表里没有
  `BLOCKED` 行」。
- **首查**：逐条读 workflow 的 blocking reason 与 incident；区分「等管理员决策」
  （见 §9）和「等证据」两类。
- **边界**：不得通过改 Store 行或手工改 workflow JSON 清除 `BLOCKED`，也不得为了消警调
  大 remediation budget。已由同 incident 的成功 successor 收敛的历史记录只能走
  `gpu-fault-admin workflow-reconcile`，见 §10.2；该命令要求存在已验证 successor 且
  `restore_reconciliation_reasons` 为空，不满足时直接拒绝写入，这是设计如此。

### GpuFaultClosedLoopSlow

- **含义**：最近 6 小时内达成 containment 里程碑的 workflow，平均检测到隔离耗时超过
  15 分钟。含义是这段时间里新的训练尝试仍在落到已知故障的节点上。
- **首查**：`gpu_fault_closed_loop_milestone_seconds_max{milestone="containment"}`
  定位最坏样本；对比容量类告警和 `GpuFaultRemoteCommandUnclaimed`，慢通常来自排队或
  claim 延迟而不是策略判定。
- **边界**：这条告警按窗口内均值计算。保留策略归档旧记录时分子会下降，此时告警会静默
  ——它可能漏报，不会误报，所以静默不等于时延达标。

### GpuFaultNotificationDeliveryFailing

- **含义**：业务通知投递失败。管理员决策请求（GPU 数量变化、spare 不足、机械检查结论）
  没有送达，闭环的人工半边静默停住。
- **首查**：SNS topic 订阅状态与是否有重复的 confirmed/pending（见 REG-7）、
  `gpu_fault_notification_outbox_depth`、失败通知对应的 workflow 是否在等决策。
- **边界**：critical。补投之前不要把等待决策的 workflow 判为「无进展故障」。

### GpuFaultPostgresPoolOversubscribed

- **含义**：某个控制面角色里"能同时握住一条池连接"的线程数（Store I/O 线程 + 处理器
  worker + 派发器 worker + 周期服务）超过了该进程的连接池上限，比值就是指标值。负载一上来，
  调用方在取连接处排队，先撞上的是请求截止时间而不是数据库本身。以前这只是启动时的一条
  WARNING，且 worker 角色少算了三类线程从未告警过。
- **级别**：已降为 info（控制面审查 2026-09-08，G-7）——这是配置常数的比值，实际排队看
  `GpuFaultPostgresPoolCheckoutQueueing`，丢槽位看 `GpuFaultPostgresPoolConnectionErrors`。
- **读的是哪个指标**：`gpu_fault_postgres_pool_oversubscription_ratio`（按角色的 gauge），
  分解见 `gpu_fault_postgres_pool_demand_connections{consumer=}` 与
  `gpu_fault_postgres_pool_max_size`；LISTEN 连接不在池内，另见
  `gpu_fault_postgres_unpooled_connections`。
- **首查**：看哪一类 consumer 贡献最大；核对该角色的
  `GPU_FAULT_PROCESSOR_WORKERS`、`GPU_FAULT_WORKFLOW_DISPATCHER_WORKERS` 与池上限配置。
- **处置**：要么把池上限调到 ≥ 需求，要么减少该角色的线程数；两者都是配置变更，走发布。
  不要为了让告警消失去改指标的统计口径。

### GpuFaultBranchEscalationBudgetRefused

- **含义**：多节点作业修复中，某个节点分支要就地升级到下一级（reset → reboot → 暖备替换），
  但该动作的资源类（如 `NODE_LIFECYCLE_MUTATION`）在本集群的并发预算已满，控制面选择把该分支
  交给人工（分支耗尽、工作流最终 FAILED / ESCALATED），而不是越过并发上限。
- **读的是哪个指标**：`gpu_fault_workflow_branch_escalation_budget_refusals_total`（执行器计数）。
- **首查**：incident_id 取自升级通知邮件（`status` 不列 incident；计数在
  `gpu_fault_incidents_by_state{state="ESCALATED"}`），`GET /v1/workflows/{workflow_id}`
  读工作流 `exhausted_branch_ids`
  与最后一条失败记录里的"remediation budget cannot take the next rung"；核对
  `GPU_FAULT_REMEDIATION_MAX_ACTIVE_PER_RESOURCE_CLASS`（默认 2）与当时在飞的重启/替换数。
- **处置**：等在飞的重启/替换收口后，由人工决定该节点是重启、换机还是送修；若频繁出现且
  确认硬件容量允许，再评估调高该资源类的并发上限。

### GpuFaultWorkflowStepStalled

- **含义**：某个恢复动作（`operation` 标签给出是哪一个）等待的时间已经超过**该动作自己的**
  预期上限仍未出终态。此时故障节点仍被扣着、其训练任务仍被挂起，而所有组件都是健康的——这
  正是本告警存在的原因：在它之前，「step 卡住」与「step 正常等待」在监控上没有区别。
- **读的是哪个指标**：`gpu_fault_workflow_step_waiting_seconds{operation=…}` 减去
  `gpu_fault_workflow_step_waiting_warning_seconds{operation=…}`，前者是非终态 workflow 中
  仍处于 `WAITING` 的 step 的最大年龄，后者是该 operation 适用的阈值。年龄而不是条数：等待
  本身是正常的，条数区分不出「节点正在重启」和「节点永远不会回答」。
- **为什么阈值是一条指标而不是规则里的常数**：阈值按 operation 分档。`REPLACE_NODE` /
  `RESTART_NODE` 交给 HyperPod 托管恢复，等的是 provider，上限就是
  `GPU_FAULT_HYPERPOD_MANAGED_RECOVERY_TIMEOUT_SECONDS`（默认 1800 秒）；其余动作的上限是
  `GPU_FAULT_WORKFLOW_STEP_TIMEOUT_SECONDS`（默认 600 秒）。规则里写死一个数只可能对其中
  一档：写 600 秒就会在每一次**正常**的节点替换上误报，写 1800 秒就等于放弃了其余所有动作
  的告警。控制面把适用阈值按同样的标签导出，规则做减法，因此两个窗口任何一次调参都不会让
  这条规则过期。告警提前量由 `GPU_FAULT_WORKFLOW_STEP_TIMEOUT_SECONDS` 与
  `GPU_FAULT_WORKFLOW_STEP_WARNING_SECONDS` 的差值决定（默认 300 秒），并按同一提前量平移
  到分档更高的 operation 上，所以它总是在 step 还在等的时候就响，而不是等上限把这个 step
  判失败之后才响。
- **首查**：读该 step 的 `details`，重点看它在等的那个对象**是否已经给出了答案**。
  2026-09-05 的实例是：node agent 已经明确回答「热备上有别人的 GPU 进程」，但这个答案被
  映射成了 `WAITING`；同时该 step 的重试计数是从一条 key 永不推进的记录里读回来的，所以
  计数停在 1，`verify_max_attempts=60` 永远到不了。若 `details` 里的证据（PID、command
  记录、快照时间）明显早于当前时间，说明引擎在重放一条已经结束的记录。
- **边界**：不得为消警调大 `GPU_FAULT_WORKFLOW_STEP_TIMEOUT_SECONDS`、
  `GPU_FAULT_WORKFLOW_STEP_WARNING_SECONDS` 或
  `GPU_FAULT_HYPERPOD_MANAGED_RECOVERY_TIMEOUT_SECONDS`，也不得手工改 workflow 的
  `step_executions`。上限到点后 step 会带明确错误失败，走正常的补偿与失败处理路径，那是
  预期行为，不是需要抢在它之前干预的事故。托管恢复超时还会额外落一条通知（附 AWS Support
  case 草稿），那条通知是这类超时唯一可执行的产物；如果只看到 step 失败却没有通知，说明是
  通用超时抢在了观察器之前，属于配置缺陷而不是运行事故。

### GpuFaultWorkflowDeadlineNotEnforced

- **含义**：有非终态 workflow 已经超过自己的 `execution_deadline` 5 分钟以上。这条告警报
  的不是「某个恢复慢」，而是**兜底机制本身失效**：deadline 到了却既没有被租约持有者执行、
  也没有被 watchdog 收掉。
- **读的是哪个指标**：`gpu_fault_workflow_overdue_seconds`，非终态 workflow 中超期最多的
  那条的超期秒数。正常情况下它应当稳定为 0：deadline 到点后，下一次派发就会由持有租约的
  executor 把当前 step 判失败并终态化。
- **首查**：读该 workflow 的 `execution_owner_id` 与 `execution_lease_expires_at`。
  - 两者都在、lease 在未来 → executor 还在续租，但没有执行 deadline；查 control-worker
    日志里的 `workflow execution deadline exceeded` 行是否出现。
  - lease 已过期或 owner 为空 → 该由 watchdog 收；查
    `workflow is past its execution deadline but held by its executor` 这条 WARNING。
    2026-09-05 之前这里是一句静默的 `continue`，唯一症状就是 workflow 永远不结束。
- **边界**：**不得**手工修改 `execution_deadline`、不得删除 workflow 行、不得为了让这个
  数字归零而重启控制面 Pod（重启只会换一个 owner 继续续租）。真正的修复在代码里，运维侧
  只负责取证。

### GpuFaultRemediationBudgetStarved

- **含义**：有 workflow 已经等待 remediation budget 超过 30 分钟。budget 限制同时变更
  的节点数，短时等待是正确的过载保护，长时等待说明配额没有被释放。
- **首查**：`gpu_fault_remediation_budget_active_claims` 按 scope type 与配置上限对比；
  确认持有 claim 的 workflow 是否仍在推进、其执行 lease 是否已过期。
- **边界**：不得为消警直接调大 budget；先确认没有「claim 持有者已死但 lease 未过期」
  的情况。配额调整走 [管理员容量配置](管理员容量配置.md)。

### GpuFaultRemediationBudgetClusterSaturated

- **含义**：某一个 GPU 集群（`cluster_id` 标签）的 remediation budget 已经打满 30 分钟：
  它的活跃 claim 数等于单集群上限（`GPU_FAULT_REMEDIATION_MAX_ACTIVE_PER_CLUSTER`，出厂 5），
  同时还有 workflow 因为这个集群的 scope 被拒而在等。整集群相关故障（一个 AZ、500+ 节点）
  下这是**预期现象**：该集群按上限并发逐个修复，排空时间约等于「等待数 ÷ 上限 × 单次修复
  时长」，几百个节点就是数十小时。本告警的价值是说出是哪个集群、要等多久，而不是说系统出错。
- **首查**：`gpu_fault_remediation_budget_cluster_active_claims{cluster_id}` 对比
  `gpu_fault_remediation_budget_cluster_limit`，确认确实顶在上限；
  `gpu_fault_remediation_budget_cluster_waiting_workflows{cluster_id}` 看该集群等待数，
  `gpu_fault_remediation_budget_waiting_workflows_by_scope` 看被拒的是 cluster 还是
  region/node/domain scope；用 `gpu_fault_workflow_duration_seconds` 的均值估排空时间；
  `gpu_fault_workflow_pending_age_seconds_max` 找最老的等待 workflow，读它的
  `remediation_budget_last_blocked_reason` / `remediation_budget_last_blocked_scope`。
  持有 claim 的 workflow 若不再推进（lease 长期不过期），转按 `GpuFaultRemediationBudgetStarved` 处理。
- **边界**：单集群上限是同时变更节点数的安全上限，不得为消警调大它；等待数按预期速度下降
  就只需等待并告知业务方排空时间。配额调整走 [管理员容量配置](管理员容量配置.md)，且需要
  变更记录与回滚方案。

### GpuFaultCompletionPendingTriageBacklog

- **含义**：完成路径把每个 attempt 结局记为一条决策；`PENDING_TRIAGE` 是「到达时分不清、
  先停一下再看」的有界状态，期限是 `GPU_FAULT_PENDING_TRIAGE_DEADLINE_SECONDS`（默认
  900 秒），到期由周期任务收口。规则 `for` 是期限的两倍：任务已经有整整一个期限加一次扫描
  的机会却没收掉，剩下的是分诊在停摆，不是某次 attempt 慢。
- **读的是哪个指标**：`gpu_fault_completion_decisions{status="PENDING_TRIAGE"}`（按
  `DecisionStatus` 的 gauge）；配套看 `gpu_fault_completion_pending_triage_reconciled_total`
  是否还在动。
- **首查**：`gpu_fault_completion_pending_triage_reconciled_total` 停了 → 看
  `gpu_fault_periodic_job_errors_total` 与 control-worker 日志里该周期任务的异常栈；还在动
  但 gauge 不降 → 新决策进得比收得快，看是不是某个集群的 Completion Watcher 在批量重投。
  单条决策用 `GET /v1/attempts/{cluster_id}/{attempt_id}/decision` 读。
- **边界**：不得手工把决策改成 `NO_ACTION`；不得为消警调大 deadline——调大只会把同样的
  停摆推迟到告警之外。

### GpuFaultCompletionEventsWithoutDecision

- **含义**：同一不变量的另一半——有完成事件但没有任何决策行。事件与决策应在同一事务落库，
  只有事件说明它被记下来又没被判定，下游再也不会看它一眼；一次失败的 attempt 可能就此没有
  任何恢复计划。事件可以比决策早一次 scrape，不可能早半小时。
- **读的是哪个指标**：`gpu_fault_completion_events_without_decision`。
- **首查**：control-worker / ingress 日志里完成事件写入之后的异常（决策写失败会留栈）；
  把这些事件对回各自的 attempt，确认对应节点是否已经由别的工作流处理。
- **边界**：不得删除事件行；重放事件之前先做完上一步对账，否则会给已恢复的节点再开一条
  工作流。

### GpuFaultIncidentsAwaitingOperator

- **含义**：`ESCALATED` 是控制面把决定交给人之后 incident 停放的状态——并发预算拒绝了下一
  级动作、工作流寿命耗尽、需要机械检查。它是设计内的正确终态，**不会**被自动收口，所以有
  数量本身不是故障；但一条一天没人动的升级，就是一个大家都忘了的 GPU 节点（或一个作业）。
  这条是「有人工队列存在」的提醒，warning，24 小时。
- **读的是哪个指标**：`gpu_fault_incidents_by_state{state="ESCALATED"}`（按
  `IncidentState` 的 gauge）。
- **首查**：这条告警只有计数，`gpu-fault-admin status` 也不列 incident。队列里每一条都对应
  一封 hardware-escalation 通知邮件（正文 `Incident: <id>`），按邮件逐条
  `GET /v1/incidents/{incident_id}` 读升级原因；按 §9 的业务处置分流（GPU 数量变化审批、
  备机预留、送修、`submit-remediation`）。若 incident 已经由人处理完但记录仍是 ESCALATED，属于处置流程没有收尾，
  不是监控误报。
- **边界**：只有操作员动作能让 incident 离开这个状态，保留策略不会；不得为消警改 Store
  行或静音规则——静音等于承认这个队列不需要有人看。

### GpuFaultWorkflowPendingAge

- **含义**：最老的 `PENDING` 工作流已经等了超过 30 分钟没有任何派发器领取。派发器以秒级
  tick 轮询，30 分钟不是排队时延，而是「没有派发器会拿它」：前驱工作流没有终态化、退役世代
  在等操作员、或派发器自己卡住了。派发器每次 tick 都观察这个年龄并在超阈值时告警一次
  （`gpu_fault_workflow_pending_age_warnings_total`），本规则是同一事实在 AMP 里的版本。
- **读的是哪个指标**：`gpu_fault_workflow_pending_age_seconds_max`；配套
  `gpu_fault_workflow_retired_generation_awaiting_operator`（被退役但还需要人关闭的世代数）
  与 `gpu_fault_workflow_dispatch_preemption_pending_seen_total`。
- **首查**：先只读——`scripts/e2e/regional/audit_stuck_workflow_baseline.py` 跑三条只读
  判据；`gpu_fault_workflow_retired_generation_awaiting_operator` 看是否有退役世代被
  dispatcher 拒绝关闭而留给人（见 §10.1）；`GET /v1/workflows/{request_id}`
  读该工作流的 `predecessor_workflow_id`，再读前驱是否已终态。前驱非终态且它自己也没人领 →
  按 `GpuFaultWorkflowDeadlineNotEnforced` 处理前驱；一切正常但仍无人领 → 看 control-worker
  的派发器日志与 `gpu_fault_periodic_lease_errors_total`。前驱是 `BLOCKED(NEEDS_OPERATOR)`
  时先看它**是否跑过步骤**：从未执行的 NEEDS_OPERATOR 记录自控制面审查 2026-09-08（C-03）起
  不再作为前驱——下一条同节点事件会把它就地重编译（`REPLACE_IN_PLACE`，同 id、代次 +1），
  只有跑过步骤的 NEEDS_OPERATOR / INTERNAL_ERROR 记录才需要 §10.2 的 `compile-blocked`。
- **边界**：不得删除或手工改 PENDING 工作流行，不得手工把前驱改成终态；退役世代只能走
  §10.1 的 `workflow-reconcile --mode retired-generation --apply`。

### GpuFaultNotificationUndeliveredTooLong

- **含义**：最老的一条未投递通知（delivery 处于 PENDING / RETRY / LEASED）已经等了超过
  30 分钟。它距离被 shelf life（`GPU_FAULT_NOTIFICATION_TTL_SECONDS`，默认 6 小时）
  直接丢弃还有余量，此刻仍可救。年龄从入队或最近一次人工重入队算起，重试退避不会重置它。
- **首查**：`gpu_fault_notification_delivery_total{status=...}` 看它卡在哪个状态——
  `RETRY` 多说明 SNS/SES 持续拒绝（看 delivery 行的 `last_error`；SNS 看 topic 存在与 role 的 `sns:Publish`，SES 看身份与配额）；
  `PENDING`/`LEASED` 多说明派发器没轮到它，转到 `GpuFaultNotificationOutboxNotDraining`。
  `GET /v1/advisory-notifications` 能读到通知正文。
- **边界**：critical。不得为消警把 TTL 缩短让它更快过期；补投走
  `POST /v1/advisory-notifications/dispatch`，不改 Store 行。

### GpuFaultNotificationOutboxNotDraining

- **含义**：outbox 里有 PENDING/RETRY 的通知，但 5 分钟内没有任何副本开始过一次派发
  周期。这就是启动日志 `notification delivery:` 一行警告的那种组合——邮件排进了 outbox，
  却没有进程在排空它。
- **首查**：control-worker Pod 的启动日志里 `notification delivery:` 的结论；
  `GPU_FAULT_NOTIFICATION_DISPATCHER_ENABLED` 是否至少在一个副本为 true；
  `gpu_fault_notification_dispatch_last_cycle_timestamp_seconds` 为 0 的副本从未派发过，
  非 0 但陈旧的副本是 `gpu-fault-notification-dispatcher` 线程死了（看该 Pod 日志里
  `notification dispatch cycle failed`）。
- **边界**：warning。内联投递（async 关）的部署不会有未投递行，本告警对它天然静默；
  出现即说明有通知真的没人送。

### GpuFaultNotificationExpiredUnsent

- **含义**：最近 30 分钟内有通知被领取时已过 shelf life，被记为 SKIPPED 直接退役、没有
  寄出。过期是有意为之（六小时前恢复的节点再寄邮件只是噪音），但它仍是一封没人收到的
  通知，持续出现说明 outbox 排空慢于灌入。
- **首查**：`gpu_fault_notification_expired_total` 看数量；对照这段时间内
  `GpuFaultNotificationOutboxNotDraining`、`GpuFaultNotificationUndeliveredTooLong`
  是否先响过，找到阻塞 outbox 的原因（派发器关、SNS/SES 拒绝、某副本卡死）。通知正文仍可在
  `GET /v1/advisory-notifications` 读到。
- **边界**：warning。先找阻塞原因，再考虑放宽 TTL；不得为消警把过期通知批量重入队。

### GpuFaultWorkflowDispatcherStalled

- **含义**：5 分钟内没有任何 control-worker 副本开始过一次工作流派发周期。
  `gpu_fault_workflow_pending_age_seconds_max` 和所有派发计数从这一刻起都是冻结值——
  写它们的线程没在跑；没有人会领取 PENDING 工作流、也没有人执行 deadline。
- **首查**：control-worker Pod 是否 Ready；Pod 内 `gpu-fault-workflow-dispatcher`
  线程是否存活（py-spy dump）；一个 Pod 在跑但时间戳不动，是某次 Store 调用挂死。
  `gpu_fault_workflow_dispatch_last_cycle_timestamp_seconds` 按 `pod` 看是哪个副本停了。
- **边界**：critical。重启前先抓线程栈；不得为消警把 dispatch lease 调长。

### GpuFaultPeriodicRunnerStalled

- **含义**：5 分钟内没有任何副本的周期服务线程 tick 过。训练健康、spare 健康、身份刷新、
  清理、归档、采集器静默检测、lease 回收、PENDING_TRIAGE 兜底、计数器漂移全部跑在这一个
  线程上，它停了这九项的计数器都不会再动。
- **首查**：`gpu_fault_periodic_job_last_run_timestamp_seconds{job=...}` 看最后跑的是
  哪个 job——通常就是卡住的那个；control-worker Pod 日志与线程栈。
- **边界**：critical。一个 job 内部一次阻塞的 Store 调用会拖住其余八个；先定位再重启。

### GpuFaultProcessorUnhealthy

- **含义**：某个 control-worker 副本把自己的处理器标成不健康，5 分钟没恢复。它拒绝领取
  处理器请求，也不参加任何周期任务；它那份队列由其他副本代扛。
- **首查**：该 Pod 的 `/healthz` 正文里的原因、处理器日志；常见是 Store 连接丢失或
  schema 版本与 wheel 不匹配（REG-10A 制品一致性检查）。
- **边界**：critical。不得靠反复重启掩盖；schema 不匹配按发布流程处理。

### GpuFaultProcessorNoActiveConsumer

- **含义**：没有任何副本在消费处理器队列。故障事件仍被接受并入队，但没人领取——检测已经
  停止，而所有 ingress 健康检查都还是绿的。
- **首查**：control-worker Deployment 是否有 Ready 副本、`GPU_FAULT_SERVICE_ROLE` 是否为
  worker、启动 guard 是否放行；随后队列深度告警会跟着响。
- **边界**：critical。这不是容量问题，不要靠加 ingress 副本解决。

### GpuFaultTelemetrySpoolConsumerStopped

- **含义**：某个 telemetry-spool-worker Pod 在跑，但它的 spool 消费循环已经退出。
  spool 到它的常规遥测不再回放，`GpuFaultTelemetrySpoolDrainDelayed` 会随后响。
- **首查**：该 Pod 日志里结束 `run_telemetry_spool` 的异常；循环不会原地重启。
- **边界**：critical。这是代码缺陷通道，先读栈再重启 Pod。

### GpuFaultTelemetrySpoolConsumerStalled

- **含义**：某个 spool 消费循环自称在跑，但 10 分钟没有发出过一次 claim。空闲的循环也会
  每 `GPU_FAULT_TELEMETRY_SPOOL_NOTIFICATION_FALLBACK_SECONDS`（2–5 秒）claim 一次，
  所以这是卡住，不是空闲。
- **首查**：该 Pod 的线程栈（py-spy）——通常卡在一次 Store 调用或一个永不完成的回放
  future 上；`gpu_fault_telemetry_spool_claim_rounds_total` 确认计数确实不动。
- **边界**：critical。重启前先抓栈，否则卡住的调用无从得知。

### GpuFaultProcessorLeaseRenewalFailing

- **含义**：15 分钟内有处理器 lease 续租被拒（另一个 owner 持有该 lane，同一请求可能在
  两个 worker 上跑过）或续租时 Store 出错。以前只计数、无人看。
- **首查**：对照 `GpuFaultProcessorExpiredLeasesReclaimed`——先回收再被拒，是某 worker
  卡过一个 lease 又醒了；`gpu_fault_processor_renewal_errors_total` 升而 fenced 不升，
  是 Store 连接问题。
- **边界**：warning。不得为消警调长 `GPU_FAULT_PROCESSOR_LEASE_SECONDS`。该计数器按进程
  统计，control-worker 每 Pod 4 个进程，`/metrics` 在 Pod 内按 SUM 聚合（不再随机命中
  一个进程）；但一个进程重启会让 Pod 之和回落，`increase()` 把它读成归零（滚动时 6 副本
  即 6 次），处理器暴露 last-seen 时间戳后本规则会改读时间戳。

### GpuFaultPeriodicServiceErrors

- **含义**：15 分钟内某个周期任务抛了异常（`job` 标签说是哪个），或者取任务 lease 时
  Store 出错。runner 会继续，该 job 这一 tick 被跳过——它提供的服务晚了一个间隔。控制面
  审查 2026-09-08（F-1）后**作业体自身的失败**（清理 job、归档、扫描抛出的异常）也计入
  `periodic_job_errors_total` 并触发本告警；以前只有 lease 与 runner 层的错误可见，作业体
  静默失败与没跑过看不出区别。
- **首查**：control-worker 日志里 `periodic service <job> failed` / `periodic task lease
  <key> could not be taken` 的 traceback；`gpu_fault_periodic_job_errors_total{job}`
  看频率。
- **边界**：warning。连续出现按对应 job 的 runbook 处理，不得把 job 从 `_JOBS` 里摘掉。

### GpuFaultWorkflowDispatchInternalErrors

- **含义**：15 分钟内派发尝试抛出了派发器不认识的异常（F-B4）。工作流保持可执行并带退避，
  恢复被推迟而非丢失，但同一次尝试会一直撞进同一个缺陷直到修复。
- **首查**：control-worker 日志 `workflow dispatch hit an internal error` 与其 traceback；
  `gpu_fault_workflow_dispatch_internal_errors_total` 看数量。
- **边界**：warning。这是本副本的接线缺陷（adapter 缺失、capability 缺失），修复走发布，
  不通过手改工作流行清除。

### GpuFaultWorkflowFailureHandlingAbandoned

- **含义**：30 分钟内有失败工作流的失败处理器反复抛异常后被放弃（F-A6）。工作流已终态，
  但失败的副作用——升级、incident 状态、通知——没有发生：一个仍在池外的节点没人知道。
- **首查**：control-worker 日志 `failure handling abandoned` 里的 workflow id；
  `GET /v1/workflows/{request_id}` 与对应 incident 的状态。
- **边界**：critical。逐条人工核对 incident 状态与节点是否仍在池外，按 §8/§9 处置；
  `workflow-reconcile` 只处理已由 successor 恢复的 BLOCKED 记录，不处理 FAILED 记录，
  dispatcher 的清扫（§10.1）也不会替它收尾，不得删除记录。

### GpuFaultOrphanWorkflows

- **含义**：存在过了聚合窗口仍为 PENDING / SAFETY_PENDING、但其 incident 已不存在或指向
  别的工作流、且没有后继指它为前驱的工作流（F-B3）。没有派发扫描会排到它、没有围栏覆盖它、
  没有清扫会关闭它；它可能仍握着节点 claim。
- **首查**：`gpu_fault_orphan_workflows` 计数对应的记录；`GET /v1/workflows/{request_id}`
  读它的 incident 与前驱（incident 是否已不存在或指向别的工作流）。
- **边界**：warning。目前没有任何路径会关闭它——`workflow-reconcile` 只处理 BLOCKED 记录，
  dispatcher 的清扫（§10.1）只关退役世代、编译期 BLOCKED 与孤儿 remote command，都不含
  这种 PENDING 孤儿。记下 request_id 作为产品缺陷跟进，不得删行、不得手改状态。

### GpuFaultIncidentDanglingWorkflowPointers

- **含义**：有 incident 的 `workflow_request_id` 指向一条不存在的工作流行（F-B3）。同一
  节点的后续事件顺着指针找不到东西，重复事件快路径只能重建链
  （`gpu_fault_ingest_stale_event_link_repairs_total`）。
- **首查**：`GET /v1/incidents/{incident_id}` 看 `workflow_request_id` 指向的行是否存在；
  对照 `GpuFaultOrphanWorkflows` 是否同时响（通常是同一次不完整写入的两面）。
- **边界**：warning。`workflow-reconcile` 不修 incident 指针；同节点的下一条事件走快路径时
  会重建链（计入 `gpu_fault_ingest_stale_event_link_repairs_total`）。不得手改 incident 行。

### GpuFaultStaleAgents

- **含义**：有 lifecycle 为 ACTIVE 的 Node Agent 超过 15 分钟没有有效心跳 lease。控制面仍
  把这些节点当成可修复目标却够不到它们：其上的每个节点动作都过不了 readiness，采集器静默
  告警会跟着响。几分钟是重启，一刻钟是 agent 没回来或 token/TLS 断了。
- **首查**：`GET /v1/fleet/agents` 列出陈旧的；节点上 `gpu-fault-node-agent` 单元状态、
  cluster token、TLS 信任链（REG-6）。
- **边界**：warning。已经不存在的节点走 drain/revoke（§5），不得删 agent 记录。

### GpuFaultFleetPinAheadOfFleet

- **含义**：控制面钉住的 agent 版本 / artifact sha256 / policy / profile / config digest
  没有任何一个活着的 agent 在跑，所以是 pin 变了、不是节点落后（readiness 里的
  `PIN_AHEAD_OF_FLEET` 提示）。该集群上每个节点动作都过不了 readiness。
- **首查**：`gpu_fault_fleet_pin_drift_nodes{cluster_id,kind}`——`PIN_AHEAD_OF_FLEET`
  修 pin 或先把构建滚出去，`NODE_STALE` 是节点落后于同伴、升级或重启节点上的 agent。
  值是该集群最近一次 readiness 评估的结果，修好后下一次评估即清零。
- **边界**：warning。不得为消警把 pin 改成「任意版本」；pin 变更走 §4 发布流程。

### GpuFaultRemoteCommandUnclaimedExpired

- **含义**：有 remote command 超过 `GPU_FAULT_REMOTE_COMMAND_CLAIM_DEADLINE_SECONDS`
  （默认 900 秒）仍无人领取，被周期清扫置为 FAILED、`status_source=
  unclaimed-deadline-exceeded`——对应工作流因此失败，没有任何节点动作被尝试过。
  `GpuFaultRemoteCommandUnclaimed` 是更早一步、命令还能被领取时的信号。
- **首查**：命令 `error` 里写的 `execution_owner`，以及本应广告它的 adapter 是否被目标
  集群 Executor 构造出来（REG-14.2）；`gpu_fault_remote_command_unclaimed_expired` 是
  保留期内此类命令的数量，随保留清理下降。
- **边界**：critical。工作流已 ESCALATED，清掉告警不会重试它；修好 owner 后按 §9 处置。

### GpuFaultProcessorFaultEventsRejected

- **含义**：15 分钟内有故障层采集事件在入口拿到 202 之后、处理器回放时被 4xx 完成——节点
  报了故障，控制面没有对它做出任何策略判定就丢掉了。以前这类 4xx 只是一行日志。
- **首查**：处理器日志 `rejected-event` 一行给出 request_id、path、status 与 Pydantic
  detail（只有 `loc/msg/type`，不含载荷）；节点的 collector status `errors` 带同一前缀。
  按 `gpu_fault_processor_completions_by_path_status_total{path,status_class}` 看是哪条通道：
  某条 path 在一次发布之后开始出 4xx，是采集器与控制面的 schema 漂移，不是节点故障。
- **边界**：warning。该计数器按进程统计，control-worker 每 Pod 4 个进程，`/metrics` 在
  Pod 内按 SUM 聚合；`increase()` 只在某个进程重启、Pod 之和回落时把它读成归零（漏报，
  不误报）。
  不得为消警放宽入口校验；
  被拒事件不会自动重放，修好漂移后由数据面重投同类事件。

### GpuFaultRegionalRegistrySecretDrift

- **含义**：某角色的进程启动时读到的区域注册表 Secret 摘要与 Aurora 里的 durable head
  已经连续 15 分钟不一致。head 是权威（join/remove 发布到那里），运行中的注册表是对的；
  过时的是发布配置——只改写 Secret 的发布什么都没改到，而从这份 Secret 重启的 Pod 在
  第一次刷新前会跑在旧的集群清单上。
- **首查**：`/healthz` 的 `regional_registry` 载荷对比 `secret_config_sha256` 与
  `durable_config_sha256`；`gpu_fault_regional_registry_secret_drift{service_role}` 说是哪个
  角色。api-ha 与 control-worker 的启动日志里 `regional registry Secret drifts` 一行给出两个摘要。
- **边界**：warning。不得手工改 Secret 或直接写 head；让发布配置追上 head——对分歧的集群走
  join/remove（§4.7），或发一次 REGISTRY 组件会把 Secret 落到 head 的发布。

### GpuFaultControlPlaneReplicaScrapeFailing

- **含义**：某个控制面 Pod 连续 5 分钟没有应答 ADOT 抓取（超时或非 200）。`absent(up==1)` 只在全部 Pod 消失时响，所以单个 Pod 的抓取失败以前是盲区——而 `GpuFaultProcessorUnhealthy` 这类 `min by (pod)` 规则恰恰看不到缺失的那个 Pod。
- **读的是哪个指标**：`up{job="gpu-fault-control-plane"} == 0`，标签 `pod`、`service_role` 来自目标 relabel。
- **首查**：该 Pod 的 readiness；`kubectl exec` 进 Pod 在 loopback 上 `curl /metrics` 看是超时还是 500；邻居 Pod 的 `gpu_fault_metrics_contributor_errors_total` 是否同时上升（store 侧原因）。
- **处置**：池丢槽位（密码轮换后）先看 `GpuFaultPostgresPoolConnectionErrors`；单 Pod 卡死则重启该 Pod。在它恢复前，把它的处理器健康与循环存活视为"未知"而非"健康"。

### GpuFaultMetricsContributorFailing

- **含义**：`/metrics` 的某个 contributor 在 10 分钟内多次抛异常。渲染现在逐 contributor 隔离：失败的族被跳过并计数，其余族照常输出，所以进程内 gauge 不再随一次 store 异常一起消失。
- **读的是哪个指标**：`increase(gpu_fault_metrics_contributor_errors_total{contributor,pod}[10m]) > 3`。
- **首查**：该 Pod 日志中 `gpu_fault.app.metric_contributors` 的首条 traceback（之后只打一行 warning）；常见是 store 读失败（池超时、failover、schema 漂移）。
- **处置**：缺失的族按"未知"处理，不按 0；修复 store 侧原因后计数停止即可，无需重启。

### GpuFaultPostgresPoolCheckoutQueueing

- **含义**：某进程连续 2 分钟每次采样都有调用方在等池连接（psycopg_pool `requests_waiting`）：池满或在丢槽位，下一步就是 `PoolTimeout` → 503 或 worker 线程停摆。
- **读的是哪个指标**：`gpu_fault_postgres_pool_requests_waiting{service_role,pod}`；配合 `gpu_fault_postgres_pool_size` vs `gpu_fault_postgres_pool_max_size`。
- **首查**：`pool_size < pool_max_size` 且在等 → 池在丢槽位（看 `GpuFaultPostgresPoolConnectionErrors`）；`pool_size == max` → 真饱和，看 Aurora 延迟与 `gpu_fault_processor_lane_wait_seconds_max`。
- **处置**：饱和走配置变更（池上限 / 线程数，见 `GpuFaultPostgresPoolOversubscribed`）；丢槽位按下一张卡处置。

### GpuFaultPostgresPoolConnectionErrors

- **含义**：某进程 5 分钟内持续有新建池连接失败。主密码轮换后这是池用旧密码重拨的形状；池每次失败都会重读挂载的 Secret 文件（`gpu_fault_postgres_credential_rotations_total` 文件变化时 +1）。
- **读的是哪个指标**：`increase(gpu_fault_postgres_pool_connections_errors_total[5m]) > 0`，按 `pod`。
- **首查**：`credential_rotations_total` 没动 → Secret 没更新，看 `GpuFaultAuroraCredentialRefreshStale/Failing` 与刷新 CronJob；failover 期间会短暂上升后停止；Secret 未变仍持续增长 → DNS / 安全组 / Aurora 可用性。
- **处置**：Secret 落后时手动跑一次刷新 Job，池自愈无需重启；网络原因按 Aurora 连接性排查。

### GpuFaultAuroraCredentialRefreshStale

- **含义**：每小时的 `gpu-fault-aurora-credential-refresh` CronJob 已超过 3 小时没有成功，挂载的 Secret 可能跟不上下一次（7 天）主密码轮换。
- **读的是哪个指标**：`gpu_fault_aurora_credential_refresh_last_success_age_seconds > 10800`，来自 Secret 里刷新器写的 `last-refresh-status.json`。
- **首查**：`gpu_fault_aurora_credential_refresh_last_run_ok` 为 0 说明在失败（看下一张卡），为 1 但 age 大说明 CronJob 没被调度；`kubectl get secret gpu-fault-aurora -o jsonpath='{.data.last-refresh-status\.json}' | base64 -d`。
- **处置**：修好原因后手动跑一次 Job；确认 CronJob 未 suspend、`startingDeadlineSeconds` 未错过。

### GpuFaultAuroraCredentialRefreshFailing

- **含义**：刷新器最近一次运行以非 ok 结束，且 15 分钟内没有后续成功。状态文件只记最后一次，所以失败时成功年龄序列会消失，本条是它的对偶。
- **读的是哪个指标**：`gpu_fault_aurora_credential_refresh_last_run_ok == 0`。
- **首查**：状态文件里的 `error`（密码已脱敏）与最新 Job 日志；常见是 Secrets Manager 读取、verify 连接（网络 / CA bundle）、对 Secret 的 patch RBAC。
- **处置**：修复后手动跑 Job，看 `last_run_ok` 回到 1。

### GpuFaultAdotMemoryHigh

- **含义**：ADOT 采集器常驻内存 10 分钟高于 200MiB（容器上限 256Mi，`GOMEMLIMIT` 220MiB）。再往上是 OOMKill 循环——每次重启仍能落一批数据，`absent(up)` 与丢弃计数都不会响，AMP 里只剩断续。
- **读的是哪个指标**：`otelcol_process_memory_rss`（self job）。
- **首查**：ADOT Pod 的 `restartCount`；新增的 `cluster_id` / `pod` 标签基数是否在增长。
- **处置**：先弄清基数来源再考虑提高限制；不要为了让告警消失去缩 keep 列表里告警依赖的族。

### GpuFaultProcessorConsumerStalled

- **含义**：某 control-worker 报告处理器消费循环未运行，或超过 30 秒没有开始新一轮认领，持续 2 分钟。以前循环线程死掉时 `gpu_fault_processor_healthy` 仍是 1。
- **读的是哪个指标**：`gpu_fault_processor_consumer_running == 0` 或 `gpu_fault_processor_consumer_last_cycle_age_seconds > 30`，按 `pod`。
- **首查**：该 Pod 的 `/livez` 会把 `processor-consumer` 列为死线程并由 kubelet 重启；反复出现时看 `gpu_fault_processor_consumer_cycle_errors_total` 与处理器日志里循环卡住的 store 调用。
- **处置**：一次性重启即可；反复则按 store 侧原因（池、failover）处置。

### GpuFaultRemoteCommandStaleFenceSwept

- **含义**：周期清扫把 LEASED 且工作流已换代（fencing token 不符）、租约过期又无人上报结果的远程命令置为 FAILED（`status_source=stale-fence`）。每一条都代表数据面在旧代次上跑完了一个动作而没人收结果。
- **读的是哪个指标**：`increase(gpu_fault_periodic_cleanup_rows_total{job="stale_fence_remote_commands"}[30m]) > 0`。
- **首查**：命令的 `result_details.stale_fence_swept`；执行器事后报上的结果保留在
  `result_details.post_stale_fence_status` / `post_stale_fence_error`（命令已死，任何持 cluster
  token 的上报都落 FAILED stale-fence，不再校验 lease_token）；对应节点上是否发生了与当前代次
  重叠的动作。顺带说明：WAITING 步骤的工作流租约现在是 `max(3 × poll, 30 s)`（D-7），
  `execution_lease_expires_at` 很近**不是**异常。
- **处置**：人工核对节点状态后再信任当前代次；这是审计信号，不需要改配置。

### GpuFaultNotificationDeliveryErrors

- **含义**：15 分钟内有通知投递在 provider 调用或其后的记账里抛异常；该行被释放重试，批内其余条目继续，所以是"变慢"而非"丢失"——除非持续响。
- **读的是哪个指标**：`increase(gpu_fault_notification_delivery_errors_total[15m]) > 0`。
- **首查**：`gpu_fault.notification_service` 日志里的异常；常见是 SES 超时（5s/20s/2 次）与 Secret/IAM 错误。
- **处置**：修复外部依赖；DEAD 的通知用 `requeue` 显式复活（`send` 不再复活 DEAD）。

### GpuFaultControlRecordArchiveErrors

- **含义**：控制记录归档器在过去 1 小时对候选 incident 抛了非安全拒绝的异常；本轮继续，该 incident 留到下轮。S3 权限或桶错误会让每个候选都失败，保留就静默停止回收。
- **读的是哪个指标**：`increase(gpu_fault_control_record_archive_errors_total{reason}[1h]) > 0`，`reason` 是异常类型。
- **首查**：归档器日志；`gpu_fault_control_record_archive_archived_total` 是否还在增长。
- **处置**：修复 S3/IAM；`GPU_FAULT_CONTROL_RECORD_ARCHIVE_S3_URI` 与 IRSA 权限见部署手册 8.4。

### GpuFaultPendingTriageReconcileFailing

- **含义**：PENDING_TRIAGE 看门狗在 30 分钟内尝试让过期决策超时时抛异常：决策留在 PENDING_TRIAGE，保守计划没被编译，看门狗每 tick 重试。
- **读的是哪个指标**：`increase(gpu_fault_completion_pending_triage_reconcile_failures_total{reason}[30m]) > 0`；对比 `GpuFaultCompletionPendingTriageBacklog`（数的是决策本身）。
- **首查**：`reason` 标签（异常类型）；常见是 event 或 profile 行缺失。
- **处置**：补齐缺失记录或按 `compile-blocked` 流程处理该决策。

## 9. 管理员业务处置

GPU 数量变化审批、spare 不足后的降级恢复、机械检查后的明确动作各有一个详细 runbook：

- [GPU 数量变化审批](部署和运维手册.md#81-gpu-数量变化审批)——一条 `kubectl annotate`，
  没有也不需要专用动词；
- [spare 不足时管理员手动降级恢复](部署和运维手册.md#82-spare-不足时管理员手动降级恢复)——
  备机预留仍是人工步骤（产品自动化缺口，见 §12）；
- [CHECK_MECHANICALS 后明确处置](部署和运维手册.md#83-check_mechanicals-后由管理员提交明确处置)——
  `gpu-fault-admin submit-remediation --state-dir ... --incident-id ... --disposition
  {inspected,reset-gpu,reboot-node,quarantine} --reference ...`，`--plan` 只打印将提交的内容。

管理员不得手工拼造不存在的 allocation、attempt ID 或 fencing token。变更决定必须引用
当前 incident、真实 workload observation 和审批单。

### 9.1 关闭 ESCALATED 事件（节点已恢复但事件仍"只记录"）

**何时用**：`GET /v1/incidents/{id}` 显示 `state=ESCALATED`（reset/reboot 因 lifetime 超时或 support 升级已交给运维），节点已通过 support 事件的 validated restore 恢复（`kubectl get node` 无 cordon、无 `gpu-fault.io/` taint），但该事件仍在吸收同节点后续 XID（`/metrics` 里 `gpu_fault_workflow_merge_record_only_total{reason="lifetime_exceeded"}` 增长）。**正常情况下不需要手工操作**：support 事件的 restore workflow SUCCEEDED 时，执行器会自动把同集群、节点被完全覆盖、且无开放 workflow 的 ESCALATED 事件写成 RECOVERED（`gpu_fault_incident_auto_closed_by_restore_total` +1，reasons 追加 `node restored via incident <id>`）。手工关闭用于：节点由厂商/人工修复、没有走 restore workflow 的场景。

**前置**：事件 `state=ESCALATED`；事件没有 PENDING/RUNNING/SAFETY_PENDING 或占位 BLOCKED 的 workflow（否则 409/refused，先等待或用 `workflow-reconcile` 处置）。QUARANTINED 事件不可手工关闭——节点仍被隔离，要走 validated restore workflow。

**CLI（推荐）**
```bash
# 先看结论，不写任何东西
gpu-fault-admin workflow-reconcile --state-dir "$STATE_DIR" \
  --close-incident inc-xxx [--close-incident inc-yyy] \
  --reason "node repaired by vendor, validated by ops" --dry-run
# 输出每行一个：inc-xxx: would-close | already-recovered | refused(<原因>)

# 执行（--reference 为审批变更/工单号；操作者身份取 aws sts get-caller-identity，写入审计事件）
gpu-fault-admin workflow-reconcile --state-dir "$STATE_DIR" \
  --close-incident inc-xxx \
  --reason "node repaired by vendor, validated by ops" \
  --reference CHG-2026-0908-01
# 输出：inc-xxx: closed | already-recovered | refused(<原因>)；任一 refused 退出码 1
# 结果归档：$STATE_DIR/workflow-reconcile/incident-close/history/<UTC 时间>-<digest>.json
```

**API（等价，CLI 在 Pod 内调用的是同一个服务函数）**
```bash
curl -sS -X POST "$CONTROL_PLANE_URL/v1/incidents/inc-xxx/close" \
  -H "X-GPU-Fault-Execution-Token: $GPU_FAULT_EXECUTION_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"reason":"node repaired by vendor","operator":"alice@example.com","reference":"CHG-2026-0908-01"}'
# 200 {"incident":{...,"state":"RECOVERED","reasons":[..., "operator closed: node repaired by vendor by alice@example.com"]},"closed":true}
# 200 closed=false：已是 RECOVERED，幂等无写入
# 409 detail：仍有开放 workflow <id> (<status>) / 状态不是 ESCALATED（QUARANTINED 请走 restore）/ 并发修改请重试
# 404：incident 不存在   403：缺少或错误的执行令牌   422：缺 reason/operator
```

**效果**：incident→RECOVERED，reasons 追加 `operator closed: <reason> by <operator>`；该 incident 最后一个 workflow 的 events 追加 `kind=OPERATOR_RECONCILED code=INCIDENT_CLOSED actor=<operator> details.reference=<ref>`；其 marker 全部退役（retired_by=<operator>）；节点对该故障范围的下一个 XID 重新生成新 incident/workflow。`gpu_fault_incident_operator_closed_total` +1。

## 10. 数据与审计维护

**控制记录保留默认关闭。** `GPU_FAULT_CONTROL_RECORD_RETENTION_DAYS` 的运行时默认值是
`0`：incident、workflow 及其关联记录一旦写入就不会被产品删除，也不会被归档，Aurora 里的
行只增不减。这是有意的：删除是有损操作，必须由站点管理员显式声明，而不是由某个 release
带进来。

需要 archive-first 保留（先把整个 incident bundle 写到 S3 并校验 SHA-256，再删 live 行）时，
分两步，全部是站点配置，不改 release：

1. 在 `<state-dir>/site.yaml` 的 `spec` 下声明：

   ```yaml
   spec:
     retention:
       controlRecordRetentionDays: 365        # >0 才开启；0 或缺省 = 关闭
       archiveS3Uri: s3://<bucket>/<prefix>    # 开启时必填，只接受 s3://
       archiveIntervalSeconds: 3600            # 可选，归档扫描周期，缺省 3600
   ```

2. 重跑 `gpu-fault-admin deploy --state-dir <state-dir>`。deploy 会：把控制面 IRSA 角色
   加上对该前缀的 `s3:PutObject`（只有这一项，归档器不读不删对象）；把这三个变量只渲染进
   control-worker 的 ConfigMap（ingress/spool 不跑归档器，也不会去校验一个它们无法执行的
   保留策略）；后续每次 deploy 重新渲染 site 时保留该块，不会悄悄改回关闭。

不声明这个块时，渲染出的控制面环境里**没有**这三个变量，`docs/管理员环境变量参考.md` 里
的默认值就是生效值。运行时对开启的校验是 fail closed：天数 > 0 但没有 S3 URI，或 Store 不是
PostgreSQL，worker 启动即拒绝。归档器按天数只处理已经闭合的记录，`gpu_fault_control_record_*`
指标 `gpu_fault_control_record_archive_withheld_total{reason}` 给出被安全拒绝（例如 incident 还有
未终态 workflow）的归档次数。

### 10.1 产品自己关闭的卡死记录（不需要命令）

下面三种形态过去各有一个`workflow-reconcile --mode ...`，每次实际使用都是为了让发布
前置检查放行。它们的判定全部只读 Store，于是现在由 dispatcher 在每轮派发扫描之前的清扫
（`WorkflowDispatcher.sweep_stuck_records`）自动关闭：判定从头重新推导、永不按"年龄"，
每条记录单独以 compare-and-set 写入（被别人改过的行拒绝而不覆盖，下一轮重读），不删
任何行。

| 形态 | 判定（全部同时成立） | 动作 | 审计落点 |
| --- | --- | --- | --- |
| 退役世代 | incident 已推进到更高 fencing 世代并指向另一个 workflow；旧 workflow 仍 `PENDING`/`RUNNING`/`SAFETY_PENDING`/`BLOCKED`，且**没有**完成过任何改动节点的操作 | 先取消其 remote command，下一轮再转 `SUPERSEDED`（`preempted_by_workflow_id` 指向 successor），释放未用的重启预留 | `preemption_reason` 与 incident 的 `reasons`；control-worker 日志 `retired generation revoked` |
| 编译期 BLOCKED | `BLOCKED` 且 `blocked_reasons` 非空、从未被 claim（`execution_epoch` 为 0）、零 step execution、无 completed operation、无 owner、无 source plan、无预算 claim、无未结 remote command，incident 为 `ESCALATED`/`RECOVERED` | 转 `SUPERSEDED`，`preemption_reason` 带原 `blocked_reasons`；**不写 incident** | workflow 上一条 `OPERATOR_RECONCILED` 事件，`actor` 为 `dispatcher`；日志 `compile-time BLOCKED workflow closed by the dispatcher` |
| 终态 workflow 遗留的 remote command | workflow 已 `FAILED`/`SUCCEEDED`/`BLOCKED`/`SUPERSEDED`，其 command 仍 `PENDING`/`LEASED`/`WAITING` | 调 Store 的 `cancel_remote_commands_for_workflow`：`PENDING`/`WAITING` 立即 `FAILED`（`status_source=workflow-timeout`），`LEASED` 记一次取消请求由 Agent 侧结算；不动 workflow 与 incident | workflow 上一条 `OPERATOR_RECONCILED` 事件（`actor=dispatcher`，`details.action=cancelled orphaned remote commands`，`details.command_ids`）；日志 `orphaned remote commands cancelled by the dispatcher` |

怎么确认它发生了：`GET /v1/workflows/{request_id}` 的 `events` 里出现上述事件（或
`preemption_reason`/incident `reasons` 出现撤销文本）；`gpu_fault_remote_command_total`
按状态的未结计数随取消下降；`gpu_fault_workflow_retired_generation_awaiting_operator`
只统计 dispatcher **拒绝**关闭的退役世代——它已经完成过改动节点的操作，有真实状态要补偿，
这类记录仍按 §8 定位它做了什么并单独处置，没有命令会替你关掉它。发布前置
`workflow_safety` 把编译期 BLOCKED 记录列在 `compile_blocked` 而不是 `blockers` 里，所以
携带清扫逻辑的那个 release 自己能过门，不需要先手工关记录。

`PENDING`/`RUNNING`/`SAFETY_PENDING` 的 workflow 留下的 command 永远不会被这条清扫碰：
那是活的工作，只有持租的执行器能结算；`CHECK_MECHANICALS` 等操作员确认的时长由
`GPU_FAULT_OPERATOR_ACKNOWLEDGEMENT_TIMEOUT_SECONDS`（默认 86400）控制。同样，dispatcher
自己因内部错误写成 `BLOCKED` 的记录（`blocked_kind=INTERNAL_ERROR`，已被 claim）不在
编译期形态之内，按 `GpuFaultWorkflowDispatchInternalErrors` 的卡片处理。

### 10.2 关闭已恢复但仍为 BLOCKED 的历史记录（workflow-reconcile）

唯一保留的手工形态：已经由同一 incident 的成功恢复 successor 完成验证和
`RESTORE_SCHEDULING`（`terminalization` 为 `verified-restore`），或从未改动过节点
（`never-changed`，要求 incident 为 `ESCALATED`/`RECOVERED`）、但历史 predecessor 仍为
`BLOCKED` 的记录。控制面自己关不了它，因为证据在节点上：GPU 节点已无本方案的 cordon、
`gpu-fault.io/quarantined` 污点和隔离 annotation。该命令用 site 渲染的 GPU kubeconfig
读这份证据（site 没有 GPU kubeconfig 时直接拒绝，绝不回落到 shell 的默认 kubeconfig），再把
判定交给 Pod 内的 `gpu_fault.workflow_reconcile` 写入。不得直接删数据库行或手改 workflow
JSON。

先看计划，不写任何东西：

```bash
gpu-fault-admin workflow-reconcile --state-dir /secure/gpu-fault --dry-run
```

不带 `--workflow-id` 时扫描全部 `BLOCKED`（按 `updated_at` 从旧到新，最多 10,000 条；超出
不拒绝，`discovery.scan_truncated` 为 true）。`--incident-id <id>`（可重复）只看一个
incident，`--max-items N` 限定本批条数，`discovery.remaining` 告诉你之后还剩多少；这两个
选择器只用于发现，与 `--workflow-id` 同时给出会被拒绝而不是被忽略。每条 item 的
`eligible`/`reasons` 与 `scheduling_evidence`（节点是否已恢复调度）说明它能不能关、为什么。

确认后一次执行——计划、复核、写入在同一次调用里完成：

```bash
gpu-fault-admin workflow-reconcile \
  --state-dir /secure/gpu-fault \
  --incident-id <incident-id> \
  --reference CHG-12345
```

- 没有 `--dry-run` 就必须给 `--reference`（变更单号，写进 workflow 的审计事件与 source
  plan 的 `reconciliation_reference`），否则拒绝；
- 命令在写入前**重新**出一次计划并与刚出的计划逐字段比对，任一字段（fencing token、
  execution epoch、successor、节点调度状态……）变了就指名拒绝
  （`workflow-...: fencing_token 7 -> 8`），什么都不写；`workflow_updated_at` 不参与比对，
  所以一次只改时间戳的写入不会作废计划；
- 用 `--workflow-id` 点名的记录若不合格，整次调用拒绝并列出原因；发现模式下不合格的
  记录跳过，列在结果的 `ineligible` 里；
- 每条记录单独写入：`applied_workflow_ids`/`failed_workflow_ids`/`failures` 说明哪些成了、
  哪些没成和原因，有失败时退出码为 1，已写入的不回滚，直接重跑即可——已关闭的记录不再
  出现在发现结果里。已验证恢复的形状在 Store 事务里同时写 workflow、incident 和 source
  plan 并保持 incident 指向恢复 successor；从未改动节点的形状只写 workflow
  （`preemption_reason`）与 source plan，不碰 incident；
- 结果与计划一并归档到 `workflow-reconcile/history/<plan_sha256>/`（`plan.json`、
  `applied.json`）；`applied.json` 的 `actor` 是执行者的 STS caller ARN（取不到时为
  `user@host`），同一身份与 `admin_plan_sha256` 也写在 workflow 的 `OPERATOR_RECONCILED`
  事件上；
- `records_deleted` 恒为 0；只有站点按 §10 开启了 `spec.retention`，整个 incident bundle 才会
  在保留期后由 archive-first 归档并删除，否则永久留在 Store。

有一类记录永远不会 eligible：`reasons` 只有 `workflow has no source recovery plan`。它们
是没有经过 plan 驱动恢复而直接提交的 workflow，没有 source plan 可写审计关联，这是设计
如此。此时正确处置是**不处置**：只要 `successor_workflow_id` 存在且没有 successor 相关
原因，节点已回训练池，`gpu_fault_workflow_blocked_unreconciled` 不再计入它，
`GpuFaultRecoveryBlockedBacklog` 不会因它触发；`BLOCKED` 行留在 Store（开启 §10 保留时到归档为止）。不得为了
让计数下降去改 Store 行。

必须手工迁移或 purge 时，先记录副本、停止 ingress、排空 consumer，再停所有 writer。
恢复顺序相反：consumer 先恢复，ingress 最后恢复。状态文件在所有原副本 Ready 前不得
删除。

## 11. 集中容器日志（CloudWatch Container Insights）

默认不装。日志止于节点本地是写下来的取舍（[详细设计-v2 §10.1](详细设计-v2.md#101-日志)），
本节是把控制面容器日志送出集群的那条已交付路径。

**适用条件**

站点已完成 bootstrap（`eks-pod-identity-agent` addon 为 ACTIVE），且已经确认接受
CloudWatch Logs 摄入与存储费用。本路径**只针对 CPU 控制面集群**；GPU 集群需要显式
放行，理由见下面的“影响范围”。

**影响范围**

- 装 `amazon-cloudwatch-observability` EKS addon，新建 `amazon-cloudwatch`
  namespace 与它自己的 DaemonSet。不改本仓库任何渲染清单，不进 `module_digest`，
  与发布事务无关，可以在独立窗口装卸。
- 新建四个日志组：`/aws/containerinsights/<cluster>/{application,dataplane,host,performance}`。
  `application` 承载集群内**每一个**容器的 stdout/stderr；在控制面上这就是本系统自己的
  日志，所以 `logging_setup` 的集中脱敏是硬前置。
- `host` 组的范围比组名看起来大。实测 `host-log.conf` 是三个 journald input：
  `_TRANSPORT=kernel`（即 dmesg 看到的内核消息）、`PRIORITY=0-6`、
  `SYSLOG_FACILITY=10`；唯一的 `grep` 排除是按 syslog facility（mail/cron/authpriv），
  **不按 unit**。所以 `PRIORITY=0-6` 这条是 unit 无关的：节点上只要有 `gpu-fault-*`
  systemd unit 在跑，它的 journal 也会进 CloudWatch。审计范围和账单都要按这个算。
- **它不会**采集训练日志文件——Fluent Bit 没有任意路径的 tail input，只有
  `/var/log/containers/*.log`。也不会采集 `PRIORITY=7`。
- 无论采不采，**故障证据通道不变**：控制面从不读 CloudWatch，
  `NodeLogBatch.collection_errors` 仍是唯一会把采集缺口送到控制面的通道
  （见 §8 `GpuFaultCollectorCollectionErrors`）。
- 所有 input 都从**尾部**开始（`READ_FROM_HEAD=Off`、`READ_FROM_TAIL=On`），装之前
  写下的日志一律不回填。
- 计费上要知道 kubelet 的 journal 被收**两遍**：`dataplane` 按
  `_SYSTEMD_UNIT=kubelet.service` 收，`host` 的 `PRIORITY=0-6` 又收一遍（已在
  2026-09-04 用同一行 `SyncLoop ADD` 在两个组里各命中一次核实）。这是上游 Container
  Insights 配置本身的性质，不是本脚本引入的；估算摄入量时按重复算。
- GPU 集群三个额外后果，所以默认拒绝：`application` 会把每个训练任务的 stdout 全部
  送进 CloudWatch；`host` 会把内核 XID 行和 `gpu-fault-*` unit 的 journal 再送一份，
  而这两类节点侧本来就在采；且 agent 自带的 dcgm-exporter 争用主机 9400 端口，而该
  端口已被 `gpu-fault-dcgm-exporter.service` 占用。放行须同时保持
  `GPU_FAULT_CLOUDWATCH_ACCELERATED_METRICS=false`。

**只读检查**

默认动作就是只读，先看当前状态（addon、pod identity association、每个日志组的
retention 与最后一条事件时间、DaemonSet ready 数）：

```bash
AWS_REGION=<region> \
EKS_CLUSTER=<cpu-eks-cluster> \
EKS_KUBECONFIG=/secure/gpu-fault-bootstrap/control-plane.kubeconfig \
  deploy/observability/install-cloudwatch-observability.sh
```

任何日志组出现 `retention=None` 都是“永不过期”，必须先修好再继续。

**执行命令**

```bash
AWS_REGION=<region> \
EKS_CLUSTER=<cpu-eks-cluster> \
EKS_KUBECONFIG=/secure/gpu-fault-bootstrap/control-plane.kubeconfig \
SITE_ID=<site-id> \
GPU_FAULT_CLOUDWATCH_ACTION=install \
GPU_FAULT_CLOUDWATCH_RETENTION_DAYS=30 \
  deploy/observability/install-cloudwatch-observability.sh
```

脚本幂等：先建 IAM 角色（打 `gpu-fault:site-id` 标签）和 pod identity association，
再把四个日志组的 retention 设好，最后才创建/更新 addon——顺序是为了不留下一个
“永不过期”的窗口。kubeconfig 与 `EKS_CLUSTER` 的集群 ARN 不一致时直接拒绝执行。

**成功标准**

不以 addon ACTIVE 或 Pod Ready 为准。脚本要求
`/aws/containerinsights/<cluster>/application` 出现日志流才算成功——association 缺失
或角色掉了策略时，agent 一样 Ready 却每次 PutLogEvents 都失败。随后用只读动作复核
四个日志组的 retention 均为期望天数。

不要以“每个 Pod 都有日志流”为准：Fluent Bit 从文件尾开始 tail，**不回填**装之前
已经写下的日志，因此装之前就已经安静的 Pod（长时间无请求的 `api-ha`、已 Completed
的 Job）在它下一次写日志之前不会有日志流。少一个流不能推断链路坏了；判断链路要看
`application` 组整体是否在持续收到事件。

**回滚**

```bash
AWS_REGION=<region> EKS_CLUSTER=<cpu-eks-cluster> \
EKS_KUBECONFIG=... SITE_ID=<site-id> \
GPU_FAULT_CLOUDWATCH_ACTION=uninstall \
  deploy/observability/install-cloudwatch-observability.sh
```

删 addon（不带 `--preserve`）并等到 addon-deleted、删 association、仅在 IAM 角色带本
站点标签时删角色。**日志组故意保留**：它是集群停止上送前所说过的话的唯一副本，
retention 已经约束了体积；要一并丢弃需另行执行脚本末尾打印的 `delete-log-group`。
不可逆边界：已经摄入的日志按 retention 计费，卸载不退。

注意与 §3 的关系：`gpu-fault-admin uninstall --cpu-cluster keep` **不会**清掉这个
addon（它不在资源注册表里，这正是它不进发布事务的代价），必须先跑上面的 uninstall；
`--cpu-cluster delete` 会随集群一并删除。

**证据**

变更单号、只读动作在装前装后的两份输出、addon 的 `--configuration-values`、四个日志组
的 retention，以及 `application` 组首个日志流的时间戳。

## 12. 当前待产品化命令

`gpu-fault-admin` 交付的全部动词（与解析器一致，没有第二份清单）：

```text
deploy               首次/升级/续跑/回滚/接入/审批Profile计划/跨schema发布，全部是同一动词加参数
status [--full]      只读健康；--full 是完整独立验收（原 verify、原 doctor 设想都并入此处）
config               管理员容量配置（计划与执行同一命令，--dry-run 只看计划）
join-cluster         deploy 加新 ARN 的别名，一个 release 内完成
remove-cluster       按 --gpu-cluster-arn 移除一个 GPU 集群
uninstall            卸载；--cpu-cluster keep|delete，--reset-database 才清库
workflow-reconcile   收敛已恢复但仍 BLOCKED 的历史 workflow（--dry-run / 执行）
rotate-token         一条命令完成 cluster token 重叠窗口轮换
submit-remediation   CHECK_MECHANICALS 后的明确处置
failure-domain-map   只读调试：打印产品将渲染的失败域映射
```

以下过去列为"路线图"的动词**不会**出现，原因各不相同：

| 曾设想的动词 | 结论 |
|---|---|
| `preflight` / `verify` / `approve-profile` / `resume` / `rollback` | 都并入 `deploy`（自动 preflight、`--approve-profile-plan`、重跑即续跑、`--rollback`）或 `status --full`，不再是独立动词 |
| `doctor` | 并入 `status --full`：Pod、证书、Agent/Collector 版本、remote command 积压都在那一份报告里 |
| `renew-certificate` | 不做。NLB 证书是 bootstrap 自签发并导入 ACM 的 3650 天证书，ACM 不续期导入证书；到期前按 §6 表重新签发、导入并走节点 rollout |
| `rotate-node-key` | 不做。每节点 key 由 fleet master 派生（key version 2）；单节点重装走 installer-state=Retrying 即重新派生 |
| `refresh-aurora-credential` | 不做。Aurora 凭据刷新已自动：每小时 CronJob 加每次 deploy/rollback 前同步跑一次（§4） |
| `approve-gpu-change` | 不做。GPU 数量变化审批就是一条 `kubectl annotate`（REG 8.1），再包一层动词没有收益 |
| `reserve-spare` | 不是动词，是产品自动化缺口：spare 不足后的降级恢复目前仍按 REG 8.2 人工执行 |

其他当前缺口：自动证据包和准入策略尚未产品化（运维仪表盘已由 deploy 自动配置，见 §8.0）。

| 优先级 | 目标 |
|---|---|
| 已完成P0 | schema化`site.yaml`、live preflight、一条`deploy`、`status --full`完整验收 |
| 已完成P0.1 | Aurora AWS注册表、单命令卸载、CPU保留/删除选择和逐项残留验证 |
| 已完成P1 | `rotate-token`、`submit-remediation`、`workflow-reconcile` 单模式、失败域映射自动化、Grafana 仪表盘自动配置 |
| P2 | 自动证据包、准入策略、spare 预留自动化 |

后续管理员能力的验收标准保持不变：不打印Secret、不要求手工`sed`、不直接编辑方案
Manifest或在线Deployment；声明式站点配置应具有dry-run、持久状态、续跑、回滚和证据。
