# GPU 故障处理系统管理员日常运维

本文从站点首次上线验收完成后开始，按“任务或症状”组织，不要求管理员理解内部模块
调用链。首次建站或应用层重建见[管理员快速部署](管理员快速部署.md)；底层命令、安全
理由和特殊恢复步骤保留在[部署和运维手册](部署和运维手册.md)。

## 2. Runbook 固定格式

任何新增管理员 runbook 都必须包含以下七项：

1. **适用条件**：什么状态下允许执行。
2. **影响范围**：CPU、哪些 GPU 集群、训练任务和外部资源会受影响。
3. **只读检查**：执行前必须满足的门禁和预期输出。
4. **执行命令**：唯一正式入口，默认 dry-run 时必须说明。
5. **成功标准**：不能只以进程退出码或 Pod Ready 判断。
6. **回滚**：恢复顺序、状态文件和不可逆边界。
7. **证据**：变更单、release/profile、命令输出和最终状态。

不得把“扩大权限、关闭 TLS、删除 fencing、修改终态记录”写成排障步骤。

### 2.1 容量配置

普通容量变化不重新build代码，也不发布Aurora动态revision。编辑
`<state-dir>/admin-config.yaml`后执行：

```bash
gpu-fault-admin config \
  --state-dir /secure/gpu-fault \
  --reference CHG-12345
```

CLI内部自动生成计划SHA和审计。该路径复用当前签名镜像和wheel，只滚受影响的
ingress、control-worker或spool-worker。完整字段、模板、首次部署和回滚语义见
[管理员容量配置](管理员容量配置.md)。

## 3. 完整卸载或永久退役

**适用条件**

- 已停止新的训练提交，活动 workflow、remote command 和节点隔离状态满足清理门禁；
- `state-dir`中的内部site包含当前全部受管GPU集群；
- 执行身份仍能访问 CPU/GPU Kubernetes API 和注册表中的 AWS 资源。

**影响范围**

- 两种模式都卸载 CPU/GPU 侧本方案组件、节点 systemd、NLB、方案 IAM/监控/PKI、
  方案专属网络对象和方案专属 Aurora；
- 所有 GPU EKS/HyperPod 和客户训练 workload 始终保留；
- `--cpu-cluster keep` 保留 CPU EKS/HyperPod；
- `--cpu-cluster delete` 删除 CPU EKS/HyperPod，但不删除其外部 VPC。

卸载依赖三层资源事实源：

| 清单 | 位置 | 用途 |
|---|---|---|
| Kubernetes安装清单 | 每个CPU/GPU EKS的`gpu-fault-system/gpu-fault-installed-resources` | 删除实际安装的workload、RBAC、Secret、ConfigMap和namespace |
| 节点安装清单 | `/opt/gpu-fault/installed-units.txt`，摘要和完整列表同步到Aurora AgentRecord | 卸载实际安装的systemd unit |
| AWS方案资源注册表 | Aurora `gpu_fault_objects`中的`installation_resource` | 记录ARN/ID、`CREATED/EXTERNAL`、`DELETE/DETACH/PRESERVE`和依赖 |

**执行命令**

```bash
# 保留 CPU 集群，便于以后重新部署
gpu-fault-admin uninstall \
  --state-dir /secure/gpu-fault \
  --cpu-cluster keep \
  --confirm UNINSTALL_GPU_FAULT

# 永久退役 CPU 控制面
gpu-fault-admin uninstall \
  --state-dir /secure/gpu-fault \
  --cpu-cluster delete \
  --aurora-final-snapshot retain \
  --confirm DELETE_CPU_CONTROL_PLANE
```

**成功标准**

- CPU 和每个 GPU EKS 的 `gpu-fault-installed-resources` 以及方案 namespace 不存在；
- 所有注册表 `DELETE`/`DETACH` 条目经真实 AWS 查询确认不存在；
- `PRESERVE` 条目仍存在，尤其是所有 GPU EKS/HyperPod；
- `uninstall/state.json` 为 `COMPLETED`；
- `uninstall/installation-resources-final.json` 的 `delete_policy_residuals` 为 `0`。

Aurora 中的 AWS 注册表必须在卸载开始时先导出。非 Aurora 资源和可选 CPU 集群验证
完成后才进入 `READY_TO_DELETE_AURORA`；Aurora cluster 及其因依赖只能后删的
subnet group/SG 构成最后一个销毁阶段。Aurora 删除后，带 SHA-256 的外部最终快照是
本次退役证据，不再依赖已经销毁的数据库。

固定顺序为：

1. 导出Aurora注册表，将待删条目标记为`DELETE_PENDING`。
2. 停止新请求并排空队列，卸载节点unit和CPU/GPU Kubernetes对象。
3. 确认两侧installed-resource ConfigMap、注册对象和方案namespace已不存在。
4. 按依赖删除NLB/listener/target group、DNS、PKI、监控、IAM和方案专属网络资源。
5. 按`--cpu-cluster`保留或删除CPU EKS/HyperPod，并再次确认所有GPU集群存在。
6. 写出`installation-resources-pre-aurora-delete.json`后才删除Aurora stack。
7. 写出带SHA-256的`installation-resources-final.json`并确认残留为0。

**失败续跑**

直接以完全相同的参数重跑命令。`uninstall/state.json`、Aurora 导出清单和
`kubernetes-cleanup.json` 会被复用；删除 API 都按幂等方式执行。不要删除
`uninstall/` 状态目录后手工续跑。

旧线上版本没有 `/v1/installation-resources` 时不需要改走手工流程。CLI 会从同站点
bootstrap state、live NLB 和 AWS 标签重建清单，并利用运行中控制面 Pod 的现有
Aurora 连接直接回填注册表。只有所有权证据缺失或冲突时才中止。

旧版注册表中标成`REUSED/PRESERVE`的方案专属Aurora、IAM、SG、PKI、监控或LBC不会
继续保留；卸载器按同站点遗留资源处理。只有EKS/HyperPod、外部公共subnet、VPC IGW、
OIDC Provider和预装Pod Identity Agent等集群基础能力可继续`PRESERVE`。

旧环境缺少内部site时，先使用受检迁移/发现流程把状态恢复到指定`state-dir`，再执行
相同uninstall命令。ARN发现参数仅保留为隐藏兼容，不属于正常管理员接口。

## 4. 区域升级

**适用条件**

- 配置包含全部已纳管 GPU 集群；
- remote command 的 `PENDING/LEASED/WAITING` 为 0；
- release artifact 已完成 `make release-preflight`；
- Runtime Profile内容未变化，或已按本节生成并独立审批新的计划。
- 若变更涉及 `ddl*.py`、Processor claim/retry/completion 或 PostgreSQL pool，
  CAP-005 runner 已在隔离 PostgreSQL 16 database 上零 skip 通过。

**只读检查**

**执行命令**

```bash
gpu-fault-admin deploy \
  --cpu-cluster-arn <cpu-arn> \
  --gpu-cluster-arn <gpu-arn> \
  --state-dir /secure/gpu-fault \
  --admin-email <operations-email>
```

`deploy` 根据 live release state 自动选择 bootstrap 或 upgrade。
当前 PostgreSQL schema 基线为 v11；schema 变化必须分类为 `FULL`。`deploy` 的 schema 阶段
（`deploy/control-plane/tools/ensure-postgres-schema.sh`，附录 A 的单集群 `deploy.sh` 同序）在滚动
业务进程之前按顺序运行三个一次性 Job，任一失败即停止，不会滚动：

1. `gpu-fault-postgres-index-build`（`gpu-fault-store-migrate --build-indexes-concurrently`）：
   对代码声明但库里缺失或无效的索引逐条执行 `CREATE INDEX CONCURRENTLY`，见 §4.2。
2. `gpu-fault-postgres-schema-ensure`（`--ensure-schema`）：幂等 DDL 与迁移登记，把
   `gpu_fault_schema_migrations` 推进到 wheel 要求的版本。索引已由上一步建好，这里只是跳过。
3. `gpu-fault-postgres-schema-preflight`（`--schema-preflight`，只读）：见 §4.3 的门禁清单，
   JSON 报告打印在部署日志里。

不能让 Pod 启动时自行 DDL：`GPU_FAULT_POSTGRES_AUTO_SCHEMA_INIT` 必须保持 `false`。

`deploy` 把快验证据写到 `<state-dir>/quick-validation.json`，随后的
`gpu-fault-admin status` 会自动读取它，复用刚刚跑过的只读校验（control plane
role split 和每个 GPU 集群的 data plane executor 探针），并在报告里列出
`reused_validation_checks`。复用有硬条件：release id、交付摘要、site 身份和线上
release state 摘要必须全部一致，且证据不超过 10 分钟；任何一项不满足就重新执行探针，
并在 `validation_evidence_fallback` 里给出原因。`verify` 不复用证据——要门禁就跑探针。

若命令因Runtime Profile策略变化停止，先审核
`<state-dir>/release-deploy/profile-plan.json`，再执行：

```bash
gpu-fault-admin approve-profile \
  --state-dir /secure/gpu-fault \
  --plan-sha256 "$(jq -er '.plan_sha256' \
    /secure/gpu-fault/release-deploy/profile-plan.json)" \
  --reference CHG-12345
```

之后重跑原四参数deploy。审批绑定具体计划和live baseline；计划漂移会废止旧审批，
失败续跑不需要重复审批，成功后活动记录被消费且不能重放。

| 分类 | 实际动作 |
|---|---|
| `NOOP` | 不上传、不迁移、不滚动，只运行 CPU/GPU verifier |
| `CONTROL_PLANE_ONLY` | 只上传 Control Plane wheel并滚动CPU三层角色 |
| `DATA_PLANE_COMPATIBLE` | 只上传变化的Executor/Node制品，按GPU集群顺序推进 |
| `FULL` | schema、协议、Agent配置、Profile或集群集合变化时执行完整两阶段发布 |

物理 SHA-256 用于确认 Pod/节点安装的实际文件，组件 `module_digest` 用于判断行为内容。
Agent 和 Executor 都携带 artifact SHA、compatibility digest 和 protocol；只有这些
值实际变化时才打开 required/compatible 窗口。共享release默认一次只推进一个GPU集群；
单集群内Executor先收敛，Watcher/Collector同波并行，随后进入Reconciler和Node Runtime。
upgrade第一波固定1，之后按节点规模和故障域自适应到4、8、16或显式32；rollback第一波
固定1，后续保守自适应为1、2或4。

涉及GPU或Node Runtime的upgrade会在schema Job和CPU rollout前写入
`candidate-preflight-ready`：候选Manifest完成server-side dry-run，逐节点只读host
probe证明制品摘要、磁盘、Python/systemd/驱动和rollback slot。进入第一台节点mutation
前仍会重新检查Node状态、Executor、remote command、破坏性workflow和Agent lease。
早期门禁失败不会触发CPU/GPU rollout；晚期动态门禁失败则按已有事务证据裁剪回滚。
未达到`data-converged`的resume会重新执行只读候选/host预检，不会永久信任旧checkpoint。

某个GPU集群出现本地容量、Agent安全门或收敛超时、Installer失败时，站点release进入`PAUSED`：已经
`CONVERGED`的集群保持候选版本，当前失败集群保留checkpoint，后续集群保持`PENDING`。
修复原因后重跑同一条四参数deploy，系统会重新校验release、执行计划、previous摘要、
CPU兼容窗口、集群身份和节点集合，然后从失败集群续跑。未知范围或全局故障仍fail closed。

**成功标准**

- CPU 三层角色、GPU Executor/Watcher/Resource Collector/Reconciler，以及节点
  systemd Collector/Agent 全部收敛；
- Control Plane、Executor、Node Runtime 各自指向目标 component；
- Agent/Executor required artifact、compatibility digest 为新版本，compatible 为空；
- Runtime Profile、Agent config digest 和 protocol 一致；
- verifier 通过且 remote command 没有新增积压。

**回滚**

```bash
deploy/control-plane/regional/rollout-regional-release.sh \
  rollback --config "${CONFIG}"
```

只执行 `kubectl rollout undo` 不会恢复 release metadata、installer bundle 或节点
artifact，不构成区域回滚。

回滚目标若是尚无独立 component pin 的旧单 wheel release，编排器会自动把 Agent
compatibility digest 回退到旧 artifact SHA，并在应用旧 Deployment 前移除新版本才
认识的 6 个 component-pin 环境变量；不得手工把这些变量留给旧进程。

升级失败或自动回滚后，直接重跑同一条四参数`gpu-fault-admin deploy`。尚未完成回滚的
`failed`事务只允许同一release按原始`release_diff`执行resume；已经验证回滚并进入
`rolled-back`终态后，下一候选复用保守差异集合，但从当前线上基线开启新事务，不把旧
release checkpoint当作resume状态。新事务会清空上一release的rollback phase和cluster
checkpoint，避免把历史回滚误判为当前回滚已完成。不要删除release state ConfigMap。
回滚只补偿有mutation证据的组件和集群，并按实际升级顺序逆序恢复；Executor-only失败
不会重装Agent，GPU-only且未改CPU pin的事务不会无意义滚动CPU。rollback verify通过后
管理site、容量desired配置和release state会对齐previous版本，因此
`gpu-fault-admin status`应以当前回滚后线上版本报告健康，而不是继续比较失败候选。
`partial-convergence`继续原upgrade checkpoint；任何`rollback-*`或
`rollback-failed`只继续rollback。若线上已经commit/rolled-back而仅临时Secret备份
清理失败，重跑只补清理，不会重新滚动组件。站点设置`autoRollback=false`时，verify或
stability失败保留候选中间态并标记`SKIPPED_POLICY`。

endpoint和regional cluster registry的变化不是事务性的，
`autoRollback=true`时部署在滚动任何组件之前就会以
`automatic rollback is not yet transactional for: <字段>`失败。这类发布必须由管理员
显式改为fail-forward：在`site.yaml`把`spec.autoRollback`设为`false`再重跑同一条部署
命令。重新部署会重新渲染site，但会保留管理员声明的`autoRollback`，不会悄悄改回
`true`；缺失或非布尔值仍按`true`处理。fail-forward期间失败不会自动回滚，恢复手段是
修复后重跑同一条部署命令续跑，或用本节上面的`rollback --config`显式回滚到上一已提交
release。发布提交后应把
`spec.autoRollback`改回`true`，让后续事务性发布重新获得自动回滚。

ADOT Manifest和ADOT image不属于这一类，只改ADOT不需要fail-forward：升级在改动
collector之前会把线上ADOT对象读入observability快照，回滚按快照恢复这些对象、删除候选
新增的对象，并重启collector等待其重新Ready，恢复的是上一release自己applied的配置和
镜像。快照缺少collector Deployment、或旧state里没有ADOT对象时回滚fail closed，不会声称
补偿了没有恢复的面。续跑一个在该能力上线之前开始的失败事务时，它的previous快照没有ADOT
对象，部署会在滚动任何组件之前以
`previous observability snapshot predates ADOT rollback capture`失败；这一个事务仍按上面
的fail-forward流程续跑，提交后再把`spec.autoRollback`改回`true`。

### 4.0 节点被 HyperPod 重镜像后 Agent 消失（UpdateClusterSoftware）

`UpdateClusterSoftware` 会原地重装 GPU 节点的系统盘：Node 对象与 UID 不变、注解全部保留，
但 `/opt/gpu-fault`、`/var/lib/gpu-fault`、`/etc/gpu-fault` 与全部 `gpu-fault-*` systemd
unit 都会消失，Agent 租约随之过期。node-installer-reconciler 过去只比对注解与 Node UID，
因此把这样的节点判为 `current`、不再重装；发布会在"previous Agent identity capture"处以
`<cluster> has no active Agent identity to capture` 失败。

reconciler 现在把安装记录绑定到 `status.nodeInfo.bootID`（注解
`gpu-fault.io/installer-boot-id`）：boot id 变化后先探测 Agent 端口
（`GPU_FAULT_NODE_AGENT_PORT`，默认 9099）——有应答只是普通重启，重新盖上 boot id；
无应答且节点 Ready 已超过 `GPU_FAULT_INSTALLER_REBOOT_GRACE_SECONDS`（默认 600）则标记
`Retrying` 并按常规波次重装（`rebooted`/`recovering` 两个计数会出现在 reconcile 日志里）。
旧版本安装的节点没有该注解，第一次 reconcile 只补注解、不重装。

携带本修复的 release 部署之前若已经发生重镜像，用 reconciler 自己的重试通道触发重装：

```bash
kubectl --context "${GPU_CONTEXT}" annotate node <node> \
  gpu-fault.io/installer-state=Retrying --overwrite
```

reconciler 会为该节点创建 installer Job（受 `max-unavailable` 约束，逐节点进行），完成后
Agent 租约恢复。这只改动安装簿记注解；不得以同样方式改动隔离/incident 注解或污点。


### 4.1 读部署日志的耗时

一次升级输出三千多行，过去只有 `release-phase` 带秒级时间戳，任何"这次为什么慢"的问题
都要人工去减两个时间戳，而单条命令的耗时根本无处可查。现在按三层读：

| 行 | 含义 |
|---|---|
| `release-begin <stamp> mode=<mode> dry_run=<bool>` | 本次脚本调用开始。一条 `gpu-fault-admin deploy` 会驱动这个脚本十余次（plan/preflight/deploy/verify/commit），所以日志里有多段 begin/end |
| `release-end <stamp> mode=<mode> exit_code=<n> total=<秒>s` | 本次调用结束，含失败路径。看不到 end 就说明进程还卡在最后一条命令里，或已被杀掉 |
| `release-phase <stamp> <phase> ... elapsed=<秒>s total=<秒>s` | `elapsed` 是从上一个 checkpoint 走到这个 checkpoint 的代价，`total` 是本次调用累计 |
| `command-elapsed <秒>s <命令>` | 单条命令耗时。只有超过 15 秒才打印，否则几千条亚秒级 kubectl 会把命令轨迹淹掉；`probe` 类只读检查本来不回显命令，也走这条线 |

phase 是 checkpoint 之间的间隔，而升级最长的一段恰好落在**一个** phase 里面：
`data-plane-progress` 每个集群只 checkpoint 一次，一个四波次的集群会打出两条相隔七分半
的 phase 行，中间全是 `get nodes`/`get jobs` 的轮询。这一段现在有自己的行，都带 `total`
但不带 `elapsed`——它们在 phase 内部打印，占用 phase 的 split 会把七分钟的 phase 记成
最后三十秒：

| 行 | 含义 |
|---|---|
| `fleet-wave <stamp> cluster=<id> phase=<phase> wave=<i>/<n> ready=<就绪>/<总数> nodes=<节点>` | 一个波次开始。`wave` 是它在本集群波次序列里的位置，`ready` 是滚动前已经在新身份上的节点数 |
| `fleet-wave-done <stamp> cluster=<id> wave=<i>/<n> ready=<就绪>/<总数> safety=<秒>s handoff=<秒>s install=<秒>s elapsed=<秒>s` | 波次结束，并把耗时拆成三段：`safety` 是 Agent lease 与未完成命令的等待，`handoff` 是 Reconciler rollout 加上一波遗留 Job 的清理，`install` 是节点自己装 |
| `installer-wait <stamp> cluster=<id> nodes=<n> aligned=<n> waiting=installers\|heartbeats pending=<节点>:<状态>,... elapsed=<秒>s` | 波次内部的等待。`waiting=installers` 是还有节点没装完，`pending` 逐个给出节点名和它的 `gpu-fault.io/installer-state`（`<none>` 表示 Reconciler 还没建 Job，下一个 reconcile pass 才会建）；`waiting=heartbeats` 表示节点已经装上新身份，在等 Agent 心跳上报。状态一变就打印，否则每 30 秒重复一次，节点多于 5 个时只列前 5 个并以 `+N` 收尾 |

看 `fleet-wave-done` 的三段拆分才知道一个慢波次值不值得优化：`install` 大就是集群在做
升级本来的工作，`safety`/`handoff` 大才是控制面自己的开销。`installer-wait` 的轮询间隔
从 5 秒退避到 15 秒，但只要 `pending` 集合缩小就立刻回到 5 秒——一波一个节点滚动时，
退避会把下一个节点的安装尾巴整段睡过去。

`make check` 的十个静态门并行跑，墙上时间等于最慢的那个门，所以每个门收尾会打印
`static-gates: <门> passed in <秒>s`；一个门里包含多条命令时，超过 5 秒的那条单独打印
`static-gates: <门> step took <秒>s: <命令>`，失败行也带上命令名和耗时。

耗时都用 monotonic 时钟测量，中途时钟跳变不会产生负数 phase。计时随每次进程调用重置，
因此 `total` 是本次调用的耗时，不是整条 deploy 的；要整条 deploy 的耗时就把各段
`release-end` 的 `total` 相加，或直接看首尾时间戳。

**边界**

- 这些行只是观测，不构成门禁。不得因为某个 phase 慢就上调超时、跳过探针或删除门；
  §8 的同一条约束在这里同样适用。
- `<sensitive command>` 的耗时行同样不展开参数。不要为了看清慢命令去打印敏感命令的
  参数，含密码/令牌的命令必须保持不可见。
- 不要为了让日志"干净"去调大慢命令阈值：那等于把要找的慢命令重新藏起来。
- `installer-wait` 长时间停在同一个 `pending` 节点上，处理的是那个节点（看它的 installer
  Job 与 `installer-state`），不是去缩短 `wait_agents` 的超时或放宽收敛判定：`pending`
  的成员判定和门禁用的是同一个 `agents_converged`，改一个就等于改门。

### 4.2 索引三步法（为什么不能让 DDL 建索引）

- 幂等 DDL 在**一个事务**里执行，而 PostgreSQL 禁止在事务内 `CREATE INDEX CONCURRENTLY`；
  如果让 ensure Job 或 Pod 启动去建一条新索引，它只能用普通 `CREATE INDEX`，建索引期间
  `gpu_fault_objects`（全部 workflow / incident）或 `gpu_fault_processor_queue`（处理器队列）
  的写入被锁住，准入、认领、完成、派发全部停摆，时长取决于表大小。
- 所以规则是：① `gpu-fault-postgres-index-build` Job 用 `CONCURRENTLY` 在线建；② DDL 只写
  `CREATE INDEX IF NOT EXISTS`，看到已存在就跳过；③ 每个副本启动时校验代码声明的索引
  全部存在，缺失即拒绝启动（`PostgreSQL indexes are missing`），宁可起不来也不让热点查询
  退化成全表扫描而无人察觉。
- `CONCURRENTLY` 建索引失败（连接中断、超时）会留下一个 `indisvalid = false` 的无效索引；
  index-build Job 会先 `DROP INDEX CONCURRENTLY` 再重建。手工核对：

```sql
SELECT c.relname, i.indisvalid
FROM pg_class c JOIN pg_index i ON i.indexrelid = c.oid
WHERE c.relname LIKE 'gpu_fault_%' ORDER BY 1;
```

- 需要手工执行时（例如 Job 无法运行），在 writer 上逐条执行
  `gpu-fault-store-migrate --build-indexes-concurrently --postgres-url <url>`，或按
  `src/gpu_fault/store/postgres/ddl*.py` 里的定义手写 `CREATE INDEX CONCURRENTLY IF NOT EXISTS`。

### 4.3 FULL 发布前的 schema preflight 清单

`gpu-fault-postgres-schema-preflight` Job 只读检查以下三项，任一不满足就以非零退出并停止部署；
也可在任何时候手工运行 `gpu-fault-store-migrate --schema-preflight --postgres-url <url>`：

| 检查 | 通过条件 | 不通过时怎么办 |
| --- | --- | --- |
| schema 版本 | `gpu_fault_schema_migrations` 的最大版本等于 wheel 要求的版本，且历史校验和一致 | 落后：跑 ensure Job；超前：wheel 比库旧，换正确的 release；校验和不一致：停止，人工比对迁移登记 |
| 索引 | 代码声明的索引全部存在且 `indisvalid` | 跑 index-build Job（§4.2） |
| 在飞的安全流程 | 没有 `RUNNING`/`SAFETY_PENDING`、`blocked_reasons` 非空且缺 `safety_only` 字段的工作流 | 等这些工作流结束（通常几分钟）再滚动；它们是 `safety_only` 字段出现之前写下的老记录，新代码无法判断它们该跑哪套步骤 |

对应的只读查询（在 writer 或只读副本上执行）：

```sql
SET default_transaction_read_only = on;
SELECT key, payload->>'status'
FROM gpu_fault_objects
WHERE kind='workflow'
  AND payload->>'status' IN ('RUNNING','SAFETY_PENDING')
  AND jsonb_array_length(coalesce(payload->'blocked_reasons','[]'::jsonb)) > 0
  AND coalesce(payload->>'safety_only','false') <> 'true';
```

### 4.4 本轮新增配置项（默认值可直接上线）

以下变量都有代码默认值，部署配置不需要新增任何键；列出是为了知道它们存在和何时调整。
完整清单见 `管理员环境变量参考.md`。

| 变量 | 默认 | 含义 | 何时调整 |
| --- | --- | --- | --- |
| `GPU_FAULT_WORKFLOW_INTERNAL_ERROR_BACKOFF_SECONDS` | 60 | 派发遇到未识别的内部错误时，工作流退避多久再试（以前直接 BLOCKED） | 内部错误多为瞬时故障且希望更快重试时调低 |
| `GPU_FAULT_PROCESSOR_DEADLINE_EXCEEDED_PROCESS_THRESHOLD` | 3 | 多少个不同请求执行超时后，处理器进程才认为是自身问题并自毁 | 更保守取 2；单条毒请求不再能重启整个机队 |
| `GPU_FAULT_PROCESSOR_UNHEALTHY_TTL_SECONDS` | 300 | 进程 unhealthy 闩锁多久后自动清除 | 关掉自毁开关时尤其重要，否则后台服务永久停摆 |
| `GPU_FAULT_JOB_WORKFLOW_MAX_LIFETIME_SECONDS` | 3600 | 作业工作流（含作业重启）从首次领取起的硬上限；到点失败并升级到人工，之后同作业事件只记录 | 作业规模大、换备机链路长时调高 |
| `GPU_FAULT_NODE_WORKFLOW_MAX_LIFETIME_SECONDS` | 3600 | 单节点无作业工作流的硬上限，整条 reset→reboot→换机链共用 | 同上 |
| `GPU_FAULT_BRANCH_ESCALATION_MAX_RUNGS` | 2 | 作业工作流里单个节点分支就地升级的最大级数（reset→reboot→换机） | 不希望自动换备机时设为 1 |
| `GPU_FAULT_JOB_WORKFLOW_NODE_BUSY_WAIT_SECONDS` | 240 | 规则 A 的唯一窗口：训练作业的节点正被别的修复占用时，作业只等这一段时间。修复在窗口内完成则作业继续（排队的作业工作流被派发；`after_incident` 重启把作业重启）；超过窗口作业不再重启——还在跑的作业以带控制面发起者标记的 STOP_WORKLOADS 停掉、已经死掉的作业其重启计划失败，工作流 FAILED、incident ESCALATED，系统自己停掉的作业不会再被任何人重启。派发器（未开始的作业工作流）与执行器（已在跑的重启前提）读的是同一个变量 | 单节点修复常超过 4 分钟时调高；两处读值不等即拒绝启动 |
| `GPU_FAULT_PROCESSOR_LEASE_RECLAIM_SECONDS` | 30 | 周期任务多久扫一次处理器队列，把 lease 已过期仍为 LEASED 的请求退回 PENDING；每次回收计入 `gpu_fault_processor_expired_leases_reclaimed_total` | 一般不调；lease 本身（`GPU_FAULT_PROCESSOR_LEASE_SECONDS`）调长时可同步放宽 |
| `GPU_FAULT_PROCESSOR_COUNTER_DRIFT_SCAN_SECONDS` | 60 | 周期任务多久对比一次处理器队列分片计数器与真实 PENDING/LEASED 行数，刷新 `gpu_fault_processor_counter_drift_abs` 与 `gpu_fault_processor_counter_mismatched_clusters`（不在 scrape 里算） | 队列表很大、这次 COUNT 明显拖慢 Aurora 时调长；告警窗口是 5 分钟，不要调到接近它 |
| `GPU_FAULT_PENDING_TRIAGE_DEADLINE_SECONDS` | 900 | 完成事件的决策允许停留在 `PENDING_TRIAGE` 多久，超过后由周期任务收口；`GpuFaultCompletionPendingTriageBacklog` 的 `for` 是它的两倍 | 观察器投递本来就慢的环境可调高，同时把告警 `for` 同比调整 |
| `GPU_FAULT_PENDING_TRIAGE_SCAN_SECONDS` | 60 | 周期任务多久扫一次超期的 `PENDING_TRIAGE` 决策；每次收口计入 `gpu_fault_completion_pending_triage_reconciled_total` | 一般不调 |
| `GPU_FAULT_WORKFLOW_INVARIANT_CHECKS` | log | 执行器每次带 lease 写入后核对 workflow 记录的状态机不变量（索引有序无重、DAG join 标记、终态无 owner/lease、`events` 有界有序等）；`off` 不查，`log` 记 error 日志继续，`raise` 让该次写入失败 | 生产保持 `log`；staging 与验收演练用 `raise` 把畸形记录当场暴露 |

**时序参数之间的顺序关系。** 上表与 §4 其它地方的等待类参数不是各自独立的，代码里有一条隐含的排序，
启动时由 `gpu_fault.execution.config.validate_timing_relationships` 逐条核对（违反即拒绝启动，
只能核对不了的项以 `warning:` 日志给出）：每个步骤等待上限（默认 `GPU_FAULT_WORKFLOW_STEP_TIMEOUT_SECONDS`
与各覆盖值，含 `GPU_FAULT_HYPERPOD_MANAGED_RECOVERY_TIMEOUT_SECONDS` 的托管恢复窗口）≤ 单节点生命周期
`GPU_FAULT_NODE_WORKFLOW_MAX_LIFETIME_SECONDS`（否则生命周期先于步骤上限把步骤判失败，adapter 自己的超时处理——
托管恢复的升级通知——不会跑；`CHECK_MECHANICALS` 的人工确认上限除外，claim 时生命周期会以它为下限）；
托管恢复窗口 + 一次 reboot 配额 ≤ 作业生命周期 `GPU_FAULT_JOB_WORKFLOW_MAX_LIFETIME_SECONDS`，且作业生命周期 ≥
`GPU_FAULT_BRANCH_ESCALATION_MAX_RUNGS` × 托管恢复窗口（升级后的分支最多做这么多次委托恢复）；执行超时
`GPU_FAULT_WORKFLOW_EXECUTION_TIMEOUT_SECONDS` ≤ 两个生命周期（claim 取两者较小值，配大了等于没配）；lease
`GPU_FAULT_WORKFLOW_LEASE_DURATION_SECONDS` < 执行超时；`GPU_FAULT_JOB_WORKFLOW_NODE_BUSY_WAIT_SECONDS`
在执行器配置与派发器配置里必须相等（规则 A 只有一个窗口，两者读同一个变量，不等说明有人绕过环境变量各配了一份），且 <
`GPU_FAULT_GPU_CLIENT_VERIFY_MAX_ATTEMPTS` × `GPU_FAULT_WORKFLOW_POLL_INTERVAL_SECONDS`（作业工作流放弃等待、
STOP 作业的时刻必须早于节点修复 VERIFY 放弃的时刻，否则 STOP 永远来不及帮到 VERIFY）；
`GPU_FAULT_WORKFLOW_DISPATCH_LEASE_SECONDS` ≥ 3 × 轮询间隔（默认即 `max(15, 3×poll)`，显式覆盖时校验）；
`GPU_FAULT_WORKFLOW_DISPATCH_CYCLE_SECONDS` 若 > 0 则 ≥ 轮询间隔。调任何一个都先对着这张关系表看它的邻居。

## 5. 接入和移除 GPU 集群

管理员只提供已有 GPU EKS 或 HyperPod ARN：

```bash
gpu-fault-admin join-cluster \
  --state-dir /secure/gpu-fault \
  --gpu-cluster-arn \
    arn:aws:eks:us-west-2:123456789012:cluster/gpu-prod-b \
  --gpu-cluster-arn \
    arn:aws:eks:us-west-2:123456789012:cluster/gpu-prod-c
```

命令自动发现 EKS/HyperPod 身份并校验同账号同 Region、`NodeRecovery=None`，然后更新
独立 kubeconfig、创建 cluster token、Executor IAM/OIDC、NLB NAT EIP 白名单、
Route53 VPC association和节点Action key。它使用候选site执行低层join与完整verify；
全部通过后才原子更新正式`site.yaml`并把EKS、HyperPod、Executor IAM和DNS association
写入Aurora注册表。

首次deploy一次提供多个GPU ARN时，第一个集群先形成稳定基线，其余集群自动使用batch
join：只运行一次基线verify、一次合并候选preflight和一次最终verify，最多4个集群并行。
每个目标仍独立经历`PENDING -> ACTIVE`；一个集群失败进入`FAILED/ROLLED_BACK`，不会
撤销同批次已成功集群。批次证据位于`join-cluster/batches/<batch-id>/state.json`。
约1000节点集群还受全局64节点Installer预算约束；当每集群波次为32时实际最多2个集群
同时部署。并发启动多个join CLI时，同一站点只执行一个完整事务，其余等待文件锁，不会
把每个进程的“最多4路”叠加。
首次多ARN目标会写入bootstrap state。中途失败后重跑原命令时，已成功成员允许是原目标
的子集，只为缺失成员继续join；原目标身份、顺序或CPU锚点变化会fail closed。

首次基础设施阶段只创建CPU和首个基线GPU集群所需的namespace、token、IAM、NAT白名单
及Private Hosted Zone VPC关联；其他GPU ARN不会提前获得网络权限。每个后续join只增加
自己的独占资源。多个集群共用同一VPC时只关联一次，移除其中一个集群不会解除仍被其他
集群使用的VPC。

状态位于`site.yaml`同目录的`join-cluster/<arn-hash>/state.json`。提交`site.yaml`
前失败会自动清理数据面、发布FAILED/ROLLED_BACK并回收本次IAM/网络变更；提交阶段在
membership锁内增量合并site、release state和Aurora registry，不会覆盖并发join。
候选verify证据有效期15分钟，提交前重新检查site、release和registry未漂移。完成这些
可补偿提交后才进入`ACTIVATION_STARTED -> ACTIVE`；该点之后失败保留已部署资源并要求
重跑同一命令fail-forward，不再执行rollback。成功标准是 registry、connection
Secret、Executor、Collector、Reconciler、全部当前Agent和Aurora资源键同时就绪。

移除前必须确认目标集群没有活动 workflow 或 remote command。正常入口是：

```bash
gpu-fault-admin remove-cluster \
  --state-dir /secure/gpu-fault \
  --cluster-id gpu-prod-b \
  --confirm REMOVE_GPU_CLUSTER
```

该命令按状态机完成目标GPU集群的数据源停止、队列drain和节点systemd卸载。
join/remove使用同一站点事务锁。独占Route53 VPC关联的解除会保存ChangeInfo，等待
`INSYNC`并确认hosted zone中关联实际消失；若其他剩余GPU集群仍使用同一VPC则保留关联。
Agent/Executor停止后先异步请求namespace删除，再并行执行CPU registry/key清理及
IAM/网络依赖波次清理，最后统一等待namespace消失，并行验证目标缺失、registry、
EKS/HyperPod保留和剩余站点健康。CPU控制面、其他GPU集群及目标GPU EKS/HyperPod均保留。

可以移除最后一个 GPU 集群；CPU 控制面会以显式空 registry `[]` 继续运行，方便以后
重新接入。Runtime Profile 注册锚点是稳定标识，不因当前 GPU 集合为空而重写。

状态和证据位于 `site.yaml` 同目录的
`remove-cluster/<cluster-id>/`。失败后以完全相同参数重跑，不要删除该目录。

  不设为无限是为了工作流终会闭合。收紧它即可缩短等待；不得低于通用步骤上限。

### 6.1 cluster token 重叠窗口轮换

registry 里每个 GPU 集群可以同时声明当前 token 和一个**退役中**的 token。运行时权威
registry 是 Aurora revision，因此生产轮换通过
`POST /v1/regional/registry/revisions` 发布，注册项直接携带摘要：

```json
{
  "cluster_id": "gpu-usw2-a",
  "token_sha256": "<新 token 的 sha256>",
  "retiring_token_sha256": "<旧 token 的 sha256>",
  "token_rotation_expires_at": "2026-09-04T02:00:00Z"
}
```

bootstrap/灾备用的 `GPU_FAULT_REGIONAL_CLUSTERS_JSON` 只在尚无 durable revision 时生效，
它额外接受明文 `token` 和 `retiring_token`，由控制面自行取摘要，管理员不需要手工算。

摘要在发布 revision 前用文件计算，不要把 token 写进命令行或 shell 历史：

```bash
umask 077
python3 -c 'import hashlib,pathlib,sys; print(hashlib.sha256(pathlib.Path(sys.argv[1]).read_text().strip().encode()).hexdigest())' \
  "${SECURE_DIR}/cluster-token.new"
```

`token_sha256` 是新凭据，立刻生效；`retiring_token_sha256` 是旧凭据，只在
`token_rotation_expires_at` 之前继续被接受。两者必须同时出现或同时缺失，摘要必须不同，
期限必须带时区且相对 `updated_at` 不超过
`gpu_fault.regional.MAX_TOKEN_ROTATION_WINDOW`（7 天）。窗口过期后仍然只接受
`token_sha256`，因此忘记收尾不会让已经切换的 Executor 掉线，只会让还没切换的集群
fail closed。

执行顺序（不需要停止故障处置）：

1. 生成新 token（至少 32 字符），先只改 CPU 控制面 registry：`token_sha256` 换成新摘要，
   `retiring_token_sha256` 填旧摘要，`token_rotation_expires_at` 设为窗口结束时间；发布
   registry revision 并等待返回的 `RegionalRegistryStatus` 中
   `missing_member_ids` 为空。此时新旧 token 都能通过鉴权。
2. 按 REG-9 更新目标 GPU 集群 Secret 和节点 systemd，滚动 Executor 与 Agent。
3. 观察控制面日志中的
   `regional cluster <id> authenticated with the retiring token`：该行消失即表示没有
   调用方再持有旧 token。`GET /v1/regional/clusters` 的
   `retiring_token_sha256_present` 和 `token_rotation_expires_at` 用于确认窗口状态和剩余
   时间（两个摘要本身始终脱敏）。
4. 确认无该日志后，删除 `retiring_token_sha256` 与 `token_rotation_expires_at` 再发布一次
   revision，结束轮换。窗口内未完成第 2 步时不要直接靠期限自然过期收尾，应延长窗口
   （不超过 7 天）或回滚 registry。

窗口是「被撤销的凭据仍然开门」的时间，因此按分钟或小时设置，不要按天。轮换过程中
不修改 execution token，也不把任一 cluster token 下发到其他 GPU 集群。真机验收见
`GF-REGIONAL-AUTH-016`。

## 7. 按症状排障

| 症状 | 首查项 | 详细参考 |
|---|---|---|
| CPU Pod CrashLoopBackOff | registry、Aurora DSN、启动守卫、配置重复 | REG-14.1 |
| remote command 一直 PENDING | Executor claim、token、CA、cluster ID、owner、protocol | REG-14.2 |
| command 长期 LEASED | Executor Pod、lease renewal、结果回传 | REG-14.3 |
| step FAILED 原因不清 | `status_source` 和 executor traceback | REG-14.4 |
| 全部 Agent 非 ACTIVE | 节点 token、systemd、artifact/config/profile pin | REG-14.5 |
| operator API 返回 403 | execution token 与 cluster token 是否混用 | REG-14.6 |
| HyperPod outcome unknown | CloudTrail、节点实际状态、幂等提交记录 | REG-14.7 |
| Profile同版本内容漂移 | 发布新的profile version，不得覆盖原版本 | REG-8.1.3 |
| 升级后Agent未收敛 | 保持compatible窗口，检查Reconciler/Installer，不得强制finalize | REG-8.1.4 |
| Executor verifier失败 | IRSA、token、CA、owner、artifact和protocol | REG-14 |
| SNS确认邮件重复到达 | 同Topic是否有重复confirmed/pending、bootstrap pending checkpoint | REG-7 |
| StaleAttemptObservation | 训练Pod、Completion Watcher、Observation投递/outbox | REG-14 |

排障顺序固定为：

```text
release/module digest
  -> 身份与 TLS
  -> queue/lease
  -> Executor owner 与 protocol
  -> Node Agent/Collector
  -> provider 实际状态
```

本节按管理员观察到的症状进入。若入口是一条 AMP 告警，直接按告警名进入 §8 的分诊卡，
不要先在本表反查症状。

## 8. 告警处置索引

本节是 `deploy/observability/amp-rules.yaml` 每条告警的收件人入口。每条告警的
`annotations.runbook_url` 指向本节同名小节，`scripts/verify-regional-alerting.py`
校验双向一致：告警缺 `runbook_url`、`runbook_url` 与告警名不符、指向的小节不存在、
或本节有小节却没有告警指向它，都会让验收失败。

小节标题直接用告警名而不是 `8.1` 编号，因为 `runbook_url` 的锚点必须能从告警名机械
推导（小写、去掉非字母数字），编号会在插入告警时漂移。

本节是三行分诊卡，不是 §2 的七项 runbook：每条只给「含义 / 首查 / 边界」，需要执行
动作时跳到卡片里引用的正式 runbook。任何告警都不得通过上调阈值、删除 Store 记录或
静音规则来消除。

### GpuFaultCollectorSilent

- **含义**：某 GPU 节点的某个 collector channel 超过静默阈值没有成功投递批次；该节点
  的故障信号此刻不可信，策略对它是盲的。
- **首查**：节点 systemd 服务状态、Node Agent TLS 与私有 CA 信任链、cluster token、
  collector outbox 积压、最后一次成功批次时间戳。「有没有投递、多久一次」看
  `GET /v1/collector-status/{cluster_id}`：`collector_status` 在每个被接受的批次上更新，
  而 raw evidence 只在批次带 finding、采集错误或非 `health-summary` 原因时才写——健康
  节点的 `GPU_METRICS` 证据为 0 条是设计如此，不是采集器死了；「采集器看到了什么」才看
  evidence。
- **边界**：不得用 `curl -k` 验证连通性，不得上调静默阈值消警。修复入口 REG-6、
  REG-14.5。

### GpuFaultCollectorCollectionErrors

- **含义**：某 collector channel 上有节点「在按时投递、但投递的内容是失败」——
  `last_error_at` 不早于 `last_success_at`。它和 `GpuFaultCollectorSilent` 是两种
  状态：这类节点连通性正常、批次不迟到，所以在最后一次成功老化到静默阈值之前
  （node-logs 是一刻钟）静默告警看不见它，而节点其实已经在丢数据。
- **首查**：`GET /v1/collector-status/{cluster_id}` 读该 channel 的 `errors` 字段，
  它是节点自己写的原因（例如 journalctl 退出码、训练日志轮转、放弃的时间窗）；再看
  节点上 collector 的 journal。
- **边界**：这条告警自愈的唯一方式是节点真的成功投递一次——不要改阈值、不要删
  `collector_status` 记录。修复入口 REG-6、REG-14.5。

### GpuFaultCollectorMetricsSnapshotStale

- **含义**：`/metrics` 里的 collector 静默快照超过 120 秒没有刷新，说明
  `GpuFaultCollectorSilent` 本身已经失去数据来源。
- **首查**：抓取目标是否指向 ingress 副本而不是 worker；ingress 到共享 Store 的
  连通性和 Aurora 凭据刷新 CronJob。
- **边界**：在快照恢复前不要把 `GpuFaultCollectorSilent` 的静默判为「已恢复」。
  详见 REG-14.1。

### GpuFaultTelemetryRemoteWriteFailing

- **含义**：ADOT 到 AMP 的 remote_write 在丢点。超过 120s 重试窗口还没成功的批次会被
  直接丢弃且不再重发，所以 AMP 里的数据是有洞的：本节其余全部告警都在这些洞上求值，
  此时「图很干净」不等于「机群没事」。
- **首查**：`kubectl -n gpu-fault-system logs deploy/gpu-fault-adot` 里的
  `Exporting failed. Dropping data.` 及其 `error`；sigv4 role 与 AMP workspace 的
  写入限流。指标自带 `error_type` / `error_permanent` 两个标签，按它们拆开看能区分
  被拒（权限/限流）和暂时性失败。
- **边界**：计数器停止上涨不代表已恢复——collector 重启同样会让它归零。要用
  `otelcol_exporter_sent_metric_points` 恢复上涨来确认。不得靠放宽
  `max_elapsed_time` 消警：那只会把丢点换成 OOMKill（容器上限 256Mi）。
- **注意**：这些 `otelcol_*` 指标名没有 `_total` 后缀，是从固定版本镜像
  （aws-otel-collector v0.49.0）的 `:8889` 实测得到的，与上游文档里带后缀的写法不同。
  改镜像版本时必须重新实测，否则告警会静默失效。

### GpuFaultTelemetryRemoteWriteQueueSaturated

- **含义**：ADOT 的重试队列已用掉 80% 以上，写 AMP 的速度跟不上抓取速度，下一波积压
  会被丢弃而不是延迟送达。这是 `GpuFaultTelemetryRemoteWriteFailing` 之前唯一的预警。
- **首查**：`otelcol_exporter_queue_size` / `otelcol_exporter_queue_capacity` 的走势；
  AMP workspace 的 ingestion 限流；控制面副本数是否刚扩容导致时间线数量上涨。
- **边界**：不得靠加大 `sending_queue` 消警——容器上限 256Mi、`GOMEMLIMIT` 220MiB，
  队列换来的是 OOMKill。

### GpuFaultAdotSelfMetricsMissing

- **含义**：ADOT 自身的 telemetry（`up{job="gpu-fault-adot-self"}`）在 AMP 里缺失。
  要么 collector 没在跑，要么 remote_write 完全失败——后一种情况下
  `GpuFaultTelemetryRemoteWriteFailing` 无法触发，因为它的计数器走的是同一条通路。
- **首查**：先和 `GpuFaultControlPlaneMetricsMissing` 对比。两条同时在响：collector
  或写入通路整体挂了，查 Pod 状态与 export 错误日志。只有这一条在响：自身 telemetry
  reader（`service.telemetry` 绑在 127.0.0.1:8889）或 `gpu-fault-adot-self` 的 keep
  过滤被改坏了。
- **边界**：这条告警存在时不得判定「无故障」，理由同
  `GpuFaultControlPlaneMetricsMissing`。

### GpuFaultControlPlaneMetricsMissing

- **含义**：`up{job="gpu-fault-control-plane"}` 缺失，整个 CPU 控制面在监控上不可见，
  本文件其余全部告警同时失效。
- **首查**：ingress Pod 状态与启动守卫日志、Service/target 发现、抓取配置里的
  namespace 和端口。
- **边界**：这条告警存在时不得判定「无故障」。详见 REG-14.1。

### GpuFaultProcessorQueueDepthHigh

- **含义**：处理器全局队列超过容量 70%，还没有拒收，但排队时延已经在增长。
- **首查**：control-worker 副本数与 lane 占用、Aurora 延迟、是否有单集群 fault 风暴
  （对比 `GpuFaultProcessorClusterBacklogHigh`）。
- **边界**：扩容走 [管理员容量配置](管理员容量配置.md) 的 `gpu-fault-admin config`，
  不下调告警阈值，也不打开 queue bypass。

### GpuFaultProcessorQueueDepthCritical

- **含义**：队列超过容量 90%，距离 admission 拒收只剩一步。
- **首查**：同 `GpuFaultProcessorQueueDepthHigh`，并确认 worker 是否在 lane 上互相
  阻塞（`gpu_fault_processor_lane_wait_seconds_max`）。
- **边界**：这是维护窗口外允许扩 worker 副本的少数情况之一，但仍需变更单和回滚方案。

### GpuFaultProcessorOldestRequestDelayed

- **含义**：最老的排队请求已经等待超过 30 秒。队列深度可能正常——这条抓的是长尾饥饿，
  通常是某个 lane 被单个慢请求占住。
- **首查**：`gpu_fault_processor_phase_oldest_seconds` 定位阶段、
  `gpu_fault_processor_claimed_not_started` 是否非零、Aurora 连接池等待。
- **边界**：不要靠重启 worker 清队列；先取到卡住的阶段和请求 ID。

### GpuFaultProcessorClusterBacklogHigh

- **含义**：单个 GPU 集群的队列超过其配额 70%，说明积压集中在一个集群而不是全局过载。
- **首查**：该集群的 collector 是否在重放、Executor 是否在 claim、是否有节点级
  fault 风暴。
- **边界**：单集群配额是隔离手段，不得为消警而扩大该集群配额挤占其他集群。

### GpuFaultWorkflowMetricScanTruncated

- **含义**：workflow 表已超出 `/metrics` 的扫描预算，
  `gpu_fault_workflow_step_total`、`gpu_fault_workflow_duration_seconds`、
  `gpu_fault_closed_loop_milestone_seconds` 三族只覆盖最新的一段，不再是全量普查。
  `gpu_fault_workflow_total` 仍是数据库侧聚合，不受影响。
- **首查**：`gpu_fault_workflow_scan_size` 与 `gpu_fault_workflow_scan_limit` 的差距、
  workflow 保留策略是否停止清理、是否有 workflow 风暴在制造新记录。
- **边界**：先确认是保留策略失效还是真实增长。仅调大
  `GPU_FAULT_METRICS_WORKFLOW_SCAN_LIMIT` 会把成本转给 Aurora 和每次抓取，
  不解决表不再收敛的问题。

### GpuFaultAttemptObservationMetricScanTruncated

- **含义**：attempt observation 表已超出 `/metrics` 的扫描预算，
  `gpu_fault_ambiguous_attempt_ownership_current` 与
  `gpu_fault_stale_attempt_observations` 只覆盖最新的一段。此时独占所有权不变量是
  在切片上求值的，较老观测之间的所有权冲突不会被报出来，
  `GpuFaultExclusiveNodeOwnershipInvariantViolation` 可能因此静默。
- **首查**：`gpu_fault_attempt_observation_scan_size` 与
  `gpu_fault_attempt_observation_scan_limit` 的差距、observation 保留清理
  （`GPU_FAULT_ATTEMPT_OBSERVATION_MAX_AGE_SECONDS`，默认 7 天）是否还在执行、
  是否有 attempt 风暴或 Completion Watcher 停止终态化导致行数不收敛。
- **边界**：切片保留的是最新的行，而所有权与过期两族的信号都在最近端，所以这是
  warning 而不是不变量失效。仅调大 `GPU_FAULT_METRICS_OBSERVATION_SCAN_LIMIT`
  会把成本转给 Aurora 和每次抓取；先确认表为什么不再收敛。

### GpuFaultProcessorAdmissionRejected

- **含义**：已经在拒收请求。被拒的 fault 事件依赖客户端重投，存在真实的检测丢失窗口。
- **首查**：拒收按路径和集群的分布
  （`gpu_fault_processor_admission_rejections_by_path_total`、`_by_cluster_total`）、
  telemetry spool 是否同时在拒收。
- **边界**：critical。先恢复容量再回溯这段窗口内是否有未处理的 XID/SXID。

### GpuFaultStoreIoSaturated

- **含义**：Store I/O lane 在用容量超过 90%，处理器随时可能开始拒 Store 操作。
- **首查**：Aurora CPU 与连接池等待、是否有全表扫描型请求、
  `gpu_fault_store_io_admission_wait_seconds_max`。
- **边界**：扩 lane 宽度前先确认不是单一慢查询；把 lane 调宽只会把压力转给 Aurora。

### GpuFaultStoreIoRejected

- **含义**：已经在拒 Store I/O。此时写入路径不完整，编排状态可能落后于真实集群状态。
- **首查**：同 `GpuFaultStoreIoSaturated`；并检查是否有 workflow 因此转入重试或
  fail-closed。
- **边界**：critical。恢复后必须核对该窗口内的 workflow 与节点实际状态是否一致。

### GpuFaultProcessorP95Slow

- **含义**：请求处理 p95 超过 5 秒并持续 10 分钟，是容量类告警里最早的领先指标。
- **首查**：event loop lag、Aurora 连接池等待、是否刚做过发布（对比 release digest）。
- **边界**：单独出现时属于 warning；与队列或 Store 告警同时出现时按后者的优先级处置。

### GpuFaultProcessorExpiredLeasesReclaimed

- **含义**：有排队请求被 worker 领取（LEASED）后超过 lease 仍没完成，被周期回收任务退回
  PENDING。请求没有丢，但至少多等了一个 lease；每一次非零增长都对应一个中途死掉或卡住的
  处理器 worker。队列深度类告警看不到它——回收前后深度不变。
- **读的是哪个指标**：`gpu_fault_processor_expired_leases_reclaimed_total`（每进程计数，
  规则按 `control_plane_cluster, region` 求和后取 10 分钟增量）。
- **首查**：同一窗口内 control-worker Pod 是否有重启（`kubectl -n <ns> get pod` 的
  RESTARTS 列与发布时间对照）；`gpu_fault_processor_phase_oldest_seconds` 是否有某个阶段
  长期偏高；`gpu_fault_periodic_job_errors_total{job=…}` 回收任务本身有没有报错。
  滚动发布期间出现一两次是预期的；发布窗口之外持续增长才是 worker 在挂。
- **边界**：不得为消警调长 `GPU_FAULT_PROCESSOR_LEASE_SECONDS`（那只是让卡住的请求多等
  一会儿）；也不要手工把 LEASED 行改回 PENDING，回收任务就是做这件事的。

### GpuFaultProcessorCounterDrift

- **含义**：处理器队列的按集群深度读的是分片计数器而不是 `COUNT(*)`，两者连续 5 分钟不一致。
  此时 `gpu_fault_processor_cluster_queue_depth`、按集群配额的 admission 判定都在用一个错
  的数。周期任务每 `GPU_FAULT_PROCESSOR_COUNTER_DRIFT_SCAN_SECONDS` 对比一次，单次采样可能
  正好跨在一次批量提交上，所以规则取 5 分钟窗口内的最小值。
- **读的是哪个指标**：`gpu_fault_processor_counter_drift_abs`（|期望总数 − 计数器总数|）
  与 `gpu_fault_processor_counter_mismatched_clusters`（有多少个集群的分片计数器不等于真实
  行数）；两者任一持续非零都算。
- **首查**：漂移量是稳定常数还是在增长——常数通常是一次事务只写了表没写计数器，增长说明
  写路径还在持续漂；对照 `GpuFaultProcessorClusterBacklogHigh` 是否同时在误报或漏报；
  `gpu_fault_periodic_job_errors_total` 看对比任务有没有失败。
- **边界**：计数器由 backfill 路径从队列表重建，不得手工改计数器行；也不要靠重启 worker
  消警，重启不会重建计数器。

### GpuFaultTelemetrySpoolListenerDown

- **含义**：telemetry spool 消费者的 `LISTEN/NOTIFY` 断开，退化为轮询。功能仍然正确，
  时延变大。
- **首查**：Aurora 连接是否被中间层掐断、spool worker Pod 重启历史、
  `gpu_fault_telemetry_spool_fallback_polls_total` 的增速。
- **边界**：不要靠禁用通知来消警；轮询是降级路径，不是目标状态。

### GpuFaultTelemetrySpoolDataLoss

- **含义**：spool 丢弃了常规样本。丢弃只作用于常规遥测，不作用于 fault 事件，但
  主机与网络趋势会出现空洞。
- **首查**：`gpu_fault_telemetry_spool_depth` 与 `_bytes` 是否触到上限、丢弃前是否
  先出现 `GpuFaultTelemetrySpoolDrainDelayed`。
- **边界**：critical。丢弃窗口内的主机健康结论不可用于事后判定。

### GpuFaultTelemetrySpoolAdmissionRejected

- **含义**：spool 在入口拒收常规样本，比 `DataLoss` 更早一环。
- **首查**：入口批量参数、in-flight 字节上限、是否有单集群刷量。
- **边界**：同上，先恢复容量再评估遥测空洞范围。

### GpuFaultTelemetrySpoolReplayError

- **含义**：spool 回放失败。已落盘的样本没能进入处理路径。
- **首查**：spool worker 日志里的异常类型、`_abandoned_total` 与 `_superseded_total`
  的比例、Store schema 版本是否与 wheel 匹配。
- **边界**：critical。回放失败可能是版本漂移，先做 REG-10A 制品一致性校验。

### GpuFaultTelemetrySpoolDrainDelayed

- **含义**：spool 中最老的样本超过 60 秒未排空，是丢弃与拒收的领先指标。
- **首查**：spool worker 副本数与 lane 占用、Aurora 写入延迟。
- **边界**：warning，但持续存在时按容量问题处置，不要等到 `DataLoss` 才动作。

### GpuFaultRemoteCommandUnclaimed

- **含义**：某个 PENDING remote command 超过 600 秒没有任何 Executor claim。没有
  unclaimed 超时也没有死信状态，所以这条告警是恢复彻底停住的唯一信号。
- **首查**：该步骤的 runtime profile owner 是否被目标集群 Executor 实际构造出的
  adapter 广告、Executor 到控制面的 TLS、cluster ID 与 owner 是否匹配、protocol
  version 是否在 compatible 窗口内。
- **边界**：critical。不得手工把命令改成终态；按 REG-14.2 逐项排查。

### GpuFaultRemoteCommandExecutorInternalError

- **含义**：Executor 因自身缺陷失败一条命令，而不是拒绝一个不安全动作。
- **首查**：Executor Pod 日志里的 traceback；重试前先读栈。告警用的是保留期内最新的
  错误时间戳，所以终态记录清理不会被误读成计数器归零。
- **边界**：critical。这是代码缺陷通道，修复走发布流程，不通过重试掩盖。详见
  REG-14.4。

### GpuFaultUnknownProductFamily

- **含义**：出现了没有映射到 NVIDIA Catalog family 的 GPU 产品；该产品上的 XID
  自动恢复是 fail-closed 的。
- **首查**：告警的 `product` 标签、当前 pinned catalog 版本、节点 instance type。
- **边界**：把产品前缀加入 pinned catalog 的 `spec.catalog.productFamilies` 并走正式
  发布，不得在线放宽策略或按未知产品猜测 family。

### GpuFaultExclusiveNodeOwnershipInvariantViolation

- **含义**：同一个 GPU 节点被多个「新鲜」active attempt 同时声明所有权，节点变更已经
  fail-closed。过期观测不计入所有权，另有独立告警。
- **首查**：告警标签里的 `cluster_id` 与 `gpu_node`、这些 attempt 对应的训练 Pod 是否
  都真实存在、Completion Watcher 的投递是否重复。
- **边界**：critical。不得手工拼造或删除 attempt/allocation 来解除歧义；处置必须引用
  真实 workload observation。见 §9。

### GpuFaultStaleAttemptObservation

- **含义**：该节点上有超过 120 秒未刷新的 `PENDING/RUNNING` attempt 观测。值是 attempt
  数量，不是邮件合并的告警实例数。
- **首查**：训练 Pod 是否仍存在、Completion Watcher 的 Ready 与日志、
  `gpu-fault-completion-watcher-outbox` 的内容。
- **边界**：等待正式的 `STOPPED/FAILED/SUCCEEDED` observation 覆盖；不得直接删 Store
  记录来消警。

### GpuFaultFleetRolloutFenceStuck

- **含义**：该集群存在一条非终态的 fleet deployment，已经超过 2 小时。fleet 围栏会把该
  集群上**所有**破坏性 remediation（GPU reset、reboot、隔离恢复）挡在它后面，所以这条
  告警的实际含义是「这个集群的自动恢复当前是停摆的」，而不是「一次升级慢了」。
- **为什么用时长而不是条数**：一次正常的区域 roll 本来就会让 deployment 处于非终态，这正
  是围栏存在的理由。四节点 p5en 观测到的最长 roll 约 7 分钟，2 小时远在其外。
- **读的是哪个指标**：`gpu_fault_fleet_rollout_fence_age_seconds{cluster_id}` 是最老那条
  非终态 deployment 的年龄。同集群的
  `gpu_fault_fleet_rollout_never_started{cluster_id}` 是分诊位：
  - **非零** —— 这条记录一个 wave 都没起过（`DeploymentStatus.PLANNED` 是派生态，只有全部
    节点仍为 `PENDING` 时才成立）。说明创建它的那次发布在写完记录后就死了，没有任何东西
    在飞。2026-09-03 就是这一类，围栏锁了 36 小时。
  - **为零** —— rollout 真的卡在某个 wave 中间。先查该 wave 节点的 Agent lease、
    `gpu-fault-node-installer-reconciler` 日志，再决定 retry 还是 rollback。
- **首查**：`gpu-fault-admin status` **不报** fleet deployment，要看 `/metrics` 的上述两个
  指标，或在控制面 Pod 内读 `list_active_fleet_deployments(<cluster_id>)`。
- **边界**：不得删 Store 行，不得关闭围栏，也不得调大 2 小时阈值来消警。
  终态化只能走发布引擎：对被放弃的记录，下一次 `rollout-regional-release`
  的 `rollback-rollout-cleaned` 阶段会扫掉同 release 的残留，而新建 deployment 时
  `supersede_never_started_deployments` 会把同集群从未启动的旧记录置为终态。

### GpuFaultWorkflowLifetimeExceeded

- **含义**：一条恢复工作流从首次被领取起超过了生命周期上限（作业工作流
  `GPU_FAULT_JOB_WORKFLOW_MAX_LIFETIME_SECONDS`、单节点工作流
  `GPU_FAULT_NODE_WORKFLOW_MAX_LIFETIME_SECONDS`，默认都是 1 小时），控制面已把它写成 FAILED、
  取消在飞远程命令，incident 进入 ESCALATED；此后同节点/同作业的事件只记录到该 incident，
  不再自动修复，直到运维处置完、incident 关闭。
- **读的是哪个指标**：`gpu_fault_workflow_lifetime_exceeded_total`（执行器计数，按进程累计）。
- **首查**：`gpu-fault-admin status` 找 ESCALATED 的 incident；读该 workflow 最后一条 FAILED
  步骤记录里的 `workflow_lifetime_exceeded` 与被取消的远程命令；看它经历了哪几级升级
  （`branch_escalation_counts`）。
- **处置**：人工判断节点是否需要换机或送修；处理完把 incident 关闭，之后该节点的新事件才会
  重新触发自动修复。不要通过延长生命周期来"修好"这个告警。

### GpuFaultJobWorkflowNodeBusyTimeout

- **含义**：规则 A 触发。一个训练作业的节点正被别的修复工作流占用，作业只等
  `GPU_FAULT_JOB_WORKFLOW_NODE_BUSY_WAIT_SECONDS`（默认 4 分钟）这一个窗口；修复在窗口内完成
  作业就继续（排队的作业工作流被派发，`after_incident` 重启把作业重启）。窗口过了作业不再重启：
  还在跑的作业以 STOP_WORKLOADS（带控制面发起者标记 `termination_initiator_incident_id`）停掉，
  已经死掉的作业其重启计划失败；工作流 FAILED、incident ESCALATED。系统自己停掉的作业不会被
  重启——完成服务看到发起者标记只记 NO_ACTION。占用节点的那条修复工作流不受影响。
  派发器（作业工作流未开始）与执行器（`RESTART_WORKLOAD` 的 `requires_incident_state` 前提已在等）
  读同一个变量，后者的步骤记录以 `reason=NODE_REMEDIATION_TIMEOUT` 收尾。
- **读的是哪个指标**：`gpu_fault_workflow_dispatch_node_busy_timeouts_total`（派发器放弃）；执行器侧
  的放弃是 STEP_ATTEMPT 事件的 `NODE_REMEDIATION_TIMEOUT` 码。
- **首查**：读失败工作流的 `terminal_failure_reason`，里面列出哪些节点被哪条工作流占着；
  确认那条节点工作流是否仍在正常推进（没有的话它自己会触发生命周期告警）。
- **处置**：节点修复完成后作业方重新提交即可——控制面不会替它重启；若作业反复落到正在修复的
  节点上，检查调度器为什么把作业放到了被 cordon 的节点。

### GpuFaultProcessorRetryHorizonFailures

- **含义**：处理器队列里某条请求的执行或完成持续失败，被释放重试的累计时间超过了
  `GPU_FAULT_PROCESSOR_RETRYABLE_RESPONSE_MAX_AGE_SECONDS`（默认 300 秒），控制面把它以
  503 完成、结束流转，车道因此解封。请求的业务副作用没有被确认。
- **读的是哪个指标**：`gpu_fault_processor_retry_horizon_failures_total`；配套看
  `gpu_fault_processor_completion_failure_releases_total`（每次带退避的失败释放）。
- **首查**：处理器日志里 `completed as failed past its retry horizon` 一行给出
  request_id、path、failure 与 retry_count；按 request_id 读完成体里的 JSON。
- **处置**：确定性失败通常是 handler 缺少参数、存储写入被拒或数据面返回 5xx；修复根因后
  由数据面重投同类事件，不要手工改队列行。

### GpuFaultRecoveryBlockedBacklog

- **含义**：`BLOCKED` 是 fail-closed 终态——证据、身份或 workload 状态不足以继续变更
  节点。单条属于正常安全行为；持续积压说明没有人在处置，每条都对应一个长期不回训练池
  的 GPU 节点。
- **读的是哪个指标**：`gpu_fault_workflow_blocked_unreconciled`，即「`BLOCKED` 且没有
  已验证 restore successor」的条数，与发布前置检查判定 workflow 是否阻塞发布用的是同一
  判据。它**不是** `gpu_fault_workflow_total{status="BLOCKED"}`：后者统计的是历史全表，
  `BLOCKED` 又是终态，所以那个数字只会因 `workflow-reconcile` 或归档而下降——同 incident
  的 successor 已经把节点放回训练池之后它仍然不降，据此告警会按 `repeat_interval` 一直
  重发。所以本告警静默的正确含义是「没有节点还被 BLOCKED 记录扣着」，不是「表里没有
  `BLOCKED` 行」。
- **首查**：逐条读 workflow 的 blocking reason 与 incident；区分「等管理员决策」
  （见 §9）和「等证据」两类。
- **边界**：不得通过改 Store 行或手工改 workflow JSON 清除 `BLOCKED`，也不得为了消警调
  大 remediation budget。已由同 incident 的成功 successor 收敛的历史记录只能走
  `gpu-fault-admin workflow-reconcile`，见 §10；该命令要求存在已验证 successor 且
  `restore_reconciliation_reasons` 为空，`--apply` 在不满足时直接报错，这是设计如此。

### GpuFaultClosedLoopSlow

- **含义**：最近 6 小时内达成 containment 里程碑的 workflow，平均检测到隔离耗时超过
  15 分钟。含义是这段时间里新的训练尝试仍在落到已知故障的节点上。
- **首查**：`gpu_fault_closed_loop_milestone_seconds_max{milestone="containment"}`
  定位最坏样本；对比容量类告警和 `GpuFaultRemoteCommandUnclaimed`，慢通常来自排队或
  claim 延迟而不是策略判定。
- **边界**：这条告警按窗口内均值计算。保留策略归档旧记录时分子会下降，此时告警会静默
  ——它可能漏报，不会误报，所以静默不等于时延达标。

### GpuFaultNotificationDeliveryFailing

- **含义**：业务通知投递失败。管理员决策请求（GPU 数量变化、spare 不足、机械检查结论）
  没有送达，闭环的人工半边静默停住。
- **首查**：SNS topic 订阅状态与是否有重复的 confirmed/pending（见 REG-7）、
  `gpu_fault_notification_outbox_depth`、失败通知对应的 workflow 是否在等决策。
- **边界**：critical。补投之前不要把等待决策的 workflow 判为「无进展故障」。

### GpuFaultPostgresPoolOversubscribed

- **含义**：某个控制面角色里"能同时握住一条池连接"的线程数（Store I/O 线程 + 处理器
  worker + 派发器 worker + 周期服务）超过了该进程的连接池上限，比值就是指标值。负载一上来，
  调用方在取连接处排队，先撞上的是请求截止时间而不是数据库本身。以前这只是启动时的一条
  WARNING，且 worker 角色少算了三类线程从未告警过。
- **读的是哪个指标**：`gpu_fault_postgres_pool_oversubscription_ratio`（按角色的 gauge），
  分解见 `gpu_fault_postgres_pool_demand_connections{consumer=}` 与
  `gpu_fault_postgres_pool_max_size`；LISTEN 连接不在池内，另见
  `gpu_fault_postgres_unpooled_connections`。
- **首查**：看哪一类 consumer 贡献最大；核对该角色的
  `GPU_FAULT_PROCESSOR_WORKERS`、`GPU_FAULT_WORKFLOW_DISPATCHER_WORKERS` 与池上限配置。
- **处置**：要么把池上限调到 ≥ 需求，要么减少该角色的线程数；两者都是配置变更，走发布。
  不要为了让告警消失去改指标的统计口径。

### GpuFaultBranchEscalationBudgetRefused

- **含义**：多节点作业修复中，某个节点分支要就地升级到下一级（reset → reboot → 暖备替换），
  但该动作的资源类（如 `NODE_LIFECYCLE_MUTATION`）在本集群的并发预算已满，控制面选择把该分支
  交给人工（分支耗尽、工作流最终 FAILED / ESCALATED），而不是越过并发上限。
- **读的是哪个指标**：`gpu_fault_workflow_branch_escalation_budget_refusals_total`（执行器计数）。
- **首查**：`gpu-fault-admin status` 找 ESCALATED 的 incident，读工作流 `exhausted_branch_ids`
  与最后一条失败记录里的"remediation budget cannot take the next rung"；核对
  `GPU_FAULT_REMEDIATION_MAX_ACTIVE_PER_RESOURCE_CLASS`（默认 2）与当时在飞的重启/替换数。
- **处置**：等在飞的重启/替换收口后，由人工决定该节点是重启、换机还是送修；若频繁出现且
  确认硬件容量允许，再评估调高该资源类的并发上限。

### GpuFaultWorkflowStepStalled

- **含义**：某个恢复动作（`operation` 标签给出是哪一个）等待的时间已经超过**该动作自己的**
  预期上限仍未出终态。此时故障节点仍被扣着、其训练任务仍被挂起，而所有组件都是健康的——这
  正是本告警存在的原因：在它之前，「step 卡住」与「step 正常等待」在监控上没有区别。
- **读的是哪个指标**：`gpu_fault_workflow_step_waiting_seconds{operation=…}` 减去
  `gpu_fault_workflow_step_waiting_warning_seconds{operation=…}`，前者是非终态 workflow 中
  仍处于 `WAITING` 的 step 的最大年龄，后者是该 operation 适用的阈值。年龄而不是条数：等待
  本身是正常的，条数区分不出「节点正在重启」和「节点永远不会回答」。
- **为什么阈值是一条指标而不是规则里的常数**：阈值按 operation 分档。`REPLACE_NODE` /
  `RESTART_NODE` 交给 HyperPod 托管恢复，等的是 provider，上限就是
  `GPU_FAULT_HYPERPOD_MANAGED_RECOVERY_TIMEOUT_SECONDS`（默认 1800 秒）；其余动作的上限是
  `GPU_FAULT_WORKFLOW_STEP_TIMEOUT_SECONDS`（默认 600 秒）。规则里写死一个数只可能对其中
  一档：写 600 秒就会在每一次**正常**的节点替换上误报，写 1800 秒就等于放弃了其余所有动作
  的告警。控制面把适用阈值按同样的标签导出，规则做减法，因此两个窗口任何一次调参都不会让
  这条规则过期。告警提前量由 `GPU_FAULT_WORKFLOW_STEP_TIMEOUT_SECONDS` 与
  `GPU_FAULT_WORKFLOW_STEP_WARNING_SECONDS` 的差值决定（默认 300 秒），并按同一提前量平移
  到分档更高的 operation 上，所以它总是在 step 还在等的时候就响，而不是等上限把这个 step
  判失败之后才响。
- **首查**：读该 step 的 `details`，重点看它在等的那个对象**是否已经给出了答案**。
  2026-09-05 的实例是：node agent 已经明确回答「热备上有别人的 GPU 进程」，但这个答案被
  映射成了 `WAITING`；同时该 step 的重试计数是从一条 key 永不推进的记录里读回来的，所以
  计数停在 1，`verify_max_attempts=60` 永远到不了。若 `details` 里的证据（PID、command
  记录、快照时间）明显早于当前时间，说明引擎在重放一条已经结束的记录。
- **边界**：不得为消警调大 `GPU_FAULT_WORKFLOW_STEP_TIMEOUT_SECONDS`、
  `GPU_FAULT_WORKFLOW_STEP_WARNING_SECONDS` 或
  `GPU_FAULT_HYPERPOD_MANAGED_RECOVERY_TIMEOUT_SECONDS`，也不得手工改 workflow 的
  `step_executions`。上限到点后 step 会带明确错误失败，走正常的补偿与失败处理路径，那是
  预期行为，不是需要抢在它之前干预的事故。托管恢复超时还会额外落一条通知（附 AWS Support
  case 草稿），那条通知是这类超时唯一可执行的产物；如果只看到 step 失败却没有通知，说明是
  通用超时抢在了观察器之前，属于配置缺陷而不是运行事故。

### GpuFaultWorkflowDeadlineNotEnforced

- **含义**：有非终态 workflow 已经超过自己的 `execution_deadline` 5 分钟以上。这条告警报
  的不是「某个恢复慢」，而是**兜底机制本身失效**：deadline 到了却既没有被租约持有者执行、
  也没有被 watchdog 收掉。
- **读的是哪个指标**：`gpu_fault_workflow_overdue_seconds`，非终态 workflow 中超期最多的
  那条的超期秒数。正常情况下它应当稳定为 0：deadline 到点后，下一次派发就会由持有租约的
  executor 把当前 step 判失败并终态化。
- **首查**：读该 workflow 的 `execution_owner_id` 与 `execution_lease_expires_at`。
  - 两者都在、lease 在未来 → executor 还在续租，但没有执行 deadline；查 control-worker
    日志里的 `workflow execution deadline exceeded` 行是否出现。
  - lease 已过期或 owner 为空 → 该由 watchdog 收；查
    `workflow is past its execution deadline but held by its executor` 这条 WARNING。
    2026-09-05 之前这里是一句静默的 `continue`，唯一症状就是 workflow 永远不结束。
- **边界**：**不得**手工修改 `execution_deadline`、不得删除 workflow 行、不得为了让这个
  数字归零而重启控制面 Pod（重启只会换一个 owner 继续续租）。真正的修复在代码里，运维侧
  只负责取证。

### GpuFaultRemediationBudgetStarved

- **含义**：有 workflow 已经等待 remediation budget 超过 30 分钟。budget 限制同时变更
  的节点数，短时等待是正确的过载保护，长时等待说明配额没有被释放。
- **首查**：`gpu_fault_remediation_budget_active_claims` 按 scope type 与配置上限对比；
  确认持有 claim 的 workflow 是否仍在推进、其执行 lease 是否已过期。
- **边界**：不得为消警直接调大 budget；先确认没有「claim 持有者已死但 lease 未过期」
  的情况。配额调整走 [管理员容量配置](管理员容量配置.md)。

### GpuFaultCompletionPendingTriageBacklog

- **含义**：完成路径把每个 attempt 结局记为一条决策；`PENDING_TRIAGE` 是「到达时分不清、
  先停一下再看」的有界状态，期限是 `GPU_FAULT_PENDING_TRIAGE_DEADLINE_SECONDS`（默认
  900 秒），到期由周期任务收口。规则 `for` 是期限的两倍：任务已经有整整一个期限加一次扫描
  的机会却没收掉，剩下的是分诊在停摆，不是某次 attempt 慢。
- **读的是哪个指标**：`gpu_fault_completion_decisions{status="PENDING_TRIAGE"}`（按
  `DecisionStatus` 的 gauge）；配套看 `gpu_fault_completion_pending_triage_reconciled_total`
  是否还在动。
- **首查**：`gpu_fault_completion_pending_triage_reconciled_total` 停了 → 看
  `gpu_fault_periodic_job_errors_total` 与 control-worker 日志里该周期任务的异常栈；还在动
  但 gauge 不降 → 新决策进得比收得快，看是不是某个集群的 Completion Watcher 在批量重投。
  单条决策用 `GET /v1/attempts/{cluster_id}/{attempt_id}/decision` 读。
- **边界**：不得手工把决策改成 `NO_ACTION`；不得为消警调大 deadline——调大只会把同样的
  停摆推迟到告警之外。

### GpuFaultCompletionEventsWithoutDecision

- **含义**：同一不变量的另一半——有完成事件但没有任何决策行。事件与决策应在同一事务落库，
  只有事件说明它被记下来又没被判定，下游再也不会看它一眼；一次失败的 attempt 可能就此没有
  任何恢复计划。事件可以比决策早一次 scrape，不可能早半小时。
- **读的是哪个指标**：`gpu_fault_completion_events_without_decision`。
- **首查**：control-worker / ingress 日志里完成事件写入之后的异常（决策写失败会留栈）；
  把这些事件对回各自的 attempt，确认对应节点是否已经由别的工作流处理。
- **边界**：不得删除事件行；重放事件之前先做完上一步对账，否则会给已恢复的节点再开一条
  工作流。

### GpuFaultIncidentsAwaitingOperator

- **含义**：`ESCALATED` 是控制面把决定交给人之后 incident 停放的状态——并发预算拒绝了下一
  级动作、工作流寿命耗尽、需要机械检查。它是设计内的正确终态，**不会**被自动收口，所以有
  数量本身不是故障；但一条一天没人动的升级，就是一个大家都忘了的 GPU 节点（或一个作业）。
  这条是「有人工队列存在」的提醒，warning，24 小时。
- **读的是哪个指标**：`gpu_fault_incidents_by_state{state="ESCALATED"}`（按
  `IncidentState` 的 gauge）。
- **首查**：`gpu-fault-admin status` 找出 ESCALATED 的 incident，逐条
  `GET /v1/incidents/{incident_id}` 读升级原因；按 §9 的业务处置分流（GPU 数量变化审批、
  备机预留、送修）。若 incident 已经由人处理完但记录仍是 ESCALATED，属于处置流程没有收尾，
  不是监控误报。
- **边界**：只有操作员动作能让 incident 离开这个状态，保留策略不会；不得为消警改 Store
  行或静音规则——静音等于承认这个队列不需要有人看。

### GpuFaultWorkflowPendingAge

- **含义**：最老的 `PENDING` 工作流已经等了超过 30 分钟没有任何派发器领取。派发器以秒级
  tick 轮询，30 分钟不是排队时延，而是「没有派发器会拿它」：前驱工作流没有终态化、退役世代
  在等操作员、或派发器自己卡住了。派发器每次 tick 都观察这个年龄并在超阈值时告警一次
  （`gpu_fault_workflow_pending_age_warnings_total`），本规则是同一事实在 AMP 里的版本。
- **读的是哪个指标**：`gpu_fault_workflow_pending_age_seconds_max`；配套
  `gpu_fault_workflow_retired_generation_awaiting_operator`（被退役但还需要人关闭的世代数）
  与 `gpu_fault_workflow_dispatch_preemption_pending_seen_total`。
- **首查**：先只读——`scripts/e2e/regional/audit_stuck_workflow_baseline.py` 跑三条只读
  判据；`gpu-fault-admin workflow-reconcile --state-dir /secure/gpu-fault --plan --mode
  retired-generation` 看是否有退役世代在等关闭（见 §10.1）；`GET /v1/workflows/{request_id}`
  读该工作流的 `predecessor_workflow_id`，再读前驱是否已终态。前驱非终态且它自己也没人领 →
  按 `GpuFaultWorkflowDeadlineNotEnforced` 处理前驱；一切正常但仍无人领 → 看 control-worker
  的派发器日志与 `gpu_fault_periodic_lease_errors_total`。
- **边界**：不得删除或手工改 PENDING 工作流行，不得手工把前驱改成终态；退役世代只能走
  §10.1 的 `workflow-reconcile --mode retired-generation --apply`。

## 10. 数据与审计维护

生产优先使用 archive-first 自动保留：

```text
GPU_FAULT_CONTROL_RECORD_RETENTION_DAYS
GPU_FAULT_CONTROL_RECORD_ARCHIVE_S3_URI
GPU_FAULT_CONTROL_RECORD_ARCHIVE_INTERVAL_SECONDS
```

已经由同一incident的成功恢复successor完成验证和`RESTORE_SCHEDULING`、但历史
predecessor仍为`BLOCKED`时，不得直接删除数据库行或手工改workflow JSON。先生成计划：

```bash
gpu-fault-admin workflow-reconcile \
  --state-dir /secure/gpu-fault \
  --plan
```

不带`--workflow-id`时计划扫描全部`BLOCKED`记录（按`updated_at`从旧到新，最多扫
10,000条；超出不拒绝，`plan.json`的`discovery.scan_truncated`为true）。积压成批时按批
复核，三个选择器可以组合：`--incident-id <id>`只看一个incident（可重复）、
`--blocked-kind {SAFETY_SETTLED,NEEDS_OPERATOR,INTERNAL_ERROR}`只看一类BLOCKED（可重
复）、`--max-items N`限定本批条数——`discovery.remaining`告诉你这批之后还剩多少。

计划把两种形状的记录标为eligible。**已验证恢复**（`terminalization`为
`verified-restore`）：incident为`RECOVERED`，当前successor为同incident的`SUCCEEDED`
workflow并完成`RESTORE_SCHEDULING`。**从未改动节点**（`terminalization`为
`never-changed`，`never_changed_a_node`为true）：该记录没有完成过任何改动节点的操作——
cordon/quarantine这类只改调度许可的隔离不算，会单列在`completed_containment_operations`
里——于是没有、也不需要restore successor；它要求incident处于`ESCALATED`或`RECOVERED`，
即没有人还在等这条workflow动手。两种形状都还要求：fencing与execution epoch未漂移；执行
lease已失效且无owner；没有`PENDING/LEASED/WAITING` remote command或未知provider动作；
source plan存在、关联正确且为`FAILED`；GPU节点已无本方案quarantine taint、隔离
annotation和cordon。审核私有`workflow-reconcile/plan.json`后执行：

```bash
gpu-fault-admin workflow-reconcile \
  --state-dir /secure/gpu-fault \
  --apply \
  --plan-sha256 <reviewed-sha256> \
  --reference CHG-12345
```

apply会重新读取数据库和GPU节点状态，计划漂移即停止，并指名是哪条记录的哪个字段变了
（`workflow-...: fencing_token 7 -> 8`）；`workflow_updated_at`不参与摘要，所以一次只
改时间戳的写入不会作废已审计划。成功后把旧predecessor转为`SUPERSEDED`：已验证恢复的
形状在Store事务里同时写workflow、incident和source plan并保持incident指向恢复
successor；从未改动节点的形状没有successor可指，只写workflow（`preemption_reason`）与
source plan（`reconciliation_reference`），不碰incident。每条记录单独写入：结果里的
`applied_workflow_ids`/`failed_workflow_ids`/`failures`说明哪些成了、哪些没成和原因，有
失败时退出码为1，已写入的不回滚——直接重新`--plan`，已关闭的记录不再出现在发现结果里。
该命令删除记录数恒为0；后续仍由现有S3 archive-first保留策略归档整个incident bundle。

### 10.1 关闭退役世代（retired generation）

另一种形态：incident已经推进到更高fencing世代并指向另一个workflow，旧workflow却仍是
`RUNNING`/`PENDING`/`SAFETY_PENDING`，握着owner、lease和`remediation_budget_claims`。症状是
某个incident的恢复迟迟不动，而`gpu-fault-admin status`显示一个世代落后的workflow在被反复
派发——因为dispatcher每incident只准入一个workflow，这条旧记录同时饿死了真正该跑的
successor。它也会让发布卡住：`workflow_safety` preflight拒绝跨过退役世代。

正常情况下不需要这条命令：dispatcher每轮会自己取消其remote command并把记录转为
`SUPERSEDED`。需要手工处置的只有一种场合——**携带该扫除逻辑的release还没部署**，而正是这
条记录在阻止它部署。此时先生成计划：

```bash
gpu-fault-admin workflow-reconcile \
  --state-dir /secure/gpu-fault \
  --mode retired-generation \
  --plan \
  --workflow-id <request-id>
```

审阅`workflow-reconcile/retired-generation/plan.json`时逐项看：

- `completed_destructive_operations`必须为空。它只数改动节点的操作（重启、停作业、停GPU
  服务等）；非空说明这条workflow真的动过集群，不能当作从未发生来关闭，`--apply`会拒绝，
  此时按§8定位它做了什么并单独处置。只做过cordon/quarantine的记录不在此列，这些隔离列
  在`completed_containment_operations`里供你知情，由successor世代的`RESTORE_SCHEDULING`
  收回。
- `blocker_codes`是机器可读的拒绝原因，`reasons`是它的文案；`cancellable`按code判定，
  只有`open_remote_commands`一项时为true。
- `already_revoked`为true表示上一次部分成功的apply已经关闭了它；这样的记录不会让计划
  被拒，apply会跳过并列在`already_revoked_workflow_ids`里，所以部分失败后重跑同一条命令
  是安全的。
- `unsettled_local_steps`必须为空。非空表示有一个provider动作没有回报，取消无从下手，
  同样拒绝。
- `open_remote_commands`非空**不是**拒绝理由，此时`eligible`为false而`cancellable`为true：
  取消一个incident已经跨过的世代的command在任何解读下都正确，apply会在同一次调用里先取消
  再终态化。
- `successor_workflow_id`必须存在。为空或原因里出现`workflow is no longer a retired
  generation`，说明形态已经变了，重新`--plan`。
- `workflow_updated_at`不参与摘要，只用来确认这是活的楔子：如果它就在几秒前，说明记录仍在
  被派发。

```bash
gpu-fault-admin workflow-reconcile \
  --state-dir /secure/gpu-fault \
  --mode retired-generation \
  --apply \
  --plan-sha256 <reviewed-sha256> \
  --reference CHG-12345
```

apply先按已审计划取消remote command，再重新出一次计划与已审计划逐字段比对：取消只允许
清空`open_remote_commands`，其它任何字段变化（世代、步骤、successor、incident状态）都指名
字段与前后值拒绝，此时什么都没有撤销。随后在事务内重新推导全部条件并比较**已审计划里**
的fencing token；每条记录单独写入，结果里的`applied_workflow_ids`/`failed_workflow_ids`/
`failures`说明哪些成了、哪些没成和原因，有失败时退出码为1。`records_deleted`恒为0。
`--reference`会写进`preemption_reason`和incident的`reasons`，是下一个读到这条记录的人判断
"这是有意关闭而不是丢了"的唯一依据，不能省。

结果里如果出现`restart_reservation_warnings`，表示workflow已经成功终态化，但restart
reservation没能释放——在旧镜像上跑时可能发生，Store瞬时错误也会落到这里而不是抛栈。对
这类告警**不要为它重跑该命令**（写入已完成）；记下告警里的workflow ID，等携带本修复的
release部署后，该job的下一次合法restart若因预算被拒，按§7的restart预算流程释放。对
`failed_workflow_ids`里的记录则相反：重新`--plan`再`--apply`，已关闭的记录会被标为
`already_revoked`并跳过。

不得用本模式关闭一个只是"跑得久"或"看起来卡住"的workflow：判定要求incident确实已经指向另一
个同incident、同当前世代的successor。这不是超时清理工具。

有一类记录永远不会变成eligible：`--plan`给出的唯一原因是
`workflow has no source recovery plan`。它们是没有经过plan驱动恢复而直接提交的
workflow，没有source plan可供reconcile写入`resolved_by_restore_workflow_id`审计关联，
所以`--apply`会以`workflow reconcile plan contains ineligible records`拒绝——这是设计
如此，不是缺陷。此时正确处置是**不处置**：只要`--plan`同时给出了
`successor_workflow_id`且没有successor相关原因，说明节点已经回到训练池，
`gpu_fault_workflow_blocked_unreconciled`已经不再计入这条记录，
`GpuFaultRecoveryBlockedBacklog`不会因它触发；数据库里的`BLOCKED`行留到保留策略归档为止。
不得为了让计数下降去改Store行。例外只有一种形态，见§10.2：记录在**编译期**就BLOCKED（`blocked_reasons`非空、零步执行、无source plan），且因含破坏性操作而被`workflow_safety` preflight计为活跃、卡住发布。

必须手工迁移或 purge 时，先记录副本、停止 ingress、排空 consumer，再停所有 writer。
恢复顺序相反：consumer 先恢复，ingress 最后恢复。状态文件在所有原副本 Ready 前不得
删除。

### 10.2 关闭编译期BLOCKED的破坏性workflow（compile-blocked）

第三种形态：Runtime Profile缺少某项能力的执行owner时，编译器在**任何步骤执行前**就把
workflow标为`BLOCKED`，`blocked_reasons`形如`no executable owner for efaDriverRemediation`。
这条记录没有lease、没有step execution、没有remote command，也没有source recovery plan，
它的containment前置动作（`MARK_UNSCHEDULABLE`）同样没有执行，所以节点上没有它的隔离。
后果是没有任何常规路径能关闭它：

- 对该incident执行验证恢复，`RESTORE_SCHEDULING`会因节点上没有本incident的隔离注解而
  fail-closed（旧版adapter；新版把"节点没有任何gpu-fault隔离"视为幂等成功），incident停在
  `ESCALATED`；
- `--mode restore`按§10.1末段的设计拒绝（无source plan）；`--mode retired-generation`只处理
  `PENDING`/`RUNNING`的退役世代。

而它含破坏性操作，`workflow_safety` preflight把它计为活跃并拒绝发布；Profile版本切换的
finalize门也把它计为旧版本活动。也就是说它恰好挡住了会补上该owner的那次发布。此时：

```bash
gpu-fault-admin workflow-reconcile \
  --state-dir /secure/gpu-fault \
  --mode compile-blocked \
  --plan \
  --workflow-id <request-id>
```

审阅`workflow-reconcile/compile-blocked/plan.json`时逐项看：

- `status`必须是`BLOCKED`，`blocked_reasons`非空且解释得通（缺owner、缺证据）；
- `step_execution_count`为0、`open_remote_commands`为空、`source_plan_id`为空——任一不满足
  都说明它不是编译期记录，`eligible`为false，`--apply`拒绝；
- `incident_state`必须是`ESCALATED`或`RECOVERED`；`incident_workflow_id`通常已指向别的
  workflow（失败的验证恢复）；
- `scheduling_evidence.restored`必须为true：`kubectl`确认节点可调度、无`gpu-fault.io/quarantined`
  污点、无ownership注解。编译期记录从未隔离任何节点，节点上若有隔离必定属于别人，此时
  拒绝——不能用关闭这条记录来掩盖另一条的隔离；
- `already_closed`为true表示上一次apply已经关闭它，apply会跳过并列入
  `already_closed_workflow_ids`，重跑同一条命令是安全的。

```bash
gpu-fault-admin workflow-reconcile \
  --state-dir /secure/gpu-fault \
  --mode compile-blocked \
  --apply \
  --plan-sha256 <reviewed-sha256> \
  --reference CHG-12345
```

apply重新出计划并与已审摘要比对（`workflow_updated_at`不参与），然后在Pod内重读每条记录、
核对fencing token与execution epoch后以`save_workflow`写入`SUPERSEDED`，`preemption_reason`
带上`--reference`和原`blocked_reasons`；**不写incident**（它没有节点状态可释放，盲写会覆盖
正在合并事件的行）。`records_deleted`恒为0；`failed_workflow_ids`/`failures`说明未成功的记录，
有失败退出码为1。该模式随源码一并送入Pod运行，因此可以在携带本模式的release部署**之前**
使用——这正是它存在的理由。

不得用本模式关闭任何已经派发过（有step execution或completed operation）的workflow，也不得
在补上缺失owner之前反复注入同类故障：每次都会再产出一条这样的记录。

### 10.3 取消终态workflow遗留的remote command（orphaned-commands）

第四种形态：workflow已经终态（`FAILED`/`SUCCEEDED`/`BLOCKED`/`SUPERSEDED`），它的某条
remote command却仍是`PENDING`/`LEASED`/`WAITING`。当前执行器在步骤触及等待上限时会先取消
该步的remote command再判失败；旧版本不会，所以一条被600s步骤上限判FAILED的
`CHECK_MECHANICALS`可以把它的command永远留在`WAITING`。执行器不会回头看终态workflow，
`--mode retired-generation`只取消被incident换代的记录，而发布升级要求
remote command的`PENDING/LEASED/WAITING`为0——这条孤儿恰好挡住会消灭孤儿的那次发布。

```bash
gpu-fault-admin workflow-reconcile \
  --state-dir /secure/gpu-fault \
  --mode orphaned-commands \
  --plan \
  --workflow-id <request-id>
```

审阅`workflow-reconcile/orphaned-commands/plan.json`时逐项看：

- `workflow_status`必须是终态之一。`PENDING`/`RUNNING`/`SAFETY_PENDING`的workflow其open
  command是活的工作，只有持租的执行器有权结算，`eligible`为false，`--apply`拒绝；
- `open_commands`列出将被取消的command（id、状态、操作、step、lease owner），为空时同样拒绝
  （没有什么可取消，不做空操作）。

```bash
gpu-fault-admin workflow-reconcile \
  --state-dir /secure/gpu-fault \
  --mode orphaned-commands \
  --apply \
  --plan-sha256 <reviewed-sha256> \
  --reference CHG-12345
```

apply重新出计划并与已审摘要比对（command在审阅期间已结算或workflow复活都会导致拒绝），然后按
workflow调用Store的`cancel_remote_commands_for_workflow`——与退役世代关闭使用的是同一个接口，
Agent侧看到取消标记即停止。**不写workflow也不写incident**；`records_deleted`恒为0。该模式同样
随源码送入Pod运行，可在携带执行器修复的release部署之前使用。

不得用本模式"催"一个还在等操作员确认的活workflow：`CHECK_MECHANICALS`在workflow为
`RUNNING`时的等待是设计行为，操作员确认超时由
`GPU_FAULT_OPERATOR_ACKNOWLEDGEMENT_TIMEOUT_SECONDS`（默认86400）控制。

## 11. 集中容器日志（CloudWatch Container Insights）

默认不装。日志止于节点本地是写下来的取舍（[详细设计-v2 §10.1](详细设计-v2.md#101-日志)），
本节是把控制面容器日志送出集群的那条已交付路径。

**适用条件**

站点已完成 bootstrap（`eks-pod-identity-agent` addon 为 ACTIVE），且已经确认接受
CloudWatch Logs 摄入与存储费用。本路径**只针对 CPU 控制面集群**；GPU 集群需要显式
放行，理由见下面的“影响范围”。

**影响范围**

- 装 `amazon-cloudwatch-observability` EKS addon，新建 `amazon-cloudwatch`
  namespace 与它自己的 DaemonSet。不改本仓库任何渲染清单，不进 `module_digest`，
  与发布事务无关，可以在独立窗口装卸。
- 新建四个日志组：`/aws/containerinsights/<cluster>/{application,dataplane,host,performance}`。
  `application` 承载集群内**每一个**容器的 stdout/stderr；在控制面上这就是本系统自己的
  日志，所以 `logging_setup` 的集中脱敏是硬前置。
- `host` 组的范围比组名看起来大。实测 `host-log.conf` 是三个 journald input：
  `_TRANSPORT=kernel`（即 dmesg 看到的内核消息）、`PRIORITY=0-6`、
  `SYSLOG_FACILITY=10`；唯一的 `grep` 排除是按 syslog facility（mail/cron/authpriv），
  **不按 unit**。所以 `PRIORITY=0-6` 这条是 unit 无关的：节点上只要有 `gpu-fault-*`
  systemd unit 在跑，它的 journal 也会进 CloudWatch。审计范围和账单都要按这个算。
- **它不会**采集训练日志文件——Fluent Bit 没有任意路径的 tail input，只有
  `/var/log/containers/*.log`。也不会采集 `PRIORITY=7`。
- 无论采不采，**故障证据通道不变**：控制面从不读 CloudWatch，
  `NodeLogBatch.collection_errors` 仍是唯一会把采集缺口送到控制面的通道
  （见 §8 `GpuFaultCollectorCollectionErrors`）。
- 所有 input 都从**尾部**开始（`READ_FROM_HEAD=Off`、`READ_FROM_TAIL=On`），装之前
  写下的日志一律不回填。
- 计费上要知道 kubelet 的 journal 被收**两遍**：`dataplane` 按
  `_SYSTEMD_UNIT=kubelet.service` 收，`host` 的 `PRIORITY=0-6` 又收一遍（已在
  2026-09-04 用同一行 `SyncLoop ADD` 在两个组里各命中一次核实）。这是上游 Container
  Insights 配置本身的性质，不是本脚本引入的；估算摄入量时按重复算。
- GPU 集群三个额外后果，所以默认拒绝：`application` 会把每个训练任务的 stdout 全部
  送进 CloudWatch；`host` 会把内核 XID 行和 `gpu-fault-*` unit 的 journal 再送一份，
  而这两类节点侧本来就在采；且 agent 自带的 dcgm-exporter 争用主机 9400 端口，而该
  端口已被 `gpu-fault-dcgm-exporter.service` 占用。放行须同时保持
  `GPU_FAULT_CLOUDWATCH_ACCELERATED_METRICS=false`。

**只读检查**

默认动作就是只读，先看当前状态（addon、pod identity association、每个日志组的
retention 与最后一条事件时间、DaemonSet ready 数）：

```bash
AWS_REGION=<region> \
EKS_CLUSTER=<cpu-eks-cluster> \
EKS_KUBECONFIG=/secure/gpu-fault-bootstrap/control-plane.kubeconfig \
  deploy/observability/install-cloudwatch-observability.sh
```

任何日志组出现 `retention=None` 都是“永不过期”，必须先修好再继续。

**执行命令**

```bash
AWS_REGION=<region> \
EKS_CLUSTER=<cpu-eks-cluster> \
EKS_KUBECONFIG=/secure/gpu-fault-bootstrap/control-plane.kubeconfig \
SITE_ID=<site-id> \
GPU_FAULT_CLOUDWATCH_ACTION=install \
GPU_FAULT_CLOUDWATCH_RETENTION_DAYS=30 \
  deploy/observability/install-cloudwatch-observability.sh
```

脚本幂等：先建 IAM 角色（打 `gpu-fault:site-id` 标签）和 pod identity association，
再把四个日志组的 retention 设好，最后才创建/更新 addon——顺序是为了不留下一个
“永不过期”的窗口。kubeconfig 与 `EKS_CLUSTER` 的集群 ARN 不一致时直接拒绝执行。

**成功标准**

不以 addon ACTIVE 或 Pod Ready 为准。脚本要求
`/aws/containerinsights/<cluster>/application` 出现日志流才算成功——association 缺失
或角色掉了策略时，agent 一样 Ready 却每次 PutLogEvents 都失败。随后用只读动作复核
四个日志组的 retention 均为期望天数。

不要以“每个 Pod 都有日志流”为准：Fluent Bit 从文件尾开始 tail，**不回填**装之前
已经写下的日志，因此装之前就已经安静的 Pod（长时间无请求的 `api-ha`、已 Completed
的 Job）在它下一次写日志之前不会有日志流。少一个流不能推断链路坏了；判断链路要看
`application` 组整体是否在持续收到事件。

**回滚**

```bash
AWS_REGION=<region> EKS_CLUSTER=<cpu-eks-cluster> \
EKS_KUBECONFIG=... SITE_ID=<site-id> \
GPU_FAULT_CLOUDWATCH_ACTION=uninstall \
  deploy/observability/install-cloudwatch-observability.sh
```

删 addon（不带 `--preserve`）并等到 addon-deleted、删 association、仅在 IAM 角色带本
站点标签时删角色。**日志组故意保留**：它是集群停止上送前所说过的话的唯一副本，
retention 已经约束了体积；要一并丢弃需另行执行脚本末尾打印的 `delete-log-group`。
不可逆边界：已经摄入的日志按 retention 计费，卸载不退。

注意与 §3 的关系：`gpu-fault-admin uninstall --cpu-cluster keep` **不会**清掉这个
addon（它不在资源注册表里，这正是它不进发布事务的代价），必须先跑上面的 uninstall；
`--cpu-cluster delete` 会随集群一并删除。

**证据**

变更单号、只读动作在装前装后的两份输出、addon 的 `--configuration-values`、四个日志组
的 retention，以及 `application` 组首个日志流的时间戳。
