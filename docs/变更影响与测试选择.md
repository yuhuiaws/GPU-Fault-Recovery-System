# 变更影响与测试选择

本文定义“代码路径/模块 → 静态检查 + pytest + 区域验收用例”的反向影响索引。
它用于日常开发和版本候选，不改变正式区域验收的事实源：

- 用例字段：`testcases/fault-scenarios.yaml`
- 正式顺序：`testcases/regional-execution-order.yaml`
- 反向影响规则：`testcases/change-impact.yaml`

选择器只生成 regional case 计划，永不自动执行 live、destructive、reboot、reset、
warm-spare 或 workload restart。

## 执行层级

| 场景 | 要求 |
|---|---|
| 日常开发 | 相关静态检查 + 相关 pytest |
| PR / 版本候选 | 日常开发门禁 + 受影响的非破坏性 regional case 计划 |
| 管理员选择执行 | 只运行明确选择的case；报告标记selective，不代表完整phase通过 |
| 正式首次上线 / 重大架构变更 | 按 `regional-execution-order.yaml` 完整验收 |
| destructive / live case | 只有对应实现受影响且取得维护窗口批准后执行 |

常用入口：

```bash
make test-impact BASE=origin/main
make regional-impact-plan BASE=origin/main

# 只生成计划，不执行pytest
python3 scripts/select-affected-tests.py --base origin/main
```

选择器会合并以下差异，避免漏掉未提交修改：

1. `BASE...HEAD` 的已提交变化；
2. 工作区变化；
3. staged变化；
4. 未跟踪且未被Git忽略的文件。

统一staging build会用`--write-plan`把一次选择结果保存到
`dist/staging-impact-plan.json`，再用`--read-plan`执行。计划文件绑定`BASE`、changed
files和内容SHA；读取时重新获取changed files并要求完全一致，因此复用计划不会接受源码
漂移。该文件同时提供regional safe/approval case清单，不再为输出区域计划重复运行规则
匹配。

选择器输出的case可以由管理员按selective scope逐条执行。selective scope不会自动补跑
正式顺序中的其他case，也不能作为后续formal case的predecessor；需要声明完整区域验收
通过时，仍按`regional-execution-order.yaml`执行formal campaign。

## 输出含义

`Changed domains`是命中的影响域。`Run static checks`和`Run pytest`可直接执行。
`Regional safe cases`只表示非破坏性影响计划，不代表已经执行。
`Require staging/live approval`中的用例必须经过对应环境和维护窗口审批。
`Not selected regional families`明确说明哪些家族没有实现路径命中。

`make test-impact`会执行静态检查和pytest，但不会执行regional case。需要真实
PostgreSQL压力测试而环境没有设置`GPU_FAULT_TEST_POSTGRES_URL`时，命令会fail closed。
统一staging入口会先读取计划中的`postgres`标志，只在该标志为true时创建隔离
PostgreSQL 16。

## Main CI内容身份复用

main CI的`unit`门禁不直接以Git commit作为唯一复用键，而是生成四个逻辑内容域：

1. `runtime`：应用Runtime源码、普通Runtime测试、共享fixture和依赖；
2. `deployment`：Runtime共享源码、部署/发布/deploy-host-only源码及其测试；
3. `fault_runner`：Runtime共享源码、catalog/scheduler/runner及runner测试；
4. `postgres`：Runtime共享源码、四个PostgreSQL contract测试、实际PostgreSQL image；
5. 每个身份还绑定Python/Runner、已安装distribution、coverage协议和worker配置。

runtime域按稳定pytest nodeid哈希继续拆成`runtime_0..2`，所以每次run实际产生六个
物理shard artifact。参数化测试的每个nodeid只进入一个runtime子shard，三者并集保持
完整Runtime测试集。

历史shard artifact必须来自已完成的main push，且对应shard job成功，并通过固定workflow
identity的Cosign验签、producer run、证据SHA和当前内容身份校验；同一run中其他job失败
不会废弃已经成功签名的独立shard。命中后，当前run使用历史
coverage/pytest/duration证据生成带`reused_from`的新shard gate并重新签名；未命中的
shard独立执行。六个物理shard完成后才统一`coverage combine`、78% floor、
deployment-only模块的per-module floor和fault report。

GitHub artifact查询或下载临时不可用时，当前shard安全回退fresh执行；已经下载的gate
若签名、摘要、producer或内容身份不一致则继续fail closed，不能用网络回退掩盖无效
证据。

因此：

- docs/CI工具变化由当前static执行，六个shard可全部复用；
- deploy-host-only管理员源码或对应测试变化只重跑deployment shard；
- fault catalog/runner变化只重跑fault_runner shard；
- PostgreSQL contract测试或相关Runtime源码变化使postgres shard重跑；
- Runtime共享源码变化会保守地使依赖它的多个shard失效，但这些fresh shard并行执行。
- CI gate、artifact下载、coverage/unit签名和候选恢复属于显式`ci-trust`域；这些文件
  改动继续升级完整门禁，不再由未分类runtime兜底。

该机制不能复用失败、取消、PR或其他分支的结果，也不能跳过当前commit的static、
artifact、统一coverage floor或PostgreSQL stress。

## Fail-closed升级

以下任一情况会升级为`make check`和完整regional计划：

- `models.py`、operation/channel registry、Store contract、授权registry等共享契约变化；
- Python版本、依赖锁、runtime image或release identity变化；
- PostgreSQL schema、事务、lease或fencing变化；
- 一次改动跨越三个以上业务影响域；
- 存在未被普通规则匹配的实现文件；
- 修改影响矩阵、选择器、case catalog或区域执行顺序本身。

完整regional计划仍只是计划。`GF-REGIONAL-DESTR-004`永不进入选择结果；其他
destructive/live case只出现在审批区，不会被`test-impact`执行。

## 规则维护

每条规则包含：

```yaml
- id: remote-command
  description: Remote command protocol and Executor.
  paths:
    - src/gpu_fault/cluster_executor/**
    - src/gpu_fault/store/**/remote_commands.py
  pytest:
    - tests/hyperpod/test_cluster_executor.py
  regional_cases:
    - GF-REGIONAL-CMD-001..016
  checks:
    - config-check
```

新增规则时运行：

```bash
make impact-check
make docs-check
python3 -m pytest -q tests/test_change_impact.py
```

`impact-check`验证重复键、路径、pytest目标、case存在性、正式顺序和
`DO_NOT_RUN`约束。任何无法证明安全的路径应进入fail-closed规则，而不是静默忽略。
