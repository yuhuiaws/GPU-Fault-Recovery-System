# GPU 故障处理系统管理员快速部署

本文只描述区域生产方案的首次建站或应用层重建成功路径：

1. 仅提供已有 CPU/GPU EKS 或 HyperPod ARN，由 ARN-only 模式自动创建方案专属
   Aurora、IAM、NLB/PKI、监控和凭据；
2. 平台或 IaC 已准备资源时，使用已有 `site.yaml` 执行应用部署。

两种路径都不要求管理员按 CPU-1～9、REG-1～8 手工拼接命令，也不编写或逐个 apply
方案 Manifest。需要逐对象审计、共享基础设施特殊处理或 break-glass 时，转到
[部署和运维手册](部署和运维手册.md)；上线后的升级、集群变更、轮换、排障和退役统一
使用[管理员日常运维](管理员日常运维.md)。

## 1. 适用范围

唯一生产形态为：

```text
区域 CPU EKS 控制面 + Aurora PostgreSQL + TLS NLB
                    |
                    +-- HyperPod EKS GPU 集群 A
                    +-- HyperPod EKS GPU 集群 B
                    +-- ...
```

受管 GPU HyperPod 必须为 EKS 编排且 `NodeRecovery=None`。通用 Kubernetes、
HyperPod Slurm 和单集群一体化不属于新生产部署路径。

## 2. 当前管理员入口

已有 `site.yaml` 时，部署主线固定为四步：

```bash
gpu-fault-admin preflight -f /secure/gpu-fault/site.yaml
gpu-fault-admin deploy -f /secure/gpu-fault/site.yaml
gpu-fault-admin verify -f /secure/gpu-fault/site.yaml
gpu-fault-admin status -f /secure/gpu-fault/site.yaml
```

首次从已有集群自动建站时，不需要手写 `site.yaml`：

```bash
gpu-fault-admin deploy \
  --cpu-cluster-arn arn:aws:sagemaker:us-west-2:123456789012:cluster/cpu-control \
  --gpu-cluster-arn arn:aws:sagemaker:us-west-2:123456789012:cluster/gpu-a \
  --admin-email gpu-operations@example.com
```

`--gpu-cluster-arn` 可以重复。输入也可以是对应 EKS ARN；脚本会反查唯一 HyperPod
cluster。自动模式负责创建当前站点专属的 Aurora、LBC、控制面和 Executor IAM、
NLB 网络/SG、私有 Route53/PKI/ACM、AMP/SNS/SQS、Secret、token、kubeconfig 和节点
Action key，并并行执行无依赖任务。已有同名对象只有在 `gpu-fault:site-id` 证明属于
当前站点时才作为未完成部署的遗留资源接管；外部同名对象会阻止部署。完成后生成权限为
`0600` 的持久 `site.yaml`，
继续执行 preflight、deploy和verify。

`--admin-email` 可省略。CLI 会优先读取 AWS Organizations 中当前账号登记的邮箱，
再尝试 Account Management 主邮箱；两种 API 都不可读时必须显式提供。该地址同时
用于 SES 故障/动作通知和 SNS 运维告警。缺少 SES identity 时脚本自动创建，管理员
完成 AWS 验证邮件后重跑同一命令；未验证前部署不会静默降级为无邮件模式。
EKS/HyperPod 自身的 VPC和基础路由属于已建集群的一部分。GPU VPC必须已有可用 NAT
出口；CPU VPC缺少NLB公网子网时，脚本会从空闲CIDR创建两个方案专属 `/28` 子网。

`gpu-fault-admin` 随项目 wheel 安装；从源码管理机执行时，先在当前虚拟环境安装项目。
`site.yaml` 的 `spec.repositoryRoot` 必须填写包含 `deploy/`、`config/` 和 `dist/`
的绝对仓库路径。

| 命令 | 含义 |
|---|---|
| `preflight` | 只读检查本地输入、AWS 身份、EKS/HyperPod/IAM、CPU 容量、Aurora、LBC、ACM、AMP/SNS |
| `deploy` | 先自动运行 preflight；没有稳定 release state 时 bootstrap，已有环境时 upgrade |
| `verify` | 独立、只读验证 CPU/GPU、Profile、API/TLS、Agent/Collector、NLB、Aurora 和告警链路 |
| `status` | 输出同一套结构化健康报告以及 release/profile/wheel 引用，健康异常时退出码非 0 |

## 3. 部署前输入

管理员只维护一个 `RegionalSite` YAML 作为应用部署的拓扑、身份、制品和健康检查事实
源。模板：

```text
config/site.example.yaml
```

该文件必须包含：

| 配置 | 要求 |
|---|---|
| `spec.awsRegion` | 操作者明确选择的 Region |
| `spec.cpu` | kubeconfig、EKS ARN、CPU HyperPod 名 |
| `spec.release` | `dist/current-release.json` 和 Agent config digest |
| `spec.runtimeProfile` | 可编辑template、不可变source快照、自动版本和稳定注册锚点 |
| `spec.nlb` | NLB 名、公共子网、Security Group、ACM certificate ARN |
| `spec.health` | Aurora、AMP、SNS 和健康阈值 |
| `spec.notifications` | SES 管理员邮箱、sender 和外部告警确认；ARN-only 自动填写 |
| `spec.clusters[]` | 每集群唯一 ID、context、EKS ARN、HyperPod 名、IRSA、namespace allowlist |
| 凭据引用 | 每集群 token 文件、CA 文件和受控 fleet master 文件 |

CLI 会逐层拒绝未知字段、错误类型、重复集群、跨 Region ARN、非 HTTPS URL 和残留
`REPLACE_*`，然后在权限为 `0700/0600` 的临时目录生成兼容 release JSON。管理员不再
手工维护 release JSON。

当前版本仍通过受控文件引用 token、CA 和 fleet master。文件必须在仓库外，目录权限
`0700`、敏感文件权限 `0600`，不得进入 Git、普通日志或构建 artifact。

## 4. 首次部署门禁

首次 ARN-only 自动部署只要求：

1. 一个已有的 3 节点 CPU EKS/HyperPod 集群。
2. 至少一个已有的 GPU EKS/HyperPod 集群，且 `NodeRecovery=None`。
3. GPU VPC 已有可用 NAT 出口。
4. 当前 AWS 执行身份具有 IAM、EKS、SageMaker、EC2、ELBv2、RDS、
   Secrets Manager、KMS、ACM、Route53、SES、AMP、SNS、SQS 和目标 EKS
   Kubernetes 管理权限。自动发现邮箱还需要
   `organizations:DescribeAccount` 或 `account:GetPrimaryEmail`；否则传
   `--admin-email`。

脚本会自动发现 Region、账号、EKS ARN、VPC、subnet、HyperPod 名和 NAT EIP，并创建
当前 `site-id` 独占的：

- Aurora Serverless v2 writer/reader、subnet group和SG；
- Load Balancer Controller、Pod Identity Agent和IAM；
- 控制面及各 GPU Executor角色；
- NLB公网子网、NLB SG和GPU NAT EIP白名单；
- 私有Route53 zone、CA、ACM certificate和PKI Secret；
- AMP workspace、Alertmanager、SNS topic和持久SQS接收队列；
- SES email identity、控制面最小 `ses:SendEmail` 权限和 `gpu-fault-email` Secret；
- Kubernetes Secret、cluster token、fleet master和kubeconfig；
- Aurora credential refresh和Node Action key。

CPU VPC缺少合格NLB公网子网时，脚本会从空闲CIDR创建两个方案专属 `/28` 子网。
即使 CPU VPC 已有其他公共子网，也不会把它们拿来共享。VPC 级 IGW、GPU EKS 的
OIDC Provider 和预装 Pod Identity Agent 属于无法重复创建的集群基础能力，可登记为
`EXTERNAL/PRESERVE`。如果 GPU VPC 没有 NAT 出口，脚本会停止，不会擅自替换现有
集群路由。

## 5. 本地检查

```bash
install -d -m 0700 /secure/gpu-fault
install -m 0600 config/site.example.yaml /secure/gpu-fault/site.yaml
${EDITOR:-vi} /secure/gpu-fault/site.yaml

make release-preflight

gpu-fault-admin preflight -f /secure/gpu-fault/site.yaml
```

`preflight` 不修改 AWS 或 Kubernetes。报告中的每个领域为
`PASS/FAIL/SKIP`，任一必需检查失败时退出码为 1，`deploy` 不会开始。

## 6. 执行部署

```bash
gpu-fault-admin deploy -f /secure/gpu-fault/site.yaml
```

开发者发布或既有站点升级使用`make PYTHON=.venv/bin/python release-deploy SITE=/secure/gpu-fault/site.yaml`；可选追加`ADMIN_EMAIL=gpu-operations@example.com`。
同release ID被明确分类为`NOOP`时，该入口跳过deploy内的preflight和NOOP verifier，
只并行执行一次全量`verify`并保存报告；管理员主动运行`status`仍会重新查询实时状态。
`deploy` 会再次执行 live preflight，避免检查后环境发生漂移，然后：

1. 没有 release state 时执行首次 bootstrap。
2. 已有 release state 时先比较 Control Plane、Executor、Node Runtime、bundle、
   schema、协议、Profile、endpoint、DCGM 和集群集合，只执行受影响的升级路径。
   finalize 仅在 required/compatible pin 的实际内容变化时滚动 CPU。
   Profile 使用规范化策略摘要比较；仅路径或 YAML 顺序变化不触发 `FULL`。
3. 失败的 bootstrap state 会重新执行幂等 bootstrap。
4. 按需上传三个内容寻址 wheel 和 Node bundle，并仅在版本变化时初始化 schema。
5. 部署 CPU 三层控制面并核对区域 Runtime Profile。
6. 验证私有 hosted zone 存在、ACM certificate 为 `ISSUED`、SAN 覆盖控制面域名，
   然后创建 NLB Service。
7. 严格等待 NLB `state=active`、TLS 443 listener 使用目标证书、原始 NLB DNS
   可解析，并且三个 API Pod target 全部为 `healthy`。
8. 只有上述门禁通过后才 `UPSERT` 私有 CNAME，并等待 Route53 change 明确变为
   `INSYNC`。
9. 对每个 GPU 集群先保持 Executor 未启动，由临时 Pod 使用连接 Secret 中的私有 CA
   完成 CNAME DNS 解析、TLS hostname/证书链和 `/healthz` HTTP 200 验证。
10. GPU Pod 门禁成功后才启动 Executor、Watcher、Resource Collector 和 Reconciler。
11. 等待所有节点 Agent 收敛，再执行发布 verifier 和自动回滚。

`plan/status` 会显示下一次部署分类：`NOOP` 快速路径只做一次并行只读验证；
`CONTROL_PLANE_ONLY` 只滚 CPU；`DATA_PLANE_COMPATIBLE` 只滚变化的数据面并最多并行
处理 4 个互不依赖的 GPU 集群；`FULL` 才执行完整两阶段门禁。升级失败或已自动回滚
时，重新执行同一条 `deploy` 会复用持久化差异计划续跑。

任一阶段失败都会停止后续阶段。特别是，NLB target 未健康时不会发布新 CNAME；
Route53 未 `INSYNC` 或 GPU Pod 的 DNS/TLS 验证失败时不会启动首次部署或重新加入流程
中的 Executor。重新执行同一条 `deploy` 命令会从幂等状态继续。

管理员不得在该命令运行期间执行 CPU-4、REG-1～8 或在线
`kubectl edit/set env/apply`。

## 7. 部署后验证

```bash
gpu-fault-admin verify -f /secure/gpu-fault/site.yaml
```

`verify` 是独立、只读命令，不注册 Profile，也不刷新 installed-resource registry。
它验证：

- CPU 三层角色、PDB、ADOT 和 Aurora refresh CronJob；
- Runtime Profile 已注册且内容无漂移；
- GPU Executor IRSA、Secret、wheel 和 adapter 开关；
- Executor 真实 readiness、TLS 私有 CA；
- Agent ACTIVE、Fleet readiness 和 Collector freshness；
- remote command 积压年龄和内部错误；
- NLB TLS listener、certificate 和三个健康 target；
- Aurora writer/reader；
- AMP rule namespace、Alertmanager 和已确认 SNS subscription。

查看当前健康状态：

```bash
gpu-fault-admin status -f /secure/gpu-fault/site.yaml
```

`status` 输出 JSON，包含 `healthy`、各检查状态、失败原因、release metadata、Runtime
Profile、三个组件 digest、CPU wheel 和每个 GPU 集群的
Executor/Reconciler/template 引用。

然后按[区域部署验收清单](部署和运维手册.md#reg-8-区域部署验收清单)执行生产验收，并用
不同 job/attempt ID 分别验证：

```bash
SITE_FILE=/secure/gpu-fault/site.yaml

gpu-training-submit customer-job.yaml \
  --site "${SITE_FILE}" \
  --job-id deployment-smoke-direct \
  --attempt-number 1

gpu-fault-workload-annotate customer-job.yaml \
  --site "${SITE_FILE}" \
  --job-id deployment-smoke-reviewed \
  --attempt-number 1 \
  --output /tmp/customer-job.managed.yaml

kubectl apply --dry-run=server -f /tmp/customer-job.managed.yaml
kubectl apply -f /tmp/customer-job.managed.yaml
```

两次训练均被 Watcher 正确观测后，才能按阶段 A～D 开放破坏性能力。

## 8. 失败处理

| 场景 | 处理 |
|---|---|
| `preflight` 失败 | 按检查名称修复站点配置、凭据或共享基础设施，不修改集群 |
| ARN-only bootstrap 失败 | 保留自动生成的私有 state 目录，修复所有权、权限或依赖后以相同参数重跑 |
| 首次应用部署失败 | 查看 release state；自动 fail-closed 后修复原因，再重跑 `gpu-fault-admin deploy` |
| `verify/status` 失败 | 不进入生产流量或破坏性能力阶段；按失败检查项修复后重新执行独立验收 |
| Profile 同版本内容不同 | 不得覆盖，发布新的 profile version |

不得用降低 readiness、扩大 allowlist、关闭签名或跳过 TLS 来让部署变绿。
升级中断、Agent未收敛、Executor verifier失败等上线后处置见
[管理员日常运维](管理员日常运维.md)的区域升级和按症状排障章节。

## 9. 上线证据

每次生产部署至少保存：

- release manifest、三个组件 wheel/Node bundle SHA 和组件 `module_digest`；
- site YAML 摘要和生成配置摘要，不包含 Secret 内容；
- `preflight`、`deploy`、`verify` 和 `status` 输出；
- CPU/GPU verifier 结果；
- Runtime Profile version 和有效 capability；
- NLB/TLS、Aurora refresh、AMP/SNS 验收结果；
- 训练 smoke 的 job/attempt ID；
- 变更单号、维护窗口和操作者。

可使用：

```bash
python3.12 scripts/capture_release_evidence.py \
  --release-id "${RELEASE_ID}" \
  --phase after \
  --cpu-kubeconfig "${CPU_KUBECONFIG}" \
  --gpu-context "${GPU_EKS_CONTEXT}"
```

## 10. 后续运维入口

首次部署、训练smoke和上线证据完成后，本文件的任务结束。后续操作统一进入
[管理员日常运维](管理员日常运维.md)：

| 后续任务 | 日常运维章节 |
|---|---|
| 健康巡检和重复验收 | 常用任务入口 |
| 区域升级、续跑和回滚 | 区域升级 |
| 接入或移除GPU集群 | `gpu-fault-admin join-cluster/remove-cluster` |
| token、证书和节点key轮换 | 凭据和证书生命周期 |
| Agent、Executor、队列或provider故障 | 按症状排障 |
| 数据迁移、归档和purge | 数据与审计维护 |
| 保留集群重装、完整卸载或永久退役 | 完整卸载或永久退役 |
| 当前能力边界和待产品化命令 | 当前待产品化命令 |

本文件不重复卸载状态机、旧环境发现、集群移除或路线图。所有退役模式都必须遵守一个
不变量：任何方案卸载命令都不得删除GPU EKS或GPU HyperPod集群。
