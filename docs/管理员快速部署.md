# GPU 故障处理系统管理员快速部署

本文只描述区域生产方案的首次建站或应用层重建成功路径。管理员提供已有CPU/GPU
EKS或HyperPod ARN，单个命令自动创建站点AWS资源、构建签名release并部署应用。
该路径不要求管理员按 CPU-1～9、REG-1～8 手工拼接命令，也不编写或逐个 apply
方案 Manifest。需要逐对象审计、共享基础设施特殊处理或 break-glass 时，转到
[部署和运维手册](部署和运维手册.md)；上线后的升级、集群变更、轮换、排障和退役统一
使用[管理员日常运维](管理员日常运维.md)。

## 1. 适用范围

唯一生产形态为：

```text
区域 CPU EKS 控制面 + Aurora PostgreSQL + TLS NLB
                    |
                    +-- HyperPod EKS GPU 集群 A
                    +-- HyperPod EKS GPU 集群 B
                    +-- ...
```

受管 GPU HyperPod 必须为 EKS 编排且 `NodeRecovery=None`。通用 Kubernetes、
HyperPod Slurm 和单集群一体化不属于新生产部署路径。

## 2. 当前管理员入口

首次部署四个参数；之后的失败续跑、升级都只需`--state-dir`一个参数，其余从站点读取：

```bash
gpu-fault-admin deploy \
  --cpu-cluster-arn <cpu-eks-or-hyperpod-arn> \
  --gpu-cluster-arn <gpu-eks-or-hyperpod-arn> \
  --state-dir /secure/gpu-fault \
  --admin-email <operations-email>
gpu-fault-admin deploy --state-dir /secure/gpu-fault   # 续跑 / 升级
```
多个GPU集群重复传`--gpu-cluster-arn`；首个GPU集群完成基线部署和验证后，其余集群自动执行
最多4路的独立batch join，单个失败不撤销同批次成功集群。已有站点上再传ARN必须是纳管集合或
其超集：多出的GPU ARN在发布后自动接入（release未变化时只接入，不滚动）；少给集群或换CPU会
拒绝并提示`remove-cluster`。同一命令加`--rollback`回退一步，加`--approve-profile-plan <sha>
--reference CHG-<id>`审批Profile计划并继续。管理员不提供release-ref、artifact、site、
release-build/release-deploy、bundle或venv路径。命令自动创建或复用签名材料和
site-tagged ECR、运行所需门禁、push并验签release，再创建或复用
Aurora、AMP/SNS、PKI/IAM等资源，并把`deploy/observability/dashboards/*.json`导入CPU集群所在Region的Amazon Managed Grafana：依次取`--grafana-workspace-id`、带site tag的workspace、该Region唯一的ACTIVE workspace，一个都没有就为客户新建一个（IAM Identity Center登录，uninstall会删掉）；新建被拒或导入失败只告警不阻断。导入完成后deploy用管理员邮箱（`--admin-email`）在IAM Identity Center里找到对应用户并授予Grafana ADMIN（需要部署主机有`sso:ListInstances`、`identitystore:GetUserId`、`grafana:ListPermissions`、`grafana:UpdatePermissions`）；找不到该用户时不阻断，部署结束打印仪表盘地址、授权自己登录的那一行`aws grafana update-permissions`命令和缺了什么，补好用户后重跑deploy即可；也可以直接传`--grafana-viewer <Identity Center用户id>`让deploy代为授予VIEWER。
EKS/HyperPod 自身的 VPC和基础路由属于已建集群的一部分。GPU VPC必须已有可用 NAT
出口；CPU VPC缺少NLB公网子网时，脚本会从空闲CIDR创建两个方案专属 `/28` 子网。

部署前先按[CI 发布流程](CI发布流程.md)的bundle规则安装并激活`gpu-fault-admin`。首次命令从当前
受信checkout确定源码根目录，后续由内部state恢复；生成的site和repository路径不进入
公共参数。

Release提供`config/admin-config.example.yaml`；deploy-host venv中同一模板位于`share/gpu-fault/admin-config.example.yaml`。首次建站可用
`deploy --config <0600-admin-config.yaml>`直接应用管理员已编辑配置；不传时持久化
release默认值并生成`<state-dir>/admin-config.yaml`。已有站点编辑该文件后执行
`gpu-fault-admin config --state-dir ... --reference ...`，完整命令见
[管理员容量配置](管理员容量配置.md)。

| 内部阶段 | 含义 |
|---|---|
| source preparation | 固定Git身份，准备或复用签名release和部署环境 |
| preflight | 只读检查AWS身份、集群、IAM、容量、Aurora、LBC、ACM和监控 |
| bootstrap/upgrade | 没有站点时按依赖图并行创建（监控、Node key与Aurora实例就绪互不等待），已有站点时先验证集群身份再升级 |
| verify/stability | 验证CPU/GPU、Profile、TLS、Agent、Aurora和稳定窗口 |

## 3. 部署前输入

**一封邮件确认是前置条件：站点只有一条邮件通道。** 站点 SNS topic 同时承载 AMP Alertmanager 的指标告警和
控制面自己发出的故障处置通知（事件升级、GPU 数量变更审批、机械检查请求，含重试与回执；纯文本、主题≤100 个
ASCII 字符、发件人 `no-reply@sns.amazonaws.com`）。`--admin-email`即 SNS 订阅地址；deploy第一分钟内发送并检查
这封确认，未确认即退出码2并列出续跑命令，或加`--wait-for-email-confirmation <分钟>`。不需要预先验证 SES 身份；需要富文本邮件的站点可在`site.yaml`声明`spec.notifications.channel: ses`（此时另需验证 SES 发件身份，见运维手册 §8）。

首次ARN命令在state中生成权限`0600`的内部`RegionalSite`，作为应用拓扑、身份、制品和健康检查
事实源。管理员不手工创建、编辑或传入该文件。内部内容包括：

| 配置 | 要求 |
|---|---|
| `spec.awsRegion` | 操作者明确选择的 Region |
| `spec.cpu` | kubeconfig、EKS ARN、CPU HyperPod 名 |
| `spec.release` | `dist/current-release.json` 和 Agent config digest |
| `spec.runtimeProfile` | 可编辑template、不可变source快照、自动版本和稳定注册锚点 |
| `spec.nlb` | NLB 名、公共子网、Security Group、ACM certificate ARN |
| `spec.health` | Aurora、AMP、SNS 和健康阈值 |
| `spec.notifications` | 通知通道（`channel: sns` 默认 / `ses`）、管理员邮箱、Subject前缀和外部告警确认；`ses` 另有 sender 和 recipient 列表 |
| `spec.clusters[]` | 每集群唯一 ID、context、EKS ARN、HyperPod 名、IRSA、namespace allowlist、GPU 节点子网 `agentEndpointAllowedCidrs` |
| 管理员配置 | `state-dir/admin-config/desired.json`中的20项规范化非敏感配置和角色摘要 |
| 凭据引用 | 每集群 token 文件、CA 文件和受控 fleet master 文件 |

CLI逐层拒绝未知字段、错误类型、重复集群、跨Region ARN、非HTTPS URL和残留
`REPLACE_*`，并在私有目录生成低层release配置。管理员不维护这些文件。

当前版本仍通过受控文件引用 token、CA 和 fleet master。文件必须在仓库外，目录权限
`0700`、敏感文件权限 `0600`，不得进入 Git、普通日志或构建 artifact。

## 4. 首次部署门禁

首次ARN自动部署要求：

1. 一个已有的 3 节点 CPU EKS/HyperPod 集群。
2. 至少一个已有的 GPU EKS/HyperPod 集群，且 `NodeRecovery=None`。
3. GPU VPC 已有可用 NAT 出口。
4. 执行身份具有ECR、EC2、RDS、AMP、SNS、EKS、Kubernetes和IAM权限。
5. 部署机已安装Python 3.12项目环境以及`aws`、`cosign`、Docker Buildx、`kubectl`（≥1.28：release 引擎的等待循环用 `kubectl wait --for=jsonpath=...`（含不带值的字段存在性判断）和 `kubectl rollout status` 代替固定间隔 sleep）、`helm`、`curl`、`jq`、`openssl`、`sha256sum`和`make`；ARN入口在AWS mutation前验证这些命令，但不自动安装系统工具。

首次应用bootstrap的`spec.clusters`必须非空；只有已完成站点可通过正式
`remove-cluster`进入显式`[]`，新站点空列表会在首个Kubernetes apply前失败。

dirty工作区和clean个人commit不查询GitHub；只有干净`HEAD == origin/main`且没有本地
签名release时才尝试消费同commit main CI候选。凭据边界见[CI 发布流程](CI发布流程.md)。

ARN bootstrap创建或复用当前`site-id`独占的：

- Aurora Serverless v2 writer/reader、subnet group和SG；
- immutable runtime ECR与mutable BuildKit cache ECR repository；cache仓库保留当前
  `buildcache-linux-amd64`，未标记的历史cache artifact在7天后过期；
- NLB SG和GPU egress CIDR白名单；
- AMP workspace、Alertmanager、SNS topic 和邮件订阅；

EKS/HyperPod作为显式ARN输入；VPC/subnet/节点CIDR由集群发现。命令自动创建独立token、
CA、fleet master和kubeconfig文件。GPU VPC没有NAT出口时部署停止，不修改现有路由。
已有cache仓库缺少该生命周期策略时ARN入口会补齐；已有策略内容不同时部署fail closed，
不会静默扩大或改写清理范围。执行身份需要ECR lifecycle policy的读取和写入权限。
ARN入口是本方案唯一的站点AWS基础设施writer。source scan、preflight和集群检查都由
统一命令内部执行，任一必需检查失败时不会开始AWS或Kubernetes mutation。

## 6. 执行部署

首次执行第2节四参数命令，续跑和升级只传`--state-dir`；首次容量覆盖是可选第五输入。
首次执行创建资源并构建release；重复执行根据bootstrap state和site tag跳过已完成资源，
runtime image输入未变化时复用registry digest，相同release由rollout判定`NOOP`。
管理员不得改写release ID或组件摘要。
组件`release-diff`被明确分类为`NOOP`时，即使release ID只因delivery identity变化，
该入口也跳过deploy内的preflight和NOOP verifier，只登记新release state、并行执行一次
全量`verify`并保存报告且不等待稳定窗口；管理员运行`status`仍会重新查询实时状态。
deploy-host-only只更新部署机并执行只读preflight；测试/文档变化只执行影响门禁；两者
都不创建应用release、不访问GPU rollout或等待稳定窗口。

Runtime Profile策略变化时，本次deploy在应用发布前写出
`<state-dir>/release-deploy/profile-plan.json`并停止，停止信息直接打印下表字段和带真实
`plan_sha256`的续跑命令，不需要`jq`。完整操作、证据和异常分支见
[Runtime Profile变更审批](管理员Profile变更审批.md)。

| 字段 | 管理员核对内容 |
|---|---|
| `site_identity.site_name` | 是否为目标站点 |
| `site_identity.aws_region` | 是否为批准的Region |
| `site_identity.cpu_eks_arn` | 是否为该站点稳定CPU控制面 |
| `site_identity_sha256` | 上述可读身份的机器校验摘要 |
| `current_version` / `desired_version` | Profile版本迁移是否符合变更单 |
| `change_kind` / `changes[]` | capability、mode、owner、adapter变化及风险 |
| `live_profile_sha256` | 审批时的线上Profile baseline |
| `policy_digest` / `source_sha256` / `snapshot_sha256` | 目标策略、模板和候选快照证据 |
| `plan_sha256` | 整份已审核计划的审批绑定值，必须写入变更单并传回审批命令 |

把打印出的`plan_sha256`写入变更单；获得变更单或维护窗口批准后，原样执行停止信息
末尾的续跑命令，只把`CHG-<id>`换成真实变更单号：

```bash
gpu-fault-admin deploy \
  --state-dir /secure/gpu-fault \
  --approve-profile-plan <plan_sha256> \
  --reference CHG-12345
```

该命令先审批再继续同一部署。`--approve-profile-plan`只接受当前待审批计划的摘要：
没有`profile-plan.json`或摘要不一致时拒绝执行并给出当前待审批摘要，不能在第一次
deploy时携带。审批只对该计划有效：模板、目标策略或live baseline变化会使旧审批归档
失效并重新停止；发布失败且计划未变化时重跑`deploy --state-dir`即可续跑；完整verify、
stability和commit成功后活动审批被一次性消费。不要编辑
`profile-plan.json`、`profile-approval.json`或审批归档。

`deploy` 会再次执行 live preflight，避免检查后环境发生漂移，然后：
1. 没有 release state 时执行首次 bootstrap。
2. 已有 release state 时比较Manifest v3中的wheel/bundle、渲染后Manifest、
   renderer/dependency lock、image digest、schema、协议、Profile、endpoint和集群集合。
   四类change kind只作摘要，实际由组件DAG选择路径；CPU分别维护ingress、worker和
   spool Manifest摘要，单角色变化只等待该角色。finalize仅在pin实际变化时滚动CPU。
   Profile 使用规范化策略摘要比较；仅路径或 YAML 顺序变化不触发 `FULL`。
3. 失败的 bootstrap state 会重新执行幂等 bootstrap。
4. 按需上传三个内容寻址 wheel 和 Node bundle；涉及GPU或Node Runtime时，用server-side dry-run和逐节点只读host probe完成`candidate-preflight-ready`，与schema/registry/CPU候选阶段并行，数据面前汇合。
5. schema 变化时依次执行 index-build、v12 ensure、schema preflight 三个 Job；preflight 不过即停；schema 版本变化只能 fail-forward：同一条 deploy 加 `--accept-schema-change`，引擎先打 Aurora 快照，`site.yaml` 不动。
6. 部署CPU三层控制面（候选兼容窗口）并核对Profile，等待Agent心跳；随后NLB endpoint与节点只读预检并行，可观测性与数据面波次并行。节点波次前复检Node、Executor、命令、workflow和lease。
7. 验证私有 hosted zone 存在、ACM certificate 为 `ISSUED`、SAN 覆盖控制面域名，
   然后创建 NLB Service。
8. 严格等待 NLB `state=active`、TLS 443 listener 使用目标证书、原始 NLB DNS
   可解析，并且三个 API Pod target 全部为 `healthy`。
9. 只有上述门禁通过后才 `UPSERT` 私有 CNAME，并等待 Route53 change 明确变为
   `INSYNC`。
10. 首次部署只把第一个GPU集群作为站点基线写入CPU registry并收敛；其余目标不预创建
   token、IAM、Private Hosted Zone VPC关联或数据面资源。
11. 其余GPU集群随后作为独立join事务最多4路接入并受全局64节点Installer预算约束；
    共享release升级默认逐集群串行，`spec.release.upgradeMaxParallelClusters`
    （默认1、上限8）才允许并行，首个集群先作为金丝雀单独完成。任一集群失败立即阻止尚未开始的集群并记录`failed_cluster_ids`与`not_started_cluster_ids`；
    单集群Executor未Ready、Agent安全门或收敛超时、Installer失败进入`PAUSED`可续跑，全局故障才自动回滚且始终逆序串行恢复。
12. Profile变化finalize前要求旧Profile workflow/workload归零。
13. bootstrap/quick证据仅在绑定当前release state且十分钟内复用（含deploy已完成但未commit的quick
    证据），不匹配时补跑。verify与稳定窗口并行；仅`GpuFaultStoreIoRejected`可等待最多420秒，随后仍
    观察120至300秒稳定窗口，队列趋势按相对增幅判定，数据面刚收敛后600秒内Collector类critical不计入。

`plan/status` 会显示下一次部署分类：`NOOP` 只做一次并行只读验证；`CONTROL_PLANE_ONLY`
只滚CPU；`DATA_PLANE_COMPATIBLE`只滚变化的数据面且跨GPU集群默认串行；`FULL`保留两阶段
pin。`plan`输出直接写出本站点生效的集群并行度；最多4路只属于首次部署后的独立batch join。
升级失败时，重新执行同一条`deploy`会复用持久化差异计划：仍处于`failed`的同一
release按checkpoint续跑；已经完成并验证自动回滚的`rolled-back`状态从当前线上基线
开启新事务，因此修复代码后生成的新release不会错误续用旧release ID。

任一阶段失败都会停止后续阶段。特别是，NLB target 未健康时不会发布新 CNAME；
Route53 未 `INSYNC` 或 GPU Pod 的 DNS/TLS 验证失败时不会启动首次部署或重新加入流程
中的 Executor。重新执行同一条 `deploy` 命令会从幂等状态继续。

管理员不得在该命令运行期间执行 CPU-4、REG-1～8 或在线
`kubectl edit/set env/apply`。

## 7. 部署后验证

统一命令成功返回前已经完成完整verify和稳定窗口，包括：

- CPU 三层角色、PDB、ADOT 和 Aurora refresh CronJob；
- Runtime Profile 已注册且内容无漂移；
- GPU Executor IRSA、Secret、wheel 和 adapter 开关；
- Executor 真实 readiness、TLS 私有 CA；
- Agent ACTIVE、Fleet readiness 和 Collector freshness；
- remote command 积压年龄和内部错误；
- NLB TLS listener、certificate 和三个健康 target；
- Aurora writer/reader；
- AMP rule namespace、Alertmanager 和已确认 SNS subscription。

然后按[区域部署验收清单](部署和运维手册.md#reg-8-区域部署验收清单)执行生产验收，并用
不同 job/attempt ID 分别验证：

```bash
SITE_FILE=/secure/gpu-fault/site.yaml

gpu-training-submit customer-job.yaml \
  --site "${SITE_FILE}" \
  --job-id deployment-smoke-direct \
  --attempt-number 1

gpu-fault-workload-annotate customer-job.yaml \
  --site "${SITE_FILE}" \
  --job-id deployment-smoke-reviewed \
  --attempt-number 1 \
  --output /tmp/customer-job.managed.yaml

kubectl apply --dry-run=server -f /tmp/customer-job.managed.yaml
kubectl apply -f /tmp/customer-job.managed.yaml
```

两次训练均被 Watcher 正确观测后，才能按阶段 A～D 开放破坏性能力。

## 8. 失败处理

| 场景 | 处理 |
|---|---|
| 邮件未确认（退出码2，第一分钟内） | 点击SNS确认邮件里的链接（`channel: ses` 的站点还要点SES验证邮件），原样重跑打印的命令；或加`--wait-for-email-confirmation <分钟>` |
| 内部preflight失败 | 按检查名称修复源码、凭据或共享基础设施，不修改集群 |
| ARN bootstrap失败 | 保留私有state目录，重跑`deploy --state-dir`；已完成资源会跳过 |
| release build失败 | 只保留已创建ECR，修复源码/门禁/凭据后重跑同一命令 |
| 首次应用部署失败 | 查看 release state；自动 fail-closed 后修复原因，再重跑 `gpu-fault-admin deploy` |
| verify/stability失败 | 不进入生产流量或破坏性能力阶段；修复后重跑`deploy --state-dir` |
| 提示加`--supersede-failed-transaction`/`--accept-schema-change` | 构建一结束即拒绝；确认后把该参数加到同一条deploy上重跑（参数优先于残留环境变量） |
| Profile计划等待审批 | 审核打印的计划字段，执行停止信息给出的`deploy --approve-profile-plan`续跑命令 |
| Profile计划或live baseline漂移 | 旧审批已归档失效；审核新计划并重新审批 |
| Profile 同版本内容不同 | 不得覆盖，发布新的 profile version |

不得用降低 readiness、扩大 allowlist、关闭签名或跳过 TLS 来让部署变绿。
升级中断、Agent未收敛、Executor verifier失败等上线后处置见
[管理员日常运维](管理员日常运维.md)的区域升级和按症状排障章节。

## 9. 上线证据

每次生产部署至少保存：

- release manifest、三个组件wheel/Node bundle SHA和`module_digest`，以及runtime image内control-plane/executor隔离venv与对应component摘要；
- site YAML 摘要和生成配置摘要，不包含 Secret 内容；
- `deploy` 和 `status --full` 输出（含 deploy 内部的 preflight/verify 报告）；
- CPU/GPU verifier 结果；
- Runtime Profile version 和有效 capability；
- Profile计划摘要、审批引用和`CONSUMED`/`SUPERSEDED`审计，不复制Secret内容；
- NLB/TLS、Aurora refresh、AMP/SNS、CAP-005 零 skip 和安装资源注册表摘要；
- 训练 smoke 的 job/attempt ID；
- 变更单号、维护窗口和操作者。

证据捕获命令和脱敏要求见[部署和运维手册](部署和运维手册.md)。
