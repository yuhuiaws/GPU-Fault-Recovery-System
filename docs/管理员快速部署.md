# GPU 故障处理系统管理员快速部署

本文只描述区域生产方案的首次建站或应用层重建成功路径。管理员提供已有CPU/GPU
EKS或HyperPod ARN，单个命令自动创建站点AWS资源、构建签名release并部署应用。
该路径不要求管理员按 CPU-1～9、REG-1～8 手工拼接命令，也不编写或逐个 apply
方案 Manifest。需要逐对象审计、共享基础设施特殊处理或 break-glass 时，转到
[部署和运维手册](部署和运维手册.md)；上线后的升级、集群变更、轮换、排障和退役统一
使用[管理员日常运维](管理员日常运维.md)。

## 1. 适用范围

唯一生产形态为：

```text
区域 CPU EKS 控制面 + Aurora PostgreSQL + TLS NLB
                    |
                    +-- HyperPod EKS GPU 集群 A
                    +-- HyperPod EKS GPU 集群 B
                    +-- ...
```

受管 GPU HyperPod 必须为 EKS 编排且 `NodeRecovery=None`。通用 Kubernetes、
HyperPod Slurm 和单集群一体化不属于新生产部署路径。

## 2. 当前管理员入口

首次部署、失败续跑和后续升级入口完全相同：

```bash
gpu-fault-admin deploy \
  --cpu-cluster-arn <cpu-eks-or-hyperpod-arn> \
  --gpu-cluster-arn <gpu-eks-or-hyperpod-arn> \
  --state-dir /secure/gpu-fault \
  --admin-email <operations-email>
```

多个GPU集群重复传`--gpu-cluster-arn`。管理员不提供release-ref、artifact、site、
release-build/release-deploy、bundle或venv路径。命令自动创建或复用签名材料和
site-tagged ECR、运行所需门禁、push并验签release，再创建或复用
Aurora、AMP/SNS/SQS、PKI/IAM等资源。
EKS/HyperPod 自身的 VPC和基础路由属于已建集群的一部分。GPU VPC必须已有可用 NAT
出口；CPU VPC缺少NLB公网子网时，脚本会从空闲CIDR创建两个方案专属 `/28` 子网。

部署前先按[CI 发布流程](CI发布流程.md)的bundle规则安装并激活`gpu-fault-admin`。首次命令从当前
受信checkout确定源码根目录，后续由内部state恢复；生成的site和repository路径不进入
公共参数。

| 内部阶段 | 含义 |
|---|---|
| source preparation | 固定Git身份，准备或复用签名release和部署环境 |
| preflight | 只读检查AWS身份、集群、IAM、容量、Aurora、LBC、ACM和监控 |
| bootstrap/upgrade | 没有站点时创建，已有站点时先验证集群身份再升级 |
| verify/stability | 验证CPU/GPU、Profile、TLS、Agent、Aurora和稳定窗口 |

## 3. 部署前输入

首次ARN命令在state中生成权限`0600`的内部`RegionalSite`，作为应用拓扑、身份、制品和
健康检查事实源。管理员不手工创建、编辑或传入该文件。内部内容包括：

| 配置 | 要求 |
|---|---|
| `spec.awsRegion` | 操作者明确选择的 Region |
| `spec.cpu` | kubeconfig、EKS ARN、CPU HyperPod 名 |
| `spec.release` | `dist/current-release.json` 和 Agent config digest |
| `spec.runtimeProfile` | 可编辑template、不可变source快照、自动版本和稳定注册锚点 |
| `spec.nlb` | NLB 名、公共子网、Security Group、ACM certificate ARN |
| `spec.health` | Aurora、AMP、SNS 和健康阈值 |
| `spec.notifications` | 管理员邮箱、SES sender、recipient列表、Subject前缀和外部告警确认 |
| `spec.clusters[]` | 每集群唯一 ID、context、EKS ARN、HyperPod 名、IRSA、namespace allowlist、GPU 节点子网 `agentEndpointAllowedCidrs` |
| 凭据引用 | 每集群 token 文件、CA 文件和受控 fleet master 文件 |

CLI逐层拒绝未知字段、错误类型、重复集群、跨Region ARN、非HTTPS URL和残留
`REPLACE_*`，并在私有目录生成低层release配置。管理员不维护这些文件。

当前版本仍通过受控文件引用 token、CA 和 fleet master。文件必须在仓库外，目录权限
`0700`、敏感文件权限 `0600`，不得进入 Git、普通日志或构建 artifact。

## 4. 首次部署门禁

首次ARN自动部署要求：

1. 一个已有的 3 节点 CPU EKS/HyperPod 集群。
2. 至少一个已有的 GPU EKS/HyperPod 集群，且 `NodeRecovery=None`。
3. GPU VPC 已有可用 NAT 出口。
4. 执行身份具有ECR、EC2、RDS、AMP、SNS、SQS、EKS、Kubernetes和IAM权限。
5. 部署机已安装Python 3.12项目环境以及`aws`、`cosign`、Docker Buildx、`kubectl`、`helm`、`curl`、`jq`、`openssl`、`sha256sum`和`make`；ARN入口在AWS mutation前验证这些命令，但不自动安装系统工具。

首次应用bootstrap的`spec.clusters`必须非空；只有已完成站点可通过正式
`remove-cluster`进入显式`[]`，新站点空列表会在首个Kubernetes apply前失败。

ARN bootstrap创建或复用当前`site-id`独占的：

- Aurora Serverless v2 writer/reader、subnet group和SG；
- immutable runtime ECR与mutable BuildKit cache ECR repository；cache仓库保留当前
  `buildcache-linux-amd64`，未标记的历史cache artifact在7天后过期；
- NLB SG和GPU egress CIDR白名单；
- AMP workspace、Alertmanager、SNS topic和持久SQS接收队列；

EKS/HyperPod作为显式ARN输入；VPC/subnet/节点CIDR由集群发现。命令自动创建独立token、
CA、fleet master和kubeconfig文件。GPU VPC没有NAT出口时部署停止，不修改现有路由。
已有cache仓库缺少该生命周期策略时ARN入口会补齐；已有策略内容不同时部署fail closed，
不会静默扩大或改写清理范围。执行身份需要ECR lifecycle policy的读取和写入权限。
ARN入口是本方案唯一的站点AWS基础设施writer。

## 5. 本地检查

执行部署前确认系统工具和AWS身份可用。其余source scan、release preflight和集群检查由
统一命令内部执行；任一必需检查失败时不会开始AWS或Kubernetes mutation。

## 6. 执行部署

执行第2节四参数命令。首次执行创建资源并构建release；重复执行根据bootstrap state和
site tag跳过已完成资源，
runtime image输入未变化时复用registry digest，相同release由rollout判定`NOOP`。
管理员不得改写release ID或组件摘要。
同release ID被明确分类为`NOOP`时，该入口跳过deploy内的preflight和NOOP verifier，
只并行执行一次全量`verify`并保存报告，且不等待稳定窗口；管理员主动运行`status`
仍会重新查询实时状态。

Runtime Profile策略变化时，本次deploy在应用发布前写出
`<state-dir>/release-deploy/profile-plan.json`并停止。该文件的管理员审核字段为：
完整操作、证据和异常分支见[Runtime Profile变更审批](管理员Profile变更审批.md)。

| 字段 | 管理员核对内容 |
|---|---|
| `site_identity.site_name` | 是否为目标站点 |
| `site_identity.aws_region` | 是否为批准的Region |
| `site_identity.cpu_eks_arn` | 是否为该站点稳定CPU控制面 |
| `site_identity_sha256` | 上述可读身份的机器校验摘要 |
| `current_version` / `desired_version` | Profile版本迁移是否符合变更单 |
| `change_kind` / `changes[]` | capability、mode、owner、adapter变化及风险 |
| `live_profile_sha256` | 审批时的线上Profile baseline |
| `policy_digest` / `source_sha256` / `snapshot_sha256` | 目标策略、模板和候选快照证据 |
| `plan_sha256` | 整份已审核计划的审批绑定值，必须写入变更单并传回审批命令 |

先查看并记录计划SHA：

```bash
STATE_DIR=/secure/gpu-fault
PLAN_FILE="${STATE_DIR}/release-deploy/profile-plan.json"
jq '{
  site_identity,
  versions: {current: .current_version, desired: .desired_version},
  change_kind, changes, live_profile_sha256,
  policy_digest, source_sha256, snapshot_sha256,
  plan_sha256
}' "${PLAN_FILE}"
PLAN_SHA256="$(jq -er '.plan_sha256' "${PLAN_FILE}")"
```

获得变更单或维护窗口批准后执行：

```bash
gpu-fault-admin approve-profile \
  --state-dir "${STATE_DIR}" \
  --plan-sha256 "${PLAN_SHA256}" \
  --reference CHG-12345
```

随后重新执行第2节完全相同的四参数deploy。审批只对该计划有效：模板、目标策略或live
baseline变化会使旧审批归档失效；发布失败且计划未变化时可直接续跑；完整verify、
stability和commit成功后活动审批被一次性消费。不要编辑
`profile-plan.json`、`profile-approval.json`或审批归档。

`deploy` 会再次执行 live preflight，避免检查后环境发生漂移，然后：

1. 没有 release state 时执行首次 bootstrap。
2. 已有 release state 时比较Manifest v3中的wheel/bundle、渲染后Manifest、
   renderer/dependency lock、image digest、schema、协议、Profile、endpoint和集群集合。
   四类change kind只作摘要，实际由组件DAG选择受影响路径。
   finalize 仅在 required/compatible pin 的实际内容变化时滚动 CPU。
   Profile 使用规范化策略摘要比较；仅路径或 YAML 顺序变化不触发 `FULL`。
3. 失败的 bootstrap state 会重新执行幂等 bootstrap。
4. 按需上传三个内容寻址 wheel 和 Node bundle；schema 变化时执行 v7 ensure Job。
5. 部署 CPU 三层控制面并核对区域 Runtime Profile。
6. 验证私有 hosted zone 存在、ACM certificate 为 `ISSUED`、SAN 覆盖控制面域名，
   然后创建 NLB Service。
7. 严格等待 NLB `state=active`、TLS 443 listener 使用目标证书、原始 NLB DNS
   可解析，并且三个 API Pod target 全部为 `healthy`。
8. 只有上述门禁通过后才 `UPSERT` 私有 CNAME，并等待 Route53 change 明确变为
   `INSYNC`。
9. 对每个 GPU 集群先保持 Executor 未启动，由临时 Pod 使用连接 Secret 中的私有 CA
   完成 CNAME DNS 解析、TLS hostname/证书链和 `/healthz` HTTP 200 验证。
10. GPU Pod 门禁成功后才启动DAG选中的Executor、Watcher、Resource Collector或
    Reconciler；Node Runtime按Fleet waves和`max_unavailable`推进。
11. Profile变化finalize前要求旧Profile workflow/workload归零。
12. 先运行change-specific quick gate，再运行一次完整verify；实际变更继续观察
    120至300秒稳定窗口，检查重启、队列、远程命令和critical alerts。

`plan/status` 会显示下一次部署分类：`NOOP` 快速路径只做一次并行只读验证；
`CONTROL_PLANE_ONLY` 只滚 CPU；`DATA_PLANE_COMPATIBLE` 只滚变化的数据面并最多并行
处理4个互不依赖的GPU集群；`FULL`仍保留两阶段pin，但不会无条件重做全部组件。
升级失败或已自动回滚
时，重新执行同一条 `deploy` 会复用持久化差异计划续跑。

任一阶段失败都会停止后续阶段。特别是，NLB target 未健康时不会发布新 CNAME；
Route53 未 `INSYNC` 或 GPU Pod 的 DNS/TLS 验证失败时不会启动首次部署或重新加入流程
中的 Executor。重新执行同一条 `deploy` 命令会从幂等状态继续。

管理员不得在该命令运行期间执行 CPU-4、REG-1～8 或在线
`kubectl edit/set env/apply`。

## 7. 部署后验证

统一命令成功返回前已经完成完整verify和稳定窗口，包括：

- CPU 三层角色、PDB、ADOT 和 Aurora refresh CronJob；
- Runtime Profile 已注册且内容无漂移；
- GPU Executor IRSA、Secret、wheel 和 adapter 开关；
- Executor 真实 readiness、TLS 私有 CA；
- Agent ACTIVE、Fleet readiness 和 Collector freshness；
- remote command 积压年龄和内部错误；
- NLB TLS listener、certificate 和三个健康 target；
- Aurora writer/reader；
- AMP rule namespace、Alertmanager 和已确认 SNS subscription。

然后按[区域部署验收清单](部署和运维手册.md#reg-8-区域部署验收清单)执行生产验收，并用
不同 job/attempt ID 分别验证：

```bash
SITE_FILE=/secure/gpu-fault/site.yaml

gpu-training-submit customer-job.yaml \
  --site "${SITE_FILE}" \
  --job-id deployment-smoke-direct \
  --attempt-number 1

gpu-fault-workload-annotate customer-job.yaml \
  --site "${SITE_FILE}" \
  --job-id deployment-smoke-reviewed \
  --attempt-number 1 \
  --output /tmp/customer-job.managed.yaml

kubectl apply --dry-run=server -f /tmp/customer-job.managed.yaml
kubectl apply -f /tmp/customer-job.managed.yaml
```

两次训练均被 Watcher 正确观测后，才能按阶段 A～D 开放破坏性能力。

## 8. 失败处理

| 场景 | 处理 |
|---|---|
| 内部preflight失败 | 按检查名称修复源码、凭据或共享基础设施，不修改集群 |
| ARN bootstrap失败 | 保留私有state目录，以相同ARN和参数重跑；已完成资源会跳过 |
| release build失败 | 只保留已创建ECR，修复源码/门禁/凭据后重跑同一命令 |
| 首次应用部署失败 | 查看 release state；自动 fail-closed 后修复原因，再重跑 `gpu-fault-admin deploy` |
| verify/stability失败 | 不进入生产流量或破坏性能力阶段；修复后重跑同一四参数命令 |
| Profile计划等待审批 | 审核`profile-plan.json`，执行`approve-profile`，再重跑原四参数命令 |
| Profile计划或live baseline漂移 | 旧审批已归档失效；审核新计划并重新审批 |
| Profile 同版本内容不同 | 不得覆盖，发布新的 profile version |

不得用降低 readiness、扩大 allowlist、关闭签名或跳过 TLS 来让部署变绿。
升级中断、Agent未收敛、Executor verifier失败等上线后处置见
[管理员日常运维](管理员日常运维.md)的区域升级和按症状排障章节。

## 9. 上线证据

每次生产部署至少保存：

- release manifest、三个组件wheel/Node bundle SHA和`module_digest`，以及runtime image内control-plane/executor隔离venv与对应component摘要；
- site YAML 摘要和生成配置摘要，不包含 Secret 内容；
- `preflight`、`deploy`、`verify` 和 `status` 输出；
- CPU/GPU verifier 结果；
- Runtime Profile version 和有效 capability；
- Profile计划摘要、审批引用和`CONSUMED`/`SUPERSEDED`审计，不复制Secret内容；
- NLB/TLS、Aurora refresh、AMP/SNS、CAP-005 零 skip 和安装资源注册表摘要；
- 训练 smoke 的 job/attempt ID；
- 变更单号、维护窗口和操作者。

可使用：

```bash
python3.12 scripts/capture_release_evidence.py \
  --release-id "${RELEASE_ID}" \
  --phase after \
  --cpu-kubeconfig "${CPU_KUBECONFIG}" \
  --gpu-context "${GPU_EKS_CONTEXT}"
```

## 10. 后续运维入口

首次部署、训练smoke和上线证据完成后，本文件的任务结束。后续操作统一进入
[管理员日常运维](管理员日常运维.md)：

| 后续任务 | 日常运维章节 |
|---|---|
| 健康巡检和重复验收 | 常用任务入口 |
| 区域升级、续跑和回滚 | 区域升级 |
| 接入或移除GPU集群 | `gpu-fault-admin join-cluster/remove-cluster` |
| token、证书和节点key轮换 | 凭据和证书生命周期 |
| Agent、Executor、队列或provider故障 | 按症状排障 |
| 数据迁移、归档和purge | 数据与审计维护 |
| 保留集群重装、完整卸载或永久退役 | 完整卸载或永久退役 |
| 当前能力边界和待产品化命令 | 当前待产品化命令 |

本文件不重复卸载状态机、旧环境发现、集群移除或路线图。所有退役模式都必须遵守一个
不变量：任何方案卸载命令都不得删除GPU EKS或GPU HyperPod集群。
