# GPU Fault 扩展指南

本指南定义新增代码能力时的登记点与必须通过的门禁。目标是避免“代码能运行，
但因为漏改一个集合而静默获得默认语义”。

扩展一旦新增生产 Manifest、systemd unit、AWS 资源、配置、凭据或管理员命令，必须
继续执行[开发者部署实现](开发者部署实现.md)。生产交付和卸载契约只在该文件维护，
本指南不再重复。

## 1. 新增 Workflow Operation

1. 在 `models.WorkflowOperation` 增加枚举成员。
2. 在 `operation_registry.OPERATION_REGISTRY` 增加完整语义行：
   capability、scope、destructive、rank、adapter、资源锁、DAG、preempt
   与 barrier；以及下列判定用字段：
   - `preemption_non_cancelable`：已下发后不可撤单。
   - `hardware_escalation_relevant`：可作为硬件升级的尝试证据。
   - `host_proc_root_dependent`：需要宿主 `/proc` 挂载，Node Agent
     启动时校验运行时路径（`HOST_PROC_ROOT_OPERATIONS`）。
   - `maintenance_generation_scoped`：NodeAction 必须继承 quiesce 时
     捕获的 maintenance generation，而不是读活的 fleet endpoint
     （`MAINTENANCE_GENERATION_OPERATIONS`）。
   - `planning_only`：不落到任何 adapter，仅参与编排决策。
   `destructive` 之外还派生出 `CONTAINMENT_ONLY_OPERATIONS`
   （`resource_claims` 只有 `SCHEDULER_MUTATION`，即 cordon/quarantine/
   恢复调度）与 `NODE_MUTATING_OPERATIONS`（其余 destructive 操作）。
   boot generation fence 与 workload_state UNKNOWN 两处闸门只看后者：
   因为证据过期或工况未知就拒绝隔离，等于把可疑节点留在可调度状态。
3. 在目标 adapter 实现执行逻辑。`OPERATIONS` 自动从registry派生，
   不得再维护独立集合；成员超过三个的派生集合不得在调用点重列字面量，
   `tests/test_registry_contracts.py` 会扫描 AST 拒绝重复。
4. 增加策略、workflow builder、adapter与负向测试。
5. 运行 `tests/test_operation_registry.py` 和
   `tests/test_registry_contracts.py`。漏登记会在import时直接失败。
6. 部署前运行 `gpu-fault-config validate`，检查生成 Manifest、控制面白名单和
   Node Agent 白名单。该命令不读取 Runtime Profile；Profile claim、observed
   capability 和 owner 一致性由 `tests/regional/test_capabilities.py`、区域发布
   verifier 和 `gpu-fault-admin verify` 检查。
7. 插件加载不代表自动授权：adapter仍必须匹配 operation registry、控制面
   allowlist 和 Runtime Profile。

动态插件不能增加新的 `WorkflowOperation` 枚举值。外部adapter只能为已有操作
提供实现；新增核心操作必须经过上述核心registry审阅。

## 2. 新增 Collector / Processor Channel

1. 在 `channel_registry.CHANNEL_REGISTRY` 登记path、priority模式、pool、
   lane、spool、edge filter、latest-wins与routine reason词汇。
2. 使用registry导出的path常量创建FastAPI路由与Collector sink调用。
3. 增加route和processor测试。应用启动会比较所有
   `/v1/collector-events/*`路由与registry，漏登记直接失败。
4. 新baseline拼写必须加入该channel的`routine_reasons`或prefix，
   不得在collector里私自创造同义词。

## 3. 支持新GPU产品族

产品族映射来自生成器，不直接编辑
`src/gpu_fault/data/nvidia-xid-catalog-610.generated.yaml`。在
`tools/generate_nvidia_xid_policy.py` 的生成输入中增加：

```yaml
spec:
  catalog:
    productFamilies:
      - family: Z100
        modelPrefixes: [Z]
```

不需要修改Python正则。未知产品会产生
`gpu_fault_policy_unknown_product_total{product=...}`并触发
`GpuFaultUnknownProductFamily`，自动恢复保持fail-closed。

使用经过审批且摘要固定的 NVIDIA Catalog XLSX 重新生成后，更新固定 source/generated
SHA 测试并运行：

```bash
make PYTHON=.venv/bin/python xid-catalog-check
```

Catalog 属于 wheel 内的 packaged data；变化会改变 `module_digest()`，必须完整重建
release，而不是在线替换文件。

## 4. 新增Store Domain或后端

1. 在`store/contracts.py`用具体模型类型扩展Protocol，禁止`Any`。
2. 三个实现显式实现或显式继承该方法。
3. 将行为加入共享contract fixture；配置PostgreSQL URL时Memory、SQLite、
   PostgreSQL必须运行同一测试。
4. 运行mypy边界检查、override shape检查和真实PostgreSQL测试。

## 5. 新增Schema迁移

1. 修改`store/postgres/ddl.py`中的最新幂等schema。
2. 计算新的DDL source SHA-256。
3. 在 `src/gpu_fault/schema_migrations.py` 的
   `POSTGRES_SCHEMA_MIGRATIONS` 追加连续版本，不得修改历史行。
4. 需要回填、类型变更等步骤时提供`apply(cursor)`回调。
5. 未增加migration直接修改DDL会在import时失败。

## 6. 新增通知Builder、Adapter或Sink

项目声明以下 entry-point 组：

- `gpu_fault.collector_sinks`
- `gpu_fault.workflow_adapters`
- `gpu_fault.notification_builders`
- `gpu_fault.metric_contributors`

同组同名插件由 `gpu_fault.plugins.discover_plugins()` fail-closed。目前只有
`gpu_fault.metric_contributors` 会由运行时自动发现并装配。

Collector sink、Workflow adapter 和 Notification builder 仍由各自 factory/registry
静态装配。外部包只声明 entry point 不会自动生效；新增这三类扩展时还必须显式接入
对应装配点、配置选择和测试。不得把“entry point 已安装”当成生产可用证明。

## 7. 新增 HTTP 路由

每个FastAPI handler必须显式添加：

```python
@router.post("/v1/example")
@authorization_bucket("execution-token")
async def example(...):
    ...
```

允许的bucket只有`public`、`metrics`、`cluster-token`、
`dual-credential`和`execution-token`。目录前缀不会继承权限；
遗漏声明会在应用启动时失败。

如果请求schema包含集群身份，字段名必须登记在
`app.cluster_binding.CLUSTER_IDENTIFIER_FIELDS`。当前支持
`cluster_id`、`clusterId`和`cluster`，所有嵌套值都会与认证集群
绑定。

## 8. 生产交付衔接

代码扩展出现以下任一变化时，继续执行
[开发者部署实现](开发者部署实现.md)：

- 新增或修改 Kubernetes Manifest、renderer、systemd unit 或容器镜像；
- 新增 `site.yaml` 字段、环境变量、Secret、IAM 或其他 AWS 资源；
- 改变 Runtime Profile、Agent/Executor protocol 或 required/compatible pin；
- 新增管理员命令、部署步骤、清理阶段或不可逆动作；
- 需要进入 `preflight/deploy/verify/status/remove-cluster/uninstall`。

生产交付必须覆盖三层资源事实源：

1. Kubernetes `gpu-fault-installed-resources`；
2. 节点 `/opt/gpu-fault/installed-units.txt`；
3. Aurora `installation_resource` AWS 注册表。

扩展指南只决定“能力登记在哪里”；开发者部署实现决定“如何生成、发布、验证、回滚和
卸载”。两类变化同时存在时，两份文档的门禁都必须执行。

## 9. 新增 Metrics

为子系统实现一个metric lines contributor并注册到metrics registry，不得继续向
核心渲染函数追加字符串块。若指标用于AMP告警，还必须同时：

1. 加入ADOT keep regex；
2. 在 `deploy/observability/amp-rules.yaml` 增加生产规则；
3. 在 `deploy/control-plane/regional/processor-alerts.yaml` 保持可选
   Prometheus Operator 路径的规则等价；
4. 运行 `tests/regional/test_production_safety_config.py` 的告警可达性测试。

区域生产控制面默认不运行 Prometheus Operator，因此只修改
`processor-alerts.yaml` 等于没有生产告警；AMP规则和ADOT keep白名单才是正常路径。
