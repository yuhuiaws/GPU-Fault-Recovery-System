# GPU Fault 扩展指南

本指南定义新增功能时的唯一登记点与必须通过的门禁。目标是避免“代码能运行，
但因为漏改一个集合而静默获得默认语义”。

## 1. 新增 Workflow Operation

1. 在 `models.WorkflowOperation` 增加枚举成员。
2. 在 `operation_registry.OPERATION_REGISTRY` 增加完整语义行：
   capability、scope、destructive、rank、adapter、资源锁、DAG、preempt
   与 barrier；以及下列判定用字段：
   - `preemption_non_cancelable`：已下发后不可撤单。
   - `hardware_escalation_relevant`：可作为硬件升级的尝试证据。
   - `host_proc_root_dependent`：需要宿主 `/proc` 挂载，Node Agent
     启动时校验运行时路径（`HOST_PROC_ROOT_OPERATIONS`）。
   - `maintenance_generation_scoped`：NodeAction 必须继承 quiesce 时
     捕获的 maintenance generation，而不是读活的 fleet endpoint
     （`MAINTENANCE_GENERATION_OPERATIONS`）。
   - `planning_only`：不落到任何 adapter，仅参与编排决策。
   `destructive` 之外还派生出 `CONTAINMENT_ONLY_OPERATIONS`
   （`resource_claims` 只有 `SCHEDULER_MUTATION`，即 cordon/quarantine/
   恢复调度）与 `NODE_MUTATING_OPERATIONS`（其余 destructive 操作）。
   boot generation fence 与 workload_state UNKNOWN 两处闸门只看后者：
   因为证据过期或工况未知就拒绝隔离，等于把可疑节点留在可调度状态。
3. 在目标 adapter 实现执行逻辑。`OPERATIONS` 自动从registry派生，
   不得再维护独立集合；成员超过三个的派生集合不得在调用点重列字面量，
   `tests/test_registry_contracts.py` 会扫描 AST 拒绝重复。
4. 增加策略、workflow builder、adapter与负向测试。
5. 运行 `tests/test_operation_registry.py` 和
   `tests/test_registry_contracts.py`。漏登记会在import时直接失败。
6. 部署前运行 `gpu-fault-config validate`，确认控制面、节点操作白名单与
   Runtime Profile 一致。插件加载不代表自动授权：adapter仍必须匹配operation
   registry与runtime profile。

动态插件不能增加新的 `WorkflowOperation` 枚举值。外部adapter只能为已有操作
提供实现；新增核心操作必须经过上述核心registry审阅。

## 2. 新增 Collector / Processor Channel

1. 在 `channel_registry.CHANNEL_REGISTRY` 登记path、priority模式、pool、
   lane、spool、edge filter、latest-wins与routine reason词汇。
2. 使用registry导出的path常量创建FastAPI路由与Collector sink调用。
3. 增加route和processor测试。应用启动会比较所有
   `/v1/collector-events/*`路由与registry，漏登记直接失败。
4. 新baseline拼写必须加入该channel的`routine_reasons`或prefix，
   不得在collector里私自创造同义词。

## 3. 支持新GPU产品族

只修改固定XID catalog中的：

```yaml
spec:
  catalog:
    productFamilies:
      - family: Z100
        modelPrefixes: [Z]
```

不需要修改Python正则。未知产品会产生
`gpu_fault_policy_unknown_product_total{product=...}`并触发
`GpuFaultUnknownProductFamily`，自动恢复保持fail-closed。

## 4. 新增Store Domain或后端

1. 在`store/contracts.py`用具体模型类型扩展Protocol，禁止`Any`。
2. 三个实现显式实现或显式继承该方法。
3. 将行为加入共享contract fixture；配置PostgreSQL URL时Memory、SQLite、
   PostgreSQL必须运行同一测试。
4. 运行mypy边界检查、override shape检查和真实PostgreSQL测试。

## 5. 新增Schema迁移

1. 修改`store/postgres/ddl.py`中的最新幂等schema。
2. 计算新的DDL source SHA-256。
3. 在`POSTGRES_SCHEMA_MIGRATIONS`追加连续版本，不得修改历史行。
4. 需要回填、类型变更等步骤时提供`apply(cursor)`回调。
5. 未增加migration直接修改DDL会在import时失败。

## 6. 新增通知Builder、Adapter或Sink

包可通过以下entry-point组发布扩展：

- `gpu_fault.collector_sinks`
- `gpu_fault.workflow_adapters`
- `gpu_fault.notification_builders`
- `gpu_fault.metric_contributors`

使用`gpu_fault.plugins.discover_plugins()`发现插件。同组同名插件会fail-closed。

## 7. 新增 HTTP 路由

每个FastAPI handler必须显式添加：

```python
@router.post("/v1/example")
@authorization_bucket("execution-token")
async def example(...):
    ...
```

允许的bucket只有`public`、`metrics`、`cluster-token`、
`dual-credential`和`execution-token`。目录前缀不会继承权限；
遗漏声明会在应用启动时失败。

如果请求schema包含集群身份，字段名必须登记在
`app.cluster_binding.CLUSTER_IDENTIFIER_FIELDS`。当前支持
`cluster_id`、`clusterId`和`cluster`，所有嵌套值都会与认证集群
绑定。

## 8. 新增需要部署和卸载的生产组件

本节只面向方案开发者。管理员和客户不编写、不逐个 apply 方案 Manifest；他们只使用
已经生成和测试的 release，通过区域 rollout 入口部署。

### 8.1 新增 Kubernetes 组件

1. 将 GPU 源 Manifest 放在 `deploy/dataplane/`；可选组件放在
   `deploy/dataplane/optional/`。CPU 组件修改
   `deploy/control-plane/base/`、regional patch 或 role-split renderer，禁止直接
   修改 `deploy/control-plane/regional/generated/`。
2. 完整定义 image、command/args、resources、探针、termination grace、安全上下文、
   ServiceAccount/RBAC 和配置挂载。注册表自动生成不代表这些运行约束可以省略。
3. Deployment、DaemonSet、CronJob 等运行型资源必须在顶层
   `metadata.annotations` 声明清理语义：

   ```yaml
   metadata:
     annotations:
       gpu-fault.io/cleanup-phase: producer
       gpu-fault.io/cleanup-order: "30"
       gpu-fault.io/deploy-mode: regional_rollout
   ```

   CPU phase 只能是 `ingress/consumer/auxiliary`；GPU phase 只能是
   `producer/executor`。`cleanup-order` 决定同一 phase 内顺序。
   `cleanup-action` 缺省为 `delete`，NLB 等只在 reset 删除的对象使用 `reset`。
   只有由区域编排器 apply 的 GPU Deployment 才声明
   `regional_rollout` 或 `regional_reconciler`。
4. ServiceAccount、Role/Binding、ClusterRole/Binding、PDB 和普通 Service 自动推导
   为 `support/delete`；ConfigMap、Secret 和 Namespace 默认由 namespace 删除覆盖。
5. 运行唯一更新入口：

   ```bash
   make PYTHON=.venv/bin/python deployment-contracts-update
   ```

   它自动渲染 CPU 三角色、从 source annotation 生成构建期候选
   `cleanup-inventory.json`、验证 generated allowlist 并运行契约测试。开发者不得
   手工编辑生成的 JSON 或 generated YAML。
6. 提交前运行：

   ```bash
   make PYTHON=.venv/bin/python deployment-contracts-check
   make PYTHON=.venv/bin/python check
   ```

   `tests/regional/test_cleanup_inventory.py` 会拒绝缺 annotation、冲突语义、僵尸资源
   和过期生成物。
7. 首次部署和升级成功 apply 后，部署入口按 `kubectl get` 的实际结果自动创建或刷新
   CPU/GPU 各自的 `gpu-fault-installed-resources` ConfigMap。它是运行时 installed
   registry，开发者和管理员都不手工维护。新 Manifest 已删除但 live object 仍存在
   时，旧登记会一直保留到对象真正删除。
8. cleanup preflight 还会跨 `gpu-fault-system`、历史 `gf-regional-*` namespace
   和 cluster-scoped RBAC 扫描未登记的 `gpu-fault-*` controller/RBAC。发现历史或
   out-of-band 对象时必须 fail closed 并先分类，不能因为新 Manifest/旧注册表里没有
   它就静默宣布清理完成。
9. 在 staging 实际执行部署、clean dry-run 和 rollback，确认新增组件被安装、登记、
   按正确 phase 停止，并在同一 PR 提交源代码、Manifest、生成物、测试和文档。

### 8.2 新增节点 systemd unit

1. unit 文件必须位于 `deploy/systemd/`，名称使用
   `gpu-fault-*.service` 或 `gpu-fault-*.timer`。
2. `install-gpu-fault-collector.sh` 必须显式复制或渲染该模板。
   `test_every_systemd_template_is_handled_by_the_node_installer` 会拒绝只新增模板却未接入
   安装器的变更。
3. 安装器完成文件落盘后自动扫描 `/etc/systemd/system/gpu-fault-*`，写入
   `/opt/gpu-fault/installed-units.txt`；不要维护第二份 unit 字面量列表。
4. Node Agent 启动或 unit 清单变化时发送完整清单与 SHA-256；稳定 heartbeat 只发送
   digest。控制面校验后持久化到 AgentRecord/Aurora。发送失败必须在下一次继续发送
   完整清单，旧 Agent 不带字段时保留已有 inventory。
5. 卸载器优先读取 `installed-units.txt`；旧节点缺文件时按相同名称模式发现。
   `/opt/gpu-fault`、`/etc/gpu-fault`、`/var/lib/gpu-fault` 和 unit 文件全部删除后，
   再用节点审计确认无残留。
6. 至少运行
   `tests/node_agent/test_node_deployment.py`、
   `tests/node_agent/test_service.py` 和
   `tests/fleet/test_installation_inventory.py`。

### 8.3 新增外部 AWS 资源或不可逆清理步骤

Kubernetes Manifest registry 不会自动覆盖 Aurora、NLB、ACM、SNS、CloudFormation、
S3 或 IAM。新增这类资源时必须同时：

1. 在部署和运维手册写出创建、ownership 验证、删除顺序和回退命令。
2. 清理前把 ARN/ID 和 metadata 记录到仓库外 `0600` 证据目录，并登记进
   `cleanup-state.json`。
3. 不得把 Aurora 自身的删除进度只存入 Aurora。停止 writer 前必须导出 live
   Kubernetes inventory、Fleet Agent/unit inventory、原副本数和阶段历史。
4. 使用 `cleanup_state.py` 原子更新并校验 `content_sha256`。Kubernetes namespace
   和 NLB Service 清理完成还不够；NLB listener/target group、ACM、PKI、专属 SG、
   LBC/IAM 等外部附件也必须验证删除后，才能把状态推进到
   `READY_TO_DELETE_AURORA/COMPLETED`。删除 Aurora 并通过 AWS API 验证后才写
   `AURORA_DELETED`。
5. 共享资源必须先查真实消费者。例如被 GPU EKS Load Balancer Controller 使用的
   IAM policy 不能因为 CPU 侧 role 已删除而一起删除。
6. 为状态前进、失败重试、篡改检测和过早删除拒绝增加
   `tests/regional/test_cleanup_state.py` 覆盖。

## 9. 新增 Metrics

为子系统实现一个metric lines contributor并注册到metrics registry，不得继续向
核心渲染函数追加字符串块。若指标用于AMP告警，还必须同时：

1. 加入ADOT keep regex；
2. 在`amp-rules.yaml`增加规则；
3. 在`processor-alerts.yaml`保持本地规则等价；
4. 运行告警可达性测试。
