# Fault Categories and Remediation Actions

This document is the item-by-item expansion of [High-Level Design v2](high-level-design-v2.md) §2 "Fault classification and policy matrix": it puts, for every fault category,
the detection rule, the official NVIDIA recommendation, this solution's policy decision and the actually compiled execution steps into one table.
The source of fact is the code; this document only organises it:

- policy decision: `src/gpu_fault/policy/engine.py`, `src/gpu_fault/policy/nvlink74.py`,
  `src/gpu_fault/policy/xid_cross_source.py`, site variant `src/gpu_fault/orchestration/xid45_policy.py`;
- official catalogs: `src/gpu_fault/data/nvidia-xid-catalog-610.generated.yaml`,
  `src/gpu_fault/data/nvidia-fabric-manager-sxid-2025-11-14.yaml`;
- step compilation: `src/gpu_fault/orchestration/workflow_builder.py`,
  `src/gpu_fault/orchestration/coordinator.py`, `src/gpu_fault/orchestration/families/health.py`,
  `src/gpu_fault/orchestration/hung_dag.py`, failure escalation `src/gpu_fault/orchestration/escalation.py`;
- non-XID rules: `src/gpu_fault/host_health.py`, `src/gpu_fault/gpu_metrics.py` and their per-topic modules (temperature
  `src/gpu_fault/gpu_temperature_policy.py`, environment/throttling `src/gpu_fault/gpu_environment_policy.py`, power
  `src/gpu_fault/gpu_power_policy.py`, memory `src/gpu_fault/gpu_memory_policy.py` and
  `src/gpu_fault/gpu_memory_repair_policy.py`, recovery action `src/gpu_fault/gpu_recovery_action_policy.py`, NVLink5
  `src/gpu_fault/gpu_nvlink5_policy.py`, fabric `src/gpu_fault/gpu_fabric_manager.py` and `src/gpu_fault/gpu_fabric_health.py`, PCIe
  `src/gpu_fault/gpu_pcie_link_policy.py`, the other audited fields `src/gpu_fault/gpu_field_rules.py`, composite rules
  `src/gpu_fault/gpu_composites.py`), log vocabularies
  `src/gpu_fault/log_rules.py`, `src/gpu_fault/efa_kernel_log.py`, `src/gpu_fault/mce_grading.py`;
- capability switches: `config/runtime-profile.regional-hyperpod-safe.example.yaml`,
  `config/runtime-profile.regional-eks-safe.example.yaml`.

If rule thresholds, action names or step order disagree with the code, the code prevails and this document is revised;
the NVIDIA catalog supply chain and gate semantics are in [NVIDIA policy supply chain and implementation](components/nvidia-policy.md).

Reading conventions:

- The "NVIDIA official recommendation" column quotes the Xid Catalog / Fabric Manager User Guide text verbatim; "This solution's decision" is the disposition and `RecoveryAction` output by the policy engine; "Actual execution" is the compiled `WorkflowOperation` step chain.
- `[...]` denotes a conditional step: `STOP_WORKLOADS` is inserted only when workload_state is ACTIVE; `CHECKPOINT_WORKLOADS` is inserted only when a checkpoint_manifest_ref exists (it only records the reference, no real checkpoint is taken); `RESTART_WORKLOAD` is appended only when there are affected_workload_ids.
- Hardware, driver and workload mutations belonging to `NODE_MUTATING_OPERATIONS` are refused at compile time when workload_state is UNKNOWN (fail closed); pure scheduling isolation is not forbidden by this. Safety isolation for BLOCKED-type decisions must still be authorised by the Profile; once granted it executes FREEZE_EVIDENCE → MARK_UNSCHEDULABLE → QUARANTINE and waits for a human.
- NVIDIA `RESTART_APP` (including the fallback of NVLink5 `XID_154_EVAL` without an accompanying 154; none of XID 154's five driver labels is restart app) is re-decided by the policy engine as MONITOR_ONLY / `NO_ACTION` when workload_state is IDLE (our deviation from the catalog: there is no managed application to restart): only an INFO marker and an investigation notification are written, no workflow is built and no cordon. The "Actual execution" column of the RESTART_APP rows in the table below describes the ACTIVE case where attribution to a workload succeeds; ACTIVE but not attributable to a workload still goes through SAFETY_PENDING isolation, and UNKNOWN still fails closed per the previous item.
- Chain A = GPU reset chain, chain B = node reboot chain; definitions are in the RecoveryAction landing table at the end of Part I.

## I. General fault categories (non-XID/SXID)

The item-by-item remediation status, existing test boundaries and new end-to-end acceptance specifications of the 32
categories in this section are in the [32-category audit and E2E specifications](../components/general-fault-e2e-audit.md).
A registered case does not mean the remediation is complete or passed on real hardware; what is still to be implemented
or executed stays an explicit gap.

Disk await definition: `disk_io_await_ms` is sysstat iostat(1)'s `await` (section "Device Utilization Report",
`https://man7.org/linux/man-pages/man1/iostat.1.html`; the sysstat 12.6.1 page carries the same sentence): "The
average time (in milliseconds) for I/O requests issued to the device to be served. This includes the time spent by
the requests in queue and the time spent servicing them." With the field definitions of the Linux kernel's
`Documentation/admin-guide/iostats.rst`, section "I/O statistics fields" (`https://docs.kernel.org/admin-guide/iostats.html`),
it is the interval's increase of field 4 "# of milliseconds spent reading" plus field 8 "# of milliseconds spent
writing" over the increase of field 1 "# of reads completed" plus field 5 "# of writes completed". Field 11
"weighted # of milliseconds spent doing I/Os" is not used: it is the in-flight-count-weighted time whose rate is iostat's
`aqu-sz`, not a per-request time, and 5.0+ kernels print it including discard and flush time -- so under an fsync-heavy
writer it would diverge from the standard await beyond the GF-GENERAL-LIVE-006
`reference_iostat` tolerance. Discards and flushes (fields 12-17) are excluded from the await (they are
`d_await`/`f_await`); `disk_io_util_percent` keeps field 10 "# of milliseconds spent doing I/Os". The kernel document
asks that "Applications reading these counters should detect and handle resets when comparing stat snapshots": when a
device is recreated, re-attached or rebooted, or a counter overflows, so that any monotonic counter goes backwards, the
interval spanning the restart produces no util/await sample and the next interval is rated from the new baseline.
Under a steady load both definitions agree (Little's law), so the 100 ms threshold keeps its meaning and its default.

When the same Host metric stays abnormal but the action, severity or failure_mode changes, a finding is produced again,
including EFA `LINK_INACTIVE -> PCI_DEVICE_MISSING`, without first returning to zero. Confirmation of a submitted incident
binds the original receipt moment and the remediation fingerprint; an old delivery cannot confirm a new round's semantics.

Observation integrity: an EFA PCI/driver/port read failure does not advance the missing-device count; an unknown
failure_mode (including `INVENTORY_UNAVAILABLE` without PCI evidence) only diagnoses, never reboots by default and is not
escalated to a reboot by a failed validation. EFA rates need complete, comparable counter pairs;
`efa_traffic_observation_valid=0` does not mean zero traffic and breaks a zero-traffic window; an UNKNOWN collector still
sends traffic edges, and the managed attempt is still confirmed by the control plane. The Host diagnostic steps bind the
triggering metric, device, threshold and time through `host_diagnostic_probe`; missing data waits, and a separate
performance/Host trigger that has not recovered authorises no hardware escalation. See
[Host hardening](../components/host-observation-hardening.md); the other completed items are in the item-by-item list.

The second round of grading, recovery intent and software tests for the original 12 pending categories is in
[Health policy hardening](../components/health-policy-hardening.md); the basis of the later temperature/power changes is in
[the environment policy review](../components/gpu-environment-policy-review.md). The metric policy version is
`site-dcgm-metric-policy/v5` and the composite rules are `site-dcgm-correlation/v3`; old workflows are not rewritten
automatically during an upgrade.

A correlated marker does not mean the old action suffices: a later XID/SXID must still verify the full action, GPU scope and attempt.
GPU and memory temperature both belong to the thermal fault category; kernel XID 32/79 joins the combined rule only when a PCIe threshold breach
on the same trusted device exists within the valid window; a kernel XID arriving alone still follows its independent policy. The
DCGM last-XID gauge is timed by its change to 32/79: a gauge left at an old value (expired) and an XID on another GPU do not
join, and the PCIe breach stays a read-only diagnostic.
Persistent isolation also differs from the temporary isolation in the reboot flow; after merging, the constrained faulty node must not be re-admitted;
recovery of a healthy warm spare must target the node actually substituted.

### How RecoveryAction lands

Generic DRAIN and GPU RUN_DIAGNOSTICS below describe paths without the new health
contract. The temperature/thermal-throttle class, the performance/counter diagnostics
on the read-only contract's list, training progress and observation recovery follow
`health_recovery_contract` instead: a WARNING is a read-only verification
(`DIAGNOSTIC_ONLY`, no DCGM diagnostic, no hardware escalation); a confirmed temperature
or thermal-throttle CRITICAL takes `ENVIRONMENT_REVIEW` (a terminal hold handed to an
operator, no automatic cooldown readmission; a step of that chain that fails before its ESCALATE_SUPPORT is handed
over by `workflow-support-after-<id>`, stage `held_chain_step`; an older persisted cooldown plan still
finishes by its own rules); none of them enters the legacy DCGM failure escalation below
merely because the action enum is the same. The WARNING diagnostics of the newer DCGM
fields (1423, 1424's unconfirmed duty cycle, the PCIe downtrain and 1501, 1211/1213, a
degraded fabric health) are on that list too and diagnose read-only like the metric family
each grades with (`health_recovery_contract.READ_ONLY_FIELD_NAMES`).
See [the twelve-category changes](../components/health-policy-hardening.md).

## II. XID table (NVIDIA Xid Catalog 610, 172 entries)

Engine order: a DCGM field 230 change that has a kernel-line twin on the same GPU takes the twin's decision (see Part IV) → catalog lookup (absent from the catalog → `SITE_SAFETY` + safety `QUARANTINE`) → product gate (A*→A100, H*/GH*→H100, B*→B100, GB*→GB200) → no Immediate Action in the catalog → MONITOR_ONLY / `NO_ACTION` → direct mapping (IGNORE→NO_ACTION, RESTART_APP→RESTART_WORKLOAD, RESET_GPU→RESET_GPU, RESTART_BM→REBOOT_NODE) or a dedicated workflow (the resolvers of XID 45, 48, 74, 154, 159 and 144-150; `CONTACT_SUPPORT`, `CHECK_MECHANICALS` and `UPDATE_SWFW` see Part IV); a workflow name without a resolver → `BLOCKED_WORKFLOW`. There is no version gate: the catalog's `xid154Linkage` (the "XID 154 linkage" column below) says from which driver/CUDA version the XID is accompanied by an XID 154 report, not the original XID's minimum supported version, so an event without that version or below it still follows its original rule; the NVLink5 decode still needs its own evidence (below). XID 154 itself waits for the 30 s companion window, decides by the driver label and is linked to the companion XID on the same GPU within the window (same boot); that action overrides the companion's Immediate Action.

## IV. Implementation notes

- `CONTACT_SUPPORT`, `CHECK_MECHANICALS` and `UPDATE_SWFW` are EXECUTABLE rather than BLOCKED at the policy layer:
  `CONTACT_SUPPORT` compiles to `ESCALATE_SUPPORT` (fixed-template mail, no cordon), `CHECK_MECHANICALS`
  compiles to a notification and waits for manual confirmation, `UPDATE_SWFW` compiles to the complete shutdown chain containing `UPDATE_SOFTWARE_FIRMWARE`.
  Only missing evidence, inapplicable product, unknown XID and workflows without a resolver go to BLOCKED + `QUARANTINE`.
- Always-Fatal SXIDs (the codes of Table 23) execute `REBOOT_NODE` directly and need neither fabric_partition nor a GPU
  inventory; fatal trunk and 10003/19084 execute `RESET_ALL_GPUS_AND_NVSWITCHES` directly and require fabric_partition and
  the complete node GPU inventory, missing either → BLOCKED. A code outside the pinned tables that claims Fatal or
  Always-Fatal authorises no destructive recovery (BLOCKED).
- XID 152/153 are officially IGNORE, but the catalog lists no applicable product, so the product gate decides NOT_APPLICABLE and isolates the node,
  stricter than the official recommendation (our deviation; the same holds for the 61 XIDs the catalog marks Unused).
- The example profile declares `nvlinkDiagnostics`, `memoryDiagnostics`, `driverRemediation` and
  `softwareFirmwareUpdate` as OBSERVE, so the field-diagnostic branch of XID 74, XID 78,
  the `RUN_FIELD_DIAGNOSTIC` appended by `row_remap_failure`, and the SXID driver/firmware repair steps under that profile
  fail closed with "no executable owner" and are handed to a human -- but no longer as "the whole plan BLOCKED at compile
  time with the node still schedulable": the fault family always contained first through its safety plan (FREEZE_EVIDENCE →
  MARK_UNSCHEDULABLE → QUARANTINE), and the node-health and node-lifecycle families likewise run the
  containment/evidence prefix compiled before the first unowned step, stop `BLOCKED/SAFETY_SETTLED` with the incident
  `QUARANTINED`, and tell the operator which capability waits with `contained-operator-handoff-zh-v1` (a plan whose first
  step is unowned still blocks at compile time).
- While a node is inside a reboot window initiated by the product itself (a `RESTART_NODE`/`REPLACE_NODE` step has been dispatched and the subsequent
  `RESTORE_SCHEDULING` has not yet completed), kmsg XID/SXID and node-health markers on that node no longer open a new incident
  but are linked as evidence to the incident that owns the reboot; kmsg events carrying the old boot_id (the agent already heartbeats with the new boot) are treated as
  pre-reboot residue, land as RECOVERED and produce no workflow (a `NOT_APPLICABLE` one still gets its notice, which says
  nothing is planned). The rules are in `orchestration/reboot_window.py`.
- An event older than the attempt now running on the node, with no recovery workflow for that attempt: only a
  recovery decision (`EXECUTABLE`, not above `RESTART_WORKLOAD`) is recorded as an ignored RECOVERED incident, the attempt
  restart having answered it; the NOT_APPLICABLE, SITE_SAFETY and BLOCKED rows keep their quarantine or evidence freeze,
  exactly as for the same event inside the current attempt.
- The kernel NVRM line and the DCGM field 230 (`DCGM_FI_DEV_XID_ERRORS`) change of one XID are one occurrence
  (`policy/xid_cross_source.py`): the second report -- a change within 120 s of its kernel line on the same GPU, or a line that
  meets a change already decided the same way -- is linked to the first one's incident as evidence and executes nothing, so
  every row's actual execution happens once per occurrence, not once per report, and so does its FAULT_DETECTED notice. A change of XID 154, 74 or 144-150, whose
  decode reads the kernel line, waits up to 120 s for it and stays BLOCKED + `QUARANTINE` only when the line never comes.
