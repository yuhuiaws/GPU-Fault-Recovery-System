# GPU 故障恢复控制面性能压测验收方案

## 1. 目标

本文件定义可重复执行的容量模型、门槛、命令入口和证据格式，不保存任何客户环境的
集群名、节点 ID、账号、私网地址、release digest 或未脱敏运行结果。

真实压测结果必须进入 CI artifact 或访问受控的私有证据库。公开仓库只保留经过脱敏的
结论，不把历史 PASS 当作新 release 的容量证明。

当前容量目标须使用[管理员容量配置](管理员容量配置.md)的共享连接预算，
计入各进程的pool和专用LISTEN连接。enabled预设默认5个control-worker，
disabled预设保持6个；本文历史6-worker enabled压测结果不改写为新拓扑的实测。
短轮询延迟与生产20秒long poll的原始等待、额外开销须分开记录。

## 2. 验收规模

必须覆盖三种拓扑：

| 拓扑 | 基线 | 余量 |
|---|---:|---:|
| 多集群区域控制面 | 32 个 GPU 集群 | 50 个 GPU 集群 |
| 单超大 GPU 集群 | 1000 个节点 | 按目标客户规模增加 |
| 复杂恢复动作 | 32 集群并发 workflow | 50 集群并发 workflow |

多集群容量模型按每集群 256 节点、每节点 8 GPU 计算：

```text
32 集群：8192 节点 / 65536 GPU
50 集群：12800 节点 / 102400 GPU
```

单集群 1000 节点场景必须使用同一个 `cluster_id`，不得通过创建多个逻辑集群代替，
否则无法覆盖单集群 lane、配额和热点行。

## 3. 发布前提

每轮正式压测必须记录：

- wheel SHA-256、node bundle SHA-256、`module_digest` 和 schema version；
- ingress、control-worker、spool-worker 的副本数与 service role；
- Aurora min/max ACU、实例状态、连接上限和测试前后 deadlock 计数；
- spool enabled/disabled、worker 数、batch size 和 in-flight byte 上限；
- processor completion cluster concurrency、retry backoff 与 lane policy 分布；
- remediation budget 的 Region、cluster、node、failure domain 和 resource class
  五档值；release 不含该能力时明确记录 `unsupported`，不得伪造为默认值；
- GPU 集群数、节点数、请求组合、持续时间和并发数；
- load generator CPU/内存限制、实际使用量和所在独立节点；
- 开始/结束 UTC 时间及清理结果。

### 3.1 压测通知绝不得外发

- 所有 synthetic 性能 cluster 必须使用保留前缀 `perf-cap-`；Store 必须把该
  前缀产生的每一条通知标记为 `drill_id=perf-capacity`，包括没有持久化 Incident
  的 Collector、Agent、容量和静默告警通知。
- AMP 告警不经过 Store：Alertmanager 直接投递到站点 SNS 主题。因此 Alertmanager 定义必须
  把 `cluster_id=~"perf-cap-.*"` 的告警路由到无投递配置的 `gpu-fault-drill-sink` 接收器
  （告警仍在 AMP 中可查）；runner 在注册前读取线上定义核对该路由，缺失即 fail closed，
  结果写入 `notification-safety-preflight.json`。
- `GPU_FAULT_NOTIFICATION_DELIVER_DRILLS` 必须未设置或为 `false`。性能 runner
  在修改 registry 或创建负载前必须逐个非零 CPU Pod 检查该值；任一副本允许投递
  drill 时 fail closed。
- 压测期间管理员邮箱新增邮件数必须为 `0`。出现任何 synthetic 邮件立即停止发压、
  暂停 dispatcher、清理本轮 `perf-cap-*` notification/result/delivery，并把本轮
  判为 `INVALID`，不得以“邮件不影响吞吐”为由继续。
- 不得只依赖 XID/SXID message 中的 `drill_id` 文本。routine telemetry、Collector
  silence、Agent 和 action completion 也可能创建通知，必须在持久化通知的统一入口
  补齐 drill 标记。

控制面与数据面必须使用同一 release。版本或 digest 不一致时，本轮结果无效。
压测工具从 release state 读取的 release（运行标签、Action runner 的 pins）必须是已提交的
`complete`：回滚后的 `rolled-back` 记录的是失败的候选，在途、停住或未提交的状态也不代表站点
实际运行的 release，这些情况一律 fail closed，错误写明阶段、记录的 release_id 与补救
（对站点自身的发布执行 `gpu-fault-admin deploy`）。release ID 取自 artifact volume 时
反映的是 live api-ha Deployment 实际运行的内容，不受此限。

### 3.2 Registry和控制面隔离

容量压测默认只能指向隔离control plane和隔离registry。默认namespace为
`gpu-fault-perf-system`，隔离控制面必须挂载自己的registry Secret；数据面namespace中
的connection Secret必须指向该隔离控制面。

```bash
export GPU_FAULT_PERF_CONTROL_NAMESPACE=gpu-fault-perf-system
export GPU_FAULT_PERF_DATAPLANE_NAMESPACE=gpu-fault-perf-system
export GPU_FAULT_PERF_REGISTRY_SECRET=gpu-fault-regional-clusters
export GPU_FAULT_PERF_CONNECTION_SECRET=gpu-fault-regional-connection
```

隔离控制面还必须使用独立、可销毁的 PostgreSQL database；只换 namespace 和 registry
Secret、但继续写生产 database，不构成隔离。该 database 仍由独立 schema ensure Job
建表，业务 Pod 不得打开 auto schema init。验收结束后必须先确认所有 synthetic 行、
Job 和连接都已终止，再删除 database。

正式轮次假定 store 已维护：一个 campaign 日的写入会让热表（processor lanes/queue counts/priority shards/queue、
`gpu_fault_gpu_metric_latest`）的堆与索引页膨胀到活行的百倍以上，ingress 吞吐减半、
`gpu_fault_processor_admission_batch_expired_total` 上升并让 reserved 503 share 判定失败；schema v19 的存储参数
阻止再次膨胀，已有膨胀在正式轮次之前用 `gpu-fault-admin store-maintenance --confirm STORE_MAINTENANCE` 回收
（管理员日常运维 §10.3）。膨胀本身就是一轮 32 集群正式压测留下的：一轮写入约 26 万条 synthetic
`gpu_fault_gpu_metric_latest` 行、8.7 万条 objects、2.7 万条队列行，拆卸把它们删掉以后堆与索引文件停在高水位
（metric latest 1,233 活行占 31,023 页、索引 118 MiB；队列 246 行配 36 MiB 索引、52 MiB TOAST；queue counts 280 行占
127 页），下一轮就在这个布局上跑。同一 release、同一准入默认值的三点对照：全新 store 1,572 req/s PASS；索引与堆都
膨胀 538 req/s FAIL（普通遥测 reserved 503 份额 29.4%，49% 的活跃语句在 `LWLock:BufferContent` 上等待——队列 INSERT
84%、completion CTE 78%、claim CTE 48%）；只重建索引并 `VACUUM FULL` 三张小表、大堆与 TOAST 原样保留 1,141 req/s
PASS、BufferContent 为零。队列/objects 的顺序扫描（9.1 万/6.4 万次）是统计过期时的读语句，占活跃样本 4%，是受害者
而非驱动者；堆膨胀**不是**吞吐变量（同一 release 上老化的 r1 在 582 MB 的 metric latest 上跑出 1,601 req/s，见 §3.3 与详细设计-v2 §4.4.2）。控制面 worker 的周期任务 `store-compaction`
（`GPU_FAULT_STORE_COMPACTION_INTERVAL_SECONDS`，默认 300 s）按目录事实——每活行堆页数、每活行索引页数、最稀疏索引的
每页条目数——自动对越过阈值的索引做 `REINDEX INDEX CONCURRENTLY`、对三张小表做 `VACUUM (FULL, ANALYZE)`，因此一轮
正式压测之后、下一轮之前不再需要人工 `store-maintenance`；大堆与 TOAST 仍只由该动词回收。r1 的吞吐塌陷并不只是膨胀：同一 release、同一数据库的五轮里，失败轮的 RDS
`log_lock_waits` 显示每窗口数千次 ≥1 s 的锁等待集中在 processor 计数行的语句级触发器上——哈希分片让同一集群的
并发 flush 与 completion 落在同一组行上形成 convoy；schema v20 把两张计数表改为按 writer backend 分行
（详细设计 §3.1.5），正式轮次应在 v20 之后进行。v20 之后锁等待移到了 COMMIT：每个发出过 NOTIFY 的事务都在
`PreCommit_Notify` 的数据库对象锁上串行提交（15 分钟窗口 2389 次 ≥1 s 等待，70% 活跃语句为 COMMIT），而每行一条
`pg_notify` 让每次 admission flush 都在通知；schema v21 把处理器队列与 spool 的唤醒改为语句级、边沿触发
（详细设计 §3.1.3），正式轮次应在 v21 之后进行。

GPU perf namespace 只部署连接 Secret、压测 ServiceAccount/RBAC 和模拟 Job，不部署
真实 Cluster Executor、Watcher、Collector 或 Node Runtime。该 namespace 与负载
ServiceAccount `gpu-fault-completion-watcher` 由运行器在缺失时自行创建（namespace
带 `gpu-fault.io/perf-namespace` 标签；ServiceAccount 作为本轮资源创建并随本轮拆卸），
连接 Secret 每轮从身份 namespace 镜像；两者跨站点存活，也可以预先手工创建。Action runner 从隔离 CPU
控制面的 release state 与当前进程 required pins 派生短租约 synthetic Agent identity
和模拟 Executor claim；两者不一致时 fail closed。只有 live registry 模式才继续要求
真实数据面 Executor Deployment 和活动 Agent identity 与 release pin 一致。
live registry 模式下 synthetic Agent 模板取自**与 synthetic 注册同 provider** 的真实 Agent（synthetic 集群注册为
`hyperpod`，可用 `ACTION_SYNTHETIC_PROVIDER` 改）：混合站点上另一 provider 的 Agent 即使更新也不会被选中；无论模板来自
live Agent 还是 release state，seed 都核对该 Runtime Profile 的 `nodeReboot` owner 等于该 provider 的 lifecycle adapter
（`PROVIDER_NODE_REBOOT_OWNERS`），不符即在发送任何负载前 fail closed，并把 `synthetic_provider`/`node_reboot_owner` 写进 seed
摘要。此前混合站点上模板落到 eks-managed 节点，所有 synthetic workflow 按 eks profile 规划，RESTART_NODE/REPLACE_NODE 归
`gpu-fault-eks-adapter`，模拟 Executor 领不到，整个集群的后续 workflow 被未领取命令扣在 PENDING。模拟 Executor 现同时
声明两种 provider 的 lifecycle adapter owner。
synthetic 集群注册时还从**同 provider 的生产注册项**复制 `runtime_profile_version` 与 `agent_config_digest`（该 provider
是站点基础家族、生产注册项没有 pin 时就不带 pin；没有该 provider 的生产注册项、或同 provider 的生产注册项 pin 不一致时
fail closed）：`FleetRegistry.cluster_policy` 让每个集群的 Agent 遵守其注册项自带的 pin、否则遵守站点 pin，而 synthetic
Agent 模板来自该 provider 的真实 Agent、上报的正是该 provider 的 Runtime Profile 与 config digest，不继承时 fleet
compatibility preflight 会以 `runtime profile mismatch ... PIN_AHEAD_OF_FLEET` 扣住每个 destructive step（eks 基础家族的
混合站点上 128 个 integrated workflow 只有 32 个 RESTART_NODE 完成）。继承的 pin 与来源集群写入
`registry-registration-intent.json`（`provider`/`inherited_pins`/`pins_source_cluster_ids`）；seed 摘要记录
`registered_runtime_profile_version`/`registered_agent_config_digest`，模板 Agent 的值与之不一致时在发送任何负载前 fail
closed。registry 的 baseline/恢复与 postflight 清理仍按 `synthetic`/run id 识别并原样移除这些注册项。

只有经审批确实要使用正式`gpu-fault-system`控制面时，命令才允许同时提供：

```text
--allow-live-registry
--confirm-live-registry ALLOW_PERF_CAPACITY_LIVE_REGISTRY
```

缺少任一确认时必须在修改registry前失败。不能仅通过换Secret名称在正式namespace中声称
已经隔离。

每个逻辑集群registry记录必须包含：

- `synthetic=true`；
- 本轮`suite_id`对应的`synthetic_run_id`；
- 带时区的`synthetic_expires_at`；
- 不指向真实EKS/HyperPod的占位身份。

过期synthetic记录不得继续认证，也不得进入运行时持久registry。压测前自动清理legacy或
已过期`perf-cap-*`残留；发现其他尚未过期run时停止，不能抢占。压测后必须删除本轮记录，
重新读取registry确认不存在任何synthetic残留，并保存`registry-preflight.json`和
`registry-postflight.json`。
注册前 runner 记录 registry Secret 中 `clusters.json` 的摘要与序列化形态
（`registry-secret-baseline.json`，只含摘要与形态，不含 token），拆除时按该形态把 Secret
逐字节还原到运行前内容（`registry-secret-restore.json` 记录 `byte_identical`）。
注册前与拆除后各做一次对齐校验并写 `registry-alignment-preflight.json` /
`registry-alignment-postflight.json`：Secret 的配置摘要必须等于持久 head 的配置摘要，
且每个 Running `gpu-fault-api-ha` 副本的 `/healthz?verbose=1` 必须报告
`regional_registry.secret_drift=false`。注册前不对齐即拒绝开跑（漂移不归因于本轮），
拆除后不对齐则本轮 cleanup 判失败并逐字段列出差异与漂移副本。

### 3.3 Store 状态前提：用 store 指标定义的稳态、乐观上界与布局记录

正式轮次的判定对象是"真实 CPU 控制面面对大量 GPU 数据面集群瞬时上报的处理能力"，不是一个刚整理过的 store。
同一 release、同一准入默认值下的四个数据点（详细设计-v2 §4.4.2）：全新 store 1,572 req/s PASS；一轮拆卸之后 538 req/s
FAIL（活跃语句 52.6% 等 `LWLock:BufferContent`、准入 INSERT 并发 148）；只重建索引 1,141 req/s PASS（0 BufferContent，
提交 I/O 与 advisory 锁等待、刚被 `VACUUM FULL` 缩小的小表在风暴中重新扩展）；再跑完一整轮 16 步套件、堆比失败时更大
（metric latest 582 MB、队列 194 MB）的"老化" r1 1,601 req/s PASS。结论：**堆/TOAST 的大小、距冷部署的时间、"上一轮之后"
都不是判定轮次是否算正式记录的依据**，索引条目的状态才是——而目录里能读到它的代理是 batch 58 写进每轮 `summary.json` 的
`store_bloat.before`（每张热表的 `index_pages_per_live_row`、`index_min_entries_per_page`、`heap_pages_per_live_row`）加上
schema v23 的 `store_layout`。因此一轮的标签由**开跑时的 store 指标**决定，而不是由时钟或部署历史决定：

- **`optimistic_bound`**：`store_bloat.before.gpu_fault_processor_queue.index_pages_per_live_row < 1`，且其
  `index_min_entries_per_page` 为空或 ≥ 64——队列索引是紧凑的（刚冷部署、刚 `REINDEX`/`store-maintenance`/压实过，
  或从未承载过一轮工作集）。这类轮次只给出上界，不作为正式记录，不论站点已经运行了多久。
- **`steady_state`**：`store_bloat.before.gpu_fault_processor_queue.index_pages_per_live_row ≥ 8`（队列索引仍停在至少一轮
  工作集的高水位：10:30 失败状态为 ≈19，老化通过状态为 ≈25），且 `store_layout.mode == detached`，且本轮之前
  **没有**人工 `store-maintenance`（`store-compaction` 周期任务照常运行）。标签由 runner 从这两个字段推导并写入
  `summary.json`，人不得手填。模式为 `inline` 的轮次只能标注为升级窗口内的对照，不是 v23 布局的正式结果。
- 两个标签各至少一轮，判定以 `steady_state` 轮为准；两轮之间不得人工压实；`store_bloat.before` 未记录（`recorded=false`）
  的轮次不能作为任一标签的记录。
- 每轮 `store_layout.after` 给出拆卸后队列、payloads、回放分区与 metric latest 分区的页数：正式结果要求拆卸之后
  `gpu_fault_processor_queue` 的堆页数回到在途集合的量级，synthetic 集群的 metric latest 分区已 `DROP`。
- 这个代理看不见叶页填充率与死条目密度（线上 store 未安装 `pgstattuple`，安装是一次写入），所以用于**判定**的只能是
  `steady_state` 轮自身的吞吐、p99 与 reserved 503 份额（§6）；`index_pages_per_live_row` 只负责把"紧凑索引上的乐观上界"
  与"承载过工作集的索引上的稳态"分开。

验收口径：`steady_state` 轮按 §6 判定；它相对 `optimistic_bound` 轮的吞吐差超过 10% 或 reserved 503 份额越过门槛，判定 FAIL
并作为写路径缺陷登记，不得以人工压实后的复跑替代。本地 Postgres 复现方法（`scripts/perf` 的 bloat harness：同一负载分别打在
全新、经一轮加拆卸、再经压实的 store 上，对比每条热语句的 shared buffers、`LWLock:BufferContent` 份额与队列更新的 HOT 份额）
是提交前的开发者门禁，不替代线上稳态轮。

## 4. 流量模型

### 4.1 三优先级混合流量

| 优先级 | 请求 |
|---|---|
| P0 | XID、SXID 和其它真实故障通道 |
| P50 | 带 edge-filter reason 的 GPU/host 可疑证据 |
| P100 | inventory、GPU metrics、host telemetry 等例行状态 |

固定正式请求矩阵如下。不得依赖 CLI 默认值猜测 P50 数量：

| 规模 | P0：XID + SXID | P50：GPU + Host evidence | P100：三类节点遥测 | 总请求 | 比例 P0/P50/P100 |
|---|---:|---:|---:|---:|---:|
| 32 集群 × 256 节点 | 500 + 500 | 500 + 500 | 8192 × 3 = 24576 | 26576 | 3.76% / 3.76% / 92.48% |
| 50 集群 × 256 节点 | 781 + 781 | 781 + 781 | 12800 × 3 = 38400 | 41524 | 3.76% / 3.76% / 92.48% |

32/50 集群必须分别测试：

1. telemetry spool disabled；
2. telemetry spool enabled；
3. enabled 且使用专用 spool-worker；
4. 至少一次控制面 Pod 退出或滚动更新期间的持续输入。

### 4.2 单集群 1000 节点

同一集群内混合发送：

- 1000 节点 heartbeat；
- inventory、GPU metrics 和 host telemetry；
- XID、SXID、P50 evidence；
- workload observation；
- 同一 attempt 多节点故障及不同 attempt 的独立故障。

必须分别验证 spool disabled 和 enabled。

### 4.3 复杂恢复动作

Action 压测使用模拟 executor，不调用真实 reset、reboot 或 provider mutation。
每个 workflow 至少包含：

- evidence；
- scheduler containment；
- workload stop/restart；
- diagnostic 分支；
- remote command claim/result；
- DAG dependency、lease 和 fencing。

包含持久 remediation budget 的 release 必须把 Action 压测拆成两档：

1. **生产预算档**：使用待发布生产默认值，验证故障风暴被限流、等待 workflow
   不调用 adapter、额度释放后最终完成且没有饥饿；
2. **原始容量档**：在隔离压测环境通过正式 release 配置把预算提高到不构成瓶颈，
   测量 dispatcher、Store 和 Executor 的原始吞吐。

当前生产默认值为：

| scope | 默认值 |
|---|---:|
| Region | 20 |
| 每集群 | 5 |
| 每节点 | 1 |
| 每 failure domain | 1 |
| 每 resource class | 2 |

当前 Action 模型的每个 workflow 同时申请 `WORKLOAD_MUTATION`、
`GPU_RUNTIME_MUTATION` 和 `NODE_LIFECYCLE_MUTATION`。因此
`--workflows-per-cluster 4` 在生产预算档中实际最多只有 2 个同集群 workflow
同时活跃，32/50 集群 × 4 workflow 也会被 Region 20 的上限分波执行。
这属于预算生效，不是 dispatcher 吞吐退化。

每个 workflow 的 claim 从准入一直持有到它终结，reset、reboot 的等待期间也不释放
（详细设计 §9.5），所以上述上限对整个修复过程都成立。按调度模型估算（模型而非实测），
生产预算档 32×4 的 workflow duration p50/p99 约 675/1301 秒、first-action p95 约
1042 秒（均含预算等待），整批完成约 23 分钟，同时在飞的 reset/reboot 不超过 20。
claim 只持有到第一个预算步骤完成的旧实现下，同一模型给出 390/644 秒、307 秒和约
12 分钟，实测 RUNNING 一路升到 dispatcher 每个 tick 100 行的选择上限；两种实现的数字
不可互相比较。生产预算档的这几项是限流的结果，判定仍按 §6.3（限流正确、无饥饿、
最终收敛），不作为回归门槛。

dispatcher 每个 tick 选取最老的 max(100, Region 预算 + 50) 个未结束 workflow，上限 400
（详细设计 §9.5）。生产预算档（Region 20）仍为 100；integrated runner 的 Region 预算 128 和
200 分别得到 178 和 250，32/50 集群一轮的全部 workflow 都在一个 tick 的选取之内，而固定
100 行时 50 集群那轮的后 100 个 workflow 要等前 100 个（调度模型在 per-command 完成与事件驱动
telemetry 下，把 integrated-50 的 workflow p99 从约 207 秒降到约 155 秒）。按固定 100 行选取
测得的轮次与之后的不可比较。

当前 seed 的合成 step 未设置 `failure_domain`、`fabric_partition` 或
`availability_zone`，所以它不能证明 failure-domain budget 生效。正式预算验收必须
为合成 workflow 提供确定性 domain，覆盖同 domain 互斥和不同 domain 并行两种方向。

### 4.4 N x 500+ 节点单 AZ 集群的整集群相关故障（计划中，尚未执行）

**本节场景没有任何一轮已执行的结果；下文只是场景定义和验收标准，不得被引用为
容量证明。**

当前产品要求是 N 个各 500+ 节点、各自单 AZ 的 GPU 集群。§2 的两种拓扑都不覆盖它：
多集群模型按每集群 256 节点计，单集群 1000 节点模型只有一个 `cluster_id`。它与
已有场景的本质区别是一次整集群相关故障（如单 AZ 网络或电源事件）会在同一集群的
≥500 个不同 node lane 上同时产生 ≥500 条 fault 优先请求，而 §13.4 的 1000 节点
模型是按矩阵分批发压，不是同一秒的整集群波。

基准拓扑与 release 默认值一致：4 个集群 x 512 节点 = 2048 受管节点，每集群一个 AZ，
AdminConfig 为 `largestClusterNodeCount=512`、`managedNodeCount=2048`、
`maxClusterQueueDepth=4096`、`aurora.minAcu>=20.5`（派生规则见管理员容量配置 §6）。
执行前必须用正式配置入口收敛上述值，并确认三个 CPU 角色 ConfigMap 中
`GPU_FAULT_PROCESSOR_FAULT_RESERVED_CLUSTER_DEPTH >= 512`。

流量模型：在 §4.1 三优先级混合流量稳定运行的背景下，对其中一个 512 节点集群在同一
秒内注入 512 条 XID fault 事件（每节点一条，各自独立 node lane），随后按 §4.3 让由此
产生的 workflow 走完 evidence、containment、stop/restart 与 remote command。其余 3 个
集群保持正常遥测流量，用于证明单集群风暴不外溢。

验收标准（每一条对应管理员容量配置 §6 的一条派生规则或运行时自检）：

1. **fault reserve 容下整波**：注入集群的 512 条 fault 请求全部 202，
   `gpu_fault_processor_admission_rejections_by_cluster_total{scope="cluster_reserved"}`
   在该集群为 0；同一时刻该集群的 routine telemetry 允许出现 429（这是预留生效，不是
   失败）。
2. **单集群深度不外溢**：其余 3 个集群的
   `gpu_fault_telemetry_spool_rejected_total{scope="cluster"}` 与 processor 429 均为 0，
   `gpu_fault_processor_admission_rejections_total{scope="global"}` 为 0。
3. **Aurora 下限成立**：整波期间 HTTP 503 为 0，Aurora 实际 ACU 不超过 Min 20.5 所
   预置容量的 100%（如超过，则 `managedNodeCount/100` 的比例需要修正并记录）。
4. **运行时自检**：把 `GPU_FAULT_PROCESSOR_FAULT_RESERVED_CLUSTER_DEPTH` 人为改为 128
   再滚动一个角色，Pod 必须以
   `fault-reserved cluster depth ... cannot hold one correlated whole-cluster fault wave`
   拒绝启动；`/metrics` 的 `gpu_fault_capacity_largest_cluster_node_count` 与
   `gpu_fault_capacity_managed_node_count` 必须等于 AdminConfig 声明值。
5. **完成侧**：512 个 fault incident 全部进入 workflow，P0 completion p99 与 §13.4 完整
   模型比较并记录，remediation budget 分波执行且无饥饿（§6.3）。

执行入口、artifact 格式与脱敏要求沿用 §8.4 和 §11；结果在首次执行后作为 §13 新的
子节补入，本节保留为场景定义。

## 5. 发压端门禁

- 不能在被测 API Pod 内发压。
- 至少使用 4 个独立 load-generator Pod。
- 发压 Pod 应分散到不同节点。
- no-op 校准吞吐必须达到目标峰值两倍。
- 发压端平均 CPU 使用低于 50%，任何资源超过 70% 时结果无效。
- 同一模型至少测试 16 和 32 两档并发。
- load generator 自身出现超时、连接耗尽或调度抖动时不得归因于控制面。
- 同步burst在start gate前对控制面hostname执行最多5次有界解析，并在单个发压进程内
  缓存、轮转解析结果。每个请求仍新建TCP/TLS连接并使用原hostname完成HTTP Host、
  TLS SNI和证书校验；不得让4万级请求矩阵同时制造4万级CoreDNS查询。正式结果必须记录
  DNS解析尝试数、地址数和缓存命中数；预解析需要重试、任一请求绕过缓存或发生
  transport retry均判失败。

## 6. 验收门槛

### 6.1 摄取和准入

```text
未达到故障硬上限时 P0 接收率 = 100%
P0 HTTP 429 = 0
P0 API p99 必须记录并与本轮批准的延迟预算比较
持续稳态 processor oldest age < 5s
```

普通遥测达到非故障额度后必须得到 reserved 拒绝；P0 仍可进入保留容量，只有达到
global/cluster 硬上限后才允许拒绝。
正式报告必须记录本轮采用的 P0 ingress 延迟预算及其依据；未预先批准统一预算时，
p99 只作为容量特征和版本回归指标，不能单独决定 PASS 或 FAIL。

### 6.2 队列和完成延迟

```text
突发结束后 60s 内 processor queue 回到测试前稳态
spool enabled 时 spool depth 最终回到稳态
fault completion p99 不超过批准预算
不同优先级不得发生永久饥饿
```

不能仅用“队列很快清空”判定通过：大量请求被 429/503 拒绝时，队列同样可能为空。
必须同时核对接收数、完成数、失败数和最终状态。

### 6.3 恢复动作

```text
未等待 remediation budget 的单节点故障首个隔离 step p99 < 10s
未等待 remediation budget 的多节点故障首个隔离 step < 聚合窗口 + 10s
预算满时 adapter/remote command 启动数 = 0
预算释放后等待 workflow 最终全部获得执行机会，不得永久饥饿
duplicate claim = 0
stale fencing write = 0
PostgreSQL deadlock = 0
```

预算等待时间必须单独统计，不能并入 dispatcher 首个隔离 step 延迟后判定实现退化。
生产预算档关注限流正确性、等待公平性和最终收敛；原始容量档才用于比较不同 release
在相同并发拓扑下的 first-action 与 workflow duration。claim 持有到 workflow 终结
（详细设计-v2 §9.5）的 release 起，生产预算档的 workflow duration、first-action 与整批
耗时同此前 release 的数字不可比较：此前 claim 在第一个预算步骤完成后即释放，实测
RUNNING 一路升到 dispatcher 每个 tick 100 行的选择上限（§4.3）。

### 6.4 高可用

- 删除一个 ingress 或 worker Pod 时不丢失 P0。
- Aurora writer failover 后不重复执行破坏性 step。
- 滚动升级期间旧/新副本协议兼容，finalize 前失败可以回滚。
- 任何副本 module digest 漂移都使本轮结果无效。
- cold-connect 突发（每请求新建连接、每 Pod 数千并发）被全部 202 接收时，不得有任何 api-ha 副本被 liveness 重启：
  探针在专用 `livez` 端口上回答，`gpu_fault_listen_accept_queue_connections` 可以达到数千，而探针时延保持在 GC 停顿量级。
- 每 Pod 并发连接超过 Pod 命名空间 `somaxconn`（4096）时不得出现 SYN 丢弃造成的秒级重传尾部：service 端口由
  `gpu_fault.app.serve` 按 worker 以 `SO_REUSEPORT` 绑定，`gpu_fault_listen_accept_queue_connections` 按进程导出、每进程 <4096，
  `gpu_fault_listen_accepted_connections_total` 各进程份额在随机分配方差之内；load 客户端的 `connection_modes` 同时覆盖
  cold-connect 与 warm-keepalive（`--prewarm-connections`），start-burst 的判定以 cold-connect 为准。

### 8.1 多集群与单集群容量

```bash
  --host-evidence-total 500 \

```

`all`/`run` 必须设置 `GPU_FAULT_AURORA_CLUSTER_ID`，缺失时在注册任何 synthetic cluster 之前以用法错误
拒绝。runner 在注册前从该 Aurora cluster 解析当前 writer 实例（`DBClusterMembers` 中唯一的 writer）和每个
成员的可用区，`aurora.json` 只读这个 writer 的实例指标与该 cluster 的集群指标——此前未设置
`GPU_FAULT_AURORA_INSTANCE` 时读的是一个默认实例名，它并不是站点的 writer，集群指标的 cluster ID 也是从该名字
猜出来的。writer 实例、writer 可用区与控制面 Pod 所在节点的可用区（节点标签
`topology.kubernetes.io/zone`，只读，读不到时记 `recorded=false`）在开跑前写入 `run.json.placement`，结束后
再读一次写入 `summary.json.placement`（`start`/`end`/`aurora_writer_changed`）：每条语句都要从控制面节点的
可用区到达 writer 的可用区，writer 又随每次 failover 移动，没有这两项的轮次之间不可比较；一轮内发生
failover 时该轮的 Aurora 证据只描述开跑时的 writer。§8.4 的 integrated runner 以 `--aurora-cluster-id` 做同样
的记录；§8.2 的 action runner 不读 Aurora 指标，设置了 `GPU_FAULT_AURORA_CLUSTER_ID` 时同样记录 placement，未设置时
照常运行并在 `summary.json.placement` 记 `recorded=false`。

`all`、`run`以及action、integrated、correlated套件无论成功、非Complete、异常或中断，
都必须在`finally`中执行同一个幂等teardown。teardown删除Job/ConfigMap/Secret、按需purge
数据库记录、注销本轮synthetic registry；purge与注销都在teardown之内，失败时最多重试3次
（间隔15、45、90秒），每次都重做全部归属检查，本轮数据未清空时绝不注销。不得把异常路径
只写成`aborted`而跳过registry清理。重试用尽仍失败时保留本轮回执目录，`status.json`标记
`aborted`并写入`cleanup_error`与`recovery_command`，日志打印一行`recovery command: ...`：
即用原`--suite-id`和`--run-dir`执行`regional_capacity_suite.py teardown`（integrated和
correlated的目录已移到`_aborted/`下），排除原因后照此执行即可完成清理。purge在同一事务的最后一次读取中
仍发现本轮数据时什么都不删，错误按计数写明残留：遍历之后才出现的记录kind（仍在写本轮集群的写者）、遍历到却仍在的
记录kind与各表残留行数，不含key、payload或凭据，据此即可判断与purge竞争的写者。

### 8.2 Action 容量

```bash
scripts/perf/regional_action_capacity_suite.py \
  --clusters 32 \
  --workflows-per-cluster 4 \
  --nodes-per-workflow 4 \
  --executor-workers 8 \
  --artifact-root artifacts/perf
```

带 remediation budget 的 release 必须用同一请求模型分别执行生产预算档和原始容量档。
原始容量档至少满足：

```text
Region limit >= clusters * workflows_per_cluster
cluster limit >= workflows_per_cluster
resource class limit >= workflows_per_cluster
node limit = 1（仅当每个 workflow 使用互不重叠节点）
failure domain limit >= 同一 domain 内计划并发的 workflow 数
```

因此固定模型中：

- 32 集群 × 4 workflow：Region 至少 128，cluster/resource class 至少 4；
- 50 集群 × 4 workflow：Region 至少 200，cluster/resource class 至少 4。

这些值只允许用于隔离的原始容量档，不是生产默认建议。配置切换必须进入正式
release/site 配置并完成滚动，不能用 `kubectl set env` 临时修改部分 Pod。
`run.json` 必须保存五档预算、测试档位以及是否给 workflow 填充了 failure domain。
运行器从一个 control-worker Pod 读取五档预算，按上表判定 `raw-capacity`、
`production-budget` 或 `unbounded` 并写入 `run.json.remediation_budget`；两档下
executor 的并发下限都只要求推进（1），每个 executor 的并发峰值
`max_concurrent_commands` 作为证据记录而不是通过条件——per-node 与 failure-domain
限制会有意串行化同集群 workflow。executor 墙钟与 Job `activeDeadlineSeconds`
跟随 `--timeout-seconds`（运行器缺省 900 秒）；生产预算档 32×4 按 §4.3 的模型约需
23 分钟、按最近一轮实测与模型之比约 27 分钟，应显式传 `--timeout-seconds 3600`
（2400 只留约 1.5 倍余量）。

运行器每次采样（`history.json`，约每 2 秒一次）统计本轮 `RUNNING` 且 claim 列出某
scope 的 workflow 数（不看租约，与 store 的占用规则一致；本模型没有抢占交接），记录每类
scope 中最忙者的持有数
`budget_holders_max`（region、cluster、class；node 与 domain 只作证据）。claim 持有到
workflow 终结，所以每个采样都必须在上限之内，而不只是准入时：
`summary.json.remediation_budget_occupancy` 用 `run.json.remediation_budget.limits` 判定，
任一采样中 region 的持有数超过 Region 上限、某集群的持有数超过每集群上限、或某集群某
resource class 的持有数超过每 resource class 上限，运行即失败（`violations` 逐条写明，
运行器退出码 3，`status.json` 原因为 `remediation budget occupancy exceeded a configured limit`）；
未设置的上限不检查，没有任何占用采样同样判失败。生产预算档 32×4（20/5/2）下这就是
RUNNING ≤ 20、每集群 ≤ 2（模型的每个 workflow 申请全部三个 resource class）；原始容量档
与综合工作流的门槛不变。

所有入口必须显式指定目标 kubeconfig/context。生产 registry token 和 Secret 不得写入
artifact；registry baseline 只允许保存 cluster ID 和 token digest。
Action 容量 teardown 还必须按 `workflow-actionperf-*` 删除不携带
`cluster_id` 的 synthetic workflow，再删除 `perf-cap-*` incident、command、
Agent 和队列记录；否则会留下缺失 incident 的孤儿 workflow，持续触发 dispatcher
错误。
teardown 在 executor Job 已删除、processor 队列已排空、registry 归属已验证后，
允许把本轮自有的未终结 workflow/command 记录一并删除（`forced_nonterminal` 计数
写入清理结果）：中止的运行留下的 LEASED/PENDING 命令没有 executor 可以完成，否则
会拒绝之后每一轮的注册。运行期间运行器每 30 秒刷新本轮 synthetic Agent 的心跳与
租约（播种脚本 `run-heartbeats` 模式），否则舰队兼容性预检会在心跳过期后扣住
破坏性步骤。

### 8.3 Live correlated-action

只把 correlated ingestion 与直接 seed 的 Action workflow 放在同一报告中，不能证明
事件到升级动作的因果链。完整验收还必须执行：

```bash
scripts/perf/regional_correlated_action_suite.py \
  --clusters 32 \
  --scenario-max-seconds 1800 \
  --terminal-drain-seconds 600 \
  --artifact-root artifacts/perf
```

该场景为每个 synthetic cluster 建立两个独立 attempt：

1. 聚合与抢占链：先对同一 attempt、node 和 GPU 连续提交两个同等级 `XID 48
   RESET_GPU` 事件，二者必须复用同一 incident 和 workflow；前一 workflow 完成
   `MARK_UNSCHEDULABLE` 与 `STOP_WORKLOADS` 后，再提交
   `SXID 11001 RESET_ALL_GPUS_NVSWITCHES`。containment 已完成、没有物理步骤在飞，
   这是 clean boundary：强事件在同一 workflow 记录内抢占，弱计划尚未执行的步骤进入
   `superseded_step_indexes`，fabric reset 作为该节点的 `branch:<node>:successor:1`
   立即执行并只继承这两个仍有效的 containment step；若抢占落在在飞的物理步骤上，
   则仍是带 `preempt_predecessor` 的跨记录 successor，审计按两种形态分别计数。
   模拟 executor 将 full fabric reset 返回 `FAILED`；该步骤位于 DAG 记录的节点
   分支上，控制面必须在同一 workflow 记录内把该分支升级为 `RESTART_NODE` 梯级
   （`BRANCH_ESCALATED` 事件），并在节点回来后完成其后的
   `VALIDATE_GPU/VALIDATE_HOST/VALIDATE_FABRIC/RESTORE_SCHEDULING`，记录以
   `SUCCEEDED` 结束。
2. 精确 reset 升级链：第二个 attempt 单独创建 `RESET_GPU` workflow，模拟 executor
   将 `RESET_GPU` command 返回 `FAILED`；该记录是线性单节点计划，控制面必须先把它
   原地长成单分支 DAG，再同样在记录内升级为 `RESTART_NODE` 梯级并在节点回来后以
   `SUCCEEDED` 结束。

模拟节点自身不产生遥测，reboot 之后的 post-action validation 只接受晚于 reboot
barrier（控制面记录的 reboot 步骤时间）的新鲜样本。runner 从创建场景 Job 起到终态排空结束，
在一个 api-ha Pod 内保持一个 `kubectl exec -i` 会话运行播种脚本的 `node-return-validation-watch`
模式（`regional_validation_telemetry.py`，与 §8.4 同一机制）：dispatcher 记录某节点的 reboot
步骤后立即发布该节点的健康 GPU/NVLink 指标（GPU UUID 与 attempt identity 一致）、主机指标和
全部 collector success 状态，模拟"节点回来"，时间戳为实际写入时刻，未严格晚于 barrier 时
再发布；只有 executor 结果而没有步骤记录时不发布。会话在 teardown 清理本轮数据之前结束。
兜底的是等待期间每 30 秒一次的心跳刷新，同样发布该包，每个节点用自己的写入时刻（不再用刷新
脚本的启动时刻）。`summary.json.validation_telemetry` 记录会话、重启与 barrier 到发布的延迟，
`run.json` 以 `validation_telemetry: event-driven+periodic-30s` 标明本口径。发布与刷新只
写本轮 `corr-node-*` 节点，不改生产节点数据。审计要求每集群 2 个 incident、
2 个 workflow（每出现一次跨记录抢占再加 1，每个 reboot-after 后继再加 1），
每个失败 reset 恰好绑定一个 reboot（记录内 `RESTART_NODE` 梯级或
`workflow-reboot-after-<id>` 后继）且全部 `SUCCEEDED` 并 validated；无主 reboot 与
`REPLACE_NODE` 梯级数为 0。正常情况下两条链都是记录内梯级，后继数为 0；集群
remediation budget 无法容纳新梯级时，控制面 fail closed：分支 exhausted（理由含
remediation budget）、记录 `FAILED`，随后由整记录升级的 `workflow-reboot-after-<id>`
完成 reboot；审计接受该形态，但 exhausted 分支必须全部是预算拒绝且其 reboot 已 validated。

```bash
  --aurora-cluster-id "${AURORA_CLUSTER_ID}" \
  --configure-aurora-capacity \
  --confirm-aurora-scaling SET_AURORA_MIN_124_MAX_128 \
  --workflows-per-cluster 4 \
  --ingress-workers 256 \
  --executor-workers 8 \

  --timeout-seconds 1800 \
  --executor-idle-seconds 300 \
  --synthetic-ttl-seconds 3600 \
  --allow-live-registry \
  --confirm-live-registry ALLOW_PERF_CAPACITY_LIVE_REGISTRY \
  --label integrated-32-disabled \
  --artifact-root artifacts/perf
```

其余三轮必须同时替换preset、`--clusters`、`--spool-mode`、`--label`和审批reference。
轮次间的 preset 切换是一次 CONTROL_PLANE_ONLY 发布：从 `*-enabled` 切到 `*-disabled` 时，
角色滚动脚本先把 ingress 滚到 spool=false，再从 spool-worker Pod 的 `http` 容器端口读取
`gpu_fault_telemetry_spool_depth/leased` 等到 0 后才把 spool-worker 缩到 0；Pod 尚未应答只是
继续轮询。发布失败时的自动回滚会重新解析 ingress Pod，不沿用升级阶段记忆的 Pod 名。
`--workflows-per-cluster`正式值固定为4，不能用CLI默认猜测。每个synthetic cluster从
原矩阵选择3条XID与1条SXID，分别覆盖两个reset、一个reboot和一个
diagnostic/fabric reset。当前线上policy编译出的step数分别为`10/10/9/12`，9-step
reboot分支包含post-reboot `VALIDATE_HOST`，12-step SXID分支同时包含diagnostic、
stop、fabric validation与workload restart。
attempt/workload和synthetic Agent上下文在start gate前预置，不计入矩阵。
runner 使用与正式四轮基线一致的 cold-connect 模型。synthetic 节点自己不发遥测，而 post-action validation
只接受晚于 reset/reboot barrier 的样本——barrier 是控制面记录该步骤 `SUCCEEDED` 的时刻（dispatcher 看到
remote command 成功时写入的步骤记录），不是模拟 executor 回传结果的时刻——所以 validation 等的是 runner
何时替节点发布遥测，两条路径都只更新本轮已有 synthetic 节点，不改变身份、workflow 或生产节点数据：

- **事件驱动发布**：整个 workflow 阶段在一个 api-ha Pod 内运行一个 watch 会话（播种脚本的
  `integrated-validation-watch` 模式，`kubectl exec -i`；程序以长度前缀从 stdin 传入，stdin 的其余部分就是
  停止信号，runner 收尾或 runner 进程退出都会关闭它）。会话每秒读取上一轮以来保存过的 workflow，某节点的
  reset/reboot 步骤一被记录就立即发布该节点的健康 GPU/NVLink 指标、主机指标和全部 collector success，
  时间戳为实际发布时刻，每个 barrier 只发布一次；只看到 executor 回传结果、还没有步骤记录时不发布，发布时刻
  若因两个 Pod 的时钟偏差不晚于 barrier，下一轮再发布，直到严格晚于 barrier。会话在本轮 workflow 全部终态、
  stdin 关闭或截止时间时结束，意外中断时最多重启 3 次；`summary.json.validation_telemetry` 记录各会话、
  重启次数、发布数和 barrier→发布延迟的 p50/p95/p99/max。
- **周期刷新（兜底）**：start gate 前以及执行期间每 30 秒刷新 synthetic Agent heartbeat、健康
  GPU/NVLink/RDMA 指标、`load1_per_cpu`、`memory_used_percent`、`filesystem_used_percent` 和该 Agent 实际
  要求的全部 collector success 状态。每个节点使用自己的写入时刻：此前整轮共用刷新脚本的启动时刻，刷新期间
  落下的 barrier 会让后写节点的样本早于 barrier，再多等一轮刷新。

模拟 executor 必须领取真实 remote command、维护 lease/fencing、等待近似动作耗时后
回传 `SUCCEEDED`。默认 `RESET_GPU=8s`、`RESTART_NODE=120s`，所有结果携带
`simulated=true`；禁止调用真实 Node Agent、Kubernetes mutation 或 provider API。
每条领取到的 command 在自己的模拟耗时结束时独立回传结果，空出的 worker 槽立即再领取（并发上限仍是
`--executor-workers`，每次领取不超过空闲槽数，每 Pod 输出 `completion_mode: per-command`）；此前 executor
要等整批领取的 command 全部结束才再领取，一条 120 秒的 `RESTART_NODE` 会扣住同集群其他 workflow 的下一步，
integrated workflow 百分位因此随 harness 的批次阶梯跳动。claim、lease 续约、fencing token 与结果内容不变，
§8.2 使用同一个模拟 executor。

集成 workflow p50/p95/p99 因此衡量的是控制面——ingress/processor、dispatcher 的轮询与唤醒、validation 与
remote command 协议——加上配置的模拟动作耗时；不包含节点自己的采集间隔（生产节点的 GPU 与主机 collector
默认每 15 秒上报，真实 reboot 之后的 validation 还要再等最多一个间隔），也不包含产品 cluster executor 的
领取方式。`run.json` 的 `simulated_command_completion: per-command` 与
`validation_telemetry: event-driven+periodic-30s` 标明本口径，与其他口径的轮次比较时必须分开。
报告统一记录 ingress/processor、workflow/command p50/p95/p99、duplicate、fencing、
budget wait、Aurora、queue drain 和 cleanup。load generator 首次连接错误后重试成功
也必须计入各路径的 `transport_retries`，不能只记录最终 HTTP 成功；模拟 executor
必须按 HTTP 状态或异常类型聚合 `claim_error_counts`，并保存不含 URL、token、
cluster ID 或异常正文的有界时间样本。

runner 在 synthetic registry 注册前记录当前 Min/Max 并核验不低于 `124/128`（高于下限的窗口原样接受），
**从不修改 Aurora**：低于下限时 fail closed，错误指明在 admin-config.yaml 里显式写 `aurora: 124/128` 并用
`gpu-fault-admin config` 应用——runner 没有评审记录，它对 Aurora 的任何修改都会被下一次 `config` 当作他人改动
拒绝（现场：runner 把 82/128 提到 124/128 后，`50-disabled` 与恢复站点配置的两次 `config` 都在修改前 fail closed）。
`--configure-aurora-capacity --confirm-aurora-scaling SET_AURORA_MIN_124_MAX_128` 只确认本轮需要正式窗口，
不授权任何写操作。随后硬校验两个 `db.serverless` 实例均为 `available` 且
CloudWatch 实际容量均不低于 124 ACU；同时
逐个读取所有 control-worker Pod 的 `GPU_FAULT_REMEDIATION_MAX_ACTIVE_*`，要求与下表
对应的 32/50 集群预算完全一致。结果分别写入 `aurora-preflight.json` 和
`remediation-budget-preflight.json`。
runner 在注册前还会把数据面身份 namespace（`GPU_FAULT_PERF_IDENTITY_NAMESPACE`）中的
连接 Secret 镜像到 perf namespace（perf namespace 会跨站点重建而残留旧站点的 CA 与令牌），
身份 namespace 缺少该 Secret 时 fail closed；镜像结果写入 `connection-secret-preflight.json`。

spool模式必须来自正式config-only release。runner逐个核对所有ingress Pod的实际环境、
spool-worker副本数和所有control-worker的五档remediation budget，不允许在线
`kubectl set env`。报告记录代码release ID、全局配置SHA和三个角色配置SHA。
runner还必须检查live ingress启动命令不含`--limit-max-requests`或对应jitter参数；
旧release仍使用请求计数回收时在注册synthetic cluster前fail closed，不能用“每轮先
重启worker”把累计请求数清零后宣称稳态容量通过。检查结果写入
`ingress-process-model-preflight.json`。

集成runner的最终verdict必须验证：

```text
固定P0/P50/P100请求数量完全一致
mixed ingress Indexed Job = Complete
P0（NVIDIA_KERNEL、FABRIC_MANAGER_LOG）与证据路径 HTTP 429/503 和客户端错误均为 0
普通遥测路径（GPU_INVENTORY、GPU_METRICS、HOST_TELEMETRY）允许 §6.1 的 reserved 503，其占比 ≤ 2%（记入 ingress.reserved_rejections / reserved_rejection_share）；429 与其他非 2xx 均为 0。ingress 普通档并发由 preset 的受管节点数派生（50 集群 preset：2560/进程），固定 1000 时该占比曾达 0.58–3.85%
所有路径首次transport retry均为0
incident/workflow数量 = clusters × 4
所有action workflow = SUCCEEDED
remote command数量 = clusters × 30
所有command终态且result_details.simulated = true
workflow step数量位于8..12
reset、fabric reset、reboot、containment和restore operation均有覆盖
duplicate claim/idempotency/workflow step = 0
fencing mismatch、claim/result error、permanent budget waiter = 0
control-plane Pod集合不变、container restart delta = 0且结束时全部Ready
长动作至少发生一次lease renewal
processor queue和spool恢复到本轮开始前深度
```

若还要验证`RESET_GPU`或fabric reset失败后自动升级为reboot、同等级聚合和preemption，
必须另行执行§8.3的`regional_correlated_action_suite.py`。该套件期望每集群2个初始
incident、2个workflow（每出现一次跨记录抢占或预算拒绝后的reboot-after后继再加1）、2个失败
reset/fabric链各自绑定一个成功且validated的reboot（记录内`RESTART_NODE`梯级；仅预算拒绝时为
`workflow-reboot-after-<id>`后继）；不得把该失败链判据混入本节集成runner的成功Workflow计数。

场景只允许`perf-cap-*` synthetic registration与模拟executor，不调用真实reset、
reboot、cordon、taint、workload mutation或provider API。runner在`finally`中删除Job、
ConfigMap、synthetic registry和本轮数据库记录；任一轮必须确认以下证据后才能继续：

```text
status.json = ok
summary.json.status = PASS
cleanup-workloads.json中的Job/Pod均为空
cleanup-residuals.json中的incident/workflow/command均为0
registry-postflight.json不存在本轮synthetic registration
所有workflow和command均为终态
```

runner进入`finally`后必须临时屏蔽`SIGINT`、`SIGTERM`和`SIGHUP`，显式等待两个Job及
其Pod全部删除。第一次终止信号只改变本轮结果为aborted，不能中断有界teardown；资源或
数据库/registry任一残留仍判失败。

测量窗口结束后，runner最多使用16路并发读取load/executor Pod日志，并按Indexed Job
completion index排序后再写artifact和聚合。该并发只缩短汇总时间，不改变发压窗口、
请求模型、延迟样本或verdict；任一读取异常仍使本轮fail closed。

任一verdict失败、critical alert、队列未排空、cleanup residual、registry未收敛或Aurora
不可用时立即停止后续轮次。失败artifact会进入`aborted/`，不能作为正式PASS证据。

runner在`aurora-preflight.json.initial_scaling`记录每轮开始时的Min/Max（`scaling_modified`恒为false，
`administrator_managed: true`），从不修改Aurora。全部轮次结束后用压测前保存的AdminConfig执行一次
`gpu-fault-admin config`：站点配置连同其`aurora`窗口一起经评审路径恢复（`config`等cluster和两个
`db.serverless`实例在原窗口上重新available），再运行`verify`。若某次`config`以
`AuroraCapacityDriftError`拒绝（live窗口既不是评审当前值也不是目标值；拒绝发生在任何修改之前，不做Aurora
补偿，`desired.json`恢复为变更前配置），按其提示先`gpu-fault-admin deploy --state-dir <dir>`把Aurora收敛回
`desired.json`的窗口，或把live窗口显式写进admin-config.yaml纳入评审后重跑。

## 9. spool A/B 方法

spool enabled/disabled 必须使用：

- 同一 wheel、schema 和 runtime profile；
- 相同集群数、节点数、请求总量和随机种子；
- 相同 Aurora ACU 和控制面资源；
- 相同 load-generator 配置；
- 独立运行目录和 UTC 时间。

配置切换必须通过正式 rollout 流程完成，不能仅修改部分 Pod 环境变量。每轮开始前确认
所有非零副本的 service role、spool 设置和 module digest 完全一致。

## 10. 结果判定

正式结果分为：

- `PASS`：全部门槛满足；
- `FAIL`：任一门槛失败；
- `INVALID`：版本漂移、发压端饱和、指标缺失、清理失败或测试模型不一致；
- `PASS_WITH_LIMITATIONS`：只允许用于不影响核心门槛的明确限制。

报告必须同时记录失败方向，不能只提供平均值或吞吐。以下情况一律不能宣称容量通过：

- 通过大量 429/503 获得较高吞吐；
- 只统计成功请求的延迟；
- 首次transport错误经内部重试成功后不计入客户端错误；
- 全失败时把 latency 写成 0；
- 用多个逻辑集群代替单集群热点测试；
- spool enabled 时只观察 ingress，不观察 spool-worker；
- 使用历史 release 的结果替代当前 release。
- 支持 remediation budget 的 release 只跑生产预算档或只跑原始容量档；
- 未记录五档预算，或缺少 budget active/wait 指标；
- 声称验证 failure-domain budget，但合成 workflow 没有 domain 字段。

`store_bloat`：`before`/`after` 为 `postgres-before.json`/`postgres-after.json` 的 `hot_tables` 换算出的每张热表的
活行、堆页、索引页、`heap_pages_per_live_row`、`index_pages_per_live_row`、`index_min_entries_per_page`、

`preflight_max_heap_pages_per_live_row`/`preflight_max_index_pages_per_live_row` 是本轮开跑时的最差值，
`preflight_bloated_indexes`/`after_bloated_indexes` 是两端规则的结论（每活行页数是报告值，接近空的队列会把它推到几十；
只有结论能说明控制面 `store-compaction` 任务当时有没有事可做），
`recorded=false` 表示 Pod 内快照失败——这样一轮跑在膨胀 store 上的事实留在验收记录里，而不是只在失败后回查。
全新或刚压实的 store 两项比值都远小于 1；上一轮拆卸后未压实的 store 读到十到几十（见 §3.2）。schema v23 之后 `summary.json` 还必须包含 `store_layout`（§3.3）：`mode`（`inline`/`detached`）与 `before`/`after` 两个快照里 `gpu_fault_gpu_metric_latest_clusters`、`gpu_fault_processor_replays` 的分区数、页数与活行；`recorded=false` 表示控制面早于 v23。正式记录还必须注明本轮的标签（`optimistic_bound`/`steady_state`，§3.3）与推导它的两个值——`store_bloat.before.gpu_fault_processor_queue.index_pages_per_live_row` 与 `store_layout.mode`——以及风暴头两分钟的 `pg_stat_activity`采样摘要（活跃语句样本数、`LWLock:BufferContent` 份额、准入 INSERT 并发峰值、autovacuum 份额；本方案 §3.3 的四个数据点正是用这组读数区分的）：一个没有这些读数的 PASS 说不清自己是在哪种 store 上跑出来的。集成runner还必须
记录`control_plane_pod_lifecycle`，至少包含restart总增量、发生restart的Pod、运行中
新增/消失的Pod、counter regression和结束时非Ready的Pod。任一项非空或非零都不得
作为正式PASS。

包含 remediation budget 的 Action 压测还必须保存 `remediation-budget.json`，至少包含
五档配置、各 scope 峰值 active claim、等待次数、最长等待、最终未获执行机会的
workflow 数和 lease 过期释放次数。action runner 在 `summary.json` 旁写出该文件
（`scripts/perf/regional_remediation_budget.py`），全部取自本轮已有数据：`tier` 与 `limits` 是
`run.json.remediation_budget` 的档位与五档配置；`peak_active_claims` 是 §8.2 占用判定在
`history.json` 全部采样中每类 scope 单个 scope 的最大 `RUNNING` 持有数（没有 workflow 申请过的类不出现）；
`waits.refused_claims` 是本轮 workflow 被预算拒绝的申请次数之和（产品在 workflow 上记录的
`remediation_budget_wait_count`），`waits.waited_workflows` 是至少被拒绝一次的 workflow 数，
`waits.longest_wait_seconds` 是这些 workflow 从创建到首个 remote command 的最长时间（预算等待加
dispatcher 拾取）；`never_executed_workflows` 是结束时没有任何 remote command 的 workflow 数；claim
持有到 workflow 终结、不随租约失效释放（详细设计-v2 §9.5），`lease_expiry_releases` 因此记
`not-applicable`。旧 release 的 workflow 记录不带相应字段时该项明确写
`unsupported`，不得用全零文件代替。

原始日志和现场标识只保存在 CI artifact 或私有对象存储。公开仓库可以发布经过复核的
汇总结论，但必须移除账号、ARN、集群名、节点 ID、IP、token、Secret 和内部 DNS。

## 12. 隔离与清理

- Store 微压测使用独立临时 schema。
- API 组合压测使用独立 audit cluster 和确定性 event ID。
- 不在容量测试中执行真实 reset、reboot 或 replace。
- 测试结束无条件删除 Job、ConfigMap、Secret、临时 registry 和数据库记录。
- 清理失败时 `status.json` 必须标记 `aborted`，不得把残缺目录作为正式证据。

### 13.1 公共配置与请求样本

除表格另有说明外，参考实验使用：

- enabled 时 3 个专用 spool-worker Pod，每 Pod 1 个进程；
- disabled 时 ingress PostgreSQL pool max 为每进程 40，spool-worker 为 0；
- enabled 时 ingress pool max 为每进程 48，spool-worker 为 3；

### 13.4 单集群 1000 节点

| 模型 | Spool cluster depth | HTTP 429/503 | Fault p99 | P0/P50/P100 completion p99 | Throughput req/s | Aurora max ACU / CPU |
|---|---:|---:|---:|---:|---:|---:|

| complete-attempt | 4096 | 0 / 0 | 12.83s | 13.17s / 5.66s / 8.80s | 234 | 124 / 39.2% |

第一组的 243 个 429 全部来自
`gpu_fault_telemetry_spool_rejected_total{scope="cluster"}`：3000 条 P100 共用一个

- 500 个 observation、500 个独立 attempt、1000 个容器节点；

priority-only 的延迟直接解释为“depth4096 变慢”。depth 变化的直接结论只有：
单集群 spool 429 从 243 降为 0。

| 集群 | Throughput | Fault p99 | Inventory p99 | GPU metrics p99 | Host p99 | Workflow p99 | Drain |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 32 | +9.9% | +37.6% | -46.5% | -44.5% | -44.8% | -5.9% | -20.1% |
| 50 | +16.8% | +14.6% | -42.5% | -42.7% | -42.9% | -2.5% | -1.6% |

判读：

- enabled在两档都显著降低三类routine telemetry p99，并改善workflow完成p99；
  50集群吞吐收益高于32集群；
- enabled同时提高Fault ingress p99，说明spool写入与fault admission仍竞争Aurora或
  Store I/O资源，不能只按总吞吐选择模式；
- 两个enabled样本都达到128 ACU和100% Aurora CPU，正式突发下没有明显数据库余量；
- 从32扩到50集群后，disabled吞吐下降8.7%，enabled吞吐下降2.9%，而Fault和workflow
  p99继续升高，说明该固定资源配置没有随集群数线性扩展；
- 本组`xact_rollback`绝对值较高，但没有deadlock、HTTP错误或workflow失败；进入生产
  默认前仍须按SQL原因拆分rollback，并至少重复三轮A/A与A/B；
- DNS单次预解析和进程cache消除了此前cold-connect负载Pod产生的DNS查询风暴，本组没有
  任何已恢复或最终transport retry。

这四轮是当前release的综合ingress、workflow和remote-command正式证据，但每种模式仍
只有一个样本。趋势可用于回归和容量判断，不能替代多轮方差、成本和目标SLO评审。

## 14. 参考结果的判读

上述脱敏实验用于容量趋势和回归比较，不直接替代当前 release 的正式 PASS/FAIL。
不采用统一的 P0 ingress p99 固定否决线；每轮结果应结合接收率、拒绝、队列恢复、
动作门槛以及该轮预先批准的延迟预算分别判定：

- 50 集群、Max ACU 64 的样本存在大量 503，不满足摄取和准入门槛；
- 96/128 ACU 的高 Min 样本消除了拒绝，但其秒级准入等待应与该轮批准预算和历史版本
  回归基线比较，不能仅因超过某个统一固定值判 FAIL；
- 单集群完整模型实现零拒绝，P0 completion p99 为 13.17 秒，该值用于判断完成阶段
  容量和版本回归，不等同于统一的 ingress 否决项。

完整单集群模型中 Aurora CPU 仅 39.2%，但 processor lane 增量为：

```text
node lane：435 次，平均等待 2.45s
attempt lane：374 次，平均等待 1.72s，最大 10.92s
cluster lane：0 次
retry reschedule：0
```

这说明该模型的主要瓶颈已经从 Aurora 容量转移到 node/attempt ordering lane 与
admission holder 时间。control-worker 出现的 CPU throttling 总量很小，不足以解释
秒级延迟。

## 15. 性能建议

1. **短突发不要只提高 Max ACU。** 已知演练或大规模作业窗口前应预置 Min ACU，并在
   `ServerlessDatabaseCapacity` 实际到位后再发压。结束后按成本策略恢复，不能只看
   `modify-db-cluster` 已返回。
2. **50 集群优先使用 enabled + 专用 spool-worker。** 它显著改善 P50 完成延迟和
   普通遥测接收率；但数据库饱和时可能增加 Fault admission 延迟，必须同时观察
   Aurora CPU、DBLoad 和 Fault p99。
3. **1000 节点单集群建议 spool cluster depth 至少 4096。** 3000 条同步 P100 在
   depth1024 下会触发预期 429。4096 只应作为超大集群 profile 的容量值，不应不经
   验证直接改成所有站点的全局默认；同时必须保留 per-cluster 上限。
4. **优先缩短 node/attempt lane holder。** 将可并行的解析、证据写入和策略预计算移到
   lane 外，只在短事务中提交 incident/workflow；纯 telemetry/evidence 应按冲突域
   与 node-control 分离。
5. **为 lane holder 增加完整性能证据。** artifact 必须采集
   `gpu_fault_processor_lane_holder_seconds` 的 path 标签，并把 before/after delta
   写入 summary，不能只保存累计 lane wait。
6. **batch delay 作为候选配置继续 A/A 与 A/B。** 当前值改善 completion p99，但
   rollback 增加；至少重复 3 轮并核对 rollback 原因、pool checkout 和 admission
   batch expired 后再进入生产默认。该 delay 现已是 AdminConfig 字段
   `spec.processor.admissionBatchDelaySeconds`（默认 0.002，预设不改），A/B 轮次按站点改值即可，
   不改代码；候选区间 20–50 ms：按 ingress 普通准入批量上限 64 估算，约 1,000 req/s 下每批从
   平均 9.7 条升到约 29–48 条，准入事务数下降 3–5×，代价是不超过该延迟值的额外接收时延。
   该窗口现已自适应：flush 时长 EWMA 超过 100 ms 时自动抬高到 `spec.processor.admissionBatchDelayMaxSeconds`
   （默认 0.05）并在恢复后回落，A/B 只需比较基础延迟。并发准入 flush 的站点级区间（上限 `admissionFlushConcurrency`
   等，默认 96/48/24；下限 `admissionFlushConcurrencyFloor` 等，默认 96/48/12——普通与故障层下限等于上限，即实测通过的
   固定上限；由 12 个 ingress 进程分摊，进程内控制器只在区间打开时动作：饱和且 flush EWMA 低于 0.15 s 时开一槽、EWMA
   超过 0.30 s 时减半余量、每次变动都要求当前层级已完成一代 flush）见管理员容量配置 §4.6。本站的三个校准点（同一
   schema v22、同一 32 集群突发、12 个进程）：**固定 24**（每进程 2）时 integrated-32 以 517 req/s 运行、普通遥测
   reserved 503 占比 18.7%（4,601 个请求在队列中到期、每进程积压 762–801、每次 flush 0.59 s）；**固定 96/48**（每进程
   8/4）时 1,051 req/s、reserved 503 与 P0 503 均为 0、每次 flush 81 ms、`BufferContent` 1%、活跃语句峰值 113 持续约
   5 s；**自适应 48..192**（每进程 4..16，阈值 1.0/2.0 s）时 543 req/s、reserved 503 占比 35.8%（8,796 个）、P0 出现
   503、故障 p50/p99 0.35/28.4 s、每进程上限落在 20–23 并震荡（开 81 次、收 51 次）、pending 峰值 615–831、每次 flush
   平均 1.08 s，数据库出现 69 s 的风暴（活跃语句峰值 142、`BufferContent` 36%、CPU 31%、`XactSync` 23%）——全站约 250
   个并发 flush 让队列表的页锁 convoy 重现，而 1.08 s 低于 2.0 s 的关闭阈值，槽位始终没有收回。结论：这套 schema 上
   数据库能承受约 100 个并发准入 flush；本站历史的 1,400+ req/s（192 槽）早于 v20 按 writer 分行的账本，仅靠并发数不可
   复现，每次 flush 的条数也不是合并窗口能加的杠杆（见管理员容量配置 §4.6 的闭环模拟）。默认配置的验收目标因此是
   1,000+ req/s、reserved 503 与 P0 503 为零；复核时读取 `gpu_fault_processor_admission_batch_in_flight_limit`
   （普通/故障层应恒为 8/4，`..._in_flight_limit_raised_total`/`..._lowered_total` 应为 0；证据层可在 1..2 间移动）、
   `..._expired_total`（应为 0）、每次 flush 的平均时长（`gpu_fault_processor_admission_batch_flush_seconds_sum / _count`，应接近 81 ms），以及
   `pg_stat_activity` 采样中的活跃语句峰值（约 113）与 `BufferContent` 占比（约 1%）；若管理员放开区间，控制器收槽的
   唯一正当理由仍是 flush 时延真正上升。
7. **区分 cold 与 warm connection SLO。** cold 结果包含 TCP/TLS 建连，warm 结果衡量
   稳态服务能力；两者都要保存，不能用 warm 结果替代公网/NLB 首次请求门槛。
8. **负载工具必须验证 processor 最终响应。** ingress 202 只表示已入队；dry-run 曾
   发现后台 422。正式工具应把 receipt/final response 非 2xx 直接判 FAIL。
9. **隔离合成 registry 的周期性云查询。** audit cluster 使用占位 HyperPod 名称，刷新它
   只会产生 `ResourceNotFound` 日志。后台身份刷新按注册的 `synthetic` 标记跳过这些
   条目（它每一轮读 registry 当前快照，套件在线登记的集群也不例外），不污染日志、
   不占控制面资源。
10. **继续提高 ACU 前先看瓶颈是否仍在数据库。** 当 Aurora CPU 已低于约 70%–80% 而
    lane wait 仍为秒级时，继续加 ACU 收益有限，应转向 transaction、lane 和
    completion 并行优化。
11. **不要为了通过原始容量档直接提高生产 remediation budget。** 生产预算档先证明
    默认值能限制故障风暴且不饥饿；原始容量档只在隔离环境提高额度，用于暴露
    dispatcher、Store 和 Executor 的下一层瓶颈。若业务确实要求每集群同时修复超过
    2 个同资源类 workflow，必须以多轮容量证据、故障域风险和恢复时间目标共同审批。
12. **cold-connect 突发暴露的是 accept 队列，不是 event loop。** 50 集群 integrated 套件（50 个发压 Pod × 256 个阻塞
    worker、cold-connect、每 api-ha 进程约 1,066 个并发连接）被全部 202 接收（0 非 2xx），三个 api-ha Pod 却在突发中途
    同时被 liveness（5 s × 2）重启。本地复现（`scripts/perf/ingress_event_loop_burst.py`：真实应用 + 渲染后的 ingress
    环境 + 4 个 uvicorn 进程钉在 8 核、50 集群 × 85 个 cold-connect worker、flush 桩 0.5 ms CPU + 60 ms I/O）给出机制：
    4,250 个连接里 3,600–3,900 个在整个突发期间停在 service 监听套接字的内核 accept 队列（进程内各 550–740 个），探针连接
    排在同一 FIFO 后面，时延 = 队列深度 / 接受速率（3.6 s @ 1,090 req/s；应用内 0.1 s；按线上 4,266 连接/Pod、
    390 req/s/Pod 折算约 11 s）。被否定的假设：GIL 饥饿（解码线程 32 与 8 完全一致，空闲线程最大 GIL 等待 0.17–0.27 s、
    等于 GC 停顿）、flush 槽位（16 与 8 一致；2 槽因请求排在进程内反而让探针中位数降到 94 ms，代价是 1,074 个 503）、
    GC（gen-2 停顿 0.15–0.6 s 是最长单次停顿，远不到 5 s）。修正：专用 `livez` 端口（同一突发下探针中位数 10 ms、
    最大 0.61 s）、10 s × 3 的探针参数、`gc.freeze()`（GC 总耗时 −26%、吞吐 +7%）。验收时读
    `gpu_fault_listen_accept_queue_connections`、`gpu_fault_event_loop_lag_seconds` 直方图与
    `gpu_fault_gc_collection_seconds_max`。把 flush 桩的 CPU 设成 8 ms/条（即假设 81 ms 的 flush 全是 CPU）只得到
    583 req/s 与 43% 的 503，与线上 1,175 req/s、0 非 2xx 不符——线上 flush 的 81 ms 主要是 Aurora 往返等待。
    后续（同一复现加 `--launcher uvicorn|serve`、`--keep-alive`、每套接字 accept 队列与各 worker 份额）：service 端口改为
    per-worker `SO_REUSEPORT` 套接字在 4,250 并发 cold 连接下与共享套接字在噪声之内（1,141/1,135 对 1,110/1,097 req/s，客户端
    p99 4.18/4.03 对 4.32/4.51 s，各 worker 份额 24.7–25.2%，四条队列忙/闲比 1.13–1.30），在 5,500 并发（超过 `somaxconn` 4096）下
    是决定性的：共享套接字队列钉在 4,097、SYN 丢弃后 1/3/7/15 s 重传，961 req/s、73 个 503、客户端 p99 27.9 s、最大 31.6 s；
    四个套接字共排 5,089 个连接（每个 1,051–1,186），1,117 req/s、0 非 2xx、p99 5.35 s、最大 5.44 s。keep-alive 闭环客户端
    （4,250 条长连接、服务端 `--timeout-keep-alive 100`）把连接建立从 41,500 次降到 4,250 次、accept 队列中位数 0，但请求全部进入
    进程内准入队列（890 对 1,100–1,140 req/s、p99 10–12.6 s）——这是闭环无思考时间的发压形状，真实 collector 每 30–300 s 才发一次。
    结论：SO_REUSEPORT 是容量杠杆（每 Pod 可排队连接 ×4），不是吞吐杠杆；长连接减少握手，不减少准入等待；两者都不改变 liveness
    （专用端口探针 p50 8–39 ms）。
