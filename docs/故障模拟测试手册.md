# GPU 故障模拟测试手册

## 1. 目标

测试体系使用 `testcases/fault-scenarios.yaml` 记录故障场景。每条 test case 必须包含：

- 唯一 ID、标题、分类、验证层级和风险等级；
- 问题描述、故障注入方式和可审计预期；
- `pytest`、受控 `command` 或人工 `procedure`；
- 可选的公开 `evidence.verdict`。

模拟事件不等同于真实硬件故障。报告必须区分以下验证层级：

| 层级 | 含义 |
|---|---|
| `unit` | 单一函数或模型边界 |
| `component` | 真实策略、Collector、Store或adapter的确定性测试 |
| `integration` | API、workflow、adapter或持久Store的多模块测试 |
| `end-to-end` | 从事件输入到决策、workflow、通知或Agent barrier的闭环 |
| `staging` | 隔离HyperPod测试集群中的受控验收 |
| `live` | 真实HyperPod环境中的人工或显式command验收 |

区域CPU控制面与GPU数据面分离部署的完整验收在
[区域模式端到端验收测试用例](区域模式端到端验收测试用例.md)。`GF-REGIONAL-*`
并非全部人工执行：当前目录同时包含 `manual`、`pytest` 和 `command` 三种自动化类型。
真实进程、身份、网络和爆炸半径验收通常为manual或显式command；纯协议和状态机契约可由
pytest覆盖。

## 2. 安全边界

默认runner只执行 `risk: non-destructive` 且 `automation: pytest` 的场景，不连接生产
Kubernetes，也不调用GPU reset、node reboot或warm-spare切换。

真实集群command必须同时满足：

1. 使用 `--include-live`；
2. 显式提供 `--case`；
3. case在catalog中声明为 `automation: command`。

人工场景即使使用 `--include-manual`，runner也只生成`NOT_RUN`记录，不执行命令。

promoted regional runner 默认使用 `formal` scope并要求正式 predecessor。管理员需要
只执行明确选择的case时，使用：

```bash
GPU_FAULT_ACCEPTANCE_EXECUTION_SCOPE=selective \
GPU_FAULT_ACCEPTANCE_SELECTION_REFERENCE=CHG-12345 \
python3 scripts/e2e/regional/<runner>.py --case <case> ...
```

selective 只跳过正式顺序 predecessor，不跳过该case自己的preflight、维护窗口、
confirmation、节点空闲、身份/pin、停止条件和清理。报告必须保留
`execution_scope=selective`、审计引用与`formal_sequence_satisfied=false`；该PASS不能
被formal runner用作后续case的前置证据。

风险等级的唯一词表在
[区域模式端到端验收测试用例 §2.2](区域模式端到端验收测试用例.md#22-风险等级词表唯一取值来源)
和 `tools/run_fault_test_cases.py` 中的 `RISK_VALUES`。本文件不复制第二份完整词表。

节点生命周期只支持以下生产路径：

| 风险 | 动作 | 约束 |
|---|---|---|
| `destructive` | Node Agent执行GPU/fabric reset | 必须quiesce、无GPU client、签名、fencing和动作后验证 |
| `destructive-provider-reboot` | HyperPod原节点reboot | `NodeRecovery=None`、二次cluster确认和provider幂等 |
| `destructive-warm-spare` | `HEALTHY_WARM_SPARE_ONLY`本地切换 | 只使用已纳管健康spare，故障实例保持存在并隔离 |

`destructive-provider-replace`不是合法risk，也不是可执行测试路径。
`BatchReplaceClusterNodes`只能作为否证目标：整个窗口内不得出现该调用；warm spare不足时
必须失败并告警，不得回退到provider replace。

任何真机测试都必须：

- 明确目标Region、context、cluster ID、节点和维护窗口；
- 确认HyperPod `NodeRecovery=None`；
- 记录当前release、Runtime Profile、required/compatible pin和节点Agent generation；
- 使用隔离节点或受控训练任务，预先定义停止条件和回滚；
- 把原始报告写入`artifacts/fault/`、CI artifact或私有证据库；
- 不把用户态`/dev/kmsg`写入描述成NVIDIA硬件真实故障。

## 3. 查看和执行 Test Case

列出默认可执行case：

```bash
python3.12 tools/run_fault_test_cases.py --list
```

按分类或层级筛选：

```bash
python3.12 tools/run_fault_test_cases.py \
  --category restart-guard

python3.12 tools/run_fault_test_cases.py \
  --level end-to-end
```

执行指定case：

```bash
python3.12 tools/run_fault_test_cases.py \
  --case GF-RST-001 \
  --case GF-RST-002 \
  --report "artifacts/fault/restart-guard-$(date -u +%Y%m%dT%H%M%SZ).json"
```

执行全部默认非破坏性pytest场景：

```bash
make fault-test-cases
```

默认仍为单worker串行。只对runner判定为parallel-safe的Case启用资源锁并行：

```bash
make fault-test-cases FAULT_TEST_WORKERS=4
```

非破坏性pytest默认使用`local-test: shared`锁，并在子进程中清空
`GPU_FAULT_STORE_URL`与`GPU_FAULT_TEST_POSTGRES_URL`，避免管理机环境变量让本地
Case误连线上数据库。command和manual Case默认使用全局独占锁；只有catalog中显式
声明`execution.parallel_safe=true`并列出资源锁的command才能并行。

CAP-005使用随机临时database，但仍共享同一PostgreSQL/Aurora服务器的CPU、I/O、
连接、WAL和锁管理器，因此声明：

```yaml
execution:
  parallel_safe: true
  environment: inherit
  locks:
  - {resource: postgres-server, mode: exclusive}
  - {resource: cap005-workdir, mode: exclusive}
```

它可以和隔离的本地pytest同时运行，但不能和使用同一数据库服务器的CAP、HA、CMD、
processor、notification或live Store测试并行。推荐入口：

```bash
GPU_FAULT_STORE_URL='<validation PostgreSQL/Aurora admin DSN>' \
  make fault-test-cases-with-cap005
```

该入口把CAP-005显式加入默认pytest集合，并用4个worker调度。`--include-live`仍是
command Case的安全确认；`--also-case`不会放开其他未点名的command。

执行显式登记的live command：

```bash
python3.12 tools/run_fault_test_cases.py \
  --case GF-LIVE-000 \
  --include-live \
  --report "artifacts/fault/live-passive-e2e-$(date -u +%Y%m%dT%H%M%SZ).json"
```

把人工场景加入报告但不执行：

```bash
python3.12 tools/run_fault_test_cases.py \
  --include-manual \
  --report "artifacts/fault/all-with-manual-$(date -u +%Y%m%dT%H%M%SZ).json"
```

## 4. 报告与证据

runner对每个pytest或command case启动独立进程，任一失败都会使最终进程返回非零。
每条结果包含：

- case ID、层级、risk、问题、注入方式和预期；
- `PASS`、`FAIL`或`NOT_RUN`；
- pytest node ID或command、耗时和原始输出；
- 要求trace的case产生的`processing_trace`。
- `scheduling`中的queued/start/completed时间、lock wait、worker、资源锁和环境模式。

`--workers`默认值为1，因此现有命令与报告顺序保持不变。并行执行时报告中的
`results`仍按声明顺序排列，不按实际完成顺序重排。

报告级verdict为：

| verdict | 含义 |
|---|---|
| `PASS` | 所有已选case都执行并通过 |
| `PASS_WITH_LIMITATIONS` | 已执行case通过，但报告包含`NOT_RUN` |
| `FAIL` | 至少一个已执行case失败 |
| `NOT_RUN` | 没有case实际执行 |

要求processing trace的case如果没有输出合法结构，即使pytest退出码为0也会判`FAIL`。

默认报告位置：

```text
artifacts/fault/fault-tests-<UTC timestamp>.json
```

CI执行unit和component层级，artifact名称为`fault-test-report`，保留30天，失败时也上传。

公开catalog中的`evidence`只允许`verdict`和`verified`：

```yaml
evidence:
  verdict: PASS
  verified:
    case_digest: <sha256>
    components:
      control_plane: <sha256>
      executor: <sha256>
      node_runtime: <sha256>
```

合法值为`PASS`、`NOT_RUN`、`BLOCKED`和`SUPERSEDED`。执行时间、环境、集群名、操作人、
报告路径和现场notes不进入catalog；它们属于runner报告或私有证据库。`SUPERSEDED`必须
使用顶层`superseded_by`指向另一条case。

`verified`只允许出现在`PASS`上，且`PASS`必须带它：`case_digest`是本用例规范性字段的
摘要，改写断言后旧结论立即失效（load时硬失败）；`components`是被验证的组件源码摘要，
漂移由`scripts/build-fault-evidence-index.py`推导成`STALE`并要求下个维护窗口重新执行。
`EVIDENCE_UNBOUND_PASS_CASES`里的历史live用例只带`case_digest`，报`UNBOUND`；该名单是
单向棘轮，只允许在真机重新执行后变短，不允许事后补摘要。完整语义见
`docs/evidence/fault/README.md`。

公开长期证据只通过`docs/evidence/fault/manifest.yaml`登记脱敏报告。目前公开manifest
可以为空；不得在本文引用未纳入manifest的环境专属JSON。规范索引由以下命令生成：

```bash
python3 scripts/build-fault-evidence-index.py
python3 scripts/build-fault-evidence-index.py --check
```

## 5. Test Case维护规则

1. 新增故障处理分支时，先增加或更新catalog case。
2. ID发布后不得复用；语义变化较大时创建新ID。
3. pytest case必须引用真实、可收集且只验证一个明确场景的node ID。
4. command case必须使用参数数组，不能依赖隐式shell或当前kubectl context。
5. manual case的procedure必须指向真实存在的Markdown标题锚点。
6. `expected`必须描述外部可观察结果，不能只写“系统正常”。
7. 缺少证据时预期`INCONCLUSIVE`、`BLOCKED`或`QUARANTINE`，不得猜测成功。
8. 破坏性case必须记录维护窗口、隔离节点、回滚方式和操作证据。
9. 分离部署case必须证明CPU控制面没有直接改变GPU节点或workload。
10. 集合一致性断言必须先限定边界，例如只比较
    `GPU_FAULT_REMOTE_EXECUTION_OWNERS`对应的owner。
11. 读取进程实际配置时，在目标Pod构造对象读取属性，并逐副本验证；不得只从env反推。
12. 非破坏性case不得为了制造失败而修改运行中adapter开关、allowlist或release pin。
13. 注入非终态记录时必须在同一case提供清理步骤，避免长期触发告警。
14. 代码依据优先引用完整Python符号；不得维护易漂移的源码行号。
15. 告警case必须区分两条独立路径：
    - 管理员动作邮件：代码生成通知，经SES发送；
    - 运维指标告警：`/metrics -> ADOT -> AMP -> SNS`。
16. AMP告警必须验证指标导出、ADOT keep、实际加载的AMP rule、SigV4查询、firing和resolve。
17. 副本数为0的Deployment仍可能引用ConfigMap；清理检查必须包含ReplicaSet和回滚引用。
18. 风险、level、automation和evidence字段只使用runner定义的闭合集合。
19. 并行策略必须显式声明`execution.parallel_safe`、`environment`和`locks`；
    未声明的command/manual默认全局独占。新增资源锁时先补调度器冲突测试。

`AdvisoryNotificationService.dispatch_remote_completion`只为成功的remote command生成
动作完成通知。因此“命令长期PENDING”必须由remote-command指标告警覆盖，不能预期SES
动作完成邮件。

## 6. 公开覆盖范围与事实源

当前公开目录覆盖：

- NVIDIA XID Catalog逐项kmsg格式重放、XID 154、companion XID和NVLink5 decode；
- SXID、DCGM、GPU inventory、host、EFA/RDMA、训练进度和日志Collector；
- training terminal、allocation、restart budget、幂等和attempt generation fence；
- 区域启动守卫、鉴权、remote command、HA、容量、通知和最小权限；
- reset、reboot和warm spare等人工破坏性验收。

权威顺序为：

1. `testcases/fault-scenarios.yaml`：case ID、risk、automation和当前公开verdict；
2. `tools/run_fault_test_cases.py`：可接受schema和runner行为；
3. [区域模式端到端验收测试用例](区域模式端到端验收测试用例.md)：区域风险词表和详细验收；
4. 本文件：通用执行方法和真机procedure锚点。

本文件不记录客户环境、集群名、节点ID、release digest或某次执行的PASS/FAIL详情。
原始结果保存在CI artifact或私有证据库。

## 7. 真实 XID 验证分级

第7章只提供当前人工procedure。执行时由训练提交工具读取站点声明的Profile，禁止硬编码
版本：

```bash
STATE_DIR="${GPU_FAULT_STATE_DIR:?set GPU_FAULT_STATE_DIR}"

gpu-fault-admin preflight --state-dir "${STATE_DIR}"
gpu-fault-admin verify --state-dir "${STATE_DIR}"
gpu-fault-admin status --state-dir "${STATE_DIR}"
```

`verify`必须确认Profile已注册、无warnings，并与CPU、Collector、Watcher、Installer和
节点Agent一致。真机报告写入`artifacts/fault/`或私有证据库，不修改公开catalog以外的
源码文件。

### 7.1 kmsg 格式重放

`GF-XID-KMSG-001`至`GF-XID-KMSG-172`以及对应B200 family由catalog生成器展开。每条case
把NVIDIA格式record作为内存输入交给`KernelLogCollector`，再进入kernel ingestion API、
normalizer、固定Catalog和策略引擎。

该层验证parser、PCI BDF、boot ID、monotonic timestamp、evidence reference和策略分支，
不会写真实`/dev/kmsg`，也不会改变GPU状态。

```bash
python3.12 tools/run_fault_test_cases.py \
  --case GF-XID-KMSG-094 \
  --report "artifacts/fault/xid-kmsg-094-$(date -u +%Y%m%dT%H%M%SZ).json"

python3.12 tools/run_fault_test_cases.py \
  --category xid-kmsg-replay \
  --report "artifacts/fault/xid-kmsg-all-$(date -u +%Y%m%dT%H%M%SZ).json"

python3.12 tools/run_fault_test_cases.py \
  --category xid-kmsg-replay-b200 \
  --report "artifacts/fault/xid-kmsg-b200-all-$(date -u +%Y%m%dT%H%M%SZ).json"
```

### 7.2 HyperPod 三节点 XID 11 重启

`GF-LIVE-XID11-001`验证XID 11触发训练workload restart，不执行GPU reset或节点动作。

```bash
gpu-training-submit \
  scripts/e2e/regional/manifests/training/xid11-three-node-pytorchjob.yaml \
  --site "${SITE_FILE}" \
  --job-id <unique-job-id> \
  --attempt-number 1 \
  --restart-budget 1
```

执行前确认三个Pod位于不同GPU节点、24-rank NCCL heartbeat正常、attempt observation
包含24个真实GPU UUID。只向控制面重放XID 11格式事件，不写节点`/dev/kmsg`。

成功标准：

- Catalog决策为`RESTART_APP`；
- 原三个Pod UID消失，新attempt重新分布到三个节点；
- restart budget只增加一次；
- NCCL all-reduce恢复；
- 不出现GPU reset、node reboot或replacement。

### 7.3 KernelLogCollector 隔离 FIFO 验证

`GF-LIVE-KERNEL-COLLECTOR-001`验证节点实际安装的Collector二进制，但不写真实
`/dev/kmsg`。

1. 确认systemd Collector为enabled/active且无重启。
2. 用只读debug Pod确认主进程持有`/dev/kmsg`文件描述符。
3. 将`scripts/e2e/regional/manifests/kernel-collector-passive-validation.yaml`渲染到`/tmp`；
   临时控制面保持simulation且关闭dispatcher。
4. 使用权限`0600`的FIFO和一次性Collector重放普通record及重复sequence的XID 11。
5. 验证普通记录被过滤、重复sequence只产生一份evidence、boot ID和attempt关联正确。
6. 确认生产训练Pod UID未变化，再删除临时资源。

### 7.4 真实 /dev/kmsg 用户态写入

`GF-LIVE-KMSG-XID11-001`只允许在无运行中managed workload的隔离节点执行。写入前记录
Collector PID、重启次数、boot ID、collector status和evidence基线。

```bash
printf '%s\n' \
  '<3>NVRM: Xid (PCI:0000:59:00): 11, pid=4242, name=python, Invalid or corrupted push buffer stream' \
  | sudo tee /dev/kmsg >/dev/null
```

不得加入`test_id`或循环写入。必须用Collector产生的boot ID、kernel sequence、
monotonic timestamp和observed time识别新增记录。无workload时不得执行workload restart、
GPU reset、node reboot或replacement；节点最终保持Ready且无遗留taint。

该测试只能证明生产Collector读取了真实`/dev/kmsg`，不能证明driver或硬件产生XID。

### 7.5 HyperPod 单独 XID 45 Fabric Manager 重启

`GF-LIVE-KMSG-XID45-SOLO-FM-20260724`和邮件case验证XID 45无companion时的完整
`RESTART_FABRIC_MANAGER`链路。

前置条件：

- 当前Profile的`fabricManagerRestart`由`gpu-fault-node-agent` OWN；
- Agent ACTIVE，artifact/config/profile pin一致；
- allowlist包含`RESTART_FABRIC_MANAGER`；
- 训练heartbeat正常，已记录Fabric Manager MainPID。

只向一个目标节点写入一条标准XID 45，等待完整correlation window。成功标准是
`FINALIZED`且无companion、workflow完成`FREEZE_EVIDENCE`和
`RESTART_FABRIC_MANAGER`、MainPID变化、训练Pod和attempt不变。启用邮件时还必须验证
固定模板通知为`SENT`且幂等重放不重复投递。

### 7.5.1 XID 45 跨副本与 companion 真机关联

本节覆盖：

- `GF-LIVE-XID45-AURORA-HA-20260724`：不同控制面副本接收XID 45和XID 14，验证Aurora
  状态及finalize lease；
- `GF-LIVE-KMSG-XID45-XID14-20260724`：同一节点`/dev/kmsg`先写XID 45，后写相同PCI
  BDF的XID 14。

两条case都必须等待完整窗口，并确认XID 45继承XID 14的`IGNORE/NO_ACTION`、复用同一
incident且不创建workflow。临时canary和注入Pod必须在报告完成后删除。

### 7.6 Kernel log SXID 闭环

`GF-LIVE-SXID-KMSG-001`在维护窗口验证SXID 10003从真实`/dev/kmsg`到全GPU/NVSwitch
reset和训练恢复的链路。

必须保存训练attempt、Pod UID、GPU inventory、Fabric Manager PID、Collector基线和
restart budget。执行顺序必须包含：

```text
STOP_WORKLOADS
-> QUIESCE_GPU_SERVICES
-> VERIFY_NO_GPU_CLIENTS
-> RESET_ALL_GPUS_NVSWITCHES
-> RESTORE_GPU_SERVICES
-> VALIDATE_GPU
-> VALIDATE_FABRIC
-> RESTORE_SCHEDULING
-> RESTART_WORKLOAD
```

任一节点缺少完整GPU inventory、generation变化、无客户端门禁失败或服务无法恢复时，
整个workflow失败关闭，不允许部分reset。

### 7.7 双节点 SXID quiesce 租约

`GF-LIVE-SXID-MULTINODE-LEASE-001`验证quiesce停止kubelet后，控制面在有界维护窗口内
使用持久化的同一Agent generation完成双节点barrier。

必须覆盖：

1. quiesce成功且generation不变时允许继续；
2. quiesce未完成时heartbeat stale，reset不得发出；
3. 超过维护窗口，reset不得发出；
4. 任一节点generation/incarnation变化或Agent非ACTIVE，整个barrier中止。

### 7.7.1 三节点 GPU 训练的三并发聚合与 reset

`GF-LIVE-THREE-CONCURRENT-RESET-001`使用真实三节点、24-GPU受管PyTorchJob，验证
workload observation、XID和SXID并发到达时只形成一个incident、一个workflow和一个
reset command。

不得伪造allocation或GPU UUID。成功标准包括：

- 三请求成功且processor无deadline exceeded；
- 单一workflow完成stop、quiesce、reset、restore和GPU/Fabric validation；
- source/target GPU数量均为24；
- 三个旧Pod UID全部替换，新attempt恢复24-rank NCCL；
- restart budget只增加一次；
- 节点最终Ready、可调度且inventory不变。

### 7.7.2 双节点 XID 95 reset 与训练恢复

`GF-LIVE-XID95-DUAL-RESET-RESUME-20260724`使用双节点、16-GPU受管PyTorchJob。通过
distributed XID API一次提交两个`synthetic=true`的XID 95事件，每个节点指定一张真实
参与训练的GPU。

完整workload停止后，两个barrier participant才可分别执行无客户端校验和reset。两者都
必须`COMMITTED`，回执中的`reset_gpu_uuids`与请求一致；任何participant未PREPARE、
generation变化或映射不完整时整个barrier中止。验证通过后启动新attempt且restart budget
只增加一次。

### 7.8 真实硬件故障注入未实现

本仓库不提供让GPU硬件或NVIDIA driver真实产生指定XID的故障注入工具、Manifest或
管理员命令。`GF-LIVE-004`是`BLOCKED`能力边界，不是可执行验收方法。

以下已有能力都不能替代真实硬件注入：

- synthetic XID/SXID API；
- 内存或FIFO格式重放；
- 用户态写入`/dev/kmsg`；
- DCGM或NVIDIA Field Diagnostic；
- GPU reset、节点reboot或warm-spare恢复。

管理员不得为了满足该case而自行下载或执行未纳入release、未固定摘要、未经过安全审查
的外部注入工具。未来只有在仓库正式交付受检实现、权限模型、维护窗口、回滚和证据契约
后，才能把`GF-LIVE-004`从`BLOCKED`改为可执行状态。

### 7.9 重启 attempt 代际时间栅栏

`GF-ATTEMPT-GENERATION-FENCE-*`是pytest场景组，验证延迟XID/SXID不会对新attempt重复
执行动作。主要分支包括：

- 同级或较弱旧事件只链接原incident，不新增workflow；
- 严格更强旧事件只排队一个successor；
- 新attempt启动后的新事件正常处理；
- 缺少可信started_at时保持fail-safe；
- `source_event_time`优先于收集时间；
- 节点独占successor等待仍运行的predecessor；
- workload-only恢复不继承旧节点动作。

使用catalog按category或case ID执行，不需要真机注入。报告必须保留所有时间戳、
predecessor/successor和动作等级。

### 7.10 HyperPod XID 74 寄存器分支真机验证

这些case使用特权Pod向目标节点真实`/dev/kmsg`写入用户态NVRM格式记录，只验证parser、
策略、workflow、Node Agent和通知链路，不证明物理NVLink故障。

```bash
python3.12 scripts/e2e/hyperpod/run_hyperpod_xid74_case.py \
  --case <operator_case> \
  --cluster-id <cluster-id> \
  --job-id <gpu-fault.io/job-id> \
  --node <kubernetes-node-name> \
  --pci-bdf <0000:bb:dd> \
  --report "artifacts/fault/<case>-$(date -u +%Y%m%dT%H%M%SZ).json"
```

支持流程case必须显式传`--allow-support`，并在要求投递时传
`--require-email-sent`；可能执行真实GPU reset的case必须传`--allow-reset`。

监控case不得创建workflow或改变Pod UID、attempt、taint和GPU annotation。reset case必须
验证旧Pod被替换、新attempt恢复、节点Ready且GPU/Fabric validation通过。任何case都必须
使用`SITE_FILE`声明的当前Profile及其实际capability，不得覆盖同版本Profile内容。

## 8. 故障注入方式总览

本章按信号进入系统的层次，列出当前仓库实际使用的每一种注入方式。它回答"这个case是怎么
制造故障的"，不替代第7章的逐case procedure，也不改变第2章的安全边界。代码依据只引用
文件与符号，不引用行号。

### 8.1 六类注入方式

| 类别 | 做法 | 覆盖的信号 |
|---|---|---|
| 伪造原始日志 | 特权Pod或probe向真实`/dev/kmsg`或Fabric Manager日志写一行NVIDIA格式记录 | 内核日志、FM日志，走完整采集到恢复的全链路 |
| 制造真实硬件或配置异常 | 在节点上改真实状态：压功率上限、解绑EFA驱动、篡改期望GPU数、影子`nvidia-smi`、占用GPU设备、停服务、带外重启 | DCGM指标、host telemetry、Node Agent检查、节点状态 |
| 向控制面API投递合成事件 | 用真实token调用collector-events、distributed XID、合成换节点接口，不碰宿主机 | 策略引擎与编排层，绕过采集层 |
| 破坏基础设施与网络 | iptables封443、删或滚动Pod、cordon驱逐、Aurora failover、密钥轮换、改Deployment环境变量 | 控制面高可用、executor协议、超时与恢复路径 |
| 在数据库里播种状态 | 注册`synthetic`集群并直接写remote command、卡死workflow、过期证据行 | dispatcher、命令协议、清理与对账逻辑，无真实节点 |
| 通知演练与进程内仿真 | 带`drill_id`的邮件；隔离进程内的假DCGM端点、假EFA计数目录、内存kmsg行 | 通知投递路径、collector解析逻辑，零副作用 |

第7.8节的结论不变：以上任何一种都不能让GPU硬件或driver真实产生指定XID。

### 8.2 共同前置条件

所有节点级注入都经`scripts/e2e/regional/host_probe_fixture.py::HostProbeFixture`
创建的特权Pod（privileged、hostPID、hostNetwork、hostPath根目录）进入宿主机，chroot到
节点当前签名槽位的venv执行probe子命令。凡是会改变节点状态的注入，都先用`systemd-run`
预排恢复定时器，再执行改动；Manifest形式的注入必须先给目标节点打
`gpu-fault.io/e2e-target-a=true`或`-b=true`标签，见
`scripts/e2e/regional/manifests/fault-injection/README.md`。

两个标记的语义不同，报告中不得混用：

- `synthetic`标记测试构造的对象或事件（`XidEvent`、`SxidEvent`、集群注册、合成换节点
  finding），控制面据此跳过过期合成集群、为合成换节点使用专用`policy_source`；
- `drill_id`从kmsg行文本解析，只影响通知投递：默认被
  `GPU_FAULT_NOTIFICATION_DELIVER_DRILLS`抑制并加`[DRILL:..]`主题标记，不改变隔离、
  reset、reboot等实际动作。

全仓库唯一的合成功能开关是`GPU_FAULT_ENABLE_SYNTHETIC_REPLACEMENT_TESTS`，且必须叠加
执行token。各CLI没有inject或simulate子命令，注入全部由e2e probe脚本或控制面路由完成。

### 8.9 维护规则

- 新增注入方式时先补本章表格，再补对应case的`injection`字段；两处描述必须一致。
- 只在专用probe子命令里实现注入，并带白名单、恢复定时器和状态快照；不得把注入写进
  部署清单或生产CLI。
- 会改变节点状态的注入，报告必须记录恢复定时器是否触发、节点是否回到基线。
