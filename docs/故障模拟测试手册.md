# GPU 故障模拟测试手册

## 1. 目标

测试体系使用 `testcases/fault-scenarios.yaml` 记录每个故障场景。每条 test case 必须包含：

- 唯一 ID、标题、分类和验证层级；
- 问题描述和故障注入方式；
- 可审计的预期结果；
- 风险等级；
- 自动化 pytest 入口或人工验收流程。

模拟事件不等同于真实硬件故障。报告必须区分以下验证层级：

| 层级 | 含义 |
|---|---|
| `component` | 使用真实策略、模型和 Store 接口的确定性组件测试 |
| `integration` | 通过 API、workflow、adapter 或持久 Store 的多模块测试 |
| `end-to-end` | 从事件输入到决策、workflow、通知或 Agent barrier 的闭环测试 |
| `staging` | 在隔离 HyperPod 测试集群执行的真实破坏性验收 |
| `live` | 在真实 SageMaker HyperPod 环境执行的人工验收，非破坏性或需维护窗口 |

区域 CPU 控制面与 GPU 集群数据面分离部署（`GPU_FAULT_DEPLOYMENT_MODE=regional`）
的完整验收用例集在 `docs/区域模式端到端验收测试用例.md`，ID 前缀为
`GF-REGIONAL-*`。这些用例验证的是真实环境中的进程边界、身份边界、网络边界
和爆炸半径——单进程 pytest 结构无法证明的部分，因此全部为 `automation: manual`。

## 2. 安全边界

默认 runner 只执行 `risk: non-destructive` 且 `automation: pytest` 的场景，不连接生产
Kubernetes，不调用 GPU reset、node reboot 或 node replacement。

真实集群非破坏性 case 也不会默认执行。必须使用 `--include-live` 并显式选择 case ID，
防止开发机回归测试意外连接当前 kube-context。

以下操作不能通过伪造 API 事件证明：

- 真实 GPU reset 后驱动和 CUDA context 是否恢复；
- HyperPod reboot 后实例 incarnation 和网络是否恢复；
- HyperPod replacement 后硬件、EFA 和 NVLink 是否通过验证。

这些场景记录为 `automation: manual`，只能在维护窗口和隔离测试节点执行。即使传入
`--include-manual`，runner 也只把它们记录为 `NOT_RUN`，不会执行破坏性命令。

`REPLACE_NODE` 有两条结构上完全不同的实现路径，风险等级必须分开标注，
一条的通过结果**不能**代表另一条：

| `risk` | 动作 | 节点来源 | provider API |
|---|---|---|---|
| `destructive` | `RESET_GPU`，经 Node Agent | — | 否 |
| `destructive-provider-reboot` | `NODE_REBOOT` | 原节点重启 | `batch_reboot_cluster_nodes` |
| `destructive-warm-spare` | `REPLACE_NODE`，`replacement_strategy=HEALTHY_WARM_SPARE_ONLY` | **只用客户自己提供并纳入监控的热备 GPU 节点**（标签 `gpu-fault.io/spare=true`） | **禁止调用 `BatchReplaceClusterNodes`** |
| `destructive-provider-replace` | `REPLACE_NODE`，HyperPod 主动替换 | provider 分配的新实例，旧实例被永久销毁 | `batch_replace_cluster_nodes` |

`destructive-warm-spare` 的验收必须包含一条否证断言：整个窗口内 CloudTrail 中
没有任何 `BatchReplaceClusterNodes` 或 `BatchDeleteClusterNodes` 调用，
且故障节点的 HyperPod / EC2 instance ID 与基线完全相同（节点未被销毁）。
热备池不足时必须失败并告警，绝不允许静默降级为 provider replace。

```bash
  --level end-to-end
```

执行指定 test case：

```bash
python3.12 tools/run_fault_test_cases.py \
  --case GF-RST-001 \
  --case GF-RST-002 \
  --report "artifacts/fault/restart-guard-$(date -u +%Y%m%dT%H%M%SZ).json"
```

```bash
make fault-test-cases
```

执行真实 HyperPod 集群的无 GPU 被动恢复闭环：

```bash
python3.12 tools/run_fault_test_cases.py \
  --case GF-LIVE-000 \
```

## 4. 报告内容

runner 对每个 case 单独启动 pytest，任何一个失败都会使最终进程返回非零。JSON 报告包含：

- 运行环境、生成时间和 catalog 路径；
- 每个 case 的问题、注入方式和预期结果；
- `PASS`、`FAIL` 或 `NOT_RUN`；
- pytest node ID、耗时及原始输出；
- XID kmsg replay case 的逐阶段 `processing_trace`；
- 汇总数量。

每个 XID 的 `processing_trace.stages` 固定记录：

1. 重放的原始 kmsg record 以及 priority、sequence、monotonic timestamp；
2. `KernelLogCollector` 的过滤、去重结果、目标 endpoint 和完整 payload；
3. kernel ingestion API 的 HTTP 结果；
4. `HyperPodHmaNormalizer` 产生的 provider signal 和 `XidEvent`；
5. 固定 NVIDIA Catalog 的版本、来源哈希和命中规则；
6. `GpuFaultPolicyEngine` 的 disposition、action、证据门禁、原因和 marker；
7. `IncidentOrchestrator` 产生的 incident、workflow 和通知 ID。

要求 trace 的 case 如果没有输出合法的结构化链路，即使 pytest 返回成功，runner 也会把
该 case 标记为 `FAIL`。

报告文件默认写入：

```text
artifacts/fault/fault-tests-<UTC timestamp>.json
```

CI 应将该 JSON 作为构建 artifact 保存，不应将临时报告提交为源代码。
GitHub Actions 中该 artifact 名为 `fault-test-report`，保留 30 天；runner
失败时也会通过 `if: always()` 上传，缺少报告文件会使上传步骤失败。
CI 为控制时长明确执行 `unit` 与 `component` 层级；本地
`make fault-test-cases` 仍执行全部默认非破坏性 pytest 用例。
需要长期保留的证据必须先脱敏，再在
`docs/evidence/fault/manifest.yaml` 登记，由
`scripts/build-fault-evidence-index.py` 生成带 SHA-256 的规范索引；不得直接把
runner 原始输出复制进交付文档目录。

## 5. Test Case 维护规则

1. 新增故障处理分支时，必须先增加或更新 catalog case。
2. `id` 发布后不得复用；语义变化较大时创建新 ID。
3. 自动化 case 必须引用真实存在且只验证一个明确场景的 pytest 函数。
4. `expected` 必须描述可观察结果，不能只写“系统正常”。
5. 缺少证据必须预期 `INCONCLUSIVE`、`BLOCKED` 或 `QUARANTINE`，不能预期成功。
6. 破坏性 case 必须记录维护窗口、隔离节点、回滚方式和操作证据。
7. 人工 case 的 `procedure` 必须指向真实存在的文档小节标题（锚点必须能命中）。
8. 人工 case 可以用可选字段 `related_pytest` 声明与之对应的自动化测试。
   这只是可追溯性索引，runner 不会执行它；写入的函数必须真实存在。
9. 分离部署的 case 必须断言"控制面没碰集群"：每个变更 step 的 `details`
   含 `mutation_submitted_by_control_plane: false`，且控制面 EKS 的节点状态
   逐字段比对结果为 `IDENTICAL`。
10. 引用清单、文档或代码行号的 case，行号必须是精确区间，
    不得写成 `~600` 这类近似值——近似行号在重构后无法判断是否失效。
11. 执行状态统一写入 `evidence.verdict`，只能是 `PASS`、`NOT_RUN`、
    `BLOCKED` 或 `SUPERSEDED`。已执行或阻塞的证据必须提供 ISO 格式
    `evidence.run_at`；`NOT_RUN`/`SUPERSEDED` 不得伪造执行时间。
    `SUPERSEDED` 必须同时提供指向另一条用例的 `superseded_by`；
    其他状态禁止携带该字段。
12. 断言"清单/文档缺少某项"的 case，判定步骤必须是**可机械执行的差集脚本**
    （例如把 `secretKeyRef` 清单与部署和运维手册创建的 key 做差集），
    不能只写"人工检查"。目视核对的用例在回归时必然退化。
13. 已知当前会失败的 case 必须在 `expected` 中写明**修复后的期望状态**，
    并在文档正文用"已知会失败的项"小节记录复核日期与确认结论。
    不允许把预期改成"失败"来让用例看起来通过。
14. 断言"两个集合必须一致/互为子集"的 case，必须先写清**集合的边界**：
    哪些成员由于架构原因永远不会出现在对侧。
    `GF-REGIONAL-BOOT-015` 原判据要求 profile 的全部 `OWN`/`DELEGATE` owner
    是 executor `execution_owners` 的子集，但 `gpu-fault-control-plane`
    等 owner 由控制面本地 adapter 执行（`src/gpu_fault/app/`），
    永不出现在 executor 侧——照该判据任何正确配置都会被判 `FAIL`。
    正确写法是先按 `GPU_FAULT_REMOTE_EXECUTION_OWNERS` 取交集再比较。
15. 读取"进程实际生效的配置"时，不得从环境开关反推，
    必须在目标 Pod 内构造对象读取其属性
    （如 `executor_from_environment().execution_owners`）。
    反推会漏掉 `*_OWNER` 一类的覆写，也观察不到构造期的一致性守卫。
    并且必须**逐副本**读取：`kubectl set env` 可能只应用到部分副本。
16. 非破坏性 case 不得为构造失效条件而修改数据面运行配置
    （关 adapter 开关、改 allow 列表等）。
    需要观察"某类记录被卡住"时，改为**直接向控制面注入一条指向
    不存在的 owner 和不存在的节点的记录**，并在同一用例内写明清理步骤。
    注入非终态记录时要特别注意：`cleanup_terminal_remote_commands`
    只删终态记录，非终态记录不清理就会一直触发告警。
17. 断言告警或通知的 case 必须先分清**本系统有两条互相独立的通知路径**，
    再判断待验证的信号属于哪一条。混淆这两条会得出错误结论。
    - **路径 A：管理员邮件（SES，与 Prometheus/AMP 完全无关）。**
      恢复动作**做完之后**由代码内部直接发信：
      `src/gpu_fault/adapters/hyperpod/notifications.py::HyperPodNotificationMixin._notify_node_restarted`
      `_notify_node_restarted` →
      `src/gpu_fault/notifications/restart_guard.py::RestartGuardEmailBuilder.build_node_restarted`
      `build_node_restarted` →
      `AdvisoryNotificationService.send` → `SesEmailNotifier`。
      同类还有 `build_gpu_reset_completed`、
      `build_fabric_manager_restarted`、`build_workload_restarted`、
      `build_budget_exhausted`、`build_gpu_count_change`，
      触发点是 `src/gpu_fault/app/` 里十余处 `alert_sender=
      context.advisory_notifications.send`。
      开关是 `GPU_FAULT_ALLOW_EMAIL` +
      `GPU_FAULT_NOTIFICATION_DISPATCHER_ENABLED`
      （`BOOT-013`/`BOOT-014` 验的就是这条）。
    - **路径 B：运维指标告警（`/metrics` → ADOT → AMP → SNS）。**
      只用于容量与健康度这类**连续量**：队列深度、Store I/O 饱和、
      p95 耗时、以及 `gpu_fault_remote_command_*`。
      区域控制面**有意不用** Prometheus Operator，
      所以 `deploy/control-plane/regional/processor-alerts.yaml`
      在这里是死配置，规则必须同时写进
      `deploy/observability/amp-rules.yaml`。
    - **判断依据是代码里有没有对应的发送点，不是"哪条更合适"。**
      例如 `notification_service.py:141-144`
      `dispatch_remote_completion` 第一行就是
      `if command.status is not RemoteCommandStatus.SUCCEEDED: return []`
      ——命令 `SUCCEEDED` 才发邮件。因此"命令永远停在 `PENDING`"
      这个失效模式**在路径 A 里结构上不可能触发**，
      当前只能由路径 B 覆盖。反过来，"节点已重启完成"
      属于路径 A，不要去 AMP 里找。
    路径 B 的告警必须逐层验证，任一层断掉都不会触发：
    1. 指标被 `/metrics` 导出；
    2. 指标在 ADOT collector 的 `metric_relabel_configs` keep
       白名单内（不在则采集侧即被丢弃，规则永远 `absent`）；
    3. 规则存在于真正生效的规则文件，且已 `put` 到 AMP
       （用 `aws amp describe-rule-groups-namespace` 看**实际加载**的，
       不要只看仓库文件）；
    4. 用 SigV4 把 expr **逐字**提交给 AMP 求值返回非空向量；
    5. 过 `for` 窗口后 `GET /api/v1/alerts` 状态为 `firing`；
    6. 清除注入条件后告警自动 resolve。
    只完成到第 1 步就写"已验证告警链路"是错误结论——
    `GF-REGIONAL-BOOT-015` 在 2026-07-31 就是这样把半个修复
    记成"已落地"的。做不到第 5 步时必须写入 `validation_limitations`。
    - **第 0 步：先确认路径 B 在被测环境是否启用。**
      截至 2026-08-18，仓库清单
      `deploy/observability/adot-control-plane.yaml` 默认
      `replicas: 1`，`install-amp-monitoring.sh` 也默认启用 ADOT；
      但运行环境仍可能被操作员显式缩容到 0。0 副本时上面六层从
      第 2 层起全断，路径 B 的告警一律不触发。所以断言路径 B
      之前仍必须先读
      `kubectl -n gpu-fault-system get deploy gpu-fault-adot
      -o jsonpath='{.spec.replicas}'`；为 0 就直接判定
      "本环境路径 B 未启用"并写入 `validation_limitations`，
      **不要**为跑通用例临时改变副本数（那是改变被测部署形态）。
      路径 A 不受影响，照常验证。
17. 判断"某个 K8s 对象是残留还是在用"时，不得只看 Pod 是否存在。
    副本数为 0 的 Deployment 仍然是**有效引用**：它引用的 ConfigMap
    不能删，且它随时可能被扩容。当前设计里
    `gpu-fault-cluster-executor` 只跑在 GPU 集群，
    CPU 控制面侧那个 0 副本同名对象是早期试验残留，
    **保持 0 副本**即可，不要扩容也不要连带删除它引用的 wheel。
    同理，回收类脚本必须把 `ReplicaSet` 也算作引用方，
    否则 `kubectl rollout undo` 会因回滚目标的 wheel 已被删而失效。

## 6. 公开覆盖范围

本公开手册只描述可重复执行的测试入口、安全边界和判定方法，不记录具体客户环境、
集群名称、节点 ID、release digest 或某一次运行的 PASS/FAIL。真实执行结果由 CI artifact
或私有证据库按 test case ID 保存。

当前公开测试目录覆盖：

- NVIDIA XID Catalog 逐项 kmsg 格式重放、XID 154、companion XID 和 NVLink5 decode；
- fatal/non-fatal SXID、access/trunk 故障域和产品代际门禁；
- DCGM、GPU inventory、host、EFA/RDMA、训练进度和日志 Collector；
- training terminal、allocation、restart budget、幂等和代际 fencing；
- 区域启动守卫、鉴权、隔离、remote command、HA、容量、通知和最小权限；
- reset、reboot、warm spare 等必须人工批准的破坏性验收。

机器可读的用例、风险等级和自动化入口以 `testcases/fault-scenarios.yaml` 为准。
公开文档不得从内部执行记录反推当前状态。

## 7. 真实 XID 验证分级

### 7.1 kmsg 格式重放

`GF-XID-KMSG-001` 至 `GF-XID-KMSG-172` 分别使用 NVIDIA driver 实际输出格式。
NVIDIA 官方材料中存在以下两种 PCI BDF 写法，解析器必须同时支持：

```text
NVRM: Xid (0000:03:00): 14, Channel 00000001
NVRM: Xid (PCI:0000:34:00): 45, Ch 00000010
```

第一种来自 NVIDIA《XID Errors》的 “Working with Xid Errors”，第二种来自
NVIDIA Fabric Manager User Guide 的 “Runtime NVSwitch and GPU Errors”。
逗号后的内容是 XID 特定的原始错误信息，不要求固定为 `pid/name`。
例如 XID 94：

```text
3,99,1100,-;NVRM: Xid (PCI:0000:b9:00): 94
```

每个 case 都把 record 作为内存输入先交给 `KernelLogCollector`，再进入
`/v1/collector-events/nvidia-kernel`，最终由 kernel normalizer 和 XID policy 处理。
它覆盖 kmsg record 解析、PCI BDF 解析、boot ID、monotonic timestamp、evidence
reference、API、Catalog 匹配和策略分支，但不会写入 `/dev/kmsg`，也不会改变 GPU
硬件状态。

XID 45、48、144–150、154 和 159 具有特殊工作流断言。仅靠 kmsg 基础行无法提供
NVLink 寄存器、XID 154 动态动作或 UVM 使用情况时，测试要求策略返回
`BLOCKED_MISSING_EVIDENCE` 或需要管理员处理，不能自行推断恢复动作。

`GF-XID-KMSG-B200-001` 至 `GF-XID-KMSG-B200-172` 使用相同链路并明确设置
`product=B200`。当前 Catalog 使用 B100 产品家族列，代码将 B200 映射到该家族：
包含 B100 的规则必须适用；仅属于 A/H/GB 或没有产品范围的规则必须返回
`NOT_APPLICABLE`，并产生固定模板通知。

不要把重放 record 写入生产节点真实 `/dev/kmsg`。这样会污染内核证据，并可能让 active
控制面执行真实恢复动作。自动化测试使用内存输入和隔离 ASGI 控制面。

执行：

```bash
python3.12 tools/run_fault_test_cases.py \
  --case GF-XID-KMSG-094 \
  --report "artifacts/fault/xid-kmsg-094-$(date -u +%Y%m%dT%H%M%SZ).json"
```

执行全部 172 个独立 case，并为每个 XID 生成单独结果：

```bash
python3.12 tools/run_fault_test_cases.py \
  --category xid-kmsg-replay \
  --report "artifacts/fault/xid-kmsg-all-$(date -u +%Y%m%dT%H%M%SZ).json"
```

执行全部 B200 case：

```bash
python3.12 tools/run_fault_test_cases.py \
  --category xid-kmsg-replay-b200 \
  --report "artifacts/fault/xid-kmsg-b200-all-$(date -u +%Y%m%dT%H%M%SZ).json"
```

也可以直接运行某个 pytest case：

```bash
python3.12 -m pytest -q \
  'tests/collectors/test_xid_kmsg_catalog_replay.py::test_xid_kmsg_catalog_replay[GF-XID-KMSG-094]'
```

### 7.2 HyperPod 三节点 XID 11 重启

`GF-LIVE-XID11-001` 使用
`tests/manifests/training/xid11-three-node-pytorchjob.yaml` 创建一个 Master 和两个
Worker。每个 Pod 请求 8 张 GPU 和 16 个 EFA 设备，并通过 NCCL
Libfabric/GDRDMA 持续执行 24-rank `all_reduce`。

使用 `gpu-training-submit` 提交独立 job/attempt，并设置 restart budget：

```bash
gpu-training-submit \
  tests/manifests/training/xid11-three-node-pytorchjob.yaml \
  --job-id <unique-job-id> \
  --attempt-id <unique-job-id>-a001 \
  --runtime-profile-version hyperpod-control-plane-recovery-v1 \
  --restart-budget 1
```

必须先确认三个 Pod 分布在不同节点、NCCL heartbeat 成功，并且控制面的 source
attempt observation 包含 24 个唯一 GPU UUID。然后只向

### 7.4 真实 /dev/kmsg 用户态写入

`GF-LIVE-KMSG-XID11-001` 只允许在没有运行中 managed workload、HyperPod
`NodeRecovery=None`、节点处于 `Ready` 且控制面恢复门禁已确认的维护窗口执行。该测试会
污染宿主机 kernel log，风险高于 FIFO 重放，不得由自动化 runner 执行。

写入前必须记录 Kernel Collector PID、`NRestarts`、boot ID，并确认其某个文件描述符指向
`/dev/kmsg`。同时记录 `/v1/collector-status/{cluster_id}` 和
`/v1/evidence/{cluster_id}` 的基线。

使用标准 NVRM 格式执行一次写入，不向消息增加 `test_id` 或其他测试字段：

```bash

```

Collector 返回的 `source_boot_id`、`kernel_sequence`、`source_monotonic_us` 和
`observed_at` 确认新增记录；这些字段由真实 `/dev/kmsg` 读取结果产生，不依赖消息中的
测试标记。

1. `collector=NVIDIA_KERNEL`、`sample_count=1` 且 `errors=[]`；

3. `record_id`、`source_boot_id`、kernel sequence 和 monotonic timestamp 来自
   Collector 读取结果，而不是测试请求构造；
4. H200 XID 11 映射到 `RESTART_APP`；
5. 无 workload 时没有执行 workload restart、GPU reset、node reboot 或 replacement；
6. 节点最终保持 `Ready`，无遗留 unschedulable 或 `gpu-fault.io` taint。

该测试能够证明生产 Collector 读取了真实 `/dev/kmsg`，但记录仍由用户态伪造，不能证明
NVIDIA driver 或 GPU 硬件真实产生了 XID。结果记录在
`docs/evidence/fault/hyperpod-dev-kmsg-xid11-20260722.json`。

### 7.7.1 三节点 GPU 训练的三并发聚合与 reset

- 故障前 Master、Worker 0、Worker 1 的 node-local rank 必须持续输出

budget。workload observation 必须使用三个实际 Pod UID、node ID，以及从各 Pod
`nvidia-smi --query-gpu=uuid` 读取的 24 个唯一 GPU UUID。禁止伪造 allocation，也禁止

1. `/v1/workload-observations`；
2. `/v1/gpu-events/xid`，XID 95，目标为实际参与训练的一个 GPU UUID；
3. `/v1/gpu-events/sxid`，trusted `ACCESS` SXID 11001，参与 GPU 至少包含同一目标。

1. 三请求都返回 HTTP 200，processor 无 deadline exceeded。

   incident 和一个 workflow。

### 7.8 驱动真实产生 XID

`GF-LIVE-004` 要求 XID 由 NVIDIA driver 写入真实 `/dev/kmsg`。这类测试没有通用且安全
的软件模拟方法：

- CUDA illegal access 可能只终止进程，不保证产生指定 XID；
- XID 79 等错误通常涉及 PCIe、GPU 掉卡或硬件状态破坏；
- 直接伪造 kernel line 不能证明驱动和硬件检测链路。

因此只能在隔离 staging 节点、无训练 workload、维护窗口和厂商批准的 fault injection
方法下执行。执行前必须关闭自动 provider mutation，先以观察模式确认 XID、PCI BDF 和
GPU UUID，再逐步开放对应恢复动作。该 case 不由 runner 自动执行。

### 7.9 重启 attempt 代际时间栅栏

`GF-ATTEMPT-GENERATION-FENCE-*` 用例组验证延迟到达的 XID/SXID 不会对已经由恢复
workflow 启动的新 attempt 重复执行破坏性动作。测试使用两节点受管分布式训练任务，
先完成一次包含 `RESTART_WORKLOAD` 的恢复并记录：

- 原 incident/workflow、official action 和动作等级；
- `RESTART_WORKLOAD` execution detail 中的 `restart_attempt_id`；
- 新 attempt 两个 Pod 的 `status.startTime` 和 Completion Watcher 上报的
  `AttemptObservation.started_at`；
- 重放前 workflow、incident、训练 Pod UID 和 NCCL heartbeat。

旧事件必须使用新的 `event_id`，`observed_at/collected_at` 使用当前重放时间，
`source_event_time` 使用新 attempt 启动前的原故障时间。它是延迟日志重放，不得描述为
硬件新产生的故障。

需要执行以下独立 test case：

1. `GF-ATTEMPT-GENERATION-FENCE-XID-EQUAL-001`：重放同级 XID，event 链接到原
   incident，reason 包含事件和 attempt 启动时间；workflow 数量、ID、状态和 step
   execution 不变。
2. `GF-ATTEMPT-GENERATION-FENCE-SXID-WEAKER-001`：重放较低级 SXID，验收条件
   同上，不得 reset GPU/NVSwitch、reboot node 或再次重启训练。
3. `GF-ATTEMPT-GENERATION-FENCE-UPGRADE-001`：重放严格更高级 action，只创建一个
   successor，`predecessor_workflow_id` 指向当前恢复 workflow；predecessor 非终态时
   successor 不得并发执行。
4. `GF-ATTEMPT-GENERATION-FENCE-FRESH-001`：事件时间晚于新 attempt 启动时间，
   正常进入现有策略和 workflow。
5. `GF-ATTEMPT-GENERATION-FENCE-NO-START-001`：删除可信 `started_at` 后重放旧
   事件，必须保持 fail-safe，不得按时间静默忽略。
6. `GF-ATTEMPT-GENERATION-FENCE-SOURCE-CLOCK-001`：令 `source_event_time` 早于
   attempt 启动、`observed_at/collected_at` 晚于启动，必须按 `source_event_time`
   判为旧 generation。
7. `GF-ATTEMPT-GENERATION-FENCE-ACTIVE-PREDECESSOR-001`：上一轮节点独占
   workflow 保持 `RUNNING`，新 attempt 启动后注入新的 fatal trunk SXID。必须创建
   不同 incident 和 workflow，保留 `RESET_ALL_GPUS_NVSWITCHES`，并令
   `predecessor_workflow_id` 指向上一轮 workflow。
8. `GF-ATTEMPT-GENERATION-FENCE-NONEXCLUSIVE-001`：上一轮节点 reboot workflow
   保持 `RUNNING`，当前 attempt 注入只需 workload restart 的 XID 11。该故障必须创建
   独立 incident/workflow，不继承 `RESTART_NODE`，也不能被误判为 stale。只有声明
   节点独占操作的 successor 才需要 predecessor 串行化。

报告必须记录 API decision、incident reason、predecessor/successor、动作等级、所有
时间戳、训练新 attempt 和 heartbeat，并明确区分单元测试、用户态日志重放和硬件真实
故障。测试后确认训练任务无额外 restart budget 消耗，节点无新增 taint/annotation。

```bash

  --case <operator_case> \
  --cluster-id <cluster-id> \
  --job-id <gpu-fault.io/job-id> \
  --node <kubernetes-node-name> \
  --pci-bdf <0000:bb:dd> \
  --report "artifacts/fault/<case>-$(date -u +%Y%m%dT%H%M%SZ).json"
```

`all-zero`、`secondary-only`、`unexpected-production`、`fabric-reset`、
`unknown-register` 和 `marginal-channel` 会进入支持流程，必须额外传
`--allow-support --require-email-sent`。所有会执行真实 GPU reset 的 case 还必须显式
传 `--allow-reset`；因此 `marginal-channel` 同时需要 `--allow-support` 和
`--allow-reset`。`safe-only`、`corrected-only` 和
`ecc-parity` 是监控用例，不得创建 workflow，目标节点、taint、GPU fault annotation、
Pod UID 和 attempt ID 必须完全不变。

当前 reset-first 用例为：

- `mechanical-first`：register1 bit 8 第一次即执行隔离、quiesce、无客户端校验和
  `RESET_GPU`；首次不运行 Field Diagnostic 或直接 support。
- `report-if-repeated`：同 Link register1 bit 27 第二次时执行诊断包、
  `RUN_NVLINK74_WORKFLOW` 和 `RESET_GPU`。
- `ecc-third`：同 Link register1 bit 4 前两次只监控，第三次执行诊断和 reset。

上述 reset 用例必须传 `--allow-reset`，不得传 `--require-email-sent`。成功标准是旧
训练 Pod UID 全部被替换、新 attempt 正常运行、目标节点最终 Ready 且可调度、
GPU/Fabric validation 通过。
`marginal-channel` 是例外：它在诊断和 reset 后保持目标节点 quarantine，同时完成固定
support 通知，workload 必须在健康容量上恢复。

真机执行前必须确认 `NodeRecovery=None`、checkpoint/restart budget、Node Agent
generation、GPU reset allowlist、Field Diagnostic 命令及 SHA-256、SES smoke 和回滚
窗口。工具报告中的 `test_case_id` 必须与 catalog ID 完全一致；历史
`REPEATEDBIT-SUPPORT` 和 `ECC-THIRD-SUPPORT` 已被 reset-first 用例取代，不得继续按旧
口径验收。
